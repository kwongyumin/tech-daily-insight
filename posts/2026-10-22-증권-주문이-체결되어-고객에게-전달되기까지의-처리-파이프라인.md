# 증권 주문이 체결되어 고객에게 전달되기까지의 처리 파이프라인

## 개요

주식 매수 버튼을 누르고 "체결되었습니다"라는 알림을 받기까지, 사용자 눈에는 단 몇 초처럼 보이는 그 순간 뒤에는 복잡한 분산 시스템 파이프라인이 동작하고 있다. 증권 시스템은 금융 도메인 특성상 **정확성(Correctness)**, **내구성(Durability)**, **실시간성(Real-time)** 이 세 가지를 동시에 충족해야 한다는 점에서 설계 난이도가 매우 높다.

이 글에서는 주문 접수부터 체결 결과가 고객에게 전달되기까지의 전체 처리 파이프라인을 아키텍처 관점에서 살펴보고, 각 구간에서 발생하는 실무적 고민과 트레이드오프를 짚어본다.

---

## 핵심 개념: 파이프라인 전체 흐름

전체 흐름은 크게 다섯 단계로 구분할 수 있다.

```
[클라이언트]
    │  REST/WebSocket
    ▼
[주문 접수 서비스 (Order Gateway)]
    │  메시지 큐 (Kafka)
    ▼
[주문 검증 및 라우팅 서비스]
    │  FIX Protocol / 내부 프로토콜
    ▼
[거래소 연계 / 체결 엔진]
    │  체결 결과 수신
    ▼
[체결 처리 서비스 (Execution Processor)]
    │  이벤트 발행 (Kafka)
    ▼
[알림/포지션 서비스 → 클라이언트]
```

각 단계는 독립적으로 장애가 격리되어야 하며, 메시지 유실이 없어야 한다. 아래에서 각 구간을 상세히 살펴보자.

## 핵심 개념: 각 구간별 역할과 설계 포인트

### 1. 주문 접수 서비스 (Order Gateway)

클라이언트로부터 주문을 받는 진입점이다. 여기서 중요한 것은 **멱등성(Idempotency)** 보장이다. 네트워크 재시도로 인해 동일한 주문이 두 번 접수되어서는 안 된다.

```java
@RestController
@RequiredArgsConstructor
public class OrderController {

    private final OrderService orderService;

    @PostMapping("/api/v1/orders")
    public ResponseEntity<OrderResponse> placeOrder(
            @RequestHeader("X-Idempotency-Key") String idempotencyKey,
            @RequestBody @Valid OrderRequest request,
            @AuthenticationPrincipal UserPrincipal user) {

        // 중복 요청 차단: Redis에서 idempotency key 확인
        OrderResponse response = orderService.placeOrder(idempotencyKey, request, user.getId());
        return ResponseEntity.ok(response);
    }
}

@Service
@RequiredArgsConstructor
public class OrderService {

    private final RedisTemplate<String, String> redisTemplate;
    private final KafkaTemplate<String, OrderEvent> kafkaTemplate;
    private final OrderRepository orderRepository;

    @Transactional
    public OrderResponse placeOrder(String idempotencyKey, OrderRequest request, Long userId) {
        String redisKey = "order:idem:" + idempotencyKey;

        // SET NX EX 로 원자적 중복 체크
        Boolean isNew = redisTemplate.opsForValue()
                .setIfAbsent(redisKey, "1", Duration.ofMinutes(10));

        if (Boolean.FALSE.equals(isNew)) {
            throw new DuplicateOrderException("이미 처리된 주문입니다: " + idempotencyKey);
        }

        Order order = Order.builder()
                .userId(userId)
                .symbol(request.getSymbol())
                .side(request.getSide())
                .quantity(request.getQuantity())
                .price(request.getPrice())
                .status(OrderStatus.PENDING)
                .idempotencyKey(idempotencyKey)
                .build();

        orderRepository.save(order);

        // DB 저장 후 Kafka 발행 (Transactional Outbox 패턴 권장)
        kafkaTemplate.send("order.submitted", order.getId().toString(),
                OrderEvent.from(order));

        return OrderResponse.from(order);
    }
}
```

> **Transactional Outbox 패턴**: DB 저장과 Kafka 발행을 단일 트랜잭션으로 묶으면 Kafka 브로커 장애 시 DB만 커밋되는 문제가 생긴다. Outbox 테이블에 이벤트를 함께 저장하고, 별도 폴링 프로세스(Debezium CDC 등)가 Kafka로 릴레이하는 구조가 안전하다.

### 2. 주문 검증 및 라우팅 서비스

주문 수량, 잔고, 종목 거래 가능 여부 등을 검증하고 거래소로 라우팅한다. 이 구간에서는 **동시성 제어**가 핵심이다. 동일 계좌에서 여러 주문이 동시에 들어올 때 잔고를 초과하는 주문이 통과되어서는 안 된다.

```java
@Service
@RequiredArgsConstructor
public class OrderValidationService {

    private final AccountRepository accountRepository;
    private final RedissonClient redissonClient;

    public void validateAndReserve(Order order) {
        // 계좌 단위 분산 락
        RLock lock = redissonClient.getLock("account:lock:" + order.getUserId());

        try {
            boolean acquired = lock.tryLock(3, 1, TimeUnit.SECONDS);
            if (!acquired) {
                throw new OrderValidationException("잠시 후 다시 시도해주세요.");
            }

            Account account = accountRepository.findByUserId(order.getUserId())
                    .orElseThrow(() -> new AccountNotFoundException(order.getUserId()));

            BigDecimal requiredAmount = order.getPrice()
                    .multiply(BigDecimal.valueOf(order.getQuantity()));

            if (account.getAvailableBalance().compareTo(requiredAmount) < 0) {
                throw new InsufficientBalanceException("잔고 부족");
            }

            // 가용 잔고 선차감 (주문 취소 시 복원)
            account.reserveBalance(requiredAmount);
            accountRepository.save(account);

        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new OrderValidationException("검증 중 인터럽트 발생");
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```

### 3. 거래소 연계 및 체결 결과 수신

실제 거래소와의 통신은 **FIX(Financial Information eXchange) 프로토콜**을 사용하는 경우가 많다. 체결 결과는 비동기로 수신되며, 이를 내부 이벤트로 변환해야 한다.

```java
@Component
@Slf4j
public class ExchangeExecutionListener implements ExecutionReportListener {

    private final KafkaTemplate<String, ExecutionEvent> kafkaTemplate;

    @Override
    public void onExecutionReport(ExecutionReport report) {
        if (report.getExecType() == ExecType.TRADE) {
            ExecutionEvent event = ExecutionEvent.builder()
                    .orderId(report.getClOrdId())
                    .executedQuantity(report.getLastQty())
                    .executedPrice(report.getLastPx())
                    .executionTime(report.getTransactTime())
                    .exchangeOrderId(report.getOrderId())
                    .build();

            // 파티션 키를 orderId로 설정해 순서 보장
            kafkaTemplate.send("execution.received",
                    event.getOrderId(), event);

            log.info("체결 수신: orderId={}, qty={}, price={}",
                    event.getOrderId(), event.getExecutedQuantity(), event.getExecutedPrice());
        }
    }
}
```

### 4. 체결 처리 서비스 (Execution Processor)

체결 이벤트를 소비하여 주문 상태를 갱신하고, 포지션과 잔고를 확정한다.

```java
@Service
@RequiredArgsConstructor
@Slf4j
public class ExecutionProcessor {

    private final OrderRepository orderRepository;
    private final PositionService positionService;
    private final AccountService accountService;
    private final KafkaTemplate<String, NotificationEvent> notificationKafka;

    @KafkaListener(
            topics = "execution.received",
            groupId = "execution-processor",
            containerFactory = "executionKafkaListenerContainerFactory"
    )
    @Transactional
    public void process(ExecutionEvent event) {
        Order order = orderRepository.findById(event.getOrderId())
                .orElseThrow(() -> new OrderNotFoundException(event.getOrderId()));

        // 멱등성: 이미 처리된 체결인지 확인
        if (order.isAlreadyProcessed(event.getExecutionTime())) {
            log.warn("중복 체결 이벤트 무시: orderId={}", event.getOrderId());
            return;
        }

        // 주문 상태 업데이트
        order.applyExecution(event.getExecutedQuantity(), event.getExecutedPrice());
        orderRepository.save(order);

        // 포지션 업데이트
        positionService.updatePosition(order.getUserId(), order.getSymbol(),
                order.getSide(), event.getExecutedQuantity(), event.getExecutedPrice());

        // 잔고 확정 (선차감된 예약금 → 실제 차감)
        accountService.confirmExecution(order.getUserId(),
                event.getExecutedQuantity(), event.getExecutedPrice());

        // 알림 이벤트 발행
        notificationKafka.send("notification.execution",
                order.getUserId().toString(),
                NotificationEvent.ofExecution(order, event));
    }
}
```

### 5. 알림 서비스: 고객에게 전달

체결 결과를 고객에게 전달하는 채널은 **WebSocket(실시간)**, **Push Notification**, **SMS/이메일** 등 복합적으로 운영된다.

```java
@Component
@RequiredArgsConstructor
@Slf4j
public class NotificationConsumer {

    private final SimpMessagingTemplate webSocketTemplate;
    private final PushNotificationService pushService;

    @KafkaListener(topics = "notification.execution", groupId = "notification-service")
    public void sendNotification(NotificationEvent event) {
        // WebSocket 연결 중인 사용자에게 즉시 전송
        String destination = "/queue/execution/" + event.getUserId();
        webSocketTemplate.convertAndSend(destination, ExecutionMessage.from(event));

        // 앱 푸시 (WebSocket 미연결 사용자 대비)
        pushService.sendAsync(event.getUserId(), buildPushPayload(event));

        log.info("체결 알림 전송 완료: userId={}, orderId={}",
                event.getUserId(), event.getOrderId());
    }

    private PushPayload buildPushPayload(NotificationEvent event) {
        return PushPayload.builder()
                .title("주문 체결")
                .body(String.format("%s %s주 %.0f원에 체결",
                        event.getSymbol(),
                        event.getExecutedQuantity(),
                        event.getExecutedPrice()))
                .data(Map.of("orderId", event.getOrderId(), "type", "EXECUTION"))
                .build();
    }
}
```

## 주의사항 및 트레이드오프

### ① 정확히-한-번(Exactly-Once) vs 최소-한-번(At-Least-Once)

Kafka의 기본 소비 보장은 **At-Least-Once**다. 체결 처리에서 멱등성을 반드시 구현해야 하는 이유다. Kafka Transactions로 Exactly-Once를 구현할 수 있지만, 처리량이 감소하고 운영 복잡도가 높아진다. 대부분의 시스템에서는 **At-Least-Once + 소비자 측 멱등성** 조합이 실용적이다.

### ② 파티션 수와 처리 순서

Kafka 파티션 키를 `orderId`로 설정하면 동일 주문의 이벤트 순서가 보장된다. 하지만 `userId`로 설정하면 한 사용자의 여러 주문 간 순서도 보장할 수 있다. **어느 수준까지 순서를 보장해야 하는지**는 비즈니스 요구사항에 따라 결정해야 하며, 파티션 수가 많아질수록 순서 보장 범위는 좁아진다.

### ③ 잔고 선차감과 롤백

주문 검증 시 가용 잔고를 선차감하는 방식은 과다 주문을 방지하지만, 체결 실패나 주문 취소 시 **보상 트랜잭션(Compensating Transaction)**으로 복원해야 한다. Saga 패턴을 활용하면 분산 환경에서 이 흐름을 체계적으로 관리할 수 있다.

### ④ WebSocket 세션과 스케일아웃

WebSocket은 특정 서버 인스턴스에 연결이 고정되기 때문에, 수평 확장 시 다른 인스턴스에서 발행한 메시지를 전달하지 못하는 문제가 생긴다. Redis Pub/Sub 또는 Spring의 `MessageBrokerRegistry`와 외부 STOMP 브로커(RabbitMQ 등)를 조합해 해결할 수 있다.

### ⑤ 지연 vs 안전성

거래소와의 통신 실패 시 재시도 로직이 필요하다. 하지만 **멱등하지 않은 주문 요청을 재시도하면** 중복 주문이 발생할 수 있다. FIX 프로토콜의 `ClOrdID`처럼 거래소 측에서도 멱등 키를 지원하는지 반드시 확인해야 한다.

## 정리

증권 주문 처리 파이프라인은 단순한 CRUD가 아니라, 금융 도메인의 정합성 요구사항이 분산 시스템의 복잡성과 맞닿는 지점이다. 핵심을 정리하면 다음과 같다.

| 구간 | 핵심 설계 포인트 |
|------|----------------|
| 주문 접수 | 멱등성 키 + Transactional Outbox |
| 주문 검증 | 분산 락 + 잔고 선차감 |
| 거래소 연계 | FIX 프로토콜 + 비동기 수신 |
| 체결 처리 | At-Least-Once + 소비자 멱등성 + Saga |
| 알림 전달 | WebSocket + 외부 브로커 + Fallback Push |

각 컴포넌트를 독립적으로 장애 격리하고, 이벤트 기반으로 느슨하게 결합하며, 모든 상태 변경에 멱등성을 보장하는 것이 안정적인 파이프라인의 기반이다. 금융 시스템이라고 특별한 마법이 있는 것이 아니다. **분산 시스템의 기본 원칙을 얼마나 철저하게 지키느냐**가 결국 신뢰성을 결정한다.
