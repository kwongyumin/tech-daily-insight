# Docker 멀티스테이지 빌드로 이미지 사이즈 최적화

## 개요

프로덕션 환경에서 Docker 이미지 크기는 단순한 저장 공간의 문제가 아니다. CI/CD 파이프라인의 속도, 컨테이너 시작 시간, 보안 취약점 노출 범위, 그리고 클라우드 비용에 직결되는 중요한 지표다.

흔히 겪는 상황을 떠올려보자. Spring Boot 애플리케이션을 처음 컨테이너화할 때 아무 생각 없이 `openjdk:17` 베이스 이미지를 사용하고, 빌드 도구와 소스코드를 그대로 이미지에 포함시키면 손쉽게 **1GB를 넘기는 이미지**가 탄생한다. 실제로 실행에 필요한 것은 컴파일된 JAR 파일 하나뿐인데도 말이다.

Docker **멀티스테이지 빌드(Multi-stage Build)** 는 이 문제를 우아하게 해결한다. 빌드 환경과 런타임 환경을 명확히 분리하여, 최종 이미지에는 애플리케이션 실행에 필요한 최소한의 파일만 포함시키는 방법론이다. 이 글에서는 개념부터 실전 적용, 그리고 주의해야 할 트레이드오프까지 실무 관점에서 깊이 있게 다룬다.

## 핵심 개념

### 멀티스테이지 빌드란?

Docker 17.05 버전부터 도입된 기능으로, 하나의 `Dockerfile` 안에서 **여러 개의 `FROM` 명령어**를 사용해 빌드 스테이지를 정의할 수 있다. 각 스테이지는 독립된 환경을 가지며, 이전 스테이지에서 생성된 **특정 파일만 선택적으로 복사**할 수 있다.

```
빌드 스테이지 (builder)          런타임 스테이지 (runtime)
┌─────────────────────┐          ┌─────────────────────┐
│ JDK + Maven         │          │ JRE (slim)          │
│ 소스코드            │  COPY    │ app.jar             │
│ 의존성 캐시         │ ──────►  │                     │
│ 테스트 클래스       │          │                     │
│ 빌드 산출물(jar)    │          │                     │
│ ~800MB              │          │ ~180MB              │
└─────────────────────┘          └─────────────────────┘
```

핵심은 최종 이미지에는 마지막 스테이지의 내용만 포함된다는 점이다. 빌드 스테이지에서 설치한 컴파일러, 빌드 도구, 임시 파일들은 흔적도 남지 않는다.

### 레이어 캐시 전략과의 조합

멀티스테이지 빌드의 효과를 극대화하려면 **레이어 캐시 전략**을 함께 이해해야 한다. 변경 빈도가 낮은 레이어(의존성)를 먼저 복사하고, 변경 빈도가 높은 레이어(소스코드)를 나중에 복사하면 빌드 시간을 대폭 단축할 수 있다.

## 실전 예제

### 예제 1: Spring Boot 애플리케이션 최적화

**Before: 나이브한 단일 스테이지 Dockerfile**

```dockerfile
FROM openjdk:17-jdk
WORKDIR /app
COPY . .
RUN ./mvnw clean package -DskipTests
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "target/app.jar"]
```

이 방식의 문제점:
- 전체 JDK, Maven 래퍼, 소스코드가 모두 최종 이미지에 포함
- 소스코드 한 줄만 바꿔도 의존성 다운로드부터 다시 시작
- 이미지 크기: 약 **900MB ~ 1.2GB**

**After: 멀티스테이지 빌드 적용**

```dockerfile
# ─── Stage 1: 의존성 다운로드 (캐시 최적화) ───────────────────
FROM maven:3.9.6-eclipse-temurin-17-alpine AS dependency-cache
WORKDIR /build
# pom.xml만 먼저 복사하여 의존성 레이어를 별도 캐시
COPY pom.xml .
RUN mvn dependency:go-offline -B

# ─── Stage 2: 빌드 ──────────────────────────────────────────────
FROM dependency-cache AS builder
WORKDIR /build
# 소스코드는 나중에 복사 (캐시 무효화 최소화)
COPY src ./src
RUN mvn clean package -DskipTests -B

# ─── Stage 3: 런타임 ────────────────────────────────────────────
FROM eclipse-temurin:17-jre-alpine AS runtime

# 보안: non-root 사용자 생성
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

WORKDIR /app

# 빌드 스테이지에서 JAR만 선택적으로 복사
COPY --from=builder /build/target/*.jar app.jar

# Spring Boot Layered JAR 활용 (선택사항)
RUN java -Djarmode=layertools -jar app.jar extract

USER appuser
EXPOSE 8080

ENTRYPOINT ["java", \
  "-XX:+UseContainerSupport", \
  "-XX:MaxRAMPercentage=75.0", \
  "-jar", "app.jar"]
```

이미지 크기 비교:
| 방식 | 이미지 크기 |
|---|---|
| 단일 스테이지 (openjdk:17-jdk) | ~1.1 GB |
| 멀티스테이지 (jre-alpine) | ~185 MB |
| 멀티스테이지 + Layered JAR | ~180 MB |

### 예제 2: Node.js 프론트엔드 빌드 + Nginx 서빙

프론트엔드 빌드도 전형적인 멀티스테이지 사용 사례다.

```dockerfile
# ─── Stage 1: 의존성 설치 ───────────────────────────────────────
FROM node:20-alpine AS deps
WORKDIR /app
# package-lock.json을 활용해 결정론적 설치
COPY package.json package-lock.json ./
RUN npm ci --only=production=false

# ─── Stage 2: 빌드 ──────────────────────────────────────────────
FROM deps AS builder
WORKDIR /app
COPY . .
# 환경변수는 빌드 ARG로 주입
ARG REACT_APP_API_URL
ENV REACT_APP_API_URL=$REACT_APP_API_URL
RUN npm run build

# ─── Stage 3: 프로덕션 서빙 ─────────────────────────────────────
FROM nginx:1.25-alpine AS runtime
# 커스텀 nginx 설정 (SPA 라우팅, gzip, 캐시 헤더 포함)
COPY nginx.conf /etc/nginx/conf.d/default.conf
# 빌드 결과물만 복사
COPY --from=builder /app/build /usr/share/nginx/html

EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

```nginx
# nginx.conf
server {
    listen 80;
    root /usr/share/nginx/html;
    index index.html;

    # SPA 라우팅 지원
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 정적 에셋 캐싱
    location ~* \.(js|css|png|jpg|ico|svg)$ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # gzip 압축
    gzip on;
    gzip_types text/plain application/javascript text/css;
}
```

Node.js 빌드 환경(~700MB) 대신 nginx-alpine(~25MB)만 최종 이미지에 남는다.

### 예제 3: 특정 스테이지만 타깃 빌드

멀티스테이지 빌드의 숨겨진 강점 중 하나는 `--target` 플래그를 이용한 **선택적 스테이지 빌드**다. CI 환경에서 테스트 실행과 프로덕션 빌드를 동일한 Dockerfile로 관리할 수 있다.

```dockerfile
FROM maven:3.9.6-eclipse-temurin-17-alpine AS builder
WORKDIR /build
COPY pom.xml .
RUN mvn dependency:go-offline -B
COPY src ./src

# 테스트 전용 스테이지
FROM builder AS test
RUN mvn test

# 프로덕션 빌드 스테이지
FROM builder AS prod-build
RUN mvn package -DskipTests -B

FROM eclipse-temurin:17-jre-alpine AS runtime
COPY --from=prod-build /build/target/*.jar app.jar
ENTRYPOINT ["java", "-jar", "app.jar"]
```

```bash
# CI에서 테스트만 실행
docker build --target test -t myapp:test .

# 프로덕션 이미지 빌드
docker build --target runtime -t myapp:latest .
```

## 주의사항 및 트레이드오프

### 1. Alpine 이미지의 함정: glibc vs musl libc

Alpine은 `musl libc`를 사용하므로, 일부 Java 애플리케이션이나 네이티브 라이브러리에서 호환성 문제가 발생할 수 있다. 특히 다음 상황에서 주의가 필요하다:

- **Cryptography 라이브러리**: 일부 암호화 모듈이 glibc 의존적
- **DNS 동작 차이**: Alpine의 musl은 `search` 도메인 처리 방식이 달라 Kubernetes 환경에서 DNS 이슈 발생 가능
- **Native Agent**: APM 에이전트(Pinpoint, Datadog 등)가 glibc를 요구하는 경우

대안으로 `eclipse-temurin:17-jre` (Debian slim 기반)나 `eclipse-temurin:17-jre-ubi9-minimal` (Red Hat UBI 기반)을 고려하라.

```bash
# 이미지별 크기 비교 (JRE 기준)
eclipse-temurin:17-jre-alpine     → ~185 MB
eclipse-temurin:17-jre            → ~270 MB
eclipse-temurin:17-jre-ubi9-minimal → ~230 MB
```

### 2. 빌드 캐시 무효화 주의

레이어 순서를 잘못 설계하면 캐시 효과를 전혀 누리지 못한다.

```dockerfile
# ❌ 잘못된 순서: 소스코드 변경 시 의존성도 재설치
COPY . .
RUN mvn dependency:go-offline

# ✅ 올바른 순서: 의존성 정의 파일만 먼저 복사
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
```

### 3. 시크릿 관리: 빌드 ARG의 보안 위험

`ARG`로 전달된 값은 `docker history` 명령으로 노출될 수 있다. API 키나 인증 토큰을 빌드 시 주입해야 한다면 **Docker BuildKit의 시크릿 마운트**를 사용하라.

```dockerfile
# BuildKit 시크릿 활용
RUN --mount=type=secret,id=maven_settings \
    mvn package -s /run/secrets/maven_settings -DskipTests
```

```bash
# 빌드 시 시크릿 파일 주입
DOCKER_BUILDKIT=1 docker build \
  --secret id=maven_settings,src=./settings.xml \
  -t myapp:latest .
```

### 4. 디버깅 어려움

멀티스테이지 빌드는 최종 이미지가 경량화되어 있어 `bash`, `curl`, `ps` 같은 디버깅 도구가 없는 경우가 많다. 이 문제는 두 가지 방식으로 해결할 수 있다.

```dockerfile
# 방법 1: 디버그 스테이지를 별도로 정의
FROM runtime AS debug
USER root
RUN apk add --no-cache curl bash
USER appuser

# 방법 2: Distroless 이미지 대신 개발 시에는 JRE 전체 이미지 사용
```

```bash
# 실행 중인 컨테이너 디버깅: kubectl debug or docker debug
docker debug <container_id>
```

### 5. Distroless 이미지: 한 단계 더 나아가기

Google의 Distroless 이미지를 사용하면 Alpine보다 더욱 경량화되고 보안이 강화된 이미지를 만들 수 있다. 쉘 자체가 없어서 공격 표면이 최소화된다.

```dockerfile
FROM gcr.io/distroless/java17-debian12 AS runtime
COPY --from=builder /build/target/*.jar app.jar
EXPOSE 8080
CMD ["app.jar"]
```

단, 디버깅이 매우 어려워지므로 팀의 운영 성숙도를 고려해 도입 여부를 결정해야 한다.

## 정리

Docker 멀티스테이지 빌드는 단순히 이미지 크기를 줄이는 기술이 아니다. 빌드 환경과 런타임 환경의 관심사를 분리하고, 보안 취약점 노출을 최소화하며, CI/CD 파이프라인의 효율을 높이는 **아키텍처적 결정**이다.

실무 적용 시 핵심 체크리스트:

- [ ] **베이스 이미지 선택**: 가능하면 slim/alpine/jre 계열 사용
- [ ] **레이어 캐시 설계**: 변경 빈도 낮은 파일(의존성)을 먼저 복사
- [ ] **Non-root 사용자**: 보안을 위해 반드시 별도 사용자 생성
- [ ] **시크릿 관리**: BuildKit 시크릿 마운트 활용
- [ ] **`--target` 플래그 활용**: 테스트/프로덕션 빌드 단일 Dockerfile 관리
- [ ] **호환성 검증**: Alpine(musl) 사용 시 의존 라이브러리 glibc 요구 여부 확인

이미지 크기를 1GB에서 200MB 이하로 줄이는 것은 어렵지 않다. 중요한 것은 이 과정에서 팀이 **왜** 이 선택을 했는지 이해하고, 운영 환경에서 발생할 수 있는 트레이드오프에 대비하는 것이다.
