# CORS 동작 원리와 프리플라이트 요청 처리

## 개요

프론트엔드와 백엔드가 분리된 아키텍처가 일반화된 지금, CORS(Cross-Origin Resource Sharing)는 웹 개발자라면 반드시 이해해야 할 핵심 개념이다. 단순히 "서버에서 헤더 추가하면 해결된다"는 수준의 이해로는 운영 환경에서 마주치는 다양한 CORS 이슈를 제대로 다루기 어렵다. 이 글에서는 CORS가 왜 존재하는지, 브라우저가 어떤 기준으로 요청을 차단하는지, 그리고 프리플라이트(Preflight) 요청이 발생하는 조건과 서버에서 이를 올바르게 처리하는 방법까지 깊이 있게 다룬다.

---

## 핵심 개념

### 동일 출처 정책(Same-Origin Policy)

CORS를 이해하려면 먼저 **동일 출처 정책(SOP, Same-Origin Policy)**을 알아야 한다. 브라우저는 보안을 위해 스크립트에서 시작된 HTTP 요청이 **동일한 출처(Origin)**로만 자원을 요청할 수 있도록 제한한다.

출처(Origin)는 세 가지 요소의 조합으로 정의된다.

```
Origin = 스킴(Scheme) + 호스트(Host) + 포트(Port)
```

예를 들어 `https://app.example.com:443`에서 요청할 때:

| 요청 대상 URL | 동일 출처 여부 | 이유 |
|---|---|---|
| `https://app.example.com/api` | ✅ 동일 | 스킴, 호스트, 포트 모두 일치 |
| `http://app.example.com/api` | ❌ 불일치 | 스킴 다름 (https vs http) |
| `https://api.example.com/api` | ❌ 불일치 | 서브도메인 다름 |
| `https://app.example.com:8080/api` | ❌ 불일치 | 포트 다름 |

### CORS란 무엇인가

SOP는 강력한 보안 장치지만, MSA 환경이나 CDN을 사용하는 경우처럼 의도적으로 다른 출처의 자원을 사용해야 하는 경우가 많다. CORS는 이런 상황에서 **서버가 명시적으로 허용한 출처에 대해서는 교차 출처 요청을 허용**하는 메커니즘이다.

CORS의 핵심은 브라우저와 서버 간의 **협상(Negotiation)** 과정이다. 브라우저가 요청 시 `Origin` 헤더를 포함하면, 서버는 응답에 `Access-Control-Allow-Origin` 등의 헤더를 포함해 해당 출처를 허용하는지 알려준다.

### 단순 요청(Simple Request) vs 프리플라이트 요청

CORS 요청은 크게 두 가지 유형으로 나뉜다.

**단순 요청(Simple Request)** 조건을 모두 만족하면 브라우저는 사전 확인 없이 바로 요청을 보낸다.

- 메서드: `GET`, `POST`, `HEAD` 중 하나
- 수동으로 설정한 헤더가 `Accept`, `Accept-Language`, `Content-Language`, `Content-Type` 외에 없을 것
- `Content-Type`이 `application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain` 중 하나일 것

위 조건 중 **하나라도 벗어나면** 브라우저는 본 요청 전에 **프리플라이트(OPTIONS) 요청**을 먼저 보낸다. 실무에서 가장 흔한 경우는 `Content-Type: application/json`을 사용하거나, `Authorization` 헤더를 포함하는 경우다.

### 프리플라이트 요청 상세 흐름

```
[브라우저]                          [서버]
    |                                  |
    |-- OPTIONS /api/users ----------->|
    |   Origin: https://app.com        |
    |   Access-Control-Request-Method: POST
    |   Access-Control-Request-Headers: Content-Type, Authorization
    |                                  |
    |<-- 200 OK ----------------------|
    |   Access-Control-Allow-Origin: https://app.com
    |   Access-Control-Allow-Methods: GET, POST, PUT, DELETE
    |   Access-Control-Allow-Headers: Content-Type, Authorization
    |   Access-Control-Max-Age: 86400  |
    |                                  |
    |-- POST /api/users --------------->|  (실제 요청)
    |   Origin: https://app.com        |
    |   Content-Type: application/json |
    |   Authorization: Bearer xxx      |
    |                                  |
    |<-- 200 OK ----------------------|
```

`Access-Control-Max-Age`는 프리플라이트 결과를 브라우저가 캐싱하는 시간(초)이다. 이 값이 없거나 0이면 매 요청마다 프리플라이트가 발생해 성능에 영향을 줄 수 있다.

## 실전 예제

### Spring Boot에서 CORS 설정

Spring Boot에서 CORS를 설정하는 방법은 여러 가지가 있다. 실무에서 권장하는 방식은 `WebMvcConfigurer`를 구현하거나 `CorsFilter`를 Bean으로 등록하는 것이다.

**전역 CORS 설정 (WebMvcConfigurer)**

```java
@Configuration
public class CorsConfig implements WebMvcConfigurer {

    @Value("${app.cors.allowed-origins}")
    private List<String> allowedOrigins;

    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins(allowedOrigins.toArray(new String[0]))
                .allowedMethods("GET", "POST", "PUT", "DELETE", "PATCH", "OPTIONS")
                .allowedHeaders("Authorization", "Content-Type", "X-Requested-With")
                .exposedHeaders("X-Custom-Header", "Authorization")
                .allowCredentials(true)
                .maxAge(86400); // 프리플라이트 캐시 24시간
    }
}
```

**Spring Security와 함께 사용할 때**

Spring Security를 사용하는 경우 Security Filter Chain보다 CORS 처리가 먼저 이뤄져야 한다. 그렇지 않으면 프리플라이트 OPTIONS 요청이 401/403으로 차단된다.

```java
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .cors(cors -> cors.configurationSource(corsConfigurationSource()))
            .csrf(csrf -> csrf.disable())
            .authorizeHttpRequests(auth -> auth
                .requestMatchers(HttpMethod.OPTIONS, "/**").permitAll() // 중요!
                .requestMatchers("/api/public/**").permitAll()
                .anyRequest().authenticated()
            );
        return http.build();
    }

    @Bean
    public CorsConfigurationSource corsConfigurationSource() {
        CorsConfiguration configuration = new CorsConfiguration();
        configuration.setAllowedOrigins(List.of(
            "https://app.example.com",
            "https://admin.example.com"
        ));
        configuration.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "PATCH", "OPTIONS"));
        configuration.setAllowedHeaders(List.of("*"));
        configuration.setExposedHeaders(List.of("Authorization", "X-Total-Count"));
        configuration.setAllowCredentials(true);
        configuration.setMaxAge(86400L);

        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        source.registerCorsConfiguration("/api/**", configuration);
        return source;
    }
}
```

### Nginx에서 CORS 처리

API Gateway나 리버스 프록시로 Nginx를 사용하는 경우, 서버 레벨에서 CORS를 처리할 수 있다. 이 방식은 백엔드 코드 변경 없이 CORS 정책을 통제할 수 있어 유연하다.

```nginx
server {
    listen 443 ssl;
    server_name api.example.com;

    location /api/ {
        # 프리플라이트 요청 처리
        if ($request_method = 'OPTIONS') {
            add_header 'Access-Control-Allow-Origin' $http_origin always;
            add_header 'Access-Control-Allow-Methods' 'GET, POST, PUT, DELETE, PATCH, OPTIONS' always;
            add_header 'Access-Control-Allow-Headers' 'Authorization, Content-Type, X-Requested-With' always;
            add_header 'Access-Control-Allow-Credentials' 'true' always;
            add_header 'Access-Control-Max-Age' 86400 always;
            add_header 'Content-Type' 'text/plain charset=UTF-8';
            add_header 'Content-Length' 0;
            return 204;
        }

        # 실제 요청에도 CORS 헤더 추가
        add_header 'Access-Control-Allow-Origin' $http_origin always;
        add_header 'Access-Control-Allow-Credentials' 'true' always;
        add_header 'Access-Control-Expose-Headers' 'Authorization, X-Total-Count' always;

        proxy_pass http://backend_upstream;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

> **주의**: Nginx의 `if` 블록은 NGINX 내부에서 컨텍스트 문제가 있을 수 있다. 가능하다면 `map` 지시어를 사용하거나, 허용 출처를 명확히 제한하는 로직을 추가하는 것이 좋다.

## 주의사항 및 트레이드오프

### `Access-Control-Allow-Origin: *` 와 Credentials

가장 흔한 실수 중 하나다. `allowCredentials(true)`로 설정하면서 `Access-Control-Allow-Origin: *`를 함께 사용하면 **브라우저가 해당 응답을 거부**한다. 쿠키나 Authorization 헤더 같은 자격증명이 포함된 요청에서는 반드시 **정확한 출처를 명시**해야 한다.

```
# 잘못된 조합 (브라우저 오류 발생)
Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true

# 올바른 조합
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
```

### 동적 Origin 허용과 보안

허용할 출처가 여러 개인 경우, 요청의 `Origin` 헤더 값을 화이트리스트와 비교해 동적으로 설정하는 방식을 쓴다. 이때 **단순 문자열 포함 여부가 아닌 정확한 출처 비교**를 해야 한다.

```java
// 위험한 방식 - 문자열 포함 여부로만 검사
if (origin.contains("example.com")) { ... }
// "https://evil-example.com" 도 통과될 수 있음

// 안전한 방식 - 사전 정의된 허용 목록과 정확히 비교
private static final Set<String> ALLOWED_ORIGINS = Set.of(
    "https://app.example.com",
    "https://admin.example.com"
);

if (ALLOWED_ORIGINS.contains(origin)) {
    response.setHeader("Access-Control-Allow-Origin", origin);
    response.setHeader("Vary", "Origin"); // 캐시 분리 필수
}
```

### `Vary: Origin` 헤더의 중요성

동적으로 Origin을 설정하는 경우 **반드시 `Vary: Origin` 헤더를 추가**해야 한다. CDN이나 중간 프록시가 응답을 캐시할 때, Origin에 따라 서로 다른 응답임을 인식하게 해야 하기 때문이다. 이를 빠뜨리면 A 출처의 응답이 B 출처 요청에 잘못 캐시되어 CORS 오류가 발생할 수 있다.

### 프리플라이트 최적화

`Access-Control-Max-Age`를 적절히 설정해 불필요한 프리플라이트 왕복을 줄여야 한다. 크롬 브라우저는 최대 7200초(2시간), Firefox는 86400초(24시간)를 상한으로 캐싱한다. 개발 환경에서는 디버깅 편의를 위해 `0`으로 설정하고, 운영 환경에서는 충분히 큰 값을 주는 것이 좋다.

### 서버 측 CORS 헤더 중복 설정

Spring Boot + Nginx 구조에서 양쪽 모두 CORS 헤더를 설정하면 **동일 헤더가 중복**되어 브라우저가 오류를 내는 경우가 있다. CORS 처리 레이어를 하나로 통일하고, 나머지에서는 중복 설정을 제거해야 한다.

## 정리

| 항목 | 핵심 포인트 |
|---|---|
| 출처 판단 | 스킴 + 호스트 + 포트 세 가지 모두 일치해야 동일 출처 |
| 프리플라이트 발생 조건 | `application/json`, `Authorization` 헤더 등 단순 요청 조건 벗어날 때 |
| Credentials + Wildcard | 함께 사용 불가, 명시적 출처 지정 필수 |
| Vary 헤더 | 동적 Origin 설정 시 반드시 `Vary: Origin` 추가 |
| Max-Age | 운영 환경에서 적절히 설정해 프리플라이트 오버헤드 감소 |
| 보안 검사 | Origin 값 화이트리스트 기반 정확한 비교 필수 |

CORS는 브라우저가 강제하는 보안 메커니즘이며, 서버는 이를 올바르게 응답하는 역할을 한다. 단순히 `*`로 열어두는 것은 편리하지만 보안 취약점으로 이어질 수 있다. 출처를 명확히 제한하고, 프리플라이트 캐싱을 최적화하며, CORS 처리 레이어를 일원화하는 것이 실무에서 안정적인 CORS 운영의 핵심이다.
