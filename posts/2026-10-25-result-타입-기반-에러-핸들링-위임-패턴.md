# Result 타입 기반 에러 핸들링 위임 패턴

## 개요

Java 생태계에서 에러 처리는 오랫동안 `try-catch`와 `checked exception`의 영역이었다. Spring 기반의 서비스에서는 `@ControllerAdvice`와 `@ExceptionHandler`를 조합해 전역 예외를 처리하는 방식이 사실상 표준처럼 자리 잡았다.

그런데 서비스 규모가 커지고 레이어 간 책임이 명확해질수록, 예외(Exception) 기반 흐름 제어에는 몇 가지 근본적인 불편함이 드러난다.

- 예외가 던져질 수 있는 지점을 **컴파일 타임에 강제하기 어렵다**
- `checked exception`은 상위 레이어까지 시그니처를 오염시킨다
- `unchecked exception`은 처리 여부를 보장할 수 없다
- 예외를 흐름 제어 수단으로 쓰면 **가독성과 추적 비용**이 높아진다

이런 문제 의식에서 Rust의 `Result<T, E>`, Haskell의 `Either`, Scala의 `Try` 같은 **함수형 에러 타입**이 Java 세계로 들어오기 시작했다. 이 포스팅에서는 이 개념을 Spring 실무에서 어떻게 설계하고 적용할 수 있는지, 특히 **에러 핸들링을 호출자에게 위임하는 패턴**을 중심으로 살펴본다.

---

## 핵심 개념

### Result 타입이란?

`Result<T, E>`는 성공 시 값(`T`)을, 실패 시 에러(`E`)를 담는 컨테이너 타입이다. 핵심은 **예외를 던지지 않고**, 성공과 실패를 **정상적인 반환값**으로 표현한다는 점이다.

```
Result<User, UserError>
  → Success(User)    // 성공 케이스
  → Failure(UserError.NOT_FOUND) // 실패 케이스
```

Java에는 기본 제공 `Result` 타입이 없지만, `Optional`, `Either`(Vavr), 또는 직접 구현한 `Result` 클래스로 이를 표현할 수 있다.

### 에러 핸들링 위임 패턴

일반적인 예외 기반 방식에서는 에러가 발생한 지점에서 예외를 **던지고**, 어딘가에서 **잡는** 구조다. 반면 Result 기반 위임 패턴은 다음 원칙을 따른다.

1. **메서드는 실패 가능성을 반환 타입으로 명시한다**
2. **호출자가 성공/실패를 처리할 책임을 갖는다**
3. **에러 처리 시점과 방식의 결정권을 호출자에게 위임한다**

이는 단순히 "예외를 안 쓴다"는 것이 아니라, **에러를 first-class value로 취급**하는 설계 철학이다.

## 실전 예제

### 1. Result 클래스 구현

먼저 실무에서 바로 쓸 수 있는 간단한 `Result` 타입을 구현한다.

```java
public sealed interface Result<T> permits Result.Success, Result.Failure {

    record Success<T>(T value) implements Result<T> {}
    record Failure<T>(AppError error) implements Result<T> {}

    static <T> Result<T> success(T value) {
        return new Success<>(value);
    }

    static <T> Result<T> failure(AppError error) {
        return new Failure<>(error);
    }

    default boolean isSuccess() {
        return this instanceof Success;
    }

    default T getOrThrow() {
        return switch (this) {
            case Success<T> s -> s.value();
            case Failure<T> f -> throw new IllegalStateException(f.error().message());
        };
    }

    default <U> Result<U> map(java.util.function.Function<T, U> mapper) {
        return switch (this) {
            case Success<T> s -> Result.success(mapper.apply(s.value()));
            case Failure<T> f -> Result.failure(f.error());
        };
    }

    default <U> Result<U> flatMap(java.util.function.Function<T, Result<U>> mapper) {
        return switch (this) {
            case Success<T> s -> mapper.apply(s.value());
            case Failure<T> f -> Result.failure(f.error());
        };
    }
}
```

```java
public record AppError(ErrorCode code, String message) {

    public enum ErrorCode {
        USER_NOT_FOUND,
        INVALID_INPUT,
        DUPLICATE_EMAIL,
        EXTERNAL_SERVICE_FAILURE
    }

    public static AppError of(ErrorCode code, String message) {
        return new AppError(code, message);
    }
}
```

> Java 17+의 `sealed interface`와 `record`를 활용하면 패턴 매칭과 함께 타입 안전한 Result를 구현할 수 있다.

### 2. 서비스 레이어에서 Result 반환

```java
@Service
@RequiredArgsConstructor
public class UserService {

    private final UserRepository userRepository;
    private final EmailValidator emailValidator;

    public Result<User> findById(Long userId) {
        return userRepository.findById(userId)
            .map(Result::success)
            .orElse(Result.failure(
                AppError.of(AppError.ErrorCode.USER_NOT_FOUND,
                    "사용자를 찾을 수 없습니다. id=" + userId)
            ));
    }

    public Result<User> registerUser(RegisterUserCommand command) {
        // 입력 유효성 검사
        if (!emailValidator.isValid(command.email())) {
            return Result.failure(
                AppError.of(AppError.ErrorCode.INVALID_INPUT, "유효하지 않은 이메일 형식입니다.")
            );
        }

        // 중복 이메일 검사
        if (userRepository.existsByEmail(command.email())) {
            return Result.failure(
                AppError.of(AppError.ErrorCode.DUPLICATE_EMAIL, "이미 사용 중인 이메일입니다.")
            );
        }

        User user = User.create(command.email(), command.name());
        userRepository.save(user);
        return Result.success(user);
    }
}
```

### 3. 체이닝을 통한 복합 비즈니스 로직

`flatMap`을 활용하면 여러 단계의 실패 가능 연산을 선언적으로 연결할 수 있다.

```java
@Service
@RequiredArgsConstructor
public class OrderService {

    private final UserService userService;
    private final ProductService productService;
    private final InventoryService inventoryService;
    private final PaymentService paymentService;

    public Result<Order> placeOrder(PlaceOrderCommand command) {
        return userService.findById(command.userId())
            .flatMap(user -> productService.findById(command.productId()))
            .flatMap(product -> inventoryService.reserveStock(product, command.quantity()))
            .flatMap(reservation -> paymentService.charge(command.userId(), reservation.totalPrice()))
            .map(payment -> Order.create(command, payment));
    }
}
```

각 단계에서 실패가 발생하면 이후 단계는 실행되지 않고, 실패 정보가 그대로 전파된다. 예외 없이 **철도 지향 프로그래밍(Railway Oriented Programming)** 스타일로 에러를 흘릴 수 있다.

### 4. 컨트롤러에서 Result 해석 및 HTTP 응답 변환

컨트롤러에서는 `Result`를 HTTP 응답으로 변환하는 책임을 진다.

```java
@RestController
@RequestMapping("/api/users")
@RequiredArgsConstructor
public class UserController {

    private final UserService userService;

    @GetMapping("/{userId}")
    public ResponseEntity<?> getUser(@PathVariable Long userId) {
        Result<User> result = userService.findById(userId);

        return switch (result) {
            case Result.Success<User> s ->
                ResponseEntity.ok(UserResponse.from(s.value()));
            case Result.Failure<User> f ->
                toErrorResponse(f.error());
        };
    }

    @PostMapping
    public ResponseEntity<?> registerUser(@RequestBody @Valid RegisterUserRequest request) {
        Result<User> result = userService.registerUser(request.toCommand());

        return switch (result) {
            case Result.Success<User> s ->
                ResponseEntity.status(HttpStatus.CREATED).body(UserResponse.from(s.value()));
            case Result.Failure<User> f ->
                toErrorResponse(f.error());
        };
    }

    private ResponseEntity<ErrorResponse> toErrorResponse(AppError error) {
        HttpStatus status = switch (error.code()) {
            case USER_NOT_FOUND -> HttpStatus.NOT_FOUND;
            case INVALID_INPUT -> HttpStatus.BAD_REQUEST;
            case DUPLICATE_EMAIL -> HttpStatus.CONFLICT;
            case EXTERNAL_SERVICE_FAILURE -> HttpStatus.BAD_GATEWAY;
        };
        return ResponseEntity.status(status)
            .body(new ErrorResponse(error.code().name(), error.message()));
    }
}
```

### 5. 외부 연동에서의 Result 활용

외부 API 호출처럼 예외가 불가피한 상황은 Result로 감싸는 어댑터를 작성한다.

```java
@Component
public class ExternalPaymentClient {

    private final RestTemplate restTemplate;

    public Result<PaymentConfirmation> charge(ChargeRequest request) {
        try {
            PaymentConfirmation confirmation = restTemplate.postForObject(
                "/payments/charge", request, PaymentConfirmation.class
            );
            return Result.success(confirmation);
        } catch (HttpClientErrorException e) {
            return Result.failure(
                AppError.of(AppError.ErrorCode.INVALID_INPUT, "결제 요청이 거부되었습니다.")
            );
        } catch (Exception e) {
            return Result.failure(
                AppError.of(AppError.ErrorCode.EXTERNAL_SERVICE_FAILURE, "외부 결제 서비스 오류가 발생했습니다.")
            );
        }
    }
}
```

예외가 발생할 수 있는 경계(외부 I/O, 파싱 등)에서만 `try-catch`를 사용하고, **내부 비즈니스 레이어로는 Result만 흐른다**는 원칙을 지키면 된다.

## 주의사항 및 트레이드오프

### ✅ 이 패턴이 유효한 상황

- **비즈니스 로직의 실패 케이스가 명확히 정의**될 때 (예: 사용자 없음, 재고 부족)
- 서비스 레이어의 호출자가 **에러 종류에 따라 다른 처리**를 해야 할 때
- **컴파일 타임에 에러 처리를 강제**하고 싶을 때
- 코드 리뷰에서 **실패 경로가 명시적으로 드러나길 원할 때**

### ⚠️ 주의할 점

**1. 모든 에러를 Result로 감싸지 말 것**

인프라 수준의 에러(DB 커넥션 실패, OOM 등)는 복구 불가능한 경우가 많다. 이런 케이스는 여전히 `RuntimeException`으로 전파하고, `@ControllerAdvice`가 처리하게 두는 것이 자연스럽다. Result는 **비즈니스 실패(business failure)** 표현에 집중해야 한다.

**2. 기존 팀 코드와의 혼용 문제**

팀 전체가 패턴을 이해하지 못한 상태에서 도입하면, 일부는 Result를 반환하고 일부는 예외를 던지는 혼재 상황이 생긴다. **점진적 도입 전략**과 **명확한 컨벤션 문서화**가 필수다.

**3. 스택 트레이스 손실**

예외와 달리 Result는 스택 트레이스를 자동으로 포함하지 않는다. 디버깅을 위해 `AppError`에 cause 정보를 선택적으로 담거나, 로깅 지점을 명시적으로 두어야 한다.

**4. 트랜잭션과의 상호작용**

Spring의 `@Transactional`은 기본적으로 `RuntimeException` 발생 시 롤백된다. Result를 반환해서 예외를 삼키면, 서비스 내부에서 실패했더라도 트랜잭션이 커밋될 수 있다. **Result.Failure를 반환하기 전에 트랜잭션 롤백 여부를 명시적으로 검토**해야 한다.

```java
@Transactional
public Result<Order> placeOrder(PlaceOrderCommand command) {
    Result<Order> result = doPlaceOrder(command);
    if (!result.isSuccess()) {
        // 필요하다면 명시적으로 롤백 처리
        TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
    }
    return result;
}
```

**5. Vavr 라이브러리 사용 검토**

직접 구현 대신 [Vavr](https://www.vavr.io/)의 `Either<L, R>`나 `Try<T>`를 사용하면 더 풍부한 함수형 연산자(fold, recover, toOption 등)를 활용할 수 있다. 다만 팀의 함수형 프로그래밍 숙련도와 의존성 추가 비용을 함께 고려하자.

## 정리

Result 타입 기반 에러 핸들링 위임 패턴은 예외를 제거하자는 운동이 아니다. **비즈니스 실패를 타입 시스템 안에서 명시적으로 표현**하고, **에러 처리 결정권을 적절한 호출자에게 위임**하는 설계 선택이다.

| 구분 | 예외 기반 | Result 기반 |
|------|----------|------------|
| 실패 표현 | 암묵적 (시그니처에 없음) | 명시적 (반환 타입에 포함) |
| 처리 강제 | 선택적 | 컴파일 타임 강제 가능 |
| 흐름 제어 | 예외 전파 | 체이닝(flatMap) |
| 트랜잭션 연동 | 자동 롤백 | 수동 처리 필요 |
| 스택 트레이스 | 자동 | 별도 관리 필요 |

이 패턴은 도입 비용이 있지만, **레이어 간 계약(contract)이 명확해지고 실패 경로를 코드에서 추적하기 쉬워진다**는 점에서 서비스가 복잡해질수록 가치를 발휘한다. 처음부터 전면 도입하기보다 신규 기능 또는 실패 케이스가 다양한 도메인부터 점진적으로 적용해 나가는 접근을 권장한다.
