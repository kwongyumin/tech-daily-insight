# 이벤트 드리븐 아키텍처 Outbox 패턴 구현

## 개요

마이크로서비스 아키텍처에서 이벤트 드리븐 방식을 채택하면 서비스 간 느슨한 결합을 달성할 수 있습니다. 그러나 **"데이터베이스 트랜잭션과 메시지 브로커 발행을 동시에 보장하는 것"** 은 생각보다 훨씬 까다로운 문제입니다.

예를 들어 주문 서비스에서 주문을 저장한 뒤 Kafka에 `OrderCreated` 이벤트를 발행하는 시나리오를 생각해봅시다. DB 저장은 성공했지만 Kafka 발행 전에 서버가 죽는다면? 반대로 Kafka에 발행한 뒤 DB 커밋이 실패한다면? 이런 **분산 시스템의 이중 쓰기(Dual Write) 문제**를 해결하는 것이 바로 **Outbox 패턴**입니다.

이 글에서는 Outbox 패턴의 핵심 개념부터 Spring Boot + Kafka + PostgreSQL 환경에서의 실전 구현까지 단계별로 살펴보겠습니다.

---

## 핵심 개념

### 이중 쓰기 문제란?

분산 시스템에서 두 개의 독립적인 시스템(DB와 메시지 브로커)에 데이터를 쓸 때 **원자성(Atomicity)** 을 보장할 수 없습니다. 전통적인 2PC(Two-Phase Commit)로 해결하려는 시도도 있지만, 메시지 브로커가 XA 트랜잭션을 지원하지 않거나 성능 저하가 심각한 경우가 많습니다.

### Outbox 패턴 동작 원리

Outbox 패턴은 다음 아이디어를 기반으로 합니다:

1. **비즈니스 데이터와 이벤트를 같은 DB 트랜잭션에서 저장**한다.
2. 이벤트는 `outbox` 테이블에 임시 저장된다.
3. 별도의 **Message Relay** 컴포넌트가 `outbox` 테이블을 폴링하거나, CDC(Change Data Capture)를 통해 메시지 브로커에 발행한다.

```
[비즈니스 로직]
    └─ DB Transaction ──┬─ orders 테이블 INSERT
                        └─ outbox 테이블 INSERT

[Message Relay]
    └─ outbox 폴링 → Kafka 발행 → outbox 처리 완료 표시
```

이 방식의 핵심은 **"DB 저장과 이벤트 저장이 단일 트랜잭션"** 이라는 점입니다. 메시지 브로커와의 통신은 이후 비동기로 처리됩니다.

### Message Relay 구현 전략

| 전략 | 설명 | 장점 | 단점 |
|------|------|------|------|
| Polling Publisher | 주기적으로 outbox 테이블 스캔 | 구현 단순 | DB 부하, 지연 발생 가능 |
| CDC (Debezium) | DB 변경 로그(WAL) 감지 | 실시간, DB 부하 적음 | 인프라 복잡도 증가 |

## 실전 예제

### 프로젝트 구성

- **Spring Boot 3.x**
- **PostgreSQL**
- **Apache Kafka**
- **Spring Data JPA**
- **Spring Scheduler** (Polling 방식)

### 1. Outbox 테이블 설계

```sql
CREATE TABLE outbox_event (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    aggregate_type VARCHAR(255) NOT NULL,  -- e.g., "Order"
    aggregate_id   VARCHAR(255) NOT NULL,  -- e.g., orderId
    event_type     VARCHAR(255) NOT NULL,  -- e.g., "OrderCreated"
    payload        JSONB        NOT NULL,
    status         VARCHAR(50)  NOT NULL DEFAULT 'PENDING',
    created_at     TIMESTAMP    NOT NULL DEFAULT NOW(),
    processed_at   TIMESTAMP
);

CREATE INDEX idx_outbox_status_created ON outbox_event(status, created_at);
```

### 2. 도메인 및 Outbox 엔티티

```java
// Order.java
@Entity
@Table(name = "orders")
@Getter
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.UUID)
    private UUID id;

    private String customerId;
    private BigDecimal totalAmount;

    @Enumerated(EnumType.STRING)
    private OrderStatus status;

    // 정적 팩토리 메서드
    public static Order create(String customerId, BigDecimal totalAmount) {
        Order order = new Order();
        order.customerId = customerId;
        order.totalAmount = totalAmount;
        order.status = OrderStatus.CREATED;
        return order;
    }
}
```

```java
// OutboxEvent.java
@Entity
@Table(name = "outbox_event")
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class OutboxEvent {

    @Id
    @GeneratedValue(strategy = GenerationType.UUID)
    private UUID id;

    private String aggregateType;
    private String aggregateId;
    private String eventType;

    @Column(columnDefinition = "jsonb")
    private String payload;

    @Enumerated(EnumType.STRING)
    private OutboxStatus status;

    private LocalDateTime createdAt;
    private LocalDateTime processedAt;

    public static OutboxEvent create(String aggregateType, String aggregateId,
                                     String eventType, String payload) {
        OutboxEvent event = new OutboxEvent();
        event.aggregateType = aggregateType;
        event.aggregateId = aggregateId;
        event.eventType = eventType;
        event.payload = payload;
        event.status = OutboxStatus.PENDING;
        event.createdAt = LocalDateTime.now();
        return event;
    }

    public void markAsProcessed() {
        this.status = OutboxStatus.PROCESSED;
        this.processedAt = LocalDateTime.now();
    }

    public void markAsFailed() {
        this.status = OutboxStatus.FAILED;
    }
}
```

### 3. 주문 생성 서비스 (단일 트랜잭션)

```java
@Service
@RequiredArgsConstructor
@Transactional
public class OrderService {

    private final OrderRepository orderRepository;
    private final OutboxEventRepository outboxEventRepository;
    private final ObjectMapper objectMapper;

    public OrderResponse createOrder(CreateOrderRequest request) {
        // 1. 비즈니스 로직 수행
        Order order = Order.create(request.getCustomerId(), request.getTotalAmount());
        orderRepository.save(order);

        // 2. 같은 트랜잭션 내에서 Outbox 이벤트 저장
        OrderCreatedEvent eventPayload = new OrderCreatedEvent(
            order.getId().toString(),
            order.getCustomerId(),
            order.getTotalAmount(),
            order.getStatus().name()
        );

        try {
            String payload = objectMapper.writeValueAsString(eventPayload);
            OutboxEvent outboxEvent = OutboxEvent.create(
                "Order",
                order.getId().toString(),
                "OrderCreated",
                payload
            );
            outboxEventRepository.save(outboxEvent);
        } catch (JsonProcessingException e) {
            throw new RuntimeException("이벤트 직렬화 실패", e);
        }

        return OrderResponse.from(order);
    }
}
```

> 핵심은 `@Transactional` 하나로 `orders` 테이블과 `outbox_event` 테이블에 대한 쓰기가 **원자적으로 처리**된다는 점입니다.

### 4. Message Relay - Polling Publisher

```java
@Component
@RequiredArgsConstructor
@Slf4j
public class OutboxMessageRelay {

    private final OutboxEventRepository outboxEventRepository;
    private final KafkaTemplate<String, String> kafkaTemplate;

    private static final int BATCH_SIZE = 100;

    @Scheduled(fixedDelay = 1000) // 1초마다 폴링
    @Transactional
    public void publishPendingEvents() {
        List<OutboxEvent> pendingEvents = outboxEventRepository
            .findTopNByStatusOrderByCreatedAtAsc(OutboxStatus.PENDING, BATCH_SIZE);

        if (pendingEvents.isEmpty()) return;

        log.info("처리할 Outbox 이벤트 수: {}", pendingEvents.size());

        for (OutboxEvent event : pendingEvents) {
            try {
                String topic = resolveTopicName(event.getAggregateType(), event.getEventType());

                kafkaTemplate.send(topic, event.getAggregateId(), event.getPayload())
                    .whenComplete((result, ex) -> {
                        if (ex != null) {
                            log.error("Kafka 발행 실패 - eventId: {}", event.getId(), ex);
                            event.markAsFailed();
                        } else {
                            event.markAsProcessed();
                            log.debug("Kafka 발행 성공 - eventId: {}", event.getId());
                        }
                    });

            } catch (Exception e) {
                log.error("이벤트 처리 중 오류 - eventId: {}", event.getId(), e);
                event.markAsFailed();
            }
        }
    }

    private String resolveTopicName(String aggregateType, String eventType) {
        return String.format("%s.%s", aggregateType.toLowerCase(), eventType);
        // e.g., "order.OrderCreated"
    }
}
```

```java
// OutboxEventRepository.java
public interface OutboxEventRepository extends JpaRepository<OutboxEvent, UUID> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT o FROM OutboxEvent o WHERE o.status = :status " +
           "ORDER BY o.createdAt ASC LIMIT :limit")
    List<OutboxEvent> findTopNByStatusOrderByCreatedAtAsc(
        @Param("status") OutboxStatus status,
        @Param("limit") int limit
    );
}
```

> `PESSIMISTIC_WRITE` 락은 다중 인스턴스 배포 환경에서 **동일 이벤트 중복 처리를 방지**합니다. PostgreSQL의 `SELECT FOR UPDATE SKIP LOCKED`를 활용하면 성능을 더 높일 수 있습니다.

### 5. SKIP LOCKED를 활용한 성능 최적화

```java
@Query(value = "SELECT * FROM outbox_event WHERE status = 'PENDING' " +
               "ORDER BY created_at ASC LIMIT :limit " +
               "FOR UPDATE SKIP LOCKED",
       nativeQuery = true)
List<OutboxEvent> findPendingEventsWithSkipLocked(@Param("limit") int limit);
```

`SKIP LOCKED`를 사용하면 이미 다른 인스턴스가 처리 중인 행을 건너뛰어 **불필요한 락 대기 없이 병렬 처리**가 가능합니다.

## 주의사항 및 트레이드오프

### ⚠️ At-Least-Once 보장과 멱등성

Outbox 패턴은 **"최소 한 번 이상(At-Least-Once)"** 전달을 보장합니다. Kafka 발행 성공 후 `PROCESSED` 상태 업데이트 전에 서버가 다운되면, 재시작 시 같은 이벤트를 다시 발행할 수 있습니다. 따라서 **컨슈머 측에서 반드시 멱등성(Idempotency)** 을 구현해야 합니다.

```java
// 컨슈머 측 멱등성 처리 예시
@KafkaListener(topics = "order.OrderCreated")
@Transactional
public void handleOrderCreated(ConsumerRecord<String, String> record) {
    String eventId = record.headers()
        .lastHeader("eventId").toString(); // 이벤트 ID를 헤더로 전달하는 것을 권장

    // 이미 처리된 이벤트인지 확인
    if (processedEventRepository.existsById(eventId)) {
        log.info("중복 이벤트 무시 - eventId: {}", eventId);
        return;
    }

    // 비즈니스 로직 처리
    processOrder(record.value());

    // 처리 완료 기록
    processedEventRepository.save(new ProcessedEvent(eventId));
}
```

### ⚠️ Outbox 테이블 증가 문제

처리 완료된 이벤트는 주기적으로 정리해야 합니다. 단순히 `PROCESSED` 상태로만 두면 테이블이 무한 증가합니다.

```java
@Scheduled(cron = "0 0 2 * * *") // 매일 새벽 2시
@Transactional
public void cleanUpProcessedEvents() {
    LocalDateTime threshold = LocalDateTime.now().minusDays(7);
    int deleted = outboxEventRepository.deleteByStatusAndProcessedAtBefore(
        OutboxStatus.PROCESSED, threshold
    );
    log.info("정리된 Outbox 이벤트 수: {}", deleted);
}
```

### ⚠️ 폴링 지연과 CDC 선택 기준

Polling 방식은 구현이 단순하지만 1~2초의 지연이 발생합니다. **실시간성이 중요한 도메인**(결제, 재고 등)이라면 **Debezium + Kafka Connect** 기반의 CDC 방식을 고려하세요. CDC는 PostgreSQL의 WAL(Write-Ahead Log)을 실시간으로 스트리밍하여 지연을 최소화합니다.

### ⚠️ 이벤트 순서 보장

Kafka의 파티션 내에서는 순서가 보장되지만, 파티션 간에는 보장되지 않습니다. 같은 `aggregateId`를 **파티션 키**로 사용하면 동일 애그리거트에 대한 이벤트 순서를 보장할 수 있습니다.

## 정리

Outbox 패턴은 분산 시스템에서 **데이터 일관성과 이벤트 발행의 신뢰성**을 동시에 달성하는 검증된 방법입니다.

| 항목 | 내용 |
|------|------|
| **문제 해결** | 이중 쓰기(Dual Write)의 원자성 문제 |
| **핵심 원리** | DB 트랜잭션으로 비즈니스 데이터 + 이벤트 동시 저장 |
| **전달 보장** | At-Least-Once (컨슈머 멱등성 필수) |
| **구현 복잡도** | Polling 방식은 낮음 / CDC 방식은 높음 |
| **적합한 환경** | 마이크로서비스 간 이벤트 기반 통합 |

실무에서는 처음에는 **Polling 방식**으로 빠르게 도입하고, 트래픽과 실시간성 요구사항이 증가함에 따라 **Debezium CDC 방식**으로 전환하는 전략을 권장합니다. 중요한 것은 "완벽한 구현"보다 **"지금 당장 데이터 유실을 막는 것"** 입니다. Outbox 패턴은 그 첫 걸음으로 충분히 강력한 도구입니다.
