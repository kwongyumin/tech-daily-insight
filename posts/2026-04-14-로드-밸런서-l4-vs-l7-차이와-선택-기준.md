# 로드 밸런서 L4 vs L7 차이와 선택 기준

## 개요

트래픽이 폭발적으로 증가하는 현대 서비스 환경에서 로드 밸런서는 사실상 필수 인프라가 되었다. 그런데 실무에서 인프라 설계를 논의하다 보면 "L4로 할까요, L7로 할까요?"라는 질문이 생각보다 자주 충돌 지점이 된다. 단순히 "L7이 더 똑똑하니까 L7 쓰면 되는 거 아냐?"라고 생각하기 쉽지만, 실제로는 트레이드오프가 명확하고 워크로드 특성에 따라 올바른 선택이 달라진다.

이 글에서는 OSI 7계층 관점에서 L4와 L7 로드 밸런서의 동작 원리를 정확히 이해하고, 실무에서 어떤 기준으로 선택해야 하는지, 그리고 Nginx와 HAProxy를 활용한 실전 설정 예제를 함께 살펴본다.

## 핵심 개념

### OSI 계층과 로드 밸런서의 관계

로드 밸런서는 이름 그대로 부하를 분산하는 장치다. 여기서 핵심은 **어느 계층의 정보를 보고 분산 결정을 내리느냐**이다.

| 구분 | 동작 계층 | 참조 정보 | 대표 프로토콜 |
|------|-----------|-----------|--------------|
| L4 LB | Transport Layer (4계층) | IP, TCP/UDP Port | TCP, UDP |
| L7 LB | Application Layer (7계층) | HTTP Header, URL, Cookie, Body | HTTP, HTTPS, gRPC, WebSocket |

### L4 로드 밸런서

L4는 **IP 주소와 포트 번호**만 보고 트래픽을 라우팅한다. 패킷의 내용을 해석하지 않으므로 처리 속도가 매우 빠르고 CPU 부하가 낮다. 주로 **NAT(Network Address Translation)** 또는 **DSR(Direct Server Return)** 방식으로 동작한다.

**핵심 특징:**
- 패킷 내용을 열어보지 않으므로 **암호화된 트래픽도 그대로 전달** 가능
- 커넥션 단위 분산 (한 TCP 세션은 하나의 서버로만 전달)
- SSL Termination 불가 (패킷을 해석하지 않으므로)
- 헬스 체크는 TCP 연결 수준에서만 가능

### L7 로드 밸런서

L7은 **애플리케이션 레벨의 정보**를 파싱하여 라우팅한다. HTTP 메서드, URL 경로, 쿠키, 헤더, 심지어 Request Body까지 보고 분산 결정을 내릴 수 있다.

**핵심 특징:**
- URL 기반 라우팅, 헤더 기반 라우팅 가능 → **마이크로서비스 API Gateway 역할** 수행
- SSL Termination 처리 가능
- 콘텐츠 기반 캐싱, 압축, 인증 로직 삽입 가능
- 패킷을 파싱하는 만큼 **레이턴시와 CPU 비용이 증가**
- 헬스 체크를 HTTP 상태 코드 수준에서 수행 가능

## 실전 예제

### HAProxy를 이용한 L4 로드 밸런싱 설정

TCP 레벨에서 MySQL 트래픽을 분산하는 예제다. 데이터베이스 앞단에 L4 LB를 두는 패턴은 실무에서 흔히 사용된다.

```haproxy
# /etc/haproxy/haproxy.cfg

global
    log /dev/log local0
    maxconn 50000
    user haproxy
    group haproxy
    daemon

defaults
    log     global
    mode    tcp          # L4 모드: TCP 스트림 처리
    option  tcplog
    option  dontlognull
    timeout connect 5s
    timeout client  30s
    timeout server  30s

frontend mysql_frontend
    bind *:3306
    default_backend mysql_backend

backend mysql_backend
    balance leastconn    # 커넥션이 가장 적은 서버로 분산
    option  tcp-check    # TCP 레벨 헬스 체크
    
    server db1 10.0.1.10:3306 check inter 2s rise 2 fall 3
    server db2 10.0.1.11:3306 check inter 2s rise 2 fall 3
    server db3 10.0.1.12:3306 check inter 2s rise 2 fall 3 backup
```

위 설정에서 `mode tcp`가 핵심이다. HAProxy는 패킷 내용을 해석하지 않고 순수하게 TCP 커넥션 단위로 트래픽을 분산한다. `db3`는 `backup` 옵션으로 active 서버가 모두 다운될 때만 투입된다.

### Nginx를 이용한 L7 로드 밸런싱 설정

MSA 환경에서 URL 경로에 따라 각기 다른 마이크로서비스로 라우팅하는 예제다.

```nginx
# /etc/nginx/nginx.conf

upstream user_service {
    least_conn;
    server 10.0.2.10:8080 weight=3;
    server 10.0.2.11:8080 weight=3;
    server 10.0.2.12:8080 weight=1 backup;
    keepalive 32;  # upstream keepalive 커넥션 풀
}

upstream order_service {
    least_conn;
    server 10.0.3.10:8081;
    server 10.0.3.11:8081;
    keepalive 32;
}

upstream payment_service {
    ip_hash;  # 결제 서비스는 세션 고정 필요
    server 10.0.4.10:8082;
    server 10.0.4.11:8082;
}

server {
    listen 443 ssl http2;
    server_name api.example.com;

    ssl_certificate     /etc/ssl/certs/api.example.com.crt;
    ssl_certificate_key /etc/ssl/private/api.example.com.key;
    ssl_protocols       TLSv1.2 TLSv1.3;

    # SSL Termination 후 내부는 HTTP로 통신
    
    # URL 경로 기반 라우팅
    location /api/v1/users {
        proxy_pass http://user_service;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_connect_timeout 3s;
        proxy_read_timeout 30s;
    }

    location /api/v1/orders {
        proxy_pass http://order_service;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    location /api/v1/payments {
        proxy_pass http://payment_service;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    # 헤더 기반 라우팅 (A/B 테스트, 카나리 배포)
    location /api/v1/feature {
        # X-Canary 헤더가 있으면 신규 서버로
        if ($http_x_canary = "true") {
            proxy_pass http://feature_canary_service;
            break;
        }
        proxy_pass http://feature_stable_service;
    }
}
```

`ip_hash`는 동일 클라이언트 IP가 항상 같은 서버로 가도록 보장한다. 결제처럼 세션 상태가 중요한 경우에 유용하지만, 특정 IP에 트래픽이 몰리면 불균형이 발생할 수 있다는 점을 주의해야 한다.

### Spring Boot + AWS 환경에서의 선택 패턴

AWS 환경을 예로 들면 다음처럼 계층을 구성하는 경우가 많다.

```
Internet
    │
    ▼
[AWS NLB - L4]          ← TCP/UDP 트래픽, 고정 IP 필요 시
    │
    ▼
[AWS ALB - L7]          ← HTTP/HTTPS, 경로 기반 라우팅
    │
    ▼
[Spring Boot Services]
```

```java
// Spring Boot에서 실제 클라이언트 IP 추출 (L7 LB 뒤에 있을 때)
@Component
public class ClientIpExtractor {

    public String getClientIp(HttpServletRequest request) {
        // L7 LB가 X-Forwarded-For 헤더를 추가함
        String xForwardedFor = request.getHeader("X-Forwarded-For");
        
        if (xForwardedFor != null && !xForwardedFor.isEmpty()) {
            // 체인이 있을 경우 첫 번째 IP가 실제 클라이언트
            // 예: "203.0.113.1, 10.0.0.1, 10.0.0.2"
            return xForwardedFor.split(",")[0].trim();
        }
        
        // L4 LB + DSR 구성이거나 직접 연결인 경우
        return request.getRemoteAddr();
    }
}

// application.yml - Spring 내장 Tomcat 설정
// server:
//   forward-headers-strategy: native  # X-Forwarded-* 헤더 신뢰
```

## 주의사항 및 트레이드오프

### 1. 성능 vs 기능

L7 LB는 패킷을 파싱하므로 L4 대비 레이턴시가 증가한다. 초당 수십만 TPS를 처리해야 하는 게임 서버나 실시간 스트리밍 같은 워크로드에서는 L4의 낮은 레이턴시가 결정적인 이점이 된다. 반면 일반적인 HTTP API 서버에서는 수 밀리초의 차이가 큰 의미를 갖지 않는 경우가 대부분이다.

### 2. SSL Termination 위치 결정

L4 LB는 TLS 패킷을 해석하지 못하므로 SSL Termination은 반드시 백엔드 서버에서 처리해야 한다. L7 LB를 사용하면 LB에서 Termination 후 내부 통신은 HTTP로 처리할 수 있어 백엔드 서버의 CPU 부담이 줄어든다. 단, 내부 네트워크를 신뢰할 수 없는 규정 준수 환경(PCI-DSS, HIPAA 등)에서는 **End-to-End TLS**를 유지해야 하므로 L7 LB에서도 re-encryption이 필요하다.

### 3. WebSocket과 gRPC의 특수성

WebSocket과 gRPC(HTTP/2)는 장기 커넥션을 유지한다. L7 LB에서 이를 처리할 때 타임아웃 설정을 일반 HTTP와 다르게 해야 한다. 또한 gRPC의 경우 HTTP/2 멀티플렉싱 때문에 **하나의 TCP 커넥션에 여러 스트림이 섞여** 라운드로빈 분산이 제대로 동작하지 않을 수 있다. 이 경우 gRPC 클라이언트 사이드 로드 밸런싱이나 별도의 service mesh(Envoy, Istio) 도입을 검토해야 한다.

### 4. 세션 고정(Sticky Session) 의존 제거

`ip_hash`나 쿠키 기반 sticky session은 상태를 서버에 저장하는 레거시 아키텍처를 위한 임시방편이다. 장기적으로는 세션을 Redis 같은 외부 스토어로 분리하여 어느 서버로 요청이 가더라도 동일하게 처리할 수 있는 **Stateless 아키텍처**로 전환하는 것이 올바른 방향이다.

### 5. 헬스 체크 레벨 차이

L4 헬스 체크는 TCP 포트가 열려있는지만 확인한다. 서버 프로세스가 올라와 있더라도 애플리케이션이 정상 동작하지 않는 경우(DB 커넥션 풀 고갈, 쓰레드 데드락 등)를 감지하지 못한다. L7 헬스 체크는 `/health` 엔드포인트의 HTTP 200 응답 여부를 확인하므로 훨씬 정확하다. Spring Boot Actuator의 `/actuator/health`를 헬스 체크 엔드포인트로 활용하면 DB, 캐시, 외부 의존성까지 한 번에 체크할 수 있다.

## 선택 기준 요약

```
워크로드 유형별 선택 가이드
────────────────────────────────────────────────────────

L4를 선택해야 할 때:
  ✓ TCP/UDP 기반 비-HTTP 프로토콜 (MySQL, Redis, DNS, SMTP)
  ✓ 극도로 낮은 레이턴시가 필요한 경우 (게임, 고빈도 거래)
  ✓ 암호화 트래픽을 LB에서 해독하지 말아야 하는 경우
  ✓ 고정 IP(Elastic IP)가 필요한 경우 (AWS NLB)

L7을 선택해야 할 때:
  ✓ HTTP/HTTPS 트래픽의 경로/헤더 기반 라우팅 필요
  ✓ 마이크로서비스 간 API Gateway 역할
  ✓ SSL Termination 중앙화
  ✓ 카나리 배포, A/B 테스트 트래픽 분기
  ✓ WAF(Web Application Firewall) 통합
  ✓ 정교한 헬스 체크 (HTTP 상태 코드 기반)

L4 + L7 조합:
  ✓ NLB(L4) → ALB(L7) 이중 구성으로 고정 IP + 경로 라우팅 동시 확보
  ✓ 대규모 트래픽 진입점은 L4로 받고, 내부 라우팅은 L7로 처리
```

## 정리

L4와 L7 로드 밸런서는 "어느 것이 더 좋다"의 문제가 아니라 **"어느 계층의 정보가 분산 결정에 필요한가"**의 문제다. 단순 TCP 트래픽 분산이나 극한의 성능이 필요하다면 L4가 답이고, HTTP 기반의 정교한 라우팅과 풍부한 기능이 필요하다면 L7이 맞다. 많은 프로덕션 환경에서는 두 계층을 조합하여 사용한다.

무엇보다 중요한 것은 로드 밸런서 선택이 단순한 인프라 결정에 그치지 않는다는 점이다. SSL 전략, 세션 관리 방식, 서비스 배포 전략과 긴밀하게 연결되어 있으므로 서비스 아키텍처 전반을 고려한 결정이 필요하다. 설정 한 줄 차이가 프로덕션 장애로 이어질 수 있는 영역인 만큼, 도입 전 충분한 부하 테스트와 페일오버 시나리오 검증은 필수다.
