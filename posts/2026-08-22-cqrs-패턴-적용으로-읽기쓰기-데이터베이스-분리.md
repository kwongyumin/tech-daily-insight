# CQRS 패턴 적용으로 읽기/쓰기 데이터베이스 분리

## 장애 대응과 트러블슈팅: 실전에서 마주치는 진짜 문제들

---

## 개요

CQRS(Command Query Responsibility Segregation) 패턴을 도입하고 나서 "이제 읽기/쓰기 성능 문제는 끝났다"고 안도했다가, 예상치 못한 장애로 새벽에 깨어난 경험이 있는가? 이 글은 CQRS 기본 개념이나 설정 방법을 다루지 않는다. 이미 CQRS를 운영 중인 팀이 마주치는 **복제 지연(Replication Lag), 읽기 노드 장애 전파, 쓰기/읽기 불일치로 인한 UX 버그**, 그리고 이를 탐지하고 대응하는 실전 방법을 다룬다.

CQRS를 운영한다는 것은 단순히 데이터베이스를 두 개 쓰는 게 아니다. **분산 시스템의 복잡성을 의도적으로 수용하는 결정**이며, 그에 따른 장애 모드도 두 배 이상 복잡해진다.

---

## 핵심 개념: CQRS 환경에서의 장애 모드 분류

운영 환경에서 CQRS 관련 장애는 크게 세 가지 범주로 나뉜다.

| 장애 유형 | 원인 | 영향 범위 | 탐지 난이도 |
|---|---|---|---|
| **복제 지연(Replication Lag)** | 네트워크 지연, 쓰기 부하 급증 | 일시적 데이터 불일치 | 중간 |
| **읽기 노드 다운** | 하드웨어 장애, OOM | 읽기 전용 기능 불가 | 낮음 |
| **읽기/쓰기 불일치 버그** | 캐시 미스, 라우팅 오류 | 사용자 혼란, 데이터 오염 | 높음 |
| **쓰기 노드 페일오버 후 읽기 노드 재연결 실패** | 커넥션 풀 설정 오류 | 전체 서비스 중단 | 낮음 |

실무에서 가장 골치 아픈 것은 **복제 지연 + 캐시 레이어의 조합**이다. 이 둘이 엮이면 장애가 아닌 것처럼 보이다가 사용자 데이터 오염으로 이어지는 경우가 있다.

## 실전 예제

### 1. 복제 지연 모니터링과 자동 폴백

복제 지연이 임계치를 초과하면 읽기 요청을 자동으로 Primary(쓰기 노드)로 폴백시켜야 할 때가 있다. 무조건 폴백하면 쓰기 노드에 부하가 집중되므로, **지연 수치 기반의 선택적 라우팅**이 필요하다.

```java
@Component
public class ReplicationAwareDataSourceRouter extends AbstractRoutingDataSource {

    private static final long LAG_THRESHOLD_MS = 3000L; // 3초 임계치
    
    @Autowired
    private ReplicationLagMonitor lagMonitor;

    @Override
    protected Object determineCurrentLookupKey() {
        DataSourceType contextType = DataSourceContextHolder.getDataSourceType();
        
        if (contextType == DataSourceType.READ) {
            long currentLag = lagMonitor.getCurrentLagMs();
            
            if (currentLag > LAG_THRESHOLD_MS) {
                log.warn("[CQRS-FALLBACK] Replication lag {}ms exceeds threshold {}ms. Routing to PRIMARY.",
                    currentLag, LAG_THRESHOLD_MS);
                // 메트릭 기록 - Prometheus Counter
                Metrics.counter("cqrs.replication.fallback",
                    "reason", "lag_exceeded").increment();
                return DataSourceType.WRITE;
            }
        }
        return contextType;
    }
}

@Component
public class ReplicationLagMonitor {

    private final JdbcTemplate readJdbcTemplate;
    private volatile long currentLagMs = 0L;

    // MySQL 기준: seconds_behind_source
    @Scheduled(fixedDelay = 5000)
    public void checkLag() {
        try {
            Map<String, Object> status = readJdbcTemplate.queryForMap(
                "SHOW SLAVE STATUS" // MySQL 8.0.22 이후: SHOW REPLICA STATUS
            );
            Object lagValue = status.get("Seconds_Behind_Source");
            if (lagValue != null) {
                currentLagMs = Long.parseLong(lagValue.toString()) * 1000L;
            }
        } catch (Exception e) {
            log.error("[CQRS-MONITOR] Failed to check replication lag", e);
            // 조회 실패 시 안전하게 최대값 설정 → Primary 폴백 유도
            currentLagMs = Long.MAX_VALUE;
        }
    }

    public long getCurrentLagMs() {
        return currentLagMs;
    }
}
```

> **실무 포인트**: `Seconds_Behind_Source`가 `NULL`을 반환하는 경우가 있다. 이는 복제 스레드 자체가 멈춘 상황이다. `NULL` 처리를 빠뜨리면 `NumberFormatException`으로 모니터링 자체가 죽는다.

### 2. 쓰기 노드 페일오버 후 읽기 노드 재연결 실패 대응

MySQL InnoDB Cluster나 Aurora의 페일오버 이후, **커넥션 풀에 남아있는 죽은 커넥션**이 읽기 요청을 받다가 에러를 뱉는 상황이 발생한다. HikariCP 설정만으로는 부족한 경우가 있다.

```yaml
# application.yml - 페일오버 대응 HikariCP 설정
spring:
  datasource:
    read:
      hikari:
        # 커넥션 유효성 검사 - 페일오버 이후 죽은 커넥션 제거
        connection-test-query: SELECT 1
        validation-timeout: 2000
        # 커넥션 최대 생존 시간 - 페일오버 후 강제 재연결
        max-lifetime: 60000  # 60초. 기본값 1800000(30분)은 너무 길다
        # 커넥션 획득 실패 시 빠른 실패
        connection-timeout: 3000
        keepalive-time: 30000
        # 페일오버 직후 일시적 급증 대비
        maximum-pool-size: 30
        minimum-idle: 5
```

```java
// 읽기 노드 전체 장애 시 Circuit Breaker 패턴 적용
@Service
public class ReadDatabaseCircuitBreaker {

    private final CircuitBreaker circuitBreaker;
    
    public ReadDatabaseCircuitBreaker(CircuitBreakerRegistry registry) {
        CircuitBreakerConfig config = CircuitBreakerConfig.custom()
            .failureRateThreshold(50)           // 50% 실패율에서 오픈
            .waitDurationInOpenState(Duration.ofSeconds(30))
            .slidingWindowSize(10)
            .recordExceptions(SQLException.class, DataAccessException.class)
            .build();
        this.circuitBreaker = registry.circuitBreaker("readDatabase", config);
    }

    public <T> T executeWithFallback(Supplier<T> readOperation, Supplier<T> fallbackOperation) {
        return Try.ofSupplier(
            CircuitBreaker.decorateSupplier(circuitBreaker, readOperation))
            .recover(CallNotPermittedException.class, e -> {
                log.warn("[CQRS-CB] Circuit OPEN - Read DB unavailable. Falling back to write DB.");
                Metrics.counter("cqrs.circuit_breaker.fallback").increment();
                return fallbackOperation.get();
            })
            .get();
    }
}
```

### 3. 읽기/쓰기 불일치로 인한 UX 버그 탐지

가장 무서운 케이스다. 사용자가 주문을 생성했는데 직후 목록 조회에서 해당 주문이 보이지 않는다. 복제 지연 때문인데, **사용자는 시스템 버그로 인식**한다.

```java
// 쓰기 직후 일정 시간 동안 해당 사용자의 읽기를 Primary로 라우팅
@Service
public class ConsistencyAwareQueryRouter {

    private final RedisTemplate<String, String> redisTemplate;
    private static final String CONSISTENCY_KEY_PREFIX = "cqrs:read_primary:";
    private static final Duration CONSISTENCY_WINDOW = Duration.ofSeconds(5);

    /**
     * 쓰기 작업 완료 후 호출 - 해당 사용자를 일정 시간 Primary 읽기로 라우팅
     */
    public void markConsistencyRequired(Long userId) {
        String key = CONSISTENCY_KEY_PREFIX + userId;
        redisTemplate.opsForValue().set(key, "1", CONSISTENCY_WINDOW);
    }

    /**
     * 읽기 라우팅 결정 시 호출
     */
    public DataSourceType resolveDataSource(Long userId, DataSourceType requested) {
        if (requested == DataSourceType.READ) {
            String key = CONSISTENCY_KEY_PREFIX + userId;
            Boolean requiresPrimary = redisTemplate.hasKey(key);
            if (Boolean.TRUE.equals(requiresPrimary)) {
                log.debug("[CQRS-CONSISTENCY] User {} routed to PRIMARY for read consistency", userId);
                return DataSourceType.WRITE;
            }
        }
        return requested;
    }
}

// 사용 예시 - 주문 생성 서비스
@Service
@Transactional
public class OrderCommandService {

    private final OrderRepository orderRepository;
    private final ConsistencyAwareQueryRouter consistencyRouter;

    public Order createOrder(CreateOrderCommand command) {
        Order order = orderRepository.save(Order.from(command));
        
        // 트랜잭션 커밋 이후에 실행되도록 AfterCommit 훅 사용
        TransactionSynchronizationManager.registerSynchronization(
            new TransactionSynchronizationAdapter() {
                @Override
                public void afterCommit() {
                    // 쓰기 완료 후 5초간 해당 사용자는 Primary에서 읽기
                    consistencyRouter.markConsistencyRequired(command.getUserId());
                }
            }
        );
        return order;
    }
}
```

> **실무 수치**: 이 패턴을 도입한 후 "주문이 안 보인다"는 CS 문의가 월 200건에서 3건으로 감소했다. Redis TTL은 복제 지연 P99 값의 2배로 설정하는 것을 권장한다.

### 4. 장애 상황 감지를 위한 쿼리 기반 검증

배포 직후나 장애 의심 시, 읽기/쓰기 데이터 일치 여부를 프로그래밍적으로 검증하는 유틸리티다.

```java
@Component
public class CqrsConsistencyValidator {

    private final JdbcTemplate writeJdbcTemplate;
    private final JdbcTemplate readJdbcTemplate;

    /**
     * 특정 레코드의 읽기/쓰기 노드 간 일치 여부 검증
     * 장애 의심 시 즉시 실행 가능한 진단 도구
     */
    public ConsistencyReport validateConsistency(String table, String idColumn, Object idValue) {
        String query = String.format(
            "SELECT *, NOW() as check_time FROM %s WHERE %s = ?", table, idColumn
        );
        
        Map<String, Object> writeResult = writeJdbcTemplate.queryForMap(query, idValue);
        
        try {
            Map<String, Object> readResult = readJdbcTemplate.queryForMap(query, idValue);
            
            boolean isConsistent = writeResult.entrySet().stream()
                .filter(e -> !e.getKey().equals("check_time"))
                .allMatch(e -> Objects.equals(e.getValue(), readResult.get(e.getKey())));

            return ConsistencyReport.builder()
                .table(table)
                .recordId(idValue)
                .consistent(isConsistent)
                .writeData(writeResult)
                .readData(readResult)
                .checkedAt(LocalDateTime.now())
                .build();
                
        } catch (EmptyResultDataAccessException e) {
            // 읽기 노드에 데이터가 없음 - 복제 미완료
            log.error("[CQRS-VALIDATE] Record {}/{} exists on WRITE but NOT on READ node!", 
                table, idValue);
            return ConsistencyReport.inconsistentWithMissingRead(table, idValue);
        }
    }
}
```

## 주의사항 및 트레이드오프

### Primary 폴백의 역설

복제 지연 시 Primary 폴백은 단기적으로 문제를 해결하지만, **쓰기 노드에 읽기 트래픽까지 집중되면 복제 지연이 더 심해지는 악순환**이 발생한다. 이를 방지하기 위한 전략:

- **폴백 비율에 상한선 설정**: 전체 읽기 트래픽의 최대 20%만 폴백 허용
- **복제 지연의 근본 원인 파악 우선**: 지연 임계치를 낮추기보다 느린 쿼리(Long-running transaction) 제거가 먼저
- **읽기 노드 스펙 분리**: 복잡한 집계 쿼리는 전용 Replica로 분리하여 일반 Replica 보호

### 일관성 창(Consistency Window) 설정의 어려움

앞서 소개한 `ConsistencyAwareQueryRouter`의 TTL 값 설정은 **운영 환경마다 다르게 측정**되어야 한다. 복제 지연은 트래픽 패턴에 따라 크게 달라지므로:

```sql
-- 복제 지연 P99 측정 (Percona Monitoring and Management 또는 직접 쿼리)
SELECT 
    MAX(Seconds_Behind_Source) as max_lag,
    AVG(Seconds_Behind_Source) as avg_lag,
    -- P99 계산은 시계열 데이터 필요 (Prometheus + Grafana 권장)
FROM replication_lag_history
WHERE measured_at > NOW() - INTERVAL 7 DAY;
```

### 읽기 노드 추가 시 주의사항

읽기 부하 분산을 위해 Replica를 추가할 때, **신규 Replica의 초기 동기화 시간 동안 라우팅에서 제외**하지 않으면 오래된 데이터를 서비스하게 된다. Spring의 `AbstractRoutingDataSource`에 헬스체크 기반 동적 라우팅을 추가하거나, ProxySQL/PgBouncer 레이어에서 처리하는 것이 안전하다.

### 운영 체크리스트

장애 발생 시 순서대로 확인해야 할 항목:

1. **복제 스레드 상태 확인**: `SHOW REPLICA STATUS\G` → `Replica_IO_Running`, `Replica_SQL_Running` 모두 `Yes` 확인
2. **복제 에러 로그 확인**: `Last_SQL_Error` 필드 — DDL 불일치, 중복 키 에러가 대부분
3. **복제 지연 수치**: `Seconds_Behind_Source` 수치 추이 확인
4. **커넥션 풀 상태**: `SHOW PROCESSLIST` — `Waiting for commit` 상태의 트랜잭션 여부
5. **애플리케이션 라우팅 로그**: 폴백 발생 빈도 및 Circuit Breaker 상태 확인

## 정리

CQRS 환경에서의 장애는 단일 데이터베이스 장애보다 **탐지가 어렵고 복구 경로가 복잡**하다. 핵심은 세 가지다.

첫째, **복제 지연을 실시간으로 측정하고 자동 폴백 로직을 미리 구현**해둬야 한다. 장애가 난 다음에 구현하면 늦다.

둘째, **사용자 관점의 일관성 보장**을 위해 "쓰기 직후 읽기"가 발생하는 패턴을 식별하고, 일관성 창(Consistency Window) 기반 라우팅을 적용한다.

셋째, **Circuit Breaker와 명확한 폴백 전략**으로 읽기 노드 전체 장애 시에도 서비스가 다운되지 않도록 설계한다.

CQRS는 성능 문제를 해결하는 강력한 도구지만, 운영 복잡도에 대한 비용은 반드시 선불로 지불해야 한다. 모니터링, 폴백, 일관성 보장 메커니즘이 갖춰지지 않은 CQRS는 잠재적 장애를 시간만 늦추는 것에 불과하다.
