# BGP와 애니캐스트 기반 글로벌 트래픽 분산

## 개요

글로벌 서비스를 운영하다 보면 필연적으로 "어떻게 전 세계 사용자에게 가장 빠른 응답을 줄 것인가"라는 문제에 직면한다. DNS 기반 지역 라우팅(GeoDNS)이 가장 흔히 거론되지만, 이보다 더 낮은 레이어에서 동작하며 더 강력한 제어를 가능하게 하는 기술이 바로 **BGP(Border Gateway Protocol)** 와 **애니캐스트(Anycast)** 다.

Cloudflare, Fastly 같은 CDN 업체나 Google의 Public DNS(8.8.8.8)가 이 조합을 사용한다는 건 알려진 사실이다. 하지만 "우리가 직접 이걸 구현한다면 어떻게 해야 하는가"에 대한 실질적인 설명은 의외로 드물다. 이 글에서는 BGP와 애니캐스트의 동작 원리를 명확히 정리하고, 실제 인프라에서 적용할 수 있는 구성 방법과 트레이드오프를 다룬다.

## 핵심 개념

### BGP란 무엇인가

BGP는 인터넷에서 AS(Autonomous System, 자율 시스템) 간 라우팅 정보를 교환하는 프로토콜이다. 각 AS는 고유한 ASN(AS Number)을 가지며, 자신이 도달할 수 있는 IP 프리픽스(prefix)를 BGP를 통해 이웃 AS에 광고(advertise)한다.

```
AS 65001 (우리 회사) ─── BGP ─── AS 3356 (Lumen/Level3)
                                        │
                                   AS 1299 (Telia)
                                        │
                                  AS 7018 (AT&T)
```

BGP의 핵심은 **정책 기반 라우팅**이다. 단순히 최단 경로가 아니라, AS Path, Local Preference, MED(Multi-Exit Discriminator), Community 등 다양한 속성을 통해 트래픽 경로를 세밀하게 제어할 수 있다.

### 애니캐스트란 무엇인가

유니캐스트(Unicast)는 1:1 통신, 멀티캐스트(Multicast)는 1:N 그룹 통신, 브로드캐스트는 1:전체 통신이다. **애니캐스트(Anycast)** 는 동일한 IP 주소를 여러 지점에서 동시에 광고하고, 네트워크 토폴로지상 가장 가까운 노드로 트래픽이 라우팅되는 방식이다.

```
클라이언트 (서울)
    │
    └──→ 192.0.2.1 로 패킷 전송
              │
         [BGP 라우팅]
              │
    ┌─────────┴─────────┐
    │ 서울 PoP          │ 도쿄 PoP
    │ 192.0.2.1 광고 중  │ 192.0.2.1 광고 중
    │ ← 더 가까움        │
    └───────────────────┘
```

서울 클라이언트의 패킷은 BGP 라우팅 테이블 기준으로 더 짧은 AS Path를 가진 서울 PoP으로 향한다. 별도의 DNS 리디렉션 없이 **IP 레이어에서 자동으로 가장 가까운 서버로 연결**된다.

### GeoDNS와의 비교

| 항목 | GeoDNS | Anycast + BGP |
|------|--------|---------------|
| 동작 레이어 | 애플리케이션(DNS) | 네트워크(IP) |
| 전환 속도 | DNS TTL 의존 (수십 초~수 분) | BGP 수렴 시간 (수 초~수십 초) |
| 세분성 | IP 대역 기반 지역 추정 | 실제 네트워크 경로 기반 |
| 구현 복잡도 | 낮음 | 높음 (ASN, PI 주소, IX 필요) |
| 장애 복구 | TTL만큼 지연 | BGP 경로 철회로 빠른 전환 |
| TCP 세션 처리 | 세션 유지 가능 | Failover 시 세션 단절 가능 |

## 실전 예제

### 사전 조건

애니캐스트 기반 글로벌 트래픽 분산을 직접 구현하려면 다음이 필요하다.

- **ASN(자율 시스템 번호)**: ARIN, RIPE, APNIC 등 지역 인터넷 레지스트리에서 발급
- **PI(Provider-Independent) IP 블록**: ISP에 종속되지 않는 독립 IP 주소 블록
- **각 PoP에서의 업스트림 ISP 또는 IX(인터넷 교환 포인트) 연결**
- **BGP 라우터 소프트웨어**: BIRD, FRRouting(FRR), Quagga 등

### BIRD를 이용한 BGP 설정 예제

**BIRD**는 오픈소스 라우팅 데몬으로, 소프트웨어 라우터 구성에 널리 사용된다.

```bash
# /etc/bird/bird.conf (서울 PoP 기준)

# 라우터 ID 설정
router id 203.0.113.1;

# 애니캐스트로 광고할 프리픽스 정의
protocol static ANYCAST_ROUTES {
    ipv4;
    route 192.0.2.0/24 blackhole;  # 실제로는 로컬 서버로 라우팅
}

# 업스트림 ISP와의 BGP 세션
protocol bgp UPSTREAM_KR {
    local 203.0.113.1 as 65001;
    neighbor 198.51.100.1 as 3356;  # 업스트림 ISP ASN

    ipv4 {
        import filter {
            # 기본 경로(default route)만 수신
            if net = 0.0.0.0/0 then accept;
            reject;
        };
        export filter {
            # 애니캐스트 프리픽스만 광고
            if net = 192.0.2.0/24 then {
                bgp_community.add((65001, 100));  # 커뮤니티 태깅
                accept;
            }
            reject;
        };
    };
}
```

### 헬스체크 기반 BGP 경로 자동 철회

노드 장애 시 BGP 광고를 자동으로 철회하는 것이 애니캐스트 운영의 핵심이다. ExaBGP를 활용한 헬스체크 연동 예시다.

```python
# healthcheck.py - ExaBGP와 연동하는 헬스체크 스크립트

import subprocess
import sys
import time
import requests
from datetime import datetime

ANYCAST_PREFIX = "192.0.2.0/24"
LOCAL_SERVICE_URL = "http://127.0.0.1:8080/health"
CHECK_INTERVAL = 5  # seconds
FAIL_THRESHOLD = 3

fail_count = 0
is_announcing = False

def check_health() -> bool:
    try:
        resp = requests.get(LOCAL_SERVICE_URL, timeout=2)
        return resp.status_code == 200
    except Exception:
        return False

def announce_route():
    """ExaBGP API를 통해 경로 광고"""
    sys.stdout.write(f"announce route {ANYCAST_PREFIX} next-hop self\n")
    sys.stdout.flush()

def withdraw_route():
    """ExaBGP API를 통해 경로 철회"""
    sys.stdout.write(f"withdraw route {ANYCAST_PREFIX} next-hop self\n")
    sys.stdout.flush()

def log(msg: str):
    print(f"[{datetime.now().isoformat()}] {msg}", file=sys.stderr)

def main():
    global fail_count, is_announcing

    while True:
        healthy = check_health()

        if healthy:
            fail_count = 0
            if not is_announcing:
                log("Service healthy. Announcing anycast route.")
                announce_route()
                is_announcing = True
        else:
            fail_count += 1
            log(f"Health check failed ({fail_count}/{FAIL_THRESHOLD})")

            if fail_count >= FAIL_THRESHOLD and is_announcing:
                log("Withdrawing anycast route due to repeated failures.")
                withdraw_route()
                is_announcing = False

        time.sleep(CHECK_INTERVAL)

if __name__ == "__main__":
    main()
```

```ini
# /etc/exabgp/exabgp.conf

process healthcheck {
    run /usr/bin/python3 /opt/bgp/healthcheck.py;
    encoder text;
}

neighbor 198.51.100.1 {
    router-id 203.0.113.1;
    local-address 203.0.113.1;
    local-as 65001;
    peer-as 3356;

    family {
        ipv4 unicast;
    }

    api {
        processes [healthcheck];
    }
}
```

### 로컬 서버로의 트래픽 포워딩 (Linux 기준)

애니캐스트 IP를 loopback에 바인딩하고, 실제 서비스 포트로 포워딩하는 설정이다.

```bash
# 애니캐스트 IP를 loopback에 추가 (arp 광고 없이)
ip addr add 192.0.2.1/32 dev lo

# 커널 파라미터 설정 (ARP 응답 방지)
sysctl -w net.ipv4.conf.all.arp_ignore=1
sysctl -w net.ipv4.conf.all.arp_announce=2

# iptables를 통해 애니캐스트 IP로 들어오는 트래픽을 로컬 서비스로 포워딩
iptables -t nat -A PREROUTING -d 192.0.2.1 -p tcp --dport 80 \
    -j DNAT --to-destination 127.0.0.1:8080

iptables -t nat -A PREROUTING -d 192.0.2.1 -p tcp --dport 443 \
    -j DNAT --to-destination 127.0.0.1:8443
```

## 주의사항 및 트레이드오프

### 1. TCP 세션과 Failover 문제

애니캐스트의 가장 큰 약점은 **TCP 세션의 취약성**이다. BGP 경로가 변경되면(예: 장애로 인한 경로 철회), 진행 중인 TCP 연결이 갑자기 다른 PoP으로 라우팅될 수 있다. 새로운 PoP은 해당 세션 상태를 모르므로 연결이 끊어진다.

**완화 방법:**
- UDP 기반 프로토콜(DNS, QUIC)에는 애니캐스트가 훨씬 안전하다
- TCP 서비스의 경우, 세션 상태를 중앙 스토리지(Redis Cluster 등)에 저장하거나
- ECMP(Equal-Cost Multi-Path)가 아닌 경우에는 단일 경로가 유지되는 경향이 있어 실제론 세션이 비교적 안정적으로 유지되기도 한다

### 2. BGP 수렴 시간

BGP는 즉각적인 프로토콜이 아니다. 경로 변경이 전체 인터넷에 전파되는 데는 보통 수십 초에서 수 분이 걸릴 수 있다. 이 시간 동안 일부 사용자는 이미 다운된 PoP으로 트래픽이 라우팅될 수 있다.

```
# BGP 타이머 튜닝 예시 (BIRD)
protocol bgp UPSTREAM {
    ...
    hold time 30;          # 기본값 보통 90초, 줄여서 빠른 감지
    keepalive time 10;
    connect retry time 10;
}
```

### 3. 비대칭 라우팅

인바운드 트래픽은 애니캐스트로 가장 가까운 PoP에 도달하지만, 아웃바운드 응답 트래픽은 업스트림 ISP 정책에 따라 다른 경로로 나갈 수 있다. 이는 디버깅을 복잡하게 만들고, 경우에 따라 방화벽 상태 추적(stateful inspection)에 문제를 일으킬 수 있다.

### 4. 운영 복잡도와 진입장벽

- ASN과 PI 주소 블록 획득에는 비용과 시간이 필요하다
- IX(인터넷 교환 포인트) 연결을 통해 더 많은 피어와 직접 연결할수록 라우팅 품질이 향상되지만, 각 IX 멤버십도 비용이 발생한다
- BGP 운영은 고도의 네트워크 전문 지식을 요구한다. 잘못된 BGP 설정은 "BGP 하이재킹"과 유사한 효과를 낼 수 있어 인터넷 전반에 영향을 줄 수 있다

### 5. 소규모 서비스에는 과도한 복잡도

이 아키텍처는 최소 3개 이상의 PoP을 운영하고, 상당한 트래픽이 존재하며, 네트워크 전문 인력이 있는 조직에 적합하다. 소규모 서비스라면 Cloudflare Spectrum, AWS Global Accelerator처럼 애니캐스트를 추상화해서 제공하는 매니지드 서비스를 활용하는 것이 현명하다.

```
# AWS Global Accelerator는 내부적으로 애니캐스트를 활용
# 직접 구현 없이 비슷한 효과를 얻을 수 있음
aws globalaccelerator create-accelerator \
    --name my-global-service \
    --ip-address-type IPV4 \
    --enabled
```

## 정리

BGP와 애니캐스트 기반 글로벌 트래픽 분산은 DNS 레이어 위에서의 편법 없이 **IP 네트워크 레이어에서 근본적으로** 트래픽을 제어하는 강력한 접근 방식이다.

핵심을 정리하면 다음과 같다.

1. **애니캐스트**는 동일 IP를 여러 지점에서 광고해 클라이언트를 가장 가까운 서버로 자연스럽게 유도한다
2. **BGP**는 그 경로 광고와 철회를 제어하는 프로토콜로, 헬스체크와 연동하면 자동 장애 복구가 가능하다
3. **UDP 기반 서비스(DNS, NTP, QUIC)** 에 가장 잘 맞으며, TCP 서비스에는 세션 처리에 추가 고려가 필요하다
4. **직접 구현**은 ASN, PI 블록, BGP 운영 전문성이 필요한 반면, **매니지드 서비스**는 이를 추상화해 준다

글로벌 서비스 아키텍처를 설계할 때 GeoDNS → 매니지드 Anycast(Global Accelerator 등) → 자체 BGP/Anycast 순으로 복잡도와 제어력이 올라간다고 이해하면, 현재 조직의 규모와 요구사항에 맞는 선택을 할 수 있을 것이다.
