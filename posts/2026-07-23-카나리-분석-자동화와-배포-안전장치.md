# 카나리 분석 자동화와 배포 안전장치

## 개요

현대 소프트웨어 배포 환경에서 "배포는 성공했지만 서비스는 망가졌다"는 아이러니한 상황은 생각보다 자주 발생한다. CI/CD 파이프라인이 아무리 잘 구축되어 있어도, 프로덕션 트래픽을 실제로 받아보기 전까지는 알 수 없는 문제들이 존재하기 때문이다.

카나리 배포(Canary Deployment)는 이런 문제를 완화하기 위한 전략으로, 신버전을 전체 사용자에게 한꺼번에 노출하지 않고 일부에게만 점진적으로 트래픽을 전환하는 방식이다. 그런데 많은 팀들이 카나리 배포를 "도입했다"고 하면서도, 실제로는 담당자가 수동으로 메트릭을 확인하고 판단하는 반자동화 상태에 머물러 있다.

이 글에서는 카나리 분석을 자동화하고, 이상이 감지됐을 때 자동으로 롤백을 트리거하는 **배포 안전장치(Deployment Safety Gate)** 구축 방법을 실전 예제와 함께 다룬다.

---

## 핵심 개념

### 카나리 분석이란?

카나리 배포의 핵심은 단순히 트래픽을 나누는 것이 아니라, **기준 버전(Baseline)과 신버전(Canary)의 메트릭을 정량적으로 비교하는 것**이다. 이 비교 프로세스를 카나리 분석(Canary Analysis)이라고 한다.

분석 대상 메트릭은 보통 세 가지 카테고리로 나뉜다.

| 카테고리 | 예시 |
|---|---|
| 오류율 | HTTP 5xx 비율, Exception 발생 횟수 |
| 레이턴시 | P50, P95, P99 응답시간 |
| 비즈니스 지표 | 결제 성공률, 로그인 성공률, 장바구니 전환율 |

### 자동화의 핵심: 판단 기준 수치화

카나리 분석 자동화의 핵심 난제는 "언제 롤백을 결정하는가"를 **코드로 표현**하는 것이다. 사람은 직관으로 판단하지만, 시스템은 명확한 임계값과 통계적 기준이 필요하다.

대표적인 판단 방식은 다음과 같다.

- **임계값 기반(Threshold-based)**: 에러율이 1%를 초과하면 롤백
- **상대 비교 기반(Relative comparison)**: 카나리 에러율이 기준 대비 20% 이상 높으면 롤백
- **통계적 유의성 기반(Statistical significance)**: Mann-Whitney U 검정 등으로 두 분포가 유의미하게 다른지 판단

Netflix의 Kayenta, Spinnaker의 내장 카나리 분석, 그리고 Argo Rollouts가 이 영역의 대표적인 오픈소스 도구들이다.

## 실전 예제

### 1. Argo Rollouts를 이용한 카나리 배포 설정

Kubernetes 환경에서 가장 실용적인 선택지는 **Argo Rollouts**다. 아래는 카나리 분석을 포함한 Rollout 리소스 정의다.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: payment-service
spec:
  replicas: 10
  strategy:
    canary:
      # 카나리 단계별 트래픽 비율 정의
      steps:
        - setWeight: 10   # 10% 트래픽을 카나리로
        - pause: {}       # 수동 승인 대기 (선택)
        - analysis:
            templates:
              - templateName: payment-success-rate
            args:
              - name: service-name
                value: payment-service
        - setWeight: 50
        - pause: {duration: 5m}
        - analysis:
            templates:
              - templateName: payment-success-rate
              - templateName: latency-check
        - setWeight: 100
  selector:
    matchLabels:
      app: payment-service
  template:
    metadata:
      labels:
        app: payment-service
    spec:
      containers:
        - name: payment-service
          image: my-registry/payment-service:{{.Values.imageTag}}
```

### 2. AnalysisTemplate 정의

분석 로직의 핵심인 `AnalysisTemplate`을 Prometheus 쿼리 기반으로 정의한다.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: payment-success-rate
spec:
  args:
    - name: service-name
  metrics:
    - name: payment-success-rate
      interval: 1m
      # 5분간 3번 측정, 2번 이상 실패 시 전체 분석 실패
      count: 5
      failureLimit: 1
      successCondition: result[0] >= 0.99
      provider:
        prometheus:
          address: http://prometheus.monitoring.svc.cluster.local:9090
          query: |
            sum(rate(payment_requests_total{
              service="{{args.service-name}}",
              status="success"
            }[2m])) /
            sum(rate(payment_requests_total{
              service="{{args.service-name}}"
            }[2m]))

    - name: error-rate
      interval: 1m
      count: 5
      failureLimit: 1
      # 에러율이 기준 대비 상대적으로 2배 이하여야 함
      successCondition: result[0] <= 0.01
      provider:
        prometheus:
          address: http://prometheus.monitoring.svc.cluster.local:9090
          query: |
            sum(rate(http_requests_total{
              service="{{args.service-name}}",
              status=~"5.."
            }[2m])) /
            sum(rate(http_requests_total{
              service="{{args.service-name}}"
            }[2m]))
---
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: latency-check
spec:
  metrics:
    - name: p99-latency
      interval: 1m
      count: 5
      failureLimit: 1
      # P99 레이턴시 500ms 이하
      successCondition: result[0] <= 0.5
      provider:
        prometheus:
          address: http://prometheus.monitoring.svc.cluster.local:9090
          query: |
            histogram_quantile(0.99, 
              sum(rate(http_request_duration_seconds_bucket{
                service="payment-service"
              }[2m])) by (le)
            )
```

### 3. Spring Boot 애플리케이션의 커스텀 메트릭 노출

카나리 분석이 의미 있으려면 애플리케이션이 **비즈니스 의미가 있는 메트릭**을 제대로 노출해야 한다. Micrometer를 활용한 결제 성공률 메트릭 예제다.

```java
@Service
@RequiredArgsConstructor
public class PaymentService {

    private final MeterRegistry meterRegistry;
    private final PaymentRepository paymentRepository;

    // Counter를 캐싱하여 성능 최적화
    private final Counter paymentSuccessCounter;
    private final Counter paymentFailureCounter;
    private final Timer paymentTimer;

    public PaymentService(MeterRegistry meterRegistry) {
        this.meterRegistry = meterRegistry;
        this.paymentSuccessCounter = Counter.builder("payment_requests_total")
            .tag("status", "success")
            .description("총 결제 성공 횟수")
            .register(meterRegistry);
        this.paymentFailureCounter = Counter.builder("payment_requests_total")
            .tag("status", "failure")
            .description("총 결제 실패 횟수")
            .register(meterRegistry);
        this.paymentTimer = Timer.builder("payment_duration_seconds")
            .description("결제 처리 시간")
            .publishPercentiles(0.5, 0.95, 0.99)
            .register(meterRegistry);
    }

    public PaymentResult processPayment(PaymentRequest request) {
        return paymentTimer.record(() -> {
            try {
                // 실제 결제 로직
                PaymentResult result = executePayment(request);
                
                if (result.isSuccess()) {
                    paymentSuccessCounter.increment();
                    // 결제 수단별 세분화 메트릭
                    meterRegistry.counter("payment_by_method",
                        "method", request.getPaymentMethod().name(),
                        "status", "success"
                    ).increment();
                } else {
                    paymentFailureCounter.increment();
                    meterRegistry.counter("payment_by_method",
                        "method", request.getPaymentMethod().name(),
                        "status", "failure",
                        "reason", result.getFailureReason()
                    ).increment();
                }
                return result;
                
            } catch (Exception e) {
                paymentFailureCounter.increment();
                meterRegistry.counter("payment_exceptions_total",
                    "exception", e.getClass().getSimpleName()
                ).increment();
                throw e;
            }
        });
    }
}
```

### 4. 자동 롤백 알림 연동 (Webhook)

분석 실패 시 Slack 등으로 알림을 보내는 AnalysisTemplate 확장이다.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: notify-on-failure
spec:
  metrics:
    - name: slack-notification
      provider:
        job:
          spec:
            template:
              spec:
                containers:
                  - name: notify
                    image: curlimages/curl:latest
                    command:
                      - sh
                      - -c
                      - |
                        curl -X POST $SLACK_WEBHOOK_URL \
                          -H 'Content-type: application/json' \
                          --data '{
                            "text": "🚨 카나리 분석 실패! payment-service 자동 롤백을 시작합니다.",
                            "attachments": [{
                              "color": "danger",
                              "fields": [
                                {"title": "서비스", "value": "payment-service"},
                                {"title": "이유", "value": "에러율 임계값 초과"}
                              ]
                            }]
                          }'
                    env:
                      - name: SLACK_WEBHOOK_URL
                        valueFrom:
                          secretKeyRef:
                            name: slack-secrets
                            key: webhook-url
                restartPolicy: Never
```

## 주의사항 및 트레이드오프

### ⚠️ 콜드 스타트 문제 (Warm-up Period)

카나리 분석은 충분한 트래픽이 쌓인 후에 의미가 있다. 배포 직후 트래픽이 적은 상황에서 분석을 시작하면 **통계적 노이즈**로 인한 오탐(False Positive) 롤백이 발생한다.

실무 권장 사항:
- `initialDelay` 설정으로 워밍업 시간 확보 (최소 2~5분)
- 트래픽이 적은 새벽 시간대 배포 시 `minRequestCount` 조건 추가

```yaml
metrics:
  - name: error-rate
    initialDelay: 3m   # 분석 시작 전 3분 대기
    interval: 1m
    count: 10
```

### ⚠️ 임계값 설정의 어려움

임계값이 너무 엄격하면 정상 배포도 롤백되고(False Positive), 너무 느슨하면 장애를 놓친다(False Negative). 초기에는 **기존 배포의 메트릭 히스토리를 분석해서 P95 수준을 임계값으로 설정**하고, 점진적으로 조정하는 것을 권장한다.

### ⚠️ 카나리와 기준의 환경 격리

카나리와 기준(Baseline)이 같은 데이터베이스, 같은 캐시를 공유하면 분석 결과가 오염될 수 있다. 예를 들어, 카나리에서 실행한 DB 마이그레이션이 기준 버전의 동작에 영향을 미치는 경우다.

**트레이드오프 요약:**

| 항목 | 자동화 강화 | 자동화 완화 |
|---|---|---|
| 롤백 속도 | 빠름 | 느림 |
| 오탐 롤백 위험 | 높음 | 낮음 |
| 운영 부담 | 낮음 | 높음 |
| 정밀한 판단 | 어려움 | 사람이 직접 판단 |

### ⚠️ 데이터베이스 스키마 변경과의 충돌

카나리 배포 중 DB 스키마가 변경되면 기준 버전과 카나리 버전이 동시에 서로 다른 스키마를 보게 된다. 이 경우 **Expand-Contract 패턴(병렬 배포 패턴)** 을 반드시 병행해야 한다. 스키마 변경은 하위 호환 가능한 방식으로만 배포하고, 컬럼 제거는 완전히 전환된 이후 별도 작업으로 처리해야 한다.

## 정리

카나리 분석 자동화는 "배포를 두려워하지 않는 조직"을 만드는 핵심 기반이다. 핵심을 정리하면 다음과 같다.

1. **메트릭 설계가 전부다**: 비즈니스 의미 있는 메트릭이 노출되지 않으면 분석도 의미 없다. 애플리케이션 레벨의 커스텀 메트릭 설계에 공을 들여라.

2. **점진적으로 자동화를 강화하라**: 처음부터 완전 자동 롤백을 도입하면 오탐으로 인한 팀 신뢰도 저하가 발생한다. 처음에는 알림 → 수동 승인 게이트 → 자동 롤백 순으로 단계를 밟아라.

3. **임계값은 데이터 기반으로 결정하라**: 직관에 의존하지 말고, 최소 2~4주 이상의 메트릭 히스토리를 분석한 후 임계값을 설정하라.

4. **안전장치는 배포 파이프라인의 일급 객체다**: 카나리 분석 설정은 애플리케이션 코드와 함께 Git으로 관리되어야 하며, 리뷰와 테스트의 대상이 되어야 한다.

카나리 분석 자동화는 한 번에 완성되는 시스템이 아니다. 운영하면서 오탐 케이스를 분석하고, 임계값을 조정하고, 분석 로직을 개선하는 지속적인 피드백 루프가 핵심이다. 이 루프가 잘 돌아갈 때 비로소 "배포를 자주, 안전하게" 하는 DevOps 문화가 자리 잡는다.
