# 리버스 프록시 타임아웃 설정과 502 오류 진단

## 개요

프로덕션 환경에서 갑자기 쏟아지는 502 Bad Gateway 오류만큼 당혹스러운 상황도 없다. 애플리케이션 서버는 멀쩡히 돌아가는 것 같은데 사용자 요청은 계속 실패하고, 로그를 뒤져봐도 명확한 원인을 찾기 어렵다. 이런 상황의 주범 중 하나가 바로 **리버스 프록시의 타임아웃 설정**이다.

Nginx, Apache, HAProxy 등의 리버스 프록시는 업스트림 서버(백엔드 애플리케이션)와의 통신 과정에서 다양한 타임아웃 값을 가진다. 이 값들이 잘못 설정되어 있거나 트래픽 패턴이 변했을 때 502 오류가 발생한다. 이 포스팅에서는 타임아웃의 핵심 개념부터 실전 진단 방법, 그리고 트레이드오프까지 체계적으로 다룬다.

---

## 핵심 개념

### 502 Bad Gateway란 정확히 무엇인가?

HTTP 502는 프록시 서버가 업스트림 서버로부터 유효하지 않은 응답을 받았을 때 반환된다. 흔히 "서버가 죽었을 때 나오는 에러"로 오해하지만, 실제로는 **프록시와 업스트림 간의 통신 실패** 전반을 의미한다.

502가 발생하는 주요 시나리오:

- 업스트림 서버가 완전히 다운된 경우
- 업스트림 서버가 응답 중이지만 **프록시의 타임아웃 시간을 초과**한 경우
- 업스트림 서버가 비정상적인 HTTP 응답을 반환한 경우 (연결 끊김, 불완전한 헤더 등)
- 업스트림 서버의 연결 큐가 가득 찬 경우

이 중 타임아웃 관련 502는 **업스트림이 살아있음에도 불구하고** 발생한다는 점에서 특히 진단이 까다롭다.

### 리버스 프록시 타임아웃의 종류

Nginx를 기준으로 업스트림 통신에 관여하는 핵심 타임아웃은 세 가지다.

| 설정값 | 기본값 | 의미 |
|---|---|---|
| `proxy_connect_timeout` | 60s | 업스트림과 TCP 연결을 맺는 데 허용되는 시간 |
| `proxy_send_timeout` | 60s | 업스트림에 요청을 전송하는 데 허용되는 시간 |
| `proxy_read_timeout` | 60s | 업스트림으로부터 응답을 읽는 데 허용되는 시간 |

여기서 중요한 포인트는 `proxy_read_timeout`이 **전체 응답 시간**이 아니라는 것이다. 이 값은 **연속된 두 읽기 작업 사이의 최대 대기 시간**이다. 즉, 청크 단위로 데이터가 오는 경우 각 청크 사이의 간격이 이 값을 초과하면 타임아웃이 발생한다.

```
[Client] ──→ [Nginx] ──→ [Upstream App]
                ↑               ↑
         proxy_connect  TCP Handshake
         _timeout       완료까지 대기

         proxy_send     요청 전송 완료까지 대기
         _timeout

         proxy_read     응답 첫 바이트 또는
         _timeout       다음 청크까지 대기
```

## 실전 예제

### 1. Nginx 타임아웃 설정

아래는 백엔드가 Spring Boot 애플리케이션인 경우의 실전 Nginx 설정이다.

```nginx
upstream spring_backend {
    server 127.0.0.1:8080;
    keepalive 32;  # keepalive 연결 풀 크기
}

server {
    listen 80;
    server_name api.example.com;

    location /api/ {
        proxy_pass http://spring_backend;

        # 타임아웃 설정
        proxy_connect_timeout 5s;    # 연결 수립: 짧게 유지 (빠른 실패)
        proxy_send_timeout    60s;   # 요청 전송: 대용량 업로드 고려
        proxy_read_timeout    120s;  # 응답 수신: 배치 작업 등 고려

        # keepalive 활성화 시 필수
        proxy_http_version 1.1;
        proxy_set_header Connection "";

        # 헤더 전달
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 버퍼 설정 (대용량 응답 시 튜닝)
        proxy_buffer_size        16k;
        proxy_buffers            8 16k;
        proxy_busy_buffers_size  32k;
    }

    # 오래 걸리는 작업 전용 엔드포인트
    location /api/batch/ {
        proxy_pass http://spring_backend;
        proxy_read_timeout 600s;  # 배치 작업: 10분
        proxy_connect_timeout 5s;
        proxy_send_timeout 60s;
    }
}
```

### 2. 502 오류 진단 스크립트

실제 운영 중에 502가 발생하면 다음 스크립트로 빠르게 원인을 좁힐 수 있다.

```bash
#!/bin/bash
# 502 오류 진단 스크립트
# Usage: ./diag_502.sh <upstream_host> <upstream_port>

UPSTREAM_HOST=${1:-"127.0.0.1"}
UPSTREAM_PORT=${2:-"8080"}
NGINX_ERROR_LOG="/var/log/nginx/error.log"

echo "===== 502 오류 진단 시작 ====="

# 1. 업스트림 연결 가능 여부 확인
echo "[1] 업스트림 TCP 연결 테스트"
timeout 5 bash -c "echo > /dev/tcp/$UPSTREAM_HOST/$UPSTREAM_PORT" 2>&1
if [ $? -eq 0 ]; then
    echo "  ✓ TCP 연결 성공"
else
    echo "  ✗ TCP 연결 실패 - 업스트림 서버 확인 필요"
fi

# 2. 업스트림 응답 시간 측정
echo "[2] 업스트림 응답 시간 측정"
RESPONSE_TIME=$(curl -o /dev/null -s -w "%{time_total}" \
    --max-time 30 \
    "http://$UPSTREAM_HOST:$UPSTREAM_PORT/actuator/health" 2>/dev/null)
echo "  응답 시간: ${RESPONSE_TIME}s"

# 3. Nginx 오류 로그에서 타임아웃 패턴 추출
echo "[3] 최근 5분간 Nginx 오류 로그 분석"
SINCE=$(date -d '5 minutes ago' '+%Y/%m/%d %H:%M' 2>/dev/null || \
        date -v-5M '+%Y/%m/%d %H:%M')

grep "upstream timed out" "$NGINX_ERROR_LOG" | tail -20 | \
    awk '{print $1, $2, $NF}' | sort | uniq -c | sort -rn

echo ""
grep "connect() failed" "$NGINX_ERROR_LOG" | tail -10

# 4. 현재 업스트림 연결 상태
echo "[4] 업스트림 연결 상태 (netstat)"
ss -tn state established "( dport = :$UPSTREAM_PORT or sport = :$UPSTREAM_PORT )" | \
    awk 'NR>1 {print $4, $5}' | sort | uniq -c

# 5. 업스트림 서버 소켓 백로그 확인
echo "[5] 업스트림 포트 상태"
ss -tlnp "sport = :$UPSTREAM_PORT"

echo "===== 진단 완료 ====="
```

### 3. Nginx 로그로 타임아웃 패턴 분석

502 원인 분석에는 Nginx 로그 포맷을 확장하는 것이 효과적이다.

```nginx
# nginx.conf - 확장 로그 포맷
log_format detailed_upstream
    '$remote_addr - $remote_user [$time_local] '
    '"$request" $status $body_bytes_sent '
    '"$http_referer" "$http_user_agent" '
    'rt=$request_time '           # 전체 요청 처리 시간
    'uct=$upstream_connect_time ' # 업스트림 연결 시간
    'uht=$upstream_header_time '  # 업스트림 헤더 수신 시간
    'urt=$upstream_response_time' # 업스트림 응답 시간
    'us=$upstream_status';        # 업스트림 HTTP 상태코드

access_log /var/log/nginx/access.log detailed_upstream;
```

이 포맷으로 기록된 로그를 분석하는 스크립트:

```bash
# 타임아웃 유발 요청 분석 (응답 시간이 100초 이상인 요청)
awk '
/urt=[0-9]/ {
    match($0, /urt=([0-9.]+)/, arr)
    if (arr[1]+0 > 100) {
        match($0, /"([A-Z]+ [^ ]+)/, req)
        print arr[1]"s\t"req[1]
    }
}
' /var/log/nginx/access.log | sort -rn | head -20

# 업스트림 연결 실패 비율 계산
awk '
{
    total++
    if ($0 ~ /us=502|us=503/) failed++
}
END {
    printf "전체 요청: %d, 실패: %d, 실패율: %.2f%%\n",
        total, failed, (failed/total)*100
}
' /var/log/nginx/access.log
```

### 4. Spring Boot 측 설정 (업스트림 관점)

프록시의 타임아웃만 조정한다고 끝이 아니다. 업스트림인 Spring Boot도 맞춰서 설정해야 한다.

```yaml
# application.yml
server:
  tomcat:
    connection-timeout: 5000          # 클라이언트 연결 수립 타임아웃 (ms)
    keep-alive-timeout: 65000         # keepalive 유지 시간 (Nginx keepalive보다 길게)
    max-keep-alive-requests: 1000     # keepalive당 최대 요청 수
    threads:
      max: 200
      min-spare: 20
    accept-count: 100                 # 연결 대기 큐 크기

spring:
  mvc:
    async:
      request-timeout: 120000         # 비동기 요청 타임아웃 (ms)
```

```java
// 오래 걸리는 API에 타임아웃 명시
@RestController
@RequestMapping("/api/batch")
public class BatchController {

    @PostMapping("/process")
    @Timeout(value = 300, unit = TimeUnit.SECONDS)  // Resilience4j
    public ResponseEntity<BatchResult> processBatch(@RequestBody BatchRequest request) {
        // 배치 처리 로직
        return ResponseEntity.ok(batchService.process(request));
    }
}
```

## 주의사항 및 트레이드오프

### 1. `proxy_connect_timeout`은 짧게 유지하라

연결 타임아웃을 길게 설정하면 업스트림이 죽었을 때 **장애 감지가 늦어진다**. 60초짜리 `proxy_connect_timeout`이 설정되어 있다면, 업스트림이 다운된 후 최대 60초 동안 모든 요청이 블로킹된다. 보통 3~10초 수준이 적절하다.

### 2. keepalive와 타임아웃의 관계

Nginx upstream keepalive를 사용하면 TCP 연결을 재사용하여 성능이 향상된다. 하지만 주의할 점이 있다. **Nginx의 `keepalive_timeout`이 업스트림(Tomcat)의 `keep-alive-timeout`보다 짧아야** 한다. 그렇지 않으면 Tomcat이 이미 닫은 연결로 요청을 보내다 502가 발생한다.

```
Nginx keepalive_timeout < Tomcat keep-alive-timeout
(예: Nginx 60s         < Tomcat 65s)
```

### 3. 타임아웃을 무작정 늘리는 것의 위험

`proxy_read_timeout`을 600초로 늘리면 당장 502는 사라질 수 있다. 하지만 이는 **느린 업스트림 요청이 Nginx 워커를 점유하는 시간이 길어짐**을 의미한다. 트래픽이 몰릴 때 Nginx 워커가 고갈되어 전체 서비스가 마비될 수 있다.

해결책은 **오래 걸리는 작업은 비동기화**하는 것이다. REST API는 즉시 작업 ID를 반환하고, 클라이언트가 폴링하거나 웹소켓/SSE로 결과를 받는 패턴을 고려해야 한다.

### 4. 헬스체크와 passive health check 활용

```nginx
upstream spring_backend {
    server 127.0.0.1:8080;

    # Nginx Plus 또는 오픈소스의 경우 nginx_upstream_check_module 사용
    # 오픈소스 대안: proxy_next_upstream 활용
}

location /api/ {
    proxy_pass http://spring_backend;

    # 업스트림 오류 시 재시도 설정
    proxy_next_upstream error timeout http_502 http_503;
    proxy_next_upstream_tries 2;
    proxy_next_upstream_timeout 10s;
}
```

`proxy_next_upstream`은 양날의 검이다. POST, PATCH 같은 **비멱등 요청에 재시도를 허용하면 중복 처리가 발생**할 수 있다. 멱등성이 보장되지 않는 엔드포인트에는 반드시 재시도를 제한해야 한다.

### 5. 클라이언트 타임아웃과의 정합성

```
Client timeout > Nginx timeout > Upstream timeout
```

클라이언트(예: 모바일 앱, 프론트엔드)의 타임아웃이 Nginx보다 짧으면, Nginx가 정상적으로 응답을 기다리는 동안 클라이언트가 먼저 연결을 끊어버린다. 이렇게 되면 Nginx 로그에는 499(Client Closed Request)가 찍히고, 업스트림은 계속 작업을 하다가 불필요한 리소스를 낭비한다.

## 정리

502 오류와 타임아웃 문제는 단순히 숫자를 늘리는 것으로 해결되지 않는다. 핵심은 **왜 업스트림이 타임아웃 시간 내에 응답하지 못하는지** 근본 원인을 찾는 것이다.

진단 프로세스를 요약하면 다음과 같다:

1. **Nginx 오류 로그 확인**: `upstream timed out`인지 `connect() failed`인지로 1차 분류
2. **확장 로그 포맷으로 업스트림 응답 시간 측정**: `urt` 값이 타임아웃에 근접한지 확인
3. **업스트림 서버 자체 진단**: GC 로그, 스레드 덤프, DB 쿼리 지연 등 애플리케이션 레벨 문제 확인
4. **네트워크 레벨 확인**: `ss`, `netstat`으로 연결 상태, 포트 백로그 확인
5. **타임아웃 값 조정**: 근본 원인 해결 후 최솟값으로 설정

타임아웃 설정의 황금률은 **"정상적인 99 퍼센타일 응답 시간의 2~3배"** 를 기준으로 잡되, 비즈니스 요구사항과 리소스 점유 비용을 함께 고려하는 것이다. 오늘 포스팅의 설정 예제와 진단 스크립트가 다음 장애 대응 때 실질적인 도움이 되길 바란다.
