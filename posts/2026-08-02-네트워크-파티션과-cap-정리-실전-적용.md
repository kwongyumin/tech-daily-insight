# 네트워크 파티션과 CAP 정리 실전 적용

## 개요

분산 시스템을 설계하다 보면 피할 수 없는 질문과 마주하게 됩니다. "데이터 일관성을 포기할 것인가, 아니면 가용성을 포기할 것인가?" 이 질문의 배경에는 Eric Brewer가 2000년에 제안하고 Gilbert와 Lynch가 2002년에 증명한 **CAP 정리(CAP Theorem)**가 있습니다.

CAP 정리는 이론적으로는 잘 알려져 있지만, 실무에서 어떻게 적용하고 트레이드오프를 어떻게 수용해야 하는지에 대한 구체적인 가이드는 부족한 경우가 많습니다. 이 글에서는 CAP 정리의 핵심 개념을 짚고, 실제 시스템에서 네트워크 파티션이 발생했을 때 어떻게 대응할 수 있는지 Spring Boot 기반의 실전 예제와 함께 살펴봅니다.

---

## 핵심 개념

### CAP 정리란?

CAP 정리는 분산 시스템이 동시에 다음 세 가지 속성을 모두 보장할 수 없다는 이론입니다.

- **C (Consistency, 일관성)**: 모든 노드에서 동일한 시점에 동일한 데이터를 읽을 수 있다.
- **A (Availability, 가용성)**: 모든 요청은 (오류가 없는 한) 반드시 응답을 받는다.
- **P (Partition Tolerance, 파티션 내성)**: 네트워크 파티션(노드 간 통신 단절)이 발생해도 시스템이 계속 동작한다.

현실의 분산 시스템에서 네트워크 파티션은 **반드시 발생**합니다. 따라서 P는 선택이 아닌 필수이며, 실질적인 선택은 **CP vs AP** 사이에서 이루어집니다.

```
+------------------+
|   네트워크 파티션 발생   |
+------------------+
         |
    P를 포기할 수 없음
         |
    +---------+
    |  CP vs AP |
    +---------+
   /             \
  CP              AP
(일관성 우선)    (가용성 우선)
```

### 네트워크 파티션이란?

네트워크 파티션은 분산 시스템의 노드 간에 메시지를 주고받지 못하는 상황을 의미합니다. 물리적 케이블 단절, 스위치 오류, 클라우드 AZ(Availability Zone) 간의 일시적 장애 등이 모두 파티션을 유발할 수 있습니다.

파티션이 발생하면 시스템은 두 가지 중 하나를 선택해야 합니다.

1. **일관성을 지킨다(CP)**: 오래된 데이터를 반환하지 않기 위해 요청에 에러를 반환한다.
2. **가용성을 지킨다(AP)**: 최신 데이터가 아닐 수 있지만 어떻게든 응답한다.

### PACELC 정리: CAP의 확장

CAP 정리의 한계를 보완한 **PACELC 정리**도 알아둘 필요가 있습니다. 파티션이 없는 정상 상태에서도 **지연(Latency) vs 일관성(Consistency)**의 트레이드오프가 존재한다는 점을 명시합니다.

> "파티션(P) 발생 시: 가용성(A) vs 일관성(C), 정상 시: 지연(L) vs 일관성(C)"

## 실전 예제

### 시나리오: 이커머스 재고 관리 시스템

재고를 관리하는 분산 시스템에서 네트워크 파티션이 발생했을 때 CP 전략과 AP 전략을 각각 적용하는 예제를 살펴보겠습니다.

#### CP 전략: Redis를 활용한 분산 락

재고 차감처럼 **정확성이 중요한 연산**에서는 CP 전략을 사용합니다. Redisson을 활용한 분산 락으로 일관성을 보장합니다.

```java
// build.gradle
// implementation 'org.redisson:redisson-spring-boot-starter:3.25.0'

@Service
@RequiredArgsConstructor
@Slf4j
public class InventoryService {

    private final RedissonClient redissonClient;
    private final InventoryRepository inventoryRepository;

    private static final String LOCK_KEY_PREFIX = "inventory:lock:";
    private static final long WAIT_TIME = 5L;
    private static final long LEASE_TIME = 3L;

    public boolean decreaseStock(Long productId, int quantity) {
        String lockKey = LOCK_KEY_PREFIX + productId;
        RLock lock = redissonClient.getLock(lockKey);

        try {
            // 락 획득 시도 (최대 5초 대기, 3초 후 자동 해제)
            boolean acquired = lock.tryLock(WAIT_TIME, LEASE_TIME, TimeUnit.SECONDS);

            if (!acquired) {
                // CP 전략: 락 획득 실패 시 에러 반환 (가용성 희생)
                log.warn("Failed to acquire lock for product: {}", productId);
                throw new LockAcquisitionException("재고 처리 중입니다. 잠시 후 다시 시도해주세요.");
            }

            Inventory inventory = inventoryRepository.findByProductIdWithLock(productId)
                    .orElseThrow(() -> new ProductNotFoundException(productId));

            if (inventory.getQuantity() < quantity) {
                throw new InsufficientStockException("재고가 부족합니다.");
            }

            inventory.decrease(quantity);
            inventoryRepository.save(inventory);
            log.info("Stock decreased for product {}: {} -> {}",
                    productId, inventory.getQuantity() + quantity, inventory.getQuantity());
            return true;

        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new LockAcquisitionException("락 처리 중 인터럽트 발생");
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```

```java
// 파티션 감지 및 서킷 브레이커 통합
@Component
@RequiredArgsConstructor
public class PartitionAwareInventoryFacade {

    private final InventoryService inventoryService;

    @CircuitBreaker(name = "inventory", fallbackMethod = "fallbackDecrease")
    @Retry(name = "inventory")
    public boolean decreaseStock(Long productId, int quantity) {
        return inventoryService.decreaseStock(productId, quantity);
    }

    // 파티션 발생 시 폴백: 요청을 큐에 적재 후 처리 예약
    private boolean fallbackDecrease(Long productId, int quantity, Exception e) {
        log.error("Circuit open for inventory service. Queuing request. Error: {}", e.getMessage());
        // 실패 요청을 DB 또는 메시지 큐에 저장하여 파티션 복구 후 재처리
        pendingOrderQueue.enqueue(new PendingOrder(productId, quantity));
        throw new ServiceUnavailableException("현재 재고 시스템에 접근할 수 없습니다.");
    }
}
```

#### AP 전략: 최종 일관성(Eventual Consistency)을 통한 상품 조회

상품 목록이나 가격 조회처럼 **약간의 오래된 데이터가 허용**되는 케이스에서는 AP 전략으로 가용성을 우선합니다.

```java
@Service
@RequiredArgsConstructor
@Slf4j
public class ProductCatalogService {

    private final ProductRepository productRepository;
    private final RedisTemplate<String, ProductDto> redisTemplate;
    private final ApplicationEventPublisher eventPublisher;

    private static final String CACHE_KEY_PREFIX = "product:";
    private static final Duration CACHE_TTL = Duration.ofMinutes(5);

    // AP 전략: 캐시에서 먼저 읽고, 없으면 DB 조회 (오래된 데이터 허용)
    public ProductDto getProduct(Long productId) {
        String cacheKey = CACHE_KEY_PREFIX + productId;

        try {
            ProductDto cached = redisTemplate.opsForValue().get(cacheKey);
            if (cached != null) {
                log.debug("Cache hit for product: {}", productId);
                return cached;
            }
        } catch (RedisConnectionFailureException e) {
            // Redis 파티션 발생 시: 가용성 유지를 위해 DB로 폴백
            log.warn("Redis connection failed, falling back to DB: {}", e.getMessage());
            return getProductFromDB(productId);
        }

        return getProductFromDB(productId);
    }

    private ProductDto getProductFromDB(Long productId) {
        Product product = productRepository.findById(productId)
                .orElseThrow(() -> new ProductNotFoundException(productId));

        ProductDto dto = ProductDto.from(product);

        // 비동기로 캐시 갱신 시도 (AP: 최종적으로 일관성 달성)
        eventPublisher.publishEvent(new CacheRefreshEvent(CACHE_KEY_PREFIX + productId, dto));
        return dto;
    }
}

@Component
@RequiredArgsConstructor
public class CacheRefreshEventListener {

    private final RedisTemplate<String, ProductDto> redisTemplate;

    @Async
    @EventListener
    public void handleCacheRefresh(CacheRefreshEvent event) {
        try {
            redisTemplate.opsForValue().set(
                event.getKey(), event.getData(), Duration.ofMinutes(5)
            );
        } catch (Exception e) {
            // 캐시 갱신 실패는 무시 (AP 전략: 최종 일관성)
            log.warn("Async cache refresh failed for key: {}", event.getKey());
        }
    }
}
```

#### 파티션 감지 헬스체크 구현

```java
@Component
@RequiredArgsConstructor
public class PartitionDetector {

    private final List<NodeHealthChecker> nodeCheckers;
    private final AtomicBoolean partitionDetected = new AtomicBoolean(false);

    @Scheduled(fixedDelay = 5000)
    public void detectPartition() {
        long reachableNodes = nodeCheckers.stream()
                .filter(NodeHealthChecker::isReachable)
                .count();

        long totalNodes = nodeCheckers.size();
        double reachableRatio = (double) reachableNodes / totalNodes;

        if (reachableRatio < 0.5) {
            // 과반수 노드 미도달: 파티션 발생으로 판단
            if (partitionDetected.compareAndSet(false, true)) {
                log.error("Network partition detected! Reachable: {}/{}", reachableNodes, totalNodes);
                // 운영팀 알림, 메트릭 기록 등
                MetricsRegistry.increment("network.partition.detected");
            }
        } else {
            if (partitionDetected.compareAndSet(true, false)) {
                log.info("Network partition resolved. Reachable: {}/{}", reachableNodes, totalNodes);
                MetricsRegistry.increment("network.partition.resolved");
            }
        }
    }

    public boolean isPartitioned() {
        return partitionDetected.get();
    }
}
```

## 주의사항 및 트레이드오프

### 1. CAP 정리는 이분법이 아니다

많은 개발자들이 "우리 시스템은 CP야" 또는 "우리 시스템은 AP야"로 단정 짓는 실수를 합니다. 실제로는 **기능별로, 연산 유형별로** 다른 전략을 선택해야 합니다.

| 기능 | 전략 | 이유 |
|------|------|------|
| 결제 처리 | CP | 이중 차감 불가, 정확성 최우선 |
| 상품 목록 조회 | AP | 수초 오래된 데이터 허용 가능 |
| 재고 조회 | CP 또는 AP | 비즈니스 정책에 따라 결정 |
| 사용자 세션 | AP | 약간의 불일치보다 서비스 중단이 더 큰 문제 |
| 포인트 잔액 | CP | 금전적 손실 위험 |

### 2. 파티션 복구 후 데이터 병합 전략

AP 전략 선택 시 파티션이 복구된 후 **충돌 해결(Conflict Resolution)**이 필요합니다.

```java
public class ConflictResolver {

    // Last Write Wins (LWW): 가장 최근 타임스탬프 우선
    public <T extends Timestamped> T resolveWithLWW(T local, T remote) {
        return local.getUpdatedAt().isAfter(remote.getUpdatedAt()) ? local : remote;
    }

    // Vector Clock 기반 충돌 감지
    public ConflictResult detectConflict(VectorClock local, VectorClock remote) {
        if (local.dominates(remote)) return ConflictResult.LOCAL_WINS;
        if (remote.dominates(local)) return ConflictResult.REMOTE_WINS;
        return ConflictResult.CONFLICT; // 병렬 수정: 수동 병합 필요
    }
}
```

### 3. 타임아웃 설정의 중요성

파티션 상황에서 무한 대기는 가장 위험합니다. 반드시 적절한 타임아웃을 설정하세요.

```yaml
# application.yml
spring:
  datasource:
    hikari:
      connection-timeout: 3000      # 3초
      max-lifetime: 600000          # 10분
  redis:
    timeout: 1000ms                 # 1초

resilience4j:
  circuitbreaker:
    instances:
      inventory:
        sliding-window-size: 10
        failure-rate-threshold: 50
        wait-duration-in-open-state: 10s
  retry:
    instances:
      inventory:
        max-attempts: 3
        wait-duration: 500ms
```

### 4. 실제 데이터베이스의 CAP 위치

| 데이터베이스 | CAP 분류 | 특징 |
|-------------|---------|------|
| MySQL (단일) | CA | 파티션 내성 없음, 분산 아님 |
| MySQL (갈레라) | CP | 강한 일관성, 파티션 시 중단 |
| Cassandra | AP | 최종 일관성, 높은 가용성 |
| MongoDB | CP (기본) | 프라이머리 중심 일관성 |
| DynamoDB | AP | 최종 일관성 (강한 일관성 옵션 별도) |
| ZooKeeper | CP | 리더 선출, 강한 일관성 |

## 정리

CAP 정리는 분산 시스템 설계의 나침반 역할을 합니다. 하지만 이를 "무엇을 포기할 것인가"의 관점이 아닌 **"비즈니스 요구사항에 맞게 무엇을 우선할 것인가"** 의 관점으로 바라봐야 합니다.

실무에서 기억해야 할 핵심 포인트를 정리하면 다음과 같습니다.

1. **P(파티션 내성)는 협상 불가**: 분산 시스템에서 네트워크 파티션은 언제든 발생한다.
2. **기능별로 전략을 달리하라**: 시스템 전체가 CP 또는 AP일 필요 없다.
3. **서킷 브레이커와 타임아웃은 필수**: 파티션 상황에서 시스템이 폭주하지 않도록 보호하라.
4. **AP 선택 시 충돌 해결 전략을 미리 설계하라**: 파티션 복구 후의 데이터 병합은 복잡하다.
5. **모니터링과 알림 체계를 구축하라**: 파티션 발생을 빠르게 감지하고 대응할 수 있어야 한다.

분산 시스템은 완벽할 수 없습니다. CAP 정리는 그 한계를 명확히 하고, 우리가 올바른 트레이드오프를 선택하도록 돕는 도구입니다. 중요한 것은 어떤 선택을 했는지 팀 전체가 이해하고, 그 선택의 결과를 시스템 운영에서 일관되게 수용하는 것입니다.
