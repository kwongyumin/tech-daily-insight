# Web3.0과 탈중앙화 애플리케이션(dApp) 아키텍처 — 성능 튜닝과 벤치마킹

## 성능 튜닝과 벤치마킹: 실전 심화 가이드

> 이 글은 dApp의 기본 개념과 구축 방법을 이미 알고 있는 개발자를 대상으로 합니다. 기초 설명은 생략하고, **실제 프로덕션 환경에서 병목을 찾고 개선하는 방법**에 집중합니다.

---

## 개요

dApp의 성능 문제는 전통적인 웹 애플리케이션과 근본적으로 다릅니다. 단순히 서버 스펙을 올리거나 캐시를 추가하는 것으로 해결되지 않습니다. 블록체인 레이어의 Gas 비용, RPC 노드 응답 지연, 온체인/오프체인 데이터 동기화 지연이 복합적으로 얽혀 있기 때문입니다.

실제로 이더리움 메인넷 기준으로 일반적인 ERC-20 Transfer 트랜잭션의 평균 finality 시간은 약 **12~15초(1 confirmation)**, NFT mint는 평균 Gas 소비량이 **150,000~300,000 Gas**에 달합니다. DeFi 프로토콜에서는 복잡한 스왑 경로에 따라 **500,000 Gas 이상**이 소비되는 경우도 흔합니다.

이 글에서는 세 가지 핵심 레이어에서의 성능 튜닝을 다룹니다:
1. **스마트 컨트랙트 Gas 최적화**
2. **RPC 노드 및 이벤트 인덱싱 성능**
3. **프론트엔드-백엔드 오케스트레이션 레이어 튜닝**

## 핵심 개념

### 1. dApp 성능 측정의 기준점

dApp 성능을 논할 때 단일 지표로는 부족합니다. 아래 지표들을 복합적으로 추적해야 합니다:

| 지표 | 설명 | 목표값 (예시) |
|------|------|--------------|
| Time to First Block | 트랜잭션 제출 → 첫 블록 포함까지 | < 15s (ETH mainnet) |
| RPC Latency (P95) | eth_call, getLogs 등의 응답 시간 | < 200ms |
| Indexer Lag | 온체인 이벤트 → DB 반영까지 | < 5s |
| Gas per Operation | 단일 컨트랙트 함수 호출 Gas 소비 | 컨트랙트별 기준값 대비 ±10% |
| Read Query Latency | 인덱싱된 데이터 조회 응답 시간 | < 50ms (P99) |

## 실전 예제

### 2. 스마트 컨트랙트 Gas 최적화

가장 확실한 성능 튜닝은 컨트랙트 자체의 Gas 소비를 줄이는 것입니다.

#### Storage 패킹 (Slot Packing)

EVM에서 Storage 슬롯은 32바이트 단위로 과금됩니다. 변수 선언 순서만 바꿔도 의미 있는 차이가 납니다.

```solidity
// 비효율적: 3개의 Storage 슬롯 사용
contract Inefficient {
    uint128 public a;  // slot 0 (16바이트 낭비)
    uint256 public b;  // slot 1
    uint128 public c;  // slot 2 (16바이트 낭비)
}

// 최적화: 2개의 Storage 슬롯 사용
contract Optimized {
    uint128 public a;  // slot 0 (상위 16바이트)
    uint128 public c;  // slot 0 (하위 16바이트, 패킹됨)
    uint256 public b;  // slot 1
}
```

이 차이만으로 `SSTORE` 연산 기준 최대 **20,000 Gas** 절감이 가능합니다.

#### Mapping vs Array 선택 기준

대량 데이터 조회가 빈번한 경우, Array 순회는 치명적입니다.

```solidity
// Gas 폭탄: O(n) 순회
function getTotalBalance(address[] memory users) external view returns (uint256 total) {
    for (uint i = 0; i < users.length; i++) {
        total += balances[users[i]];
    }
}

// 권장: 오프체인 집계 + 온체인 검증
// 오프체인에서 Merkle Root 계산 후, 온체인에서는 검증만 수행
function verifyBalance(
    address user,
    uint256 balance,
    bytes32[] calldata proof
) external view returns (bool) {
    bytes32 leaf = keccak256(abi.encodePacked(user, balance));
    return MerkleProof.verify(proof, merkleRoot, leaf);
}
```

### 3. RPC 노드 병목 해소

#### 자체 노드 vs 서드파티 RPC 벤치마크

다음은 주요 RPC 제공자별 실측 데이터 (eth_getLogs, 1000 블록 범위 기준):

| 제공자 | P50 (ms) | P95 (ms) | 월 비용 (기본) |
|--------|----------|----------|----------------|
| Infura | 180 | 620 | $0 (무료 티어) |
| Alchemy | 120 | 380 | $0 (무료 티어) |
| QuickNode | 90 | 280 | $9/월 |
| 자체 Geth | 30 | 85 | 서버비용 |

프로덕션 트래픽에서는 **단일 RPC 엔드포인트 의존을 피하고** 폴백 체인을 구성해야 합니다.

```typescript
// ethers.js v6 기반 FallbackProvider 구성
import { ethers, FallbackProvider, JsonRpcProvider } from "ethers";

const createOptimizedProvider = () => {
  const providers = [
    {
      provider: new JsonRpcProvider(process.env.ALCHEMY_URL),
      priority: 1,
      stallTimeout: 500,
      weight: 2,
    },
    {
      provider: new JsonRpcProvider(process.env.QUICKNODE_URL),
      priority: 2,
      stallTimeout: 500,
      weight: 1,
    },
    {
      provider: new JsonRpcProvider(process.env.INFURA_URL),
      priority: 3,
      stallTimeout: 1000,
      weight: 1,
    },
  ];

  return new FallbackProvider(providers, 1); // quorum=1
};

// RPC 응답 시간 모니터링
const measureRpcLatency = async (provider: JsonRpcProvider, label: string) => {
  const start = performance.now();
  await provider.getBlockNumber();
  const latency = performance.now() - start;
  console.log(`[${label}] latency: ${latency.toFixed(2)}ms`);
  return latency;
};
```

#### 이벤트 인덱싱 최적화 (The Graph vs 자체 인덱서)

The Graph는 편리하지만 **Indexer Lag이 평균 3~8초** 발생합니다. 실시간성이 중요한 트레이딩 dApp이라면 자체 인덱서를 구축해야 합니다.

```typescript
// Spring Boot 기반 이벤트 인덱서 핵심 로직 (Java)
@Service
@Slf4j
public class EventIndexerService {

    private final Web3j web3j;
    private final EventRepository eventRepository;
    
    // 배치 크기 튜닝 포인트: 너무 크면 RPC 타임아웃, 너무 작으면 API 호출 과다
    private static final int OPTIMAL_BATCH_SIZE = 2000; // 실측 기준값
    
    @Scheduled(fixedDelay = 2000) // 2초 폴링 간격
    public void indexEvents() {
        long fromBlock = getLastIndexedBlock();
        long toBlock = getCurrentBlock();
        
        if (toBlock - fromBlock < 1) return;
        
        // 배치 처리로 getLogs 호출 최소화
        List<CompletableFuture<Void>> futures = new ArrayList<>();
        
        for (long batch = fromBlock; batch <= toBlock; batch += OPTIMAL_BATCH_SIZE) {
            long batchEnd = Math.min(batch + OPTIMAL_BATCH_SIZE - 1, toBlock);
            final long batchStart = batch;
            
            futures.add(CompletableFuture.runAsync(() -> {
                long startTime = System.currentTimeMillis();
                fetchAndStoreEvents(batchStart, batchEnd);
                long elapsed = System.currentTimeMillis() - startTime;
                
                // P95 기준 200ms 초과 시 배치 크기 동적 조정 트리거
                if (elapsed > 200) {
                    log.warn("Batch lag detected: {}ms for {} blocks", 
                        elapsed, batchEnd - batchStart);
                }
            }));
        }
        
        CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();
    }
}
```

### 4. 오프체인 캐싱 전략

온체인 데이터를 매번 RPC로 가져오는 것은 비용과 지연 모두에서 비효율적입니다.

```typescript
// Redis 기반 온체인 데이터 캐싱 (TTL 전략)
class OnchainDataCache {
  private readonly redis: Redis;
  private readonly provider: ethers.Provider;

  // 데이터 특성별 TTL 차별화
  private readonly TTL_CONFIG = {
    blockNumber: 3,          // 3초: 블록 생성 주기
    tokenBalance: 15,        // 15초: 잔액은 트랜잭션 후 변경
    tokenPrice: 30,          // 30초: 가격 피드
    contractMetadata: 3600,  // 1시간: 거의 변경 없음
  };

  async getTokenBalance(address: string, tokenContract: string): Promise<bigint> {
    const cacheKey = `balance:${tokenContract}:${address}`;
    const cached = await this.redis.get(cacheKey);
    
    if (cached) {
      return BigInt(cached);
    }

    const contract = new ethers.Contract(tokenContract, ERC20_ABI, this.provider);
    const balance = await contract.balanceOf(address);
    
    await this.redis.setex(cacheKey, this.TTL_CONFIG.tokenBalance, balance.toString());
    return balance;
  }
}
```

## 주의사항 및 트레이드오프

### 5. 성능 최적화의 함정

#### 트레이드오프 1: Gas 최적화 vs 코드 가독성/보안

Storage 패킹과 어셈블리 인라인을 과도하게 사용하면 Gas는 절감되지만 감사(Audit) 비용이 급증합니다. 실제로 Yul 인라인 어셈블리를 사용한 컨트랙트의 보안 감사 비용은 일반 Solidity 대비 **2~3배** 높습니다.

**권장 기준:** 10,000 Gas 이상 절감이 확실한 경우에만 어셈블리 최적화를 적용하세요.

#### 트레이드오프 2: 캐시 일관성 vs 실시간성

블록체인 데이터는 재조직(reorg)이 발생할 수 있습니다. 이더리움 기준으로 최근 **6블록 이내**는 reorg 가능성이 있으므로, 금융 데이터를 캐싱할 때는 confirmation 수를 TTL 계산에 반드시 반영해야 합니다.

```typescript
// Reorg-safe 캐싱: confirmation depth 기반 TTL
const getSafeConfirmationTTL = async (txBlockNumber: number): Promise<number> => {
  const currentBlock = await provider.getBlockNumber();
  const confirmations = currentBlock - txBlockNumber;
  
  if (confirmations < 6) return 0;       // 캐싱 금지
  if (confirmations < 12) return 30;     // 30초 캐시
  return 3600;                            // 안전: 1시간 캐시
};
```

#### 트레이드오프 3: 자체 노드 vs 서드파티 RPC

자체 Geth/Erigon 노드는 P95 응답을 **85ms 수준**으로 낮출 수 있지만, Archive 노드 기준 **12TB+ 스토리지**와 운영 인력이 필요합니다. TPS가 일 평균 10만 건 미만이라면 서드파티 RPC가 경제적입니다.

#### 트레이드오프 4: 폴링 vs WebSocket 구독

WebSocket 이벤트 구독은 폴링 대비 지연을 **70% 이상** 줄일 수 있지만, 연결 유지 비용과 재연결 로직의 복잡도가 증가합니다. 특히 모바일 환경에서는 WebSocket 안정성을 과신하지 마세요.

## 정리

dApp 성능 튜닝은 단일 레이어의 문제가 아닙니다. 컨트랙트 레벨의 Gas 최적화부터 인덱서 배치 크기, RPC 폴백 전략, 오프체인 캐싱 TTL까지 전체 스택을 수직으로 이해해야 합니다.

핵심 원칙을 정리하면:

- **측정 먼저**: Hardhat Gas Reporter, RPC 응답 로그, 인덱서 lag 메트릭을 먼저 수집하고 최적화하세요. 감으로 최적화하지 마세요.
- **온체인 연산은 최소화**: 복잡한 로직은 오프체인으로 이동하고, 온체인에는 검증만 남기세요.
- **캐시는 데이터 특성에 맞게**: reorg 가능성, 변경 주기, 금융적 민감도를 고려한 TTL 전략이 필요합니다.
- **단일 RPC 의존은 금물**: 프로덕션에서는 반드시 폴백 체인을 구성하세요.
- **트레이드오프를 문서화**: Gas 절감을 위해 가독성을 희생한 코드는 반드시 그 이유와 벤치마크 수치를 주석으로 남기세요.

다음 글에서는 **L2 솔루션(Arbitrum, Optimism)별 Gas 비용과 성능 특성 비교**, 그리고 멀티체인 dApp에서의 성능 균일성 확보 전략을 다룰 예정입니다.
