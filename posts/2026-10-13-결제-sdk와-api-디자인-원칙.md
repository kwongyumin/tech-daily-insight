# 결제 SDK와 API 디자인 원칙

## 개요

결제 시스템은 서비스에서 가장 민감한 도메인 중 하나다. 돈이 오가는 만큼 **오류 하나가 직접적인 금전 손실이나 신뢰 손상**으로 이어질 수 있다. 이 때문에 결제 관련 SDK나 API를 설계할 때는 단순한 CRUD 설계와는 다른 원칙이 필요하다.

이 포스팅에서는 결제 SDK와 API를 설계할 때 실무에서 반드시 고려해야 할 핵심 원칙들을 다룬다. 단순히 "이렇게 하면 좋다"는 수준이 아니라, 각 설계 결정이 왜 필요한지, 어떤 트레이드오프가 존재하는지를 중심으로 설명한다.

---

## 핵심 개념

### 1. 멱등성(Idempotency)은 선택이 아닌 필수

결제 API에서 가장 중요한 개념은 멱등성이다. 네트워크 타임아웃, 클라이언트 재시도, 서버 장애 등 다양한 이유로 **같은 요청이 여러 번 전송될 수 있다**. 이때 결제가 중복으로 처리되면 심각한 문제가 발생한다.

멱등성을 보장하는 일반적인 방법은 클라이언트가 생성한 고유한 `Idempotency-Key`를 요청 헤더에 포함시키는 것이다. 서버는 이 키를 기반으로 동일 요청의 중복 처리를 방지한다.

```
POST /v1/payments
Idempotency-Key: a1b2c3d4-e5f6-7890-abcd-ef1234567890
Content-Type: application/json

{
  "amount": 10000,
  "currency": "KRW",
  "payment_method_id": "pm_xxx"
}
```

서버 측에서는 이 키를 Redis나 DB에 저장하고, 동일 키로 요청이 들어오면 최초 응답을 그대로 반환한다.

### 2. 명확한 상태 머신 설계

결제는 단일 트랜잭션이 아니라 **여러 상태를 거치는 흐름**이다. 상태 전이가 불명확하면 "결제가 됐는지 안 됐는지 모르는" 최악의 상황이 발생한다.

```
INITIATED → PENDING → AUTHORIZED → CAPTURED → COMPLETED
                  ↘ FAILED
                  ↘ CANCELLED
              AUTHORIZED → PARTIALLY_REFUNDED → REFUNDED
```

상태 머신을 명확히 정의하면 API 응답에서도 현재 상태와 가능한 다음 액션을 명시할 수 있다.

### 3. 에러 코드 체계의 일관성

결제 실패 원인은 매우 다양하다. 잔액 부족, 카드 한도 초과, 사기 감지, PG사 장애 등이 모두 "결제 실패"지만 클라이언트 입장에서는 완전히 다른 처리가 필요하다.

에러 코드는 계층적으로 설계해야 한다:

- **카테고리**: `PAYMENT_DECLINED`, `AUTHORIZATION_ERROR`, `NETWORK_ERROR`
- **세부 코드**: `INSUFFICIENT_FUNDS`, `CARD_EXPIRED`, `FRAUD_DETECTED`
- **retry 가능 여부**: 클라이언트가 재시도 여부를 판단할 수 있어야 한다

## 실전 예제

### Spring Boot 기반 결제 API 서버 구현

#### 멱등성 처리 필터

```java
@Component
@Order(1)
public class IdempotencyFilter extends OncePerRequestFilter {

    private final IdempotencyStore idempotencyStore;

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain) throws ServletException, IOException {

        if (!isPaymentMutatingMethod(request.getMethod())) {
            filterChain.doFilter(request, response);
            return;
        }

        String idempotencyKey = request.getHeader("Idempotency-Key");
        if (idempotencyKey == null || idempotencyKey.isBlank()) {
            response.sendError(HttpStatus.BAD_REQUEST.value(), "Idempotency-Key header is required");
            return;
        }

        Optional<CachedResponse> cached = idempotencyStore.get(idempotencyKey);
        if (cached.isPresent()) {
            // 동일 요청 재시도 → 캐시된 응답 그대로 반환
            CachedResponse cachedResponse = cached.get();
            response.setStatus(cachedResponse.getStatusCode());
            response.setContentType("application/json");
            response.getWriter().write(cachedResponse.getBody());
            return;
        }

        // 요청 처리 후 응답 캐싱
        ContentCachingResponseWrapper wrappedResponse =
            new ContentCachingResponseWrapper(response);

        filterChain.doFilter(request, wrappedResponse);

        String responseBody = new String(wrappedResponse.getContentAsByteArray());
        idempotencyStore.save(
            idempotencyKey,
            new CachedResponse(wrappedResponse.getStatus(), responseBody),
            Duration.ofHours(24)
        );

        wrappedResponse.copyBodyToResponse();
    }

    private boolean isPaymentMutatingMethod(String method) {
        return "POST".equals(method) || "PATCH".equals(method);
    }
}
```

#### 결제 도메인 상태 머신

```java
public enum PaymentStatus {
    INITIATED, PENDING, AUTHORIZED, CAPTURED, COMPLETED,
    FAILED, CANCELLED, PARTIALLY_REFUNDED, REFUNDED;

    private static final Map<PaymentStatus, Set<PaymentStatus>> VALID_TRANSITIONS =
        Map.of(
            INITIATED,  Set.of(PENDING, FAILED),
            PENDING,    Set.of(AUTHORIZED, FAILED, CANCELLED),
            AUTHORIZED, Set.of(CAPTURED, CANCELLED, FAILED),
            CAPTURED,   Set.of(COMPLETED, PARTIALLY_REFUNDED, REFUNDED),
            COMPLETED,  Set.of(PARTIALLY_REFUNDED, REFUNDED)
        );

    public void validateTransition(PaymentStatus next) {
        Set<PaymentStatus> allowed = VALID_TRANSITIONS.getOrDefault(this, Set.of());
        if (!allowed.contains(next)) {
            throw new InvalidPaymentStateTransitionException(
                String.format("Cannot transition from %s to %s", this, next)
            );
        }
    }
}
```

#### 구조화된 에러 응답

```java
@RestControllerAdvice
public class PaymentExceptionHandler {

    @ExceptionHandler(PaymentDeclinedException.class)
    public ResponseEntity<PaymentErrorResponse> handlePaymentDeclined(
            PaymentDeclinedException ex) {

        PaymentErrorResponse error = PaymentErrorResponse.builder()
            .errorCode(ex.getErrorCode())           // INSUFFICIENT_FUNDS
            .errorCategory("PAYMENT_DECLINED")
            .message(ex.getMessage())
            .retryable(ex.isRetryable())             // false (잔액 부족은 재시도 의미 없음)
            .paymentId(ex.getPaymentId())
            .timestamp(Instant.now())
            .build();

        return ResponseEntity.status(HttpStatus.UNPROCESSABLE_ENTITY).body(error);
    }

    @ExceptionHandler(PgNetworkException.class)
    public ResponseEntity<PaymentErrorResponse> handlePgNetworkError(
            PgNetworkException ex) {

        PaymentErrorResponse error = PaymentErrorResponse.builder()
            .errorCode("PG_NETWORK_ERROR")
            .errorCategory("NETWORK_ERROR")
            .message("Payment gateway temporarily unavailable")
            .retryable(true)                         // 재시도 가능
            .retryAfterSeconds(30)
            .timestamp(Instant.now())
            .build();

        return ResponseEntity.status(HttpStatus.SERVICE_UNAVAILABLE).body(error);
    }
}
```

### 클라이언트 SDK 설계 원칙

SDK를 제공할 때는 내부 구현을 숨기고, **사용자가 실수하기 어려운 인터페이스**를 설계해야 한다.

```java
// Bad: 너무 많은 파라미터, 순서를 실수하기 쉬움
PaymentResult pay(String amount, String currency, String methodId, boolean capture, String idempotencyKey);

// Good: 빌더 패턴으로 가독성과 안전성 확보
PaymentRequest request = PaymentRequest.builder()
    .amount(Money.of(10000, Currency.KRW))
    .paymentMethod(PaymentMethod.ofId("pm_xxx"))
    .captureMode(CaptureMode.AUTOMATIC)
    .idempotencyKey(IdempotencyKey.generate())  // SDK가 자동 생성 지원
    .metadata(Map.of("orderId", "order_abc123"))
    .build();

PaymentResult result = paymentClient.charge(request);
```

SDK 내부에서는 재시도 로직을 내장시켜야 한다:

```java
public class RetryablePaymentClient {

    private final PaymentClient delegate;
    private final RetryPolicy retryPolicy;

    public PaymentResult charge(PaymentRequest request) {
        return retryPolicy.execute(() -> {
            try {
                return delegate.charge(request);
            } catch (PaymentException e) {
                if (!e.isRetryable()) {
                    throw new NoRetryException(e); // 재시도 불필요 예외는 즉시 전파
                }
                throw e; // retryable 예외는 정책에 따라 재시도
            }
        });
    }
}
```

## 주의사항 및 트레이드오프

### 1. 웹훅 vs 폴링

결제 완료 통보 방식으로 **웹훅(Webhook)** 과 **폴링(Polling)** 중 어떤 것을 선택할지는 실무에서 자주 논쟁이 된다.

| 항목 | 웹훅 | 폴링 |
|------|------|------|
| 실시간성 | 높음 | 낮음 (인터벌 의존) |
| 복잡도 | 높음 (서버 필요, 서명 검증) | 낮음 |
| 신뢰성 | 재전송 로직 필요 | 구현 단순 |
| 확장성 | 이벤트 기반으로 적합 | 대량 처리 시 부하 |

실무에서는 **웹훅 + 폴링 보완** 방식이 많이 사용된다. 웹훅이 실패했을 때 폴링으로 상태를 동기화하는 형태다.

웹훅에서는 반드시 서명 검증이 필요하다:

```java
public boolean verifyWebhookSignature(String payload, String receivedSignature, String secret) {
    try {
        Mac hmac = Mac.getInstance("HmacSHA256");
        hmac.init(new SecretKeySpec(secret.getBytes(StandardCharsets.UTF_8), "HmacSHA256"));
        byte[] computed = hmac.doFinal(payload.getBytes(StandardCharsets.UTF_8));
        String expectedSignature = "sha256=" + HexFormat.of().formatHex(computed);
        return MessageDigest.isEqual(
            expectedSignature.getBytes(),
            receivedSignature.getBytes()
        );
    } catch (Exception e) {
        return false;
    }
}
```

`MessageDigest.isEqual()`을 사용하는 이유는 **타이밍 공격(Timing Attack)** 방지를 위해 상수 시간 비교를 수행하기 때문이다.

### 2. 버전 관리 전략

결제 API는 한번 릴리즈되면 하위 호환성을 깨기가 매우 어렵다. 외부 SDK를 사용하는 가맹점들이 빠르게 업그레이드를 못하는 경우가 대부분이기 때문이다.

- **URL 기반 버전**: `/v1/payments`, `/v2/payments` — 명확하지만 코드 중복 가능성
- **헤더 기반 버전**: `API-Version: 2024-01-01` — 유연하지만 클라이언트 구현 복잡
- **점진적 deprecation 정책**: 최소 6~12개월의 지원 기간을 공시해야 신뢰를 유지할 수 있다

### 3. 민감 데이터 마스킹

로그와 에러 응답에서 카드 번호, CVV, 계좌번호 등이 노출되지 않도록 주의해야 한다. 직렬화/역직렬화 단계에서 마스킹을 강제하는 것이 안전하다:

```java
public class CardNumber {
    private final String value;

    // 직렬화 시 마스킹
    @JsonValue
    public String masked() {
        return "**** **** **** " + value.substring(value.length() - 4);
    }

    @Override
    public String toString() {
        return masked(); // 로그에 출력되더라도 마스킹
    }
}
```

### 4. 동시성과 분산 락

동일한 결제 건에 대해 여러 요청이 동시에 들어올 때 상태 충돌이 발생할 수 있다. 특히 환불 처리 시 잔액보다 많은 금액이 환불되는 시나리오를 방지해야 한다.

```java
public void refund(String paymentId, Money amount) {
    String lockKey = "payment:refund:" + paymentId;
    // Redisson 또는 DB 비관적 락 사용
    RLock lock = redissonClient.getLock(lockKey);
    try {
        if (!lock.tryLock(3, 10, TimeUnit.SECONDS)) {
            throw new ConcurrentRefundException("Refund already in progress");
        }
        // 환불 처리 로직
        processRefund(paymentId, amount);
    } finally {
        if (lock.isHeldByCurrentThread()) {
            lock.unlock();
        }
    }
}
```

## 정리

결제 SDK와 API 설계는 기능 구현을 넘어 **장애 상황, 재시도, 상태 일관성, 보안**을 모두 고려해야 하는 복합적인 작업이다. 핵심 원칙을 정리하면 다음과 같다:

1. **멱등성**: 모든 결제 변경 API에 `Idempotency-Key`를 강제하라
2. **명확한 상태 머신**: 상태와 전이를 코드로 강제하고 문서화하라
3. **구조화된 에러 응답**: 에러 카테고리, 세부 코드, 재시도 가능 여부를 분리하라
4. **SDK는 실수 방지 설계**: 빌더 패턴, 자동 재시도, 타입 안전성을 SDK 내부에 캡슐화하라
5. **웹훅 + 폴링 보완**: 비동기 이벤트의 신뢰성을 폴링으로 보완하라
6. **민감 데이터 보호**: 직렬화와 로깅 레이어에서 마스킹을 강제하라
7. **하위 호환성 우선**: API 버전 전략과 deprecation 정책을 릴리즈 전에 결정하라

결제 시스템은 "일단 돌아가면 된다"는 접근이 가장 위험한 도메인이다. 초기 설계에 투자한 시간이 나중에 발생할 장애 대응과 비교할 수 없을 만큼 값싸다는 점을 항상 기억하자.
