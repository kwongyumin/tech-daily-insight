# gRPC 스트리밍 패턴과 백프레셔 처리

## 개요

마이크로서비스 아키텍처가 성숙해지면서 서비스 간 통신의 효율성은 더욱 중요한 화두가 되었다. REST/HTTP 기반의 단순 요청-응답 패턴으로는 대용량 데이터 스트리밍, 실시간 이벤트 처리, 양방향 통신 등의 요구사항을 효율적으로 충족하기 어렵다.

gRPC는 HTTP/2 위에서 동작하며, 멀티플렉싱, 헤더 압축, 바이너리 직렬화(Protocol Buffers) 등의 특성 덕분에 고성능 서비스 간 통신에 널리 채택되고 있다. 특히 **스트리밍 패턴**은 gRPC의 핵심 강점 중 하나로, 단순 Unary 호출 외에도 세 가지 스트리밍 방식을 지원한다.

그러나 스트리밍을 도입할 때 반드시 고민해야 할 문제가 있다. 바로 **백프레셔(Backpressure)**다. 생산자가 소비자보다 빠르게 데이터를 전송할 경우 메모리 고갈, 연결 타임아웃, 서비스 장애로 이어질 수 있다. 이 글에서는 gRPC의 네 가지 통신 패턴을 살펴보고, 실무에서 백프레셔를 어떻게 처리해야 하는지 Java(grpc-java) 기반의 실전 코드와 함께 설명한다.

## 핵심 개념

### gRPC의 네 가지 통신 패턴

| 패턴 | 설명 | 사용 사례 |
|------|------|-----------|
| **Unary RPC** | 단일 요청 → 단일 응답 | 일반적인 API 호출 |
| **Server Streaming** | 단일 요청 → 다중 응답 스트림 | 실시간 데이터 피드, 로그 스트리밍 |
| **Client Streaming** | 다중 요청 스트림 → 단일 응답 | 파일 업로드, 배치 데이터 전송 |
| **Bidirectional Streaming** | 다중 요청 ↔ 다중 응답 | 채팅, 실시간 협업 도구 |

### 백프레셔란?

백프레셔는 **소비자가 처리할 수 없는 속도로 데이터가 밀려올 때 생산자에게 신호를 보내 속도를 조절하는 메커니즘**이다. HTTP/2의 플로우 컨트롤(Flow Control)이 기반이 되지만, 애플리케이션 레이어에서도 명시적으로 처리해야 하는 부분이 있다.

gRPC에서 백프레셔는 두 계층에서 작동한다.

- **Transport Layer**: HTTP/2 WINDOW_UPDATE 프레임을 통한 플로우 컨트롤
- **Application Layer**: `onNext()` 호출 빈도 제어, `request(n)` 메서드를 통한 수동 플로우 컨트롤

grpc-java는 `ServerCallStreamObserver`와 `ClientCallStreamObserver`를 통해 애플리케이션 레이어 백프레셔를 구현할 수 있는 API를 제공한다.

## 실전 예제

### Proto 정의

```protobuf
syntax = "proto3";

package stream.demo;

option java_package = "com.example.grpc.stream";

service DataStreamService {
  // Server Streaming
  rpc FetchLargeDataset (DataRequest) returns (stream DataChunk);

  // Client Streaming
  rpc UploadData (stream DataChunk) returns (UploadResult);

  // Bidirectional Streaming
  rpc ProcessStream (stream DataChunk) returns (stream ProcessedResult);
}

message DataRequest {
  string query = 1;
  int32 batch_size = 2;
}

message DataChunk {
  string id = 1;
  bytes payload = 2;
  int64 timestamp = 3;
}

message ProcessedResult {
  string id = 1;
  string status = 2;
  string message = 3;
}

message UploadResult {
  int32 total_received = 1;
  bool success = 2;
}
```

### Server Streaming + 백프레셔 처리

서버 스트리밍에서 가장 흔히 발생하는 문제는 서버가 클라이언트의 처리 속도를 고려하지 않고 무작정 데이터를 밀어 넣는 것이다. `ServerCallStreamObserver`를 사용하여 `isReady()` 체크와 `onReadyHandler`를 통해 이를 제어할 수 있다.

```java
@GrpcService
public class DataStreamServiceImpl extends DataStreamServiceGrpc.DataStreamServiceImplBase {

    private static final Logger log = LoggerFactory.getLogger(DataStreamServiceImpl.class);
    private final DataRepository dataRepository;

    public DataStreamServiceImpl(DataRepository dataRepository) {
        this.dataRepository = dataRepository;
    }

    @Override
    public void fetchLargeDataset(DataRequest request,
                                   StreamObserver<DataChunk> responseObserver) {

        ServerCallStreamObserver<DataChunk> serverObserver =
                (ServerCallStreamObserver<DataChunk>) responseObserver;

        // 클라이언트가 취소했을 때 처리
        serverObserver.setOnCancelHandler(() ->
                log.warn("Client cancelled the stream request: {}", request.getQuery()));

        // 수동 플로우 컨트롤 활성화
        serverObserver.disableAutoInboundFlowControl();

        List<DataChunk> dataset = dataRepository.fetchAll(request.getQuery());
        Iterator<DataChunk> iterator = dataset.iterator();

        // isReady 상태가 될 때마다 호출되는 핸들러 등록
        serverObserver.setOnReadyHandler(new Runnable() {
            @Override
            public void run() {
                // isReady()가 true일 때만 데이터 전송
                while (serverObserver.isReady() && iterator.hasNext()) {
                    DataChunk chunk = iterator.next();
                    serverObserver.onNext(chunk);
                    log.debug("Sent chunk: {}", chunk.getId());
                }

                // 모든 데이터 전송 완료
                if (!iterator.hasNext()) {
                    serverObserver.onCompleted();
                    log.info("Stream completed for query: {}", request.getQuery());
                }
            }
        });
    }
}
```

### Bidirectional Streaming + 백프레셔 처리

양방향 스트리밍은 가장 복잡한 패턴이다. 클라이언트와 서버 모두 독립적으로 스트림을 열고 닫을 수 있으며, 양측의 처리 속도 차이를 모두 고려해야 한다.

```java
@Override
public StreamObserver<DataChunk> processStream(
        StreamObserver<ProcessedResult> responseObserver) {

    ServerCallStreamObserver<ProcessedResult> serverObserver =
            (ServerCallStreamObserver<ProcessedResult>) responseObserver;

    // 수동 플로우 컨트롤 활성화
    serverObserver.disableAutoInboundFlowControl();

    return new StreamObserver<DataChunk>() {
        private final AtomicInteger pendingCount = new AtomicInteger(0);
        private static final int MAX_PENDING = 100;

        {
            // 서버가 응답 가능한 상태일 때만 클라이언트 요청을 받도록 설정
            serverObserver.setOnReadyHandler(() -> {
                if (pendingCount.get() < MAX_PENDING) {
                    serverObserver.request(1); // 한 번에 하나씩 요청
                }
            });
            // 초기 요청
            serverObserver.request(1);
        }

        @Override
        public void onNext(DataChunk chunk) {
            pendingCount.incrementAndGet();

            try {
                ProcessedResult result = processChunk(chunk);

                if (serverObserver.isReady()) {
                    serverObserver.onNext(result);
                    pendingCount.decrementAndGet();

                    // 버퍼 여유가 있으면 다음 요청
                    if (pendingCount.get() < MAX_PENDING) {
                        serverObserver.request(1);
                    }
                } else {
                    // 서버가 아직 준비되지 않은 경우 큐에 넣거나 처리 지연
                    log.warn("Server observer not ready, chunk {} will be delayed", chunk.getId());
                    // 실제로는 별도 큐에 넣어 onReadyHandler에서 flush
                    pendingCount.decrementAndGet();
                }
            } catch (Exception e) {
                log.error("Error processing chunk: {}", chunk.getId(), e);
                serverObserver.onError(
                    Status.INTERNAL
                        .withDescription("Processing error: " + e.getMessage())
                        .asRuntimeException()
                );
            }
        }

        @Override
        public void onError(Throwable t) {
            log.error("Client stream error", t);
            // 리소스 정리
        }

        @Override
        public void onCompleted() {
            serverObserver.onCompleted();
            log.info("Bidirectional stream completed. Total processed: {}", pendingCount.get());
        }

        private ProcessedResult processChunk(DataChunk chunk) {
            // 실제 비즈니스 처리 로직
            return ProcessedResult.newBuilder()
                    .setId(chunk.getId())
                    .setStatus("SUCCESS")
                    .setMessage("Processed at: " + System.currentTimeMillis())
                    .build();
        }
    };
}
```

### 클라이언트 측 구현

```java
@Component
public class DataStreamClient {

    private final DataStreamServiceGrpc.DataStreamServiceStub asyncStub;

    public DataStreamClient(ManagedChannel channel) {
        this.asyncStub = DataStreamServiceGrpc.newStub(channel);
    }

    public void consumeServerStream(String query) {
        DataRequest request = DataRequest.newBuilder()
                .setQuery(query)
                .setBatchSize(100)
                .build();

        CountDownLatch latch = new CountDownLatch(1);

        asyncStub.fetchLargeDataset(request, new StreamObserver<DataChunk>() {
            private int receivedCount = 0;

            @Override
            public void onNext(DataChunk chunk) {
                receivedCount++;
                // 실제 처리 로직 (처리 속도가 느릴 경우 여기서 병목 발생)
                processChunk(chunk);

                if (receivedCount % 1000 == 0) {
                    log.info("Received {} chunks so far", receivedCount);
                }
            }

            @Override
            public void onError(Throwable t) {
                Status status = Status.fromThrowable(t);
                log.error("Stream error: {} - {}", status.getCode(), status.getDescription());
                latch.countDown();
            }

            @Override
            public void onCompleted() {
                log.info("Stream completed. Total received: {}", receivedCount);
                latch.countDown();
            }
        });

        try {
            latch.await(30, TimeUnit.SECONDS);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
```

## 주의사항 및 트레이드오프

### 1. `isReady()` 폴링의 함정

`isReady()`는 네트워크 버퍼의 현재 상태를 반영하지만, **바쁜 대기(Busy Waiting)** 방식으로 사용하면 CPU를 낭비한다. 반드시 `onReadyHandler`와 조합해서 이벤트 기반으로 사용해야 한다.

```java
// 잘못된 방법 - CPU 낭비
while (!serverObserver.isReady()) {
    Thread.sleep(10); // 절대 이렇게 하지 말 것
}

// 올바른 방법 - 이벤트 기반
serverObserver.setOnReadyHandler(() -> {
    // isReady가 true가 될 때 이 핸들러가 호출됨
    flushPendingData(serverObserver);
});
```

### 2. 스트림 생명주기 관리

스트리밍 연결은 장시간 유지되기 때문에 서버/클라이언트 모두 비정상 종료 시나리오를 반드시 처리해야 한다.

- `onCancelHandler`: 클라이언트가 연결을 끊었을 때 서버 리소스 정리
- `Deadline/Timeout` 설정으로 무한정 열린 스트림 방지
- `keepAlive` 설정으로 유휴 연결 관리

```java
// 채널 생성 시 keepAlive 설정
ManagedChannel channel = ManagedChannelBuilder.forAddress(host, port)
    .keepAliveTime(30, TimeUnit.SECONDS)
    .keepAliveTimeout(10, TimeUnit.SECONDS)
    .keepAliveWithoutCalls(true)
    .build();
```

### 3. 에러 처리와 재시도 전략

gRPC 스트리밍에서 에러가 발생하면 해당 스트림 전체가 종료된다. Unary 호출과 달리 스트림 중간에서의 에러 복구는 일반적으로 불가능하므로, **애플리케이션 레벨의 재시도 로직**을 설계해야 한다.

- `UNAVAILABLE`, `RESOURCE_EXHAUSTED` 상태 코드에 대한 Exponential Backoff 재시도
- 처리 위치(offset/cursor)를 추적하여 재연결 시 이어받기 구현
- gRPC의 내장 Retry Policy 활용 (Service Config 기반)

### 4. 모니터링 포인트

실무에서 스트리밍 서비스를 운영할 때 반드시 모니터링해야 할 지표들이 있다.

| 지표 | 설명 |
|------|------|
| `grpc.server.stream.received_messages_per_rpc` | RPC당 수신 메시지 수 |
| `grpc.server.stream.sent_messages_per_rpc` | RPC당 전송 메시지 수 |
| Active Stream Count | 현재 열린 스트림 수 |
| HTTP/2 Flow Control Window Size | 네트워크 레이어 백프레셔 지표 |
| Queue Depth | 애플리케이션 레이어 처리 대기 수 |

### 5. 트레이드오프 정리

| 항목 | 스트리밍 장점 | 스트리밍 단점 |
|------|---------------|---------------|
| **처리량** | 연결 오버헤드 감소로 높은 처리량 | 잘못된 백프레셔 처리 시 OOM 위험 |
| **지연시간** | 첫 번째 바이트 빠르게 수신 가능 | 스트림 설정 오버헤드 존재 |
| **복잡성** | 실시간 데이터 처리 용이 | 에러 처리, 재시도 로직 복잡 |
| **리소스** | 대용량 전송 시 효율적 | 장시간 연결로 서버 리소스 점유 |

## 정리

gRPC 스트리밍은 단순히 API를 스트리밍으로 바꾸는 것이 아니라, **데이터 흐름의 전체 생명주기를 설계하는 일**이다.

핵심을 정리하면 다음과 같다.

1. **패턴 선택을 신중하게**: 모든 API가 스트리밍이 필요하지 않다. 데이터 특성과 사용 패턴을 분석하고 적합한 패턴을 선택하라.

2. **백프레셔는 선택이 아닌 필수**: `ServerCallStreamObserver.isReady()`와 `onReadyHandler`, `request(n)` 메서드를 조합하여 반드시 구현하라. 이를 무시하면 운영 환경에서 반드시 문제가 발생한다.

3. **스트림 생명주기를 완전히 제어하라**: 정상 종료(`onCompleted`), 에러(`onError`), 취소(`onCancel`) 모든 케이스를 처리하고 리소스를 철저히 정리하라.

4. **관찰 가능성(Observability) 확보**: 스트리밍 서비스는 디버깅이 어렵다. 처음부터 메트릭, 로그, 트레이싱을 충분히 설계하라.

gRPC 스트리밍을 올바르게 구현하면 서비스 간 통신의 효율성과 실시간 처리 능력을 동시에 확보할 수 있다. 복잡성이 높은 만큼 철저한 설계와 테스트가 뒷받침되어야 한다.
