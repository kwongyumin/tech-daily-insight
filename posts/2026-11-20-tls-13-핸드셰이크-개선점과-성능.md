# TLS 1.3 핸드셰이크 개선점과 성능

## 개요

HTTPS가 사실상 표준이 된 오늘날, TLS(Transport Layer Security)는 웹 서비스 보안의 핵심 프로토콜입니다. 그런데 많은 개발자들이 TLS를 "그냥 켜두는 것"으로 취급하고, 그 내부 동작에는 크게 신경 쓰지 않는 경향이 있습니다.

TLS 1.3은 2018년 RFC 8446으로 표준화되었으며, 이전 버전인 TLS 1.2와 비교해 보안성과 성능 모두에서 의미 있는 개선이 이루어졌습니다. 특히 핸드셰이크 과정의 RTT(Round Trip Time) 단축은 레이턴시에 민감한 서비스에서 실질적인 사용자 경험 개선으로 이어집니다.

이 글에서는 TLS 1.2와 1.3의 핸드셰이크 차이를 분석하고, Java/Spring 환경에서 TLS 1.3을 적용하는 실전 예제와 함께 주의해야 할 트레이드오프까지 살펴보겠습니다.

## 핵심 개념

### TLS 1.2 핸드셰이크: 2-RTT의 비용

TLS 1.2에서 새로운 연결을 맺을 때는 최소 **2-RTT**가 필요합니다. 간략한 흐름은 다음과 같습니다.

```
Client                          Server
  |                               |
  |------ ClientHello ----------->|   (1)
  |<----- ServerHello ------------|   (2)
  |<----- Certificate ------------|
  |<----- ServerHelloDone --------|
  |------ ClientKeyExchange ----->|   (3)
  |------ ChangeCipherSpec ------>|
  |------ Finished -------------->|
  |<----- ChangeCipherSpec -------|   (4)
  |<----- Finished ---------------|
  |                               |
  |===== Application Data =======>|   (실제 데이터 전송)
```

TCP 3-way handshake 이후에도 TLS 핸드셰이크로 인해 2번의 왕복이 발생합니다. 즉, DNS 조회 + TCP + TLS만으로 클라이언트가 첫 번째 HTTP 요청을 보내기까지 상당한 시간이 소요됩니다.

또한 TLS 1.2는 지원하는 암호 스위트(Cipher Suite)가 매우 많았으며, RC4, 3DES 등 오늘날 취약한 것으로 판명된 알고리즘들도 포함되어 있어 협상 과정의 복잡도가 높았습니다.

### TLS 1.3 핸드셰이크: 1-RTT로 단축

TLS 1.3은 핸드셰이크를 **1-RTT**로 줄였습니다.

```
Client                          Server
  |                               |
  |------ ClientHello ----------->|   (1)
  |       (KeyShare 포함)          |
  |<----- ServerHello ------------|   (2)
  |       (KeyShare 포함)          |
  |<----- {Certificate} ----------|
  |<----- {CertificateVerify} ----|
  |<----- {Finished} -------------|
  |------ {Finished} ------------>|   (3)
  |                               |
  |===== Application Data =======>|   (실제 데이터 전송)
```

클라이언트는 `ClientHello`에 키 교환에 필요한 정보(KeyShare)를 미리 포함시켜 보냅니다. 서버는 이를 받는 즉시 키를 계산하고 암호화된 응답을 보낼 수 있습니다. 이를 통해 왕복 횟수가 절반으로 줄어듭니다.

### 0-RTT 재개(Session Resumption)

TLS 1.3의 또 다른 핵심 기능은 **0-RTT**입니다. 이전에 연결한 적 있는 서버에 재접속할 때, 클라이언트는 첫 번째 메시지에 애플리케이션 데이터를 바로 포함시킬 수 있습니다.

```
Client                          Server
  |                               |
  |------ ClientHello ----------->|
  |       (early_data 포함)        |
  |===== Early Application Data =>|   (0-RTT!)
  |<----- ServerHello ------------|
  |       ...                     |
```

이 기능은 성능 측면에서 매력적이지만, **재전송 공격(Replay Attack)** 취약점을 내포하고 있어 신중하게 사용해야 합니다(뒤에서 자세히 다룹니다).

### 제거된 취약 알고리즘

TLS 1.3은 하위 호환성을 과감히 포기하고 취약한 암호 스위트를 대거 제거했습니다.

| 항목 | TLS 1.2 | TLS 1.3 |
|------|---------|---------|
| 키 교환 | RSA, DHE, ECDHE | ECDHE, DHE만 허용 (Forward Secrecy 보장) |
| 암호화 | RC4, 3DES, AES-CBC 등 다수 | AES-GCM, ChaCha20-Poly1305, AES-CCM |
| 해시 | MD5, SHA-1 포함 | SHA-256, SHA-384 |
| RSA 직접 키 교환 | 허용 | **완전 제거** |

RSA 직접 키 교환 제거는 특히 중요합니다. TLS 1.2에서는 서버의 개인키가 노출되면 과거의 모든 세션이 복호화될 수 있었습니다. TLS 1.3은 ECDHE를 강제하여 **Perfect Forward Secrecy(PFS)**를 기본으로 보장합니다.

## 실전 예제

### Java 환경에서 TLS 1.3 활성화

Java 11+에서는 TLS 1.3이 기본 지원됩니다. 아래는 `HttpClient`를 사용해 TLS 1.3을 명시적으로 설정하는 예제입니다.

```java
import javax.net.ssl.SSLContext;
import javax.net.ssl.SSLParameters;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.net.URI;

public class Tls13ClientExample {

    public static HttpClient buildTls13HttpClient() throws Exception {
        SSLContext sslContext = SSLContext.getInstance("TLSv1.3");
        sslContext.init(null, null, null); // 기본 KeyManager, TrustManager 사용

        SSLParameters sslParameters = new SSLParameters();
        sslParameters.setProtocols(new String[]{"TLSv1.3"});
        // TLS 1.3 지원 Cipher Suite 명시
        sslParameters.setCipherSuites(new String[]{
            "TLS_AES_128_GCM_SHA256",
            "TLS_AES_256_GCM_SHA384",
            "TLS_CHACHA20_POLY1305_SHA256"
        });

        return HttpClient.newBuilder()
            .sslContext(sslContext)
            .sslParameters(sslParameters)
            .version(HttpClient.Version.HTTP_2) // HTTP/2와 함께 사용 권장
            .build();
    }

    public static void main(String[] args) throws Exception {
        HttpClient client = buildTls13HttpClient();

        HttpRequest request = HttpRequest.newBuilder()
            .uri(URI.create("https://example.com/api/data"))
            .GET()
            .build();

        HttpResponse<String> response = client.send(
            request, HttpResponse.BodyHandlers.ofString()
        );

        System.out.println("Status: " + response.statusCode());
        System.out.println("Body: " + response.body());
    }
}
```

### Spring Boot에서 내장 Tomcat TLS 1.3 설정

`application.yml`에서 간단하게 TLS 버전을 제한할 수 있습니다.

```yaml
server:
  port: 8443
  ssl:
    enabled: true
    key-store: classpath:keystore.p12
    key-store-password: ${SSL_KEYSTORE_PASSWORD}
    key-store-type: PKCS12
    key-alias: myapp
    # TLS 1.3만 허용 (1.2도 허용하려면 TLSv1.2,TLSv1.3)
    enabled-protocols: TLSv1.3
    ciphers:
      - TLS_AES_128_GCM_SHA256
      - TLS_AES_256_GCM_SHA384
      - TLS_CHACHA20_POLY1305_SHA256
```

구버전 클라이언트 호환성이 필요한 경우, `enabled-protocols: TLSv1.2,TLSv1.3`으로 설정하되 서버가 TLS 1.3을 우선 협상하도록 하는 것이 일반적인 전략입니다.

### Nginx 리버스 프록시 TLS 1.3 설정

실제 운영 환경에서는 Nginx가 TLS를 종료(termination)하는 구성이 많습니다.

```nginx
server {
    listen 443 ssl http2;
    server_name example.com;

    ssl_certificate     /etc/ssl/certs/example.com.crt;
    ssl_certificate_key /etc/ssl/private/example.com.key;

    # TLS 버전: 1.2와 1.3 병행 지원 (광범위한 호환성)
    ssl_protocols TLSv1.2 TLSv1.3;

    # TLS 1.2용 Cipher Suite (강력한 것만)
    ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305;
    ssl_prefer_server_ciphers off; # TLS 1.3에서는 무의미

    # 세션 재개 설정 (TLS 1.3 Session Ticket)
    ssl_session_timeout 1d;
    ssl_session_cache shared:SSL:10m;
    ssl_session_tickets off; # 보안 강화를 위해 비활성화 권장

    # OCSP Stapling
    ssl_stapling on;
    ssl_stapling_verify on;

    # HSTS
    add_header Strict-Transport-Security "max-age=63072000; includeSubDomains; preload" always;

    location / {
        proxy_pass http://backend:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

### TLS 핸드셰이크 시간 측정 (curl)

실제 TLS 버전 협상 결과와 핸드셰이크 시간을 확인하는 방법입니다.

```bash
# TLS 협상 버전 및 Cipher Suite 확인
curl -v --tlsv1.3 https://example.com 2>&1 | grep -E "TLS|SSL|cipher"

# 세부 타이밍 측정
curl -w "\n\
namelookup:    %{time_namelookup}s\n\
connect:       %{time_connect}s\n\
appconnect:    %{time_appconnect}s\n\
pretransfer:   %{time_pretransfer}s\n\
total:         %{time_total}s\n" \
-o /dev/null -s https://example.com

# OpenSSL로 직접 핸드셰이크 테스트
openssl s_client -connect example.com:443 -tls1_3 -brief
```

`time_appconnect`는 TLS 핸드셰이크 완료 시점을 나타내며, `time_connect`와의 차이가 TLS 핸드셰이크 소요 시간입니다.

## 주의사항 및 트레이드오프

### 0-RTT의 재전송 공격(Replay Attack) 위험

0-RTT 데이터는 서버가 첫 메시지를 받기 전에 전송되기 때문에, 중간자가 해당 패킷을 복사해 여러 번 전송하는 재전송 공격에 취약합니다.

**0-RTT를 사용해도 비교적 안전한 경우:**
- 멱등성이 보장되는 GET 요청
- 단순 조회성 API

**0-RTT를 절대 사용하면 안 되는 경우:**
- 결제, 송금 등 금전 관련 POST 요청
- 상태를 변경하는 모든 write 연산

Nginx에서 0-RTT를 명시적으로 비활성화하려면:

```nginx
ssl_early_data off; # 기본값이므로 명시적으로 선언
```

### Session Ticket 키 관리

TLS 1.3의 세션 재개는 Session Ticket을 사용하는데, 이 티켓을 암호화하는 키가 노출되면 세션 복호화가 가능해집니다. 특히 여러 서버가 Session Ticket을 공유하는 로드밸런서 환경에서는 키 rotation 전략이 필요합니다.

```bash
# Nginx에서 Session Ticket을 비활성화해 PFS를 완전히 보장
ssl_session_tickets off;
```

PFS를 최우선으로 한다면 Session Ticket을 비활성화하고, 대신 세션 캐시(`ssl_session_cache`)를 활용하는 것을 권장합니다.

### 구버전 클라이언트 호환성

TLS 1.3은 IE 11, Android 4.x 등 구형 환경에서 지원되지 않습니다. 서비스 사용자의 클라이언트 환경을 분석하고, 필요하다면 `TLSv1.2,TLSv1.3` 병행 지원 전략을 택해야 합니다.

[Can I Use](https://caniuse.com/tls1-3)에 따르면 2024년 기준 주요 브라우저의 TLS 1.3 지원율은 95% 이상이지만, 레거시 기기나 사내 시스템이 많은 B2B 서비스에서는 반드시 사전 조사가 필요합니다.

### Java 버전과 TLS 지원 현황

| Java 버전 | TLS 1.3 지원 |
|-----------|-------------|
| Java 8 (8u261+) | 지원 (제한적) |
| Java 11+ | 완전 지원 |
| Java 17+ | TLS 1.3 기본값 |

Java 8을 사용 중이라면 TLS 1.3 지원이 불완전하거나 별도 설정이 필요할 수 있으므로, 가능하면 Java 11 이상으로 마이그레이션하는 것을 권장합니다.

## 정리

TLS 1.3은 단순한 버전 업그레이드가 아닌, 보안과 성능을 근본적으로 재설계한 프로토콜입니다.

**핵심 정리:**

| 항목 | 개선 내용 |
|------|----------|
| 핸드셰이크 RTT | 2-RTT → 1-RTT |
| 세션 재개 | 0-RTT 지원 (단, 재전송 공격 주의) |
| 보안 알고리즘 | 취약한 Cipher Suite 제거, PFS 강제 |
| 협상 복잡도 | 암호 스위트 간소화로 협상 오버헤드 감소 |

실무에서 TLS 1.3을 도입할 때의 권장 사항은 다음과 같습니다.

1. **새 서비스**라면 TLS 1.3을 기본으로 설정하고, 필요한 경우 TLS 1.2를 병행 지원하세요.
2. **0-RTT는 멱등성이 보장되는 요청에만** 선택적으로 활성화하세요.
3. **Session Ticket 키는 주기적으로 rotation**하거나, 보안이 최우선이라면 비활성화하세요.
4. **Nginx/HAProxy 같은 프록시 레이어**에서 TLS를 종료하고, 백엔드와는 내부망 통신을 활용하는 것이 운영 편의성 측면에서 유리합니다.
5. **Java 환경**이라면 Java 17+ 사용을 강력히 권장하며, `SSLParameters`로 허용 프로토콜을 명시적으로 제한하세요.

TLS 핸드셰이크는 사용자의 첫 경험을 결정짓는 레이턴시와 직결됩니다. 보안 설정을 "켜두는 것"에서 나아가, 어떤 버전과 알고리즘으로 어떻게 협상하는지 이해하고 최적화하는 것이 시니어 개발자로서의 역량 차이를 만드는 부분입니다.
