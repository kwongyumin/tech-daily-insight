# 데이터베이스 데드락 원인 분석과 회피 전략

## 개요

데드락(Deadlock)은 두 개 이상의 트랜잭션이 서로가 보유한 락을 기다리며 무한정 대기 상태에 빠지는 현상이다. 개발 환경에서는 좀처럼 재현되지 않다가 트래픽이 몰리는 프로덕션 환경에서 갑자기 터지는 경우가 많아, 많은 백엔드 개발자들이 한 번쯤은 새벽 알람을 받아본 경험이 있을 것이다.

데드락은 단순히 "잠금 충돌"이 아니다. 발생 원인을 정확히 이해하지 못하면 임시방편으로 `retry` 로직만 추가하다가 근본 원인을 방치하게 된다. 이 글에서는 데드락이 발생하는 근본 원인을 분석하고, 실무에서 적용할 수 있는 회피 전략을 코드 예제와 함께 살펴본다.

---

## 핵심 개념

### 데드락의 4가지 필요 조건

데드락은 아래 4가지 조건이 **동시에** 성립할 때 발생한다. 하나라도 깨뜨리면 데드락은 발생하지 않는다.

| 조건 | 설명 |
|------|------|
| **상호 배제 (Mutual Exclusion)** | 자원은 한 번에 하나의 트랜잭션만 보유 가능 |
| **점유 대기 (Hold and Wait)** | 자원을 보유한 채 다른 자원을 기다림 |
| **비선점 (No Preemption)** | 보유 중인 자원을 강제로 빼앗을 수 없음 |
| **순환 대기 (Circular Wait)** | T1→T2→T1 형태의 순환 의존 관계 형성 |

실무에서 가장 자주 마주치는 원인은 **순환 대기**다. 두 트랜잭션이 동일한 행(Row)들을 **다른 순서**로 접근할 때 데드락이 발생한다.

### MySQL InnoDB에서의 락 종류

InnoDB에서는 다음과 같은 락이 데드락과 관련된다.

- **Row-level Lock (S/X Lock)**: 개별 행에 대한 공유/배타 락
- **Gap Lock**: 인덱스 범위에 대한 락 (팬텀 리드 방지)
- **Next-Key Lock**: Row Lock + Gap Lock의 조합
- **Table Lock**: DDL 또는 명시적 `LOCK TABLES` 사용 시

특히 **Gap Lock**은 예상치 못한 데드락을 유발하는 주범 중 하나다. `SELECT ... FOR UPDATE` 또는 범위 조건을 사용하는 `UPDATE` 쿼리에서 자주 발생한다.

## 실전 예제

### 예제 1: 순환 락으로 인한 데드락

가장 고전적인 패턴이다. `Account` 테이블에서 두 계좌 간 이체를 처리할 때 발생하는 시나리오를 보자.

```sql
-- 트랜잭션 A: 계좌 1 → 계좌 2로 이체
BEGIN;
SELECT * FROM account WHERE id = 1 FOR UPDATE; -- account 1 락 획득
-- (여기서 컨텍스트 스위치 발생)
SELECT * FROM account WHERE id = 2 FOR UPDATE; -- account 2 락 대기

-- 트랜잭션 B: 계좌 2 → 계좌 1로 이체
BEGIN;
SELECT * FROM account WHERE id = 2 FOR UPDATE; -- account 2 락 획득
SELECT * FROM account WHERE id = 1 FOR UPDATE; -- account 1 락 대기 → 데드락!
```

**해결책: 락 획득 순서를 고정한다.**

```java
@Service
@RequiredArgsConstructor
public class TransferService {

    private final AccountRepository accountRepository;

    @Transactional
    public void transfer(Long fromId, Long toId, BigDecimal amount) {
        // 항상 작은 ID를 먼저 락 → 순환 대기 조건 제거
        Long firstId = Math.min(fromId, toId);
        Long secondId = Math.max(fromId, toId);

        Account first = accountRepository.findByIdWithLock(firstId);
        Account second = accountRepository.findByIdWithLock(secondId);

        Account from = fromId.equals(firstId) ? first : second;
        Account to = toId.equals(firstId) ? first : second;

        from.withdraw(amount);
        to.deposit(amount);
    }
}
```

```java
// Repository
public interface AccountRepository extends JpaRepository<Account, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT a FROM Account a WHERE a.id = :id")
    Account findByIdWithLock(@Param("id") Long id);
}
```

### 예제 2: Gap Lock으로 인한 데드락

```sql
-- 테이블 구조
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    INDEX idx_user_status (user_id, status)
);

-- 트랜잭션 A
BEGIN;
UPDATE orders SET status = 'PROCESSING'
WHERE user_id = 100 AND status = 'PENDING'; -- Gap Lock 획득

-- 트랜잭션 B (동시 실행)
BEGIN;
INSERT INTO orders (user_id, status) VALUES (100, 'PENDING'); -- Gap Lock 대기 → 데드락
```

이 경우 InnoDB는 `user_id = 100` 범위에 Gap Lock을 걸기 때문에, 같은 범위에 INSERT하려는 트랜잭션과 충돌한다.

**해결책: 트랜잭션 격리 수준 조정 또는 쿼리 재설계**

```java
// 옵션 1: READ COMMITTED 격리 수준 사용 (Gap Lock 비활성화)
@Transactional(isolation = Isolation.READ_COMMITTED)
public void processOrders(Long userId) {
    // READ_COMMITTED에서는 Gap Lock이 발생하지 않음
    orderRepository.updateStatusByUserId(userId, "PENDING", "PROCESSING");
}

// 옵션 2: PK 기반 접근으로 Gap Lock 범위 제한
@Transactional
public void processOrderById(Long orderId) {
    // PK로 직접 접근하면 Gap Lock 대신 Row Lock만 발생
    Order order = orderRepository.findByIdWithLock(orderId);
    order.process();
}
```

> ⚠️ `READ_COMMITTED`로 변경하면 팬텀 리드가 발생할 수 있다. 비즈니스 요구사항에 따라 신중하게 선택해야 한다.

### 예제 3: 낙관적 락으로 데드락 회피

비관적 락 대신 낙관적 락을 사용하면 아예 락을 보유하지 않으므로 데드락 자체가 발생하지 않는다.

```java
@Entity
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private Integer stock;

    @Version  // 낙관적 락 버전 필드
    private Long version;

    public void decreaseStock(int quantity) {
        if (this.stock < quantity) {
            throw new InsufficientStockException();
        }
        this.stock -= quantity;
    }
}
```

```java
@Service
@RequiredArgsConstructor
public class OrderService {

    private final ProductRepository productRepository;
    private static final int MAX_RETRY = 3;

    public void placeOrder(Long productId, int quantity) {
        int attempt = 0;
        while (attempt < MAX_RETRY) {
            try {
                attemptOrder(productId, quantity);
                return;
            } catch (ObjectOptimisticLockingFailureException e) {
                attempt++;
                if (attempt >= MAX_RETRY) {
                    throw new OrderFailedException("재고 처리 중 충돌이 발생했습니다.");
                }
                // 짧은 지연 후 재시도 (지수 백오프 권장)
                sleep(50L * attempt);
            }
        }
    }

    @Transactional
    private void attemptOrder(Long productId, int quantity) {
        Product product = productRepository.findById(productId)
            .orElseThrow(ProductNotFoundException::new);
        product.decreaseStock(quantity);
    }
}
```

낙관적 락은 충돌이 드문 환경(읽기 비율이 높은 경우)에 적합하다. 충돌이 잦으면 재시도 오버헤드가 오히려 성능을 저하시킨다.

## 주의사항 및 트레이드오프

### 1. 트랜잭션 범위를 최소화하라

트랜잭션이 길수록 락 보유 시간이 길어지고 데드락 가능성이 높아진다. 외부 API 호출, 파일 I/O, 복잡한 비즈니스 로직은 트랜잭션 밖으로 꺼내야 한다.

```java
// ❌ 나쁜 예: 트랜잭션 안에서 외부 API 호출
@Transactional
public void processPayment(Long orderId) {
    Order order = orderRepository.findByIdWithLock(orderId);
    String result = paymentApiClient.charge(order); // 외부 API, 수 초 소요 가능
    order.complete(result);
}

// ✅ 좋은 예: 트랜잭션 밖에서 외부 호출
public void processPayment(Long orderId) {
    Order order = orderRepository.findById(orderId).orElseThrow();
    String result = paymentApiClient.charge(order); // 트랜잭션 외부
    updateOrderStatus(orderId, result);             // 짧은 트랜잭션
}

@Transactional
private void updateOrderStatus(Long orderId, String result) {
    Order order = orderRepository.findByIdWithLock(orderId);
    order.complete(result);
}
```

### 2. 인덱스 설계와 데드락의 관계

인덱스가 없는 컬럼에 `WHERE` 조건을 걸면 InnoDB는 테이블 전체에 락을 걸 수 있다. 이는 불필요하게 큰 범위에 락을 거는 것과 동일해 데드락 가능성을 크게 높인다.

```sql
-- ❌ 인덱스 없는 컬럼 조건 → 테이블 전체 락 가능성
UPDATE orders SET status = 'DONE' WHERE created_at < '2024-01-01';

-- ✅ 인덱스가 있는 컬럼 사용 → Row/Gap Lock 범위 최소화
-- ALTER TABLE orders ADD INDEX idx_created_at (created_at);
UPDATE orders SET status = 'DONE' WHERE created_at < '2024-01-01';
```

### 3. 락 타임아웃 설정

데드락은 DBMS가 감지해 한 쪽 트랜잭션을 자동 롤백하지만, 단순 락 대기(Lock Wait)는 감지되지 않는다. 적절한 타임아웃 설정이 필요하다.

```sql
-- MySQL InnoDB 락 대기 타임아웃 설정 (기본값: 50초)
SET innodb_lock_wait_timeout = 10;

-- 세션 단위 설정
SET SESSION innodb_lock_wait_timeout = 5;
```

```yaml
# Spring application.yml (HikariCP)
spring:
  datasource:
    hikari:
      connection-timeout: 5000       # 커넥션 획득 타임아웃
      idle-timeout: 600000
      max-lifetime: 1800000
  jpa:
    properties:
      javax.persistence.lock.timeout: 5000  # JPA 락 타임아웃 (ms)
```

### 4. 비관적 락 vs 낙관적 락 선택 기준

| 기준 | 비관적 락 | 낙관적 락 |
|------|-----------|-----------|
| 충돌 빈도 | 높을 때 적합 | 낮을 때 적합 |
| 처리 비용 | 충돌 방지, 대기 발생 | 충돌 시 재시도 비용 |
| 데드락 가능성 | 존재 | 없음 |
| 사용 예시 | 재고 차감, 금융 이체 | 게시글 수정, 설정 변경 |

## 정리

데드락은 단일한 원인이 아니라 여러 요소가 복합적으로 작용해 발생한다. 핵심 회피 전략을 정리하면 다음과 같다.

1. **락 획득 순서를 애플리케이션 전역에서 일관되게 정의** → 순환 대기 조건 제거
2. **트랜잭션 범위를 최소화** → 락 보유 시간 단축
3. **적절한 인덱스 설계** → 불필요한 락 범위 최소화
4. **격리 수준 검토** → Gap Lock이 필요 없다면 `READ_COMMITTED` 고려
5. **낙관적 락 활용** → 충돌이 드문 시나리오에서 데드락 원천 차단
6. **데드락 로그 모니터링 체계화** → `SHOW ENGINE INNODB STATUS` 또는 APM 연동으로 조기 감지

데드락 문제는 발생 후 땜질식 수정보다 **설계 단계에서의 트랜잭션 접근 순서 정의**와 **락 범위 최소화 원칙**을 지키는 것이 훨씬 효과적이다. 코드 리뷰 시 트랜잭션 경계와 락 획득 순서를 의식적으로 검토하는 습관을 팀 내에 정착시키는 것을 강력히 권장한다.
