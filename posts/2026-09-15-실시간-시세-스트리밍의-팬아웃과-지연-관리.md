# 실시간 시세 스트리밍의 팬아웃과 지연 관리

## 개요

주식, 암호화폐, 외환 시세를 실시간으로 제공하는 서비스를 설계할 때 가장 먼저 마주치는 기술적 도전은 **팬아웃(Fan-out)** 문제다. 단일 거래소 피드에서 수신한 하나의 시세 이벤트가 수만~수십만 명의 동시 접속자에게 전파되어야 한다. 이 과정에서 지연(latency)을 수 밀리초 이내로 유지하면서도 시스템이 과부하되지 않도록 제어하는 것이 핵심 과제다.

이 글에서는 시세 스트리밍 시스템의 팬아웃 구조를 단계별로 분석하고, 지연을 최소화하기 위한 설계 패턴과 실제 적용 가능한 코드 예제를 다룬다.

---

## 핵심 개념

### 팬아웃이란?

팬아웃은 하나의 메시지를 여러 수신자에게 동시에 전달하는 패턴이다. 시세 스트리밍 맥락에서는 다음 두 가지 레이어에서 발생한다.

- **브로커 레벨 팬아웃**: Kafka, Redis Pub/Sub 등에서 하나의 토픽 메시지를 여러 컨슈머 그룹에 전달
- **서버 레벨 팬아웃**: 각 애플리케이션 서버에서 웹소켓/SSE 연결을 통해 연결된 클라이언트들에게 브로드캐스트

팬아웃 비율이 높아질수록 한 번의 시세 업데이트가 시스템 전체에 미치는 증폭 효과가 커진다. 예를 들어 초당 100건의 시세 업데이트가 들어오고, 서버 1대에 10,000개의 웹소켓 연결이 붙어 있다면, 그 서버는 초당 최대 **100만 건의 쓰기 작업**을 처리해야 한다.

### 지연의 구성 요소

시세 데이터의 End-to-End 지연은 다음 구간의 합산이다.

```
[거래소] → [수신 서버] → [메시지 브로커] → [애플리케이션 서버] → [클라이언트]
    L1           L2              L3                  L4
```

- **L1**: 거래소 피드 수신 지연 (네트워크, 위치 의존적)
- **L2**: 메시지 직렬화/역직렬화, 브로커 produce 지연
- **L3**: 브로커 consume + 비즈니스 로직 처리
- **L4**: 웹소켓 전송 + 클라이언트 렌더링

우리가 코드 레벨에서 제어 가능한 구간은 주로 L2~L4다.

## 실전 예제

### 1. 거래소 피드 수신 및 Kafka 발행

거래소 WebSocket에서 시세를 받아 Kafka로 발행하는 수신 서버다. 핵심은 **최소한의 변환**만 수행하고 즉시 발행하는 것이다.

```java
@Component
@Slf4j
public class ExchangeFeedHandler {

    private final KafkaTemplate<String, byte[]> kafkaTemplate;
    private final ObjectMapper objectMapper;

    // Protobuf 또는 Avro 사용을 권장하지만 예제는 JSON으로 단순화
    public void onMessage(String rawMessage) {
        long receiveNanos = System.nanoTime();
        
        try {
            TickerEvent event = parseMinimal(rawMessage, receiveNanos);
            
            ProducerRecord<String, byte[]> record = new ProducerRecord<>(
                "ticker-raw",
                event.getSymbol(),                    // 파티션 키: 심볼별 순서 보장
                objectMapper.writeValueAsBytes(event)
            );
            
            // acks=1, linger.ms=0으로 설정해 지연 최소화
            kafkaTemplate.send(record);
            
        } catch (Exception e) {
            log.error("Feed parsing error", e);
        }
    }

    private TickerEvent parseMinimal(String raw, long receiveNanos) throws Exception {
        // 필요한 필드만 추출 (전체 파싱 비용 최소화)
        JsonNode node = objectMapper.readTree(raw);
        return TickerEvent.builder()
            .symbol(node.get("s").asText())
            .price(node.get("p").asText())
            .volume(node.get("v").asText())
            .exchangeTs(node.get("T").asLong())
            .serverReceiveNanos(receiveNanos)
            .build();
    }
}
```

**Kafka Producer 설정 포인트**:

```yaml
spring:
  kafka:
    producer:
      acks: "1"           # all(=-1)은 지연 증가, 시세 특성상 1로도 충분
      linger-ms: 0        # 배치 대기 없이 즉시 전송
      compression-type: lz4  # 처리량 vs 지연 균형
      buffer-memory: 33554432
```

### 2. 서버 레벨 팬아웃: 심볼 기반 구독 관리

모든 클라이언트에게 모든 심볼의 시세를 브로드캐스트하면 불필요한 트래픽이 폭발한다. 클라이언트가 구독한 심볼만 전송하는 **선택적 팬아웃** 구조를 구현한다.

```java
@Component
public class TickerSubscriptionManager {

    // symbol -> Set<WebSocketSession> 매핑
    private final ConcurrentHashMap<String, Set<WebSocketSession>> symbolSubscribers
        = new ConcurrentHashMap<>();

    // sessionId -> Set<String> 구독 심볼 역인덱스
    private final ConcurrentHashMap<String, Set<String>> sessionSymbols
        = new ConcurrentHashMap<>();

    public void subscribe(WebSocketSession session, String symbol) {
        symbolSubscribers
            .computeIfAbsent(symbol, k -> ConcurrentHashMap.newKeySet())
            .add(session);

        sessionSymbols
            .computeIfAbsent(session.getId(), k -> ConcurrentHashMap.newKeySet())
            .add(symbol);
    }

    public void unsubscribeAll(WebSocketSession session) {
        Set<String> symbols = sessionSymbols.remove(session.getId());
        if (symbols != null) {
            symbols.forEach(symbol -> {
                Set<WebSocketSession> sessions = symbolSubscribers.get(symbol);
                if (sessions != null) sessions.remove(session);
            });
        }
    }

    public Set<WebSocketSession> getSubscribers(String symbol) {
        return symbolSubscribers.getOrDefault(symbol, Collections.emptySet());
    }
}
```

### 3. Kafka 컨슈머 → 웹소켓 팬아웃

```java
@Component
@Slf4j
public class TickerFanoutConsumer {

    private final TickerSubscriptionManager subscriptionManager;
    // 단일 공유 버퍼 대신 심볼별 최신값만 캐싱 (Last-Value Cache)
    private final ConcurrentHashMap<String, String> latestTickerCache
        = new ConcurrentHashMap<>();

    @KafkaListener(
        topics = "ticker-raw",
        concurrency = "4",           // 파티션 수에 맞게 조정
        containerFactory = "tickerKafkaListenerContainerFactory"
    )
    public void consume(ConsumerRecord<String, byte[]> record) {
        String symbol = record.key();
        String payload = new String(record.value());

        // 최신값 캐시 갱신 (구독자 연결 시 즉시 전송용)
        latestTickerCache.put(symbol, payload);

        // 비동기 팬아웃
        fanoutToSubscribers(symbol, payload);
    }

    private void fanoutToSubscribers(String symbol, String payload) {
        Set<WebSocketSession> subscribers = subscriptionManager.getSubscribers(symbol);
        if (subscribers.isEmpty()) return;

        TextMessage message = new TextMessage(payload);

        // 병렬 전송: VirtualThread(Java 21) 또는 별도 ExecutorService 활용
        subscribers.parallelStream().forEach(session -> {
            if (session.isOpen()) {
                try {
                    session.sendMessage(message);
                } catch (IOException e) {
                    log.warn("Send failed for session {}", session.getId());
                    subscriptionManager.unsubscribeAll(session);
                }
            }
        });
    }

    // 신규 구독자에게 최신 스냅샷 즉시 전송
    public void sendSnapshot(WebSocketSession session, String symbol) throws IOException {
        String latest = latestTickerCache.get(symbol);
        if (latest != null) {
            session.sendMessage(new TextMessage(latest));
        }
    }
}
```

### 4. 역압력(Back-pressure) 제어

클라이언트 처리 속도가 서버 전송 속도를 따라가지 못할 때 메시지가 쌓이는 문제를 방지한다.

```java
public class BackpressureAwareSession {

    private final WebSocketSession delegate;
    private final AtomicInteger pendingCount = new AtomicInteger(0);
    private static final int MAX_PENDING = 50;

    public boolean trySend(TextMessage message) {
        if (pendingCount.get() >= MAX_PENDING) {
            // 슬로우 컨슈머: 메시지 드롭 또는 세션 종료 결정
            log.warn("Session {} is slow, dropping message", delegate.getId());
            return false;
        }

        pendingCount.incrementAndGet();
        try {
            delegate.sendMessage(message);
            return true;
        } catch (IOException e) {
            return false;
        } finally {
            pendingCount.decrementAndGet();
        }
    }
}
```

## 주의사항 및 트레이드오프

### 1. 메시지 순서 보장 vs 처리량

Kafka에서 심볼을 파티션 키로 사용하면 동일 심볼의 시세 순서가 보장되지만, 파티션 수가 컨슈머 스레드 수의 병목이 된다. 시세 특성상 **최신값이 이전 값을 항상 덮어쓰는** 성질을 활용하면, 순서 역전이 발생해도 결과적으로는 정합성이 유지되는 경우가 많다.

반대로 OHLC 집계나 체결 이력처럼 순서가 중요한 데이터는 반드시 파티션 내 순서 보장 컨슈머를 유지해야 한다.

### 2. 연결 수 vs 서버 수 스케일링

웹소켓은 연결당 파일 디스크립터를 점유하므로, OS 레벨의 `ulimit`과 네트워크 버퍼 설정이 필수다.

```bash
# /etc/sysctl.conf
net.core.somaxconn = 65535
net.ipv4.tcp_max_syn_backlog = 65535
fs.file-max = 1000000

# /etc/security/limits.conf
* soft nofile 1000000
* hard nofile 1000000
```

단일 서버에 수만 개 이상의 연결이 붙는다면, 수평 확장과 함께 **클라이언트가 어느 서버에 연결되어도 동일한 데이터를 받을 수 있는** 구조가 필요하다. Redis Pub/Sub이나 Kafka 컨슈머 그룹을 서버 간 메시지 공유 레이어로 사용하되, 이 과정에서 추가 지연이 발생함을 인지해야 한다.

### 3. 스로틀링과 티어별 지연 차등화

모든 사용자에게 동일한 지연을 제공할 필요는 없다. 유료 구독자에게는 실시간, 무료 사용자에게는 N초 지연 데이터를 제공하는 티어링 전략은 인프라 비용 절감과 비즈니스 모델 보호 모두에 효과적이다.

```java
public class TieredTickerDispatcher {
    
    private final ScheduledExecutorService scheduler = 
        Executors.newScheduledThreadPool(2);

    public void dispatch(TickerEvent event, WebSocketSession session, UserTier tier) {
        switch (tier) {
            case PREMIUM -> sendImmediate(event, session);
            case BASIC   -> sendDelayed(event, session, 3, TimeUnit.SECONDS);
            case FREE    -> sendDelayed(event, session, 15, TimeUnit.SECONDS);
        }
    }

    private void sendImmediate(TickerEvent event, WebSocketSession session) {
        // 직접 전송
    }

    private void sendDelayed(TickerEvent event, WebSocketSession session,
                              long delay, TimeUnit unit) {
        scheduler.schedule(() -> {
            if (session.isOpen()) {
                try {
                    session.sendMessage(new TextMessage(event.toJson()));
                } catch (IOException ignored) {}
            }
        }, delay, unit);
    }
}
```

### 4. 심볼 핫스팟 문제

BTC/USDT, AAPL 같은 인기 심볼은 구독자 수가 수백 배 이상 많을 수 있다. 이런 심볼에 대한 팬아웃이 집중되면 특정 Kafka 파티션과 특정 애플리케이션 서버에 부하가 집중된다.

해결책으로는:
- **Kafka 파티션을 심볼 단위가 아닌 심볼 그룹 단위**로 설계해 핫 파티션 완화
- **인기 심볼 전용 서버 분리** 또는 가중치 기반 컨슈머 할당
- 서버 내 팬아웃을 `parallelStream()` 대신 **Work Stealing Pool**로 처리해 스레드 기아 방지

## 정리

실시간 시세 스트리밍의 팬아웃과 지연 문제는 단일 기술로 해결되지 않는다. 다음 설계 원칙을 기억하자.

| 레이어 | 주요 전략 |
|--------|-----------|
| 수신 서버 | 최소 변환, 즉시 발행, linger.ms=0 |
| 메시지 브로커 | 심볼 기반 파티셔닝, 핫스팟 파티션 분리 |
| 애플리케이션 서버 | 선택적 팬아웃, Last-Value Cache, Back-pressure 제어 |
| 클라이언트 연결 | OS 레벨 튜닝, 티어별 지연 차등화, 수평 확장 |

**팬아웃 비율이 높을수록** 각 레이어의 처리 시간 증가가 전체 지연에 미치는 영향이 기하급수적으로 커진다. 지연 목표값을 먼저 정의하고, 각 구간을 측정한 뒤 병목을 순차적으로 개선하는 접근이 가장 실효성 있다. 시세 특성인 "최신값 우선" 원칙을 설계 전반에 일관되게 적용하면, 완벽한 전달 보장보다 낮은 지연이 더 가치 있는 트레이드오프임을 시스템이 자연스럽게 반영하게 된다.
