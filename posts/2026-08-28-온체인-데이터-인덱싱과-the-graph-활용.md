# 온체인 데이터 인덱싱과 The Graph 활용

## 개요

블록체인 애플리케이션을 개발하다 보면 필연적으로 마주치는 문제가 있다. 스마트 컨트랙트에서 발생한 이벤트를 효율적으로 조회하거나, 특정 주소의 트랜잭션 히스토리를 빠르게 집계하고 싶을 때, 단순히 `eth_getLogs`나 `getPastEvents`를 반복 호출하는 것은 심각한 성능 문제를 야기한다.

예를 들어 Uniswap의 특정 풀에서 지난 30일간의 거래량을 집계하려면 수천 개의 블록을 순회해야 하며, RPC 노드의 레이트 리밋에 금방 걸리게 된다. 이러한 문제를 해결하기 위해 등장한 것이 **The Graph**다.

The Graph는 블록체인 데이터를 인덱싱하고 GraphQL API로 조회할 수 있게 해주는 탈중앙화 프로토콜이다. 실무에서 DeFi 대시보드, NFT 마켓플레이스, DAO 거버넌스 플랫폼 등 다양한 Web3 서비스가 The Graph를 기반으로 구축되어 있다. 이 포스팅에서는 The Graph의 핵심 개념부터 Subgraph 개발, 실전 쿼리 활용까지 실무 관점에서 깊이 있게 다뤄보겠다.

## 핵심 개념

### Subgraph란?

The Graph에서 인덱싱의 단위는 **Subgraph**다. Subgraph는 세 가지 핵심 파일로 구성된다.

| 파일 | 역할 |
|---|---|
| `subgraph.yaml` | 인덱싱할 컨트랙트, 이벤트, 네트워크 등 설정 |
| `schema.graphql` | 노출할 데이터의 GraphQL 스키마 정의 |
| `src/mapping.ts` | 이벤트를 받아 엔티티로 변환하는 AssemblyScript 핸들러 |

### 인덱싱 파이프라인

The Graph 노드는 다음 흐름으로 동작한다.

```
이더리움 노드 (RPC/Firehose)
        ↓
  블록/트랜잭션/이벤트 수신
        ↓
  Subgraph 매니페스트 매칭
        ↓
  AssemblyScript 핸들러 실행
        ↓
  엔티티 저장 (PostgreSQL)
        ↓
  GraphQL API 노출
```

### Graph Node vs Hosted Service vs Subgraph Studio

- **Graph Node (Self-hosted)**: 직접 노드를 운영하는 방식. 완전한 제어권을 갖지만 인프라 비용이 발생한다.
- **Subgraph Studio**: The Graph의 공식 개발/배포 환경. 테스트넷 배포는 무료다.
- **The Graph Network**: 탈중앙화 네트워크에 배포하여 Indexer들이 쿼리를 처리하는 방식.

## 실전 예제

ERC-20 토큰의 Transfer 이벤트를 인덱싱하고, 주소별 잔액과 거래 내역을 조회하는 Subgraph를 처음부터 구축해보자.

### 1. 프로젝트 초기화

```bash
npm install -g @graphprotocol/graph-cli

graph init \
  --studio \
  --protocol ethereum \
  --from-contract 0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48 \
  --network mainnet \
  --contract-name USDC \
  --index-events \
  my-erc20-subgraph

cd my-erc20-subgraph
npm install
```

### 2. 스키마 정의 (schema.graphql)

```graphql
type Account @entity {
  id: ID!                        # 지갑 주소
  balance: BigInt!               # 현재 잔액
  transfersFrom: [Transfer!]! @derivedFrom(field: "from")
  transfersTo: [Transfer!]! @derivedFrom(field: "to")
  totalSent: BigInt!
  totalReceived: BigInt!
  txCount: Int!
}

type Transfer @entity {
  id: ID!                        # txHash-logIndex
  from: Account!
  to: Account!
  amount: BigInt!
  blockNumber: BigInt!
  timestamp: BigInt!
  txHash: Bytes!
}

type DailyVolume @entity {
  id: ID!                        # YYYY-MM-DD
  date: Int!
  volume: BigInt!
  txCount: Int!
}
```

### 3. 매니페스트 설정 (subgraph.yaml)

```yaml
specVersion: 0.0.5
schema:
  file: ./schema.graphql
dataSources:
  - kind: ethereum
    name: USDC
    network: mainnet
    source:
      address: "0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48"
      abi: ERC20
      startBlock: 6082465   # 컨트랙트 배포 블록부터 인덱싱
    mapping:
      kind: ethereum/events
      apiVersion: 0.0.7
      language: wasm/assemblyscript
      entities:
        - Account
        - Transfer
        - DailyVolume
      abis:
        - name: ERC20
          file: ./abis/ERC20.json
      eventHandlers:
        - event: Transfer(indexed address,indexed address,uint256)
          handler: handleTransfer
      file: ./src/mapping.ts
```

### 4. 핸들러 구현 (src/mapping.ts)

```typescript
import {
  Transfer as TransferEvent,
} from "../generated/USDC/ERC20";
import {
  Account,
  Transfer,
  DailyVolume,
} from "../generated/schema";
import {
  BigInt,
  Bytes,
} from "@graphprotocol/graph-ts";

function getOrCreateAccount(address: Bytes): Account {
  let id = address.toHexString();
  let account = Account.load(id);

  if (!account) {
    account = new Account(id);
    account.balance = BigInt.fromI32(0);
    account.totalSent = BigInt.fromI32(0);
    account.totalReceived = BigInt.fromI32(0);
    account.txCount = 0;
  }

  return account;
}

function getDayId(timestamp: BigInt): string {
  let daySeconds = BigInt.fromI32(86400);
  let dayIndex = timestamp.div(daySeconds);
  return dayIndex.toString();
}

export function handleTransfer(event: TransferEvent): void {
  // Transfer 엔티티 생성
  let transferId =
    event.transaction.hash.toHexString() +
    "-" +
    event.logIndex.toString();

  let transfer = new Transfer(transferId);
  transfer.txHash = event.transaction.hash;
  transfer.blockNumber = event.block.number;
  transfer.timestamp = event.block.timestamp;
  transfer.amount = event.params.value;

  // 송신자 계정 업데이트
  let fromAccount = getOrCreateAccount(event.params.from);
  fromAccount.balance = fromAccount.balance.minus(event.params.value);
  fromAccount.totalSent = fromAccount.totalSent.plus(event.params.value);
  fromAccount.txCount = fromAccount.txCount + 1;
  fromAccount.save();

  // 수신자 계정 업데이트
  let toAccount = getOrCreateAccount(event.params.to);
  toAccount.balance = toAccount.balance.plus(event.params.value);
  toAccount.totalReceived = toAccount.totalReceived.plus(event.params.value);
  toAccount.txCount = toAccount.txCount + 1;
  toAccount.save();

  transfer.from = fromAccount.id;
  transfer.to = toAccount.id;
  transfer.save();

  // 일별 거래량 집계
  let dayId = getDayId(event.block.timestamp);
  let dailyVolume = DailyVolume.load(dayId);

  if (!dailyVolume) {
    dailyVolume = new DailyVolume(dayId);
    dailyVolume.date = event.block.timestamp
      .div(BigInt.fromI32(86400))
      .toI32();
    dailyVolume.volume = BigInt.fromI32(0);
    dailyVolume.txCount = 0;
  }

  dailyVolume.volume = dailyVolume.volume.plus(event.params.value);
  dailyVolume.txCount = dailyVolume.txCount + 1;
  dailyVolume.save();
}
```

### 6. GraphQL 쿼리 활용

배포된 Subgraph에 대해 다양한 쿼리를 실행할 수 있다.

```graphql
# 특정 주소의 잔액 및 최근 거래 조회
query GetAccountInfo($address: ID!) {
  account(id: $address) {
    balance
    totalSent
    totalReceived
    txCount
    transfersFrom(
      first: 10
      orderBy: timestamp
      orderDirection: desc
    ) {
      amount
      timestamp
      to {
        id
      }
    }
  }
}

# 최근 7일 일별 거래량 집계
query GetWeeklyVolume($since: Int!) {
  dailyVolumes(
    where: { date_gte: $since }
    orderBy: date
    orderDirection: asc
  ) {
    date
    volume
    txCount
  }
}

# 대용량 데이터 페이지네이션 (skip + first 대신 cursor 방식)
query GetTransfersCursor($lastId: ID!) {
  transfers(
    first: 1000
    where: { id_gt: $lastId }
    orderBy: id
    orderDirection: asc
  ) {
    id
    from { id }
    to { id }
    amount
    timestamp
  }
}
```

### 7. Spring Boot 백엔드에서 통합

Spring Boot 서버에서 The Graph API를 호출하는 서비스 레이어를 구성할 수 있다.

```java
@Service
@RequiredArgsConstructor
public class GraphQueryService {

    private final WebClient webClient;

    @Value("${graph.subgraph.url}")
    private String subgraphUrl;

    public Mono<AccountInfo> getAccountInfo(String address) {
        String query = """
            query GetAccountInfo($address: ID!) {
              account(id: $address) {
                balance
                totalSent
                totalReceived
                txCount
              }
            }
            """;

        Map<String, Object> requestBody = Map.of(
            "query", query,
            "variables", Map.of("address", address.toLowerCase())
        );

        return webClient.post()
            .uri(subgraphUrl)
            .contentType(MediaType.APPLICATION_JSON)
            .bodyValue(requestBody)
            .retrieve()
            .bodyToMono(GraphResponse.class)
            .map(response -> response.getData().getAccount())
            .retryWhen(Retry.backoff(3, Duration.ofSeconds(1)));
    }
}
```

## 주의사항 및 트레이드오프

### 1. 인덱싱 지연 (Indexing Lag)

The Graph는 **실시간 데이터가 아니다**. 일반적으로 수 초에서 수십 초의 지연이 발생한다. 최신 블록 번호를 `_meta` 쿼리로 확인하고, 지연이 임계치를 초과하면 폴백 처리를 구현해야 한다.

```graphql
query CheckIndexingStatus {
  _meta {
    block {
      number
    }
    hasIndexingErrors
  }
}
```

### 2. `skip` 페이지네이션의 한계

The Graph의 `skip`은 최대 5,000까지만 허용된다. 대용량 데이터 조회 시에는 반드시 `id_gt` 방식의 커서 기반 페이지네이션을 사용해야 한다. 위 예제의 `GetTransfersCursor` 쿼리가 올바른 패턴이다.

### 3. AssemblyScript 제약

매핑 핸들러는 JavaScript가 아닌 **AssemblyScript**로 작성되며, 일반 TS/JS 라이브러리를 그대로 사용할 수 없다. `Map`, `Set` 등 자료구조도 WASM 환경에 맞는 타입을 사용해야 하며, `try-catch`가 지원되지 않는다.

### 4. 비용 구조

The Graph Network에 배포할 경우 GRT 토큰으로 Indexer에게 쿼리 비용을 지불한다. 트래픽이 많은 서비스는 상당한 비용이 발생할 수 있으므로, **Self-hosted Graph Node** 운영과 비용/운영 부담을 비교 검토해야 한다.

### 5. 리오그(Reorg) 처리

이더리움 체인 리오그 시 The Graph는 자동으로 롤백하지만, 이미 클라이언트에 전달된 데이터는 되돌릴 수 없다. 금융 서비스라면 일정 블록 컨펌 이후 데이터를 확정하는 로직을 별도로 구현해야 한다.

### 6. Self-hosted vs Managed 선택 기준

| 기준 | Self-hosted | The Graph Network |
|---|---|---|
| 비용 | 인프라 비용 고정 | 쿼리량 비례 |
| 신뢰성 | 직접 관리 | 탈중앙화로 안정적 |
| 검열 저항성 | 낮음 | 높음 |
| 설정 유연성 | 완전 제어 | 제한적 |

## 정리

The Graph는 온체인 데이터 인덱싱 문제를 우아하게 해결하는 도구다. 핵심을 정리하면 다음과 같다.

- **Subgraph**는 `subgraph.yaml`, `schema.graphql`, `mapping.ts` 세 파일로 구성된다.
- **AssemblyScript 핸들러**에서 이벤트를 받아 엔티티로 변환하고 저장한다.
- GraphQL의 강력한 쿼리 기능으로 복잡한 온체인 데이터 집계를 클라이언트에서 유연하게 처리할 수 있다.
- 인덱싱 지연, 페이지네이션 한계, 리오그 처리 등 **실무 함정**을 사전에 인지하고 대비해야 한다.

Web3 백엔드 개발에서 The Graph를 능숙하게 활용하면 RPC 노드 의존도를 크게 줄이고, 데이터 조회 성능을 수십 배 향상시킬 수 있다. 특히 DeFi 분석 서비스, 포트폴리오 트래커, 온체인 거버넌스 플랫폼을 구축한다면 The Graph는 필수 인프라라고 할 수 있다.
