# 데이터베이스 백업과 시점 복구(PITR) 설계

## 개요

운영 중인 서비스에서 데이터베이스 장애나 실수로 인한 데이터 손실은 언제든 발생할 수 있다. DBA나 개발자가 `DROP TABLE`이나 `DELETE FROM orders` 같은 치명적인 실수를 저질렀을 때, 혹은 애플리케이션 버그로 인해 데이터가 대량으로 오염되었을 때, 우리에게 남은 최후의 수단은 **백업과 복구 전략**이다.

단순히 주기적으로 풀 백업을 뜨는 것만으로는 충분하지 않다. "어제 새벽 3시에 백업한 데이터를 오늘 오전 11시 42분 상태로 되돌려줄 수 있어?"라는 요구에 답할 수 있어야 한다. 이것이 바로 **PITR(Point-In-Time Recovery, 시점 복구)**이다.

이 글에서는 PostgreSQL을 기준으로 백업 전략의 핵심 개념부터, 실무에서 바로 활용 가능한 PITR 설계 방법, 그리고 각 접근법의 트레이드오프까지 깊이 있게 다룬다.

## 핵심 개념

### 백업의 세 가지 유형

| 유형 | 설명 | 장점 | 단점 |
|------|------|------|------|
| **풀 백업(Full Backup)** | 전체 데이터를 통째로 복사 | 복구가 단순 | 시간·용량 비용 큼 |
| **증분 백업(Incremental Backup)** | 이전 백업 이후 변경분만 복사 | 용량 효율적 | 복구 시 체인 조합 필요 |
| **차등 백업(Differential Backup)** | 마지막 풀 백업 이후 모든 변경분 | 복구가 풀+차등 두 단계 | 증분보다 용량 큼 |

### WAL(Write-Ahead Log)이 PITR의 핵심

PostgreSQL의 PITR은 **WAL(Write-Ahead Log)** 파일을 기반으로 동작한다. 모든 데이터 변경은 먼저 WAL에 기록되며, 이 로그를 순차적으로 재적용(replay)함으로써 임의의 시점으로 복구가 가능하다.

```
[베이스 백업] → [WAL 아카이브 스트림] → [목표 시점]
     ↓                    ↓                    ↓
  특정 시점의           변경 이력            여기까지만
  스냅샷 파일          (연속적)              적용 후 종료
```

MySQL/MariaDB의 경우 Binary Log(binlog)가 같은 역할을 한다. 기본 원리는 동일하다.

### RPO와 RTO

백업 설계에서 반드시 정의해야 하는 두 가지 지표다.

- **RPO(Recovery Point Objective)**: 복구 가능한 최대 데이터 손실 허용 시간. "최대 5분 전 데이터까지는 잃을 수 있다"
- **RTO(Recovery Time Objective)**: 복구에 허용되는 최대 시간. "장애 발생 후 30분 안에 서비스를 재개해야 한다"

RPO가 낮을수록(손실 허용치 작을수록) WAL 아카이빙 간격을 짧게 가져가야 하고, RTO가 낮을수록(빠른 복구) 베이스 백업 빈도를 높이거나 대기(standby) 서버를 별도로 운용해야 한다.

## 실전 예제

### 1. PostgreSQL 베이스 백업 구성

먼저 `postgresql.conf`에서 WAL 아카이빙을 활성화한다.

```conf
# postgresql.conf
wal_level = replica
archive_mode = on
archive_command = 'aws s3 cp %p s3://my-db-backup/wal/%f'
archive_timeout = 300   # 5분마다 강제 WAL 세그먼트 전환

# 복구를 위한 WAL 보존 설정
wal_keep_size = 1024    # 1GB 분량의 WAL을 로컬에 보관
```

`pg_basebackup`을 이용해 베이스 백업을 생성하는 스크립트:

```bash
#!/bin/bash
# base_backup.sh

BACKUP_DATE=$(date +%Y%m%d_%H%M%S)
BACKUP_DIR="/backup/base/${BACKUP_DATE}"
S3_BUCKET="s3://my-db-backup/base/${BACKUP_DATE}"

echo "[$(date)] 베이스 백업 시작"

pg_basebackup \
  --host=localhost \
  --port=5432 \
  --username=replicator \
  --pgdata="${BACKUP_DIR}" \
  --format=tar \
  --gzip \
  --compress=9 \
  --checkpoint=fast \
  --progress \
  --verbose

if [ $? -eq 0 ]; then
  echo "[$(date)] 로컬 백업 완료. S3 업로드 시작..."
  aws s3 sync "${BACKUP_DIR}" "${S3_BUCKET}" --storage-class STANDARD_IA
  
  # 로컬 백업 정리 (7일치 유지)
  find /backup/base -maxdepth 1 -type d -mtime +7 -exec rm -rf {} \;
  
  echo "[$(date)] 베이스 백업 완료: ${S3_BUCKET}"
else
  echo "[$(date)] 베이스 백업 실패!" >&2
  # 슬랙 알림 또는 PagerDuty 호출
  curl -X POST "${SLACK_WEBHOOK_URL}" \
    -H 'Content-Type: application/json' \
    -d '{"text": "🚨 DB 베이스 백업 실패! 즉시 확인 필요"}'
  exit 1
fi
```

### 2. PITR 복구 절차

실제 장애 시나리오: 오전 10시 30분에 운영자가 실수로 `TRUNCATE TABLE payments`를 실행했다. 마지막 베이스 백업은 새벽 2시에 완료된 상태다.

**Step 1: 백업 데이터 준비**

```bash
#!/bin/bash
# pitr_restore.sh

TARGET_TIME="2024-01-15 10:29:00"  # 장애 직전 시각
RESTORE_DIR="/restore/pitr_recovery"

# S3에서 가장 최근 베이스 백업 다운로드
LATEST_BASE=$(aws s3 ls s3://my-db-backup/base/ | sort | tail -1 | awk '{print $2}')
echo "복구에 사용할 베이스 백업: ${LATEST_BASE}"

mkdir -p "${RESTORE_DIR}"
aws s3 sync "s3://my-db-backup/base/${LATEST_BASE}" "${RESTORE_DIR}"

# tar 압축 해제
cd "${RESTORE_DIR}"
tar -xzf base.tar.gz
```

**Step 2: recovery.conf (PostgreSQL 12 이하) 또는 postgresql.conf 설정**

PostgreSQL 13 이상에서는 `postgresql.conf`와 `recovery.signal` 파일을 사용한다.

```bash
# recovery.signal 파일 생성 (PostgreSQL 13+)
touch "${RESTORE_DIR}/recovery.signal"

# postgresql.conf에 복구 설정 추가
cat >> "${RESTORE_DIR}/postgresql.conf" << EOF

# PITR 복구 설정
restore_command = 'aws s3 cp s3://my-db-backup/wal/%f %p'
recovery_target_time = '${TARGET_TIME}'
recovery_target_action = 'promote'   # 복구 완료 후 읽기-쓰기 모드로 전환
recovery_target_inclusive = false    # 목표 시각의 트랜잭션은 제외
EOF
```

**Step 3: 복구 실행 및 검증**

```bash
# PostgreSQL 시작 (복구 모드)
pg_ctl start -D "${RESTORE_DIR}" -l /var/log/postgresql/recovery.log

# 복구 진행 상황 모니터링
tail -f /var/log/postgresql/recovery.log

# 복구 완료 확인 후 데이터 검증
psql -h localhost -U postgres -c "
  SELECT 
    pg_is_in_recovery() AS is_recovering,
    now() AS current_time,
    (SELECT COUNT(*) FROM payments) AS payment_count;
"
```

### 3. Spring Boot 애플리케이션에서 백업 상태 모니터링

```java
@Component
@Slf4j
public class DatabaseBackupMonitor {

    private final JdbcTemplate jdbcTemplate;
    private final MeterRegistry meterRegistry;

    @Scheduled(fixedDelay = 60000) // 1분마다 실행
    public void checkBackupStatus() {
        try {
            // 마지막 WAL 위치 확인
            String walLsn = jdbcTemplate.queryForObject(
                "SELECT pg_current_wal_lsn()::text", String.class
            );
            
            // 아카이브 상태 확인
            Map<String, Object> archiveStatus = jdbcTemplate.queryForMap(
                "SELECT archived_count, failed_count, last_archived_wal, " +
                "last_archived_time, last_failed_wal, last_failed_time " +
                "FROM pg_stat_archiver"
            );

            long failedCount = (Long) archiveStatus.get("failed_count");
            if (failedCount > 0) {
                log.error("WAL 아카이빙 실패 감지! failed_count={}, last_failed_wal={}",
                    failedCount, archiveStatus.get("last_failed_wal"));
                // 알림 전송
                alertService.sendCriticalAlert("WAL 아카이빙 실패", archiveStatus.toString());
            }

            // 메트릭 기록
            meterRegistry.gauge("db.wal.archive.failed_count", failedCount);

            Timestamp lastArchivedTime = (Timestamp) archiveStatus.get("last_archived_time");
            if (lastArchivedTime != null) {
                long minutesSinceLastArchive = Duration.between(
                    lastArchivedTime.toInstant(), Instant.now()
                ).toMinutes();
                
                meterRegistry.gauge("db.wal.minutes_since_last_archive", minutesSinceLastArchive);
                
                // archive_timeout(300초)의 2배를 넘으면 경고
                if (minutesSinceLastArchive > 10) {
                    log.warn("마지막 WAL 아카이빙으로부터 {}분 경과. RPO 위험!", minutesSinceLastArchive);
                }
            }

        } catch (Exception e) {
            log.error("백업 상태 모니터링 중 오류 발생", e);
        }
    }
}
```

## 주의사항 및 트레이드오프

### ① WAL 아카이빙 지연과 RPO 괴리

`archive_command`가 실패하거나 지연될 경우, 실제 RPO는 설계값보다 훨씬 나빠질 수 있다. PostgreSQL은 아카이빙이 실패해도 서비스를 중단하지 않는다. 따라서 `pg_stat_archiver`의 `failed_count`를 **반드시** 모니터링해야 한다.

### ② 베이스 백업 시점과 복구 시간의 관계

베이스 백업이 오래될수록, 그 이후의 WAL을 모두 재적용해야 하므로 **복구 시간(RTO)이 늘어난다**. 일반적으로 다음 공식을 참고한다.

```
예상 복구 시간 ≈ (베이스 백업 복원 시간) + (WAL 재적용 시간)
WAL 재적용 속도 ≈ 프로덕션 처리량의 약 50~80% (I/O 특성에 따라 다름)
```

하루에 한 번 베이스 백업을 찍는다면, 최악의 경우 23시간치의 WAL을 재적용해야 한다. RTO 요구사항에 따라 베이스 백업 빈도를 조정하라.

### ③ 백업 복구 테스트를 정기적으로 수행하라

백업 파일이 존재한다고 해서 복구가 된다는 보장은 없다. WAL 파일이 중간에 누락되거나, 백업 파일이 손상되었을 수도 있다. **분기에 한 번 이상 실제 복구 드릴(Restore Drill)을 수행**해야 한다. 이를 자동화하면 더 좋다.

### ④ 클라우드 관리형 서비스의 PITR

AWS RDS, Google Cloud SQL, Azure Database 등 관리형 서비스는 PITR을 기본 제공한다. 직접 구축 대비 운영 부담이 크게 줄지만, 다음을 반드시 확인하라.

- **보관 기간 설정**: 기본값(7일)이 RPO 요구사항에 충분한지 검토
- **복구 목표 시각의 정밀도**: 초 단위까지 지정 가능한지
- **다른 리전/계정으로의 복구 지원 여부**: 재해 복구(DR) 시나리오 고려
- **복구 중 다운타임**: 관리형 서비스라도 복구 시간은 데이터 크기에 비례

### ⑤ 보안과 암호화

백업 파일에는 민감한 데이터가 그대로 담겨 있다. S3에 저장할 경우 **SSE-KMS(서버 사이드 암호화)** 를 활성화하고, 백업 버킷에 대한 접근 정책을 최소 권한으로 제한하라. 백업 데이터가 유출되면 프로덕션 DB 보안과 동일한 수준의 사고가 된다.

## 정리

효과적인 PITR 설계는 단순히 툴 설정을 넘어서, 비즈니스 요구사항(RPO/RTO)을 정확히 이해하고 그에 맞는 아키텍처를 구성하는 일이다.

| 체크리스트 | 확인 |
|-----------|------|
| RPO/RTO 목표값을 이해관계자와 합의했는가? | ✅ |
| WAL 아카이빙이 정상 동작하는지 모니터링하고 있는가? | ✅ |
| 베이스 백업 빈도가 RTO를 충족하는가? | ✅ |
| 백업 파일이 암호화되어 안전하게 저장되는가? | ✅ |
| 정기적으로 복구 테스트를 수행하고 있는가? | ✅ |
| 복구 절차가 문서화되어 팀 전체가 숙지하고 있는가? | ✅ |

백업은 찍는 순간이 아니라 **성공적으로 복구하는 순간** 비로소 가치를 갖는다. 아무도 주목하지 않을 때 조용히 백업을 설계하고 검증하는 것, 그것이 시니어 엔지니어의 역할이다.
