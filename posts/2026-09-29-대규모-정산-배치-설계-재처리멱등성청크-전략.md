# 대규모 정산 배치 설계: 재처리·멱등성·청크 전략

## 개요

정산 배치는 금융, 이커머스, 결제 도메인에서 가장 민감하고 중요한 작업 중 하나다. 수백만 건의 거래 데이터를 집계하고, 각 파트너사나 사용자에게 정확한 금액을 산출해야 한다. 그런데 실무에서 정산 배치를 처음 설계할 때 흔히 마주치는 문제들이 있다.

- 중간에 실패했을 때 **어디서부터 다시 실행해야 하는가?**
- 같은 배치를 두 번 실행했을 때 **데이터가 중복 집계되지 않는가?**
- 수백만 건을 한 번에 처리하면 **메모리가 터지지 않는가?**

이 세 가지 질문이 각각 **재처리(Retry/Restart)**, **멱등성(Idempotency)**, **청크 전략(Chunk Strategy)**의 핵심이다. 이 글에서는 Spring Batch를 기반으로 실전에서 바로 적용할 수 있는 설계 전략을 구체적인 코드와 함께 설명한다.

---

## 핵심 개념

### 1. 재처리 (Restart & Retry)

배치 작업은 언제든 실패할 수 있다. 네트워크 타임아웃, DB 커넥션 오류, 외부 API 장애 등 예측 불가능한 원인이 많다. 이때 전체 배치를 처음부터 다시 실행하면 시간과 비용이 낭비되고, 이미 처리된 데이터가 중복 처리될 위험이 있다.

Spring Batch는 `JobRepository`를 통해 실행 상태를 영속화한다. 이미 완료된 Step은 건너뛰고 실패한 지점부터 이어서 실행하는 **재시작(Restart)** 기능을 제공한다.

또한 일시적인 오류에 대해서는 **재시도(Retry)** 를 설정해 자동 복구가 가능하다.

### 2. 멱등성 (Idempotency)

멱등성이란 동일한 연산을 여러 번 실행해도 결과가 항상 같다는 성질이다. 정산 배치에서 멱등성이 깨지면 금액이 중복 집계되어 심각한 오류로 이어진다.

멱등성 보장의 핵심은 **"이 데이터를 이미 처리했는가?"를 판단하는 기준**을 명확히 하는 것이다. 일반적으로 배치 실행 단위(예: 날짜, 배치 ID)와 대상 데이터의 고유 키를 조합해 처리 여부를 추적한다.

### 3. 청크 전략 (Chunk Strategy)

수백만 건의 데이터를 한 번에 메모리에 올리면 OOM(Out of Memory)이 발생한다. 청크 단위로 데이터를 읽고(Read) → 처리하고(Process) → 쓰는(Write) 방식으로 분할하면 메모리 사용량을 제어할 수 있다.

청크 크기는 성능과 트랜잭션 안전성 사이의 트레이드오프다. 너무 작으면 트랜잭션 오버헤드가 커지고, 너무 크면 실패 시 롤백 범위가 커진다.

## 실전 예제

### 기본 Job 구성

```java
@Configuration
@RequiredArgsConstructor
public class SettlementJobConfig {

    private final JobRepository jobRepository;
    private final PlatformTransactionManager transactionManager;
    private final SettlementItemReader settlementItemReader;
    private final SettlementItemProcessor settlementItemProcessor;
    private final SettlementItemWriter settlementItemWriter;

    @Bean
    public Job settlementJob() {
        return new JobBuilder("settlementJob", jobRepository)
                .start(settlementStep())
                .build();
    }

    @Bean
    public Step settlementStep() {
        return new StepBuilder("settlementStep", jobRepository)
                .<RawTransaction, SettlementResult>chunk(500, transactionManager)
                .reader(settlementItemReader)
                .processor(settlementItemProcessor)
                .writer(settlementItemWriter)
                .faultTolerant()
                .retryLimit(3)
                .retry(TransientDataAccessException.class)
                .retry(SocketTimeoutException.class)
                .skipLimit(10)
                .skip(NonTransientDataAccessException.class)
                .build();
    }
}
```

청크 크기를 500으로 설정하고, 일시적 오류(`TransientDataAccessException`)는 최대 3회 재시도, 복구 불가 오류는 최대 10건까지 스킵하도록 구성했다.

### 멱등성 보장: 처리 이력 테이블 활용

```sql
CREATE TABLE settlement_execution_log (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    batch_date      DATE NOT NULL,
    partner_id      BIGINT NOT NULL,
    status          VARCHAR(20) NOT NULL,  -- PROCESSING, COMPLETED, FAILED
    created_at      DATETIME NOT NULL,
    updated_at      DATETIME NOT NULL,
    UNIQUE KEY uk_batch_date_partner (batch_date, partner_id)
);
```

```java
@Service
@RequiredArgsConstructor
public class IdempotentSettlementService {

    private final SettlementExecutionLogRepository logRepository;
    private final SettlementRepository settlementRepository;

    @Transactional
    public void processSettlement(LocalDate batchDate, Long partnerId,
                                   List<RawTransaction> transactions) {
        // 이미 처리된 경우 스킵
        logRepository.findByBatchDateAndPartnerId(batchDate, partnerId)
                .filter(log -> "COMPLETED".equals(log.getStatus()))
                .ifPresent(log -> {
                    throw new AlreadyProcessedException(
                        "Already completed: " + batchDate + "/" + partnerId);
                });

        // PROCESSING 상태로 마킹 (중복 실행 방지)
        SettlementExecutionLog log = logRepository.save(
            SettlementExecutionLog.builder()
                .batchDate(batchDate)
                .partnerId(partnerId)
                .status("PROCESSING")
                .build()
        );

        try {
            BigDecimal totalAmount = transactions.stream()
                    .map(RawTransaction::getAmount)
                    .reduce(BigDecimal.ZERO, BigDecimal::add);

            settlementRepository.upsert(batchDate, partnerId, totalAmount);

            log.complete();
            logRepository.save(log);

        } catch (Exception e) {
            log.fail();
            logRepository.save(log);
            throw e;
        }
    }
}
```

`UNIQUE KEY`를 통해 동일한 `(batch_date, partner_id)` 조합의 레코드가 두 번 삽입되지 않도록 막고, 상태(Status)를 통해 처리 진행 중인 작업과 완료된 작업을 구분한다.

### 재시작 가능한 ItemReader 구성

```java
@Component
@StepScope
public class SettlementItemReader implements ItemReader<RawTransaction> {

    private final RawTransactionRepository repository;
    private final LocalDate batchDate;
    private int offset = 0;
    private static final int PAGE_SIZE = 500;
    private List<RawTransaction> buffer = new ArrayList<>();

    public SettlementItemReader(RawTransactionRepository repository,
            @Value("#{jobParameters['batchDate']}") String batchDateStr) {
        this.repository = repository;
        this.batchDate = LocalDate.parse(batchDateStr);
    }

    @Override
    public RawTransaction read() {
        if (buffer.isEmpty()) {
            List<RawTransaction> page = repository
                    .findUnprocessedByDate(batchDate, offset, PAGE_SIZE);
            if (page.isEmpty()) return null;
            buffer.addAll(page);
            offset += page.size();
        }
        return buffer.isEmpty() ? null : buffer.remove(0);
    }
}
```

`Pageable` 기반으로 데이터를 청크 단위로 읽어오며, `offset`을 추적해 이미 읽은 데이터를 다시 읽지 않는다. `@StepScope`를 사용해 Step 실행 시 새로 생성되도록 한다.

### Job Parameter를 활용한 실행 단위 격리

```java
@Component
@RequiredArgsConstructor
public class SettlementJobLauncher {

    private final JobLauncher jobLauncher;
    private final Job settlementJob;

    public void launch(LocalDate targetDate) throws Exception {
        JobParameters params = new JobParametersBuilder()
                .addString("batchDate", targetDate.toString())
                .addLong("timestamp", System.currentTimeMillis()) // 강제 재실행 시 사용
                .toJobParameters();

        jobLauncher.run(settlementJob, params);
    }

    public void forceRerun(LocalDate targetDate) throws Exception {
        // timestamp를 현재 시각으로 새로 설정하면 새 JobInstance로 실행됨
        // 단, 멱등성 처리는 애플리케이션 레벨에서 별도 보장해야 함
        JobParameters params = new JobParametersBuilder()
                .addString("batchDate", targetDate.toString())
                .addLong("timestamp", System.currentTimeMillis())
                .toJobParameters();

        jobLauncher.run(settlementJob, params);
    }
}
```

## 주의사항 및 트레이드오프

### 청크 크기 결정 기준

청크 크기는 단순히 크면 좋은 것이 아니다. 다음 요소를 고려해야 한다.

| 고려 요소 | 청크가 작을 때 | 청크가 클 때 |
|---|---|---|
| 메모리 사용 | 낮음 | 높음 |
| 트랜잭션 오버헤드 | 높음 | 낮음 |
| 실패 시 롤백 범위 | 좁음 | 넓음 |
| 처리 속도 | 느림 | 빠름 |

**실무 권장사항**: 일반적으로 100~1000 사이에서 시작해, 부하 테스트를 통해 최적값을 찾는다. 처리 로직이 복잡하거나 외부 API 호출이 포함된 경우 100 이하로 낮추는 것이 안전하다.

### Skip vs Retry 선택 기준

- **Retry**: 일시적인 오류(네트워크 장애, DB 락 경합)에 적합. 동일 조건에서 재시도하면 성공할 가능성이 있을 때 사용한다.
- **Skip**: 데이터 자체의 문제(잘못된 포맷, 유효성 실패)에 적합. 단, 정산 배치에서 Skip은 매우 신중하게 사용해야 한다. **한 건이라도 빠지면 정산 금액이 틀어지기 때문**이다.

Skip을 사용한다면 반드시 별도 알림(Slack, 이메일)과 함께 수동 검토 프로세스를 갖춰야 한다.

### 멱등성의 함정: 부분 실패

청크 단위로 처리하다가 중간에 실패하면 일부 청크만 커밋된 상태가 된다. 이 경우 재실행 시 이미 처리된 청크를 어떻게 판별할 것인가?

해결책은 두 가지다.

1. **처리된 레코드에 플래그 설정**: 각 트랜잭션에 `processed_at` 컬럼을 두고, Reader에서 미처리 데이터만 조회한다.
2. **Upsert 방식**: Writer에서 INSERT 대신 `INSERT ... ON DUPLICATE KEY UPDATE`를 사용해 동일 키 재처리 시 덮어쓰도록 한다.

```sql
-- Upsert 예시 (MySQL)
INSERT INTO settlement_result (batch_date, partner_id, total_amount, updated_at)
VALUES (?, ?, ?, NOW())
ON DUPLICATE KEY UPDATE
    total_amount = VALUES(total_amount),
    updated_at   = NOW();
```

### 분산 환경에서의 중복 실행 방지

여러 인스턴스가 동시에 배치를 실행할 경우 중복 처리가 발생할 수 있다. 이때는 분산 락(ShedLock, Redis Lock)을 적용한다.

```java
@Scheduled(cron = "0 0 2 * * *")
@SchedulerLock(name = "settlementJob", lockAtMostFor = "PT2H")
public void runSettlement() throws Exception {
    settlementJobLauncher.launch(LocalDate.now().minusDays(1));
}
```

ShedLock은 DB나 Redis를 통해 락을 관리하므로, 다중 인스턴스 환경에서도 하나의 인스턴스만 배치를 실행하도록 보장한다.

## 정리

대규모 정산 배치를 안정적으로 운영하려면 세 가지 축이 잘 맞물려야 한다.

| 전략 | 목적 | 핵심 구현 포인트 |
|---|---|---|
| **재처리** | 실패 지점에서 안전하게 재시작 | JobRepository 활용, Retry/Skip 정책 |
| **멱등성** | 중복 실행 시 결과 동일 보장 | 처리 이력 추적, Upsert 패턴 |
| **청크 전략** | 메모리 효율 + 트랜잭션 안전성 | 적절한 청크 크기, 페이지 기반 Reader |

정산 배치에서 가장 위험한 것은 "잘 되겠지"라는 낙관적 가정이다. 실패 시나리오를 미리 정의하고, 각 시나리오에서 데이터 정합성이 유지되는지를 설계 단계에서부터 검증해야 한다.

특히 **멱등성은 테스트 코드로 반드시 검증**해야 한다. 동일 파라미터로 두 번 실행했을 때 결과가 동일한지 확인하는 통합 테스트를 CI 파이프라인에 포함시키는 것을 강력히 권장한다. 배치는 한 번 잘못 돌면 복구 비용이 크다. 설계에 투자한 시간은 반드시 운영 안정성으로 돌아온다.
