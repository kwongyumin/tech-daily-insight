# MSA에서 Enum·공통 코드 계약을 안전하게 관리하기

## 개요

모놀리식 아키텍처에서는 `OrderStatus.PENDING` 같은 Enum 값을 하나의 코드베이스에서 공유하기 때문에 컴파일 타임에 불일치를 즉시 감지할 수 있다. 하지만 MSA로 전환하는 순간, 이 당연했던 안전망이 사라진다.

주문 서비스가 `"WAIT"`을 보내고, 배송 서비스가 `"WAITING"`을 기대한다면? 결제 서비스가 신규 상태값 `"PARTIAL_REFUND"`를 추가했는데 정산 서비스가 이를 모른다면? 이런 **공통 코드 계약의 불일치**는 런타임에야 드러나고, 종종 장애로 이어진다.

이 글에서는 MSA 환경에서 Enum과 공통 코드를 어떻게 설계하고, 서비스 간 계약을 안전하게 유지할 수 있는지 실무적인 관점에서 다룬다.

---

## 핵심 개념

### 왜 Enum 계약이 어려운가?

MSA에서 Enum 불일치 문제는 크게 세 가지 레이어에서 발생한다.

1. **직렬화/역직렬화 불일치**: 서비스 A가 `CANCELED`를 보냈는데 서비스 B의 역직렬화 로직이 해당 값을 모르면 예외가 발생한다.
2. **버전 드리프트**: 서비스들이 독립적으로 배포되다 보면 같은 개념을 다른 이름으로 표현하게 된다.
3. **공유 라이브러리 의존성 지옥**: 공통 Enum을 별도 라이브러리로 추출하면 한 서비스의 변경이 모든 서비스에 영향을 준다.

### 두 가지 상반된 접근법

| 전략 | 설명 | 장점 | 단점 |
|------|------|------|------|
| **공유 라이브러리** | Enum을 공통 모듈에 정의하고 각 서비스가 의존 | 타입 안전성, 일관성 | 배포 결합도 증가 |
| **로컬 정의 + 계약 검증** | 각 서비스가 자신의 Enum을 로컬에 정의하되 계약 테스트로 보장 | 서비스 독립성 유지 | 계약 관리 비용 증가 |

어느 쪽이 정답이라기보다, **팀 규모·배포 주기·조직 구조**에 따라 선택이 달라진다. 중요한 것은 선택한 전략을 일관되게 강제하는 메커니즘을 갖추는 것이다.

## 실전 예제

### 1. 방어적 역직렬화 전략

가장 먼저 적용할 수 있는 실용적인 패턴이다. 외부 메시지에서 들어오는 Enum 값은 **절대 직접 매핑하지 않는다.**

```java
// Bad: 외부 값을 그대로 Enum으로 역직렬화
public enum OrderStatus {
    PENDING, CONFIRMED, CANCELED
}

// 외부 메시지에서 "CANCELLATION_REQUESTED" 값이 오면 예외 발생!
```

```java
// Good: 알 수 없는 값을 안전하게 처리하는 방어적 Enum
public enum OrderStatus {
    PENDING,
    CONFIRMED,
    CANCELED,
    UNKNOWN; // 알 수 없는 값의 폴백

    @JsonCreator
    public static OrderStatus fromValue(String value) {
        if (value == null) return UNKNOWN;
        try {
            return OrderStatus.valueOf(value.toUpperCase());
        } catch (IllegalArgumentException e) {
            log.warn("Unknown OrderStatus value received: {}", value);
            return UNKNOWN;
        }
    }
}
```

이 패턴은 외부 서비스가 새로운 상태값을 추가해도 기존 서비스가 즉시 죽지 않도록 해준다. `UNKNOWN`으로 처리하면서 알람을 발생시키면 **무중단 + 조기 감지**가 가능하다.

### 2. 공유 라이브러리 전략: 엄격한 버전 관리

공유 모듈을 선택했다면, **Semantic Versioning**과 하위 호환성 원칙을 반드시 강제해야 한다.

```
// 공유 모듈 구조 예시
common-contracts/
├── src/main/java/com/example/contracts/
│   ├── order/
│   │   └── OrderStatus.java
│   ├── payment/
│   │   └── PaymentStatus.java
│   └── delivery/
│       └── DeliveryStatus.java
└── CHANGELOG.md
```

```java
// common-contracts 모듈의 OrderStatus
// @since 어노테이션으로 추가 시점을 명시
public enum OrderStatus {
    PENDING,           // @since 1.0.0
    CONFIRMED,         // @since 1.0.0
    CANCELED,          // @since 1.0.0
    PARTIAL_REFUNDED;  // @since 1.3.0 - 부분 환불 상태 추가
}
```

```groovy
// 각 서비스의 build.gradle - 버전을 명시적으로 고정
dependencies {
    implementation 'com.example:common-contracts:1.2.0'
    // 버전 범위(+)나 latest는 절대 사용하지 않는다
}
```

**핵심 규칙**: 공유 Enum에 값을 **추가**하는 것은 하위 호환이지만, 값을 **삭제하거나 이름을 변경**하는 것은 Breaking Change다. 이를 SemVer와 연동하여 Major 버전을 올려야 한다.

### 3. 로컬 정의 + Pact 계약 테스트

서비스 독립성을 최우선으로 한다면, 각 서비스가 Enum을 로컬에 정의하고 **Consumer-Driven Contract Testing**으로 호환성을 검증한다.

```java
// 주문 서비스 (Consumer) - 자신의 로컬 Enum 정의
public enum LocalOrderStatus {
    PENDING, CONFIRMED, CANCELED
}

// 배송 서비스 (Provider) - 자신의 로컬 Enum 정의
// 이름이 달라도 괜찮다. 계약 테스트가 검증한다.
public enum DeliveryOrderStatus {
    WAITING, IN_PROGRESS, DELIVERED, CANCELED
}
```

```java
// Pact Consumer 테스트 - 주문 서비스에서 작성
@ExtendWith(PactConsumerTestExt.class)
@PactTestFor(providerName = "delivery-service")
class OrderToDeliveryContractTest {

    @Pact(consumer = "order-service")
    public RequestResponsePact createPact(PactDslWithProvider builder) {
        return builder
            .given("delivery exists for order")
            .uponReceiving("get delivery status")
            .path("/deliveries/ORDER-001/status")
            .method("GET")
            .willRespondWith()
            .status(200)
            .body(new PactDslJsonBody()
                // 계약: 이 필드는 반드시 존재해야 하고,
                // 값은 이 목록 중 하나여야 한다
                .stringMatcher("status",
                    "WAITING|IN_PROGRESS|DELIVERED|CANCELED",
                    "IN_PROGRESS")
            )
            .toPact();
    }

    @Test
    @PactTestFor(pactMethod = "createPact")
    void shouldHandleDeliveryStatus(MockServer mockServer) {
        // Consumer 측에서 실제 HTTP 호출 검증
        DeliveryStatusResponse response = deliveryClient
            .getStatus("ORDER-001");
        assertThat(response.getStatus()).isNotNull();
    }
}
```

Pact 계약 파일은 **Pact Broker**에 게시되고, Provider 서비스의 CI 파이프라인에서 이 계약을 검증한다. 계약을 깨는 배포는 자동으로 차단된다.

### 4. 이벤트 기반 메시징에서의 Enum 관리

Kafka 같은 이벤트 스트리밍 환경에서는 **Schema Registry + Avro/Protobuf**를 사용하는 것이 가장 안전하다.

```protobuf
// order_events.proto
syntax = "proto3";

enum OrderStatus {
  ORDER_STATUS_UNSPECIFIED = 0;  // Protobuf 기본값 (알 수 없는 값의 폴백)
  ORDER_STATUS_PENDING = 1;
  ORDER_STATUS_CONFIRMED = 2;
  ORDER_STATUS_CANCELED = 3;
  // 새 값 추가는 항상 새로운 번호를 부여한다
  // 기존 번호는 절대 재사용하지 않는다
}

message OrderEvent {
  string order_id = 1;
  OrderStatus status = 2;
  int64 event_time = 3;
}
```

Protobuf는 정의되지 않은 enum 값을 `UNSPECIFIED(0)`으로 역직렬화하므로, 구버전 Consumer가 신규 상태값을 받아도 안전하게 처리된다.

## 주의사항 및 트레이드오프

### 공유 라이브러리의 함정

공유 라이브러리 전략의 가장 큰 위험은 **암묵적 결합**이다. 표면적으로는 독립적인 서비스처럼 보이지만, 실제로는 공통 모듈 릴리즈 주기에 묶여버린다.

- 공통 모듈 변경 시 **모든 소비 서비스를 동시에 업데이트**해야 하는 압박이 생긴다.
- 팀이 많아질수록 공통 모듈의 **소유권 모호성** 문제가 발생한다.
- 공통 모듈에 비즈니스 로직이 슬금슬금 들어오면 **분산 모놀리식**이 된다.

**권장**: 공유 모듈은 순수한 데이터 계약(Enum, DTO)만 포함하고, 어떤 비즈니스 로직도 넣지 않는다.

### 방어적 역직렬화의 함정

`UNKNOWN` 폴백이 남용되면 오히려 문제를 숨기는 도구가 된다.

```java
// 위험: UNKNOWN을 그냥 무시하면 데이터 유실
if (status == OrderStatus.UNKNOWN) {
    return; // 조용히 무시 - 절대 하면 안 됨!
}

// 올바른 처리: 알람 + 별도 처리 큐
if (status == OrderStatus.UNKNOWN) {
    alertService.sendSlackAlert("Unknown status: " + rawValue);
    deadLetterQueueService.send(message);
    return;
}
```

### 데이터베이스에서의 Enum 저장

DB에 Enum을 저장할 때는 **숫자 대신 문자열**을 강력히 권장한다.

```java
@Entity
public class Order {
    // Bad: 숫자 ordinal 저장 - Enum 순서 변경 시 데이터 깨짐
    @Enumerated(EnumType.ORDINAL)
    private OrderStatus status;

    // Good: 문자열 저장 - 명시적이고 안전
    @Enumerated(EnumType.STRING)
    private OrderStatus status;
}
```

DB에 `"PARTIAL_REFUNDED"`라는 문자열이 있으면, 나중에 코드를 보지 않아도 의미를 파악할 수 있다. `3`이라는 숫자는 Enum 순서가 바뀌는 순간 전혀 다른 의미가 된다.

### 배포 순서와 Enum 추가

신규 Enum 값 추가 시에는 반드시 **Consumer 업데이트 → Provider 배포** 순서를 따른다.

```
# 안전한 배포 순서
1. Consumer 서비스에 방어적 역직렬화 코드 배포 (UNKNOWN 처리 포함)
2. Provider 서비스에 신규 Enum 값 추가 배포
3. 로그/모니터링으로 UNKNOWN 발생 여부 확인
4. Consumer 서비스 업데이트하여 신규 값 명시적 처리
```

반대로 배포하면, Provider가 `NEW_STATUS`를 보내는 시점에 Consumer가 이를 처리하지 못해 장애가 발생한다.

## 정리

MSA에서 Enum·공통 코드 계약 관리는 단순한 코드 공유 문제가 아니라 **서비스 경계와 팀 자율성, 배포 독립성**이 얽힌 아키텍처 결정이다.

핵심 원칙을 정리하면 다음과 같다.

| 원칙 | 설명 |
|------|------|
| **방어적 역직렬화** | 외부 Enum은 항상 UNKNOWN 폴백으로 처리하고 알람 연동 |
| **추가는 허용, 삭제/변경은 금지** | Enum 값 추가는 하위 호환, 변경/삭제는 Breaking Change |
| **String 저장** | DB에 Enum은 항상 EnumType.STRING으로 저장 |
| **계약 가시화** | Pact, Protobuf Schema Registry 등으로 계약을 코드로 명시 |
| **배포 순서 준수** | Consumer 먼저 준비 → Provider 배포 |
| **비즈니스 로직 배제** | 공유 모듈은 데이터 계약만 포함 |

모든 팀이 같은 규칙을 인지하고, CI 파이프라인이 이를 강제하는 구조를 갖추는 것이 핵심이다. 계약은 문서가 아니라 **실행 가능한 테스트**로 존재해야 한다.
