# IPFS 분산 파일 시스템과 블록체인 연동

## 개요

NFT 붐이 절정에 달했던 2021~2022년, 많은 개발자들이 공통적인 문제에 직면했다. "토큰은 온체인에 있는데, 실제 이미지와 메타데이터는 어디에 저장해야 하나?" 단순히 중앙화된 서버 URL을 스마트 컨트랙트에 박아넣는 방식은 **단일 실패 지점(Single Point of Failure)** 문제를 피할 수 없다. 서버가 다운되거나 도메인이 만료되면, 블록체인에 영원히 기록된 토큰은 존재하지 않는 자원을 가리키게 된다.

IPFS(InterPlanetary File System)는 이 문제를 해결하기 위한 핵심 인프라로 자리 잡았다. 중앙화된 URL 대신 **콘텐츠 주소 지정 방식(Content Addressing)** 을 사용해, 파일 자체의 해시를 식별자로 삼는다. 블록체인의 불변성(Immutability)과 IPFS의 탈중앙화 스토리지를 결합하면, 데이터의 무결성과 가용성을 동시에 확보할 수 있다.

이 글에서는 IPFS의 핵심 개념을 정리하고, Solidity 스마트 컨트랙트와 연동하는 실전 예제를 통해 실무에서 바로 적용할 수 있는 패턴을 다룬다.

## 핵심 개념

### 콘텐츠 주소 지정 (Content Addressing)

전통적인 웹은 **위치 기반 주소 지정(Location Addressing)** 을 사용한다. `https://example.com/image.jpg`는 특정 서버의 특정 경로를 가리킨다. 파일 내용이 바뀌어도 URL은 동일하다.

IPFS는 다르다. 파일을 업로드하면 그 내용을 SHA-256 기반의 알고리즘으로 해싱하여 **CID(Content Identifier)** 를 생성한다.

```
QmZ4tDuvesekSs4qM5ZBKpXiZGun7S2CYtEZRB3DYXkjGx
```

같은 파일을 업로드하면 항상 같은 CID가 나온다. 파일이 조금이라도 달라지면 완전히 다른 CID가 생성된다. 이 특성이 블록체인과의 연동에서 핵심 가치를 발휘한다.

### DAG 구조와 Merkle Tree

IPFS는 파일을 저장할 때 **Merkle DAG(Directed Acyclic Graph)** 구조를 사용한다. 큰 파일은 여러 블록(청크)으로 나뉘고, 각 블록의 해시가 상위 노드의 해시 계산에 포함된다. 이는 Git의 오브젝트 스토어나 블록체인의 머클 트리와 유사한 개념이다. 덕분에 대용량 파일도 부분 검증이 가능하고, 중복 청크는 자동으로 중복 제거된다.

### IPFS vs Filecoin vs Pinning 서비스

| 구분 | 역할 | 영속성 보장 |
|------|------|-----------|
| IPFS 노드 | 파일 배포 및 라우팅 | X (캐시 기반) |
| Filecoin | 탈중앙화 스토리지 마켓 | O (경제적 인센티브) |
| Pinata/nft.storage | 중앙화 Pinning 서비스 | O (SLA 기반) |

IPFS 자체는 파일의 영속성을 보장하지 않는다. 아무도 해당 CID를 "핀(Pin)" 하지 않으면 가비지 컬렉션으로 사라질 수 있다. 프로덕션 환경에서는 반드시 Filecoin, Pinata, nft.storage 등의 Pinning 솔루션을 함께 사용해야 한다.

## 실전 예제

### 1. IPFS에 파일 업로드 (Node.js + Helia)

기존의 `js-ipfs`는 deprecated 되었고, 현재는 **Helia**가 공식 후속 라이브러리다.

```javascript
import { createHelia } from 'helia'
import { unixfs } from '@helia/unixfs'
import { FsBlockstore } from 'blockstore-fs'
import { FsDatastore } from 'datastore-fs'
import { readFileSync } from 'fs'

async function uploadToIPFS(filePath) {
  const blockstore = new FsBlockstore('./ipfs-blocks')
  const datastore = new FsDatastore('./ipfs-data')

  const helia = await createHelia({ blockstore, datastore })
  const fs = unixfs(helia)

  const fileContent = readFileSync(filePath)
  const cid = await fs.addBytes(fileContent)

  console.log(`CID: ${cid.toString()}`)

  // 메타데이터 JSON 업로드
  const metadata = {
    name: 'My NFT',
    description: 'A unique digital asset',
    image: `ipfs://${cid.toString()}`,
    attributes: [
      { trait_type: 'Rarity', value: 'Legendary' }
    ]
  }

  const metadataBytes = new TextEncoder().encode(JSON.stringify(metadata))
  const metadataCid = await fs.addBytes(metadataBytes)

  console.log(`Metadata CID: ${metadataCid.toString()}`)

  await helia.stop()
  return { imageCid: cid.toString(), metadataCid: metadataCid.toString() }
}
```

### 2. Pinata API를 통한 안정적인 Pinning

프로덕션에서는 Pinata REST API를 활용하는 것이 현실적이다.

```javascript
import FormData from 'form-data'
import axios from 'axios'
import { createReadStream } from 'fs'

const PINATA_API_KEY = process.env.PINATA_API_KEY
const PINATA_SECRET_KEY = process.env.PINATA_SECRET_KEY

async function pinFileToPinata(filePath, fileName) {
  const formData = new FormData()
  formData.append('file', createReadStream(filePath), { filename: fileName })

  const pinataMetadata = JSON.stringify({ name: fileName })
  formData.append('pinataMetadata', pinataMetadata)

  const pinataOptions = JSON.stringify({ cidVersion: 1 })
  formData.append('pinataOptions', pinataOptions)

  const response = await axios.post(
    'https://api.pinata.cloud/pinning/pinFileToIPFS',
    formData,
    {
      maxBodyLength: Infinity,
      headers: {
        ...formData.getHeaders(),
        pinata_api_key: PINATA_API_KEY,
        pinata_secret_api_key: PINATA_SECRET_KEY,
      },
    }
  )

  return response.data.IpfsHash // CID 반환
}

async function pinJSONToPinata(metadata) {
  const response = await axios.post(
    'https://api.pinata.cloud/pinning/pinJSONToIPFS',
    {
      pinataContent: metadata,
      pinataOptions: { cidVersion: 1 },
    },
    {
      headers: {
        pinata_api_key: PINATA_API_KEY,
        pinata_secret_api_key: PINATA_SECRET_KEY,
        'Content-Type': 'application/json',
      },
    }
  )

  return response.data.IpfsHash
}
```

### 3. Solidity 스마트 컨트랙트 연동

IPFS CID를 온체인에 기록하는 ERC-721 기반 NFT 컨트랙트다.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@openzeppelin/contracts/token/ERC721/ERC721.sol";
import "@openzeppelin/contracts/access/Ownable.sol";
import "@openzeppelin/contracts/utils/Counters.sol";

contract IPFSBackedNFT is ERC721, Ownable {
    using Counters for Counters.Counter;
    Counters.Counter private _tokenIdCounter;

    // tokenId => IPFS CID (메타데이터)
    mapping(uint256 => string) private _tokenCIDs;

    event NFTMinted(
        address indexed to,
        uint256 indexed tokenId,
        string ipfsCID
    );

    constructor() ERC721("IPFSBackedNFT", "IBNFT") Ownable(msg.sender) {}

    /**
     * @dev IPFS CID를 검증하고 NFT를 민팅
     * CIDv0는 'Qm'으로 시작, CIDv1은 'b'로 시작
     */
    function mintWithIPFS(address to, string calldata ipfsCID)
        external
        onlyOwner
        returns (uint256)
    {
        require(bytes(ipfsCID).length > 0, "CID cannot be empty");
        require(_isValidCIDPrefix(ipfsCID), "Invalid CID format");

        uint256 tokenId = _tokenIdCounter.current();
        _tokenIdCounter.increment();

        _safeMint(to, tokenId);
        _tokenCIDs[tokenId] = ipfsCID;

        emit NFTMinted(to, tokenId, ipfsCID);
        return tokenId;
    }

    function tokenURI(uint256 tokenId)
        public
        view
        override
        returns (string memory)
    {
        _requireOwned(tokenId);
        return string(abi.encodePacked("ipfs://", _tokenCIDs[tokenId]));
    }

    function getTokenCID(uint256 tokenId)
        external
        view
        returns (string memory)
    {
        _requireOwned(tokenId);
        return _tokenCIDs[tokenId];
    }

    function _isValidCIDPrefix(string calldata cid)
        private
        pure
        returns (bool)
    {
        bytes memory cidBytes = bytes(cid);
        if (cidBytes.length < 2) return false;
        // CIDv0: 'Qm' 시작
        if (cidBytes[0] == 0x51 && cidBytes[1] == 0x6D) return true;
        // CIDv1: 'b' 시작 (base32)
        if (cidBytes[0] == 0x62) return true;
        return false;
    }
}
```

### 4. 이벤트 리스닝 및 CID 검증 (ethers.js)

```javascript
import { ethers } from 'ethers'
import axios from 'axios'

const IPFS_GATEWAY = 'https://gateway.pinata.cloud/ipfs/'

async function verifyNFTMetadata(contractAddress, tokenId, provider) {
  const abi = [
    'function getTokenCID(uint256 tokenId) view returns (string)',
    'event NFTMinted(address indexed to, uint256 indexed tokenId, string ipfsCID)'
  ]

  const contract = new ethers.Contract(contractAddress, abi, provider)

  // 온체인에서 CID 조회
  const cid = await contract.getTokenCID(tokenId)
  console.log(`On-chain CID: ${cid}`)

  // IPFS 게이트웨이를 통해 메타데이터 가져오기
  const response = await axios.get(`${IPFS_GATEWAY}${cid}`)
  const metadata = response.data

  // 이미지 CID 추출 후 재검증
  const imageCid = metadata.image.replace('ipfs://', '')
  const imageResponse = await axios.get(`${IPFS_GATEWAY}${imageCid}`, {
    responseType: 'arraybuffer'
  })

  // 로컬에서 해시 재계산 후 CID와 비교 (무결성 검증)
  const { CID } = await import('multiformats/cid')
  const { sha256 } = await import('multiformats/hashes/sha2')

  const hash = await sha256.digest(new Uint8Array(imageResponse.data))
  const computedCid = CID.createV1(0x55, hash) // raw codec

  console.log(`Computed CID: ${computedCid.toString()}`)
  console.log(`Metadata image CID: ${imageCid}`)
  console.log(`Integrity check: ${computedCid.toString() === imageCid ? 'PASS' : 'FAIL'}`)

  return metadata
}
```

## 주의사항 및 트레이드오프

### 게이트웨이 의존성 문제

`ipfs://` 프로토콜을 일반 브라우저가 직접 해석하지 못한다. 실제 서비스에서는 `https://ipfs.io/ipfs/{CID}` 같은 HTTP 게이트웨이를 거쳐야 한다. 이는 다시 중앙화 문제를 야기한다. **Brave 브라우저**처럼 IPFS를 네이티브 지원하는 환경이 아니라면, 여러 게이트웨이를 폴백으로 구성하거나 전용 게이트웨이를 운영하는 것이 좋다.

```javascript
const GATEWAYS = [
  'https://ipfs.io/ipfs/',
  'https://cloudflare-ipfs.com/ipfs/',
  'https://gateway.pinata.cloud/ipfs/',
  'https://dweb.link/ipfs/'
]

async function fetchFromIPFS(cid) {
  for (const gateway of GATEWAYS) {
    try {
      const response = await axios.get(`${gateway}${cid}`, { timeout: 5000 })
      return response.data
    } catch {
      continue
    }
  }
  throw new Error('All IPFS gateways failed')
}
```

### 온체인 저장 비용 vs 오프체인 CID 참조

CID 문자열(46~59바이트)을 `string` 타입으로 저장하는 것은 가스 비용이 높다. CIDv0는 bytes32로 변환하여 저장하면 가스를 절약할 수 있다.

### 데이터 가용성과 핀닝 관리

Pinata나 nft.storage 같은 서비스가 폐업하면 데이터가 소실될 수 있다. 중요한 데이터는 **복수의 Pinning 서비스에 동시 등록**하고, 가능하면 자체 IPFS 노드도 운영하는 것이 좋다. Filecoin을 통한 탈중앙화 스토리지 계약 체결도 장기 보존 전략으로 고려할 만하다.

### 변경 불가능성의 양날

CID는 콘텐츠 해시이므로, 파일을 수정하면 CID가 바뀐다. 이미 민팅된 NFT의 tokenURI를 업데이트하려면 컨트랙트 설계 시 업데이트 가능성을 미리 고려해야 한다. 단순히 `Ownable` 패턴으로 CID를 갱신할 수 있게 열어두면 탈중앙화 원칙에 위배될 수 있어, 커뮤니티와의 합의 메커니즘(거버넌스)을 함께 설계해야 한다.

## 정리

IPFS와 블록체인의 결합은 단순히 "비싼 온체인 스토리지 대신 싼 오프체인을 쓰자"는 이야기가 아니다. 콘텐츠 주소 지정을 통한 **검증 가능한 불변성**이 핵심이다.

| 구성 요소 | 역할 |
|----------|------|
| 블록체인 | CID 소유권 기록, 변경 이력 추적 |
| IPFS | 콘텐츠 주소 지정 및 P2P 배포 |
| Pinning 서비스 | 데이터 영속성 보장 |
| HTTP 게이트웨이 | 일반 클라이언트 접근성 확보 |

실무에서 이 스택을 도입할 때는 다음 체크리스트를 확인하자.

- [ ] CIDv1(base32) 사용으로 대소문자 구분 문제 방지
- [ ] 복수 Pinning 서비스 등록으로 가용성 확보
- [ ] 게이트웨이 폴백 로직 구현
- [ ] 온체인 CID와 실제 콘텐츠 무결성 검증 로직 포함
- [ ] 장기 보존이 필요한 데이터는 Filecoin 계약 검토

탈중앙화 애플리케이션의 진정한 탈중앙화는 스마트 컨트랙트만으로 달성되지 않는다. 데이터 레이어까지 탈중앙화 철학을 일관되게 적용할 때, 블록체인의 불변성이 온전히 빛을 발한다.
