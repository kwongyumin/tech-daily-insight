# 데이터베이스 커넥션 풀 HikariCP 최적화 가이드

## 개요

Spring Boot 2.x 이후 기본 커넥션 풀로 채택된 HikariCP는 "The fastest connection pool"이라는 별명답게 경쟁 제품 대비 압도적인 성능을 자랑한다. 그러나 단순히 기본 설정만으로 사용한다면 프로덕션 환경에서 Connection timeout, Pool exhaustion, 혹은 과도한 커넥션 낭비 같은 문제에 직면하게 된다.

이 글에서는 HikariCP의 핵심 동작 원리를 짚어보고, 실제 운영 환경에서 발생하는 병목을 진단하며 최적의 설정값을 도출하는 방법을 다룬다. 단순한 파라미터 나열이 아니라, 각 설정이 **왜** 그 값이어야 하는지 근거와 함께 설명한다.

## 핵심 개념

### HikariCP가 빠른 이유

HikariCP의 성능 우위는 몇 가지 설계 철학에서 비롯된다.

- **Bytecode-level optimization**: 불필요한 추상화 레이어 제거
- **ConcurrentBag**: `LinkedBlockingQueue` 대신 커스텀 자료구조로 락 경합 최소화
- **Connection 재사용 우선**: 이미 사용 중이던 스레드가 커넥션을 먼저 반환받아 CPU 캐시 효율 극대화
- **최소한의 JDBC 프록시 계층**: 프록시 객체를 최대한 줄여 오버헤드 감소

이 구조 덕분에 HikariCP는 동일 부하 조건에서 c3p0, DBCP2 대비 수십 배의 throughput을 보여준다.

### 커넥션 풀의 생명주기

```
애플리케이션 요청
      │
      ▼
[ConcurrentBag에서 유휴 커넥션 검색]
      │
  있음 ──────────────────────────────► 커넥션 반환
      │
  없음
      │
      ▼
[minimumIdle < maximumPoolSize ?]
      │
  YES ─► 새 커넥션 생성 (connectionTimeout 이내)
      │
  NO  ─► connectionTimeout 동안 대기 → 초과 시 SQLException
```

이 흐름을 이해해야 각 파라미터의 역할이 명확해진다.

### 핵심 파라미터 정의

| 파라미터 | 기본값 | 설명 |
|---|---|---|
| `maximumPoolSize` | 10 | 풀이 유지할 수 있는 최대 커넥션 수 |
| `minimumIdle` | maximumPoolSize와 동일 | 유휴 상태로 유지할 최소 커넥션 수 |
| `connectionTimeout` | 30000ms | 커넥션 획득 대기 최대 시간 |
| `idleTimeout` | 600000ms | 유휴 커넥션이 풀에서 제거되기까지의 시간 |
| `maxLifetime` | 1800000ms | 커넥션의 최대 수명 (DB의 wait_timeout보다 짧게 설정) |
| `keepaliveTime` | 0 (비활성) | 유휴 커넥션에 ping을 보내는 주기 |
| `validationTimeout` | 5000ms | 커넥션 유효성 검사 타임아웃 |

## 실전 예제

### 1. Spring Boot 기본 설정

`application.yml`에서 HikariCP를 설정하는 가장 일반적인 방법이다.

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/mydb?useSSL=false&serverTimezone=UTC&characterEncoding=UTF-8
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}
    driver-class-name: com.mysql.cj.jdbc.Driver
    hikari:
      pool-name: MyAppHikariPool
      maximum-pool-size: 20
      minimum-idle: 5
      connection-timeout: 3000       # 3초
      idle-timeout: 300000           # 5분
      max-lifetime: 1200000          # 20분 (MySQL wait_timeout 28800 기준)
      keepalive-time: 60000          # 1분마다 ping
      validation-timeout: 2000
      connection-test-query: SELECT 1  # JDBC4 미지원 드라이버용
      data-source-properties:
        cachePrepStmts: true
        prepStmtCacheSize: 250
        prepStmtCacheSqlLimit: 2048
        useServerPrepStmts: true
```

### 2. Java Config로 세밀하게 제어하기

멀티 DataSource 환경이나 조건별 분기가 필요한 경우 Java Config가 유리하다.

```java
@Configuration
public class DataSourceConfig {

    @Bean
    @Primary
    @ConfigurationProperties(prefix = "spring.datasource.hikari")
    public HikariDataSource primaryDataSource() {
        HikariConfig config = new HikariConfig();

        config.setPoolName("PrimaryPool");
        config.setJdbcUrl("jdbc:mysql://primary-db:3306/mydb");
        config.setUsername(dbUsername);
        config.setPassword(dbPassword);
        config.setDriverClassName("com.mysql.cj.jdbc.Driver");

        // 풀 사이즈 설정
        config.setMaximumPoolSize(20);
        config.setMinimumIdle(5);

        // 타임아웃 설정
        config.setConnectionTimeout(3_000);
        config.setIdleTimeout(300_000);
        config.setMaxLifetime(1_200_000);
        config.setKeepaliveTime(60_000);

        // MySQL 성능 최적화 옵션
        config.addDataSourceProperty("cachePrepStmts", "true");
        config.addDataSourceProperty("prepStmtCacheSize", "250");
        config.addDataSourceProperty("prepStmtCacheSqlLimit", "2048");
        config.addDataSourceProperty("useServerPrepStmts", "true");
        config.addDataSourceProperty("rewriteBatchedStatements", "true");

        // 메트릭 수집 (Micrometer 연동)
        config.setMetricRegistry(meterRegistry);

        return new HikariDataSource(config);
    }

    @Bean
    public DataSource readReplicaDataSource() {
        HikariConfig config = new HikariConfig();
        config.setPoolName("ReadReplicaPool");
        config.setJdbcUrl("jdbc:mysql://replica-db:3306/mydb");
        config.setMaximumPoolSize(30);  // 읽기 트래픽이 더 많으므로 크게 설정
        config.setMinimumIdle(10);
        config.setReadOnly(true);       // Read-only 커넥션으로 최적화
        // ... 나머지 설정 동일
        return new HikariDataSource(config);
    }
}
```

### 3. maximumPoolSize 공식 계산

HikariCP 공식 문서에서 제안하는 커넥션 풀 사이즈 공식은 다음과 같다.

```
pool_size = Tn × (Cm - 1) + 1

Tn = 최대 동시 스레드 수
Cm = 단일 트랜잭션에서 동시에 필요한 최대 커넥션 수
```

예를 들어, 100개의 스레드가 동시에 요청하고, 각 트랜잭션이 하나의 커넥션만 사용한다면:

```
pool_size = 100 × (1 - 1) + 1 = 1 (이론값)
실제 운영에서는 여유분 포함: core_count * 2 + effective_spindle_count
```

**실용적인 접근법:**

```java
// CPU 코어 기반 초기 추정값 계산
int availableProcessors = Runtime.getRuntime().availableProcessors();
int initialPoolSize = availableProcessors * 2 + 1;

System.out.printf("권장 초기 풀 사이즈: %d%n", initialPoolSize);
// 4코어 서버: 4 * 2 + 1 = 9
// 8코어 서버: 8 * 2 + 1 = 17
```

### 4. 모니터링 및 메트릭 수집

Micrometer + Prometheus 연동으로 풀 상태를 실시간 모니터링하자.

```java
@Component
@Slf4j
public class HikariPoolMonitor {

    private final HikariDataSource dataSource;
    private final MeterRegistry meterRegistry;

    public HikariPoolMonitor(DataSource dataSource, MeterRegistry meterRegistry) {
        this.dataSource = (HikariDataSource) dataSource;
        this.meterRegistry = meterRegistry;
        this.dataSource.setMetricRegistry(meterRegistry);
    }

    @Scheduled(fixedDelay = 30_000)
    public void logPoolStatus() {
        HikariPoolMXBean poolMXBean = dataSource.getHikariPoolMXBean();

        int activeConnections = poolMXBean.getActiveConnections();
        int idleConnections = poolMXBean.getIdleConnections();
        int totalConnections = poolMXBean.getTotalConnections();
        int threadsAwaitingConnection = poolMXBean.getThreadsAwaitingConnection();

        log.info("[HikariCP] Active={}, Idle={}, Total={}, Waiting={}",
                activeConnections, idleConnections,
                totalConnections, threadsAwaitingConnection);

        // 위험 임계값 알림
        if (threadsAwaitingConnection > 5) {
            log.warn("[HikariCP] 대기 스레드 수 임계값 초과! Waiting={}", threadsAwaitingConnection);
        }

        double usageRate = (double) activeConnections / dataSource.getMaximumPoolSize();
        if (usageRate > 0.8) {
            log.warn("[HikariCP] 커넥션 사용률 80% 초과! Usage={:.1f}%", usageRate * 100);
        }
    }
}
```

### 5. 커넥션 누수 감지

```yaml
spring:
  datasource:
    hikari:
      leak-detection-threshold: 2000  # 2초 이상 반환되지 않은 커넥션 경고
```

```java
// 실수로 커넥션을 닫지 않는 상황 시뮬레이션 (절대 이렇게 하지 말 것!)
@Service
public class LeakyService {

    @Autowired
    private DataSource dataSource;

    // BAD: try-with-resources 미사용
    public void badMethod() throws SQLException {
        Connection conn = dataSource.getConnection();
        // conn.close() 누락 → leak-detection-threshold 후 경고 로그 출력
    }

    // GOOD: try-with-resources로 자동 반환 보장
    public void goodMethod() throws SQLException {
        try (Connection conn = dataSource.getConnection();
             PreparedStatement ps = conn.prepareStatement("SELECT 1")) {
            ps.execute();
        } // 자동으로 conn.close() 호출 → 풀에 반환
    }
}
```

## 주의사항 및 트레이드오프

### ⚠️ maximumPoolSize를 무작정 크게 설정하면 안 되는 이유

많은 개발자가 커넥션 부족 문제를 겪으면 reflexively하게 `maximumPoolSize`를 늘린다. 하지만 DB 서버 관점에서 커넥션은 **각각 스레드, 메모리, 파일 디스크립터**를 소비한다.

- MySQL 기준: 커넥션 하나당 약 **1~2MB** 메모리 사용
- 100개 커넥션 × 10개 서버 인스턴스 = DB에 **1,000개** 커넥션
- DB max_connections 초과 시 전체 서비스 장애

**권장 접근법**: 먼저 DB 쿼리 최적화, 트랜잭션 범위 축소로 커넥션 점유 시간을 줄인 후 풀 사이즈 조정.

### ⚠️ maxLifetime과 DB wait_timeout 관계

```
DB wait_timeout (기본 8시간) > HikariCP maxLifetime (기본 30분)
```

반드시 `maxLifetime`을 DB `wait_timeout`보다 **수십 초 이상 짧게** 설정해야 한다. 그렇지 않으면 DB가 먼저 커넥션을 끊어버려 `CommunicationsException`이 발생한다.

```yaml
# MySQL wait_timeout = 28800초(8시간) 기준
hikari:
  max-lifetime: 1740000  # 29분 (30분보다 1분 여유)
```

### ⚠️ minimumIdle 설정의 트레이드오프

| minimumIdle = maximumPoolSize (고정 풀) | minimumIdle < maximumPoolSize (동적 풀) |
|---|---|
| 예측 가능한 성능 | 트래픽 변화에 유연 |
| 항상 커넥션 유지 비용 발생 | 피크 시 커넥션 생성 지연 가능 |
| 트래픽이 일정한 서비스에 적합 | 트래픽 변동이 큰 서비스에 적합 |

HikariCP 공식 문서는 **고정 풀 크기(minimumIdle = maximumPoolSize)**를 권장한다.

### ⚠️ connectionTimeout vs socketTimeout

이 두 가지는 자주 혼동된다.

- `connectionTimeout`: 풀에서 커넥션을 **빌리는** 데 걸리는 최대 시간
- `socketTimeout` (JDBC URL 파라미터): 이미 획득한 커넥션에서 DB 응답을 **기다리는** 최대 시간

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/mydb?socketTimeout=30000&connectTimeout=3000
    hikari:
      connection-timeout: 3000  # 풀에서 커넥션 획득 대기 시간
```

## 정리

HikariCP 최적화는 단순히 숫자를 조정하는 작업이 아니다. 서비스의 트래픽 패턴, DB 서버의 스펙, 쿼리 특성을 종합적으로 이해한 뒤에 설정해야 한다.

**핵심 요약:**

1. **maximumPoolSize**는 DB 서버 용량을 고려해 보수적으로 시작하고, 모니터링 결과를 바탕으로 점진적으로 조정한다.
2. **maxLifetime**은 반드시 DB의 `wait_timeout`보다 짧게 설정한다.
3. **leakDetectionThreshold**를 설정해 커넥션 누수를 조기에 발견한다.
4. **Micrometer 메트릭**으로 풀 상태를 지속적으로 모니터링한다.
5. 커넥션 부족 문제는 풀 사이즈 확대보다 **쿼리 최적화와 트랜잭션 범위 축소**로 먼저 접근한다.

커넥션 풀은 애플리케이션과 DB 사이의 고속도로다. 차선(커넥션)을 늘리는 것도 방법이지만, 차량(쿼리)이 도로를 점유하는 시간을 줄이는 것이 근본적인 해결책임을 항상 기억하자.
