# 블록체인 핵심 개념과 백엔드 개발자 관점에서의 이해

## 개요

백엔드 개발자로 일하다 보면 어느 순간 블록체인 관련 프로젝트를 마주하게 된다. NFT 플랫폼, DeFi 서비스, 토큰 발행 시스템... 처음에는 "분산 장부 아닌가?"라는 막연한 이해로 시작하지만, 실제 개발에 뛰어들면 생각보다 낯선 개념들이 쏟아진다.

이 글은 블록체인을 처음 접하는 분들을 위한 입문서가 아니다. **전통적인 서버-클라이언트 아키텍처에 익숙한 중급 이상의 백엔드 개발자**가 블록체인의 핵심 개념을 빠르게 실무 관점으로 재해석할 수 있도록 돕는 것이 목적이다.

RDB의 트랜잭션, REST API의 상태 관리, 분산 시스템의 일관성 문제를 이미 고민해본 개발자라면, 블록체인의 많은 개념이 익숙하면서도 미묘하게 다르다는 것을 느낄 것이다.

---

## 핵심 개념

### 1. 블록과 체인 — "불변 로그"로 이해하라

블록체인을 가장 빠르게 이해하는 방법은 **append-only log**로 바라보는 것이다. RDB의 WAL(Write-Ahead Log)이나 Kafka의 토픽과 유사하게, 한번 기록된 데이터는 수정되지 않고 오직 새로운 블록이 추가될 뿐이다.

각 블록은 다음 구조를 가진다:

```
Block {
  index: 블록 높이 (순서)
  timestamp: 생성 시각
  data: 트랜잭션 목록
  previousHash: 이전 블록의 해시
  hash: 현재 블록의 해시 (previousHash + data + nonce 등의 해시)
  nonce: PoW에서 사용하는 임의값
}
```

`previousHash`를 통해 블록이 체인처럼 연결되기 때문에, 과거 블록을 변조하면 이후 모든 블록의 해시가 깨진다. 이것이 **불변성(Immutability)**의 기술적 근거다.

### 2. 합의 알고리즘 — 분산 시스템의 "투표"

분산 시스템에서 CAP 정리를 고민해봤다면, 블록체인의 합의 문제도 비슷한 맥락으로 이해할 수 있다. 어떤 노드의 블록이 "진짜"인지 모든 참여자가 동의하는 메커니즘이 바로 합의 알고리즘이다.

| 알고리즘 | 방식 | 특징 | 대표 체인 |
|--------|------|------|---------|
| PoW (Proof of Work) | 해시 연산 경쟁 | 에너지 소모 大, 보안성 高 | Bitcoin |
| PoS (Proof of Stake) | 지분 기반 검증자 선출 | 에너지 효율적 | Ethereum(현재) |
| DPoS | 대표자 위임 투표 | 빠른 처리, 덜 탈중앙화 | EOS, TRON |
| PBFT | 노드 간 메시지 교환 | 낮은 지연, 소규모 네트워크에 적합 | Hyperledger |

백엔드 개발자 관점에서 핵심은 **finality(완결성)**다. 전통 DB는 커밋되면 즉시 확정이지만, PoW 기반 블록체인은 블록이 쌓일수록 확정 확률이 높아지는 **확률적 완결성**을 가진다. 결제 시스템 연동 시 이더리움은 보통 12~30 confirmation을 기다린다.

### 3. 스마트 컨트랙트 — 체인 위의 "서버리스 함수"

스마트 컨트랙트는 블록체인 위에 배포된 코드로, 특정 조건이 충족되면 자동으로 실행된다. AWS Lambda나 Cloud Functions와 개념적으로 유사하지만, 결정적인 차이가 있다:

- **실행 결과가 불변**: 한번 실행된 트랜잭션은 되돌릴 수 없다.
- **상태가 체인에 저장**: 별도 DB가 아닌 블록체인 자체가 상태 저장소다.
- **Gas 비용**: 모든 연산에 비용이 따른다. 루프 최적화가 비즈니스 이슈가 된다.

### 4. 지갑과 서명 — PKI의 실전 활용

백엔드에서 JWT나 OAuth를 다뤄봤다면 공개키 암호화에 익숙할 것이다. 블록체인의 지갑은 **비대칭 키 쌍(Private Key / Public Key)**으로 동작한다.

```
Private Key → (타원 곡선 암호화, secp256k1) → Public Key → (Keccak-256 해시) → Address
```

트랜잭션 서명 과정:
1. 사용자가 Private Key로 트랜잭션 데이터에 서명
2. 네트워크 노드가 서명을 검증 (Public Key로 복원)
3. 검증 성공 시 트랜잭션을 메모리풀에 추가

## 실전 예제

### Web3j로 이더리움 트랜잭션 연동하기 (Java/Spring)

실제 백엔드 서비스에서 이더리움 네트워크와 통신하는 예제를 살펴보자.

**의존성 추가 (build.gradle)**

```groovy
dependencies {
    implementation 'org.web3j:core:4.10.3'
    implementation 'org.springframework.boot:spring-boot-starter-web'
}
```

**Web3j 설정 Bean**

```java
@Configuration
public class Web3jConfig {

    @Value("${ethereum.rpc-url}")
    private String rpcUrl;

    @Bean
    public Web3j web3j() {
        // Infura, Alchemy 등의 노드 프로바이더 사용
        return Web3j.build(new HttpService(rpcUrl));
    }
}
```

**트랜잭션 조회 서비스**

```java
@Service
@RequiredArgsConstructor
@Slf4j
public class EthereumService {

    private final Web3j web3j;

    /**
     * 트랜잭션 해시로 상태 확인
     * PoW/PoS의 확률적 완결성 때문에 confirmation 수를 반드시 체크해야 한다.
     */
    public TransactionStatus getTransactionStatus(String txHash, int requiredConfirmations)
            throws IOException {

        EthTransaction ethTransaction = web3j.ethGetTransactionByHash(txHash).send();

        if (ethTransaction.getTransaction().isEmpty()) {
            return TransactionStatus.PENDING;
        }

        Transaction tx = ethTransaction.getTransaction().get();

        // 트랜잭션이 포함된 블록 번호 확인
        if (tx.getBlockNumber() == null) {
            return TransactionStatus.PENDING;
        }

        // 현재 최신 블록 번호 조회
        BigInteger currentBlock = web3j.ethBlockNumber().send().getBlockNumber();
        BigInteger txBlock = tx.getBlockNumber();

        // confirmation 수 계산
        BigInteger confirmations = currentBlock.subtract(txBlock).add(BigInteger.ONE);

        if (confirmations.intValue() >= requiredConfirmations) {
            // Receipt로 성공/실패 구분 (status: 1 = 성공, 0 = 실패/revert)
            EthGetTransactionReceipt receipt =
                web3j.ethGetTransactionReceipt(txHash).send();

            return receipt.getTransactionReceipt()
                .map(r -> "0x1".equals(r.getStatus())
                    ? TransactionStatus.CONFIRMED
                    : TransactionStatus.FAILED)
                .orElse(TransactionStatus.PENDING);
        }

        return TransactionStatus.CONFIRMING;
    }

    /**
     * ETH 잔액 조회
     */
    public BigDecimal getEthBalance(String address) throws IOException {
        EthGetBalance balance = web3j
            .ethGetBalance(address, DefaultBlockParameterName.LATEST)
            .send();

        // Wei → ETH 변환 (1 ETH = 10^18 Wei)
        return Convert.fromWei(balance.getBalance().toString(), Convert.Unit.ETHER);
    }
}

public enum TransactionStatus {
    PENDING,      // 아직 블록에 포함되지 않음
    CONFIRMING,   // 포함됐지만 confirmation 미달
    CONFIRMED,    // 충분한 confirmation 확보
    FAILED        // revert 또는 실패
}
```

**스마트 컨트랙트 이벤트 리스닝 (WebSocket 기반)**

```java
@Component
@RequiredArgsConstructor
@Slf4j
public class ContractEventListener {

    private final Web3j web3j;

    @Value("${contract.erc20.address}")
    private String contractAddress;

    /**
     * ERC-20 Transfer 이벤트 구독
     * 실시간 입금 감지에 활용 가능
     */
    @PostConstruct
    public void subscribeTransferEvents() {
        EthFilter filter = new EthFilter(
            DefaultBlockParameterName.LATEST,
            DefaultBlockParameterName.LATEST,
            contractAddress
        );

        // Transfer(address indexed from, address indexed to, uint256 value)
        filter.addSingleTopic(EventEncoder.encode(
            new Event("Transfer",
                Arrays.asList(
                    new TypeReference<Address>(true) {},  // indexed: from
                    new TypeReference<Address>(true) {},  // indexed: to
                    new TypeReference<Uint256>() {}       // value
                ))
        ));

        web3j.ethLogFlowable(filter)
            .subscribeOn(Schedulers.io())
            .subscribe(
                this::handleTransferEvent,
                error -> log.error("Event listening error", error)
            );
    }

    private void handleTransferEvent(Log eventLog) {
        List<Type> decoded = FunctionReturnDecoder.decode(
            eventLog.getData(),
            Utils.convert(List.of(new TypeReference<Uint256>() {}))
        );

        BigInteger amount = (BigInteger) decoded.get(0).getValue();
        String from = "0x" + eventLog.getTopics().get(1).substring(26);
        String to = "0x" + eventLog.getTopics().get(2).substring(26);

        log.info("Transfer detected: {} → {}, amount: {}", from, to, amount);
        // 내부 DB 업데이트, 알림 발송 등 비즈니스 로직 처리
    }
}
```

## 주의사항 및 트레이드오프

### ⚠️ Private Key 절대로 서버에 평문 저장 금지

가장 흔한 실수이자 치명적인 보안 사고의 원인이다. 서버에서 트랜잭션을 서명해야 한다면:

- **AWS KMS, HashiCorp Vault** 같은 HSM/시크릿 매니저를 활용
- 사용자의 Private Key를 서버에서 관리하는 아키텍처 자체를 재고
- MPC(Multi-Party Computation) 월렛 솔루션 검토

### ⚠️ 이벤트 리스닝의 신뢰성 문제

블록체인 이벤트를 WebSocket으로 구독하면 네트워크 단절, 노드 장애 시 이벤트를 누락할 수 있다. **Chain reorg(체인 재구성)**가 발생하면 이미 처리한 이벤트가 무효화될 수도 있다.

**권장 아키텍처:**
```
[Blockchain Node] → [Event Indexer (The Graph / 자체 구현)] → [Internal DB] → [Business Logic]
```

폴링 방식과 이벤트 구독을 혼합하고, 처리된 이벤트를 DB에 멱등하게(idempotent) 기록하는 것이 안전하다.

### ⚠️ Gas 비용과 트랜잭션 실패

스마트 컨트랙트 호출이 `revert`되면 Gas는 소모되지만 상태 변경은 일어나지 않는다. 비즈니스 로직에서 반드시 `status` 필드를 확인해야 한다. 또한 네트워크 혼잡 시 Gas Price를 동적으로 조정하는 로직(EIP-1559 기준의 `maxFeePerGas`, `maxPriorityFeePerGas`)이 필요하다.

### 트레이드오프 정리

| 항목 | 전통 백엔드 | 블록체인 |
|------|-----------|---------|
| 트랜잭션 완결성 | 즉시 (ACID) | 확률적 (confirmation) |
| 데이터 수정 | UPDATE/DELETE 가능 | 불변 (append-only) |
| 처리 속도 | 수천~수만 TPS | 수십~수천 TPS |
| 비용 | 서버 운영비 | Gas Fee (변동) |
| 디버깅 | 로그, 디버거 | Tenderly, Hardhat |
| 롤백 | 가능 | 불가 (새 트랜잭션으로 보정) |

## 정리

블록체인은 완전히 새로운 패러다임처럼 보이지만, 백엔드 개발자의 눈으로 보면 **분산 시스템 + 불변 로그 + PKI 인증**의 조합이다. 기존 지식을 기반으로 낯선 개념들을 재해석하면 훨씬 빠르게 실무에 적응할 수 있다.

핵심을 다시 정리하면:

1. **블록** = Append-Only 불변 로그
2. **합의 알고리즘** = 분산 환경에서의 일관성 확보 메커니즘 (완결성에 주의)
3. **스마트 컨트랙트** = 체인 위의 비즈니스 로직 (실패도 비용이 든다)
4. **지갑/서명** = 실전 PKI (Private Key 관리가 핵심 보안 이슈)
5. **이벤트 처리** = 신뢰성 있는 인덱싱 레이어 설계 필수

다음 단계로는 **Hardhat/Foundry를 활용한 로컬 개발 환경 구성**, **The Graph를 이용한 이벤트 인덱싱**, **ERC-20/ERC-721 표준 구현**을 살펴보면 실무 역량을 빠르게 올릴 수 있다.

블록체인은 은총알이 아니다. 하지만 특정 도메인에서는 강력한 도구가 된다. 어떤 문제를 풀기 위해 블록체인이 필요한지 명확히 하고, 그 위에 탄탄한 백엔드 레이어를 설계하는 것이 우리의 역할이다.
