# IPv6 전환과 백엔드 서비스 고려사항

## 개요

전 세계 IPv4 주소 고갈 문제는 이제 더 이상 먼 미래의 이야기가 아니다. IANA(Internet Assigned Numbers Authority)는 이미 2011년에 IPv4 주소 블록 할당을 완료했고, 각 지역 인터넷 레지스트리(RIR)들도 순차적으로 소진을 선언했다. 그럼에도 불구하고 많은 백엔드 서비스들은 여전히 IPv4 중심으로 설계되어 있으며, IPv6 전환을 "언젠가 해야 할 일"로 미루고 있는 경우가 많다.

문제는 모바일 네트워크, 클라우드 환경, IoT 기기의 폭발적 증가로 인해 IPv6 지원이 선택이 아닌 필수가 되고 있다는 점이다. 특히 AWS, GCP, Azure 같은 클라우드 플랫폼들이 IPv6 듀얼스택을 적극 지원하기 시작하면서, 백엔드 개발자가 IPv6를 이해하고 서비스에 적용하는 역량이 점점 더 중요해지고 있다.

이 글에서는 IPv6 전환 시 백엔드 서비스에서 고려해야 할 핵심 개념과 실전 예제를 살펴본다.

---

## 핵심 개념

### IPv4 vs IPv6 주소 체계

가장 먼저 이해해야 할 것은 주소 체계의 근본적인 차이다.

| 구분 | IPv4 | IPv6 |
|---|---|---|
| 주소 길이 | 32비트 | 128비트 |
| 표기 방식 | 점 십진수 (192.168.1.1) | 콜론 16진수 (2001:db8::1) |
| 주소 공간 | 약 43억 개 | 약 3.4 × 10³⁸ 개 |
| NAT 필요 여부 | 필수 | 불필요 |
| 브로드캐스트 | 지원 | 미지원 (멀티캐스트로 대체) |

IPv6 주소에는 몇 가지 특수한 형태가 있다. 백엔드 개발자가 자주 마주치는 것들을 정리하면 다음과 같다.

- **`::1`** — 루프백 주소 (IPv4의 `127.0.0.1`)
- **`::ffff:192.168.1.1`** — IPv4-mapped IPv6 주소. IPv6 소켓에서 IPv4 연결을 처리할 때 나타남
- **`fe80::/10`** — 링크-로컬 주소. 같은 네트워크 세그먼트 내에서만 유효
- **`2001:db8::/32`** — 문서/예시용으로 예약된 주소

### 듀얼스택, 터널링, 변환 방식

전환 전략은 크게 세 가지로 나뉜다.

**듀얼스택(Dual Stack):** 하나의 호스트가 IPv4와 IPv6 주소를 동시에 가지고, 양쪽 프로토콜을 모두 처리한다. 가장 안정적이고 권장되는 방식이다. 단, 네트워크 장비와 애플리케이션 모두 듀얼스택을 지원해야 한다.

**터널링(Tunneling):** IPv6 패킷을 IPv4 패킷으로 캡슐화하여 전송한다. 6in4, 6to4, Teredo 등이 대표적이다. 과도기적 방법으로, 성능 오버헤드가 있다.

**변환(Translation):** NAT64/DNS64 같은 방식으로 프로토콜 간 변환을 수행한다. IPv6만 지원하는 클라이언트가 IPv4 서버에 접근할 때 활용된다.

실무에서는 **듀얼스택** 방식이 가장 현실적인 선택이며, 이 글도 이를 중심으로 다룬다.

## 실전 예제

### 1. Java/Spring에서 IPv6 주소 처리

Java의 `InetAddress`는 IPv4와 IPv6를 모두 지원한다. 그러나 IPv6 주소를 문자열로 다룰 때는 주의가 필요하다.

```java
import java.net.Inet4Address;
import java.net.Inet6Address;
import java.net.InetAddress;
import java.net.UnknownHostException;

public class IpAddressUtils {

    /**
     * IP 주소 문자열을 파싱하고 버전을 판별한다.
     * IPv4-mapped IPv6 주소(::ffff:x.x.x.x)도 올바르게 처리한다.
     */
    public static String normalizeIpAddress(String rawIp) throws UnknownHostException {
        // IPv4-mapped IPv6 주소 처리: "::ffff:192.168.1.1" 형태
        if (rawIp != null && rawIp.startsWith("::ffff:")) {
            return rawIp.substring(7); // IPv4 부분만 추출
        }

        InetAddress addr = InetAddress.getByName(rawIp);

        if (addr instanceof Inet6Address) {
            // 링크-로컬 주소는 zone ID(%eth0)가 붙을 수 있으므로 제거
            String hostAddress = addr.getHostAddress();
            int zoneIndex = hostAddress.indexOf('%');
            return zoneIndex != -1 ? hostAddress.substring(0, zoneIndex) : hostAddress;
        }

        return addr.getHostAddress();
    }

    public static boolean isIpv6(String ip) {
        try {
            InetAddress addr = InetAddress.getByName(ip);
            return addr instanceof Inet6Address;
        } catch (UnknownHostException e) {
            return false;
        }
    }

    public static boolean isPrivateAddress(String ip) throws UnknownHostException {
        InetAddress addr = InetAddress.getByName(ip);
        return addr.isSiteLocalAddress()   // fc00::/7, 10.x, 172.16.x, 192.168.x
            || addr.isLinkLocalAddress()   // fe80::/10, 169.254.x.x
            || addr.isLoopbackAddress();   // ::1, 127.x.x.x
    }
}
```

### 2. Spring Boot 애플리케이션 IPv6 바인딩 설정

기본적으로 Spring Boot의 내장 Tomcat은 `0.0.0.0`에 바인딩되어 IPv4만 리슨한다. IPv6를 함께 지원하려면 설정을 수정해야 한다.

```yaml
# application.yml
server:
  address: "::"  # IPv4와 IPv6 모두 리슨 (듀얼스택)
  port: 8080
```

단, 운영체제의 `net.ipv6.bindv6only` 설정에 따라 동작이 달라진다.
- `0`(기본값, Linux): `::` 바인딩 시 IPv4도 함께 처리 (IPv4-mapped 방식)
- `1`: IPv6 전용, IPv4는 별도 소켓 필요

```java
// 프로그래밍 방식으로 설정 (필요한 경우)
@Bean
public TomcatServletWebServerFactory tomcatFactory() {
    TomcatServletWebServerFactory factory = new TomcatServletWebServerFactory();
    factory.addConnectorCustomizers(connector -> {
        connector.setProperty("address", "::");
    });
    return factory;
}
```

### 3. 클라이언트 IP 추출 시 IPv6 고려

리버스 프록시(Nginx, ALB 등) 뒤에서 클라이언트 IP를 추출할 때, `X-Forwarded-For` 헤더에 IPv6 주소가 포함될 수 있다.

```java
@Component
public class ClientIpExtractor {

    private static final String[] IP_HEADERS = {
        "X-Forwarded-For",
        "X-Real-IP",
        "Proxy-Client-IP",
        "WL-Proxy-Client-IP"
    };

    public String extractClientIp(HttpServletRequest request) {
        for (String header : IP_HEADERS) {
            String ip = request.getHeader(header);
            if (ip != null && !ip.isBlank() && !"unknown".equalsIgnoreCase(ip)) {
                // X-Forwarded-For는 쉼표로 여러 IP가 올 수 있음
                // 첫 번째가 실제 클라이언트 IP
                String firstIp = ip.split(",")[0].trim();
                return normalizeForStorage(firstIp);
            }
        }
        return normalizeForStorage(request.getRemoteAddr());
    }

    private String normalizeForStorage(String ip) {
        // IPv4-mapped IPv6 주소를 IPv4로 정규화
        if (ip.startsWith("::ffff:")) {
            return ip.substring(7);
        }
        return ip;
    }
}
```

### 4. 데이터베이스에서 IP 주소 저장 전략

기존에 `VARCHAR(15)`로 IPv4 주소를 저장하던 컬럼은 IPv6를 담을 수 없다. IPv6 최대 길이는 39자(풀 표기)이므로 컬럼 크기를 늘려야 한다.

```sql
-- 기존 IPv4 전용 컬럼
ALTER TABLE user_access_log
    MODIFY COLUMN client_ip VARCHAR(15);

-- IPv6 대응 마이그레이션
ALTER TABLE user_access_log
    MODIFY COLUMN client_ip VARCHAR(45);
-- 45자 이유: IPv4-mapped IPv6 "::ffff:xxx.xxx.xxx.xxx" 최대 45자

-- 범위 검색이 필요한 경우 VARBINARY(16) 사용 권장
-- IPv4 → 4바이트, IPv6 → 16바이트를 바이너리로 저장
ALTER TABLE user_access_log
    ADD COLUMN client_ip_binary VARBINARY(16);
```

```java
// VARBINARY 방식으로 저장 시 변환 유틸리티
public class IpBinaryConverter {

    public static byte[] ipToBytes(String ip) throws UnknownHostException {
        return InetAddress.getByName(ip).getAddress();
        // IPv4: 4바이트, IPv6: 16바이트
    }

    public static String bytesToIp(byte[] bytes) throws UnknownHostException {
        return InetAddress.getByAddress(bytes).getHostAddress();
    }
}
```

### 5. Nginx 듀얼스택 설정

```nginx
# /etc/nginx/nginx.conf

http {
    server {
        # IPv4와 IPv6 동시 리슨
        listen 80;
        listen [::]:80;

        # HTTPS
        listen 443 ssl;
        listen [::]:443 ssl;

        server_name example.com;

        # 클라이언트 IP 로깅 시 IPv6 주소 처리
        set_real_ip_from 10.0.0.0/8;
        set_real_ip_from fc00::/7;  # IPv6 사설 대역도 추가
        real_ip_header X-Forwarded-For;

        location / {
            proxy_pass http://backend;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Real-IP $remote_addr;
        }
    }
}
```

## 주의사항 및 트레이드오프

### IP 기반 화이트리스트/블랙리스트의 복잡성 증가

IPv4 환경에서는 `192.168.1.0/24` 같은 CIDR 블록으로 간단히 관리하던 접근 제어가, IPv6에서는 훨씬 방대한 주소 공간을 다뤄야 한다. 예를 들어, 하나의 IPv6 `/48` 블록에는 2⁸⁰개의 주소가 존재한다. 단순 IP 기반 차단 정책은 IPv6에서 효과가 크게 떨어질 수 있으므로, **IP 범위(CIDR) 기반 매칭 라이브러리**(예: Google의 `google/ipaddress-go`, Java의 `commons-net`)를 활용하거나, 보다 상위 레이어의 인증/인가 정책을 강화해야 한다.

### 세션 관리와 IP 고정 가정의 위험성

일부 레거시 시스템은 세션 고정화(Session Fixation) 방지나 사용자 추적 목적으로 IP 주소를 세션에 묶는다. IPv6 환경에서는 **Privacy Extensions(RFC 4941)** 에 의해 클라이언트 IP가 주기적으로 변경될 수 있다. 이를 고려하지 않으면 정상적인 사용자가 세션에서 강제로 로그아웃되는 문제가 발생할 수 있다. IP 기반 세션 바인딩은 IPv6 환경에서는 사용하지 않거나, 서브넷 단위로 완화하는 것이 바람직하다.

### DNS 설정의 이중화

듀얼스택 운영 시에는 DNS에 A 레코드(IPv4)와 AAAA 레코드(IPv6)를 모두 등록해야 한다. 클라이언트는 **Happy Eyeballs(RFC 6555)** 알고리즘에 따라 IPv6를 우선 시도하고, 실패 시 IPv4로 폴백한다. 이 과정에서 연결 지연이 발생할 수 있으므로, AAAA 레코드를 등록했다면 해당 엔드포인트가 실제로 정상 동작하는지 반드시 확인해야 한다.

### 로그 분석 파이프라인 호환성 검토

기존 로그 파싱 정규식, GeoIP 조회, 보안 분석 도구들이 IPv6 주소 형식을 올바르게 처리하는지 반드시 검토해야 한다. `::1`이나 `2001:db8:85a3::8a2e:370:7334` 같은 주소가 로그에 나타났을 때 파싱 오류나 GeoIP 조회 실패가 발생하면 모니터링 사각지대가 생긴다.

### 방화벽 및 보안 그룹 규칙 이중 관리

클라우드 환경에서 IPv6를 활성화하면 보안 그룹 규칙을 IPv4와 IPv6 각각에 대해 별도로 관리해야 한다. IPv4 규칙만 꼼꼼하게 작성하고 IPv6 규칙을 방치하면 의도치 않은 포트 노출로 이어질 수 있다. **인프라-애즈-코드(Terraform, CloudFormation 등)로 두 버전의 규칙을 함께 관리**하는 것이 실수를 줄이는 방법이다.

```hcl
# Terraform 예시: IPv4와 IPv6 인바운드 규칙 함께 정의
resource "aws_security_group_rule" "allow_https_ipv4" {
  type        = "ingress"
  from_port   = 443
  to_port     = 443
  protocol    = "tcp"
  cidr_blocks = ["0.0.0.0/0"]
  security_group_id = aws_security_group.main.id
}

resource "aws_security_group_rule" "allow_https_ipv6" {
  type             = "ingress"
  from_port        = 443
  to_port          = 443
  protocol         = "tcp"
  ipv6_cidr_blocks = ["::/0"]
  security_group_id = aws_security_group.main.id
}
```

## 정리

IPv6 전환은 단순히 "주소 체계가 바뀌는 것"이 아니라, 애플리케이션 코드, 데이터베이스 스키마, 네트워크 설정, 보안 정책, 로그 분석 파이프라인 전반에 걸친 변화를 요구한다. 체크리스트 형태로 정리하면 다음과 같다.

- [ ] **애플리케이션:** `InetAddress` 등 IP 처리 로직이 IPv6와 IPv4-mapped 주소를 올바르게 처리하는가?
- [ ] **API/미들웨어:** 클라이언트 IP 추출, 화이트리스트 검사 로직이 IPv6 형식을 지원하는가?
- [ ] **데이터베이스:** IP 저장 컬럼의 최대 길이가 IPv6를 수용하는가? (최소 `VARCHAR(45)` 또는 `VARBINARY(16)`)
- [ ] **인프라:** Nginx, 로드밸런서, 보안 그룹에 IPv6 규칙이 IPv4와 동등하게 적용되어 있는가?
- [ ] **DNS:** A 레코드와 AAAA 레코드가 모두 등록되어 있고, AAAA 엔드포인트가 실제로 동작하는가?
- [ ] **보안:** 세션 IP 바인딩, IP 기반 Rate Limiting 로직이 Privacy Extensions를 고려하고 있는가?
- [ ] **모니터링:** GeoIP, 로그 파서, 보안 도구가 IPv6 주소를 처리할 수 있는가?

지금 당장 모든 것을 바꿀 필요는 없다. 하지만 신규 서비스를 설계할 때부터 IPv6를 염두에 두고 "IPv4만 된다"는 가정을 코드에 심지 않는 것이, 나중에 발생할 대규모 마이그레이션 비용을 줄이는 가장 현실적인 접근법이다.
