# Ansible로 서버 구성 관리 자동화

## 개요

서버 인프라가 수십 대를 넘어서는 순간, 수동으로 SSH 접속하여 패키지를 설치하고 설정 파일을 수정하는 방식은 더 이상 지속 가능하지 않습니다. 운영 중 "이 서버만 설정이 다른데?" 라는 상황, 즉 **Configuration Drift**가 발생하기 시작하고, 이는 장애의 씨앗이 됩니다.

Ansible은 이러한 문제를 해결하기 위한 오픈소스 IT 자동화 도구입니다. Chef나 Puppet과 달리 **에이전트리스(Agentless)** 방식으로 동작하며, 대상 서버에 별도 클라이언트 소프트웨어를 설치할 필요 없이 SSH만으로 연결합니다. 또한 YAML 기반의 선언적 문법을 사용하기 때문에 진입 장벽이 낮고, 기존 인프라에 점진적으로 도입하기 쉽습니다.

이 글에서는 Ansible의 핵심 개념을 정리하고, 실제 운영 환경에서 바로 활용할 수 있는 Spring Boot 애플리케이션 서버 구성 자동화 예제를 함께 살펴보겠습니다.

---

## 핵심 개념

### Inventory

Ansible이 관리할 호스트 목록을 정의하는 파일입니다. 정적(Static) 방식과 동적(Dynamic) 방식 모두 지원하며, AWS EC2, GCP 같은 클라우드 환경에서는 동적 인벤토리 플러그인을 활용하는 것이 일반적입니다.

```ini
# inventory/hosts.ini

[webservers]
web01 ansible_host=10.0.1.10
web02 ansible_host=10.0.1.11

[dbservers]
db01 ansible_host=10.0.2.10

[all:vars]
ansible_user=ubuntu
ansible_ssh_private_key_file=~/.ssh/my-key.pem
ansible_python_interpreter=/usr/bin/python3
```

### Playbook

자동화할 작업(Task)의 집합을 YAML로 정의한 파일입니다. "어떤 호스트에서 무엇을 실행할지"를 선언적으로 기술합니다.

### Role

Playbook이 복잡해질수록 하나의 파일에 모든 것을 담으면 관리가 어려워집니다. Role은 태스크, 변수, 핸들러, 템플릿 등을 표준화된 디렉토리 구조로 분리하여 재사용성을 높입니다.

```
roles/
└── spring-app/
    ├── tasks/
    │   └── main.yml
    ├── handlers/
    │   └── main.yml
    ├── templates/
    │   ├── application.yml.j2
    │   └── spring-app.service.j2
    ├── vars/
    │   └── main.yml
    └── defaults/
        └── main.yml
```

### Handler

특정 태스크가 변경(changed) 상태를 반환했을 때만 실행되는 특수한 태스크입니다. 설정 파일이 변경된 경우에만 서비스를 재시작하는 용도로 주로 사용됩니다.

### Idempotency (멱등성)

Ansible의 핵심 원칙입니다. 동일한 Playbook을 몇 번 실행해도 최종 결과가 항상 같아야 합니다. 이미 설치된 패키지를 다시 설치하거나, 이미 올바른 내용의 파일을 덮어쓰는 불필요한 작업이 발생하지 않습니다.

## 실전 예제: Spring Boot 애플리케이션 서버 구성 자동화

Java 17 + Spring Boot 애플리케이션을 systemd 서비스로 운영하는 서버를 자동으로 구성하는 예제입니다.

### 디렉토리 구조

```
ansible-infra/
├── inventory/
│   ├── production/
│   │   └── hosts.ini
│   └── staging/
│       └── hosts.ini
├── group_vars/
│   ├── all.yml
│   └── webservers.yml
├── roles/
│   ├── common/
│   └── spring-app/
├── site.yml
└── ansible.cfg
```

### ansible.cfg 설정

```ini
[defaults]
inventory = inventory/production/hosts.ini
roles_path = roles
host_key_checking = False
stdout_callback = yaml
retry_files_enabled = False

[ssh_connection]
pipelining = True
ssh_args = -o ControlMaster=auto -o ControlPersist=60s
```

### group_vars 변수 정의

```yaml
# group_vars/all.yml
java_version: "17"
app_user: "appuser"
app_group: "appuser"
app_base_dir: "/opt/apps"

# group_vars/webservers.yml
spring_app_name: "my-service"
spring_app_port: 8080
spring_app_jar: "my-service-1.0.0.jar"
spring_active_profile: "production"
spring_datasource_url: "jdbc:postgresql://{{ db_host }}:5432/mydb"
```

### common Role: 기본 시스템 구성

```yaml
# roles/common/tasks/main.yml
---
- name: apt 패키지 캐시 업데이트
  apt:
    update_cache: yes
    cache_valid_time: 3600

- name: 필수 패키지 설치
  apt:
    name:
      - curl
      - wget
      - unzip
      - net-tools
      - htop
    state: present

- name: 애플리케이션 전용 유저 생성
  user:
    name: "{{ app_user }}"
    group: "{{ app_group }}"
    system: yes
    shell: /sbin/nologin
    create_home: no

- name: 애플리케이션 디렉토리 생성
  file:
    path: "{{ item }}"
    state: directory
    owner: "{{ app_user }}"
    group: "{{ app_group }}"
    mode: "0755"
  loop:
    - "{{ app_base_dir }}"
    - "{{ app_base_dir }}/{{ spring_app_name }}"
    - "{{ app_base_dir }}/{{ spring_app_name }}/config"
    - "/var/log/{{ spring_app_name }}"

- name: Java 17 설치 (Amazon Corretto)
  block:
    - name: Corretto GPG 키 추가
      apt_key:
        url: https://apt.corretto.aws/corretto.key
        state: present

    - name: Corretto 저장소 추가
      apt_repository:
        repo: "deb https://apt.corretto.aws stable main"
        state: present

    - name: Java 17 설치
      apt:
        name: java-17-amazon-corretto-jdk
        state: present
        update_cache: yes
```

### spring-app Role: 애플리케이션 배포 및 서비스 구성

```yaml
# roles/spring-app/tasks/main.yml
---
- name: JAR 파일 배포
  copy:
    src: "files/{{ spring_app_jar }}"
    dest: "{{ app_base_dir }}/{{ spring_app_name }}/{{ spring_app_jar }}"
    owner: "{{ app_user }}"
    group: "{{ app_group }}"
    mode: "0644"
  notify: restart spring-app

- name: application.yml 설정 파일 배포
  template:
    src: application.yml.j2
    dest: "{{ app_base_dir }}/{{ spring_app_name }}/config/application.yml"
    owner: "{{ app_user }}"
    group: "{{ app_group }}"
    mode: "0640"
  notify: restart spring-app

- name: systemd 서비스 파일 배포
  template:
    src: spring-app.service.j2
    dest: "/etc/systemd/system/{{ spring_app_name }}.service"
    mode: "0644"
  notify:
    - reload systemd
    - restart spring-app

- name: 서비스 활성화 및 시작
  systemd:
    name: "{{ spring_app_name }}"
    enabled: yes
    state: started
```

### Jinja2 템플릿

```jinja2
{# roles/spring-app/templates/spring-app.service.j2 #}
[Unit]
Description={{ spring_app_name }} Spring Boot Application
After=network.target

[Service]
Type=simple
User={{ app_user }}
Group={{ app_group }}
WorkingDirectory={{ app_base_dir }}/{{ spring_app_name }}
ExecStart=/usr/bin/java \
  -Xms512m -Xmx1024m \
  -Dspring.profiles.active={{ spring_active_profile }} \
  -Dspring.config.location={{ app_base_dir }}/{{ spring_app_name }}/config/ \
  -jar {{ app_base_dir }}/{{ spring_app_name }}/{{ spring_app_jar }}
SuccessExitStatus=143
Restart=on-failure
RestartSec=10
StandardOutput=journal
StandardError=journal
SyslogIdentifier={{ spring_app_name }}

[Install]
WantedBy=multi-user.target
```

### Handler 정의

```yaml
# roles/spring-app/handlers/main.yml
---
- name: reload systemd
  systemd:
    daemon_reload: yes

- name: restart spring-app
  systemd:
    name: "{{ spring_app_name }}"
    state: restarted
```

### 최상위 Playbook

```yaml
# site.yml
---
- name: 웹 서버 기본 구성
  hosts: webservers
  become: yes
  roles:
    - common
    - spring-app

  post_tasks:
    - name: 헬스체크 엔드포인트 확인
      uri:
        url: "http://localhost:{{ spring_app_port }}/actuator/health"
        method: GET
        status_code: 200
      retries: 5
      delay: 10
      register: health_result
      until: health_result.status == 200
```

### 실행 명령어

```bash
# 문법 검사
ansible-playbook site.yml --syntax-check

# Dry-run (실제 변경 없이 미리 확인)
ansible-playbook site.yml --check --diff

# 특정 태그만 실행
ansible-playbook site.yml --tags "spring-app"

# 특정 호스트만 대상으로
ansible-playbook site.yml --limit web01

# Vault로 암호화된 변수 사용 시
ansible-playbook site.yml --ask-vault-pass
```

## 주의사항 및 트레이드오프

### 시크릿 관리: Ansible Vault

데이터베이스 비밀번호, API 키 같은 민감 정보는 반드시 **Ansible Vault**로 암호화해야 합니다. Git에 평문으로 커밋하는 실수는 치명적입니다.

```bash
# 변수 파일 암호화
ansible-vault encrypt group_vars/production/secrets.yml

# 특정 값만 암호화하여 인라인 삽입
ansible-vault encrypt_string 'my_secret_password' --name 'db_password'
```

CI/CD 파이프라인에서는 Vault 패스워드를 환경 변수나 파일로 주입하고, 해당 파일은 `.gitignore`에 등록해야 합니다.

### 멱등성 깨짐 주의

`shell`이나 `command` 모듈은 항상 `changed` 상태를 반환하여 멱등성을 깨뜨립니다. 가능하면 전용 모듈(apt, copy, template, systemd 등)을 사용하고, 불가피하게 `shell`을 써야 한다면 `creates` 옵션이나 `when` 조건을 활용하세요.

```yaml
# 나쁜 예
- shell: mkdir -p /opt/myapp

# 좋은 예
- file:
    path: /opt/myapp
    state: directory
```

### 실행 속도

Ansible은 태스크를 순차적으로 실행하기 때문에 대규모 인프라에서는 느릴 수 있습니다. `forks` 값을 조정하거나(기본값 5), `async`와 `poll`을 활용한 비동기 실행을 고려하세요. 또한 `ansible.cfg`의 `pipelining = True` 옵션은 SSH 연결 횟수를 줄여 실행 속도를 크게 개선합니다.

### Terraform과의 역할 분리

Terraform이 인프라 *프로비저닝*(서버를 만드는 것)을 담당한다면, Ansible은 *구성 관리*(만들어진 서버를 설정하는 것)를 담당합니다. 두 도구를 명확히 분리하여 사용하는 것이 권장됩니다. Terraform의 `null_resource`나 `local-exec`으로 Ansible을 호출하는 패턴으로 연동할 수 있습니다.

### 상태 관리의 부재

Terraform과 달리 Ansible은 현재 인프라 상태를 저장하지 않습니다. 이전에 생성한 리소스를 삭제하거나 롤백하는 작업은 직접 Playbook을 작성해야 합니다. 상태 추적이 중요한 작업은 Terraform이 더 적합합니다.

## 정리

Ansible은 완만한 학습 곡선과 에이전트리스 아키텍처 덕분에 기존 인프라에 즉시 도입하기 좋은 도구입니다. 다음 원칙을 기억하면서 사용하면 효과적입니다.

| 원칙 | 실천 방법 |
|------|-----------|
| **코드로서의 인프라** | 모든 Playbook과 Role을 Git으로 버전 관리 |
| **멱등성 유지** | shell/command 대신 전용 모듈 우선 사용 |
| **역할 분리** | Role 단위로 기능을 분리하여 재사용성 확보 |
| **시크릿 보호** | Ansible Vault 또는 외부 시크릿 관리 도구 연동 |
| **검증 습관화** | `--check --diff` 옵션으로 변경 사항을 항상 미리 확인 |

서버 한 대를 손으로 설정하는 시간이 아깝지 않더라도, 그 작업을 Ansible로 작성해두면 열 번째 서버부터는 비용이 0에 수렴합니다. "나중에 자동화해야지"라고 미루기보다, 지금 당장 Playbook 한 줄부터 시작해보세요.
