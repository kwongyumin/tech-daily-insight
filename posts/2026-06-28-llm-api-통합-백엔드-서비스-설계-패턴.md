# LLM API 통합 백엔드 서비스 설계 패턴

## 개요

ChatGPT, Claude, Gemini 등 대형 언어 모델(LLM) API가 실무 서비스에 본격적으로 통합되면서, 기존 REST API 연동과는 다른 차원의 설계 고민이 필요해졌다. LLM API는 응답 지연이 수 초~수십 초에 달하고, 토큰 기반 과금 모델을 사용하며, 스트리밍 응답·프롬프트 버전 관리·멀티 프로바이더 전환 등 일반적인 외부 API 연동에서는 접하기 어려운 요구사항을 동반한다.

이 글에서는 실무에서 LLM API를 백엔드 서비스에 안정적으로 통합하기 위한 핵심 설계 패턴들을 소개한다. Spring Boot 기반 예제를 중심으로 다루지만, 패턴 자체는 언어에 무관하게 적용 가능하다.

---

## 핵심 개념

### 1. Provider Abstraction (프로바이더 추상화)

LLM 시장은 아직 표준화가 덜 된 상태다. OpenAI, Anthropic, Google 등 각 프로바이더는 API 스펙이 다르고, 비용·성능·특정 태스크에 대한 적합도도 다르다. 특정 벤더에 락인(lock-in)되지 않으려면 **추상화 레이어**를 통해 프로바이더를 교체 가능하게 설계해야 한다.

### 2. Prompt Management (프롬프트 관리)

프롬프트는 코드와 같다. 버전 관리, 테스트, 배포 파이프라인이 필요하다. 프롬프트를 소스 코드에 하드코딩하면 변경 시마다 재배포가 필요하고, A/B 테스트도 불가능해진다.

### 3. Streaming & Async 처리

LLM 응답의 TTFB(Time to First Byte)는 짧지만 전체 응답 시간은 길다. 사용자 경험을 위해 **SSE(Server-Sent Events)** 또는 **WebSocket** 기반 스트리밍을 적극 활용해야 한다.

### 4. Cost Control & Observability

토큰 사용량은 곧 비용이다. 요청별 토큰 사용량 추적, 사용자별 할당량 관리, 캐싱 전략이 필요하다.

## 실전 예제

### 프로바이더 추상화 레이어 설계

```java
// LLM 프로바이더 공통 인터페이스
public interface LlmProvider {
    Mono<LlmResponse> complete(LlmRequest request);
    Flux<String> streamComplete(LlmRequest request);
    String getProviderName();
}

// 공통 요청/응답 모델
@Builder
@Getter
public class LlmRequest {
    private String model;
    private List<Message> messages;
    private Integer maxTokens;
    private Double temperature;
    private Map<String, Object> metadata;
}

@Builder
@Getter
public class LlmResponse {
    private String content;
    private int promptTokens;
    private int completionTokens;
    private String finishReason;
    private String provider;
}
```

```java
// OpenAI 구현체
@Component
@Slf4j
public class OpenAiProvider implements LlmProvider {

    private final OpenAiClient openAiClient;

    @Override
    public Mono<LlmResponse> complete(LlmRequest request) {
        return openAiClient.chatCompletion(toOpenAiRequest(request))
            .map(this::toCommonResponse)
            .doOnError(e -> log.error("[OpenAI] completion failed", e));
    }

    @Override
    public Flux<String> streamComplete(LlmRequest request) {
        return openAiClient.streamChatCompletion(toOpenAiRequest(request))
            .mapNotNull(chunk -> chunk.getChoices().get(0).getDelta().getContent());
    }

    @Override
    public String getProviderName() { return "openai"; }
}

// 프로바이더 라우터
@Service
@RequiredArgsConstructor
public class LlmRouter {

    private final Map<String, LlmProvider> providers;

    public LlmProvider resolve(String providerName) {
        return Optional.ofNullable(providers.get(providerName))
            .orElseThrow(() -> new UnsupportedProviderException(providerName));
    }
}
```

### 프롬프트 관리 시스템

프롬프트를 DB에 저장하고, 버전 관리와 A/B 테스트를 지원하는 구조다.

```java
@Entity
@Table(name = "prompt_templates")
@Getter
@Builder
public class PromptTemplate {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String templateKey;   // 예: "customer-support-v1"
    private String version;
    private String systemPrompt;
    private String userPromptTemplate;  // Mustache/Thymeleaf 템플릿
    private boolean active;

    @CreationTimestamp
    private LocalDateTime createdAt;
}
```

```java
@Service
@RequiredArgsConstructor
@Slf4j
public class PromptService {

    private final PromptTemplateRepository templateRepo;
    private final TemplateEngine templateEngine; // Thymeleaf

    // 캐싱으로 DB 조회 최소화
    @Cacheable(value = "promptTemplates", key = "#templateKey")
    public PromptTemplate getActiveTemplate(String templateKey) {
        return templateRepo.findByTemplateKeyAndActiveTrue(templateKey)
            .orElseThrow(() -> new PromptNotFoundException(templateKey));
    }

    public String renderUserPrompt(String templateKey, Map<String, Object> variables) {
        PromptTemplate template = getActiveTemplate(templateKey);
        Context context = new Context();
        context.setVariables(variables);
        return templateEngine.process(template.getUserPromptTemplate(), context);
    }
}
```

### SSE 기반 스트리밍 응답

```java
@RestController
@RequestMapping("/api/v1/llm")
@RequiredArgsConstructor
public class LlmStreamController {

    private final LlmRouter llmRouter;
    private final PromptService promptService;
    private final UsageTracker usageTracker;

    @PostMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<ServerSentEvent<String>> streamChat(
        @RequestBody ChatRequest request,
        @AuthenticationPrincipal UserPrincipal user
    ) {
        return usageTracker.checkQuota(user.getId())
            .then(Mono.fromCallable(() -> buildLlmRequest(request)))
            .flatMapMany(llmRequest -> 
                llmRouter.resolve(request.getProvider())
                         .streamComplete(llmRequest)
            )
            .map(token -> ServerSentEvent.<String>builder()
                .data(token)
                .build()
            )
            .concatWith(Flux.just(
                ServerSentEvent.<String>builder()
                    .event("done")
                    .data("[DONE]")
                    .build()
            ))
            .doOnComplete(() -> usageTracker.recordUsage(user.getId(), request))
            .onErrorResume(QuotaExceededException.class, e ->
                Flux.just(ServerSentEvent.<String>builder()
                    .event("error")
                    .data("quota_exceeded")
                    .build())
            );
    }
}
```

### 비용 추적 및 캐싱 레이어

동일한 요청에 대한 LLM 호출을 캐싱하면 비용을 대폭 줄일 수 있다. 입력 프롬프트의 해시를 캐시 키로 활용한다.

```java
@Service
@RequiredArgsConstructor
@Slf4j
public class CachingLlmService {

    private final LlmRouter llmRouter;
    private final RedisTemplate<String, LlmResponse> redisTemplate;
    private final UsageRepository usageRepository;

    private static final Duration CACHE_TTL = Duration.ofHours(24);

    public Mono<LlmResponse> completeWithCache(LlmRequest request, String userId) {
        String cacheKey = buildCacheKey(request);

        // 캐시 히트 확인
        LlmResponse cached = redisTemplate.opsForValue().get(cacheKey);
        if (cached != null) {
            log.debug("LLM cache hit for key: {}", cacheKey);
            recordUsage(userId, cached, true);
            return Mono.just(cached);
        }

        // 캐시 미스 → 실제 LLM 호출
        return llmRouter.resolve(request.getProvider())
            .complete(request)
            .doOnNext(response -> {
                redisTemplate.opsForValue().set(cacheKey, response, CACHE_TTL);
                recordUsage(userId, response, false);
                log.info("LLM call completed. tokens={}/{}",
                    response.getPromptTokens(), response.getCompletionTokens());
            });
    }

    private String buildCacheKey(LlmRequest request) {
        String content = request.getModel() + ":" + request.getMessages().toString();
        return "llm:cache:" + DigestUtils.sha256Hex(content);
    }

    private void recordUsage(String userId, LlmResponse response, boolean cached) {
        usageRepository.save(UsageRecord.builder()
            .userId(userId)
            .provider(response.getProvider())
            .promptTokens(response.getPromptTokens())
            .completionTokens(response.getCompletionTokens())
            .cached(cached)
            .recordedAt(LocalDateTime.now())
            .build());
    }
}
```

### Fallback & Retry 패턴

LLM API는 Rate Limit, 일시적 장애가 잦다. Resilience4j를 활용한 서킷브레이커와 폴백 체인을 구성하자.

```java
@Service
@RequiredArgsConstructor
public class ResilientLlmService {

    private final OpenAiProvider openAiProvider;
    private final AnthropicProvider anthropicProvider;
    private final CircuitBreakerRegistry circuitBreakerRegistry;

    public Mono<LlmResponse> completeWithFallback(LlmRequest request) {
        CircuitBreaker openAiCb = circuitBreakerRegistry.circuitBreaker("openai");

        return Mono.defer(() -> openAiProvider.complete(request))
            .transform(CircuitBreakerOperator.of(openAiCb))
            .retryWhen(Retry.backoff(2, Duration.ofSeconds(1))
                .filter(this::isRetryable))
            .onErrorResume(e -> {
                log.warn("OpenAI failed, falling back to Anthropic: {}", e.getMessage());
                return anthropicProvider.complete(
                    request.toBuilder().model("claude-3-haiku-20240307").build()
                );
            });
    }

    private boolean isRetryable(Throwable e) {
        return e instanceof RateLimitException || e instanceof ServiceUnavailableException;
    }
}
```

## 주의사항 및 트레이드오프

### ⚠️ 프롬프트 인젝션 방어

사용자 입력이 프롬프트에 직접 삽입될 경우, 악의적인 사용자가 시스템 프롬프트를 무력화하는 **프롬프트 인젝션** 공격이 가능하다. 사용자 입력을 항상 `user` 역할의 별도 메시지로 분리하고, 입력 길이 제한 및 패턴 필터링을 적용해야 한다.

### ⚠️ 스트리밍과 에러 처리

SSE 스트리밍 중간에 오류가 발생하면 클라이언트가 오류를 감지하기 어렵다. 반드시 `event: error` 타입의 명시적 에러 이벤트를 전송하고, 클라이언트 측에서 이를 처리하는 로직을 구현해야 한다.

### ⚠️ 캐싱의 함정

LLM 응답 캐싱은 비용 절감에 효과적이지만, **창의적 응답이 필요한 태스크**(예: 글쓰기 도우미)나 **시간에 민감한 정보**를 다룰 때는 캐싱이 오히려 품질 저하를 유발한다. 태스크 유형별로 캐싱 정책을 다르게 적용하라.

### ⚠️ 토큰 폭발과 컨텍스트 관리

대화형 서비스에서 히스토리를 그대로 쌓으면 컨텍스트 윈도우 초과 및 비용 폭발이 발생한다. **슬라이딩 윈도우** 방식으로 최근 N개 메시지만 유지하거나, 오래된 대화를 **요약(summarization)**해서 압축하는 전략이 필요하다.

| 전략 | 비용 | 컨텍스트 보존 | 구현 복잡도 |
|------|------|--------------|------------|
| 슬라이딩 윈도우 | 낮음 | 낮음 | 낮음 |
| 요약 압축 | 중간 | 높음 | 높음 |
| 벡터 검색 기반 RAG | 중간 | 높음 | 매우 높음 |

### ⚠️ Observability 투자 필수

LLM 서비스는 블랙박스 특성이 강하다. 프롬프트 버전, 토큰 사용량, 응답 품질 피드백(thumbs up/down), 레이턴시를 모두 로깅하고, Grafana/Datadog 등으로 대시보드를 구성해야 품질 개선이 가능하다.

## 정리

LLM API 통합은 단순한 HTTP 클라이언트 연동이 아니다. 다음 핵심 패턴들을 기억하자.

1. **Provider Abstraction**: 벤더 락인을 피하고, 비용·성능 최적화를 위한 멀티 프로바이더 전략을 가능하게 한다.
2. **Prompt as Code**: 프롬프트를 DB에서 관리하고, 버전 관리와 A/B 테스트를 적용한다.
3. **Streaming First**: 긴 응답 시간을 UX 관점에서 극복하기 위해 SSE 스트리밍을 기본 설계로 삼는다.
4. **Semantic Caching**: 동일하거나 유사한 요청에 대한 캐싱으로 비용을 절감한다.
5. **Resilience**: 서킷브레이커와 프로바이더 폴백 체인으로 가용성을 높인다.
6. **Observability**: 토큰 사용량, 레이턴시, 품질 피드백을 빠짐없이 추적한다.

LLM 생태계는 빠르게 변하고 있다. 특정 프로바이더나 모델에 과도하게 결합된 코드를 작성하지 않는 것이 지속 가능한 설계의 출발점이다. 추상화 레이어에 투자한 시간은 반드시 돌아온다.
