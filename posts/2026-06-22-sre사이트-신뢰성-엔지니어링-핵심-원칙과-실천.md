# SRE(사이트 신뢰성 엔지니어링) 핵심 원칙과 실천

## 개요

구글이 2003년 처음 도입한 SRE(Site Reliability Engineering)는 이제 대규모 서비스를 운영하는 조직이라면 반드시 고려해야 할 엔지니어링 문화로 자리잡았다. SRE는 단순한 운영(Ops) 역할이 아니라, **소프트웨어 엔지니어링 관점으로 시스템 안정성 문제를 해결**하는 방법론이다.

"운영팀에 던지고 끝"이 아니라, 개발자가 직접 신뢰성을 설계하고 측정하고 개선하는 것이 SRE의 핵심이다. 이 글에서는 SRE의 핵심 원칙을 살펴보고, 실무에서 바로 적용할 수 있는 구체적인 예제와 함께 트레이드오프를 정직하게 짚어보겠다.

---

## 핵심 개념

### 1. SLI / SLO / SLA — 신뢰성의 언어

SRE를 도입할 때 가장 먼저 정의해야 하는 것이 **서비스 수준 지표(Service Level Indicators)**다.

| 용어 | 의미 | 예시 |
|------|------|------|
| **SLI** | 신뢰성을 측정하는 지표 | 요청 성공률, p99 레이턴시 |
| **SLO** | SLI에 대한 목표값 | 성공률 99.9%, p99 < 200ms |
| **SLA** | 외부와 계약된 보장 수준 | 99.5% 미달 시 환불 |

SLO는 SLA보다 항상 엄격하게 설정해야 한다. SLA를 위반하기 전에 내부적으로 먼저 경보를 울려야 하기 때문이다.

### 2. 에러 버짓(Error Budget)

에러 버짓은 SRE 철학의 가장 독창적인 개념이다. **"100% 신뢰성은 목표가 아니다"** 라는 전제에서 출발한다.

- SLO가 99.9%라면, 한 달 기준 약 **43.8분**의 다운타임이 허용된다.
- 이 허용된 오류 공간을 "예산"처럼 관리한다.
- 에러 버짓이 남아있으면 → 빠른 배포, 실험, 기능 개발 가속
- 에러 버짓이 소진되면 → 배포 동결, 안정화 작업 우선

이 구조 덕분에 개발팀과 운영팀이 **공통의 언어**로 신뢰성 vs 속도의 균형을 협상할 수 있다.

### 3. 토일(Toil) 제거

SRE는 반복적이고 자동화 가능한 수작업, 즉 **토일(Toil)**을 줄이는 것을 핵심 목표로 삼는다. 구글은 SRE 엔지니어가 토일에 50% 이상의 시간을 쓰지 않도록 조직적으로 제한한다.

토일의 특징:
- 수동적(Manual)
- 반복적(Repetitive)
- 자동화 가능(Automatable)
- 전술적 가치만 있음 (장기적 개선 없음)

### 4. 포스트모텀(Postmortem) 문화

장애가 발생했을 때 비난 없는(Blameless) 포스트모텀을 통해 **시스템 개선**에 집중한다. 개인의 실수보다 시스템과 프로세스의 취약점을 찾는 것이 목적이다.

## 실전 예제

### 예제 1: Spring Boot + Micrometer로 SLI 측정하기

가장 실용적인 출발점은 현재 서비스의 SLI를 측정하는 것이다. Spring Boot + Micrometer + Prometheus 조합을 활용하면 빠르게 구현할 수 있다.

```java
// build.gradle
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-actuator'
    implementation 'io.micrometer:micrometer-registry-prometheus'
}
```

```java
@RestController
@RequiredArgsConstructor
public class OrderController {

    private final MeterRegistry meterRegistry;
    private final OrderService orderService;

    @PostMapping("/orders")
    public ResponseEntity<OrderResponse> createOrder(@RequestBody OrderRequest request) {
        Timer.Sample sample = Timer.start(meterRegistry);
        String status = "success";

        try {
            OrderResponse response = orderService.create(request);
            return ResponseEntity.ok(response);
        } catch (BusinessException e) {
            status = "client_error";
            return ResponseEntity.badRequest().build();
        } catch (Exception e) {
            status = "server_error";
            // SLI 관점에서 5xx만 실패로 카운트
            meterRegistry.counter("api.errors.total",
                "endpoint", "/orders",
                "error_type", "server_error"
            ).increment();
            throw e;
        } finally {
            sample.stop(Timer.builder("api.request.duration")
                .tag("endpoint", "/orders")
                .tag("status", status)
                .publishPercentiles(0.5, 0.95, 0.99)
                .register(meterRegistry));
        }
    }
}
```

```java
// SLI 계산을 위한 커스텀 메트릭 서비스
@Service
@RequiredArgsConstructor
public class SliMetricsService {

    private final MeterRegistry meterRegistry;

    // 성공률 SLI: (총 요청 - 5xx 에러) / 총 요청
    public void recordRequest(String endpoint, int statusCode, long durationMs) {
        boolean isSuccess = statusCode < 500;

        meterRegistry.counter("sli.requests.total",
            "endpoint", endpoint,
            "success", String.valueOf(isSuccess)
        ).increment();

        // 레이턴시 SLI
        meterRegistry.timer("sli.request.latency",
            "endpoint", endpoint
        ).record(durationMs, TimeUnit.MILLISECONDS);
    }
}
```

### 예제 2: Prometheus 쿼리로 에러 버짓 계산

```yaml
# prometheus/rules/slo.yml
groups:
  - name: slo_rules
    interval: 30s
    rules:
      # SLI: 최근 1시간 성공률
      - record: job:api_success_rate:1h
        expr: |
          sum(rate(sli_requests_total{success="true"}[1h]))
          /
          sum(rate(sli_requests_total[1h]))

      # 에러 버짓 소진율 (SLO = 99.9%)
      - record: job:error_budget_burn_rate:1h
        expr: |
          (1 - job:api_success_rate:1h) / (1 - 0.999)

      # 에러 버짓 잔여량 (월 기준)
      - record: job:error_budget_remaining:30d
        expr: |
          1 - (
            sum(increase(sli_requests_total{success="false"}[30d]))
            /
            sum(increase(sli_requests_total[30d]))
          ) / (1 - 0.999)
```

### 예제 3: 다중 번 레이트 알림 (Multi-window Alert)

단순 임계값 알림보다 **에러 버짓 소진 속도**를 기반으로 알림을 설계하면 노이즈를 크게 줄일 수 있다.

```yaml
# alerting rules
groups:
  - name: error_budget_alerts
    rules:
      # 🔴 심각: 짧은 시간에 버짓을 빠르게 소진 중 (1시간 내 14배 소진율)
      - alert: ErrorBudgetBurnRateCritical
        expr: |
          job:error_budget_burn_rate:1h > 14
          AND
          job:error_budget_burn_rate:5m > 14
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "에러 버짓 급격 소진 - 즉시 대응 필요"
          description: "현재 소진율로는 1시간 내 월 버짓의 14% 소모"

      # 🟡 경고: 느리지만 지속적인 소진 (6시간 기준 3배 소진율)
      - alert: ErrorBudgetBurnRateWarning
        expr: |
          job:error_budget_burn_rate:6h > 3
          AND
          job:error_budget_burn_rate:30m > 3
        for: 15m
        labels:
          severity: warning
        annotations:
          summary: "에러 버짓 지속 소진 중"
          description: "현재 추세 유지 시 월말 SLO 위반 가능"
```

## 주의사항 및 트레이드오프

### ⚠️ SLO는 너무 빡빡하게 잡지 마라

99.99% SLO를 설정하면 월 허용 다운타임이 **4.3분**에 불과하다. 이는 카나리 배포 하나도 제대로 못 하는 수준이다. 처음에는 현재 실제 측정값보다 약간 느슨하게 잡고, 분기마다 점진적으로 조정하는 것이 현실적이다.

### ⚠️ 모든 지표를 SLI로 만들지 마라

대시보드에 지표가 100개 있어도 정작 중요한 신호가 묻힌다. SLI는 **사용자가 체감하는 신뢰성**에 직결된 것만 선별해야 한다. 일반적으로 서비스당 3~5개면 충분하다.

### ⚠️ 에러 버짓 정책은 조직 합의가 필수

에러 버짓이 소진됐을 때 배포를 동결하는 정책은, 개발팀·제품팀·경영진이 사전에 합의하지 않으면 실제로 작동하지 않는다. 기술 도입 전에 **조직 문화 세팅**이 우선이다.

### ⚠️ 포스트모텀 피로를 조심하라

장애마다 포스트모텀을 강제하면 형식적인 문서 작성으로 전락한다. **SLO 위반이 발생하거나 사용자 영향이 큰 장애**에 한해 포스트모텀을 의무화하고, 소규모 이슈는 간소화된 형식으로 처리하는 것이 지속 가능하다.

### 트레이드오프 요약

| 결정 | 장점 | 단점 |
|------|------|------|
| SLO를 엄격하게 | 높은 신뢰성 | 혁신 속도 저하 |
| SLO를 느슨하게 | 빠른 배포 | SLA 위반 위험 |
| 토일 자동화 투자 | 장기 생산성 향상 | 단기 개발 리소스 소모 |
| 온콜 순환 확대 | 맥락 공유, 공정성 | 엔지니어 부담 증가 |

## 정리

SRE는 단순히 Prometheus를 설치하고 대시보드를 만드는 것이 아니다. **신뢰성을 측정 가능한 엔지니어링 문제로 전환**하는 사고방식의 변화다.

실무에서 SRE를 도입할 때 권장하는 순서는 다음과 같다:

1. **현재 상태 측정**: 아무것도 없다면 SLI 메트릭 수집부터 시작
2. **SLO 초안 설정**: 현실적인 숫자로 시작, 이해관계자와 합의
3. **알림 재설계**: 에러 버짓 소진율 기반 알림으로 전환
4. **토일 목록화**: 매주 반복하는 수작업을 리스트업하고 우선순위 정해 자동화
5. **포스트모텀 문화**: 첫 장애 때 비난 없는 포스트모텀을 실제로 실천

SRE의 궁극적인 목적은 **개발자가 두려움 없이 빠르게 배포하면서도 안정적인 서비스를 운영**할 수 있는 환경을 만드는 것이다. 에러 버짓이라는 개념이 그 균형점을 제공한다. 오늘 당장 여러분 서비스의 SLI 하나를 정의하는 것부터 시작해보자.
