# 크로스체인 브리지 동작 원리와 보안 위험

## 개요

멀티체인 생태계가 성숙해지면서 이더리움, BNB Chain, Solana, Polygon 등 서로 다른 블록체인 네트워크 간에 자산을 이동시키는 **크로스체인 브리지(Cross-Chain Bridge)** 의 수요가 폭발적으로 증가했다. 그러나 동시에 Ronin Bridge($625M), Wormhole($320M), Nomad($190M) 등 역사상 가장 큰 규모의 해킹 사건들도 브리지에서 발생했다.

브리지는 단순히 "토큰을 옮기는 도구"가 아니다. 서로 다른 합의 메커니즘, 파이널리티 보장 수준, 스마트 컨트랙트 환경을 가진 체인들을 연결하는 복잡한 인프라다. 이 글에서는 브리지의 핵심 동작 원리를 분석하고, 실제 코드 수준에서 어떤 보안 취약점이 발생하는지, 그리고 설계 시 반드시 고려해야 할 트레이드오프를 다룬다.

---

## 핵심 개념

### 1. Lock-and-Mint 방식

가장 일반적인 브리지 패턴이다. 소스 체인에서 자산을 **잠그고(Lock)**, 목적지 체인에서 **래핑된 토큰(Wrapped Token)을 발행(Mint)** 한다.

```
[User] → Lock ETH on Ethereum → [Bridge Contract]
                                      ↓ (Relay/Oracle)
                               [Bridge Contract] → Mint wETH on BNB Chain → [User]
```

반대 방향은 목적지 체인에서 wETH를 **소각(Burn)** 하고, 소스 체인에서 ETH를 **언락(Unlock)** 한다.

### 2. 릴레이어(Relayer)와 검증 모델

브리지의 핵심은 **체인 A의 이벤트를 체인 B가 어떻게 신뢰하는가**다. 이 검증 방식에 따라 브리지의 보안 모델이 결정된다.

| 검증 방식 | 신뢰 모델 | 예시 |
|---|---|---|
| 중앙화 멀티시그 | 서명자 집합 신뢰 | Ronin Bridge |
| 낙관적 검증 | 사기 증명(Fraud Proof) | Nomad |
| 라이트 클라이언트 | 수학적 증명 | IBC, Stargate |
| ZK 증명 | 영지식 증명 | zkBridge, Succinct |

### 3. 파이널리티(Finality) 문제

이더리움은 약 12~15분 후 파이널리티가 확정되며, 비트코인은 6컨펌(~1시간)이 일반적이다. 브리지가 파이널리티를 충분히 기다리지 않으면 **체인 재구성(Reorg)** 공격에 노출될 수 있다.

## 실전 예제

### Lock 컨트랙트 구현 (Solidity)

소스 체인에서 ETH를 잠그고 이벤트를 발생시키는 기본 구조다.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.19;

import "@openzeppelin/contracts/security/ReentrancyGuard.sol";
import "@openzeppelin/contracts/security/Pausable.sol";
import "@openzeppelin/contracts/access/AccessControl.sol";

contract SourceBridge is ReentrancyGuard, Pausable, AccessControl {
    bytes32 public constant RELAYER_ROLE = keccak256("RELAYER_ROLE");
    
    // 체인별 최소 컨펌 수
    mapping(uint256 => uint256) public minConfirmations;
    
    // 이중 처리 방지: 처리된 nonce 추적
    mapping(bytes32 => bool) public processedNonces;
    
    // 일일 출금 한도 (TVL 보호)
    uint256 public dailyLimit;
    uint256 public dailyVolume;
    uint256 public lastResetTime;
    
    event TokensLocked(
        address indexed sender,
        uint256 indexed destChainId,
        address destAddress,
        uint256 amount,
        uint256 nonce,
        bytes32 transferId
    );
    
    constructor(uint256 _dailyLimit) {
        _grantRole(DEFAULT_ADMIN_ROLE, msg.sender);
        dailyLimit = _dailyLimit;
        lastResetTime = block.timestamp;
    }
    
    function lockETH(
        uint256 destChainId,
        address destAddress
    ) external payable nonReentrant whenNotPaused {
        require(msg.value > 0, "Amount must be > 0");
        require(destAddress != address(0), "Invalid dest address");
        require(minConfirmations[destChainId] > 0, "Unsupported chain");
        
        // 일일 한도 체크 및 초기화
        _checkAndResetDailyLimit();
        require(dailyVolume + msg.value <= dailyLimit, "Daily limit exceeded");
        dailyVolume += msg.value;
        
        uint256 nonce = _generateNonce(msg.sender, destChainId);
        bytes32 transferId = keccak256(
            abi.encodePacked(msg.sender, destChainId, destAddress, msg.value, nonce)
        );
        
        emit TokensLocked(
            msg.sender,
            destChainId,
            destAddress,
            msg.value,
            nonce,
            transferId
        );
    }
    
    function _checkAndResetDailyLimit() internal {
        if (block.timestamp >= lastResetTime + 1 days) {
            dailyVolume = 0;
            lastResetTime = block.timestamp;
        }
    }
    
    function _generateNonce(address sender, uint256 destChainId) 
        internal view returns (uint256) 
    {
        return uint256(keccak256(
            abi.encodePacked(sender, destChainId, block.timestamp, block.prevrandao)
        ));
    }
    
    // 긴급 일시정지 (보안 이슈 발생 시)
    function emergencyPause() external onlyRole(DEFAULT_ADMIN_ROLE) {
        _pause();
    }
}
```

### Mint 컨트랙트 구현 (목적지 체인)

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.19;

import "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import "@openzeppelin/contracts/security/ReentrancyGuard.sol";
import "@openzeppelin/contracts/access/AccessControl.sol";

contract DestinationBridge is ERC20, ReentrancyGuard, AccessControl {
    bytes32 public constant RELAYER_ROLE = keccak256("RELAYER_ROLE");
    
    // 재생 공격(Replay Attack) 방지
    mapping(bytes32 => bool) public executedTransfers;
    
    // 멀티시그 임계값
    uint256 public threshold;
    mapping(bytes32 => mapping(address => bool)) public signatures;
    mapping(bytes32 => uint256) public signatureCount;
    
    event TokensMinted(address indexed recipient, uint256 amount, bytes32 transferId);
    event SignatureCollected(bytes32 indexed transferId, address relayer);
    
    constructor(uint256 _threshold) ERC20("Wrapped ETH", "wETH") {
        _grantRole(DEFAULT_ADMIN_ROLE, msg.sender);
        threshold = _threshold;
    }
    
    // 릴레이어가 서명 제출
    function submitSignature(bytes32 transferId) 
        external 
        onlyRole(RELAYER_ROLE) 
    {
        require(!executedTransfers[transferId], "Already executed");
        require(!signatures[transferId][msg.sender], "Already signed");
        
        signatures[transferId][msg.sender] = true;
        signatureCount[transferId]++;
        
        emit SignatureCollected(transferId, msg.sender);
    }
    
    // 임계값 도달 시 민팅 실행
    function executeMint(
        address recipient,
        uint256 amount,
        bytes32 transferId,
        uint256 srcChainId,
        uint256 nonce
    ) external nonReentrant onlyRole(RELAYER_ROLE) {
        // transferId 검증
        bytes32 computedId = keccak256(
            abi.encodePacked(srcChainId, recipient, amount, nonce)
        );
        require(computedId == transferId, "Invalid transferId");
        require(!executedTransfers[transferId], "Already executed");
        require(signatureCount[transferId] >= threshold, "Insufficient signatures");
        
        executedTransfers[transferId] = true;
        _mint(recipient, amount);
        
        emit TokensMinted(recipient, amount, transferId);
    }
}
```

### 릴레이어 서비스 (Java/Spring)

오프체인 릴레이어는 소스 체인 이벤트를 모니터링하고 목적지 체인에 트랜잭션을 제출한다.

```java
@Service
@Slf4j
public class BridgeRelayerService {

    private final Web3j sourceChain;
    private final Web3j destChain;
    private final BridgeRepository bridgeRepository;
    
    // 재시도 로직: 지수 백오프 적용
    @Retryable(
        value = {Exception.class},
        maxAttempts = 5,
        backoff = @Backoff(delay = 1000, multiplier = 2)
    )
    public void processLockEvent(TokensLockedEventResponse event) {
        String transferId = Numeric.toHexString(event.transferId);
        
        // 이미 처리된 이벤트인지 확인 (멱등성 보장)
        if (bridgeRepository.existsByTransferId(transferId)) {
            log.warn("Transfer {} already processed, skipping", transferId);
            return;
        }
        
        // 소스 체인 파이널리티 확인
        long currentBlock = sourceChain.ethBlockNumber().send().getBlockNumber().longValue();
        long eventBlock = event.log.getBlockNumber().longValue();
        long requiredConfirmations = getRequiredConfirmations(event.destChainId.longValue());
        
        if (currentBlock - eventBlock < requiredConfirmations) {
            throw new InsufficientConfirmationsException(
                String.format("Need %d confirmations, have %d",
                    requiredConfirmations, currentBlock - eventBlock)
            );
        }
        
        // DB에 pending 상태로 저장
        BridgeTransfer transfer = BridgeTransfer.builder()
            .transferId(transferId)
            .sender(event.sender)
            .destAddress(event.destAddress)
            .amount(event.amount)
            .status(TransferStatus.PENDING)
            .srcTxHash(event.log.getTransactionHash())
            .build();
        bridgeRepository.save(transfer);
        
        // 서명 제출 및 민팅 실행
        submitSignatureAndMint(transfer);
    }
    
    private long getRequiredConfirmations(long chainId) {
        // 체인별 파이널리티 특성에 따른 컨펌 수
        return switch ((int) chainId) {
            case 1 -> 32;     // Ethereum: ~6.4분
            case 56 -> 15;    // BNB Chain: ~45초
            case 137 -> 256;  // Polygon: 재구성 위험이 높아 더 많은 컨펌 필요
            default -> throw new UnsupportedChainException("Chain " + chainId);
        };
    }
}
```

## 주의사항 및 트레이드오프

### 1. 멀티시그의 함정 — Ronin 해킹 사례

Ronin Bridge는 9개 검증자 노드 중 5개의 서명이면 자산 출금이 가능한 구조였다. 공격자는 Sky Mavis가 보유한 4개 노드와 Axie DAO 노드 1개를 장악해 임계값을 넘겼다. **키 분산이 실제로 분산되어 있는지** 정기적으로 감사해야 한다.

```
⚠️ 체크리스트:
- 검증자 키가 동일한 클라우드 제공자에 집중되어 있지 않은가?
- HSM(Hardware Security Module)을 사용하는가?
- 검증자 운영 주체가 실질적으로 독립적인가?
```

### 2. 낙관적 브리지의 사기 증명 창 — Nomad 취약점

Nomad는 메시지 검증 로직에서 `bytes32(0)`이 유효한 루트로 처리되는 버그가 있었다. 초기화 트랜잭션이 실행되자 누구나 임의의 메시지를 복사해 재생하며 자산을 탈취했다.

```solidity
// 취약한 코드 (개념적 예시)
function process(bytes memory message) public {
    bytes32 messageHash = keccak256(message);
    // confirmAt[bytes32(0)] 가 초기화 시 0이 아닌 값으로 설정되었음
    require(confirmAt[messageHash] != 0, "Not yet confirmable"); // ← 버그
    require(confirmAt[messageHash] <= block.timestamp, "Too early");
    // ...
}

// 수정된 코드
function process(bytes memory message) public {
    bytes32 messageHash = keccak256(message);
    require(messageHash != bytes32(0), "Invalid message hash"); // ← 추가
    require(confirmAt[messageHash] != 0, "Not confirmed");
    require(confirmAt[messageHash] <= block.timestamp, "Too early");
    // ...
}
```

### 3. 트레이드오프 정리

| 항목 | 중앙화 멀티시그 | 낙관적 검증 | ZK 증명 |
|---|---|---|---|
| 보안성 | 낮음 (키 손상 위험) | 중간 (사기 증명 창) | 높음 |
| 속도 | 빠름 (수분) | 중간 (수십 분) | 느림 (증명 생성 시간) |
| 비용 | 낮음 | 중간 | 높음 (증명 검증 가스비) |
| 구현 복잡도 | 낮음 | 중간 | 매우 높음 |

### 4. TVL 보호 전략

브리지에 잠긴 총 자산(TVL)이 곧 공격 목표가 된다. 단일 장애점을 줄이기 위한 실무 권고사항:

- **출금 속도 제한(Rate Limiting)**: 시간당/일당 최대 출금량 설정
- **대형 출금 지연**: 임계값(예: $100K) 초과 시 24시간 지연 + 알림
- **회로 차단기(Circuit Breaker)**: 이상 징후 감지 시 자동 일시정지
- **보험 풀**: Nexus Mutual 같은 온체인 보험 연동

## 정리

크로스체인 브리지는 블록체인 생태계의 필수 인프라지만, 현재까지 해킹된 금액의 상당 부분이 브리지에서 발생했다는 사실을 절대 간과해서는 안 된다.

**핵심 설계 원칙을 정리하면:**

1. **신뢰 최소화**: 가능하면 ZK 증명이나 라이트 클라이언트 기반 검증으로 이동하라
2. **파이널리티 존중**: 체인별 특성에 맞는 충분한 컨펌 수를 설정하라
3. **멱등성 보장**: 릴레이어가 같은 트랜잭션을 중복 처리하지 않도록 nonce와 transferId를 철저히 관리하라
4. **TVL 제한**: 잠길 수 있는 자산에 상한을 두어 최악의 시나리오를 제한하라
5. **비상 탈출구**: 긴급 일시정지 및 자산 복구 메커니즘을 사전에 설계하라

보안 감사는 배포 전 단 한 번으로 끝나는 것이 아니다. 브리지 로직이 변경될 때마다, 그리고 주기적으로 재감사를 받아야 하며, 버그 바운티 프로그램 운영도 강력히 권장한다. 브리지 개발은 단순한 스마트 컨트랙트 개발이 아니라, **분산 시스템 + 암호학 + 경제적 인센티브 설계**가 복합된 고난도 영역임을 항상 인지하자.
