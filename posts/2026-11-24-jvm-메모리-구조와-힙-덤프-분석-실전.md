# JVM 메모리 구조와 힙 덤프 분석 실전

## 개요

운영 환경에서 애플리케이션이 갑자기 `OutOfMemoryError`를 던지거나, GC가 과도하게 발생해 응답 지연이 생기는 상황은 백엔드 개발자라면 한 번쯤 경험해봤을 것이다. 이런 상황에서 근본 원인을 찾으려면 JVM 메모리 구조를 정확히 이해하고, 힙 덤프를 통해 실제 메모리 상태를 분석하는 능력이 필수적이다.

이 글에서는 JVM 메모리 구조의 핵심 영역을 짚어보고, 실제 힙 덤프를 생성·분석하는 실전 과정을 다룬다. 단순히 개념 설명에 그치지 않고, 실무에서 메모리 누수를 탐지하고 튜닝 포인트를 찾는 방법까지 함께 살펴본다.

## 핵심 개념: JVM 메모리 구조

### 메모리 영역 전체 그림

JVM 메모리는 크게 **힙(Heap)**, **스택(Stack)**, **메서드 영역(Method Area)**, **PC 레지스터**, **네이티브 메서드 스택**으로 구성된다. 실무에서 가장 자주 문제가 되는 영역은 힙과 메서드 영역(Metaspace)이다.

```
+---------------------------------------------------+
|                     JVM Memory                    |
|                                                   |
|  +-------------+   +--------------------------+   |
|  |    Heap     |   |     Non-Heap             |   |
|  |             |   |  +--------------------+  |   |
|  |  Young Gen  |   |  |   Metaspace        |  |   |
|  |  - Eden     |   |  +--------------------+  |   |
|  |  - S0, S1   |   |  |   Code Cache       |  |   |
|  |             |   |  +--------------------+  |   |
|  |  Old Gen    |   +--------------------------+   |
|  +-------------+                                  |
|                                                   |
|  Thread Stack (per thread)                        |
|  PC Register (per thread)                         |
+---------------------------------------------------+
```

### Young Generation vs Old Generation

힙은 **Young Generation**과 **Old Generation**으로 나뉜다.

- **Eden**: 새로 생성된 객체가 최초로 할당되는 공간
- **Survivor (S0, S1)**: Minor GC에서 살아남은 객체가 이동하는 공간. 두 개가 번갈아 사용된다.
- **Old Generation**: Survivor에서 일정 Age를 넘긴 객체가 승격(Promotion)되는 공간. Major GC(Full GC)의 대상이다.

```java
// 객체 Age 임계값 설정 (기본값: 15)
// -XX:MaxTenuringThreshold=15
```

### Metaspace

Java 8 이후 PermGen이 제거되고 **Metaspace**로 대체되었다. 클래스 메타데이터, 메서드 정보, static 변수 등이 저장된다. 기본적으로 네이티브 메모리를 사용하므로 별도로 상한을 걸지 않으면 무제한 증가할 수 있다.

```bash
# Metaspace 상한 설정 (필수)
-XX:MaxMetaspaceSize=256m
```

## 실전 예제

### 1. 힙 덤프 생성 방법

힙 덤프를 얻는 방법은 여러 가지다.

**방법 1: OOM 발생 시 자동 생성**

```bash
# JVM 옵션에 추가
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/var/log/app/heapdump.hprof
```

**방법 2: jmap으로 수동 생성**

```bash
# 프로세스 PID 확인
jps -l

# 힙 덤프 생성 (live 옵션: GC 후 살아있는 객체만 포함)
jmap -dump:format=b,file=/tmp/heapdump.hprof <PID>
jmap -dump:live,format=b,file=/tmp/heapdump_live.hprof <PID>
```

**방법 3: jcmd 활용 (권장)**

```bash
# jcmd는 jmap보다 안전하고 기능이 풍부함
jcmd <PID> GC.heap_dump /tmp/heapdump.hprof
```

**방법 4: Spring Actuator 엔드포인트 (개발/스테이징 환경)**

```yaml
# application.yml
management:
  endpoints:
    web:
      exposure:
        include: heapdump
  endpoint:
    heapdump:
      enabled: true
```

```bash
# HTTP 요청으로 힙 덤프 다운로드
curl -O http://localhost:8080/actuator/heapdump
```

### 2. 메모리 누수 시나리오 코드

실무에서 자주 발생하는 메모리 누수 패턴을 살펴보자.

**패턴 1: static 컬렉션에 계속 추가만 하는 경우**

```java
@Component
public class EventCache {
    // 위험: static 맵에 계속 쌓임, 제거 로직 없음
    private static final Map<String, List<Event>> cache = new HashMap<>();

    public void addEvent(String userId, Event event) {
        cache.computeIfAbsent(userId, k -> new ArrayList<>()).add(event);
        // 오래된 데이터를 제거하는 로직이 없다!
    }
}
```

```java
// 개선: Caffeine 캐시로 TTL 및 최대 사이즈 적용
@Bean
public Cache<String, List<Event>> eventCache() {
    return Caffeine.newBuilder()
            .maximumSize(10_000)
            .expireAfterWrite(10, TimeUnit.MINUTES)
            .build();
}
```

**패턴 2: ThreadLocal 미정리**

```java
// 위험: ThreadLocal을 정리하지 않으면 스레드 풀 환경에서 메모리 누수 발생
public class RequestContext {
    private static final ThreadLocal<UserContext> context = new ThreadLocal<>();

    public static void set(UserContext ctx) {
        context.set(ctx);
    }

    public static UserContext get() {
        return context.get();
    }

    // remove()를 호출하지 않으면 스레드가 재사용될 때 이전 데이터가 남음
}
```

```java
// 개선: 필터나 인터셉터에서 반드시 정리
@Component
public class RequestContextFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain) throws ServletException, IOException {
        try {
            RequestContext.set(extractUserContext(request));
            filterChain.doFilter(request, response);
        } finally {
            RequestContext.remove(); // 반드시 정리
        }
    }
}
```

**패턴 3: 대용량 ResultSet을 한 번에 로딩**

```java
// 위험: 수백만 건 조회 시 힙 고갈
public List<Order> getAllOrders() {
    return orderRepository.findAll(); // 전체 로딩
}
```

```java
// 개선: 페이지네이션 또는 스트리밍 처리
@Transactional(readOnly = true)
public void processAllOrders(Consumer<Order> processor) {
    try (Stream<Order> stream = orderRepository.streamAll()) {
        stream.forEach(processor);
    }
}
```

```java
// Repository 인터페이스
public interface OrderRepository extends JpaRepository<Order, Long> {
    @QueryHints(value = @QueryHint(name = HINT_FETCH_SIZE, value = "1000"))
    Stream<Order> streamAll();
}
```

### 3. 힙 덤프 분석: Eclipse MAT 활용

Eclipse Memory Analyzer Tool(MAT)은 힙 덤프 분석의 사실상 표준 도구다.

**주요 분석 포인트**

```
1. Leak Suspects Report 확인
   - MAT가 자동으로 메모리 누수 의심 지점을 리포트
   - "Problem Suspect 1" 항목부터 확인

2. Dominator Tree
   - 메모리를 가장 많이 점유하는 객체 트리 확인
   - Retained Heap이 큰 객체가 주요 용의자

3. OQL (Object Query Language)로 세부 분석
```

```sql
-- MAT OQL: 특정 클래스의 모든 인스턴스 조회
SELECT * FROM java.util.HashMap

-- 1MB 이상 차지하는 byte 배열 조회
SELECT * FROM byte[] b WHERE b.@retainedHeapSize > 1024 * 1024

-- 특정 패키지의 객체 개수와 크기 집계
SELECT classof(s).@displayName, COUNT(*), SUM(s.@retainedHeapSize)
FROM "com.example.*" s
GROUP BY classof(s).@displayName
```

**jhat으로 간단히 분석하기 (소규모 덤프)**

```bash
# 힙 덤프를 HTTP 서버로 열어 브라우저에서 확인
jhat -port 7000 /tmp/heapdump.hprof

# 브라우저에서 접속
# http://localhost:7000
```

### 4. GC 로그로 메모리 압박 사전 감지

힙 덤프 전에 GC 로그만으로도 많은 정보를 얻을 수 있다.

```bash
# Java 11+ GC 로그 설정
-Xlog:gc*:file=/var/log/app/gc.log:time,uptime,level,tags:filecount=10,filesize=50m
```

```bash
# GC Easy (https://gceasy.io) 업로드 전 간단 grep 분석
# Full GC 빈도 확인
grep "GC(.*) Pause Full" gc.log | wc -l

# Old Gen 사용률 추이 확인
grep "Old" gc.log | tail -50
```

## 주의사항 및 트레이드오프

### 힙 덤프 생성 시 주의사항

**1. Stop-the-World 발생**
힙 덤프 생성은 애플리케이션을 완전히 멈춘다. 프로덕션에서 `jmap`을 직접 실행하는 것은 서비스 중단을 의미할 수 있다. 가능하면 로드밸런서에서 해당 인스턴스를 미리 제외한 후 덤프를 떠야 한다.

**2. 덤프 파일 크기**
힙 크기와 덤프 파일 크기는 비례한다. 힙이 8GB라면 덤프 파일도 수 GB에 달한다. 디스크 여유 공간을 미리 확보해야 한다.

**3. `live` 옵션 사용 주의**
`jmap -dump:live`는 덤프 전에 Full GC를 강제 실행한다. 덤프 크기는 줄어들지만 GC 부하가 추가로 발생한다. 목적에 따라 선택해야 한다.

### 메모리 튜닝 트레이드오프

| 설정 | 장점 | 단점 |
|---|---|---|
| 힙 크기 증가 | OOM 발생 빈도 감소 | GC 시간 증가, 비용 증가 |
| Young Gen 비율 증가 | Minor GC 빈도 감소 | Old Gen 공간 감소 |
| G1GC 사용 | 긴 GC 멈춤 감소 | CPU 오버헤드 증가 |
| ZGC/Shenandoah | 매우 짧은 GC 멈춤 | 처리량(Throughput) 약간 감소 |

### 메모리 누수 vs 메모리 압박 구분

두 가지를 구분하는 것이 중요하다.

- **메모리 누수**: GC 후에도 Old Gen이 계속 증가. 힙 덤프로 원인 클래스를 찾아야 한다.
- **메모리 압박**: 실제로 필요한 데이터가 많아 힙이 부족한 경우. 힙 증설 또는 로직 최적화가 해결책이다.

GC 로그에서 Full GC 이후 Old Gen 사용량이 계속 우상향한다면 누수, 일정 수준에서 유지된다면 압박으로 판단할 수 있다.

## 정리

JVM 메모리 문제는 발생 후 대응보다 사전 대비가 훨씬 중요하다. 핵심 체크리스트를 정리하면 다음과 같다.

**사전 준비**
- `-XX:+HeapDumpOnOutOfMemoryError` 옵션은 프로덕션 필수 설정
- GC 로그를 반드시 파일로 남기고 모니터링 대시보드에 연결
- Metaspace 상한(`-XX:MaxMetaspaceSize`)을 명시적으로 설정

**개발 단계**
- static 컬렉션은 항상 의심하고, 사용 시 크기 제한과 TTL을 적용
- ThreadLocal은 반드시 `remove()`로 정리하는 로직을 함께 작성
- 대량 데이터 처리 시 전체 로딩 대신 스트리밍이나 배치 처리 적용

**장애 대응**
- 로드밸런서에서 인스턴스 제외 → 힙 덤프 생성 → MAT 분석 순서로 접근
- Dominator Tree와 Leak Suspects Report를 함께 보며 원인 객체를 특정
- OQL을 활용해 특정 클래스 인스턴스 수와 크기를 직접 쿼리

메모리 문제는 대부분 패턴이 있다. GC 로그와 힙 덤프를 꾸준히 분석하다 보면 반복되는 문제 유형을 빠르게 파악하는 직관이 생긴다. 도구에 익숙해지는 것보다 "왜 이 객체가 여기에 이만큼 쌓였는가"를 질문하는 습관이 더 중요하다.
