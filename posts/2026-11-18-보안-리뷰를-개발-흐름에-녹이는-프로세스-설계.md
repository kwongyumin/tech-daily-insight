# 보안 리뷰를 개발 흐름에 녹이는 프로세스 설계

## 개요

"보안은 나중에 한다"는 말은 개발 현장에서 흔히 들리는 문장이다. 기능 개발 일정에 쫓기다 보면 보안 검토는 릴리즈 직전이나 사고 이후로 미뤄지는 경우가 많다. 이 패턴의 문제는 단순히 "늦다"는 것이 아니라, **보안 결함을 발견할수록 수정 비용이 기하급수적으로 늘어난다**는 데 있다.

DevSecOps라는 용어가 등장한 이유가 바로 여기에 있다. 보안을 별도의 게이트가 아닌 개발 파이프라인의 일부로 녹여내는 것이다. 이 글에서는 실제 개발 흐름 — 코드 작성, PR, CI/CD, 배포 — 각 단계에 보안 리뷰를 어떻게 통합할 수 있는지 프로세스 설계 관점에서 살펴본다.

---

## 핵심 개념: Shift Left Security

**Shift Left**는 소프트웨어 개발 생명주기(SDLC)에서 보안 검토를 가능한 한 왼쪽(앞 단계)으로 당긴다는 개념이다.

```
[요구사항] → [설계] → [개발] → [테스트] → [배포] → [운영]
     ↑
  보안을 여기서부터 시작
```

전통적인 방식에서는 보안 검토가 테스트 단계나 배포 직전에 몰렸다. Shift Left는 이를 요구사항 및 설계 단계부터 가져오며, 각 단계마다 적절한 자동화 도구와 리뷰 체크포인트를 배치한다.

핵심은 **"사람이 모든 것을 검토"하는 것이 아니라, 자동화가 처리할 수 있는 것은 자동화하고, 사람의 판단이 필요한 지점에만 사람을 개입**시키는 것이다.

## 실전 예제: 단계별 보안 통합 설계

### 1단계: 개발 환경 — Pre-commit Hook

개발자가 코드를 커밋하기 전에 기본적인 보안 체크를 로컬에서 수행하게 한다. 이 단계에서 걸러지는 것들은 주로 **시크릿 노출, 명백한 취약 패턴** 등이다.

`.pre-commit-config.yaml` 예시:

```yaml
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.18.0
    hooks:
      - id: gitleaks
        name: Detect hardcoded secrets

  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.5.0
    hooks:
      - id: detect-private-key
      - id: check-merge-conflict

  - repo: https://github.com/pycqa/bandit
    rev: 1.7.5
    hooks:
      - id: bandit
        args: ["-c", "pyproject.toml"]
```

Java/Spring 프로젝트라면 `git-secrets` 또는 `detect-secrets`를 활용해 `.properties`, `.yml` 파일에 패스워드나 API 키가 하드코딩되는 것을 방지할 수 있다.

```bash
# detect-secrets 초기 baseline 생성
detect-secrets scan > .secrets.baseline

# pre-commit 실행 시 baseline 대비 새로운 시크릿 탐지
detect-secrets audit .secrets.baseline
```

### 2단계: PR 단계 — SAST 자동화 및 보안 체크리스트

PR이 열리는 순간 CI에서 **SAST(Static Application Security Testing)** 도구를 실행한다. Java Spring 환경에서는 SpotBugs + Find Security Bugs 플러그인 조합이 효과적이다.

`build.gradle` 설정:

```groovy
plugins {
    id 'com.github.spotbugs' version '5.2.1'
}

spotbugs {
    toolVersion = '4.8.3'
    effort = 'max'
    reportLevel = 'low'
    excludeFilter = file('config/spotbugs-exclude.xml')
}

spotbugsMain {
    reports {
        xml.required = false
        html.required = true
    }
    pluginClasspath = configurations.spotbugsPlugins
}

dependencies {
    spotbugsPlugins 'com.h3xstream.findsecbugs:findsecbugs-plugin:1.12.0'
}
```

GitHub Actions와 연동한 보안 스캔 워크플로우:

```yaml
name: Security Scan

on:
  pull_request:
    branches: [main, develop]

jobs:
  sast:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up JDK 17
        uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'

      - name: Run SpotBugs Security Scan
        run: ./gradlew spotbugsMain

      - name: Upload SpotBugs Report
        uses: actions/upload-artifact@v4
        if: always()
        with:
          name: spotbugs-report
          path: build/reports/spotbugs/

      - name: Dependency Vulnerability Check
        run: ./gradlew dependencyCheckAnalyze
        env:
          NVD_API_KEY: ${{ secrets.NVD_API_KEY }}

      - name: Fail on High Severity
        run: |
          if grep -q 'CVSS.*[89]\.' build/reports/dependency-check-report.xml; then
            echo "High severity vulnerability found!"
            exit 1
          fi
```

**PR 보안 체크리스트** 템플릿을 GitHub PR 템플릿에 포함시키는 것도 중요하다.

`.github/pull_request_template.md`:

```markdown
## 보안 체크리스트

- [ ] 하드코딩된 시크릿/자격증명이 없는가?
- [ ] SQL 쿼리에 파라미터 바인딩을 사용하고 있는가?
- [ ] 사용자 입력값에 대한 검증/이스케이프 처리가 되어 있는가?
- [ ] 민감한 데이터가 로그에 출력되지 않는가?
- [ ] 새로운 외부 의존성 추가 시 라이선스 및 취약점 확인을 했는가?
- [ ] 인증/인가 로직 변경 시 별도 보안 리뷰를 요청했는가?
```

### 3단계: CI/CD 파이프라인 — SCA와 컨테이너 이미지 스캔

의존성 취약점 스캔(SCA, Software Composition Analysis)과 컨테이너 이미지 스캔을 파이프라인에 추가한다.

```yaml
  container-scan:
    runs-on: ubuntu-latest
    needs: build
    steps:
      - name: Build Docker image
        run: docker build -t myapp:${{ github.sha }} .

      - name: Run Trivy vulnerability scanner
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: 'myapp:${{ github.sha }}'
          format: 'sarif'
          output: 'trivy-results.sarif'
          severity: 'CRITICAL,HIGH'
          exit-code: '1'

      - name: Upload Trivy scan results to GitHub Security tab
        uses: github/codeql-action/upload-sarif@v3
        if: always()
        with:
          sarif_file: 'trivy-results.sarif'
```

OWASP Dependency-Check를 Gradle에 통합하는 예시:

```groovy
plugins {
    id 'org.owasp.dependencycheck' version '9.0.9'
}

dependencyCheck {
    failBuildOnCVSS = 7.0  // CVSS 7.0 이상 시 빌드 실패
    formats = ['HTML', 'JSON']
    suppressionFile = 'config/dependency-check-suppression.xml'
    nvd {
        apiKey = System.getenv('NVD_API_KEY')
    }
}
```

### 4단계: 코드 리뷰 — 보안 전문 리뷰어 지정 (CODEOWNERS)

인증/인가, 암호화, 외부 연동 관련 코드 변경 시 보안 담당자가 자동으로 리뷰어에 추가되도록 설정한다.

`.github/CODEOWNERS`:

```
# 인증/인가 관련 코드
src/main/java/com/example/auth/        @security-team @backend-lead

# 외부 결제/민감 데이터 처리
src/main/java/com/example/payment/     @security-team

# 인프라 및 배포 설정
infrastructure/                         @infra-team @security-team
*.tf                                   @infra-team @security-team

# 보안 설정 파일
src/main/resources/application*.yml    @backend-lead
```

### 5단계: 설계 단계 — Threat Modeling 가이드 문서화

기능 설계 단계에서 위협 모델링을 간소화된 형태로 수행하도록 템플릿을 제공한다. STRIDE 모델 기반의 간단한 체크 형태로도 충분히 효과적이다.

```markdown
## 기능명: [기능 이름]

### 데이터 흐름 요약
> 어떤 데이터가, 어디서 어디로 흐르는가?

### STRIDE 위협 체크
| 위협 유형       | 해당 여부 | 대응 방안 |
|----------------|-----------|-----------|
| Spoofing (인증 위조) | Y/N | |
| Tampering (데이터 변조) | Y/N | |
| Repudiation (부인) | Y/N | |
| Information Disclosure (정보 노출) | Y/N | |
| Denial of Service (서비스 거부) | Y/N | |
| Elevation of Privilege (권한 상승) | Y/N | |

### 민감 데이터 처리
- 처리 데이터 목록:
- 저장 방식 (암호화 여부):
- 로깅 제외 필드:
```

## 주의사항 및 트레이드오프

### 자동화 도구의 오탐(False Positive) 관리

SAST 도구는 초기에 많은 오탐을 발생시킨다. 이를 방치하면 개발자들이 경고를 무시하는 **"알림 피로(Alert Fatigue)"** 현상이 생긴다. 오탐은 suppression 파일로 관리하되, 반드시 사유를 명시해야 한다.

```xml
<!-- spotbugs-exclude.xml -->
<FindBugsFilter>
    <!-- 테스트 코드의 보안 경고는 제외 -->
    <Match>
        <Class name="~.*Test"/>
        <Bug category="SECURITY"/>
    </Match>

    <!-- 특정 패턴에 대한 예외: 사유 명시 필수 -->
    <!-- 사유: 내부 시스템 간 통신으로 TLS 적용 불가한 레거시 연동 -->
    <Match>
        <Class name="com.example.legacy.InternalApiClient"/>
        <Bug pattern="UNENCRYPTED_SERVER_SOCKET"/>
    </Match>
</FindBugsFilter>
```

### 보안 게이트가 개발 속도를 막을 때

모든 단계에 엄격한 보안 게이트를 두면 개발 속도가 체감될 정도로 느려진다. 아래와 같은 전략이 균형을 잡는 데 도움이 된다.

- **Critical/High만 빌드 블로킹**: Medium 이하는 리포트만 하고 빌드는 통과시킨다.
- **신규 코드에만 적용**: 레거시 코드 전체에 SAST를 돌리면 오탐이 폭발한다. `--diff-only` 옵션이나 baseline 비교 방식을 활용한다.
- **로컬 스캔과 CI 스캔 분리**: Pre-commit에서는 빠른 도구만, CI에서는 무거운 스캔을 돌린다.

### 보안 리뷰와 개발팀의 협업 문제

보안 담당자가 별도로 존재하는 조직에서는 CODEOWNERS로 지정된 리뷰어가 병목이 되기 쉽다. 이를 해소하려면:

- 보안 리뷰가 필요한 코드 변경의 범위를 명확히 정의하고 문서화
- 자주 발생하는 패턴에 대해 **"사전 승인된 패턴"** 목록을 관리
- 보안팀이 개발팀에게 주기적으로 **보안 훈련 세션**을 제공해 판단력 위임

### 시크릿 관리는 별도 전략 필요

Pre-commit에서 시크릿 탐지를 한다고 해도, 이미 Git 히스토리에 올라간 시크릿은 `git filter-branch`나 `BFG Repo Cleaner`로 제거해야 한다. 근본적으로는 **Vault, AWS Secrets Manager, GCP Secret Manager** 같은 시크릿 관리 솔루션을 도입하고, 애플리케이션이 환경변수나 시크릿 스토어에서 자격증명을 주입받는 구조로 가야 한다.

## 정리

보안 리뷰를 개발 흐름에 녹이는 것의 핵심은 **"보안을 개발자의 일상 워크플로우 안으로 가져오는 것"**이다. 별도의 프로세스로 분리할수록 개발자는 보안을 외부에서 가해지는 제약으로 인식하게 된다.

| 단계 | 도구/방법 | 목적 |
|------|-----------|------|
| 로컬 개발 | pre-commit, detect-secrets | 시크릿/명백한 취약점 조기 차단 |
| PR | SAST (SpotBugs + FSB), 체크리스트 | 코드 수준 취약점 탐지 |
| CI/CD | OWASP Dependency-Check, Trivy | 의존성·컨테이너 취약점 |
| 코드 리뷰 | CODEOWNERS | 민감 코드 전문가 리뷰 보장 |
| 설계 | Threat Modeling 템플릿 | 아키텍처 수준 위협 식별 |

이 모든 프로세스를 한 번에 도입할 필요는 없다. **Pre-commit 시크릿 탐지 → PR 체크리스트 → CI 의존성 스캔** 순으로 점진적으로 도입하고, 팀이 각 단계에 익숙해지면 다음 단계를 추가하는 방식이 현실적이다.

보안은 결국 문화의 문제다. 도구는 그 문화를 구조적으로 뒷받침하는 수단이다.
