# 스크래핑 기반 외부 데이터 수집 시스템의 안정성 설계

## 개요

외부 사이트나 API에 의존하는 데이터 수집 시스템은 겉보기엔 단순해 보이지만, 실무에서는 매우 까다로운 안정성 문제를 내포하고 있다. 대상 사이트의 구조 변경, 일시적인 네트워크 오류, IP 차단, 세션 만료, 응답 지연 등 통제 불가능한 외부 요인이 항상 존재하기 때문이다.

이 글에서는 스크래핑 기반 외부 데이터 수집 시스템을 운영할 때 맞닥뜨리는 대표적인 장애 패턴을 분석하고, 이를 견고하게 설계하기 위한 아키텍처 전략과 실전 코드를 소개한다. 단순한 HTTP 요청 코드 수준이 아니라, 운영 환경에서의 실패를 전제한 방어적 설계에 초점을 맞춘다.

---

## 핵심 개념

### 1. 외부 의존성은 항상 실패한다는 전제

스크래핑 시스템의 첫 번째 설계 원칙은 **"외부 시스템은 언제든 실패할 수 있다"** 는 것이다. 이는 단순한 주의사항이 아니라 아키텍처 결정의 근간이 되어야 한다.

외부 의존성에서 발생하는 실패는 크게 세 가지로 분류할 수 있다.

| 실패 유형 | 예시 | 대응 전략 |
|---|---|---|
| **일시적 오류** | 503, 타임아웃, 커넥션 거부 | 재시도(Retry) + 지수 백오프 |
| **구조적 변경** | HTML 셀렉터 불일치, 응답 스키마 변경 | 파싱 검증 + 알림 |
| **정책적 차단** | IP 블락, 봇 감지, Rate Limit | 요청 제어 + 프록시 로테이션 |

이 세 가지 실패 유형을 모두 처리할 수 있도록 각각의 레이어에서 방어 로직을 구성해야 한다.

### 2. 수집 파이프라인의 계층 분리

데이터 수집 파이프라인은 다음과 같이 역할을 분리하는 것이 유지보수와 장애 대응에 유리하다.

```
[스케줄러] → [수집 작업 큐] → [스크래퍼] → [파서/검증기] → [저장소]
                                     ↑
                              [재시도 큐 / DLQ]
```

- **스케줄러**: 수집 주기와 대상 관리
- **수집 작업 큐**: 수집 요청의 버퍼링과 비동기 처리
- **스크래퍼**: 실제 HTTP 요청 및 응답 획득
- **파서/검증기**: 응답 데이터의 파싱과 무결성 검사
- **저장소**: 수집된 데이터의 영속화

이처럼 계층을 분리하면 각 단계에서의 실패를 독립적으로 처리할 수 있고, 특정 레이어만 교체하거나 스케일아웃하는 것도 가능해진다.

### 3. 멱등성(Idempotency) 보장

재시도가 발생하더라도 중복 데이터가 쌓이거나 부작용이 생기지 않도록, 수집 작업은 반드시 멱등하게 설계해야 한다. 같은 수집 작업이 두 번 실행되어도 결과가 동일해야 한다.

## 실전 예제

### Resilience4j를 활용한 스크래퍼 안정성 처리

Spring Boot 환경에서 Resilience4j의 Retry, CircuitBreaker, RateLimiter를 조합하여 스크래퍼의 안정성을 확보하는 예제를 살펴보자.

**의존성 추가 (build.gradle)**

```groovy
implementation 'io.github.resilience4j:resilience4j-spring-boot3:2.1.0'
implementation 'io.github.resilience4j:resilience4j-reactor:2.1.0'
implementation 'org.springframework.boot:spring-boot-starter-webflux'
```

**application.yml 설정**

```yaml
resilience4j:
  retry:
    instances:
      scraper:
        max-attempts: 3
        wait-duration: 2s
        exponential-backoff-multiplier: 2
        retry-exceptions:
          - java.io.IOException
          - java.net.SocketTimeoutException
          - org.springframework.web.reactive.function.client.WebClientResponseException$ServiceUnavailable

  circuitbreaker:
    instances:
      scraper:
        sliding-window-size: 10
        failure-rate-threshold: 50
        wait-duration-in-open-state: 30s
        permitted-number-of-calls-in-half-open-state: 3

  ratelimiter:
    instances:
      scraper:
        limit-for-period: 5
        limit-refresh-period: 1s
        timeout-duration: 3s
```

**스크래퍼 서비스 구현**

```java
@Service
@RequiredArgsConstructor
@Slf4j
public class ExternalDataScraper {

    private final WebClient webClient;
    private final RetryRegistry retryRegistry;
    private final CircuitBreakerRegistry circuitBreakerRegistry;
    private final RateLimiterRegistry rateLimiterRegistry;

    public Mono<ScrapedData> scrape(ScrapeTarget target) {
        Retry retry = retryRegistry.retry("scraper");
        CircuitBreaker circuitBreaker = circuitBreakerRegistry.circuitBreaker("scraper");
        RateLimiter rateLimiter = rateLimiterRegistry.rateLimiter("scraper");

        return fetchRaw(target)
            .transformDeferred(RateLimiterOperator.of(rateLimiter))
            .transformDeferred(CircuitBreakerOperator.of(circuitBreaker))
            .transformDeferred(RetryOperator.of(retry))
            .map(this::parse)
            .doOnError(e -> log.error("[Scraper] 수집 실패: target={}, error={}", target.url(), e.getMessage()))
            .onErrorMap(CallNotPermittedException.class,
                e -> new ScraperCircuitOpenException("Circuit Breaker OPEN: " + target.url()));
    }

    private Mono<String> fetchRaw(ScrapeTarget target) {
        return webClient.get()
            .uri(target.url())
            .headers(headers -> headers.addAll(target.headers()))
            .retrieve()
            .onStatus(HttpStatusCode::is4xxClientError, response -> {
                if (response.statusCode() == HttpStatus.TOO_MANY_REQUESTS) {
                    return Mono.error(new RateLimitExceededException("429 Too Many Requests"));
                }
                return Mono.error(new NonRetryableScraperException("4xx 오류: " + response.statusCode()));
            })
            .onStatus(HttpStatusCode::is5xxServerError,
                response -> Mono.error(new IOException("5xx 오류: " + response.statusCode())))
            .bodyToMono(String.class)
            .timeout(Duration.ofSeconds(10));
    }

    private ScrapedData parse(String html) {
        // Jsoup 등을 활용한 파싱 로직
        Document doc = Jsoup.parse(html);
        String title = Optional.ofNullable(doc.selectFirst("h1.product-title"))
            .map(Element::text)
            .orElseThrow(() -> new ParseFailureException("셀렉터 불일치: h1.product-title"));

        return new ScrapedData(title, LocalDateTime.now());
    }
}
```

### 수집 작업 큐와 DLQ(Dead Letter Queue) 처리

일시적 오류는 재시도로 해결되지만, 반복적으로 실패하는 작업은 DLQ로 보내어 별도로 관리해야 한다.

```java
@Component
@RequiredArgsConstructor
@Slf4j
public class ScrapeJobConsumer {

    private final ExternalDataScraper scraper;
    private final ScrapeJobRepository jobRepository;

    @RabbitListener(queues = "scrape.jobs")
    public void consume(ScrapeJobMessage message) {
        scraper.scrape(message.toTarget())
            .subscribe(
                data -> {
                    jobRepository.saveResult(message.jobId(), data);
                    log.info("[Job] 수집 완료: jobId={}", message.jobId());
                },
                error -> handleFailure(message, error)
            );
    }

    private void handleFailure(ScrapeJobMessage message, Throwable error) {
        int retryCount = message.retryCount() + 1;

        if (error instanceof NonRetryableScraperException) {
            log.warn("[Job] 재시도 불가 오류, DLQ 전송: jobId={}", message.jobId());
            sendToDlq(message.withError(error.getMessage()));
            return;
        }

        if (retryCount >= 5) {
            log.error("[Job] 최대 재시도 초과, DLQ 전송: jobId={}", message.jobId());
            sendToDlq(message.withError("최대 재시도 초과"));
            return;
        }

        // 지수 백오프로 재큐잉
        long delayMs = (long) Math.pow(2, retryCount) * 1000;
        requeueWithDelay(message.withRetryCount(retryCount), delayMs);
    }
}
```

### 파싱 검증과 구조 변경 감지

HTML 구조 변경은 스크래핑 시스템에서 가장 조용하고 치명적인 장애다. 파서에서 검증 로직을 별도로 두어 이상을 조기에 감지해야 한다.

```java
@Component
public class ScrapedDataValidator {

    private static final double FIELD_PRESENCE_THRESHOLD = 0.8;

    public ValidationResult validate(List<ScrapedData> batch) {
        long nullTitleCount = batch.stream()
            .filter(d -> d.title() == null || d.title().isBlank())
            .count();

        double nullRatio = (double) nullTitleCount / batch.size();

        if (nullRatio > (1 - FIELD_PRESENCE_THRESHOLD)) {
            return ValidationResult.anomaly(
                String.format("title 필드 누락률 %.1f%% 초과 - 셀렉터 변경 의심", nullRatio * 100)
            );
        }

        return ValidationResult.ok();
    }
}
```

이처럼 배치 단위의 품질 지표를 모니터링하면, 개별 파싱 오류보다 훨씬 빠르게 구조 변경을 감지할 수 있다.

## 주의사항 및 트레이드오프

### 재시도와 부하 증폭 사이의 균형

재시도는 일시적 오류에 효과적이지만, 대상 서버가 이미 과부하 상태일 때 무분별한 재시도는 상황을 악화시킨다. **지수 백오프(Exponential Backoff)** 에 **Jitter(무작위 지연)** 를 더해 요청이 동시에 몰리는 것을 방지해야 한다.

```java
// Jitter 적용 예시
long baseDelay = 1000L;
long jitter = ThreadLocalRandom.current().nextLong(0, 500);
long delay = (long) Math.pow(2, retryCount) * baseDelay + jitter;
```

### CircuitBreaker 임계값 튜닝

CircuitBreaker의 `failure-rate-threshold`를 너무 낮게 설정하면 잠깐의 오류에도 Circuit이 열려 정상적인 수집이 중단된다. 반대로 너무 높게 설정하면 보호 효과가 없다. 초기에는 보수적으로 설정하고, 실제 오류율 데이터를 기반으로 조정하는 것이 좋다.

### 수집 주기와 robots.txt 준수

기술적 안정성 외에도, 대상 사이트의 `robots.txt`와 이용 약관을 준수하는 것은 법적, 윤리적 의무다. 무분별한 고빈도 수집은 IP 차단뿐만 아니라 법적 분쟁으로 이어질 수 있다. 요청 간격을 적절히 설정하고, User-Agent를 명확히 식별 가능하게 설정하는 것이 권장된다.

### 스키마 변경에 대한 선택: 엄격한 파싱 vs 관대한 파싱

파싱 검증을 얼마나 엄격하게 할지는 비즈니스 요구사항에 따라 다르다.

- **엄격한 파싱**: 필수 필드 누락 시 즉시 오류 처리 → 데이터 품질은 높지만 가용성이 낮아질 수 있음
- **관대한 파싱**: 가능한 필드만 추출하고 나머지는 null 허용 → 가용성은 높지만 품질 저하 위험

일반적으로 금액, 재고 상태 등 비즈니스 크리티컬 필드는 엄격하게, 보조 정보는 관대하게 처리하는 **하이브리드 전략**이 실용적이다.

### 분산 환경에서의 중복 수집 방지

여러 인스턴스가 동시에 같은 대상을 수집하면 불필요한 외부 부하와 중복 데이터가 발생한다. Redis를 활용한 분산 락 또는 큐 기반의 단일 소비 패턴으로 이를 방지해야 한다.

```java
// Redis 분산 락 예시 (Redisson)
RLock lock = redissonClient.getLock("scrape:lock:" + target.id());
if (lock.tryLock(0, 30, TimeUnit.SECONDS)) {
    try {
        scraper.scrape(target);
    } finally {
        lock.unlock();
    }
}
```

## 정리

스크래핑 기반 외부 데이터 수집 시스템의 안정성은 단일 기술로 해결되지 않는다. 아래의 설계 원칙을 계층별로 적용하는 종합적인 접근이 필요하다.

| 레이어 | 핵심 전략 |
|---|---|
| **수집 요청** | Retry + 지수 백오프 + Jitter, RateLimiter |
| **장애 전파 차단** | CircuitBreaker로 연쇄 장애 방지 |
| **데이터 품질** | 파싱 검증, 배치 이상 감지, 알림 |
| **작업 관리** | 큐 기반 비동기 처리, DLQ, 멱등성 보장 |
| **운영** | 분산 락, 메트릭 모니터링, 셀렉터 변경 감지 |

외부 시스템은 내 통제 밖에 있다. 중요한 것은 그 불확실성을 인정하고, 각 실패 유형에 맞는 방어 로직을 미리 준비하는 것이다. 처음부터 완벽한 시스템을 만들려 하기보다, 실패 시 빠르게 감지하고 복구할 수 있는 관측 가능성(Observability)과 복원력(Resilience)을 갖추는 것이 더 현실적이고 효과적인 목표다.
