# 빠른 데이터 서빙을 위한 조회 전용 저장소 설계

## 개요

트래픽이 늘어날수록 서비스에서 가장 먼저 병목이 발생하는 곳은 대부분 **읽기 경로(Read Path)**다. 쓰기는 상대적으로 단순한 경우가 많지만, 조회는 복잡한 조인, 집계, 필터링이 뒤섞이면서 DB에 부하를 누적시킨다. 이를 해결하는 대표적인 전략 중 하나가 **조회 전용 저장소(Read-Optimized Store)** 를 별도로 설계하는 것이다.

이 글에서는 조회 전용 저장소가 필요한 시점, 설계 방법, 구현 예제, 그리고 도입 시 반드시 고려해야 할 트레이드오프를 실무 관점에서 정리한다.

---

## 핵심 개념

### CQRS와 조회 전용 저장소

조회 전용 저장소 설계는 **CQRS(Command Query Responsibility Segregation)** 패턴과 밀접하게 연결된다. 쓰기(Command)와 읽기(Query) 모델을 분리하여, 각각 최적화된 저장소를 사용하자는 아이디어다.

```
[Client]
   |
   ├── Write Path → Command Handler → Primary DB (e.g., MySQL)
   │                                      |
   │                              (이벤트 or CDC)
   │                                      |
   └── Read Path  → Query Handler  → Read Store (e.g., Redis, Elasticsearch)
```

핵심은 **원본 데이터(Source of Truth)는 Primary DB에 유지**하되, 조회 성능에 최적화된 형태로 별도 저장소에 데이터를 복제·변환하는 것이다.

### 조회 전용 저장소가 필요한 신호

다음과 같은 상황이라면 조회 전용 저장소 도입을 검토할 시점이다.

- 복잡한 다중 조인 쿼리로 인해 읽기 레이턴시가 지속적으로 높음
- 읽기 트래픽이 쓰기 트래픽 대비 압도적으로 많음 (예: 10:1 이상)
- 집계/정렬을 위한 인덱스가 과도하게 늘어나 쓰기 성능에 영향을 줌
- 전문 검색(Full-text search), 지리 검색 등 RDBMS가 취약한 조회가 필요함

## 실전 예제

### 시나리오

상품 목록 페이지를 제공하는 이커머스 서비스를 가정하자. 상품 조회 API는 다음 조건을 만족해야 한다.

- 카테고리, 가격 범위, 키워드로 필터링
- 인기순/최신순/가격순 정렬
- 재고 수량, 판매자 정보, 리뷰 평점을 하나의 응답으로 반환

이를 RDBMS 단일 조회로 처리하면 쿼리가 지나치게 복잡해지고, 인덱스 설계도 어렵다. 여기서 **Elasticsearch를 조회 전용 저장소로** 활용하는 구조를 설계한다.

### 데이터 동기화 전략: CDC + Kafka

Primary DB의 변경 사항을 조회 전용 저장소로 전파하는 방법은 크게 두 가지다.

1. **애플리케이션 레벨 이벤트 발행**: 서비스 코드에서 저장 후 이벤트를 직접 발행
2. **CDC(Change Data Capture)**: Debezium 같은 도구로 DB 로그(binlog)를 읽어 이벤트화

CDC 방식은 애플리케이션 코드 변경 없이 인프라 레벨에서 동기화를 처리할 수 있어 장기적으로 유지보수에 유리하다.

```yaml
# Debezium MySQL Connector 설정 예시
connector.class: io.debezium.connector.mysql.MySqlConnector
database.hostname: mysql-primary
database.port: 3306
database.user: debezium
database.password: secret
database.server.name: product-db
database.include.list: ecommerce
table.include.list: ecommerce.products, ecommerce.reviews, ecommerce.inventory
```

### Kafka Consumer: 인덱스 동기화

Kafka에서 변경 이벤트를 소비하여 Elasticsearch에 색인하는 Spring 컴포넌트 예제다.

```java
@Service
@RequiredArgsConstructor
public class ProductIndexSyncConsumer {

    private final ElasticsearchOperations elasticsearchOperations;
    private final ProductReadModelAssembler assembler;

    @KafkaListener(topics = "product-db.ecommerce.products", groupId = "product-index-sync")
    public void handleProductChange(ConsumerRecord<String, ProductChangeEvent> record) {
        ProductChangeEvent event = record.value();

        if (event.getOperation() == Operation.DELETE) {
            elasticsearchOperations.delete(event.getId(), ProductDocument.class);
            return;
        }

        ProductDocument document = assembler.toDocument(event.getAfter());
        elasticsearchOperations.save(document);
    }
}
```

```java
@Document(indexName = "products")
@Data
public class ProductDocument {

    @Id
    private String id;
    private String name;
    private String description;
    private String categoryId;
    private BigDecimal price;
    private int stockQuantity;
    private double reviewScore;
    private String sellerName;
    private LocalDateTime createdAt;

    // 전문 검색을 위한 별도 필드
    @MultiField(
        mainField = @Field(type = FieldType.Text, analyzer = "korean"),
        otherFields = @InnerField(suffix = "keyword", type = FieldType.Keyword)
    )
    private String searchableText;
}
```

### Query Handler: 조회 전용 저장소에서 데이터 서빙

```java
@Service
@RequiredArgsConstructor
public class ProductQueryService {

    private final ElasticsearchOperations elasticsearchOperations;

    public Page<ProductSummary> search(ProductSearchRequest request, Pageable pageable) {
        BoolQuery.Builder boolQuery = new BoolQuery.Builder();

        // 카테고리 필터
        if (StringUtils.hasText(request.getCategoryId())) {
            boolQuery.filter(TermQuery.of(t -> t
                .field("categoryId")
                .value(request.getCategoryId())
            )._toQuery());
        }

        // 가격 범위 필터
        if (request.getMinPrice() != null || request.getMaxPrice() != null) {
            boolQuery.filter(RangeQuery.of(r -> r
                .field("price")
                .gte(JsonData.of(request.getMinPrice()))
                .lte(JsonData.of(request.getMaxPrice()))
            )._toQuery());
        }

        // 키워드 검색
        if (StringUtils.hasText(request.getKeyword())) {
            boolQuery.must(MultiMatchQuery.of(m -> m
                .fields("name^2", "description", "sellerName")
                .query(request.getKeyword())
            )._toQuery());
        }

        // 재고 있는 상품만
        boolQuery.filter(RangeQuery.of(r -> r
            .field("stockQuantity")
            .gt(JsonData.of(0))
        )._toQuery());

        NativeQuery query = NativeQuery.builder()
            .withQuery(boolQuery.build()._toQuery())
            .withPageable(pageable)
            .build();

        SearchHits<ProductDocument> hits = elasticsearchOperations.search(query, ProductDocument.class);

        return SearchHitSupport.searchPageFor(hits, pageable)
            .map(hit -> ProductSummary.from(hit.getContent()));
    }
}
```

### Read Model 조립: 비정규화된 문서 생성

조회 전용 저장소의 핵심은 **조회에 필요한 데이터를 미리 조합(비정규화)** 해두는 것이다. `ProductReadModelAssembler`는 여러 도메인 데이터를 하나의 문서로 조립한다.

```java
@Component
@RequiredArgsConstructor
public class ProductReadModelAssembler {

    private final InventoryRepository inventoryRepository;
    private final ReviewSummaryRepository reviewSummaryRepository;
    private final SellerRepository sellerRepository;

    public ProductDocument toDocument(ProductData product) {
        Inventory inventory = inventoryRepository.findByProductId(product.getId())
            .orElse(Inventory.empty());

        ReviewSummary reviewSummary = reviewSummaryRepository.findByProductId(product.getId())
            .orElse(ReviewSummary.empty());

        Seller seller = sellerRepository.findById(product.getSellerId())
            .orElseThrow();

        return ProductDocument.builder()
            .id(product.getId().toString())
            .name(product.getName())
            .description(product.getDescription())
            .categoryId(product.getCategoryId())
            .price(product.getPrice())
            .stockQuantity(inventory.getQuantity())
            .reviewScore(reviewSummary.getAverageScore())
            .sellerName(seller.getName())
            .searchableText(buildSearchableText(product, seller))
            .createdAt(product.getCreatedAt())
            .build();
    }

    private String buildSearchableText(ProductData product, Seller seller) {
        return String.join(" ", product.getName(), product.getDescription(), seller.getName());
    }
}
```

## 주의사항 및 트레이드오프

### 1. 최종 일관성(Eventual Consistency) 수용

조회 전용 저장소는 Primary DB와 **항상 동기화 상태가 아닐 수 있다**. CDC나 이벤트 기반 동기화는 수십 밀리초에서 수 초의 지연이 발생할 수 있으며, 이는 비즈니스 요구사항과 협의가 필요하다.

- **허용 가능한 경우**: 상품 목록, 추천 피드, 검색 결과처럼 약간의 지연이 UX에 큰 영향을 주지 않는 경우
- **허용 불가능한 경우**: 주문/결제/재고 차감처럼 정합성이 즉시 보장되어야 하는 경우 → 이 경우는 Primary DB를 직접 조회하거나 강력한 동기화 메커니즘이 필요

### 2. 데이터 정합성 모니터링

동기화 파이프라인에 장애가 생기면 조회 전용 저장소가 오래된 데이터를 서빙하게 된다. 다음과 같은 모니터링이 필수다.

```java
// Kafka Consumer Lag 모니터링 예시 (Micrometer)
@Scheduled(fixedDelay = 30_000)
public void reportConsumerLag() {
    Map<TopicPartition, Long> lagMap = adminClient.listConsumerGroupOffsets("product-index-sync")
        // ... lag 계산 로직
    
    lagMap.forEach((partition, lag) ->
        meterRegistry.gauge("kafka.consumer.lag",
            Tags.of("topic", partition.topic(), "partition", String.valueOf(partition.partition())),
            lag)
    );
}
```

Consumer lag이 일정 임계치를 초과하면 알림을 발송하고, 경우에 따라 Primary DB로 Fallback하는 전략도 고려할 수 있다.

### 3. 초기 색인(Backfill) 전략

시스템을 처음 구축하거나 인덱스 스키마를 변경할 때는 기존 데이터를 전부 재색인해야 한다. 이때 Primary DB에 과부하가 발생하지 않도록 배치 처리와 속도 제한(Rate Limiting)을 적용한다.

```java
@Component
@RequiredArgsConstructor
public class ProductBackfillJob {

    private final ProductRepository productRepository;
    private final ProductIndexSyncConsumer syncConsumer;

    @Async
    public void backfill() {
        Pageable pageable = PageRequest.of(0, 100);
        Page<Product> page;

        do {
            page = productRepository.findAll(pageable);
            page.getContent().forEach(product -> {
                ProductDocument doc = assembler.toDocument(ProductData.from(product));
                elasticsearchOperations.save(doc);
            });

            pageable = pageable.next();
            Uninterruptibles.sleepUninterruptibly(100, TimeUnit.MILLISECONDS); // 부하 조절
        } while (page.hasNext());
    }
}
```

### 4. 운영 복잡도 증가

조회 전용 저장소를 추가하면 **운영해야 할 컴포넌트가 늘어난다**: Kafka, Debezium, Elasticsearch 등이 모두 별도 장애 포인트가 된다. 팀의 운영 역량과 시스템의 규모를 냉정하게 평가한 후 도입해야 하며, 단순한 서비스라면 Read Replica + 쿼리 최적화로 충분한 경우도 많다.

| 접근 방식 | 복잡도 | 성능 | 정합성 | 적합한 규모 |
|---|---|---|---|---|
| 단일 RDBMS | 낮음 | 보통 | 강함 | 소규모 |
| Read Replica | 낮음 | 좋음 | 준강함 | 중규모 |
| 조회 전용 저장소 (CQRS) | 높음 | 매우 좋음 | 최종 일관성 | 대규모 |

## 정리

조회 전용 저장소는 읽기 성능의 한계를 돌파하는 강력한 수단이지만, 무조건적인 도입은 오히려 독이 될 수 있다.

핵심을 정리하면 다음과 같다.

1. **비정규화가 핵심이다**: 조회 시점에 필요한 모든 데이터를 미리 조합해 하나의 문서/레코드로 저장한다.
2. **동기화 파이프라인의 신뢰성이 전체 시스템의 신뢰성을 결정한다**: CDC 기반 파이프라인과 lag 모니터링을 함께 설계한다.
3. **최종 일관성은 비즈니스와 협의해야 한다**: 기술적으로 해결 가능한 문제가 아니라 도메인 특성에 따른 판단의 문제다.
4. **점진적으로 도입한다**: 전체 시스템을 한 번에 CQRS로 전환하기보다, 병목이 명확한 특정 조회 경로부터 시작하는 것이 현실적이다.

읽기 경로의 병목을 제거하는 것은 사용자 경험에 직접적인 영향을 미친다. 올바른 도구를 올바른 문제에 적용하는 것, 그것이 이 설계의 출발점이다.
