# 커서 기반 페이지네이션과 대용량 조회 설계

## 개요

페이지네이션은 모든 목록 조회 API에서 반드시 마주치는 문제다. "다음 페이지 주세요"라는 단순한 요청 뒤에는 데이터베이스의 정렬, 인덱스 스캔, 결과 슬라이싱이라는 복잡한 연산이 숨어 있다.

초기에는 `OFFSET/LIMIT` 방식으로 구현하는 경우가 많다. 빠르게 동작하는 것처럼 보이지만, 데이터가 수백만 건을 넘어가는 순간 성능이 급격히 저하된다. 반면 **커서 기반 페이지네이션(Cursor-based Pagination)** 은 대용량 데이터에서도 일관된 응답 속도를 유지할 수 있는 방법이다.

이 글에서는 두 방식의 차이를 분석하고, 실무에서 커서 기반 페이지네이션을 어떻게 설계하고 구현하는지 구체적인 예제와 함께 설명한다.

---

## 핵심 개념

### OFFSET 기반 페이지네이션의 한계

`OFFSET` 방식은 직관적이다.

```sql
SELECT * FROM posts
ORDER BY created_at DESC
LIMIT 20 OFFSET 1000;
```

문제는 `OFFSET 1000`이라는 구문이 실제로 1000개의 행을 읽고 버린다는 것이다. 즉, 페이지가 뒤로 갈수록 데이터베이스는 더 많은 데이터를 스캔해야 한다. `OFFSET 100000`이라면 10만 개 행을 읽고 20개만 반환하는 셈이다.

또한 실시간으로 데이터가 추가·삭제되는 환경에서는 **페이지 스큐(Page Skew)** 문제가 발생한다. 1페이지를 조회하는 사이에 새로운 데이터가 삽입되면, 2페이지에서 동일한 데이터가 중복되거나 일부 데이터가 누락될 수 있다.

### 커서 기반 페이지네이션이란?

커서 기반 페이지네이션은 "어디까지 봤는지"를 나타내는 **커서(cursor)** 를 기준으로 다음 데이터를 가져오는 방식이다. `OFFSET`처럼 행을 세지 않고, 특정 컬럼의 값을 조건으로 직접 비교하기 때문에 인덱스를 효율적으로 활용할 수 있다.

```sql
-- 마지막으로 받은 created_at이 '2024-01-15 10:00:00'일 때
SELECT * FROM posts
WHERE created_at < '2024-01-15 10:00:00'
ORDER BY created_at DESC
LIMIT 20;
```

이 쿼리는 인덱스 범위 스캔(range scan)으로 처리되어, 데이터가 수천만 건이어도 일정한 성능을 보장한다.

### 커서의 종류

커서로 사용할 수 있는 컬럼은 다음 조건을 만족해야 한다.

- **유일성(Uniqueness)**: 중복 값이 있으면 페이지 경계에서 데이터가 누락될 수 있다.
- **정렬 가능성(Orderability)**: 비교 연산(`<`, `>`)이 가능해야 한다.
- **불변성(Immutability)**: 커서 기준 컬럼이 변경되면 동일한 데이터를 다시 조회하거나 건너뛸 수 있다.

`id`(자동 증가 PK)나 `(created_at, id)` 복합 커서가 대표적이다. `created_at` 단독으로는 중복이 발생할 수 있으므로, 실무에서는 복합 커서를 많이 사용한다.

## 실전 예제

### 도메인 설정

게시글 목록을 최신순으로 조회하는 API를 예제로 사용한다.

```sql
CREATE TABLE posts (
    id          BIGINT       NOT NULL AUTO_INCREMENT,
    title       VARCHAR(255) NOT NULL,
    content     TEXT,
    created_at  DATETIME(6)  NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    PRIMARY KEY (id),
    INDEX idx_created_at_id (created_at DESC, id DESC)
);
```

### Repository 구현 (Spring Data JPA + QueryDSL)

```java
@Repository
@RequiredArgsConstructor
public class PostRepositoryCustomImpl implements PostRepositoryCustom {

    private final JPAQueryFactory queryFactory;

    public Slice<Post> findPostsByCursor(CursorRequest request, int size) {
        QPost post = QPost.post;

        BooleanExpression cursorCondition = buildCursorCondition(post, request);

        List<Post> posts = queryFactory
            .selectFrom(post)
            .where(cursorCondition)
            .orderBy(post.createdAt.desc(), post.id.desc())
            .limit(size + 1L) // 다음 페이지 존재 여부 확인용
            .fetch();

        boolean hasNext = posts.size() > size;
        if (hasNext) {
            posts.remove(posts.size() - 1);
        }

        return new SliceImpl<>(posts, Pageable.unpaged(), hasNext);
    }

    private BooleanExpression buildCursorCondition(QPost post, CursorRequest request) {
        if (request.getCursorCreatedAt() == null || request.getCursorId() == null) {
            return null; // 첫 페이지는 조건 없음
        }

        LocalDateTime cursorCreatedAt = request.getCursorCreatedAt();
        Long cursorId = request.getCursorId();

        // (created_at, id) 복합 커서 조건
        // created_at이 같다면 id로 구분
        return post.createdAt.lt(cursorCreatedAt)
            .or(post.createdAt.eq(cursorCreatedAt)
                .and(post.id.lt(cursorId)));
    }
}
```

### 커서 요청/응답 DTO

```java
@Getter
@NoArgsConstructor
public class CursorRequest {
    private LocalDateTime cursorCreatedAt;
    private Long cursorId;

    public CursorRequest(LocalDateTime cursorCreatedAt, Long cursorId) {
        this.cursorCreatedAt = cursorCreatedAt;
        this.cursorId = cursorId;
    }

    public boolean isFirstPage() {
        return cursorCreatedAt == null && cursorId == null;
    }
}

@Getter
@Builder
public class PostCursorResponse {
    private List<PostDto> posts;
    private boolean hasNext;
    private String nextCursor; // Base64 인코딩된 커서

    public static PostCursorResponse of(Slice<Post> slice) {
        List<PostDto> postDtos = slice.getContent()
            .stream()
            .map(PostDto::from)
            .collect(Collectors.toList());

        String nextCursor = null;
        if (slice.hasNext()) {
            Post lastPost = slice.getContent().get(slice.getContent().size() - 1);
            nextCursor = CursorEncoder.encode(lastPost.getCreatedAt(), lastPost.getId());
        }

        return PostCursorResponse.builder()
            .posts(postDtos)
            .hasNext(slice.hasNext())
            .nextCursor(nextCursor)
            .build();
    }
}
```

### 커서 인코딩/디코딩 유틸리티

커서 값을 URL 파라미터로 노출할 때는 불투명(opaque)하게 처리하는 것이 좋다. 클라이언트가 커서 값을 직접 조작하는 것을 방지하고, 내부 구현을 숨길 수 있다.

```java
public class CursorEncoder {

    private static final String DELIMITER = ":";

    public static String encode(LocalDateTime createdAt, Long id) {
        String raw = createdAt.toString() + DELIMITER + id;
        return Base64.getUrlEncoder()
            .encodeToString(raw.getBytes(StandardCharsets.UTF_8));
    }

    public static CursorRequest decode(String cursor) {
        if (cursor == null || cursor.isBlank()) {
            return new CursorRequest();
        }
        try {
            byte[] decoded = Base64.getUrlDecoder().decode(cursor);
            String raw = new String(decoded, StandardCharsets.UTF_8);
            String[] parts = raw.split(DELIMITER, 2);

            LocalDateTime createdAt = LocalDateTime.parse(parts[0]);
            Long id = Long.parseLong(parts[1]);
            return new CursorRequest(createdAt, id);
        } catch (Exception e) {
            throw new InvalidCursorException("유효하지 않은 커서입니다.");
        }
    }
}
```

### API 컨트롤러

```java
@RestController
@RequestMapping("/api/v1/posts")
@RequiredArgsConstructor
public class PostController {

    private final PostService postService;

    @GetMapping
    public ResponseEntity<PostCursorResponse> getPosts(
        @RequestParam(required = false) String cursor,
        @RequestParam(defaultValue = "20") @Max(100) int size
    ) {
        CursorRequest cursorRequest = CursorEncoder.decode(cursor);
        PostCursorResponse response = postService.getPosts(cursorRequest, size);
        return ResponseEntity.ok(response);
    }
}
```

## 주의사항 및 트레이드오프

### 1. 역방향 페이지 이동이 어렵다

커서 기반 방식은 기본적으로 **단방향(forward-only)** 이다. 이전 페이지로 돌아가려면 별도의 커서 스택을 클라이언트에서 관리하거나, 서버에서 세션/캐시로 커서 히스토리를 유지해야 한다.

무한 스크롤(infinite scroll) UI에는 적합하지만, "3페이지로 이동" 같은 **임의 페이지 점프**는 지원하기 어렵다. 이런 기능이 반드시 필요하다면 OFFSET 방식과 병행하거나, Elasticsearch 같은 검색 엔진의 `search_after`를 활용하는 것을 고려해야 한다.

### 2. 정렬 기준 변경의 복잡성

정렬 컬럼이 바뀌면 커서도 바뀌어야 한다. `created_at` 기준 커서와 `updated_at` 기준 커서는 서로 호환되지 않는다. 다양한 정렬 옵션을 지원해야 한다면 커서 구조를 설계할 때부터 확장 가능하게 만들어야 한다.

```java
// 정렬 타입별 커서를 구분하는 방식 예시
public record CursorPayload(
    String sortType,   // "LATEST", "POPULAR"
    String sortValue,  // 정렬 기준 값
    Long id
) {}
```

### 3. 복합 커서 조건의 SQL 복잡성

`(created_at, id)` 복합 커서 조건을 SQL로 표현하면 OR 조건이 등장한다. 대부분의 경우 인덱스를 잘 타지만, 일부 데이터베이스나 쿼리 플래너에 따라 예상과 다른 실행 계획이 나올 수 있다. 반드시 `EXPLAIN`으로 실행 계획을 확인해야 한다.

**Row Value Comparison**을 지원하는 데이터베이스(MySQL 8.0+, PostgreSQL)에서는 다음과 같이 더 간결하게 표현할 수 있다.

```sql
-- Row Value Comparison (튜플 비교)
SELECT * FROM posts
WHERE (created_at, id) < ('2024-01-15 10:00:00', 12345)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

### 4. 총 개수(Total Count) 제공의 어려움

커서 기반 방식에서는 전체 결과 수를 알기 어렵다. 커서 조회는 전체 집합을 탐색하지 않기 때문이다. "총 N건 중 M건" 같은 UI가 필요하다면 별도의 `COUNT` 쿼리를 병행해야 하는데, 이는 캐싱 전략과 함께 설계해야 한다.

### 5. 커서 유효성과 보안

클라이언트에서 전달하는 커서는 **반드시 검증**해야 한다. 악의적인 사용자가 커서 값을 조작해 권한 없는 데이터에 접근하거나, 서버에 부하를 주는 쿼리를 유발할 수 있다. 커서에 서명(HMAC)을 적용하거나, 서버 세션에 커서를 저장하는 방식을 고려한다.

| 항목 | OFFSET 방식 | 커서 방식 |
|------|------------|---------|
| 초기 구현 난이도 | 낮음 | 중간 |
| 대용량 성능 | 페이지 증가에 따라 저하 | 일정하게 유지 |
| 임의 페이지 이동 | 가능 | 어려움 |
| 실시간 데이터 안정성 | 취약 | 강함 |
| 총 개수 제공 | 용이 | 어려움 |
| 정렬 변경 | 쉬움 | 복잡 |

## 정리

커서 기반 페이지네이션은 만능 해결책이 아니다. 다음 기준으로 방식을 선택하는 것을 권장한다.

- **OFFSET 방식이 적합한 경우**: 데이터가 적고(수십만 건 이하), 임의 페이지 이동이 필요하며, 실시간 데이터 변경이 드문 경우.
- **커서 방식이 적합한 경우**: 데이터가 수백만 건 이상이고, 무한 스크롤이나 단방향 탐색 UI를 사용하며, 데이터가 실시간으로 변경되는 피드·타임라인·로그 조회.

실무에서는 두 방식을 혼용하는 경우도 많다. 관리자 페이지처럼 데이터 건수가 적고 페이지 이동이 중요한 곳은 OFFSET, 사용자 피드처럼 대용량이면서 무한 스크롤인 곳은 커서 방식을 택하는 것이 현실적인 접근이다.

커서 기반 설계의 핵심은 **올바른 인덱스 설계**와 **커서 컬럼의 유일성 보장**이다. 이 두 가지를 놓치면 커서 방식을 쓰더라도 성능 이점을 얻을 수 없다. 설계 초기에 `EXPLAIN` 분석을 습관화하고, 실제 데이터 볼륨에 가까운 환경에서 부하 테스트를 반드시 진행하길 권한다.
