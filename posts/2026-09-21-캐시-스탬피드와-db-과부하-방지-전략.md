# 캐시 스탬피드와 DB 과부하 방지 전략

## 개요

캐시는 데이터베이스 부하를 줄이고 응답 속도를 높이는 가장 효과적인 수단 중 하나입니다. 그런데 아이러니하게도, 캐시가 만료되는 순간 오히려 DB에 폭발적인 트래픽이 몰릴 수 있습니다. 이 현상을 **캐시 스탬피드(Cache Stampede)** 또는 **썬더링 허드(Thundering Herd)** 라고 부릅니다.

고트래픽 서비스에서 인기 있는 키의 캐시가 만료되면, 동시에 수백 개의 요청이 캐시 미스를 감지하고 모두 DB로 향합니다. 이때 DB는 갑작스러운 부하를 감당하지 못해 응답 시간이 급증하고, 심각한 경우 서비스 장애로 이어집니다. 이 글에서는 캐시 스탬피드가 발생하는 원인을 이해하고, 실무에서 적용 가능한 방지 전략들을 코드와 함께 살펴봅니다.

---

## 핵심 개념

### 캐시 스탬피드란?

```
T=0   : 캐시 키 "product:1234" TTL 만료
T=0+  : 요청 100개 동시에 캐시 미스 감지
T=0++ : 요청 100개 모두 DB 쿼리 실행
T=1   : DB 부하 급증, 응답 지연 또는 커넥션 풀 고갈
```

이 시나리오는 일반적인 Look-Aside 캐시 패턴에서 흔히 발생합니다. 캐시를 먼저 조회하고, 미스 시 DB를 조회한 뒤 결과를 다시 캐시에 저장하는 단순한 구조가 동시성 환경에서 취약점이 됩니다.

### 왜 위험한가?

- **DB 커넥션 풀 고갈**: 동시 쿼리가 몰리면 커넥션이 부족해져 대기 큐가 쌓입니다.
- **연쇄 장애**: DB 응답 지연 → API 응답 지연 → 클라이언트 타임아웃 → 재시도 폭발의 악순환.
- **Cold Start 증폭**: 배포 직후 또는 캐시 서버 재시작 시 모든 키가 동시에 없는 상태에서 시작합니다.

## 실전 예제

### 전략 1: 뮤텍스 락(Mutex Lock)을 이용한 단일 재충전

가장 직관적인 방법입니다. 캐시 미스가 발생했을 때 **하나의 요청만 DB를 조회**하도록 락을 걸고, 나머지 요청은 락이 해제될 때까지 대기하거나 이전 캐시 값을 반환합니다.

```java
@Service
@RequiredArgsConstructor
public class ProductCacheService {

    private final RedisTemplate<String, Product> redisTemplate;
    private final ProductRepository productRepository;
    private final RedissonClient redissonClient;

    private static final Duration CACHE_TTL = Duration.ofMinutes(10);
    private static final Duration LOCK_TTL = Duration.ofSeconds(5);

    public Product getProduct(Long productId) {
        String cacheKey = "product:" + productId;
        String lockKey = "lock:product:" + productId;

        // 1. 캐시 조회
        Product cached = redisTemplate.opsForValue().get(cacheKey);
        if (cached != null) {
            return cached;
        }

        // 2. 분산 락 획득 시도
        RLock lock = redissonClient.getLock(lockKey);
        try {
            boolean acquired = lock.tryLock(3, 5, TimeUnit.SECONDS);
            if (acquired) {
                // 3. 락 획득 후 다시 캐시 확인 (Double-Checked Locking)
                cached = redisTemplate.opsForValue().get(cacheKey);
                if (cached != null) {
                    return cached;
                }

                // 4. DB 조회 및 캐시 저장
                Product product = productRepository.findById(productId)
                    .orElseThrow(() -> new EntityNotFoundException("Product not found"));
                redisTemplate.opsForValue().set(cacheKey, product, CACHE_TTL);
                return product;
            } else {
                // 5. 락 획득 실패 시 재시도 또는 fallback
                Thread.sleep(100);
                cached = redisTemplate.opsForValue().get(cacheKey);
                return cached != null ? cached : productRepository.findById(productId).orElseThrow();
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new RuntimeException("Lock interrupted", e);
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```

> **포인트**: 락 획득 후 반드시 **Double-Checked Locking**을 적용해야 합니다. 락을 기다리던 스레드가 획득했을 때 이미 다른 스레드가 캐시를 채워놓았을 수 있기 때문입니다.

### 전략 2: 확률적 조기 갱신(Probabilistic Early Recomputation)

PER(Probabilistic Early Recomputation) 알고리즘은 TTL이 완전히 만료되기 **전에 확률적으로 캐시를 미리 갱신**하는 방법입니다. 만료에 가까울수록 갱신 확률이 높아집니다.

```java
@Component
public class ProbabilisticCacheManager {

    private final RedisTemplate<String, CacheEntry> redisTemplate;
    private final Random random = new Random();

    // beta: 갱신 적극성 조절 (1.0이 기본값, 높을수록 일찍 갱신)
    private static final double BETA = 1.0;

    public <T> T getWithEarlyRecompute(
            String key,
            Supplier<T> loader,
            Duration ttl,
            Class<T> type) {

        CacheEntry<T> entry = redisTemplate.opsForValue().get(key);

        if (entry != null) {
            long now = System.currentTimeMillis();
            long remainingMs = entry.getExpiresAt() - now;
            double recomputeTime = entry.getDeltaMs(); // 마지막 재계산에 걸린 시간

            // XFetch 알고리즘: 만료가 임박할수록 갱신 확률 증가
            double threshold = -recomputeTime * BETA * Math.log(random.nextDouble());

            if (remainingMs > threshold) {
                return entry.getValue(); // 아직 갱신 불필요
            }
        }

        // 캐시 미스 또는 조기 갱신 결정
        long start = System.currentTimeMillis();
        T value = loader.get();
        long delta = System.currentTimeMillis() - start;

        CacheEntry<T> newEntry = CacheEntry.<T>builder()
            .value(value)
            .expiresAt(System.currentTimeMillis() + ttl.toMillis())
            .deltaMs(delta)
            .build();

        redisTemplate.opsForValue().set(key, newEntry, ttl);
        return value;
    }
}

@Builder
@Getter
public class CacheEntry<T> {
    private T value;
    private long expiresAt;
    private long deltaMs; // DB 조회에 걸린 시간 (ms)
}
```

이 방법은 별도의 락 없이도 스탬피드를 완화할 수 있어 구현이 단순하고 락 경합이 없다는 장점이 있습니다.

### 전략 3: TTL 지터(Jitter) 적용

여러 키가 동시에 만료되는 것을 막는 가장 간단한 방법은 TTL에 **무작위 편차를 추가**하는 것입니다.

```java
@Component
public class JitteredCacheService {

    private final RedisTemplate<String, Object> redisTemplate;
    private final Random random = new Random();

    /**
     * 기본 TTL에 ±20% 범위의 지터를 추가
     */
    public void setWithJitter(String key, Object value, Duration baseTtl) {
        long baseTtlMs = baseTtl.toMillis();
        long jitterMs = (long) (baseTtlMs * 0.2 * (random.nextDouble() * 2 - 1));
        Duration finalTtl = Duration.ofMillis(baseTtlMs + jitterMs);

        redisTemplate.opsForValue().set(key, value, finalTtl);
    }

    /**
     * 배치 캐시 저장 시: 키별로 분산된 TTL 적용
     */
    public void setBatch(Map<String, Object> entries, Duration baseTtl) {
        entries.forEach((key, value) -> setWithJitter(key, value, baseTtl));
    }
}
```

TTL 지터는 단독으로 스탬피드를 완전히 막지는 못하지만, 다른 전략과 함께 사용하면 만료 시점을 분산시켜 전체적인 부하를 줄입니다.

### 전략 4: 백그라운드 비동기 갱신(Stale-While-Revalidate)

캐시가 만료되더라도 **이전 값(stale data)을 즉시 반환**하고, 갱신은 백그라운드에서 비동기로 처리합니다.

```java
@Service
@RequiredArgsConstructor
public class StaleWhileRevalidateService {

    private final RedisTemplate<String, StaleEntry> redisTemplate;
    private final Executor cacheRefreshExecutor;

    private static final Duration SOFT_TTL = Duration.ofMinutes(5);   // 신선도 기준
    private static final Duration HARD_TTL = Duration.ofMinutes(30);  // 실제 만료

    public <T> T get(String key, Supplier<T> loader) {
        StaleEntry<T> entry = redisTemplate.opsForValue().get(key);

        if (entry == null) {
            // 완전 캐시 미스: 동기 로딩
            return refreshSynchronously(key, loader);
        }

        if (entry.isStale()) {
            // Soft TTL 초과: 즉시 stale 값 반환 + 백그라운드 갱신
            triggerAsyncRefresh(key, loader);
            return entry.getValue();
        }

        return entry.getValue();
    }

    private <T> T refreshSynchronously(String key, Supplier<T> loader) {
        T value = loader.get();
        StaleEntry<T> entry = StaleEntry.<T>builder()
            .value(value)
            .createdAt(System.currentTimeMillis())
            .softTtlMs(SOFT_TTL.toMillis())
            .build();
        redisTemplate.opsForValue().set(key, entry, HARD_TTL);
        return value;
    }

    private <T> void triggerAsyncRefresh(String key, Supplier<T> loader) {
        cacheRefreshExecutor.execute(() -> {
            try {
                refreshSynchronously(key, loader);
            } catch (Exception e) {
                log.warn("Async cache refresh failed for key: {}", key, e);
            }
        });
    }
}

@Builder
@Getter
public class StaleEntry<T> {
    private T value;
    private long createdAt;
    private long softTtlMs;

    public boolean isStale() {
        return System.currentTimeMillis() - createdAt > softTtlMs;
    }
}
```

## 주의사항 및 트레이드오프

### 각 전략의 비교

| 전략 | 구현 복잡도 | 일관성 | 스탬피드 방지 효과 | 추가 인프라 |
|------|------------|--------|------------------|-----------|
| 뮤텍스 락 | 중간 | 높음 | 높음 | 분산 락 (Redisson 등) |
| 확률적 조기 갱신 | 높음 | 높음 | 중간 | 없음 |
| TTL 지터 | 낮음 | 높음 | 낮음 | 없음 |
| Stale-While-Revalidate | 중간 | 낮음 | 높음 | 비동기 실행기 |

### 뮤텍스 락의 함정

- **락 타임아웃 설정이 핵심**입니다. DB 쿼리가 5초 걸린다면 락 TTL은 그보다 길어야 합니다. 너무 짧으면 락이 자동 해제되어 복수의 스레드가 DB를 조회합니다.
- 분산 락 서버(Redis)가 SPOF가 될 수 있습니다. Redlock 알고리즘을 고려하거나, 락 실패 시 graceful degradation 전략을 마련해두어야 합니다.

### Stale 데이터의 허용 범위

Stale-While-Revalidate는 **데이터 일관성이 낮아도 되는 경우**에만 적합합니다. 상품 재고, 주문 상태, 금융 데이터처럼 실시간성이 중요한 데이터에는 적용하면 안 됩니다. 반면 추천 리스트, 통계 데이터, 카테고리 정보 등에는 매우 효과적입니다.

### 워밍업(Cache Warming) 전략 병행

배포 직후 Cold Start 문제를 막으려면 캐시 워밍업이 필요합니다.

```java
@Component
@RequiredArgsConstructor
public class CacheWarmupRunner implements ApplicationRunner {

    private final ProductCacheService cacheService;
    private final ProductRepository productRepository;

    @Override
    public void run(ApplicationArguments args) {
        log.info("Starting cache warmup...");
        // 인기 상품 상위 N개를 사전 로딩
        productRepository.findTopPopularProducts(100)
            .forEach(product -> cacheService.warmup(product.getId()));
        log.info("Cache warmup completed.");
    }
}
```

### DB 레벨에서의 방어

캐시 전략만으로 완벽하지 않습니다. DB 레벨에서도 방어선을 구축해야 합니다.

- **커넥션 풀 적절히 설정**: HikariCP의 `maximumPoolSize`는 무조건 크게 설정하는 것이 능사가 아닙니다. DB 서버의 실제 처리 한계를 고려해 설정해야 합니다.
- **쿼리 타임아웃 설정**: 스탬피드 상황에서 슬로우 쿼리가 커넥션을 점유하지 않도록 합니다.
- **Read Replica 활용**: 캐시 미스 시 Read Replica에서 조회하면 Primary DB 부하를 분산할 수 있습니다.

## 정리

캐시 스탬피드는 단순한 Look-Aside 패턴의 구조적 취약점에서 비롯됩니다. 이를 해결하기 위한 전략은 하나만 선택할 필요가 없으며, 서비스의 특성에 따라 **조합해서 사용하는 것이 일반적**입니다.

- **데이터 일관성이 중요하고 트래픽이 높다면** → 뮤텍스 락 + TTL 지터
- **응답 속도가 최우선이고 약간의 stale이 허용된다면** → Stale-While-Revalidate + TTL 지터
- **구현 리소스가 제한적이라면** → TTL 지터만으로 시작하고 점진적으로 고도화

가장 중요한 것은 **캐시 장애를 DB가 대신 흡수할 수 있는 구조를 만들지 않는 것**입니다. 캐시는 DB를 보조하는 존재이지, DB가 캐시의 장애를 감당하는 구조가 되어선 안 됩니다. 스탬피드 방지 전략은 결국 이 원칙을 지키기 위한 방어막입니다.
