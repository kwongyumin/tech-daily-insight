# 영지식 증명(ZKP) 개념과 프라이버시 보호 활용

## 개요

블록체인의 가장 큰 딜레마 중 하나는 **투명성과 프라이버시의 공존**이다. 퍼블릭 블록체인은 모든 트랜잭션이 공개되어 감사 가능성(auditability)을 보장하지만, 그만큼 민감한 비즈니스 로직이나 개인 정보가 노출되는 문제가 있다. 이 딜레마를 우아하게 해결하는 암호학적 기법이 바로 **영지식 증명(Zero-Knowledge Proof, ZKP)**이다.

ZKP는 "어떤 명제가 참임을 증명할 때, 그 명제가 참이라는 사실 외에 아무런 추가 정보도 공개하지 않는" 암호학적 프로토콜이다. 예컨대 자신이 성인임을 증명하면서 실제 생년월일은 노출하지 않거나, 특정 계좌의 잔액이 충분하다는 것을 증명하면서 정확한 잔액은 숨길 수 있다.

이 글에서는 ZKP의 핵심 개념을 정리하고, 실제 개발에 활용할 수 있는 **zk-SNARK** 기반 예제를 통해 프라이버시 보호 시스템을 구축하는 방법을 살펴본다.

## 핵심 개념

### ZKP의 세 가지 속성

ZKP가 유효하려면 다음 세 가지 수학적 속성을 만족해야 한다.

| 속성 | 설명 |
|---|---|
| **완전성 (Completeness)** | 명제가 참이면, 정직한 증명자(Prover)는 검증자(Verifier)를 납득시킬 수 있다. |
| **건전성 (Soundness)** | 명제가 거짓이면, 어떠한 부정직한 증명자도 검증자를 납득시킬 수 없다. |
| **영지식성 (Zero-Knowledge)** | 검증자는 명제의 참/거짓 여부 외에 아무 정보도 얻지 못한다. |

### zk-SNARK vs zk-STARK

실무에서 가장 많이 사용되는 ZKP 시스템은 두 가지다.

- **zk-SNARK** (Zero-Knowledge Succinct Non-Interactive Argument of Knowledge)
  - 증명 크기가 매우 작고 검증 속도가 빠름
  - **Trusted Setup** 필요 (초기 파라미터 생성 시 신뢰 가정 존재)
  - Zcash, Tornado Cash, Polygon zkEVM에서 사용
  - 라이브러리: Circom, SnarkJS, Groth16

- **zk-STARK** (Zero-Knowledge Scalable Transparent Argument of Knowledge)
  - Trusted Setup 불필요 (투명성 보장)
  - 증명 크기가 상대적으로 크지만 양자 컴퓨터에 강인
  - StarkNet에서 사용
  - 라이브러리: Cairo, Stone Prover

### 회로(Circuit)란?

ZKP에서 증명하고 싶은 연산은 **산술 회로(Arithmetic Circuit)**로 표현된다. 회로는 덧셈 게이트와 곱셈 게이트로 구성되며, 이를 **R1CS(Rank-1 Constraint System)**로 변환한 뒤 증명을 생성한다.

```
비밀 입력(private input) + 공개 입력(public input) → 회로 → 증명(Proof)
                                                              ↓
                                                         검증자(Verifier)
```

### 예제 1: 나이 검증 회로 (성인 여부 증명)

생년월일을 공개하지 않고 "만 18세 이상"임을 증명하는 회로를 작성한다.

**`age_verify.circom`**

```circom
pragma circom 2.0.0;

include "node_modules/circomlib/circuits/comparators.circom";

/*
 * AgeVerifier Circuit
 * private input: age (실제 나이, 비공개)
 * public input: threshold (기준 나이, 공개)
 * output: 나이 >= threshold 임을 증명
 */
template AgeVerifier() {
    // private signal: 증명자만 알고 있는 실제 나이
    signal input age;
    
    // public signal: 검증자도 알고 있는 기준 나이
    signal input threshold;
    
    // GreaterEqThan: age >= threshold 이면 1, 아니면 0 반환
    // 비트 수는 8 (0~255 범위)
    component gte = GreaterEqThan(8);
    gte.in[0] <== age;
    gte.in[1] <== threshold;
    
    // 반드시 1이어야 함을 제약 조건으로 강제
    gte.out === 1;
}

component main { public [threshold] } = AgeVerifier();
```

**회로 컴파일 및 증명 생성**

```bash
# 1. 회로 컴파일
circom age_verify.circom --r1cs --wasm --sym -o ./build

# 2. Powers of Tau (Trusted Setup Phase 1)
snarkjs powersoftau new bn128 12 pot12_0000.ptau -v
snarkjs powersoftau contribute pot12_0000.ptau pot12_0001.ptau \
  --name="First contribution" -v

# 3. Phase 2 Setup (회로별 설정)
snarkjs powersoftau prepare phase2 pot12_0001.ptau pot12_final.ptau -v
snarkjs groth16 setup build/age_verify.r1cs pot12_final.ptau \
  age_verify_0000.zkey

# 4. Verification Key 추출
snarkjs zkey export verificationkey age_verify_0000.zkey verification_key.json
```

**증명 생성 (Node.js)**

```javascript
// generate_proof.js
const snarkjs = require("snarkjs");
const fs = require("fs");

async function generateAgeProof(actualAge, threshold) {
    // private input은 증명자 로컬에서만 처리됨
    const input = {
        age: actualAge,       // 비공개: 실제 나이 (예: 25)
        threshold: threshold  // 공개: 기준 나이 (예: 18)
    };

    // witness 계산 및 증명 생성
    const { proof, publicSignals } = await snarkjs.groth16.fullProve(
        input,
        "./build/age_verify_js/age_verify.wasm",
        "./age_verify_0000.zkey"
    );

    console.log("생성된 증명(Proof):", JSON.stringify(proof, null, 2));
    console.log("공개 신호(Public Signals):", publicSignals);
    // publicSignals에는 threshold만 포함됨. 실제 나이(age)는 절대 노출되지 않음.

    return { proof, publicSignals };
}

async function verifyProof(proof, publicSignals) {
    const verificationKey = JSON.parse(
        fs.readFileSync("./verification_key.json")
    );

    const isValid = await snarkjs.groth16.verify(
        verificationKey,
        publicSignals,
        proof
    );

    console.log(`증명 검증 결과: ${isValid ? "✅ 유효" : "❌ 무효"}`);
    return isValid;
}

// 실행
(async () => {
    // 실제 나이 25세, 기준 18세 → 성인 증명
    const { proof, publicSignals } = await generateAgeProof(25, 18);
    await verifyProof(proof, publicSignals);

    // 미성년자 시도: 실제 나이 16세 → 증명 생성 자체가 실패
    try {
        await generateAgeProof(16, 18);
    } catch (e) {
        console.log("❌ 조건 불만족: 증명 생성 불가", e.message);
    }
})();
```

### 예제 2: Solidity 온체인 검증

생성된 증명을 이더리움 스마트 컨트랙트에서 검증하는 예제다.

```bash
# Solidity 검증 컨트랙트 자동 생성
snarkjs zkey export solidityverifier age_verify_0000.zkey AgeVerifier.sol
```

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.19;

// snarkjs가 자동 생성한 Verifier 컨트랙트를 import
import "./AgeVerifier.sol";

contract AgeGatedService {
    Groth16Verifier public verifier;
    
    // 검증된 주소 목록 (실제 나이는 온체인에 저장되지 않음)
    mapping(address => bool) public verifiedAdults;

    event AgeVerified(address indexed user, uint256 threshold);

    constructor(address _verifier) {
        verifier = Groth16Verifier(_verifier);
    }

    /**
     * @notice ZKP를 통해 성인 여부를 검증하고 서비스 접근 권한 부여
     * @param proof zk-SNARK 증명
     * @param pubSignals 공개 신호 [threshold]
     * 
     * 핵심: 실제 나이(age)는 절대 온체인에 기록되지 않음
     */
    function verifyAdulthood(
        uint[2] calldata _pA,
        uint[2][2] calldata _pB,
        uint[2] calldata _pC,
        uint[1] calldata _pubSignals
    ) external {
        uint256 threshold = _pubSignals[0];
        require(threshold >= 18, "Invalid threshold");

        // 온체인 ZKP 검증 (가스 비용 발생)
        bool valid = verifier.verifyProof(_pA, _pB, _pC, _pubSignals);
        require(valid, "Invalid age proof");

        verifiedAdults[msg.sender] = true;
        emit AgeVerified(msg.sender, threshold);
    }

    modifier onlyVerifiedAdult() {
        require(verifiedAdults[msg.sender], "Age verification required");
        _;
    }

    function accessRestrictedContent() external onlyVerifiedAdult {
        // 성인 인증된 사용자만 접근 가능한 서비스 로직
    }
}
```

## 주의사항 및 트레이드오프

### ⚠️ Trusted Setup의 위험성

zk-SNARK의 Groth16 방식은 초기 **Trusted Setup(독성 폐기물, Toxic Waste)** 파라미터 생성 시 참여자가 비밀 값을 완전히 폐기해야 한다. 만약 이 값이 유출된다면 **허위 증명을 생성**할 수 있다.

```
⚠️ 대응 방안:
- Multi-Party Computation (MPC) 세리머니 활용
- Powers of Tau 퍼블릭 세리머니 참여자 수 극대화
- 가능하면 Universal Setup(PLONK, Marlin) 또는 zk-STARK 고려
```

### ⚠️ 높은 계산 복잡도

증명 생성(Proving)은 검증(Verification)에 비해 수십~수백 배 더 많은 연산을 요구한다. 복잡한 회로일수록 클라이언트 부담이 크다.

| 단계 | 시간 | 주체 |
|---|---|---|
| 증명 생성 | 수백ms ~ 수십초 | 클라이언트 (증명자) |
| 온체인 검증 | ~수ms | 스마트 컨트랙트 |
| 오프체인 검증 | ~수ms | 서버 |

### ⚠️ 회로 버그는 치명적

회로에 로직 오류가 있으면 잘못된 명제를 증명할 수 있다. **스마트 컨트랙트보다 더 엄밀한 형식 검증(Formal Verification)**이 필요하다.

```bash
# circom의 --inspect 플래그로 under-constrained 신호 탐지
circom age_verify.circom --r1cs --inspect
```

### ⚠️ 온체인 검증 가스 비용

Groth16 온체인 검증은 약 **200,000~300,000 gas**가 소모된다. 잦은 검증이 필요한 경우 레이어2(Layer 2) 또는 오프체인 검증을 고려해야 한다.

```
비용 최적화 전략:
1. 오프체인 검증 후 서명만 온체인 저장
2. zkRollup 방식으로 다수의 증명을 배치 처리
3. PLONK 방식으로 검증 비용 절감
```

## 정리

ZKP는 단순한 학문적 개념이 아니라, **프라이버시 보호 DeFi, 신원 증명, 컴플라이언스** 등 실제 프로덕션 시스템에 점점 더 폭넓게 적용되고 있다.

핵심 요약:

- **ZKP = 정보를 공개하지 않고 사실을 증명하는 암호학적 기법**
- Circom + SnarkJS로 비교적 쉽게 zk-SNARK 회로를 작성하고 검증 컨트랙트를 생성할 수 있다.
- Trusted Setup, 계산 복잡도, 회로 버그, 가스 비용은 반드시 고려해야 할 트레이드오프다.
- 규모와 요구사항에 따라 **Groth16 → PLONK → zk-STARK** 순으로 마이그레이션을 검토하라.

ZKP 생태계는 빠르게 발전하고 있으며, **zkEVM(Polygon, Scroll, zkSync)** 의 등장으로 기존 EVM 컨트랙트에 ZKP를 투명하게 적용하는 것도 가능해지고 있다. 프라이버시가 중요한 엔터프라이즈 블록체인 프로젝트를 설계한다면, ZKP를 아키텍처 초기 단계부터 진지하게 고려할 것을 권장한다.
