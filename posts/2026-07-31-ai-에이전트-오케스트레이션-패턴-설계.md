# AI 에이전트 오케스트레이션 패턴 설계

## 개요

LLM(Large Language Model) 기반 AI 에이전트가 단순 챗봇 수준을 넘어 복잡한 비즈니스 로직을 수행하는 시대가 도래했다. 단일 에이전트로는 처리하기 어려운 태스크를 여러 전문화된 에이전트가 협력하여 해결하는 **멀티 에이전트 시스템(Multi-Agent System)**이 실무 아키텍처로 빠르게 자리잡고 있다.

그러나 단순히 에이전트를 여러 개 만드는 것만으로는 충분하지 않다. 에이전트 간의 통신, 작업 분배, 오류 처리, 상태 관리를 어떻게 설계하느냐에 따라 시스템의 안정성과 성능이 극명하게 갈린다. 이 글에서는 실무에서 검증된 AI 에이전트 오케스트레이션 패턴을 소개하고, Java/Spring 환경에서 바로 적용할 수 있는 구체적인 구현 예제를 함께 다룬다.

## 핵심 개념

### 오케스트레이션 vs 코레오그래피

에이전트 조율 방식은 크게 두 가지로 나뉜다.

| 구분 | 오케스트레이션 (Orchestration) | 코레오그래피 (Choreography) |
|------|-------------------------------|----------------------------|
| 제어 방식 | 중앙 집중형 (Supervisor 존재) | 분산형 (이벤트 기반) |
| 복잡도 | 낮음 (흐름 파악 용이) | 높음 (전체 흐름 추적 어려움) |
| 확장성 | 제한적 | 높음 |
| 적합한 상황 | 순차 의존적 태스크 | 독립적 병렬 태스크 |

실무에서는 두 방식을 혼합하는 **하이브리드 패턴**이 가장 효과적이다.

### 주요 오케스트레이션 패턴

**1. Supervisor Pattern**
하나의 오케스트레이터 에이전트가 하위 에이전트들에게 태스크를 위임하고 결과를 취합한다.

**2. Plan-and-Execute Pattern**
먼저 전체 실행 계획을 수립(Plan)한 뒤 각 단계를 순차적으로 실행(Execute)한다. 복잡한 태스크에서 토큰 낭비를 줄이는 데 효과적이다.

**3. Reflective Pattern**
에이전트가 자신의 출력을 스스로 평가하고 개선하는 자기 반성(Self-reflection) 루프를 포함한다.

**4. Parallel Fan-out Pattern**
독립적인 서브태스크를 병렬로 실행하고 결과를 집계한다.

### AgentContext - 공유 상태 관리

에이전트 간 컨텍스트를 안전하게 전달하기 위한 불변 객체를 설계한다.

```java
@Builder
@Getter
public class AgentContext {
    private final String sessionId;
    private final String userQuery;
    private final Map<String, Object> metadata;
    private final List<TaskResult> previousResults;

    public AgentContext withResult(TaskResult result) {
        List<TaskResult> updatedResults = new ArrayList<>(this.previousResults);
        updatedResults.add(result);
        return AgentContext.builder()
                .sessionId(this.sessionId)
                .userQuery(this.userQuery)
                .metadata(this.metadata)
                .previousResults(Collections.unmodifiableList(updatedResults))
                .build();
    }
}
```

### Supervisor Pattern 구현

```java
@Component
@RequiredArgsConstructor
@Slf4j
public class SupervisorAgent {

    private final ClassifierAgent classifierAgent;
    private final KnowledgeAgent knowledgeAgent;
    private final ResponseAgent responseAgent;

    public String process(String userQuery) {
        AgentContext context = AgentContext.builder()
                .sessionId(UUID.randomUUID().toString())
                .userQuery(userQuery)
                .metadata(new HashMap<>())
                .previousResults(new ArrayList<>())
                .build();

        // Step 1: 문의 유형 분류
        TaskResult classificationResult = classifierAgent.execute(context);
        if (!classificationResult.isSuccess()) {
            log.error("Classification failed: {}", classificationResult.getError());
            return "처리 중 오류가 발생했습니다.";
        }
        context = context.withResult(classificationResult);

        // Step 2: 분류 결과에 따라 동적 에이전트 라우팅
        String category = (String) classificationResult.getData().get("category");
        TaskResult knowledgeResult = knowledgeAgent.execute(context, category);
        context = context.withResult(knowledgeResult);

        // Step 3: 최종 응답 생성
        return responseAgent.generate(context);
    }
}
```

### Parallel Fan-out Pattern 구현

독립적인 에이전트를 병렬로 실행하여 응답 시간을 단축한다.

```java
@Service
@RequiredArgsConstructor
public class ParallelOrchestrator {

    private final List<AnalysisAgent> analysisAgents;
    
    @Qualifier("agentTaskExecutor")
    private final Executor taskExecutor;

    public AggregatedResult executeParallel(AgentContext context) {
        List<CompletableFuture<TaskResult>> futures = analysisAgents.stream()
                .map(agent -> CompletableFuture
                        .supplyAsync(() -> agent.execute(context), taskExecutor)
                        .orTimeout(30, TimeUnit.SECONDS)
                        .exceptionally(ex -> {
                            log.warn("Agent {} failed: {}", agent.getName(), ex.getMessage());
                            return TaskResult.failed(agent.getName(), ex.getMessage());
                        }))
                .collect(Collectors.toList());

        List<TaskResult> results = futures.stream()
                .map(CompletableFuture::join)
                .collect(Collectors.toList());

        return aggregate(results);
    }

    private AggregatedResult aggregate(List<TaskResult> results) {
        Map<String, Object> mergedData = results.stream()
                .filter(TaskResult::isSuccess)
                .flatMap(r -> r.getData().entrySet().stream())
                .collect(Collectors.toMap(
                        Map.Entry::getKey,
                        Map.Entry::getValue,
                        (v1, v2) -> v2  // 충돌 시 후행 값 우선
                ));

        long successCount = results.stream().filter(TaskResult::isSuccess).count();

        return AggregatedResult.builder()
                .data(mergedData)
                .successRate((double) successCount / results.size())
                .build();
    }
}
```

### Reflective Pattern - 자기 개선 루프

```java
@Component
@RequiredArgsConstructor
public class ReflectiveResponseAgent {

    private final LlmClient llmClient;
    private static final int MAX_REFLECTION_ROUNDS = 3;
    private static final double QUALITY_THRESHOLD = 0.85;

    public String generateWithReflection(AgentContext context) {
        String response = llmClient.generate(buildPrompt(context));
        
        for (int round = 0; round < MAX_REFLECTION_ROUNDS; round++) {
            double qualityScore = evaluateQuality(response, context.getUserQuery());
            
            log.debug("Reflection round {}: quality score = {}", round + 1, qualityScore);
            
            if (qualityScore >= QUALITY_THRESHOLD) {
                break;
            }
            
            // 품질이 기준 미달이면 개선 프롬프트로 재생성
            String refinementPrompt = buildRefinementPrompt(
                    context.getUserQuery(), response, qualityScore);
            response = llmClient.generate(refinementPrompt);
        }
        
        return response;
    }

    private double evaluateQuality(String response, String originalQuery) {
        String evalPrompt = """
                다음 응답의 품질을 0.0 ~ 1.0 점수로만 평가하세요.
                원본 질문: %s
                생성된 응답: %s
                점수만 숫자로 출력하세요.
                """.formatted(originalQuery, response);

        String scoreStr = llmClient.generate(evalPrompt).trim();
        return Double.parseDouble(scoreStr);
    }
}
```

### Spring Configuration

```java
@Configuration
@EnableAsync
public class AgentConfig {

    @Bean(name = "agentTaskExecutor")
    public ThreadPoolTaskExecutor agentTaskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(5);
        executor.setMaxPoolSize(20);
        executor.setQueueCapacity(100);
        executor.setThreadNamePrefix("agent-worker-");
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        executor.setWaitForTasksToCompleteOnShutdown(true);
        executor.setAwaitTerminationSeconds(30);
        executor.initialize();
        return executor;
    }

    @Bean
    public RetryTemplate agentRetryTemplate() {
        return RetryTemplate.builder()
                .maxAttempts(3)
                .exponentialBackoff(500, 2.0, 5000)
                .retryOn(LlmApiException.class)
                .build();
    }
}
```

## 주의사항 및 트레이드오프

### 1. 토큰 비용 폭발 문제

멀티 에이전트 시스템에서 가장 간과하기 쉬운 문제다. 에이전트가 체인으로 연결될수록 이전 컨텍스트가 누적되어 **토큰 사용량이 기하급수적으로 증가**한다.

**대응 전략:**
- 에이전트 간 전달 컨텍스트를 최소화하고 **요약(summarization)** 단계를 삽입한다.
- `previousResults`에는 전체 raw 결과 대신 핵심 키-값만 담는다.
- LLM 호출 결과를 Redis 등에 **단기 캐싱**하여 동일 입력의 중복 호출을 방지한다.

### 2. 에이전트 루프(Loop) 탈출 실패

Reflective Pattern이나 자율적 의사결정 에이전트에서 루프를 탈출하지 못하는 현상이 발생할 수 있다. 반드시 **최대 반복 횟수와 타임아웃**을 하드코딩으로 강제해야 한다.

```java
// 절대 이렇게 하지 말 것 - 무한 루프 가능
while (!isGoodEnough(response)) {
    response = improve(response);
}

// 반드시 탈출 조건을 명시적으로 설정
for (int i = 0; i < MAX_ITERATIONS; i++) {
    if (isGoodEnough(response)) break;
    response = improve(response);
}
```

### 3. 에이전트 간 신뢰 문제

한 에이전트의 잘못된 출력이 하위 에이전트로 전파되는 **오류 증폭(Error Amplification)** 현상을 주의해야 한다. 각 에이전트의 출력에 대한 **스키마 검증**과 **신뢰 점수 임계값**을 설정하는 것이 중요하다.

### 4. 관찰 가능성(Observability) 확보

에이전트가 중첩될수록 디버깅이 기하급수적으로 어려워진다. **LangSmith**, **Langfuse**, **OpenTelemetry** 등의 도구를 통해 각 에이전트의 입출력, 지연 시간, 토큰 사용량을 트레이싱해야 한다.

```java
@Aspect
@Component
@Slf4j
public class AgentTracingAspect {

    @Around("@annotation(TraceAgent)")
    public Object traceAgentExecution(ProceedingJoinPoint pjp) throws Throwable {
        String agentName = pjp.getSignature().getDeclaringTypeName();
        long startTime = System.currentTimeMillis();
        
        try {
            Object result = pjp.proceed();
            long elapsed = System.currentTimeMillis() - startTime;
            log.info("[AGENT_TRACE] agent={}, status=SUCCESS, elapsed={}ms", agentName, elapsed);
            return result;
        } catch (Exception e) {
            log.error("[AGENT_TRACE] agent={}, status=FAILED, error={}", agentName, e.getMessage());
            throw e;
        }
    }
}
```

### 5. 결정론적 vs 확률론적 트레이드오프

LLM 기반 에이전트는 본질적으로 확률론적이다. 동일한 입력에도 다른 결과가 나올 수 있어, **금융이나 의료처럼 결정론적 정확성이 요구되는 도메인**에서는 에이전트의 역할을 보조(Assist) 수준으로 제한하고 최종 의사결정은 규칙 기반 시스템에 위임해야 한다.

## 정리

AI 에이전트 오케스트레이션은 단순한 LLM API 호출의 연결이 아니다. 분산 시스템 설계의 원칙—내결함성, 관찰 가능성, 확장성—이 그대로 적용된다.

핵심을 정리하면 다음과 같다.

- **Supervisor Pattern**: 복잡도가 낮고 흐름이 명확한 시나리오에 적합
- **Plan-and-Execute**: 장기 태스크의 토큰 효율을 높이는 데 효과적
- **Reflective Pattern**: 출력 품질이 중요한 콘텐츠 생성에 활용
- **Parallel Fan-out**: 독립적 분석 태스크의 응답 시간 단축

어떤 패턴을 선택하든 **명시적인 루프 탈출 조건**, **컨텍스트 크기 관리**, **분산 트레이싱** 세 가지는 반드시 구현해야 한다. 멀티 에이전트 시스템의 복잡성은 기능이 추가될수록 가파르게 증가하므로, 초기 설계 단계에서 인터페이스를 명확히 정의하고 각 에이전트의 책임을 단일 원칙으로 제한하는 것이 장기적인 유지보수의 핵심이다.
