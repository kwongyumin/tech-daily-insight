# 외부 가맹점용 Open API 플랫폼 설계

## 개요

핀테크, 커머스, 결제 플랫폼이 성장하면서 외부 가맹점(Partner)에게 자사 서비스 기능을 API로 제공하는 Open API 플랫폼 수요가 급증하고 있다. 단순히 REST API를 외부에 노출하는 것과, 수백~수천 개의 가맹점이 안전하고 안정적으로 사용할 수 있는 **플랫폼**을 설계하는 것은 완전히 다른 문제다.

이 글에서는 외부 가맹점용 Open API 플랫폼을 설계할 때 반드시 고려해야 할 핵심 요소들을 실무 관점에서 다룬다. 인증/인가, API Gateway 구성, Rate Limiting, 버전 관리, 요청/응답 표준화까지 실전 코드와 함께 살펴본다.

---

## 핵심 개념

### 1. 인증 체계 설계: OAuth 2.0 Client Credentials

외부 가맹점은 사용자(User)가 아니라 **시스템(Machine-to-Machine)** 으로 API를 호출한다. 이 경우 OAuth 2.0의 **Client Credentials Flow**가 가장 적합하다.

```
가맹점 서버 → [POST /oauth/token] → Authorization Server
             ← Access Token (JWT) ←
가맹점 서버 → [API 호출 + Bearer Token] → API Gateway
                                         → Resource Server
```

각 가맹점에게 `client_id`와 `client_secret`을 발급하고, 이를 통해 Access Token을 획득하는 구조다. JWT를 사용하면 Resource Server가 Authorization Server에 매번 검증 요청을 보내지 않아도 되므로 성능상 유리하다.

### 2. API Gateway의 역할 분리

API Gateway는 단순한 리버스 프록시가 아니다. 가맹점 플랫폼에서 Gateway는 다음 책임을 담당해야 한다.

| 책임 | 설명 |
|------|------|
| 인증/인가 | JWT 검증, 권한 스코프 확인 |
| Rate Limiting | 가맹점별 요청 수 제한 |
| 요청 로깅 | 감사(Audit) 목적의 전체 요청 기록 |
| 요청/응답 변환 | 내부 포맷과 외부 포맷 간 변환 |
| 라우팅 | 버전별, 가맹점 등급별 라우팅 |
| Circuit Breaker | 내부 서비스 장애 전파 차단 |

비즈니스 로직은 Gateway에 두지 않는 것이 핵심이다. Gateway가 비대해지면 배포 병목이 생기고 테스트하기 어려워진다.

### 3. Rate Limiting 전략

가맹점마다 다른 SLA(Service Level Agreement)를 적용해야 한다. Rate Limiting은 **토큰 버킷(Token Bucket)** 또는 **슬라이딩 윈도우(Sliding Window)** 알고리즘을 주로 사용한다.

가맹점 등급(Tier)에 따라 한도를 차등 적용하는 것이 일반적이다.

```
Basic  : 100 req/min
Standard: 1,000 req/min
Premium : 10,000 req/min
```

## 실전 예제

### Spring Boot 기반 Authorization Server 구현

Spring Authorization Server를 활용한 Client Credentials 토큰 발급 구성이다.

```java
@Configuration
@EnableWebSecurity
public class AuthorizationServerConfig {

    @Bean
    public RegisteredClientRepository registeredClientRepository() {
        RegisteredClient partnerClient = RegisteredClient
            .withId(UUID.randomUUID().toString())
            .clientId("partner-001")
            .clientSecret("{bcrypt}" + new BCryptPasswordEncoder().encode("secret"))
            .clientAuthenticationMethod(ClientAuthenticationMethod.CLIENT_SECRET_BASIC)
            .authorizationGrantType(AuthorizationGrantType.CLIENT_CREDENTIALS)
            .scope("payment.read")
            .scope("payment.write")
            .tokenSettings(TokenSettings.builder()
                .accessTokenTimeToLive(Duration.ofMinutes(30))
                .build())
            .build();

        return new InMemoryRegisteredClientRepository(partnerClient);
    }

    @Bean
    public JwtEncoder jwtEncoder(JWKSource<SecurityContext> jwkSource) {
        return new NimbusJwtEncoder(jwkSource);
    }

    @Bean
    public JWKSource<SecurityContext> jwkSource() throws NoSuchAlgorithmException {
        KeyPairGenerator keyPairGenerator = KeyPairGenerator.getInstance("RSA");
        keyPairGenerator.initialize(2048);
        KeyPair keyPair = keyPairGenerator.generateKeyPair();

        RSAPublicKey publicKey = (RSAPublicKey) keyPair.getPublic();
        RSAPrivateKey privateKey = (RSAPrivateKey) keyPair.getPrivate();

        RSAKey rsaKey = new RSAKey.Builder(publicKey)
            .privateKey(privateKey)
            .keyID(UUID.randomUUID().toString())
            .build();

        return new ImmutableJWKSet<>(new JWKSet(rsaKey));
    }
}
```

### API Gateway에서 JWT 검증 및 Rate Limiting (Spring Cloud Gateway)

```java
@Component
public class JwtAuthenticationFilter implements GlobalFilter, Ordered {

    private final JwtDecoder jwtDecoder;
    private final RateLimiterService rateLimiterService;

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String token = extractToken(exchange.getRequest());

        if (token == null) {
            return unauthorized(exchange);
        }

        try {
            Jwt jwt = jwtDecoder.decode(token);
            String clientId = jwt.getClaimAsString("sub");
            List<String> scopes = jwt.getClaimAsStringList("scope");

            // Rate Limiting 체크
            if (!rateLimiterService.tryAcquire(clientId)) {
                return tooManyRequests(exchange);
            }

            // 다운스트림에 가맹점 정보 전달
            ServerHttpRequest mutatedRequest = exchange.getRequest().mutate()
                .header("X-Partner-Id", clientId)
                .header("X-Partner-Scopes", String.join(",", scopes))
                .build();

            return chain.filter(exchange.mutate().request(mutatedRequest).build());

        } catch (JwtException e) {
            return unauthorized(exchange);
        }
    }

    private String extractToken(ServerHttpRequest request) {
        String authHeader = request.getHeaders().getFirst(HttpHeaders.AUTHORIZATION);
        if (authHeader != null && authHeader.startsWith("Bearer ")) {
            return authHeader.substring(7);
        }
        return null;
    }

    @Override
    public int getOrder() {
        return -100; // 가장 먼저 실행
    }
}
```

### Redis 기반 슬라이딩 윈도우 Rate Limiter

```java
@Service
public class RateLimiterService {

    private final RedisTemplate<String, String> redisTemplate;

    public boolean tryAcquire(String clientId) {
        String key = "rate_limit:" + clientId;
        long now = System.currentTimeMillis();
        long windowStart = now - 60_000; // 1분 윈도우

        // 오래된 요청 제거
        redisTemplate.opsForZSet().removeRangeByScore(key, 0, windowStart);

        // 현재 요청 수 조회
        Long currentCount = redisTemplate.opsForZSet().size(key);
        int limit = getLimit(clientId); // 가맹점 등급별 한도 조회

        if (currentCount != null && currentCount >= limit) {
            return false;
        }

        // 현재 요청 추가
        redisTemplate.opsForZSet().add(key, String.valueOf(now), now);
        redisTemplate.expire(key, 70, TimeUnit.SECONDS); // 윈도우보다 약간 길게

        return true;
    }

    private int getLimit(String clientId) {
        // 실제로는 DB 또는 캐시에서 가맹점 등급 조회
        return partnerTierCache.getLimit(clientId);
    }
}
```

### 표준화된 API 응답 형식

외부 가맹점에게 일관된 응답 형식을 제공하는 것은 매우 중요하다.

```java
@Getter
@Builder
public class ApiResponse<T> {

    private final String requestId;
    private final String timestamp;
    private final boolean success;
    private final T data;
    private final ApiError error;

    public static <T> ApiResponse<T> success(T data) {
        return ApiResponse.<T>builder()
            .requestId(MDC.get("requestId"))
            .timestamp(Instant.now().toString())
            .success(true)
            .data(data)
            .build();
    }

    public static <T> ApiResponse<T> failure(String code, String message) {
        return ApiResponse.<T>builder()
            .requestId(MDC.get("requestId"))
            .timestamp(Instant.now().toString())
            .success(false)
            .error(ApiError.of(code, message))
            .build();
    }
}

@Getter
@AllArgsConstructor(staticName = "of")
public class ApiError {
    private final String code;
    private final String message;
}
```

응답 예시:

```json
{
  "requestId": "req-550e8400-e29b",
  "timestamp": "2024-01-15T09:30:00Z",
  "success": false,
  "error": {
    "code": "PAYMENT_001",
    "message": "결제 금액이 한도를 초과했습니다."
  }
}
```

### API 버전 관리

URI 버전 방식(`/v1/payments`)을 사용할 경우, Spring에서 라우팅 설정은 다음과 같다.

```yaml
# application.yml - Spring Cloud Gateway 라우팅
spring:
  cloud:
    gateway:
      routes:
        - id: payment-v1
          uri: lb://payment-service-v1
          predicates:
            - Path=/api/v1/payments/**
          filters:
            - StripPrefix=2

        - id: payment-v2
          uri: lb://payment-service-v2
          predicates:
            - Path=/api/v2/payments/**
          filters:
            - StripPrefix=2
```

## 주의사항 및 트레이드오프

### 1. JWT vs Opaque Token

JWT는 stateless하여 성능상 유리하지만, **즉각적인 토큰 무효화(Revocation)** 가 불가능하다. 가맹점 계약 해지, 보안 침해 시 해당 가맹점의 토큰을 즉시 차단해야 한다면 opaque token + 중앙 검증 방식을 고려해야 한다. 또는 JWT 유효 시간을 짧게(5~10분) 유지하고 Refresh Token을 활용하는 방법도 있다. 어느 쪽이든 트레이드오프가 명확하니 요구사항에 맞게 선택해야 한다.

### 2. Rate Limiting의 분산 환경 동기화

Redis 기반 Rate Limiting은 네트워크 레이턴시와 Redis 장애 시 동작을 고려해야 한다. Redis가 다운되면 Rate Limiting을 우회하도록 허용(fail-open)할 것인지, 아니면 모든 요청을 차단(fail-closed)할 것인지 정책을 미리 결정해야 한다. 일반적으로 가용성이 중요한 플랫폼은 fail-open을 선택하되, 모니터링과 알림을 강화한다.

### 3. API 버전 관리의 복잡성

URI 버전(`/v1`, `/v2`), 헤더 버전(`API-Version: 2`), 쿼리 파라미터 방식 중 **URI 버전**이 가장 명시적이고 가맹점 입장에서 직관적이다. 단, 오래된 버전을 언제까지 유지할 것인지 **Deprecation 정책**을 문서화하고, 가맹점에게 Sunset 헤더로 명시적으로 전달해야 한다.

```
Deprecation: true
Sunset: Sat, 31 Dec 2024 23:59:59 GMT
```

### 4. 감사 로깅(Audit Logging)과 개인정보 보호

외부 가맹점 API는 모든 요청/응답을 감사 목적으로 로깅해야 하는 경우가 많다. 이때 요청 바디에 카드번호, 주민등록번호 등 민감 정보가 포함될 수 있으므로, **마스킹 처리 후 저장**하는 파이프라인을 Gateway 레벨에서 반드시 구성해야 한다. 개인정보 보호법과 금융 규제 요건을 함께 검토해야 한다.

### 5. 내부 서비스와 외부 API의 계층 분리

내부 서비스의 API를 그대로 외부에 노출하는 것은 금물이다. 내부 스키마 변경이 곧바로 가맹점 장애로 이어지기 때문이다. **Anti-Corruption Layer(ACL)** 또는 **BFF(Backend for Frontend)** 패턴을 적용해 내부와 외부 계약을 명확히 분리해야 한다.

## 정리

외부 가맹점용 Open API 플랫폼은 단순한 API 설계가 아니라, 인증/인가, 트래픽 제어, 안정성, 버전 관리, 감사 추적이라는 다층적 요구사항을 동시에 충족해야 하는 복합적인 아키텍처 과제다.

핵심을 정리하면 다음과 같다.

- **인증**: OAuth 2.0 Client Credentials + JWT, 필요 시 Revocation 전략 병행
- **Gateway**: 인증, Rate Limiting, 로깅의 책임을 Gateway에 집중, 비즈니스 로직 배제
- **Rate Limiting**: 가맹점 등급별 차등 적용, Redis 슬라이딩 윈도우 방식
- **응답 표준화**: 일관된 응답 포맷과 에러 코드 체계는 가맹점 개발 경험(DX)의 핵심
- **버전 관리**: URI 버전 + Deprecation 정책 문서화 + Sunset 헤더
- **계층 분리**: 내부 서비스와 외부 API 스키마를 ACL로 분리

플랫폼이 성숙해질수록 가맹점 수와 트래픽이 늘어나며 설계 결함이 점점 크게 드러난다. 초기부터 위 원칙들을 지키는 것이 장기적인 유지보수 비용을 크게 줄이는 길이다.
