# 벡터 데이터베이스 선택 기준과 성능 비교

## 개요

RAG(Retrieval-Augmented Generation), 시맨틱 검색, 추천 시스템 등 AI 기반 애플리케이션의 폭발적인 성장으로 **벡터 데이터베이스(Vector Database)**가 현대 백엔드 아키텍처의 핵심 컴포넌트로 자리잡고 있다. 기존 관계형 데이터베이스나 NoSQL로는 고차원 임베딩 벡터의 유사도 검색(ANN, Approximate Nearest Neighbor)을 효율적으로 처리하기 어렵다.

이 글에서는 현재 시장에서 주목받고 있는 벡터 데이터베이스들의 선택 기준과 실제 성능 특성을 비교하고, 실무에서 바로 활용할 수 있는 예제 코드와 함께 트레이드오프를 분석한다.

---

## 핵심 개념

### 벡터 데이터베이스가 필요한 이유

텍스트, 이미지, 오디오 데이터는 AI 모델을 통해 고차원 **임베딩 벡터**로 변환된다. 예를 들어 OpenAI의 `text-embedding-ada-002` 모델은 1536차원 벡터를 생성한다. 이러한 벡터들 사이의 의미적 유사도(코사인 유사도, 유클리드 거리 등)를 기반으로 빠른 검색을 제공하는 것이 벡터 데이터베이스의 핵심 역할이다.

### 주요 인덱싱 알고리즘

| 알고리즘 | 특징 | 대표 DB |
|---------|------|---------|
| **HNSW** (Hierarchical Navigable Small World) | 높은 정확도, 빠른 검색, 높은 메모리 사용 | Milvus, Weaviate, Qdrant |
| **IVF** (Inverted File Index) | 대용량 데이터에 효율적, 파라미터 튜닝 필요 | Milvus, pgvector |
| **DiskANN** | 디스크 기반, 메모리 효율적 | Azure Cognitive Search |
| **Flat** | 브루트포스, 100% 정확도 | 소규모 데이터셋 |

### 선택 기준 체크리스트

실무에서 벡터 DB를 선택할 때 반드시 고려해야 할 기준은 다음과 같다.

1. **데이터 규모**: 수백만 vs 수십억 벡터
2. **쿼리 레이턴시 요구사항**: P99 레이턴시 목표
3. **정확도(Recall)**: ANN 검색의 정확도 허용 범위
4. **운영 복잡도**: 관리형 서비스 vs 자체 호스팅
5. **필터링 지원**: 메타데이터 기반 필터 + 벡터 검색 하이브리드
6. **스케일링 전략**: 수평 확장 지원 여부
7. **비용 모델**: 클라우드 관리형 서비스 vs 오픈소스

## 주요 벡터 데이터베이스 비교

### 1. Pinecone

관리형 서비스로 운영 부담이 최소화된다. 빠른 프로토타이핑에 최적화되어 있으며, 서버리스 플랜도 제공한다.

### 2. Weaviate

GraphQL 기반 쿼리를 지원하며, 모듈 시스템으로 OpenAI, Cohere 등과 직접 통합이 가능하다. 하이브리드 검색(BM25 + 벡터)을 기본 지원한다.

### 3. Qdrant

Rust로 작성되어 성능이 뛰어나고, 페이로드 필터링이 강력하다. Docker로 쉽게 로컬 테스트가 가능하다.

### 4. Milvus

대규모 엔터프라이즈 환경에 최적화된 오픈소스 벡터 DB다. etcd, MinIO 등 의존성이 많아 운영 복잡도가 높지만, 수십억 벡터 처리에 적합하다.

### 5. pgvector

기존 PostgreSQL에 확장으로 추가한다. 벡터 전용 DB 대비 성능은 낮지만, 이미 PostgreSQL을 사용 중이라면 운영 복잡도를 크게 줄일 수 있다.

## 실전 예제

### Spring Boot + Qdrant 연동 예제

Qdrant는 Docker로 빠르게 로컬 환경을 구성할 수 있어 실무 POC에 적합하다.

```yaml
# docker-compose.yml
version: '3.8'
services:
  qdrant:
    image: qdrant/qdrant:latest
    ports:
      - "6333:6333"
      - "6334:6334"
    volumes:
      - qdrant_storage:/qdrant/storage
volumes:
  qdrant_storage:
```

```xml
<!-- pom.xml -->
<dependency>
    <groupId>io.qdrant</groupId>
    <artifactId>client</artifactId>
    <version>1.8.0</version>
</dependency>
<dependency>
    <groupId>com.theokanning.openai-gpt3-java</groupId>
    <artifactId>service</artifactId>
    <version>0.18.2</version>
</dependency>
```

```java
@Service
@RequiredArgsConstructor
public class VectorSearchService {

    private final QdrantClient qdrantClient;
    private final EmbeddingService embeddingService;

    private static final String COLLECTION_NAME = "documents";
    private static final int VECTOR_SIZE = 1536; // OpenAI ada-002

    public void createCollection() throws ExecutionException, InterruptedException {
        qdrantClient.createCollectionAsync(
            COLLECTION_NAME,
            VectorsConfig.newBuilder()
                .setParams(VectorParams.newBuilder()
                    .setSize(VECTOR_SIZE)
                    .setDistance(Distance.Cosine)
                    .build())
                .build()
        ).get();
    }

    public void upsertDocuments(List<Document> documents) 
            throws ExecutionException, InterruptedException {
        
        List<PointStruct> points = documents.stream()
            .map(doc -> {
                List<Float> embedding = embeddingService.embed(doc.getContent());
                
                return PointStruct.newBuilder()
                    .setId(PointId.newBuilder()
                        .setUuid(doc.getId().toString())
                        .build())
                    .setVectors(Vectors.newBuilder()
                        .setVector(Vector.newBuilder()
                            .addAllData(embedding)
                            .build())
                        .build())
                    .putAllPayload(Map.of(
                        "title", Value.newBuilder()
                            .setStringValue(doc.getTitle()).build(),
                        "category", Value.newBuilder()
                            .setStringValue(doc.getCategory()).build(),
                        "createdAt", Value.newBuilder()
                            .setIntegerValue(doc.getCreatedAt().toEpochSecond(ZoneOffset.UTC))
                            .build()
                    ))
                    .build();
            })
            .collect(Collectors.toList());

        qdrantClient.upsertAsync(COLLECTION_NAME, points).get();
    }

    public List<SearchResult> semanticSearch(
            String query, 
            String categoryFilter, 
            int topK) throws ExecutionException, InterruptedException {

        List<Float> queryVector = embeddingService.embed(query);

        // 메타데이터 필터와 벡터 검색을 동시에 적용 (하이브리드 필터링)
        Filter filter = Filter.newBuilder()
            .addMust(Condition.newBuilder()
                .setField(FieldCondition.newBuilder()
                    .setKey("category")
                    .setMatch(Match.newBuilder()
                        .setKeyword(categoryFilter)
                        .build())
                    .build())
                .build())
            .build();

        List<ScoredPoint> results = qdrantClient.searchAsync(
            SearchPoints.newBuilder()
                .setCollectionName(COLLECTION_NAME)
                .addAllVector(queryVector)
                .setFilter(filter)
                .setLimit(topK)
                .setWithPayload(WithPayloadSelector.newBuilder()
                    .setEnable(true)
                    .build())
                .build()
        ).get();

        return results.stream()
            .map(point -> SearchResult.builder()
                .id(point.getId().getUuid())
                .score(point.getScore())
                .title(point.getPayloadMap().get("title").getStringValue())
                .build())
            .collect(Collectors.toList());
    }
}
```

### pgvector 활용 예제 (기존 PostgreSQL 환경)

```sql
-- pgvector 확장 활성화
CREATE EXTENSION IF NOT EXISTS vector;

-- 테이블 생성
CREATE TABLE document_embeddings (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    content     TEXT NOT NULL,
    category    VARCHAR(100),
    embedding   vector(1536),
    created_at  TIMESTAMPTZ DEFAULT NOW()
);

-- HNSW 인덱스 생성 (Recall과 속도의 균형)
CREATE INDEX ON document_embeddings 
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- 코사인 유사도 기반 검색 쿼리
SELECT 
    id,
    content,
    category,
    1 - (embedding <=> '[벡터값...]'::vector) AS similarity
FROM document_embeddings
WHERE category = 'tech'
ORDER BY embedding <=> '[벡터값...]'::vector
LIMIT 10;
```

```java
@Repository
public class PgVectorDocumentRepository {

    private final JdbcTemplate jdbcTemplate;

    public List<DocumentSearchResult> findSimilarDocuments(
            float[] queryEmbedding,
            String category,
            int limit) {

        String vectorStr = Arrays.stream(
                IntStream.range(0, queryEmbedding.length)
                    .mapToObj(i -> String.valueOf(queryEmbedding[i]))
                    .toArray(String[]::new))
            .collect(Collectors.joining(",", "[", "]"));

        String sql = """
            SELECT id, content, category,
                   1 - (embedding <=> ?::vector) AS similarity
            FROM document_embeddings
            WHERE category = ?
            ORDER BY embedding <=> ?::vector
            LIMIT ?
            """;

        return jdbcTemplate.query(
            sql,
            (rs, rowNum) -> DocumentSearchResult.builder()
                .id(UUID.fromString(rs.getString("id")))
                .content(rs.getString("content"))
                .similarity(rs.getDouble("similarity"))
                .build(),
            vectorStr, category, vectorStr, limit
        );
    }
}
```

## 성능 벤치마크 요약

실제 프로덕션 환경(1M 벡터, 1536차원, 코사인 유사도 기준)에서의 대략적인 성능 특성이다. 환경에 따라 수치는 달라질 수 있으며, 반드시 자체 벤치마크를 수행해야 한다.

| 항목 | Qdrant | Weaviate | Milvus | pgvector |
|------|--------|----------|--------|----------|
| P99 레이턴시 | ~5ms | ~10ms | ~8ms | ~50ms |
| Recall@10 | 99%+ | 98%+ | 99%+ | 100% |
| QPS (단일 노드) | ~2000 | ~1200 | ~1500 | ~300 |
| 메모리 효율 | 높음 | 중간 | 중간 | 높음 |
| 운영 복잡도 | 낮음 | 중간 | 높음 | 낮음 |

## 주의사항 및 트레이드오프

### 1. Recall vs Latency 트레이드오프

HNSW 인덱스의 `ef` 파라미터는 검색 시 탐색 범위를 결정한다. 값이 높을수록 Recall은 올라가지만 레이턴시도 증가한다. 서비스 요구사항에 맞춰 반드시 튜닝 테스트를 수행해야 한다.

```java
// Qdrant에서 ef 파라미터 동적 조정
SearchPoints.newBuilder()
    .setParams(SearchParams.newBuilder()
        .setHnswEf(128) // 기본값보다 높게 설정 시 Recall 향상
        .build())
    .build();
```

### 2. 필터링 성능 저하 문제

벡터 검색과 메타데이터 필터를 함께 사용할 때, 필터 조건이 지나치게 선택적이면(전체의 0.1% 미만) 성능이 크게 저하될 수 있다. Qdrant는 이를 위해 **payload 인덱스**를 별도로 생성해야 한다.

```python
# Qdrant payload 인덱스 생성
client.create_payload_index(
    collection_name="documents",
    field_name="category",
    field_schema=PayloadSchemaType.KEYWORD
)
```

### 3. 메모리 용량 계산

프로덕션 투입 전 메모리 용량을 반드시 사전 계산해야 한다.

> **HNSW 메모리 추정식**: `벡터 수 × 차원 × 4bytes × (1 + m × 2 / 차원)`

예를 들어 1M 벡터, 1536차원, m=16인 경우 약 **7~9GB** 메모리가 필요하다.

### 4. 관리형 서비스 vs 자체 호스팅

- **Pinecone, Weaviate Cloud**: 초기 개발/소규모 서비스에 적합. 비용이 데이터 증가에 따라 급격히 증가할 수 있음.
- **Qdrant, Milvus 자체 호스팅**: 대규모 데이터 처리 시 비용 효율적. 단, 인프라 운영 역량 필요.
- **pgvector**: 기존 RDS 또는 PostgreSQL 인프라 재활용 가능. 수천만 벡터 이하 규모에서 현실적인 선택지.

## 정리

벡터 데이터베이스 선택은 "최고 성능"이 아닌 **"팀의 운영 역량과 서비스 요구사항에 맞는 최적의 선택"**이어야 한다.

| 시나리오 | 추천 솔루션 |
|---------|-----------|
| 빠른 프로토타이핑, 소규모 팀 | Pinecone (관리형) |
| PostgreSQL 기반 기존 스택 | pgvector |
| 고성능 + 자체 호스팅 | Qdrant |
| 대규모 엔터프라이즈 | Milvus |
| 하이브리드 검색 중요 | Weaviate |

결국 실무에서 가장 중요한 것은 **자체 데이터셋과 쿼리 패턴으로 직접 벤치마크**를 수행하는 것이다. 공개된 벤치마크 결과는 참고 수준으로만 활용하고, 프로덕션 투입 전 반드시 실제 부하 테스트(Load Test)와 Recall 측정을 병행할 것을 강력히 권장한다.
