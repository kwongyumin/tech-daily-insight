# TCP/IP 핵심 개념과 백엔드 개발자가 알아야 할 것들

## 개요

백엔드 개발자로 일하다 보면 네트워크 지식을 "어느 정도 알고 있다"고 생각하기 쉽습니다. HTTP 통신, REST API, 소켓 프로그래밍 정도는 다루지만, 실제로 TCP/IP 레벨에서 무슨 일이 일어나는지 깊이 이해하는 개발자는 생각보다 많지 않습니다.

하지만 프로덕션 환경에서 발생하는 다양한 문제들 — 간헐적인 연결 끊김, 높은 레이턴시, 타임아웃 설정 문제, 대규모 트래픽에서의 포트 고갈 — 은 대부분 TCP/IP의 동작 방식을 제대로 이해하지 못해서 발생합니다.

이 글에서는 백엔드 개발자가 반드시 알아야 할 TCP/IP의 핵심 개념을 정리하고, 실무에서 직접 활용할 수 있는 예제와 함께 트레이드오프까지 다루겠습니다.

## 핵심 개념

### 1. 3-Way Handshake와 4-Way Teardown

TCP 연결은 단순히 "연결됐다/끊겼다"가 아닙니다. 연결 수립과 해제 과정 자체가 상태를 가지며, 이 상태를 이해하는 것이 중요합니다.

**연결 수립 (3-Way Handshake)**

```
Client                    Server
  |  --- SYN (seq=100) -->  |
  |  <-- SYN-ACK (seq=200, ack=101) ---  |
  |  --- ACK (ack=201) -->  |
  |       [ESTABLISHED]     |
```

**연결 해제 (4-Way Teardown)**

```
Client                    Server
  |  --- FIN -->           |
  |  <-- ACK ---           |
  |  <-- FIN ---           |   ← 서버가 남은 데이터 전송 가능
  |  --- ACK -->           |
  | [TIME_WAIT: 2MSL]      |
```

`TIME_WAIT` 상태는 기본적으로 60~120초간 유지됩니다. 대규모 서비스에서 클라이언트 역할을 하는 서버(예: 내부 API 호출)는 이 상태의 소켓이 쌓이면서 포트 고갈이 발생할 수 있습니다.

### 2. TCP 흐름 제어와 혼잡 제어

**슬라이딩 윈도우 (Flow Control)**

수신자의 버퍼 크기를 기반으로 송신 속도를 조절합니다. 수신자가 `rwnd(Receive Window)`를 ACK에 실어 보내면, 송신자는 이 값을 초과해서 데이터를 보내지 않습니다.

**혼잡 제어 (Congestion Control)**

네트워크 자체의 혼잡을 감지하고 조절하는 메커니즘입니다.

- **Slow Start**: 초기에는 cwnd(Congestion Window)를 1 MSS로 시작, ACK마다 두 배로 증가
- **Congestion Avoidance**: ssthresh 도달 후 선형 증가
- **Fast Retransmit/Recovery**: 3번의 중복 ACK 시 재전송

이 개념이 실무에서 중요한 이유는, **처음 TCP 연결을 맺었을 때 전송 속도가 느린 것이 정상**이기 때문입니다. 커넥션 풀을 재사용하는 것이 성능상 유리한 이유가 여기 있습니다.

### 3. TCP 소켓 상태와 커널 파라미터

```
LISTEN → SYN_RCVD → ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED
```

서버 운영 시 자주 마주치는 소켓 상태:

| 상태 | 의미 | 문제 징후 |
|------|------|-----------|
| `LISTEN` | 연결 대기 | backlog 초과 시 SYN drop |
| `SYN_RCVD` | 핸드셰이크 진행 중 | SYN Flood 공격 시 급증 |
| `ESTABLISHED` | 연결 완료 | 정상 상태 |
| `TIME_WAIT` | 연결 해제 대기 | 과다 시 포트 고갈 |
| `CLOSE_WAIT` | 상대방이 FIN 보냄 | 애플리케이션이 close() 안 함 |

`CLOSE_WAIT`이 지속적으로 쌓인다면 **애플리케이션 버그**입니다. 서버가 FIN을 받았는데 소켓을 제대로 닫지 않는 것으로, 커넥션 풀 관리 코드를 반드시 점검해야 합니다.

## 실전 예제

### 예제 1: Java에서 소켓 타임아웃 설정

대부분의 개발자가 단순히 `connect timeout`만 설정하고 넘어가는데, `read timeout`과 `keepalive` 설정도 함께 챙겨야 합니다.

```java
import java.net.Socket;
import java.net.InetSocketAddress;

public class TcpSocketExample {

    public static Socket createConfiguredSocket(String host, int port) throws Exception {
        Socket socket = new Socket();

        // TCP KeepAlive 활성화 (OS 레벨 keepalive)
        socket.setKeepAlive(true);

        // Nagle 알고리즘 비활성화 (소규모 패킷 지연 방지, 실시간 통신에 유리)
        socket.setTcpNoDelay(true);

        // SO_LINGER: close() 호출 시 즉시 RST 전송 (TIME_WAIT 회피, 주의 필요)
        // socket.setSoLinger(true, 0);

        // 연결 타임아웃: 3초
        socket.connect(new InetSocketAddress(host, port), 3000);

        // 읽기 타임아웃: 5초 (이후 SocketTimeoutException 발생)
        socket.setSoTimeout(5000);

        return socket;
    }
}
```

### 예제 2: Spring Boot에서 HTTP 커넥션 풀 튜닝

```java
import org.apache.hc.client5.http.impl.classic.CloseableHttpClient;
import org.apache.hc.client5.http.impl.classic.HttpClients;
import org.apache.hc.client5.http.impl.io.PoolingHttpClientConnectionManager;
import org.apache.hc.core5.util.TimeValue;
import org.apache.hc.core5.util.Timeout;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.client.HttpComponentsClientHttpRequestFactory;
import org.springframework.web.client.RestTemplate;

import java.util.concurrent.TimeUnit;

@Configuration
public class HttpClientConfig {

    @Bean
    public RestTemplate restTemplate() {
        PoolingHttpClientConnectionManager connectionManager =
                new PoolingHttpClientConnectionManager();

        // 전체 최대 커넥션 수
        connectionManager.setMaxTotal(200);

        // 호스트당 최대 커넥션 수 (기본값 2는 너무 낮음!)
        connectionManager.setDefaultMaxPerRoute(50);

        // 유휴 커넥션 TTL 설정 (서버의 keepalive timeout보다 짧게)
        connectionManager.setConnectionMaxIdleTime(TimeValue.of(30, TimeUnit.SECONDS));

        CloseableHttpClient httpClient = HttpClients.custom()
                .setConnectionManager(connectionManager)
                // 유휴 커넥션 정리 스레드
                .evictIdleConnections(TimeValue.of(30, TimeUnit.SECONDS))
                .evictExpiredConnections()
                .build();

        HttpComponentsClientHttpRequestFactory factory =
                new HttpComponentsClientHttpRequestFactory(httpClient);
        factory.setConnectTimeout(3000);
        factory.setReadTimeout(5000);

        return new RestTemplate(factory);
    }
}
```

### 예제 3: 리눅스 커널 파라미터 튜닝

```bash
# 현재 소켓 상태 확인
ss -s
ss -tnp | grep TIME_WAIT | wc -l

# TIME_WAIT 재사용 허용 (클라이언트 측)
echo 1 > /proc/sys/net/ipv4/tcp_tw_reuse

# SYN backlog 크기 증가 (트래픽이 많은 서버)
echo 4096 > /proc/sys/net/ipv4/tcp_max_syn_backlog
echo 65535 > /proc/sys/net/core/somaxconn

# 로컬 포트 범위 확장 (포트 고갈 방지)
echo "1024 65535" > /proc/sys/net/ipv4/ip_local_port_range

# keepalive 설정
echo 60 > /proc/sys/net/ipv4/tcp_keepalive_time      # 첫 keepalive 전송 대기
echo 10 > /proc/sys/net/ipv4/tcp_keepalive_intvl     # keepalive 간격
echo 6  > /proc/sys/net/ipv4/tcp_keepalive_probes    # 실패 허용 횟수

# /etc/sysctl.conf에 영구 적용
cat >> /etc/sysctl.conf << EOF
net.ipv4.tcp_tw_reuse = 1
net.ipv4.tcp_max_syn_backlog = 4096
net.core.somaxconn = 65535
net.ipv4.ip_local_port_range = 1024 65535
net.ipv4.tcp_keepalive_time = 60
net.ipv4.tcp_keepalive_intvl = 10
net.ipv4.tcp_keepalive_probes = 6
EOF
sysctl -p
```

### 예제 4: Wireshark / tcpdump로 TCP 트래픽 분석

```bash
# 특정 포트의 TCP 트래픽 캡처
tcpdump -i eth0 -nn tcp port 8080 -w capture.pcap

# SYN 패킷만 필터링 (연결 요청 모니터링)
tcpdump -i eth0 'tcp[tcpflags] & tcp-syn != 0' -c 100

# RST 패킷 모니터링 (비정상 연결 종료 탐지)
tcpdump -i eth0 'tcp[tcpflags] & tcp-rst != 0' -nn

# 특정 호스트와의 통신 추적
tcpdump -i eth0 -nn host 192.168.1.100 and tcp port 443

# 패킷 내용 포함 출력 (페이로드 확인)
tcpdump -i eth0 -A -s 0 tcp port 8080
```

## 주의사항 및 트레이드오프

### ⚠️ tcp_tw_recycle은 사용하지 마세요

과거에는 `tcp_tw_recycle=1`로 TIME_WAIT 소켓을 빠르게 회수하려 했지만, **NAT 환경에서 패킷 드롭**이 발생하는 치명적인 문제가 있어 Linux 4.12부터 커널에서 제거되었습니다. `tcp_tw_reuse`만 사용하세요.

### ⚠️ SO_LINGER(0)의 위험성

`SO_LINGER`를 0으로 설정하면 `close()` 시 FIN 대신 **RST를 즉시 전송**합니다. TIME_WAIT를 피할 수 있지만 상대방이 아직 전송 중인 데이터가 유실될 수 있습니다. 프록시나 로드밸런서 앞단에서 사용하면 예기치 않은 연결 오류를 유발할 수 있습니다.

### ⚠️ Nagle 알고리즘과 Delayed ACK의 조합

`TCP_NODELAY`를 설정하지 않으면 Nagle 알고리즘이 소규모 패킷을 모아서 전송합니다. 그런데 수신 측에서 Delayed ACK(200ms 지연)를 사용하면, 두 메커니즘이 결합되어 최대 **200ms의 불필요한 지연**이 발생할 수 있습니다. 대화형 프로토콜이나 RPC 통신에서는 반드시 `TCP_NODELAY=true`를 설정하세요.

### ⚠️ 커넥션 풀 사이즈와 DB 연결

```
적절한 DB 커넥션 풀 사이즈 = (CPU 코어 수 * 2) + 유효 스핀들 수
```

HikariCP 공식 문서에서 제안하는 공식입니다. 커넥션이 많다고 성능이 좋아지지 않습니다. 오히려 **컨텍스트 스위칭 오버헤드**와 DB 서버의 부하만 증가합니다. 대부분의 경우 10~20개면 충분합니다.

### 트레이드오프 정리

| 설정 | 장점 | 단점 |
|------|------|------|
| `TCP_NODELAY=true` | 지연 감소 | 네트워크 대역폭 낭비 증가 |
| 큰 SO_RCVBUF | 처리량 향상 | 메모리 사용량 증가 |
| `tcp_tw_reuse=1` | TIME_WAIT 포트 재사용 | 일부 에지케이스에서 패킷 혼동 가능 |
| 큰 커넥션 풀 | 동시 요청 처리 | 메모리, DB 서버 부하 |
| keepalive | 재연결 비용 절감 | 유휴 연결로 인한 리소스 점유 |

## 정리

TCP/IP는 백엔드 개발자에게 "알면 좋은 지식"이 아니라 **프로덕션 문제를 해결하기 위한 필수 지식**입니다. 핵심을 다시 정리하면:

1. **3-Way Handshake와 TIME_WAIT**를 이해하면 포트 고갈 문제를 선제적으로 방지할 수 있습니다.
2. **TCP Slow Start** 때문에 새 연결은 항상 느립니다. 커넥션 풀을 적극 활용하세요.
3. **CLOSE_WAIT 누적**은 항상 애플리케이션 버그입니다. 커넥션 반환 코드를 점검하세요.
4. **커널 파라미터 튜닝**은 애플리케이션 최적화 이후의 마지막 수단입니다. 먼저 코드를 고치세요.
5. **tcpdump/Wireshark**를 능숙하게 다룰 수 있어야 실제 네트워크 이슈를 진단할 수 있습니다.

네트워크 레이어에서 발생하는 문제는 재현이 어렵고 로그도 없는 경우가 많습니다. TCP/IP를 깊이 이해하고 있는 개발자는 이런 상황에서 가설을 세우고 검증하는 능력에서 차이가 납니다. 이 글이 그 이해의 발판이 되길 바랍니다.
