# mTLS 상호 인증과 서비스 간 보안 통신

## 개요

마이크로서비스 아키텍처가 보편화되면서 서비스 간 통신 보안은 더 이상 선택이 아닌 필수가 됐다. 일반적인 TLS는 클라이언트가 서버의 인증서를 검증하는 단방향 인증이지만, **mTLS(Mutual TLS)** 는 서버도 클라이언트의 인증서를 검증하는 상호 인증 방식이다.

Zero Trust 보안 모델이 주목받으면서 "네트워크 내부라도 믿지 않는다"는 원칙이 강조되고 있다. 내부 서비스라도 신원을 증명해야 통신을 허용하는 mTLS는 이 철학을 구현하는 가장 실용적인 방법 중 하나다.

이 글에서는 mTLS의 동작 원리부터 Spring Boot와 Nginx를 활용한 실전 구현까지, 실무에서 바로 적용할 수 있는 내용을 다룬다.

## 핵심 개념

### 일반 TLS vs mTLS

일반 TLS 핸드셰이크는 다음과 같이 진행된다.

```
Client → Server: ClientHello
Server → Client: ServerHello + Certificate
Client → Server: 서버 인증서 검증 후 키 교환
// 클라이언트는 서버를 검증하지만, 서버는 클라이언트를 검증하지 않음
```

mTLS는 여기에 클라이언트 인증 단계가 추가된다.

```
Client → Server: ClientHello
Server → Client: ServerHello + Certificate + CertificateRequest
Client → Server: Certificate (클라이언트 인증서)
Server → Client: 클라이언트 인증서 검증
// 양방향 신원 확인 완료 후 암호화 통신 시작
```

### PKI 구조 이해

mTLS를 제대로 구현하려면 PKI(Public Key Infrastructure) 구조를 이해해야 한다.

- **Root CA**: 최상위 인증 기관. 내부 서비스용으로는 자체 CA를 구축한다.
- **Intermediate CA**: Root CA가 서명한 중간 CA. 실제 인증서 발급에 사용한다.
- **Leaf Certificate**: 각 서비스에 발급되는 실제 인증서.

```
Root CA
  └── Intermediate CA
        ├── service-a.internal (서버/클라이언트 인증서)
        └── service-b.internal (서버/클라이언트 인증서)
```

내부 서비스 간 통신에서는 자체 CA(Private CA)를 구축해 인증서를 발급하는 방식이 일반적이다.

## 실전 예제

### 1단계: 자체 CA 및 인증서 생성

OpenSSL을 이용해 간단한 Private CA와 서비스 인증서를 생성한다.

```bash
# Root CA 생성
openssl genrsa -out ca.key 4096
openssl req -new -x509 -days 3650 -key ca.key -out ca.crt \
  -subj "/CN=Internal Root CA/O=MyCompany/C=KR"

# Service-A 서버/클라이언트 인증서 생성
openssl genrsa -out service-a.key 2048
openssl req -new -key service-a.key -out service-a.csr \
  -subj "/CN=service-a.internal/O=MyCompany/C=KR"

# CA로 서명
openssl x509 -req -days 365 -in service-a.csr \
  -CA ca.crt -CAkey ca.key -CAcreateserial \
  -out service-a.crt \
  -extfile <(printf "subjectAltName=DNS:service-a.internal,DNS:localhost\nextendedKeyUsage=serverAuth,clientAuth")

# Java용 PKCS12 키스토어로 변환
openssl pkcs12 -export \
  -in service-a.crt \
  -inkey service-a.key \
  -certfile ca.crt \
  -out service-a.p12 \
  -passout pass:changeit

# Truststore 생성 (CA 인증서 포함)
keytool -importcert -trustcacerts \
  -alias internal-ca \
  -file ca.crt \
  -keystore truststore.p12 \
  -storetype PKCS12 \
  -storepass changeit -noprompt
```

### 2단계: Spring Boot 서버 설정

`application.yml`에 SSL 설정을 추가한다.

```yaml
server:
  port: 8443
  ssl:
    enabled: true
    key-store: classpath:certs/service-a.p12
    key-store-password: changeit
    key-store-type: PKCS12
    trust-store: classpath:certs/truststore.p12
    trust-store-password: changeit
    trust-store-type: PKCS12
    client-auth: need  # 클라이언트 인증서를 반드시 요구
```

`client-auth` 옵션은 세 가지 값을 가진다.
- `none`: 클라이언트 인증서를 요구하지 않음
- `want`: 선택적으로 요구 (없어도 연결 허용)
- `need`: 반드시 요구 (없으면 연결 거부)

### 3단계: Spring RestClient에 mTLS 적용

클라이언트 서비스에서 mTLS로 통신하는 `RestClient` 설정이다.

```java
@Configuration
public class MtlsRestClientConfig {

    @Value("${mtls.keystore.path}")
    private Resource keystorePath;

    @Value("${mtls.keystore.password}")
    private String keystorePassword;

    @Value("${mtls.truststore.path}")
    private Resource truststorePath;

    @Value("${mtls.truststore.password}")
    private String truststorePassword;

    @Bean
    public RestClient mtlsRestClient() throws Exception {
        SSLContext sslContext = buildSslContext();

        SSLConnectionSocketFactory socketFactory =
            new SSLConnectionSocketFactory(sslContext);

        CloseableHttpClient httpClient = HttpClients.custom()
            .setSSLSocketFactory(socketFactory)
            .build();

        HttpComponentsClientHttpRequestFactory factory =
            new HttpComponentsClientHttpRequestFactory(httpClient);

        return RestClient.builder()
            .requestFactory(factory)
            .baseUrl("https://service-b.internal:8443")
            .build();
    }

    private SSLContext buildSslContext() throws Exception {
        // KeyStore (클라이언트 인증서)
        KeyStore keyStore = KeyStore.getInstance("PKCS12");
        try (InputStream ks = keystorePath.getInputStream()) {
            keyStore.load(ks, keystorePassword.toCharArray());
        }

        // TrustStore (서버 인증서 검증용 CA)
        KeyStore trustStore = KeyStore.getInstance("PKCS12");
        try (InputStream ts = truststorePath.getInputStream()) {
            trustStore.load(ts, truststorePassword.toCharArray());
        }

        KeyManagerFactory kmf = KeyManagerFactory.getInstance(
            KeyManagerFactory.getDefaultAlgorithm());
        kmf.init(keyStore, keystorePassword.toCharArray());

        TrustManagerFactory tmf = TrustManagerFactory.getInstance(
            TrustManagerFactory.getDefaultAlgorithm());
        tmf.init(trustStore);

        SSLContext sslContext = SSLContext.getInstance("TLS");
        sslContext.init(kmf.getKeyManagers(), tmf.getTrustManagers(), null);

        return sslContext;
    }
}
```

### 4단계: 클라이언트 인증서 정보 추출

서버 측에서 클라이언트 인증서의 Subject를 파싱해 추가 인가 처리를 할 수 있다.

```java
@RestController
@RequestMapping("/api/data")
public class DataController {

    @GetMapping
    public ResponseEntity<String> getData(HttpServletRequest request) {
        X509Certificate[] certs = (X509Certificate[])
            request.getAttribute("jakarta.servlet.request.X509Certificate");

        if (certs == null || certs.length == 0) {
            return ResponseEntity.status(HttpStatus.UNAUTHORIZED).build();
        }

        X509Certificate clientCert = certs[0];
        String subject = clientCert.getSubjectX500Principal().getName();

        // CN 파싱
        String cn = Arrays.stream(subject.split(","))
            .map(String::trim)
            .filter(s -> s.startsWith("CN="))
            .map(s -> s.substring(3))
            .findFirst()
            .orElse("unknown");

        log.info("Request from service: {}, cert expires: {}",
            cn, clientCert.getNotAfter());

        // 특정 서비스만 허용하는 추가 인가 로직
        if (!isAllowedService(cn)) {
            return ResponseEntity.status(HttpStatus.FORBIDDEN).build();
        }

        return ResponseEntity.ok("Data for " + cn);
    }

    private boolean isAllowedService(String serviceName) {
        Set<String> allowedServices = Set.of(
            "service-b.internal",
            "service-c.internal"
        );
        return allowedServices.contains(serviceName);
    }
}
```

### 5단계: Nginx를 통한 mTLS 프록시 구성

Nginx를 리버스 프록시로 사용할 때 mTLS를 처리하는 설정이다.

```nginx
server {
    listen 443 ssl;
    server_name service-a.internal;

    ssl_certificate     /etc/nginx/certs/service-a.crt;
    ssl_certificate_key /etc/nginx/certs/service-a.key;

    # 클라이언트 인증서 검증 설정
    ssl_client_certificate /etc/nginx/certs/ca.crt;
    ssl_verify_client on;
    ssl_verify_depth 2;

    # 강화된 TLS 설정
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384;
    ssl_prefer_server_ciphers on;
    ssl_session_timeout 1d;
    ssl_session_cache shared:MozSSL:10m;

    location /api/ {
        # 클라이언트 인증서 정보를 헤더로 upstream에 전달
        proxy_set_header X-Client-Cert-CN $ssl_client_s_dn_cn;
        proxy_set_header X-Client-Cert-Subject $ssl_client_s_dn;
        proxy_set_header X-Client-Verify $ssl_client_verify;

        proxy_pass http://backend:8080;
        proxy_ssl_verify off;  # Nginx-Backend 구간은 내부망이라면 생략 가능
    }
}
```

## 주의사항 및 트레이드오프

### 인증서 만료 관리가 핵심이다

mTLS 운영에서 가장 흔한 장애 원인은 **인증서 만료**다. 인증서가 만료되면 서비스 간 통신이 전면 차단된다.

```bash
# 만료일 확인 스크립트
#!/bin/bash
CERT_PATH="/etc/service/certs/service-a.crt"
WARN_DAYS=30

EXPIRY=$(openssl x509 -enddate -noout -in $CERT_PATH | cut -d= -f2)
EXPIRY_EPOCH=$(date -d "$EXPIRY" +%s)
NOW_EPOCH=$(date +%s)
DAYS_LEFT=$(( ($EXPIRY_EPOCH - $NOW_EPOCH) / 86400 ))

if [ $DAYS_LEFT -lt $WARN_DAYS ]; then
    echo "WARN: Certificate expires in $DAYS_LEFT days!"
    # 알림 발송 로직
fi
```

실무에서는 **cert-manager**(Kubernetes 환경)나 **HashiCorp Vault**를 활용해 인증서 자동 갱신 파이프라인을 구축하는 것이 강력히 권장된다.

### 성능 오버헤드를 고려하라

TLS 핸드셰이크는 CPU와 레이턴시 비용이 발생한다. mTLS는 양방향이므로 일반 TLS보다 약간 더 비용이 크다.

- **TLS Session Resumption** 활성화로 반복 핸드셰이크를 줄인다.
- **HTTP/2** 또는 **gRPC**와 함께 사용하면 멀티플렉싱으로 연결 재사용 효율이 높아진다.
- 내부 서비스가 매우 많다면 **Istio**나 **Linkerd** 같은 서비스 메시를 통해 mTLS를 사이드카에서 투명하게 처리하는 방안도 고려하자.

### 디버깅이 어렵다

mTLS 핸드셰이크 실패는 에러 메시지가 불친절하다. 다음 도구를 활용하면 원인 파악이 수월해진다.

```bash
# OpenSSL로 mTLS 핸드셰이크 직접 테스트
openssl s_client \
  -connect service-a.internal:8443 \
  -cert service-b.crt \
  -key service-b.key \
  -CAfile ca.crt \
  -verify_return_error \
  -showcerts

# curl로 mTLS 요청 테스트
curl -v \
  --cert service-b.crt \
  --key service-b.key \
  --cacert ca.crt \
  https://service-a.internal:8443/api/data
```

Java 애플리케이션에서는 JVM 옵션 `-Djavax.net.debug=ssl:handshake`를 추가하면 핸드셰이크 과정의 상세 로그를 확인할 수 있다.

### mTLS만으로 완전한 보안이 되지는 않는다

mTLS는 **전송 계층 인증**이다. 인증서가 탈취되면 신뢰가 무너진다. 다음 보완책을 함께 적용해야 한다.

| 위협 | 보완책 |
|------|--------|
| 인증서 탈취 | 인증서 유효기간 단축 + 자동 갱신 |
| 만료된 인증서 사용 | OCSP/CRL 검증 활성화 |
| 내부자 위협 | 애플리케이션 레이어 인가(RBAC) 병행 |
| 중간자 공격 | Certificate Pinning 고려 |

## 정리

mTLS는 마이크로서비스 환경에서 서비스 간 신뢰를 코드나 설정이 아닌 **암호학적 증명**으로 확보하는 강력한 방법이다. 핵심을 정리하면 다음과 같다.

- **상호 인증**: 서버와 클라이언트 모두 인증서로 신원을 증명한다.
- **구현 방법**: Spring Boot SSL 설정 + SSLContext 기반 RestClient, 또는 Nginx/서비스 메시에서 오프로드.
- **운영 핵심**: 인증서 만료 모니터링과 자동 갱신 파이프라인이 없으면 장애로 이어진다.
- **한계 인지**: mTLS는 전송 계층의 해결책이며, 애플리케이션 레이어 인가와 함께 계층적 방어를 구성해야 한다.

소규모 팀이라면 Nginx mTLS 설정부터 시작하고, 서비스가 많아지면 **Istio의 PeerAuthentication**으로 전환하는 점진적 접근이 현실적이다. 중요한 것은 내부망이라는 이유로 보안을 소홀히 하지 않는 Zero Trust 마인드셋을 갖추는 것이다.
