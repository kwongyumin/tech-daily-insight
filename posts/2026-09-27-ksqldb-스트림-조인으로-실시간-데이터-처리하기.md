# ksqlDB 스트림 조인으로 실시간 데이터 처리하기

## 개요

이벤트 기반 아키텍처가 보편화되면서 실시간 데이터 처리에 대한 요구는 점점 높아지고 있다. Kafka를 도입한 팀이라면 자연스럽게 "스트리밍 데이터를 SQL처럼 다룰 수 없을까?"라는 고민을 하게 된다. ksqlDB는 바로 그 지점에서 등장한다.

ksqlDB는 Kafka 위에서 동작하는 스트리밍 SQL 엔진으로, Kafka Streams를 기반으로 만들어졌다. SQL 문법으로 스트림과 테이블을 정의하고, 필터링, 집계, 그리고 **조인(Join)** 연산을 선언적으로 표현할 수 있다. 특히 스트림 조인은 실시간 데이터 파이프라인에서 핵심적인 역할을 한다. 주문 이벤트와 사용자 정보를 실시간으로 결합하거나, 클릭 로그와 상품 정보를 조인하는 시나리오가 대표적이다.

이 글에서는 ksqlDB의 핵심 조인 개념을 정리하고, 실무에서 자주 마주치는 시나리오를 예제 코드와 함께 살펴본다. 또한 운영 관점에서 주의해야 할 트레이드오프도 함께 다룬다.

## 핵심 개념

### Stream vs Table

ksqlDB를 이해하는 출발점은 **Stream**과 **Table**의 차이다.

- **Stream**: Kafka 토픽의 이벤트 로그 그 자체. 불변(immutable)이며 시간 순서로 쌓이는 이벤트의 연속이다. "무슨 일이 일어났는가"를 표현한다.
- **Table**: 특정 키 기준으로 최신 상태를 유지하는 구체화된 뷰(Materialized View). "현재 상태가 무엇인가"를 표현한다. 내부적으로는 Kafka 토픽의 changelog를 읽어 RocksDB에 상태를 저장한다.

### 조인의 세 가지 유형

ksqlDB는 세 가지 조인 조합을 지원한다.

| 조인 유형 | 윈도우 필요 여부 | 설명 |
|---|---|---|
| Stream-Stream | 필요 | 두 스트림 이벤트를 시간 윈도우 내에서 결합 |
| Stream-Table | 불필요 | 스트림 이벤트를 테이블의 현재 값과 결합 |
| Table-Table | 불필요 | 두 테이블의 최신 상태를 결합 |

### 윈도우(Window)

Stream-Stream 조인에서는 반드시 **윈도우**를 지정해야 한다. 두 스트림의 이벤트가 정확히 동시에 도달하지 않기 때문에, "어느 시간 범위 안에 도착한 이벤트끼리 결합할지"를 지정해야 한다.

```sql
-- WITHIN 절로 윈도우 크기를 지정한다
JOIN stream_b WITHIN 1 HOURS ON ...
```

## 실전 예제

### 시나리오 설정

이커머스 플랫폼에서 다음과 같은 실시간 처리가 필요하다고 가정한다.

1. `orders` 토픽: 주문 이벤트 (주문 ID, 사용자 ID, 상품 ID, 수량)
2. `payments` 토픽: 결제 이벤트 (결제 ID, 주문 ID, 금액, 결제 수단)
3. `users` 토픽: 사용자 정보 (사용자 ID, 이름, 등급)

목표는 주문과 결제를 실시간으로 결합하고, 사용자 정보까지 enrichment하여 하나의 완성된 이벤트로 만드는 것이다.

### Step 1: 스트림과 테이블 정의

먼저 기존 Kafka 토픽 위에 ksqlDB 스트림과 테이블을 정의한다.

```sql
-- 주문 스트림 생성
CREATE STREAM orders (
  order_id    VARCHAR KEY,
  user_id     VARCHAR,
  product_id  VARCHAR,
  quantity    INT,
  created_at  BIGINT
) WITH (
  KAFKA_TOPIC = 'orders',
  VALUE_FORMAT = 'JSON',
  TIMESTAMP = 'created_at'
);

-- 결제 스트림 생성
CREATE STREAM payments (
  payment_id     VARCHAR KEY,
  order_id       VARCHAR,
  amount         DECIMAL(10, 2),
  payment_method VARCHAR,
  paid_at        BIGINT
) WITH (
  KAFKA_TOPIC = 'payments',
  VALUE_FORMAT = 'JSON',
  TIMESTAMP = 'paid_at'
);

-- 사용자 테이블 생성 (최신 상태를 유지)
CREATE TABLE users (
  user_id  VARCHAR PRIMARY KEY,
  name     VARCHAR,
  grade    VARCHAR
) WITH (
  KAFKA_TOPIC = 'users',
  VALUE_FORMAT = 'JSON'
);
```

### Step 2: Stream-Stream 조인 (주문 + 결제)

주문과 결제는 두 이벤트 모두 실시간으로 발생한다. 주문 이벤트 이후 최대 2시간 이내에 결제가 완료된다고 가정하고, `order_id`를 키로 조인한다.

Stream-Stream 조인을 수행하려면 먼저 두 스트림의 키를 조인 기준 컬럼으로 맞춰야 한다.

```sql
-- payments를 order_id 키로 재파티셔닝
CREATE STREAM payments_by_order AS
  SELECT
    order_id AS order_id,
    payment_id,
    amount,
    payment_method,
    paid_at
  FROM payments
  PARTITION BY order_id;

-- Stream-Stream 조인: 주문과 결제를 2시간 윈도우 내에서 결합
CREATE STREAM order_payment_joined AS
  SELECT
    o.order_id,
    o.user_id,
    o.product_id,
    o.quantity,
    p.payment_id,
    p.amount,
    p.payment_method,
    o.created_at AS ordered_at,
    p.paid_at
  FROM orders o
  INNER JOIN payments_by_order p
    WITHIN 2 HOURS
    ON o.order_id = p.order_id
  EMIT CHANGES;
```

> **주의**: Stream-Stream 조인 전, 양쪽 스트림은 동일한 파티션 수를 가진 토픽을 기반으로 해야 하며, 조인 키로 파티셔닝되어 있어야 한다. 그렇지 않으면 ksqlDB가 자동으로 내부 토픽을 생성해 재파티셔닝한다.

### Step 3: Stream-Table 조인 (주문결제 + 사용자 정보)

이제 위에서 만든 `order_payment_joined` 스트림에 사용자 정보를 enrichment한다. 사용자 정보는 자주 변하지 않는 차원 데이터이므로 Table로 정의했다.

```sql
-- Stream-Table 조인: 실시간 이벤트에 사용자 정보 결합
CREATE STREAM enriched_orders AS
  SELECT
    op.order_id,
    op.user_id,
    u.name          AS user_name,
    u.grade         AS user_grade,
    op.product_id,
    op.quantity,
    op.payment_id,
    op.amount,
    op.payment_method,
    op.ordered_at,
    op.paid_at
  FROM order_payment_joined op
  LEFT JOIN users u
    ON op.user_id = u.user_id
  EMIT CHANGES;
```

Stream-Table 조인에서 `LEFT JOIN`을 사용하면, 테이블에 해당 키가 없는 경우에도 스트림 이벤트를 누락 없이 내보낸다. 사용자 정보가 아직 채워지지 않은 엣지 케이스를 처리하는 데 유용하다.

### Step 4: 집계 - 실시간 등급별 매출 집계

최종 enriched 데이터를 바탕으로 사용자 등급별 실시간 매출을 집계해 보자.

```sql
-- 1분 Tumbling 윈도우로 등급별 매출 집계
CREATE TABLE grade_revenue_per_minute AS
  SELECT
    user_grade,
    WINDOWSTART                          AS window_start,
    WINDOWEND                            AS window_end,
    COUNT(*)                             AS order_count,
    SUM(amount)                          AS total_revenue,
    AVG(amount)                          AS avg_order_value
  FROM enriched_orders
  WINDOW TUMBLING (SIZE 1 MINUTES)
  GROUP BY user_grade
  EMIT FINAL;
```

`EMIT FINAL`은 윈도우가 닫힐 때 최종 결과만 내보내도록 한다. 대시보드나 알림 시스템에 연동할 때 중간 업데이트를 필터링하고 싶다면 유용하다. 반대로 `EMIT CHANGES`를 사용하면 집계가 갱신될 때마다 이벤트가 발행된다.

### 결과 확인

```sql
-- 실시간 스트림 데이터 확인
SELECT * FROM enriched_orders EMIT CHANGES LIMIT 10;

-- 특정 사용자 등급 필터링
SELECT *
FROM enriched_orders
WHERE user_grade = 'VIP'
EMIT CHANGES;

-- 집계 테이블 조회
SELECT *
FROM grade_revenue_per_minute
WHERE WINDOWSTART > '2024-01-01T00:00:00'
EMIT CHANGES;
```

## 주의사항 및 트레이드오프

### 1. 재파티셔닝 비용

Stream-Stream 조인에서 양쪽 스트림의 파티션 키가 일치하지 않으면 ksqlDB는 내부적으로 재파티셔닝 토픽을 생성한다. 이는 **추가적인 Kafka 쓰기/읽기 오버헤드**를 유발한다. 토픽 설계 단계에서부터 조인 키 기준으로 파티셔닝을 맞춰두면 이 비용을 줄일 수 있다.

### 2. 윈도우 크기와 상태 저장소 크기

Stream-Stream 조인의 윈도우를 크게 잡을수록 RocksDB에 보관해야 하는 상태 데이터가 많아진다. 예를 들어 2시간 윈도우를 설정하면, 최대 2시간치 이벤트를 메모리+디스크에 유지한다. **처리량이 높은 토픽에서 윈도우를 지나치게 크게 설정하면 상태 저장소가 급격히 비대해질 수 있다.** `ksql.streams.state.dir` 설정과 디스크 용량 모니터링을 반드시 챙겨야 한다.

### 3. 이벤트 도착 순서와 지연(Late Events)

이벤트가 네트워크 지연 등으로 늦게 도착하는 경우, 이미 윈도우가 닫힌 후에 도착한 이벤트는 기본적으로 조인 결과에 포함되지 않는다. Kafka Streams의 `grace period` 개념처럼, ksqlDB에서는 `GRACE PERIOD` 절로 늦은 이벤트를 어느 정도 수용할 수 있다.

```sql
WINDOW TUMBLING (SIZE 1 MINUTES, GRACE PERIOD 30 SECONDS)
```

허용 범위 내 지연 이벤트까지 포함하되, grace period를 길게 잡으면 결과 발행 지연도 그만큼 늘어난다.

### 4. Stream-Table 조인의 타이밍 이슈

Stream-Table 조인에서 스트림 이벤트가 도착했을 때 테이블에 아직 해당 키가 없으면 `LEFT JOIN`이라도 사용자 정보 컬럼이 null로 채워진다. 테이블 데이터가 초기 로딩(bootstrapping)되기 전에 스트림 이벤트가 처리되는 시나리오를 고려해야 한다. 이 경우 null 처리 로직이나 다운스트림에서의 재처리 전략이 필요하다.

### 5. ksqlDB vs Kafka Streams 직접 사용

ksqlDB는 편의성이 높지만, 복잡한 비즈니스 로직이나 세밀한 상태 관리가 필요한 경우에는 **Kafka Streams API를 직접 사용하는 것이 더 적합**하다. ksqlDB는 SQL 레이어 아래에서 Kafka Streams를 사용하므로, 복잡한 커스터마이징이 필요하면 표현력의 한계에 부딪히게 된다. 팀의 SQL 친화도, 로직 복잡도, 운영 편의성을 종합적으로 고려해 선택해야 한다.

### 6. 운영 관점: 쿼리 재시작과 오프셋

ksqlDB의 영구 쿼리(Persistent Query)는 Kafka Consumer Group처럼 오프셋을 관리한다. 쿼리를 삭제하고 재생성하면 **기본적으로 latest 오프셋에서 시작**하므로, 중간에 누락된 이벤트가 발생할 수 있다. `ksql.streams.auto.offset.reset=earliest` 설정과 쿼리 생명주기 관리 전략을 미리 수립해두어야 한다.

## 정리

ksqlDB 스트림 조인은 복잡한 Kafka Streams 코드 없이 SQL 선언적 문법으로 실시간 데이터 파이프라인을 구성할 수 있게 해준다. 핵심 포인트를 정리하면 다음과 같다.

- **Stream-Stream 조인**은 시간 윈도우가 필수이며, 파티션 키 정렬이 성능에 직접 영향을 준다.
- **Stream-Table 조인**은 실시간 이벤트에 차원 데이터를 enrichment하는 가장 일반적인 패턴이다.
- **윈도우 크기, 상태 저장소 크기, 지연 이벤트 처리**는 운영 단계에서 반드시 고려해야 할 변수다.
- 복잡한 로직이 필요한 경우 Kafka Streams API와의 역할 분담을 고려하라.

실시간 데이터 파이프라인 설계는 기능 구현만큼이나 **운영 안정성과 확장성**이 중요하다. ksqlDB를 처음 도입할 때는 작은 스코프에서 충분한 부하 테스트와 모니터링 체계를 갖춘 뒤 점진적으로 확장하는 접근이 안전하다.
