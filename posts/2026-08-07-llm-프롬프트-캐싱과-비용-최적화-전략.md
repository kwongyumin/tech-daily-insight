# LLM 프롬프트 캐싱과 비용 최적화 전략

## 개요

LLM(Large Language Model) API를 프로덕션 환경에서 운용하다 보면, 어느 순간 청구서를 보고 당황하는 경험을 하게 된다. GPT-4나 Claude Opus 같은 고성능 모델은 토큰당 비용이 상당하며, 트래픽이 늘어날수록 비용은 선형이 아닌 기하급수적으로 증가하는 경향이 있다.

이 문제를 해결하는 핵심 전략 중 하나가 **프롬프트 캐싱(Prompt Caching)**이다. 단순히 응답 결과를 캐싱하는 것을 넘어, LLM 공급자가 제공하는 네이티브 캐싱 기능과 애플리케이션 레벨의 캐싱 전략을 결합하면 비용을 최대 90%까지 절감하는 사례도 존재한다.

이 글에서는 프롬프트 캐싱의 핵심 개념부터 Spring Boot 기반의 실전 구현 예제, 그리고 실무에서 반드시 알아야 할 트레이드오프까지 다룬다.

---

## 핵심 개념

### 1. LLM 비용 구조 이해

대부분의 LLM API는 **입력 토큰(Input Token)**과 **출력 토큰(Output Token)**을 기준으로 과금한다. 일반적으로 출력 토큰이 입력 토큰보다 3~5배 비싸지만, RAG(Retrieval-Augmented Generation) 패턴처럼 긴 컨텍스트를 반복적으로 주입하는 경우에는 입력 토큰 비용이 지배적이 된다.

```
총 비용 = (입력 토큰 수 × 입력 단가) + (출력 토큰 수 × 출력 단가)

예시 (GPT-4o 기준):
- 입력: $5.00 / 1M tokens
- 출력: $15.00 / 1M tokens

시스템 프롬프트 2,000 토큰 × 일 10,000 요청 = 20M 토큰 = $100/일
```

이처럼 고정적인 시스템 프롬프트나 컨텍스트가 반복적으로 전송되는 것이 비용 낭비의 주범이다.

### 2. 프롬프트 캐싱의 두 가지 레이어

프롬프트 캐싱은 크게 두 레이어에서 작동한다.

**레이어 1: Provider-Side Caching (공급자 측 캐싱)**

Anthropic Claude는 `cache_control` 파라미터를 통해 프롬프트의 특정 부분을 서버에 캐싱한다. 캐시된 입력 토큰은 일반 입력 토큰 대비 약 90% 할인된 가격으로 처리된다. OpenAI도 유사하게 긴 프롬프트에 대해 자동 캐싱(Automatic Prompt Caching)을 지원한다.

**레이어 2: Application-Side Caching (애플리케이션 측 캐싱)**

동일하거나 유사한 입력에 대해 LLM 호출 자체를 건너뛰고 캐시된 응답을 반환한다. Redis, Memcached 같은 인메모리 캐시나 데이터베이스를 활용한다.

### 3. 캐싱 전략의 종류

| 전략 | 적합한 케이스 | 히트율 | 비고 |
|---|---|---|---|
| Exact Match | FAQ, 고정 쿼리 | 낮음 | 구현 단순 |
| Semantic Similarity | 유사 질문 군집 | 중간 | 임베딩 필요 |
| Prefix Caching | 긴 시스템 프롬프트 | 높음 | Provider 지원 필요 |
| Normalized Caching | 공백/대소문자 정규화 | 중간 | 전처리 필요 |

## 실전 예제

### Spring Boot + Redis 기반 LLM 응답 캐싱

아래는 실무에서 바로 사용할 수 있는 계층형 캐싱 구조다. Exact Match와 Semantic Similarity 캐싱을 조합한 방식이다.

**의존성 추가 (build.gradle)**

```groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-data-redis'
    implementation 'org.springframework.boot:spring-boot-starter-cache'
    implementation 'com.fasterxml.jackson.core:jackson-databind'
    // OpenAI Java SDK
    implementation 'com.theokanning.openai-gpt3-java:service:0.18.0'
}
```

**캐시 설정**

```java
@Configuration
@EnableCaching
public class CacheConfig {

    @Bean
    public RedisCacheManager cacheManager(RedisConnectionFactory factory) {
        RedisCacheConfiguration exactMatchConfig = RedisCacheConfiguration
            .defaultCacheConfig()
            .entryTtl(Duration.ofHours(24))
            .serializeValuesWith(
                RedisSerializationContext.SerializationPair
                    .fromSerializer(new GenericJackson2JsonRedisSerializer())
            );

        RedisCacheConfiguration semanticConfig = RedisCacheConfiguration
            .defaultCacheConfig()
            .entryTtl(Duration.ofHours(6)); // 시맨틱 캐시는 짧게

        return RedisCacheManager.builder(factory)
            .withCacheConfiguration("llm-exact", exactMatchConfig)
            .withCacheConfiguration("llm-semantic", semanticConfig)
            .build();
    }
}
```

**LLM 서비스 구현**

```java
@Service
@RequiredArgsConstructor
@Slf4j
public class LlmCachingService {

    private final RedisTemplate<String, String> redisTemplate;
    private final OpenAiService openAiService;
    private final EmbeddingService embeddingService;

    private static final String EXACT_CACHE_PREFIX = "llm:exact:";
    private static final String SEMANTIC_INDEX_KEY = "llm:semantic:index";
    private static final double SIMILARITY_THRESHOLD = 0.92;
    private static final Duration CACHE_TTL = Duration.ofHours(24);

    public LlmResponse getCachedOrFetch(LlmRequest request) {
        String normalizedPrompt = normalizePrompt(request.getUserMessage());
        String cacheKey = generateCacheKey(request.getSystemPrompt(), normalizedPrompt);

        // 1단계: Exact Match 캐시 조회
        String cachedExact = redisTemplate.opsForValue().get(EXACT_CACHE_PREFIX + cacheKey);
        if (cachedExact != null) {
            log.info("[CACHE HIT - EXACT] key={}", cacheKey);
            return LlmResponse.fromCached(cachedExact, CacheType.EXACT);
        }

        // 2단계: Semantic Similarity 캐시 조회
        Optional<LlmResponse> semanticResult = findSemanticCache(normalizedPrompt);
        if (semanticResult.isPresent()) {
            log.info("[CACHE HIT - SEMANTIC] similarity match found");
            return semanticResult.get();
        }

        // 3단계: 실제 LLM 호출
        log.info("[CACHE MISS] calling LLM API");
        LlmResponse response = callLlmApi(request);

        // 캐시 저장 (비동기)
        saveToCache(cacheKey, normalizedPrompt, response);

        return response;
    }

    private String normalizePrompt(String prompt) {
        return prompt.trim()
            .toLowerCase()
            .replaceAll("\\s+", " ")
            .replaceAll("[^가-힣a-z0-9\\s?!.,]", "");
    }

    private String generateCacheKey(String systemPrompt, String userMessage) {
        String combined = systemPrompt + "|" + userMessage;
        return DigestUtils.sha256Hex(combined);
    }

    private Optional<LlmResponse> findSemanticCache(String prompt) {
        try {
            float[] queryEmbedding = embeddingService.embed(prompt);
            // Redis Vector Search 또는 별도 벡터 DB 활용
            return embeddingService.findSimilar(queryEmbedding, SIMILARITY_THRESHOLD);
        } catch (Exception e) {
            log.warn("Semantic cache lookup failed", e);
            return Optional.empty();
        }
    }

    @Async
    protected void saveToCache(String cacheKey, String prompt, LlmResponse response) {
        try {
            // Exact Match 저장
            redisTemplate.opsForValue().set(
                EXACT_CACHE_PREFIX + cacheKey,
                response.getContent(),
                CACHE_TTL
            );
            // 임베딩 저장 (Semantic Cache용)
            embeddingService.saveEmbedding(prompt, response);
        } catch (Exception e) {
            log.error("Cache save failed", e);
        }
    }

    private LlmResponse callLlmApi(LlmRequest request) {
        ChatCompletionRequest completionRequest = ChatCompletionRequest.builder()
            .model("gpt-4o")
            .messages(List.of(
                new ChatMessage("system", request.getSystemPrompt()),
                new ChatMessage("user", request.getUserMessage())
            ))
            .maxTokens(1000)
            .build();

        ChatCompletionResult result = openAiService.createChatCompletion(completionRequest);
        return LlmResponse.from(result);
    }
}
```

### Anthropic Claude Provider-Side Caching 활용

Claude의 `cache_control`을 활용하면 긴 시스템 프롬프트를 서버 측에 캐싱할 수 있다.

```java
@Service
public class ClaudeCachingService {

    private final WebClient webClient;

    // 긴 시스템 프롬프트 (수천 토큰짜리 RAG 컨텍스트 등)
    private static final String LONG_SYSTEM_PROMPT = """
        당신은 금융 도메인 전문가입니다.
        [... 수천 토큰의 도메인 지식 및 규정 문서 ...]
        """;

    public Mono<String> askWithCaching(String userQuestion) {
        Map<String, Object> requestBody = Map.of(
            "model", "claude-3-5-sonnet-20241022",
            "max_tokens", 1024,
            "system", List.of(
                Map.of(
                    "type", "text",
                    "text", LONG_SYSTEM_PROMPT,
                    "cache_control", Map.of("type", "ephemeral") // 캐싱 지시
                )
            ),
            "messages", List.of(
                Map.of("role", "user", "content", userQuestion)
            )
        );

        return webClient.post()
            .uri("https://api.anthropic.com/v1/messages")
            .header("anthropic-beta", "prompt-caching-2024-07-31")
            .bodyValue(requestBody)
            .retrieve()
            .bodyToMono(ClaudeResponse.class)
            .map(response -> {
                // cache_creation_input_tokens vs cache_read_input_tokens 로깅
                logCacheUsage(response.getUsage());
                return response.getContent();
            });
    }

    private void logCacheUsage(Usage usage) {
        log.info("Cache Stats - Created: {}, Read: {}, Regular Input: {}, Output: {}",
            usage.getCacheCreationInputTokens(),
            usage.getCacheReadInputTokens(),
            usage.getInputTokens(),
            usage.getOutputTokens()
        );
    }
}
```

### 비용 모니터링 컴포넌트

```java
@Component
@Slf4j
public class LlmCostTracker {

    private final MeterRegistry meterRegistry;
    private static final double INPUT_COST_PER_1K = 0.005;
    private static final double OUTPUT_COST_PER_1K = 0.015;
    private static final double CACHE_READ_DISCOUNT = 0.1; // 90% 할인

    public void track(TokenUsage usage, CacheType cacheType) {
        double cost = calculateCost(usage, cacheType);

        // Micrometer로 Prometheus/Grafana 연동
        meterRegistry.counter("llm.cost.usd",
            "cache_type", cacheType.name(),
            "model", usage.getModel()
        ).increment(cost);

        meterRegistry.counter("llm.tokens.input",
            "cache_type", cacheType.name()
        ).increment(usage.getInputTokens());

        log.info("LLM Cost Tracked: ${} ({})", String.format("%.6f", cost), cacheType);
    }

    private double calculateCost(TokenUsage usage, CacheType cacheType) {
        double inputCost = switch (cacheType) {
            case EXACT, SEMANTIC -> 0.0; // 캐시 히트 = API 호출 없음
            case PROVIDER_CACHE_READ ->
                (usage.getCacheReadTokens() / 1000.0) * INPUT_COST_PER_1K * CACHE_READ_DISCOUNT;
            case NONE ->
                (usage.getInputTokens() / 1000.0) * INPUT_COST_PER_1K;
        };
        double outputCost = (usage.getOutputTokens() / 1000.0) * OUTPUT_COST_PER_1K;
        return inputCost + outputCost;
    }
}
```

## 주의사항 및 트레이드오프

### 1. 캐시 일관성(Cache Consistency) 문제

LLM 응답은 기본적으로 **확률적(stochastic)**이다. 동일한 입력이라도 매번 다른 응답이 나올 수 있으며, 이것이 기대되는 동작인 경우가 많다. 창의적인 콘텐츠 생성이나 다양한 추천 결과가 필요한 유즈케이스에 캐싱을 적용하면 사용자 경험이 오히려 저하될 수 있다.

> **실무 팁**: `temperature=0`으로 설정하는 경우에만 Exact Match 캐싱을 적극 적용하고, 그 외에는 시맨틱 캐싱도 신중하게 사용하라.

### 2. 시맨틱 캐싱의 임계값 설정

Cosine Similarity 임계값을 너무 낮게 설정하면 관련 없는 응답이 반환되고, 너무 높게 설정하면 캐시 히트율이 떨어진다. **0.90~0.95** 사이를 권장하며, 도메인별로 A/B 테스트를 통해 튜닝해야 한다.

### 3. Provider-Side Cache의 TTL 제약

Anthropic의 ephemeral 캐시는 **5분**의 TTL을 가진다. 요청 간격이 5분을 초과하면 캐시 미스가 발생하므로, 트래픽 패턴이 산발적인 서비스에서는 효과가 제한적이다. 또한 캐시 생성(write) 시에는 오히려 일반 입력 토큰보다 25% 비싼 비용이 발생한다.

### 4. 개인정보 및 보안

사용자의 민감한 정보가 포함된 프롬프트는 절대 캐싱하면 안 된다. 캐시 키 생성 전에 PII(개인식별정보) 탐지 및 마스킹 로직을 반드시 선행해야 하며, 멀티테넌트 환경에서는 테넌트 ID를 캐시 키에 포함시켜 데이터 격리를 보장해야 한다.

```java
// 안전한 캐시 키 생성 예시
private String generateSafeCacheKey(String tenantId, String prompt) {
    String sanitized = piiDetector.mask(prompt); // PII 마스킹
    return tenantId + ":" + DigestUtils.sha256Hex(sanitized);
}
```

### 5. 캐시 무효화(Cache Invalidation) 전략

모델 버전이 업그레이드되거나 시스템 프롬프트가 변경되면 기존 캐시는 즉시 무효화되어야 한다. 캐시 키에 모델 버전과 프롬프트 버전을 포함시키는 **버전 기반 무효화** 전략을 사용하는 것이 안전하다.

## 정리

LLM 비용 최적화는 단일 기법이 아니라 여러 레이어의 전략을 조합하는 것이 핵심이다.

| 전략 | 예상 절감 효과 | 구현 복잡도 |
|---|---|---|
| Exact Match 캐싱 | 반복 쿼리의 100% | 낮음 |
| Semantic 캐싱 | 유사 쿼리의 60~80% | 중간 |
| Provider Prefix Caching | 입력 토큰의 최대 90% | 낮음 |
| 배치 처리 | 처리량 기반 10~20% | 중간 |
| 모델 다운그레이드 | 전체의 50~90% | 낮음 |

실무에서는 먼저 **트래픽 로그를 분석하여 반복 패턴을 파악**하고, 가장 효과가 큰 구간에 Exact Match 캐싱을 적용한 뒤 점차 Semantic 캐싱과 Provider-Side 캐싱으로 확장하는 것을 권장한다. 비용 절감 못지않게 **캐시 히트율, 응답 품질, 레이턴시**를 함께 모니터링하는 관찰 가능성(Observability) 체계를 구축하는 것이 장기적으로 훨씬 중요하다.

LLM 인프라 비용은 앞으로도 AI 서비스의 핵심 관심사로 남을 것이다. 지금부터 캐싱 전략을 내재화해두면, 서비스 스케일업 시에도 비용 곡선을 완만하게 유지할 수 있다.
