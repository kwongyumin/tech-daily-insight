# 이벤트 소싱 저장소 설계와 스냅샷 전략

## 개요

이벤트 소싱(Event Sourcing)은 도메인 객체의 현재 상태를 직접 저장하는 대신, 상태 변화를 유발한 **이벤트의 시퀀스**를 저장하는 패턴이다. 현재 상태는 저장된 이벤트를 순서대로 재생(replay)함으로써 도출된다.

이 패턴은 감사 로그(audit log), 시간 여행 쿼리(temporal query), CQRS와의 자연스러운 결합 등 강력한 이점을 제공한다. 그러나 이벤트가 수십만 건 이상 쌓이기 시작하면 단순히 "이벤트를 쌓는다"는 개념만으로는 성능 문제를 피하기 어렵다.

이 글에서는 이벤트 소싱 저장소를 실무 수준으로 설계하는 방법과, 그 핵심 최적화 기법인 **스냅샷 전략**을 다룬다. 단순한 개념 소개보다는 실제 구현 판단에 필요한 트레이드오프를 중심으로 설명한다.

## 핵심 개념

### 이벤트 스토어의 구조

이벤트 스토어는 본질적으로 **append-only 로그**다. 핵심 속성은 다음과 같다.

- **Stream**: 단일 Aggregate의 이벤트 시퀀스. 보통 `{aggregate_type}-{aggregate_id}` 형태로 식별한다.
- **Global Sequence**: 전체 스토어를 아우르는 단조 증가 순서 번호. 프로젝션 구독에 사용된다.
- **Stream Version**: 특정 스트림 내 이벤트의 순서 번호. 낙관적 동시성 제어(Optimistic Concurrency Control)에 사용된다.

이벤트 저장 테이블의 기본 스키마는 아래와 같이 설계할 수 있다.

```sql
CREATE TABLE event_store (
    global_seq      BIGSERIAL PRIMARY KEY,          -- 전역 순서
    stream_id       VARCHAR(255)    NOT NULL,        -- {type}-{id}
    stream_version  BIGINT          NOT NULL,        -- 스트림 내 순서
    event_type      VARCHAR(255)    NOT NULL,        -- 이벤트 클래스명
    payload         JSONB           NOT NULL,        -- 직렬화된 이벤트 데이터
    metadata        JSONB,                           -- 상관 ID, 사용자 등 메타
    occurred_at     TIMESTAMPTZ     NOT NULL DEFAULT now(),

    -- 낙관적 동시성 제어를 위한 유니크 제약
    CONSTRAINT uq_stream_version UNIQUE (stream_id, stream_version)
);

CREATE INDEX idx_event_store_stream ON event_store (stream_id, stream_version);
CREATE INDEX idx_event_store_global ON event_store (global_seq);
```

`UNIQUE (stream_id, stream_version)` 제약은 동시에 같은 버전으로 쓰기를 시도하는 경우 DB 레벨에서 충돌을 감지하게 해준다. 이것이 이벤트 소싱에서 낙관적 잠금을 구현하는 핵심이다.

### 스냅샷이 필요한 이유

Aggregate를 로드할 때마다 처음부터 모든 이벤트를 재생하면, 이벤트 수가 늘어날수록 로딩 시간이 선형으로 증가한다. 주문 하나에 이벤트가 500건이라면 매 조회마다 500건을 읽고 적용해야 한다.

**스냅샷(Snapshot)**은 특정 시점의 Aggregate 상태를 직렬화해 별도로 저장하는 최적화 기법이다. 로드 시 가장 최근 스냅샷을 불러온 뒤, 그 이후의 이벤트만 재생하면 된다.

```
[스냅샷 v100] → [이벤트 v101] → [이벤트 v102] → [현재 상태]
```

## 실전 예제

### Java/Spring 기반 이벤트 스토어 구현

```java
// 이벤트 메타데이터를 담는 래퍼
public record EventEnvelope(
    long globalSeq,
    String streamId,
    long streamVersion,
    String eventType,
    Object payload,
    Instant occurredAt
) {}

@Repository
@RequiredArgsConstructor
public class JdbcEventStore {

    private final JdbcTemplate jdbcTemplate;
    private final ObjectMapper objectMapper;

    // 이벤트 저장 - 낙관적 동시성 제어 포함
    public void appendEvents(String streamId, long expectedVersion, List<Object> events) {
        long version = expectedVersion;
        for (Object event : events) {
            version++;
            try {
                jdbcTemplate.update("""
                    INSERT INTO event_store (stream_id, stream_version, event_type, payload)
                    VALUES (?, ?, ?, ?::jsonb)
                    """,
                    streamId,
                    version,
                    event.getClass().getSimpleName(),
                    serialize(event)
                );
            } catch (DuplicateKeyException e) {
                throw new OptimisticConcurrencyException(
                    "Stream %s has been modified concurrently at version %d"
                        .formatted(streamId, version)
                );
            }
        }
    }

    // 특정 버전 이후의 이벤트 조회
    public List<EventEnvelope> loadEvents(String streamId, long fromVersion) {
        return jdbcTemplate.query("""
            SELECT global_seq, stream_id, stream_version, event_type, payload, occurred_at
            FROM event_store
            WHERE stream_id = ? AND stream_version > ?
            ORDER BY stream_version ASC
            """,
            (rs, rowNum) -> new EventEnvelope(
                rs.getLong("global_seq"),
                rs.getString("stream_id"),
                rs.getLong("stream_version"),
                rs.getString("event_type"),
                deserialize(rs.getString("payload"), rs.getString("event_type")),
                rs.getTimestamp("occurred_at").toInstant()
            ),
            streamId, fromVersion
        );
    }

    private String serialize(Object event) {
        try {
            return objectMapper.writeValueAsString(event);
        } catch (JsonProcessingException e) {
            throw new EventSerializationException(e);
        }
    }
}
```

### 스냅샷 저장소 설계

```sql
CREATE TABLE aggregate_snapshot (
    stream_id       VARCHAR(255)    NOT NULL,
    version         BIGINT          NOT NULL,
    aggregate_type  VARCHAR(255)    NOT NULL,
    state           JSONB           NOT NULL,
    created_at      TIMESTAMPTZ     NOT NULL DEFAULT now(),

    PRIMARY KEY (stream_id, version)
);

-- 가장 최근 스냅샷만 빠르게 조회하기 위한 인덱스
CREATE INDEX idx_snapshot_latest ON aggregate_snapshot (stream_id, version DESC);
```

```java
@Repository
@RequiredArgsConstructor
public class SnapshotStore {

    private final JdbcTemplate jdbcTemplate;
    private final ObjectMapper objectMapper;

    public void saveSnapshot(String streamId, long version, Object aggregateState) {
        jdbcTemplate.update("""
            INSERT INTO aggregate_snapshot (stream_id, version, aggregate_type, state)
            VALUES (?, ?, ?, ?::jsonb)
            ON CONFLICT (stream_id, version) DO NOTHING
            """,
            streamId,
            version,
            aggregateState.getClass().getSimpleName(),
            serialize(aggregateState)
        );
    }

    public Optional<SnapshotEnvelope> loadLatestSnapshot(String streamId) {
        List<SnapshotEnvelope> results = jdbcTemplate.query("""
            SELECT stream_id, version, aggregate_type, state
            FROM aggregate_snapshot
            WHERE stream_id = ?
            ORDER BY version DESC
            LIMIT 1
            """,
            (rs, rowNum) -> new SnapshotEnvelope(
                rs.getString("stream_id"),
                rs.getLong("version"),
                rs.getString("aggregate_type"),
                rs.getString("state")
            ),
            streamId
        );
        return results.stream().findFirst();
    }
}
```

### Aggregate 로딩 조합 로직

```java
@Service
@RequiredArgsConstructor
public class AggregateRepository<T extends AggregateRoot> {

    private final JdbcEventStore eventStore;
    private final SnapshotStore snapshotStore;
    private static final int SNAPSHOT_THRESHOLD = 50; // 스냅샷 생성 기준

    public T load(String streamId, Class<T> type) {
        // 1. 최신 스냅샷 조회
        Optional<SnapshotEnvelope> snapshot = snapshotStore.loadLatestSnapshot(streamId);

        T aggregate;
        long fromVersion;

        if (snapshot.isPresent()) {
            // 2a. 스냅샷에서 복원
            aggregate = deserializeState(snapshot.get().state(), type);
            fromVersion = snapshot.get().version();
        } else {
            // 2b. 초기 상태 생성
            aggregate = createEmpty(type);
            fromVersion = 0L;
        }

        // 3. 스냅샷 이후 이벤트만 재생
        List<EventEnvelope> events = eventStore.loadEvents(streamId, fromVersion);
        events.forEach(e -> aggregate.apply(e.payload()));

        return aggregate;
    }

    public void save(T aggregate) {
        List<Object> pendingEvents = aggregate.getPendingEvents();
        if (pendingEvents.isEmpty()) return;

        eventStore.appendEvents(
            aggregate.getStreamId(),
            aggregate.getBaseVersion(),
            pendingEvents
        );

        long newVersion = aggregate.getBaseVersion() + pendingEvents.size();

        // 4. 스냅샷 생성 조건 판단
        if (shouldTakeSnapshot(aggregate.getBaseVersion(), newVersion)) {
            aggregate.applyAll(pendingEvents);
            snapshotStore.saveSnapshot(
                aggregate.getStreamId(),
                newVersion,
                aggregate
            );
        }

        aggregate.clearPendingEvents();
    }

    private boolean shouldTakeSnapshot(long baseVersion, long newVersion) {
        // 버전이 threshold 배수를 넘어가는 시점에 스냅샷
        return (newVersion / SNAPSHOT_THRESHOLD) > (baseVersion / SNAPSHOT_THRESHOLD);
    }
}
```

## 주의사항 및 트레이드오프

### 1. 스냅샷 전략 선택

스냅샷을 언제 생성할지는 세 가지 접근 방식이 있으며, 각각 적합한 상황이 다르다.

| 전략 | 설명 | 적합한 경우 |
|------|------|-------------|
| **버전 기반** | N개 이벤트마다 생성 | 이벤트 발생 빈도가 균일할 때 |
| **시간 기반** | 주기적으로 비동기 생성 | 쓰기 경로 지연을 최소화하고 싶을 때 |
| **크기 기반** | 이벤트 수 대신 payload 크기 기준 | 이벤트 크기 편차가 클 때 |

쓰기 경로에서 동기적으로 스냅샷을 생성하면 레이턴시가 증가한다. 중요도가 높은 서비스라면 **비동기 스냅샷 워커**를 별도로 두는 것이 더 안전하다.

### 2. 이벤트 스키마 진화(Schema Evolution)

이벤트는 한번 저장되면 수정이 불가능하다. 이벤트 클래스 구조가 바뀌면 과거 이벤트를 역직렬화할 수 없게 되는 문제가 생긴다.

대응 전략:
- **Upcaster 패턴**: 오래된 버전의 이벤트를 최신 버전으로 변환하는 변환기를 로딩 파이프라인에 삽입한다.
- **이벤트 버전 필드 명시**: `event_type` 필드에 버전을 포함(`OrderCreatedV2`)하거나 별도 `schema_version` 컬럼을 둔다.
- **하위 호환 필드 추가 원칙**: 필드 삭제/이름 변경은 금지하고 추가만 허용한다. Jackson의 `@JsonIgnoreProperties(ignoreUnknown = true)` 설정을 활용한다.

### 3. 스냅샷 무효화

이벤트 타입이 아닌 Aggregate 상태 직렬화 형식이 바뀌면 기존 스냅샷이 무효화된다. 이를 대비해 스냅샷 테이블에도 `schema_version` 컬럼을 두고, 로딩 시 버전이 맞지 않는 스냅샷은 무시하고 이벤트 전체를 재생하도록 처리해야 한다.

### 4. 프로젝션과 Global Sequence

CQRS의 Read Model을 구성하는 프로젝션은 `global_seq`를 기반으로 처리 위치를 추적한다. PostgreSQL에서는 `LISTEN/NOTIFY` 또는 Outbox 패턴으로 새 이벤트 발생을 구독자에게 알릴 수 있다. `global_seq`에 갭(gap)이 생길 수 있으므로(트랜잭션 롤백 등), 순서 처리 로직에서 이를 감안해야 한다.

### 5. 보관 및 아카이빙 정책

이벤트 스토어는 데이터를 절대 삭제하지 않는 것이 원칙이지만, GDPR 같은 규제 대응이나 스토리지 비용 관리를 위해 아카이빙 전략이 필요할 수 있다. Cold storage 이전이나 이벤트 압축(여러 이벤트를 하나의 스냅샷으로 대체) 방식을 사전에 설계해두어야 한다.

## 정리

이벤트 소싱은 강력하지만, 단순히 이벤트를 테이블에 쌓는다고 완성되는 패턴이 아니다. 실무에서 안정적으로 운영하려면 다음 사항을 반드시 설계 단계에서 고려해야 한다.

- **낙관적 동시성 제어**: `UNIQUE (stream_id, stream_version)` 제약으로 충돌을 DB 레벨에서 차단한다.
- **스냅샷 전략**: 버전 기반, 시간 기반 중 서비스 특성에 맞는 방식을 선택하고, 가능하면 쓰기 경로 외부에서 비동기로 생성한다.
- **이벤트 스키마 진화**: Upcaster와 버전 관리 전략 없이는 장기 운영이 불가능하다.
- **Global Sequence 활용**: 프로젝션과 구독 처리의 기반이 되므로 갭 처리 로직을 명확히 한다.

이벤트 소싱의 복잡도는 비즈니스 요구사항의 복잡도를 반영한다. 감사 추적, 복잡한 도메인 로직, 이벤트 기반 통합이 핵심인 시스템이라면 초기 설계 비용을 충분히 상쇄하는 아키텍처가 될 것이다.
