# 이더리움 Layer 2 확장성 솔루션 비교 분석

## 개요

이더리움 메인넷(Layer 1)은 탈중앙화와 보안성에서 탁월하지만, 초당 약 15~30 TPS라는 처리 한계와 높은 가스비 문제를 안고 있다. 이를 해결하기 위해 등장한 **Layer 2(L2) 솔루션**은 트랜잭션 처리를 오프체인으로 위임하면서도 이더리움의 보안성을 상속받는 방식으로 설계되었다.

2024년 현재, Optimistic Rollup과 ZK Rollup이 L2 생태계의 양대 산맥을 형성하고 있으며, Arbitrum, Optimism, zkSync, StarkNet, Polygon zkEVM 등 다양한 프로덕션급 솔루션이 활발하게 운영 중이다. 이 글에서는 각 솔루션의 아키텍처적 차이, 개발자 관점에서의 트레이드오프, 그리고 실제 코드 예제를 통해 어떤 상황에서 어떤 L2를 선택해야 하는지 심층적으로 비교 분석한다.

---

## 핵심 개념

### Rollup의 동작 원리

모든 Rollup은 다음 세 가지 핵심 단계로 동작한다.

1. **트랜잭션 수집**: Sequencer가 L2 트랜잭션을 배치로 묶는다.
2. **상태 전이**: 배치 트랜잭션을 실행하여 새로운 상태 루트를 계산한다.
3. **데이터 게시**: 압축된 트랜잭션 데이터와 상태 루트를 L1에 게시한다.

두 방식의 핵심 차이는 **상태 전이의 유효성을 어떻게 보장하느냐**에 있다.

### Optimistic Rollup vs ZK Rollup

| 항목 | Optimistic Rollup | ZK Rollup |
|---|---|---|
| 유효성 검증 | Fraud Proof (사후 검증) | Validity Proof (즉시 검증) |
| 출금 대기 시간 | 7일 (챌린지 기간) | 수 분 ~ 수 시간 |
| 연산 비용 | 낮음 | 높음 (ZK 증명 생성) |
| EVM 호환성 | 거의 완전 (EVM Equivalent) | 제한적~완전 (구현마다 상이) |
| 대표 프로젝트 | Arbitrum One, OP Mainnet | zkSync Era, StarkNet, Polygon zkEVM |

### State Channel과 Plasma (레거시 L2)

State Channel과 Plasma는 초기 L2 접근 방식으로, Rollup 이전에 주목받았지만 데이터 가용성 문제와 일반 스마트 컨트랙트 지원의 한계로 현재는 Rollup에 자리를 내준 상태다. 다만 Lightning Network처럼 결제 특화 채널은 여전히 유효한 사용 사례를 가진다.

## 실전 예제

### 1. Arbitrum에 스마트 컨트랙트 배포하기

Arbitrum은 EVM Equivalent를 표방하므로, 기존 Solidity 코드를 수정 없이 배포할 수 있다. Hardhat 기반 배포 스크립트를 살펴보자.

```typescript
// hardhat.config.ts
import { HardhatUserConfig } from "hardhat/config";
import "@nomicfoundation/hardhat-toolbox";

const config: HardhatUserConfig = {
  solidity: "0.8.24",
  networks: {
    arbitrumOne: {
      url: "https://arb1.arbitrum.io/rpc",
      accounts: [process.env.PRIVATE_KEY!],
      chainId: 42161,
    },
    arbitrumSepolia: {
      url: "https://sepolia-rollup.arbitrum.io/rpc",
      accounts: [process.env.PRIVATE_KEY!],
      chainId: 421614,
    },
  },
  etherscan: {
    apiKey: {
      arbitrumOne: process.env.ARBISCAN_API_KEY!,
    },
  },
};

export default config;
```

```typescript
// scripts/deploy.ts
import { ethers } from "hardhat";

async function main() {
  const [deployer] = await ethers.getSigners();
  console.log("Deploying with account:", deployer.address);

  // L1 가스비와 비교해 수십~수백 배 저렴
  const gasPrice = await ethers.provider.getFeeData();
  console.log("Current gas price:", ethers.formatUnits(gasPrice.gasPrice!, "gwei"), "gwei");

  const Token = await ethers.getContractFactory("MyERC20Token");
  const token = await Token.deploy("MyToken", "MTK", ethers.parseEther("1000000"));
  
  await token.waitForDeployment();
  console.log("Token deployed to:", await token.getAddress());
}

main().catch(console.error);
```

### 2. L1 ↔ L2 브리지 메시지 패싱 (Arbitrum)

크로스체인 메시지 패싱은 L2 개발에서 가장 복잡한 부분 중 하나다. Arbitrum의 `Inbox` 컨트랙트를 이용한 L1→L2 메시지 전송 예제다.

```solidity
// contracts/L1Sender.sol
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

interface IInbox {
    function createRetryableTicket(
        address to,
        uint256 l2CallValue,
        uint256 maxSubmissionCost,
        address excessFeeRefundAddress,
        address callValueRefundAddress,
        uint256 gasLimit,
        uint256 maxFeePerGas,
        bytes calldata data
    ) external payable returns (uint256);
}

contract L1Sender {
    address public immutable inbox;
    address public immutable l2Target;

    event MessageSent(uint256 indexed ticketId, bytes data);

    constructor(address _inbox, address _l2Target) {
        inbox = _inbox;
        l2Target = _l2Target;
    }

    function sendMessageToL2(
        bytes calldata message,
        uint256 maxSubmissionCost,
        uint256 gasLimit,
        uint256 maxFeePerGas
    ) external payable returns (uint256 ticketId) {
        ticketId = IInbox(inbox).createRetryableTicket{value: msg.value}(
            l2Target,
            0,                    // L2에서 사용할 ETH 없음
            maxSubmissionCost,
            msg.sender,           // 초과 수수료 환불 주소
            msg.sender,           // callValue 환불 주소
            gasLimit,
            maxFeePerGas,
            message
        );
        emit MessageSent(ticketId, message);
    }
}
```

        // 실제 비즈니스 로직 처리
        _processMessage(data);
        emit MessageReceived(msgHash, data);
    }

    }

### 3. zkSync Era에서의 Account Abstraction 활용

zkSync Era는 네이티브 AA(Account Abstraction)를 지원한다. ERC-4337과 달리 프로토콜 레벨에서 지원하므로 더 효율적이다.

```solidity
// contracts/zksync/GaslessPaymaster.sol
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "@matterlabs/zksync-contracts/l2/system-contracts/interfaces/IPaymaster.sol";
import "@matterlabs/zksync-contracts/l2/system-contracts/interfaces/IPaymasterFlow.sol";
import "@matterlabs/zksync-contracts/l2/system-contracts/Constants.sol";

contract GaslessPaymaster is IPaymaster {
    address public immutable allowedToken;
    uint256 public constant TOKEN_PER_TX = 1e18; // 1 Token per tx

    constructor(address _token) {
        allowedToken = _token;
    }

    function validateAndPayForPaymasterTransaction(
        bytes32,
        bytes32,
        Transaction calldata _transaction
    ) external payable override onlyBootloader returns (
        bytes4 magic,
        bytes memory context
    ) {
        magic = PAYMASTER_VALIDATION_SUCCESS_MAGIC;
        
        require(
            _transaction.paymasterInput.length >= 4,
            "Invalid paymaster input"
        );

        bytes4 paymasterInputSelector = bytes4(_transaction.paymasterInput[0:4]);
        
        if (paymasterInputSelector == IPaymasterFlow.approvalBased.selector) {
            (address token, uint256 amount, ) = abi.decode(
                _transaction.paymasterInput[4:],
                (address, uint256, bytes)
            );
            
            require(token == allowedToken, "Invalid token");
            require(amount >= TOKEN_PER_TX, "Insufficient token allowance");

            address userAddress = address(uint160(_transaction.from));
            
            // 사용자 토큰을 paymaster로 전송
            bool success = IERC20(allowedToken).transferFrom(
                userAddress,
                address(this),
                TOKEN_PER_TX
            );
            require(success, "Token transfer failed");
        }

        // L2 가스비를 ETH로 부트로더에 지불
        uint256 requiredETH = _transaction.gasLimit * _transaction.maxFeePerGas;
        (bool ethSent, ) = payable(BOOTLOADER_FORMAL_ADDRESS).call{value: requiredETH}("");
        require(ethSent, "Failed to pay bootloader");
    }

    function postTransaction(
        bytes calldata,
        Transaction calldata,
        bytes32,
        bytes32,
        ExecutionResult,
        uint256
    ) external payable override onlyBootloader {}

    modifier onlyBootloader() {
        require(msg.sender == BOOTLOADER_FORMAL_ADDRESS, "Only bootloader");
        _;
    }

    receive() external payable {}
}
```

## 주의사항 및 트레이드오프

### 1. Sequencer 중앙화 리스크

현재 대부분의 L2는 단일 Sequencer를 운영한다. Sequencer가 다운되거나 검열(Censorship)을 수행할 경우, 사용자는 L1을 통한 강제 포함(Force Inclusion) 메커니즘을 사용할 수 있지만, 이는 지연과 추가 비용을 수반한다. 프로덕션 서비스에서는 이 시나리오에 대한 폴백 로직을 반드시 구현해야 한다.

### 2. 출금 지연 (Optimistic Rollup)

Optimistic Rollup의 7일 챌린지 기간은 DeFi 프로토콜에서 치명적 제약이 될 수 있다. 이를 우회하기 위해 **Fast Bridge** 서비스(Hop Protocol, Across Protocol 등)를 활용하는 것이 일반적이지만, 유동성 제공자에게 수수료를 지불해야 한다.

```typescript
// Across Protocol을 이용한 빠른 출금 예시
import { across } from "@across-protocol/sdk";

async function fastWithdraw(
  amount: bigint,
  destinationChainId: number
): Promise<void> {
  const client = new across.Client({
    originChainId: 42161, // Arbitrum One
    destinationChainId,   // Ethereum Mainnet: 1
  });

  const quote = await client.getQuote({
    inputToken: "0xFF970A61A04b1cA14834A43f5dE4533eBDDB5CC8", // USDC on Arbitrum
    outputToken: "0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48", // USDC on Mainnet
    inputAmount: amount,
  });

  console.log(`Bridge fee: ${quote.relayerFeePct}%`);
  console.log(`Estimated time: ${quote.estimatedFillTimeSec}s`);
}
```

### 3. ZK 증명 비용과 지연

ZK Rollup은 출금 속도가 빠르지만, 증명 생성(Prover)의 연산 비용이 상당하다. 이는 운영 비용에 직접 반영되며, 복잡한 스마트 컨트랙트 로직일수록 증명 비용이 기하급수적으로 증가할 수 있다. 특히 재귀적 연산이나 복잡한 암호화 연산은 일부 zkEVM에서 지원하지 않거나 매우 비효율적으로 동작할 수 있다.

### 4. EVM 호환성 수준 차이

Vitalik Buterin이 제안한 zkEVM 타입 분류를 기억해야 한다.

- **Type 1** (완전 동일): Ethereum 자체, 증명 생성 느림
- **Type 2** (EVM Equivalent): Polygon zkEVM, 기존 툴 완전 호환
- **Type 3** (거의 EVM): 일부 프리컴파일 미지원
- **Type 4** (고수준 언어 호환)**: zkSync Era (Solidity→LLVM), 가장 빠른 증명

Type이 낮을수록 호환성은 높지만 증명 비용이 증가한다. 기존 코드 재사용이 우선이라면 Type 2를, 성능이 우선이라면 Type 4를 고려하라.

## 정리

L2 솔루션 선택은 단순히 기술적 우열의 문제가 아니라 **비즈니스 요구사항과의 정합성** 문제다.

| 상황 | 추천 솔루션 |
|---|---|
| 기존 dApp 빠른 마이그레이션 | Arbitrum One (EVM 완전 호환) |
| 빠른 최종성 + 보안 우선 | zkSync Era 또는 Polygon zkEVM |
| 가스리스 UX 구현 | zkSync Era (네이티브 AA) |
| 게임/고빈도 트랜잭션 | StarkNet (Cairo 기반 고성능) |
| 프라이버시 + ZK 증명 | StarkNet 또는 커스텀 ZK 회로 |

현시점에서 필자가 권장하는 접근법은 다음과 같다. **신규 프로젝트라면 zkSync Era 또는 Arbitrum One을 기본 타겟으로 삼고**, 프로덕션 환경에서는 멀티체인 전략을 통해 특정 L2에 대한 락인(Lock-in)을 최소화하라. 브리지 컨트랙트와 체인 추상화 레이어를 설계 초기부터 고려하는 것이 장기적으로 유지보수 비용을 절감하는 지름길이다.

L2 생태계는 2024~2025년을 기점으로 **EIP-4844(Proto-Danksharding)** 도입으로 데이터 가용성 비용이 대폭 감소하면서 한 단계 더 성숙해질 것으로 전망된다. 지금이 L2 아키텍처를 깊이 이해하고 프로덕션 경험을 축적하기에 최적의 시기다.
