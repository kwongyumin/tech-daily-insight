# Redis를 활용한 분산 캐싱 전략과 패턴

## 개요

마이크로서비스 아키텍처가 보편화되면서 분산 환경에서의 캐싱 전략은 선택이 아닌 필수가 되었다. 단일 서버 인메모리 캐시는 서버 재시작 시 데이터가 소실되고, 다중 인스턴스 환경에서는 캐시 불일치(Cache Inconsistency) 문제가 발생한다. Redis는 이러한 문제를 해결하는 중앙화된 분산 캐시 솔루션으로, 단순한 키-값 저장소를 넘어 다양한 자료구조와 고급 기능을 제공한다.

이 글에서는 실무에서 자주 마주치는 캐싱 패턴과 그에 따른 트레이드오프를 Redis와 Spring Boot 기반 예제로 구체적으로 살펴본다.

---

## 핵심 개념

### 캐싱 전략의 분류

캐싱 전략은 크게 **읽기 전략**과 **쓰기 전략**으로 나뉜다.

**읽기 전략**
- **Cache-Aside (Lazy Loading)**: 캐시 미스 시 애플리케이션이 DB에서 조회 후 캐시에 적재
- **Read-Through**: 캐시가 DB 조회를 대리하여 처리 (캐시 레이어 추상화)

**쓰기 전략**
- **Write-Through**: 캐시와 DB에 동시 쓰기 (강한 일관성, 쓰기 지연 발생)
- **Write-Behind (Write-Back)**: 캐시에 먼저 쓰고 비동기로 DB에 반영 (높은 성능, 데이터 유실 위험)
- **Write-Around**: 캐시를 우회하고 DB에 직접 쓰기 (읽기 빈도 낮은 데이터에 적합)

### TTL과 캐시 무효화

캐시의 핵심 난제는 **"캐시 무효화(Cache Invalidation)"**다. Phil Karlton의 유명한 말처럼, 컴퓨터 과학에서 가장 어려운 두 가지 문제 중 하나다. TTL 기반 만료와 이벤트 기반 명시적 무효화를 상황에 맞게 조합해야 한다.

## 실전 예제

### 1. Cache-Aside 패턴 구현

가장 널리 쓰이는 패턴이다. 애플리케이션이 캐시 적중/미스를 직접 제어한다.

```java
@Service
@RequiredArgsConstructor
public class ProductService {

    private final ProductRepository productRepository;
    private final RedisTemplate<String, Object> redisTemplate;
    
    private static final String CACHE_KEY_PREFIX = "product:";
    private static final Duration TTL = Duration.ofMinutes(30);

    public ProductDto getProduct(Long productId) {
        String cacheKey = CACHE_KEY_PREFIX + productId;
        
        // 1. 캐시 조회
        ProductDto cached = (ProductDto) redisTemplate.opsForValue().get(cacheKey);
        if (cached != null) {
            return cached;
        }
        
        // 2. Cache Miss → DB 조회
        Product product = productRepository.findById(productId)
            .orElseThrow(() -> new EntityNotFoundException("Product not found: " + productId));
        
        ProductDto dto = ProductDto.from(product);
        
        // 3. 캐시 적재
        redisTemplate.opsForValue().set(cacheKey, dto, TTL);
        
        return dto;
    }

    public void updateProduct(Long productId, ProductUpdateRequest request) {
        productRepository.updateProduct(productId, request);
        
        // 캐시 무효화
        String cacheKey = CACHE_KEY_PREFIX + productId;
        redisTemplate.delete(cacheKey);
    }
}
```

### 2. Spring Cache 추상화 활용

Spring의 `@Cacheable`, `@CacheEvict` 어노테이션을 활용하면 캐싱 로직을 비즈니스 코드와 분리할 수 있다.

```java
// CacheConfig.java
@Configuration
@EnableCaching
public class CacheConfig {

    @Bean
    public RedisCacheManager cacheManager(RedisConnectionFactory connectionFactory) {
        RedisCacheConfiguration defaultConfig = RedisCacheConfiguration.defaultCacheConfig()
            .entryTtl(Duration.ofMinutes(10))
            .serializeKeysWith(
                RedisSerializationContext.SerializationPair.fromSerializer(new StringRedisSerializer()))
            .serializeValuesWith(
                RedisSerializationContext.SerializationPair.fromSerializer(
                    new GenericJackson2JsonRedisSerializer()))
            .disableCachingNullValues();

        Map<String, RedisCacheConfiguration> cacheConfigurations = Map.of(
            "products", defaultConfig.entryTtl(Duration.ofMinutes(30)),
            "userSessions", defaultConfig.entryTtl(Duration.ofHours(2)),
            "rankings", defaultConfig.entryTtl(Duration.ofMinutes(1))
        );

        return RedisCacheManager.builder(connectionFactory)
            .cacheDefaults(defaultConfig)
            .withInitialCacheConfigurations(cacheConfigurations)
            .build();
    }
}
```

```java
// ProductService.java
@Service
@RequiredArgsConstructor
public class ProductService {

    private final ProductRepository productRepository;

    @Cacheable(value = "products", key = "#productId", unless = "#result == null")
    public ProductDto getProduct(Long productId) {
        return productRepository.findById(productId)
            .map(ProductDto::from)
            .orElse(null);
    }

    @CachePut(value = "products", key = "#productId")
    public ProductDto updateProduct(Long productId, ProductUpdateRequest request) {
        Product updated = productRepository.updateProduct(productId, request);
        return ProductDto.from(updated);
    }

    @CacheEvict(value = "products", key = "#productId")
    public void deleteProduct(Long productId) {
        productRepository.deleteById(productId);
    }
    
    // 카테고리 단위 전체 무효화
    @CacheEvict(value = "products", allEntries = true)
    public void refreshAllProducts() {
        // 캐시 전체 초기화
    }
}
```

### 3. Cache Stampede 방지: Mutex Lock 패턴

캐시 만료 시 다수의 요청이 동시에 DB를 조회하는 **Cache Stampede** 문제를 Redis 분산 락으로 해결한다.

```java
@Service
@RequiredArgsConstructor
public class ResilientCacheService {

    private final RedisTemplate<String, Object> redisTemplate;
    private final ProductRepository productRepository;
    
    private static final String LOCK_PREFIX = "lock:product:";
    private static final long LOCK_TIMEOUT_MS = 3000;

    public ProductDto getProductWithLock(Long productId) {
        String cacheKey = "product:" + productId;
        String lockKey = LOCK_PREFIX + productId;

        // 1차 캐시 조회
        ProductDto cached = (ProductDto) redisTemplate.opsForValue().get(cacheKey);
        if (cached != null) return cached;

        // 분산 락 획득 시도
        Boolean acquired = redisTemplate.opsForValue()
            .setIfAbsent(lockKey, "LOCKED", Duration.ofMillis(LOCK_TIMEOUT_MS));

        if (Boolean.TRUE.equals(acquired)) {
            try {
                // 락 획득 후 재조회 (다른 스레드가 이미 캐시를 채웠을 수 있음)
                cached = (ProductDto) redisTemplate.opsForValue().get(cacheKey);
                if (cached != null) return cached;

                // DB 조회 및 캐시 적재
                Product product = productRepository.findById(productId)
                    .orElseThrow(() -> new EntityNotFoundException("Not found: " + productId));
                ProductDto dto = ProductDto.from(product);
                redisTemplate.opsForValue().set(cacheKey, dto, Duration.ofMinutes(30));
                return dto;
            } finally {
                redisTemplate.delete(lockKey);
            }
        } else {
            // 락 획득 실패 시 짧게 대기 후 재귀 호출 또는 DB 직접 조회
            try {
                Thread.sleep(100);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
            return getProductWithLock(productId);
        }
    }
}
```

### 4. 계층적 캐싱 (Local + Redis)

로컬 캐시(Caffeine)와 Redis를 조합한 **2-Level Cache** 전략으로 네트워크 오버헤드를 최소화한다.

```java
@Service
@RequiredArgsConstructor
public class MultiLevelCacheService {

    private final RedisTemplate<String, Object> redisTemplate;
    private final ProductRepository productRepository;

    // Caffeine 로컬 캐시 (L1)
    private final Cache<Long, ProductDto> localCache = Caffeine.newBuilder()
        .maximumSize(1_000)
        .expireAfterWrite(Duration.ofMinutes(5))
        .build();

    public ProductDto getProduct(Long productId) {
        // L1: 로컬 캐시 조회
        ProductDto local = localCache.getIfPresent(productId);
        if (local != null) return local;

        // L2: Redis 캐시 조회
        String redisKey = "product:" + productId;
        ProductDto redis = (ProductDto) redisTemplate.opsForValue().get(redisKey);
        if (redis != null) {
            localCache.put(productId, redis); // L1에 백필
            return redis;
        }

        // L3: DB 조회
        Product product = productRepository.findById(productId)
            .orElseThrow(() -> new EntityNotFoundException("Not found: " + productId));
        ProductDto dto = ProductDto.from(product);

        // 양쪽 캐시에 적재
        redisTemplate.opsForValue().set(redisKey, dto, Duration.ofMinutes(30));
        localCache.put(productId, dto);

        return dto;
    }
}
```

## 주의사항 및 트레이드오프

### Cache Penetration (캐시 침투)
존재하지 않는 키에 대한 반복 요청이 DB로 쏟아지는 문제다. **Null 캐싱** 또는 **Bloom Filter**로 방어한다.

```java
// Null 캐싱 예시
public ProductDto getProduct(Long productId) {
    String cacheKey = "product:" + productId;
    Object cached = redisTemplate.opsForValue().get(cacheKey);
    
    if (cached != null) {
        // NULL_VALUE는 존재하지 않는 데이터를 나타내는 sentinel 값
        return "NULL_VALUE".equals(cached) ? null : (ProductDto) cached;
    }
    
    Optional<Product> product = productRepository.findById(productId);
    if (product.isEmpty()) {
        // 짧은 TTL로 null 캐싱
        redisTemplate.opsForValue().set(cacheKey, "NULL_VALUE", Duration.ofMinutes(5));
        return null;
    }
    
    ProductDto dto = ProductDto.from(product.get());
    redisTemplate.opsForValue().set(cacheKey, dto, Duration.ofMinutes(30));
    return dto;
}
```

### Hot Key 문제
특정 키에 트래픽이 집중되면 Redis 단일 노드에 부하가 몰린다. **Key Sharding** 또는 **로컬 캐시 보조** 전략을 적용한다.

```java
// Hot Key Sharding: 키를 샤딩하여 여러 슬롯에 분산
private String getShardedKey(String baseKey, int shardCount) {
    int shard = ThreadLocalRandom.current().nextInt(shardCount);
    return baseKey + ":shard:" + shard;
}
```

### 직렬화 전략 선택

| 방식 | 장점 | 단점 |
|---|---|---|
| JDK Serialization | 구현 간단 | 성능 낮음, 클래스 의존적 |
| JSON (Jackson) | 가독성, 호환성 | 타입 정보 손실 가능 |
| Kryo | 고성능 | 설정 복잡 |
| Protobuf | 매우 빠름, 스키마 강제 | 학습 비용 |

실무에서는 대부분 **GenericJackson2JsonRedisSerializer** 또는 **Jackson2JsonRedisSerializer**를 사용하되, 클래스 타입 정보를 JSON에 포함시켜 역직렬화 오류를 방지한다.

### 메모리 정책 (eviction-policy) 설정

Redis의 메모리가 가득 찼을 때 동작을 결정하는 정책은 반드시 명시적으로 설정해야 한다.

```
# redis.conf
maxmemory 4gb
maxmemory-policy allkeys-lru   # 캐시 용도: allkeys-lru 권장
                                # 세션 저장소: volatile-lru 고려
```

## 정리

Redis 분산 캐싱은 단순히 `@Cacheable`을 붙이는 것으로 끝나지 않는다. 실무에서는 다음 체크리스트를 반드시 점검해야 한다.

1. **패턴 선택**: 데이터 특성(읽기/쓰기 비율, 일관성 요구 수준)에 따라 Cache-Aside, Write-Through 등 적합한 패턴을 선택한다.
2. **TTL 설계**: 데이터 변경 주기와 허용 가능한 staleness를 기반으로 TTL을 결정한다. "무한 TTL"은 위험하다.
3. **장애 대응**: Redis 장애 시 서비스 전체가 중단되지 않도록 Circuit Breaker 패턴과 fallback 전략을 준비한다.
4. **직렬화 일관성**: 배포 시 클래스 변경으로 인한 역직렬화 오류를 방지하기 위해 버전 전략을 수립한다.
5. **모니터링**: Redis의 `cache hit ratio`, `eviction count`, `memory usage`를 Prometheus + Grafana로 지속적으로 모니터링한다.

캐싱은 성능 최적화의 강력한 도구이지만, 잘못 설계된 캐시는 데이터 불일치, 메모리 낭비, 장애 전파의 원인이 된다. 트레이드오프를 명확히 이해하고, 시스템의 요구사항에 맞는 전략을 선택하는 것이 핵심이다.
