# 사용자 영향 없이 레거시 결제 시스템을 전면 재작성하기

## 개요

결제 시스템은 서비스에서 가장 민감한 도메인 중 하나다. 돈이 오가는 로직에 버그가 생기면 단순한 UX 불편을 넘어 실제 금전적 손해로 이어진다. 그런데도 많은 팀이 수년간 누적된 레거시 결제 코드를 그대로 운영하고 있다. "건드리면 터진다"는 공포가 개선을 막는다.

하지만 언젠가는 반드시 손대야 할 시점이 온다. PG사 API 버전 단절, 새로운 결제 수단 추가, 모놀리스 분리 등 외부 압력이 쌓이면 더 이상 미룰 수 없다. 이 글에서는 **사용자에게 단 한 건의 결제 오류도 발생시키지 않으면서 레거시 결제 시스템을 전면 재작성하는 전략**을 다룬다.

핵심은 "빅뱅 전환"을 피하고, 검증된 점진적 마이그레이션 패턴을 활용하는 것이다.

---

## 핵심 개념

### 1. Strangler Fig Pattern

마틴 파울러가 소개한 이 패턴은 레거시 시스템을 한 번에 교체하지 않고, 새 시스템이 기존 시스템을 점진적으로 "감싸며" 대체하는 방식이다. 열대우림의 교살 무화과나무가 숙주 나무를 천천히 대체하는 것에서 이름을 따왔다.

결제 도메인에 적용하면 다음과 같은 흐름이 된다:

```
[클라이언트] → [결제 파사드/라우터] → [레거시 시스템] (초기)
                                      ↘ [신규 시스템] (점진적 확대)
```

트래픽 분기 비율을 조절하면서 신규 시스템의 안정성을 검증하고, 최종적으로 레거시를 완전히 제거한다.

### 2. Parallel Run (Shadow Mode)

신규 시스템을 실제 프로덕션 트래픽에 연결하되, **결과는 레거시 시스템의 결과를 사용하고** 신규 시스템의 결과는 비교·로깅만 하는 방식이다. 사용자는 전혀 영향을 받지 않으면서 신규 시스템의 정확성을 오랜 기간 검증할 수 있다.

### 3. Feature Flag를 통한 점진적 롤아웃

사용자 ID, 결제 수단, 금액 범위 등 다양한 기준으로 신규 시스템 적용 대상을 세밀하게 제어한다. 문제가 발생하면 즉시 플래그를 꺼서 레거시로 롤백할 수 있어야 한다.

## 실전 예제

### Step 1: 결제 파사드 도입

가장 먼저 레거시 코드를 직접 호출하는 모든 지점에 파사드 레이어를 추가한다. 이 레이어가 이후 모든 라우팅과 비교 로직을 담당한다.

```java
@Service
@RequiredArgsConstructor
public class PaymentFacade {

    private final LegacyPaymentService legacyPaymentService;
    private final NewPaymentService newPaymentService;
    private final PaymentRouter paymentRouter;
    private final PaymentResultComparator comparator;

    public PaymentResult processPayment(PaymentRequest request) {
        PaymentRoute route = paymentRouter.resolve(request);

        return switch (route) {
            case LEGACY -> legacyPaymentService.process(request);
            case NEW -> newPaymentService.process(request);
            case SHADOW -> processShadowMode(request);
        };
    }

    private PaymentResult processShadowMode(PaymentRequest request) {
        // 레거시 결과가 실제 사용자에게 반환됨
        PaymentResult legacyResult = legacyPaymentService.process(request);

        // 신규 시스템은 비동기로 실행, 결과 비교만
        CompletableFuture.runAsync(() -> {
            try {
                PaymentResult newResult = newPaymentService.process(request);
                comparator.compare(request, legacyResult, newResult);
            } catch (Exception e) {
                log.error("Shadow mode error for requestId={}", request.getId(), e);
            }
        });

        return legacyResult;
    }
}
```

### Step 2: 라우터 구현

Feature Flag와 사용자 세그먼트 기반으로 라우팅을 결정한다.

```java
@Component
@RequiredArgsConstructor
public class PaymentRouter {

    private final FeatureFlagService featureFlagService;

    public PaymentRoute resolve(PaymentRequest request) {
        String userId = request.getUserId();
        String paymentMethod = request.getPaymentMethod();

        // 1단계: 특정 결제 수단만 Shadow 적용
        if (featureFlagService.isEnabled("payment.shadow.card", userId)) {
            if ("CARD".equals(paymentMethod)) {
                return PaymentRoute.SHADOW;
            }
        }

        // 2단계: 카나리 롤아웃 (5% 사용자에게 신규 시스템 직접 적용)
        if (featureFlagService.isEnabledForPercentage("payment.new.rollout", userId, 5)) {
            return PaymentRoute.NEW;
        }

        return PaymentRoute.LEGACY;
    }
}
```

### Step 3: 결과 비교기 구현

Shadow Mode에서 두 시스템의 결과 차이를 감지하고 알림을 발송한다. 이 데이터가 신규 시스템 검증의 핵심 근거가 된다.

```java
@Component
@RequiredArgsConstructor
public class PaymentResultComparator {

    private final MismatchRepository mismatchRepository;
    private final AlertService alertService;

    public void compare(PaymentRequest request,
                        PaymentResult legacyResult,
                        PaymentResult newResult) {

        List<String> diffs = new ArrayList<>();

        if (!Objects.equals(legacyResult.getStatus(), newResult.getStatus())) {
            diffs.add(String.format("status: legacy=%s, new=%s",
                legacyResult.getStatus(), newResult.getStatus()));
        }

        if (!amountEquals(legacyResult.getAmount(), newResult.getAmount())) {
            diffs.add(String.format("amount: legacy=%s, new=%s",
                legacyResult.getAmount(), newResult.getAmount()));
        }

        if (!diffs.isEmpty()) {
            MismatchRecord record = MismatchRecord.builder()
                .requestId(request.getId())
                .userId(request.getUserId())
                .diffs(diffs)
                .detectedAt(Instant.now())
                .build();

            mismatchRepository.save(record);

            // 불일치율이 임계치를 초과하면 알림
            if (mismatchRepository.recentMismatchRate() > 0.01) {
                alertService.sendAlert("결제 시스템 불일치율 임계치 초과", record);
            }
        }
    }

    private boolean amountEquals(BigDecimal a, BigDecimal b) {
        if (a == null && b == null) return true;
        if (a == null || b == null) return false;
        return a.compareTo(b) == 0;
    }
}
```

### Step 4: 멱등성 보장

신규 시스템에서 Shadow Mode로 결제를 "실행"할 경우, PG사에 실제 과금이 되어서는 안 된다. 반드시 **Dry-Run 모드**를 지원하거나, 신규 시스템의 Shadow 실행 시에는 PG사 호출을 모의(Mock)해야 한다.

또한 실제 롤아웃 이후에는 네트워크 오류 등으로 인한 중복 결제를 막기 위해 멱등키를 필수로 적용해야 한다.

```java
@Service
@RequiredArgsConstructor
public class NewPaymentService {

    private final PgClient pgClient;
    private final IdempotencyKeyStore idempotencyKeyStore;

    public PaymentResult process(PaymentRequest request) {
        String idempotencyKey = generateKey(request);

        // 이미 처리된 요청이면 저장된 결과 반환
        return idempotencyKeyStore.get(idempotencyKey)
            .orElseGet(() -> {
                PaymentResult result = pgClient.charge(request);
                idempotencyKeyStore.save(idempotencyKey, result, Duration.ofHours(24));
                return result;
            });
    }

    private String generateKey(PaymentRequest request) {
        return String.format("%s:%s:%s",
            request.getUserId(),
            request.getOrderId(),
            request.getAmount());
    }
}
```

## 마이그레이션 단계별 체크리스트

전환 과정을 단계별로 명확히 나누면 팀 전체가 현재 위치를 공유할 수 있다.

| 단계 | 목표 | 완료 기준 |
|------|------|-----------|
| 0단계 | 파사드 도입 | 모든 결제 호출이 파사드를 경유 |
| 1단계 | Shadow Mode | 불일치율 0% 2주 이상 유지 |
| 2단계 | 카나리 (5%) | 에러율·지연 시간 레거시 대비 동일 수준 |
| 3단계 | 점진적 확대 (20% → 50% → 100%) | 각 단계별 24~72시간 모니터링 |
| 4단계 | 레거시 제거 | 신규 시스템 단독 운영 1개월 후 |

## 주의사항 및 트레이드오프

### 데이터 이중화 문제

Shadow Mode 기간 동안 레거시와 신규 시스템이 각각 별도의 DB에 데이터를 쌓을 경우, 결제 이력 조회나 정산 처리가 복잡해진다. 초기에는 신규 시스템도 레거시 DB를 공유하거나, 명확한 소유권 분리 전략을 사전에 수립해야 한다.

### Shadow Mode의 비용

신규 시스템을 비동기로 실행하더라도 PG사 연동 테스트 환경을 항상 가동해야 하고, 불일치 로그 저장 비용이 추가된다. 또한 Shadow Mode 실행 중 비동기 작업이 메인 스레드보다 느릴 경우 스레드 풀 고갈로 이어질 수 있으니 반드시 별도 스레드 풀을 격리해야 한다.

```java
// Shadow 전용 스레드 풀 격리
@Bean("shadowExecutor")
public Executor shadowExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(5);
    executor.setMaxPoolSize(10);
    executor.setQueueCapacity(100);
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.DiscardPolicy());
    executor.setThreadNamePrefix("shadow-payment-");
    executor.initialize();
    return executor;
}
```

### 롤백 계획은 항상 먼저 준비하라

Feature Flag 시스템이 없다면 이 접근 방법 자체가 의미 없다. 플래그를 1분 내에 꺼서 레거시로 완전히 되돌릴 수 있어야 한다. 배포 없이 런타임 설정만으로 제어 가능한 구조가 필수다.

### 테스트 커버리지 확보가 선행 조건

파사드를 도입하기 전에 레거시 시스템의 주요 결제 플로우에 대한 E2E 테스트를 먼저 작성해야 한다. 이 테스트가 신규 시스템 검증의 안전망이 된다. 테스트 없이 시작하면 불일치가 발생했을 때 어느 쪽이 올바른지 판단할 기준이 없다.

### 운영팀과 CS팀 사이드카

마이그레이션 기간 중에는 동일한 결제 건에 대해 두 시스템에서 로그를 조회해야 하는 상황이 생긴다. 운영/CS 담당자가 혼란을 겪지 않도록 통합 조회 화면이나 운영 가이드를 함께 준비해야 한다.

## 정리

레거시 결제 시스템 재작성은 기술적 도전만큼이나 **운영적, 조직적 도전**이다. 성공의 핵심은 다음 세 가지로 요약할 수 있다.

1. **절대 빅뱅 전환하지 않는다.** 파사드와 라우터를 먼저 도입하고, Shadow Mode로 충분히 검증한 뒤에 실제 트래픽을 넘긴다.

2. **관찰 가능성을 먼저 구축한다.** 불일치 감지, 에러율 대시보드, 알림 체계가 없으면 문제가 생겨도 모른다.

3. **롤백이 배포보다 쉬워야 한다.** Feature Flag 시스템은 선택이 아니라 필수다.

"코드를 고치는 것"보다 "사용자가 느끼지 못하게 고치는 것"이 훨씬 어렵다. 하지만 위 패턴들을 체계적으로 적용하면, 가장 민감한 결제 도메인도 안전하게 현대화할 수 있다.
