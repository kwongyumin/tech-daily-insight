# 대출·금융 상품 시스템의 상태 머신 설계

## 개요

금융 시스템에서 대출 상품의 생애주기는 복잡하다. 신청서 접수부터 심사, 약정, 실행, 상환, 연체, 상각, 조기상환에 이르기까지 수십 개의 상태와 전이가 얽혀 있다. 이를 잘못 설계하면 특정 상태에서만 허용되어야 하는 연산이 다른 상태에서 실행되거나, 상태 전이 과정에서 데이터 정합성이 깨지는 심각한 결함이 발생한다.

"상태값을 컬럼 하나로 관리하면 되지 않나?"라는 단순한 접근은 초기에는 빠르게 동작하지만, 비즈니스 규칙이 늘어나고 예외 케이스가 추가될수록 if/switch 분기가 폭발적으로 증가하고 결국 유지보수 불가능한 코드를 낳는다.

이 글에서는 대출·금융 상품 도메인에서 상태 머신(State Machine)을 설계하고 Spring 기반으로 구현하는 실전 방법을 다룬다. 상태 머신 라이브러리 선택, 퍼시스턴스 전략, 동시성 제어, 감사 로그 설계까지 실무에서 마주치는 핵심 문제를 함께 살펴본다.

---

## 핵심 개념

### 상태 머신이 필요한 이유

상태 머신의 핵심 가치는 **허용된 전이만 실행을 보장**하는 것이다. 대출 도메인을 예로 들면:

- `APPLIED(신청)` → `UNDER_REVIEW(심사중)` → `APPROVED(승인)` → `CONTRACTED(약정)` → `DISBURSED(실행)` → `REPAYING(상환중)` → `CLOSED(종결)`
- `UNDER_REVIEW` → `REJECTED(거절)`
- `REPAYING` → `OVERDUE(연체)` → `WRITTEN_OFF(상각)`
- `REPAYING` → `EARLY_REPAID(조기상환완료)`

이 흐름을 단순 Enum과 if-else로 처리하면, 코드 어딘가에서 `CLOSED` 상태의 대출에 상환 처리가 가능해지는 버그가 생긴다. 상태 머신은 이를 선언적으로 막아준다.

### 유한 상태 머신의 구성 요소

| 구성 요소 | 설명 | 예시 |
|---|---|---|
| State | 시스템이 존재할 수 있는 상태 | `APPLIED`, `APPROVED` |
| Event | 상태 전이를 유발하는 사건 | `SUBMIT_REVIEW`, `APPROVE` |
| Transition | 특정 상태에서 이벤트 발생 시 다음 상태 | `APPLIED + SUBMIT_REVIEW → UNDER_REVIEW` |
| Guard | 전이 조건 (선택적) | 심사 서류 완비 여부 |
| Action | 전이 시 실행되는 부수 효과 | 알림 발송, 이력 기록 |

## 실전 예제

### 상태와 이벤트 정의

```java
public enum LoanState {
    APPLIED,
    UNDER_REVIEW,
    APPROVED,
    REJECTED,
    CONTRACTED,
    DISBURSED,
    REPAYING,
    OVERDUE,
    WRITTEN_OFF,
    EARLY_REPAID,
    CLOSED
}

public enum LoanEvent {
    SUBMIT_FOR_REVIEW,
    APPROVE,
    REJECT,
    SIGN_CONTRACT,
    DISBURSE,
    START_REPAYMENT,
    MARK_OVERDUE,
    WRITE_OFF,
    EARLY_REPAY,
    CLOSE
}
```

### Spring State Machine 설정

Spring State Machine을 사용하면 상태 전이 규칙을 선언적으로 정의할 수 있다.

```java
@Configuration
@EnableStateMachineFactory
public class LoanStateMachineConfig
        extends StateMachineConfigurerAdapter<LoanState, LoanEvent> {

    @Override
    public void configure(StateMachineStateConfigurer<LoanState, LoanEvent> states)
            throws Exception {
        states
            .withStates()
            .initial(LoanState.APPLIED)
            .end(LoanState.CLOSED)
            .end(LoanState.REJECTED)
            .end(LoanState.WRITTEN_OFF)
            .end(LoanState.EARLY_REPAID)
            .states(EnumSet.allOf(LoanState.class));
    }

    @Override
    public void configure(StateMachineTransitionConfigurer<LoanState, LoanEvent> transitions)
            throws Exception {
        transitions
            .withExternal()
                .source(LoanState.APPLIED).target(LoanState.UNDER_REVIEW)
                .event(LoanEvent.SUBMIT_FOR_REVIEW)
                .guard(documentCompleteGuard())
                .action(notifyReviewTeamAction())
                .and()
            .withExternal()
                .source(LoanState.UNDER_REVIEW).target(LoanState.APPROVED)
                .event(LoanEvent.APPROVE)
                .and()
            .withExternal()
                .source(LoanState.UNDER_REVIEW).target(LoanState.REJECTED)
                .event(LoanEvent.REJECT)
                .action(sendRejectionNoticeAction())
                .and()
            .withExternal()
                .source(LoanState.APPROVED).target(LoanState.CONTRACTED)
                .event(LoanEvent.SIGN_CONTRACT)
                .and()
            .withExternal()
                .source(LoanState.CONTRACTED).target(LoanState.DISBURSED)
                .event(LoanEvent.DISBURSE)
                .and()
            .withExternal()
                .source(LoanState.DISBURSED).target(LoanState.REPAYING)
                .event(LoanEvent.START_REPAYMENT)
                .and()
            .withExternal()
                .source(LoanState.REPAYING).target(LoanState.OVERDUE)
                .event(LoanEvent.MARK_OVERDUE)
                .and()
            .withExternal()
                .source(LoanState.OVERDUE).target(LoanState.WRITTEN_OFF)
                .event(LoanEvent.WRITE_OFF)
                .and()
            .withExternal()
                .source(LoanState.REPAYING).target(LoanState.EARLY_REPAID)
                .event(LoanEvent.EARLY_REPAY)
                .and()
            .withExternal()
                .source(LoanState.REPAYING).target(LoanState.CLOSED)
                .event(LoanEvent.CLOSE);
    }

    @Bean
    public Guard<LoanState, LoanEvent> documentCompleteGuard() {
        return context -> {
            Long loanId = context.getExtendedState()
                .get("loanId", Long.class);
            // 서류 완비 여부 검증 로직
            return documentService.isComplete(loanId);
        };
    }

    @Bean
    public Action<LoanState, LoanEvent> notifyReviewTeamAction() {
        return context -> {
            Long loanId = context.getExtendedState()
                .get("loanId", Long.class);
            notificationService.notifyReviewTeam(loanId);
        };
    }
}
```

### 상태 이력 퍼시스턴스

상태 머신을 메모리에만 두면 서버 재기동 시 상태를 잃는다. 모든 상태 전이는 DB에 영속화해야 하며, 감사 목적의 이력 테이블도 필수다.

```sql
-- 대출 현재 상태 테이블
CREATE TABLE loan (
    id          BIGINT PRIMARY KEY,
    state       VARCHAR(30) NOT NULL,
    version     BIGINT NOT NULL DEFAULT 0,  -- 낙관적 락용
    updated_at  TIMESTAMP NOT NULL,
    updated_by  VARCHAR(100) NOT NULL
);

-- 상태 전이 이력 테이블
CREATE TABLE loan_state_history (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    loan_id         BIGINT NOT NULL,
    from_state      VARCHAR(30),
    to_state        VARCHAR(30) NOT NULL,
    event           VARCHAR(50) NOT NULL,
    triggered_by    VARCHAR(100) NOT NULL,
    triggered_at    TIMESTAMP NOT NULL,
    reason          TEXT,
    FOREIGN KEY (loan_id) REFERENCES loan(id)
);
```

```java
@Service
@Transactional
public class LoanStateMachineService {

    private final StateMachineFactory<LoanState, LoanEvent> factory;
    private final LoanRepository loanRepository;
    private final LoanStateHistoryRepository historyRepository;

    public void sendEvent(Long loanId, LoanEvent event, String triggeredBy) {
        Loan loan = loanRepository.findByIdWithLock(loanId)
            .orElseThrow(() -> new EntityNotFoundException("Loan not found: " + loanId));

        StateMachine<LoanState, LoanEvent> sm = buildStateMachine(loan);

        LoanState previousState = sm.getState().getId();

        sm.getExtendedState().getVariables().put("loanId", loanId);
        boolean accepted = sm.sendEvent(event);

        if (!accepted) {
            throw new InvalidStateTransitionException(
                String.format("Cannot apply event %s to loan %d in state %s",
                    event, loanId, previousState));
        }

        LoanState newState = sm.getState().getId();

        // 현재 상태 업데이트 (낙관적 락으로 동시 수정 방지)
        loan.setState(newState);
        loan.setUpdatedBy(triggeredBy);
        loanRepository.save(loan);

        // 전이 이력 기록
        historyRepository.save(LoanStateHistory.builder()
            .loanId(loanId)
            .fromState(previousState)
            .toState(newState)
            .event(event)
            .triggeredBy(triggeredBy)
            .triggeredAt(LocalDateTime.now())
            .build());
    }

    private StateMachine<LoanState, LoanEvent> buildStateMachine(Loan loan) {
        StateMachine<LoanState, LoanEvent> sm = factory.getStateMachine(
            loan.getId().toString());
        sm.stop();
        sm.getStateMachineAccessor().doWithAllRegions(accessor ->
            accessor.resetStateMachine(
                new DefaultStateMachineContext<>(loan.getState(), null, null, null)));
        sm.start();
        return sm;
    }
}
```

## 주의사항 및 트레이드오프

### 1. 동시성 제어는 필수

같은 대출에 대해 두 개의 요청이 동시에 상태를 변경하려 할 때, 마지막 쓰기가 이전 쓰기를 덮어쓰는 Lost Update 문제가 발생한다. 위 예제처럼 **낙관적 락(Optimistic Lock)** 또는 DB 수준의 **비관적 락(SELECT FOR UPDATE)**을 반드시 적용해야 한다.

```java
// JPA 낙관적 락 적용
@Entity
public class Loan {
    @Version
    private Long version;
    // ...
}

// 비관적 락 쿼리 예시
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT l FROM Loan l WHERE l.id = :id")
Optional<Loan> findByIdWithLock(@Param("id") Long id);
```

금융 도메인에서는 일반적으로 **비관적 락**이 안전하다. 낙관적 락은 재시도 로직이 필요하고, 충돌이 잦은 환경에서는 오히려 처리량이 낮아질 수 있다.

### 2. 상태 머신 인스턴스 관리 전략

Spring State Machine은 **인스턴스를 재사용할지, 매 요청마다 새로 생성할지** 선택해야 한다. 실무에서는 대출 수가 많으므로 StateMachine 인스턴스를 메모리에 상주시키는 것은 부적절하다. 요청마다 현재 상태를 DB에서 읽어 상태 머신을 복원(restore)하고, 이벤트를 처리한 뒤 버리는 **Stateless 복원 패턴**이 일반적이다.

단, 이 경우 매 요청마다 복원 비용이 발생하므로, 트랜잭션 안에서 처리하고 Spring State Machine의 `StateMachinePersist` 인터페이스를 활용하면 코드를 더 깔끔하게 관리할 수 있다.

### 3. Guard 실패와 예외 처리의 명확한 분리

Guard가 `false`를 반환하면 `sendEvent`는 조용히 `false`를 반환한다. 이를 별도의 예외로 변환하지 않으면 호출자가 실패 원인을 알 수 없다. **Guard 실패 사유를 ExtendedState에 기록**하거나, Guard 내부에서 비즈니스 예외를 던지는 방식으로 명확한 실패 원인을 제공해야 한다.

### 4. 외부 시스템 연동 Action의 멱등성

Action 내부에서 외부 API 호출이나 이벤트 발행이 일어난다면, **네트워크 오류로 인한 재시도 시 중복 실행**을 고려해야 한다. 이벤트 ID를 기반으로 멱등성 키를 설계하거나, Outbox Pattern을 통해 DB 트랜잭션과 메시지 발행을 원자적으로 묶어야 한다.

### 5. 상태 머신 라이브러리 선택 기준

| 기준 | Spring State Machine | 직접 구현 |
|---|---|---|
| 학습 비용 | 중간 (개념 + 설정) | 낮음 |
| 유연성 | 제한적 (프레임워크 제약) | 높음 |
| 서브 상태 머신 | 지원 | 직접 구현 필요 |
| 퍼시스턴스 | 별도 어댑터 필요 | 자유롭게 설계 |
| 유지보수 | 프레임워크 의존 | 팀 역량 의존 |

복잡도가 낮다면 **도메인 객체 내부에 상태 전이 메서드를 직접 구현**하는 방식이 오히려 명확하고 테스트하기 쉬울 수 있다. 상태와 전이가 복잡해지고 서브 상태, 병렬 상태 등이 필요한 경우에 라이브러리 도입을 고려하자.

## 정리

대출·금융 상품 시스템에서 상태 머신은 단순한 패턴 적용이 아니라, **비즈니스 규칙의 선언적 표현이자 안전장치**다. 핵심 설계 원칙을 정리하면 다음과 같다.

1. **허용된 전이만 실행되도록** 상태 머신이 강제하게 설계한다.
2. **모든 상태 전이는 DB에 영속화**하고, 감사 이력을 빠짐없이 기록한다.
3. **동시성 제어**는 비관적 락 또는 낙관적 락으로 반드시 처리한다.
4. **Action의 부수 효과는 멱등성을 보장**하거나 Outbox Pattern으로 분리한다.
5. 복잡도에 따라 **라이브러리 vs 직접 구현**을 트레이드오프하여 선택한다.

금융 도메인은 잘못된 상태 전이 하나가 실제 손실로 이어질 수 있다. 상태 머신을 코드 수준에서 명확히 정의하고, 테스트로 모든 전이 경우의 수를 검증하는 것이 장기적으로 안정적인 시스템을 만드는 지름길이다.
