# 이더리움 계정 추상화 ERC-4337 이해하기

## 개요

이더리움을 사용하다 보면 반드시 마주치는 불편함이 있다. 트랜잭션을 보내려면 반드시 ETH가 있어야 하고, 개인 키를 잃어버리면 계정을 복구할 방법이 없으며, 모든 서명은 단일 키 쌍에 의존한다. 이런 근본적인 UX 문제를 해결하기 위해 등장한 것이 **계정 추상화(Account Abstraction)** 개념이다.

ERC-4337은 2021년 Vitalik Buterin을 포함한 여러 이더리움 개발자들이 제안한 표준으로, **이더리움 프로토콜 레벨의 변경 없이** 스마트 컨트랙트 기반 계정을 EOA(Externally Owned Account)처럼 동작하게 만드는 방법을 정의한다. 2023년 3월 메인넷에 배포된 이후 지갑 인프라의 패러다임 전환을 이끌고 있다.

이 글에서는 ERC-4337의 핵심 아키텍처를 이해하고, 실제 구현 예제를 통해 어떻게 활용할 수 있는지 살펴본다.

## 핵심 개념

### EOA vs Smart Contract Account

기존 이더리움 계정은 두 가지 유형이 존재한다.

| 구분 | EOA | Smart Contract Account |
|------|-----|----------------------|
| 트랜잭션 시작 | 가능 | 불가능 (ERC-4337 이전) |
| 로직 커스터마이징 | 불가능 | 가능 |
| 키 복구 | 불가능 | 가능 |
| 가스 지불 | ETH 필수 | 대납 가능 |

ERC-4337은 Smart Contract Account가 트랜잭션을 시작할 수 있도록 **별도의 멤풀(Alternative Mempool)** 과 새로운 객체 `UserOperation`을 도입한다.

### 핵심 컴포넌트

**1. UserOperation**

기존 트랜잭션을 대체하는 새로운 데이터 구조다. 사용자는 이 객체에 원하는 작업을 담아 번들러에게 전달한다.

```solidity
struct UserOperation {
    address sender;           // Smart Account 주소
    uint256 nonce;            // 리플레이 방지
    bytes initCode;           // 최초 배포 시 사용
    bytes callData;           // 실행할 함수 데이터
    uint256 callGasLimit;
    uint256 verificationGasLimit;
    uint256 preVerificationGas;
    uint256 maxFeePerGas;
    uint256 maxPriorityFeePerGas;
    bytes paymasterAndData;   // Paymaster 정보 (가스 대납)
    bytes signature;          // 검증에 사용될 서명
}
```

**2. EntryPoint Contract**

ERC-4337의 핵심 싱글턴 컨트랙트다. 모든 UserOperation은 이 컨트랙트를 통해 실행된다. `handleOps()` 함수가 번들러로부터 배치 UserOperation을 받아 처리한다.

**3. Bundler**

UserOperation을 수집하고 배치로 묶어 EntryPoint의 `handleOps()`를 호출하는 특수 노드다. 기존 마이너/검증자와 유사한 역할을 한다.

**4. Smart Account (Wallet Contract)**

사용자의 실제 계정 컨트랙트다. `IAccount` 인터페이스를 구현해야 하며, 가장 중요한 함수는 `validateUserOp()`이다.

**5. Paymaster**

가스비를 대신 지불해주는 컨트랙트다. ERC-20 토큰으로 가스 지불을 허용하거나, 특정 dApp이 사용자 가스를 스폰서하는 방식으로 활용된다.

### 실행 플로우

```
User → UserOperation 생성
     → Bundler에 전송 (별도 RPC: eth_sendUserOperation)
     → Bundler가 시뮬레이션으로 유효성 검증
     → 여러 UserOperation을 배치로 묶음
     → EntryPoint.handleOps() 호출 (온체인 트랜잭션)
     → EntryPoint가 각 Smart Account의 validateUserOp() 호출
     → 검증 성공 시 callData 실행
     → Paymaster가 있다면 가스 정산
```

## 실전 예제

### 1. 간단한 Smart Account 구현 (Solidity)

`IAccount` 인터페이스를 구현하는 최소한의 스마트 계정을 작성해보자.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.19;

import "@account-abstraction/contracts/interfaces/IAccount.sol";
import "@account-abstraction/contracts/interfaces/IEntryPoint.sol";
import "@openzeppelin/contracts/utils/cryptography/ECDSA.sol";

contract SimpleSmartAccount is IAccount {
    using ECDSA for bytes32;

    IEntryPoint public immutable entryPoint;
    address public owner;

    uint256 private constant SIG_VALIDATION_FAILED = 1;
    uint256 private constant SIG_VALIDATION_SUCCESS = 0;

    constructor(IEntryPoint _entryPoint, address _owner) {
        entryPoint = _entryPoint;
        owner = _owner;
    }

    modifier onlyEntryPoint() {
        require(msg.sender == address(entryPoint), "only entrypoint");
        _;
    }

    /// @inheritdoc IAccount
    function validateUserOp(
        UserOperation calldata userOp,
        bytes32 userOpHash,
        uint256 missingAccountFunds
    ) external override onlyEntryPoint returns (uint256 validationData) {
        // 서명 검증
        bytes32 hash = userOpHash.toEthSignedMessageHash();
        address recovered = hash.recover(userOp.signature);

        if (recovered != owner) {
            return SIG_VALIDATION_FAILED;
        }

        // EntryPoint에 부족한 가스비 선납
        if (missingAccountFunds > 0) {
            (bool success,) = payable(address(entryPoint)).call{
                value: missingAccountFunds
            }("");
            require(success, "prefund failed");
        }

        return SIG_VALIDATION_SUCCESS;
    }

    /// 실제 호출 실행 함수
    function execute(
        address dest,
        uint256 value,
        bytes calldata func
    ) external onlyEntryPoint {
        (bool success, bytes memory result) = dest.call{value: value}(func);
        if (!success) {
            assembly {
                revert(add(result, 32), mload(result))
            }
        }
    }

    /// 멀티콜 지원
    function executeBatch(
        address[] calldata dest,
        bytes[] calldata func
    ) external onlyEntryPoint {
        require(dest.length == func.length, "length mismatch");
        for (uint256 i = 0; i < dest.length; i++) {
            (bool success,) = dest[i].call(func[i]);
            require(success, "batch call failed");
        }
    }

    receive() external payable {}
}
```

### 2. UserOperation 생성 및 서명 (TypeScript + ethers.js)

백엔드 서비스에서 UserOperation을 구성하고 번들러에 전달하는 예제다.

```typescript
import { ethers } from "ethers";
import { UserOperationBuilder } from "userop";

const ENTRY_POINT_ADDRESS = "0x5FF137D4b0FDCD49DcA30c7CF57E578a026d2789";
const BUNDLER_RPC = "https://api.stackup.sh/v1/node/YOUR_API_KEY";

interface UserOperation {
  sender: string;
  nonce: string;
  initCode: string;
  callData: string;
  callGasLimit: string;
  verificationGasLimit: string;
  preVerificationGas: string;
  maxFeePerGas: string;
  maxPriorityFeePerGas: string;
  paymasterAndData: string;
  signature: string;
}

async function sendUserOperation(
  smartAccountAddress: string,
  targetAddress: string,
  callData: string,
  signerPrivateKey: string
): Promise<string> {
  const provider = new ethers.JsonRpcProvider(BUNDLER_RPC);
  const signer = new ethers.Wallet(signerPrivateKey);

  // EntryPoint ABI (필요 함수만 포함)
  const entryPointAbi = [
    "function getNonce(address sender, uint192 key) view returns (uint256)",
  ];
  const entryPoint = new ethers.Contract(
    ENTRY_POINT_ADDRESS,
    entryPointAbi,
    provider
  );

  // 현재 nonce 조회
  const nonce = await entryPoint.getNonce(smartAccountAddress, 0);

  // Smart Account execute 함수 인코딩
  const accountAbi = [
    "function execute(address dest, uint256 value, bytes calldata func)",
  ];
  const accountInterface = new ethers.Interface(accountAbi);
  const executeCallData = accountInterface.encodeFunctionData("execute", [
    targetAddress,
    0n,
    callData,
  ]);

  // 기본 UserOperation 구성
  const userOp: UserOperation = {
    sender: smartAccountAddress,
    nonce: ethers.toBeHex(nonce),
    initCode: "0x",
    callData: executeCallData,
    callGasLimit: ethers.toBeHex(200000),
    verificationGasLimit: ethers.toBeHex(150000),
    preVerificationGas: ethers.toBeHex(50000),
    maxFeePerGas: ethers.toBeHex(ethers.parseUnits("10", "gwei")),
    maxPriorityFeePerGas: ethers.toBeHex(ethers.parseUnits("1", "gwei")),
    paymasterAndData: "0x",
    signature: "0x",
  };

  // UserOperation 해시 계산
  const chainId = (await provider.getNetwork()).chainId;
  const userOpHash = getUserOpHash(userOp, ENTRY_POINT_ADDRESS, chainId);

  // 서명 생성
  const signature = await signer.signMessage(ethers.getBytes(userOpHash));
  userOp.signature = signature;

  // 번들러에 전송
  const txHash = await provider.send("eth_sendUserOperation", [
    userOp,
    ENTRY_POINT_ADDRESS,
  ]);

  console.log("UserOperation submitted:", txHash);
  return txHash;
}

function getUserOpHash(
  userOp: UserOperation,
  entryPointAddress: string,
  chainId: bigint
): string {
  const packed = ethers.AbiCoder.defaultAbiCoder().encode(
    [
      "address", "uint256", "bytes32", "bytes32",
      "uint256", "uint256", "uint256",
      "uint256", "uint256", "bytes32",
    ],
    [
      userOp.sender,
      userOp.nonce,
      ethers.keccak256(userOp.initCode),
      ethers.keccak256(userOp.callData),
      userOp.callGasLimit,
      userOp.verificationGasLimit,
      userOp.preVerificationGas,
      userOp.maxFeePerGas,
      userOp.maxPriorityFeePerGas,
      ethers.keccak256(userOp.paymasterAndData),
    ]
  );

  const inner = ethers.keccak256(packed);
  return ethers.keccak256(
    ethers.AbiCoder.defaultAbiCoder().encode(
      ["bytes32", "address", "uint256"],
      [inner, entryPointAddress, chainId]
    )
  );
}
```

### 3. Paymaster를 활용한 가스리스 트랜잭션

Verifying Paymaster의 핵심 검증 로직 예시다.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.19;

import "@account-abstraction/contracts/core/BasePaymaster.sol";

contract SponsorPaymaster is BasePaymaster {
    mapping(address => bool) public sponsoredAccounts;
    address public paymasterSigner;

    constructor(
        IEntryPoint _entryPoint,
        address _signer
    ) BasePaymaster(_entryPoint) {
        paymasterSigner = _signer;
    }

    function _validatePaymasterUserOp(
        UserOperation calldata userOp,
        bytes32 userOpHash,
        uint256 maxCost
    ) internal override returns (bytes memory context, uint256 validationData) {
        // paymasterAndData에서 서명 추출 (첫 20바이트는 paymaster 주소)
        bytes calldata paymasterSignature = userOp.paymasterAndData[20:];

        // 오프체인 서명 검증으로 스폰서 여부 확인
        bytes32 hash = ECDSA.toEthSignedMessageHash(userOpHash);
        address recovered = ECDSA.recover(hash, paymasterSignature);

        require(recovered == paymasterSigner, "invalid paymaster signature");

        // 컨텍스트로 sender 전달 (postOp에서 활용)
        return (abi.encode(userOp.sender), 0);
    }

    function _postOp(
        PostOpMode mode,
        bytes calldata context,
        uint256 actualGasCost
    ) internal override {
        address sender = abi.decode(context, (address));
        // 가스비 사용 로깅, 쿼터 차감 등 후처리 로직
        emit GasSponsored(sender, actualGasCost);
    }

    event GasSponsored(address indexed account, uint256 gasCost);

    receive() external payable {}
}
```

## 주의사항 및 트레이드오프

### ⚠️ 가스 오버헤드

ERC-4337은 기존 트랜잭션 대비 **약 20~40% 가스 오버헤드**가 발생한다. EntryPoint 컨트랙트 호출, 검증 로직, 번들러 수수료가 추가되기 때문이다. 단순한 ETH 전송 같은 경우에는 EOA가 여전히 더 효율적이다.

### ⚠️ 번들러 중앙화 위험

현재 번들러 생태계는 Stackup, Pimlico, Alchemy 등 소수 업체에 의존하고 있다. 분산화된 번들러 네트워크가 성숙하기 전까지는 가용성 위험이 존재한다.

### ⚠️ 검증 로직의 제약

`validateUserOp()`은 스토리지 접근 및 외부 컨트랙트 호출에 엄격한 제한이 있다. 번들러는 시뮬레이션 단계에서 이 제약을 강제하며, 위반 시 UserOperation이 거부된다. 특히 오라클에 의존하는 검증 로직은 구현이 복잡해진다.

### ⚠️ 프론트런닝과 MEV

번들러가 UserOperation을 배치로 묶는 과정에서 MEV 추출 가능성이 생긴다. 번들러가 유리한 순서로 오퍼레이션을 재정렬할 수 있으므로, 민감한 DeFi 트랜잭션에서는 주의가 필요하다.

### ⚠️ 스마트 컨트랙트 취약점 책임

Smart Account는 코드이므로 버그가 있으면 자산을 잃을 수 있다. 반드시 검증된 감사를 받은 구현체(예: Safe, Biconomy, ZeroDev)를 기반으로 구축하고, 직접 작성한 로직은 철저한 테스트와 감사를 진행해야 한다.

### 트레이드오프 요약

| 장점 | 단점 |
|------|------|
| 소셜 복구, 멀티시그 지원 | 가스 오버헤드 |
| 가스리스 UX (Paymaster) | 번들러 의존성 |
| 배치 트랜잭션 | 컨트랙트 취약점 위험 |
| ERC-20으로 가스 지불 | 구현 복잡도 |
| 세션 키, 권한 위임 | 생태계 미성숙 |

## 정리

ERC-4337은 이더리움의 고질적인 UX 문제를 프로토콜 변경 없이 해결하는 영리한 접근법이다. `UserOperation`, `EntryPoint`, `Bundler`, `Paymaster`의 네 가지 핵심 컴포넌트를 이해하면 전체 아키텍처를 파악할 수 있다.

실무에서 도입을 고려한다면 다음 순서를 권장한다.

1. **검증된 SDK 활용**: `permissionless.js`, `userop.js`, `@zerodev/sdk` 등으로 시작
2. **감사된 Smart Account 기반 사용**: Safe나 Biconomy Modular Account 활용
3. **Bundler는 관리형 서비스 우선**: Pimlico, Stackup, Alchemy AA
4. **Paymaster로 UX 개선**: 스폰서십 또는 ERC-20 가스 지불 단계적 적용

계정 추상화는 단순한 기술 스펙이 아니라 Web3 대중화의 핵심 인프라다. 지금 당장 모든 프로젝트에 필요하지는 않지만, 지갑과 온보딩 UX가 중요한 컨슈머 프로덕트라면 반드시 검토해야 할 기술이다.
