# 블록체인 트랜잭션 가스비 최적화 전략

## 개요

이더리움을 비롯한 EVM 호환 블록체인에서 스마트 컨트랙트를 운영하다 보면, **가스비(Gas Fee)** 는 단순한 부대비용이 아니라 서비스 존폐를 가를 수 있는 핵심 운영 비용이 된다. DeFi 프로토콜이나 NFT 마켓플레이스에서 트랜잭션 한 건당 수십 달러의 가스비가 발생하는 상황은 이미 익숙한 풍경이다.

이 포스팅에서는 스마트 컨트랙트 레벨에서의 가스 최적화 기법부터, 백엔드 서버에서 트랜잭션을 제출할 때 적용할 수 있는 실전 전략까지 중급~시니어 개발자 관점에서 체계적으로 다룬다.

---

## 핵심 개념

### 가스(Gas)란 무엇인가

가스는 EVM에서 연산 작업의 비용을 나타내는 단위다. 트랜잭션의 최종 비용은 아래 공식으로 계산된다.

```
// EIP-1559 이후 (London Hardfork)
Total Fee = Gas Used × (Base Fee + Priority Fee)

// 레거시 방식
Total Fee = Gas Used × Gas Price
```

- **Base Fee**: 네트워크가 자동으로 결정하는 기본 수수료 (소각됨)
- **Priority Fee (Tip)**: 채굴자/검증자에게 지급되는 팁
- **Gas Limit**: 트랜잭션에 허용할 최대 가스량

### 가스 소비 주요 요인

| 연산 종류 | 가스 비용 |
|---|---|
| SSTORE (신규 저장) | 20,000 |
| SSTORE (업데이트) | 2,900 |
| SLOAD | 2,100 |
| 외부 함수 호출 | 700+ |
| 이벤트 로그 발생 | 375 + 데이터 크기 |
| 기본 트랜잭션 | 21,000 |

스토리지 연산(`SSTORE`, `SLOAD`)이 압도적으로 비싸다는 점을 항상 염두에 두어야 한다.

## 실전 예제

### 1. 스토리지 최적화: 변수 패킹(Variable Packing)

EVM의 스토리지 슬롯은 32바이트(256비트) 단위다. 여러 작은 변수를 하나의 슬롯에 묶으면 `SSTORE` 횟수를 줄일 수 있다.

```solidity
// ❌ 비효율적: 각 변수가 별도 슬롯 사용 (3 slots)
contract Inefficient {
    uint256 public price;    // slot 0
    uint128 public amount;   // slot 1 (128비트만 사용)
    uint128 public balance;  // slot 2 (128비트만 사용)
}

// ✅ 최적화: 변수 순서 재배치로 2슬롯 -> 1슬롯 절약
contract Optimized {
    uint256 public price;    // slot 0
    uint128 public amount;   // slot 1 (상위 128비트)
    uint128 public balance;  // slot 1 (하위 128비트)
}
```

### 2. 메모리 vs 스토리지 활용

반복 접근이 필요한 스토리지 변수는 `memory`에 캐싱하라.

```solidity
// ❌ 반복 SLOAD 발생
function sumBad(uint256[] storage data) internal view returns (uint256 total) {
    for (uint256 i = 0; i < data.length; i++) {
        total += data[i]; // 매 반복마다 SLOAD
    }
}

// ✅ memory 캐싱으로 SLOAD 최소화
function sumGood(uint256[] storage data) internal view returns (uint256 total) {
    uint256[] memory cachedData = data; // 한 번만 SLOAD
    uint256 len = cachedData.length;
    for (uint256 i = 0; i < len; i++) {
        total += cachedData[i];
    }
}
```

### 3. 이벤트(Event) 활용으로 스토리지 대체

조회 전용 데이터는 스토리지에 저장하지 말고 이벤트 로그로 남겨라. 이벤트는 스토리지보다 훨씬 저렴하다.

```solidity
// ❌ 조회용 데이터를 스토리지에 저장 (SSTORE 비용)
contract WithStorage {
    address[] public participants;
    
    function join() external {
        participants.push(msg.sender); // 비쌈
    }
}

// ✅ 이벤트 로그 활용 (오프체인 인덱싱)
contract WithEvent {
    event Joined(address indexed participant, uint256 timestamp);
    
    function join() external {
        emit Joined(msg.sender, block.timestamp); // 저렴함
    }
}
```

백엔드에서는 **The Graph** 또는 자체 이벤트 리스너로 인덱싱하면 된다.

### 4. 커스텀 에러 사용 (Solidity 0.8.4+)

`require`의 문자열 메시지는 스토리지에 올라가며 가스를 소모한다. 커스텀 에러를 쓰면 최대 50% 절약 가능하다.

```solidity
// ❌ string revert 메시지 (비쌈)
function transferLegacy(address to, uint256 amount) external {
    require(balanceOf[msg.sender] >= amount, "Insufficient balance");
    require(to != address(0), "Invalid address");
    // ...
}

// ✅ Custom Error (저렴함, ABI 인코딩 최소화)
error InsufficientBalance(address sender, uint256 required, uint256 available);
error InvalidAddress();

function transfer(address to, uint256 amount) external {
    if (balanceOf[msg.sender] < amount) {
        revert InsufficientBalance(msg.sender, amount, balanceOf[msg.sender]);
    }
    if (to == address(0)) revert InvalidAddress();
    // ...
}
```

### 5. 백엔드에서 EIP-1559 동적 가스 전략 (Java + Web3j)

Spring 백엔드에서 트랜잭션을 제출할 때 가스비를 동적으로 제어하는 예제다.

```java
@Service
@Slf4j
public class GasOptimizedTransactionService {

    private final Web3j web3j;
    private final GasPriceOracle gasPriceOracle;

    // EIP-1559 트랜잭션 전송 (동적 maxFeePerGas 계산)
    public TransactionReceipt sendOptimizedTransaction(
            Credentials credentials,
            String toAddress,
            BigInteger value,
            GasPriority priority) throws Exception {

        // 현재 블록의 baseFee 조회
        EthBlock latestBlock = web3j.ethGetBlockByNumber(
                DefaultBlockParameterName.LATEST, false).send();
        BigInteger baseFee = latestBlock.getBlock().getBaseFeePerGas();

        // 우선순위별 maxPriorityFeePerGas 설정
        BigInteger maxPriorityFee = switch (priority) {
            case SLOW   -> Convert.toWei("1", Convert.Unit.GWEI).toBigInteger();
            case NORMAL -> Convert.toWei("1.5", Convert.Unit.GWEI).toBigInteger();
            case FAST   -> Convert.toWei("3", Convert.Unit.GWEI).toBigInteger();
        };

        // maxFeePerGas = 2 * baseFee + maxPriorityFee (권장 공식)
        BigInteger maxFeePerGas = baseFee.multiply(BigInteger.TWO).add(maxPriorityFee);

        // 가스 리밋 추정 (버퍼 20% 추가)
        BigInteger estimatedGas = web3j.ethEstimateGas(
                Transaction.createEthCallTransaction(
                        credentials.getAddress(), toAddress, Numeric.toHexString(value.toByteArray()))
        ).send().getAmountUsed();
        BigInteger gasLimit = estimatedGas.multiply(BigInteger.valueOf(120))
                                          .divide(BigInteger.valueOf(100));

        log.info("Gas Strategy - baseFee: {} wei, maxPriorityFee: {} wei, maxFeePerGas: {} wei, gasLimit: {}",
                baseFee, maxPriorityFee, maxFeePerGas, gasLimit);

        RawTransaction rawTx = RawTransaction.createEtherTransaction(
                getNonce(credentials.getAddress()),
                null,         // gasPrice (EIP-1559에서 null)
                gasLimit,
                toAddress,
                value,
                maxPriorityFee,
                maxFeePerGas
        );

        byte[] signedTx = TransactionEncoder.signMessage(rawTx, credentials);
        String txHash = web3j.ethSendRawTransaction(
                Numeric.toHexString(signedTx)).send().getTransactionHash();

        return waitForReceipt(txHash);
    }

    public enum GasPriority { SLOW, NORMAL, FAST }
}
```

### 6. 트랜잭션 배칭(Batching)

여러 트랜잭션을 하나로 묶으면 기본 트랜잭션 비용(21,000 gas)을 절약할 수 있다.

```solidity
// Multicall 패턴: 여러 호출을 단일 트랜잭션으로
contract Multicall {
    struct Call {
        address target;
        bytes callData;
    }

    function aggregate(Call[] calldata calls) 
        external 
        returns (uint256 blockNumber, bytes[] memory returnData) 
    {
        blockNumber = block.number;
        returnData = new bytes[](calls.length);
        
        for (uint256 i = 0; i < calls.length; i++) {
            (bool success, bytes memory ret) = calls[i].target.call(calls[i].callData);
            require(success, "Multicall: call failed");
            returnData[i] = ret;
        }
    }
}
```

## 주의사항 및 트레이드오프

### ⚠️ 과도한 최적화의 위험

**가독성 vs 가스 절약**: 변수 패킹이나 `uint8` 대신 `uint256` 사용이 오히려 유리한 경우도 있다. EVM은 32바이트 미만의 타입을 처리할 때 내부적으로 패딩 연산이 추가되어 **단독 사용 시 오히려 가스가 더 들 수 있다**.

```solidity
// 단독으로 쓰이는 경우 uint256이 uint8보다 빠름
// uint8은 패킹 이점이 있을 때만 사용할 것
uint256 counter; // ✅ 단독 변수는 uint256 권장
```

### ⚠️ 가스 추정의 함정

`eth_estimateGas`는 현재 상태 기준의 추정치다. 같은 블록 내 앞선 트랜잭션이 상태를 바꾸면 실제 소비량이 달라질 수 있다. **항상 10~20% 버퍼**를 두어야 `Out of Gas` 오류를 방지할 수 있다.

### ⚠️ L1 vs L2 전략 차이

Arbitrum, Optimism 같은 L2에서는 연산 비용보다 **L1 calldata 비용**이 지배적이다. 이 경우에는 calldata 크기를 줄이는 것이 최우선 전략이 된다. 동일한 최적화 기법을 L1과 L2에 동일하게 적용하면 오히려 역효과가 날 수 있다.

### ⚠️ 배칭의 원자성 위험

Multicall 패턴은 트랜잭션 하나가 실패하면 전체가 롤백된다. 비즈니스 로직상 일부 실패를 허용해야 한다면 `try-catch` 패턴의 부분 실패 허용 Multicall을 별도 구현해야 한다.

### ⚠️ 가스 가격 오라클 신뢰성

외부 가스 오라클(예: Etherscan Gas Tracker API)에 의존하는 경우 API 다운타임이나 지연으로 인해 가스 가격이 잘못 설정될 수 있다. **폴백 로직**과 **최대 가스 상한선(hard cap)** 을 반드시 설정하라.

## 정리

블록체인 가스비 최적화는 단일 기법으로 해결되는 문제가 아니다. 컨트랙트 레벨의 코드 최적화부터 백엔드의 동적 가스 전략, 그리고 아키텍처 수준의 L2 전환까지 다층적으로 접근해야 한다.

| 최적화 레벨 | 기법 | 예상 절감 효과 |
|---|---|---|
| 컨트랙트 코드 | 변수 패킹, 메모리 캐싱 | 10~40% |
| 에러 처리 | Custom Error | 최대 50% |
| 아키텍처 | 이벤트 로그, Multicall | 20~60% |
| 트랜잭션 제출 | EIP-1559 동적 전략 | 운영 비용 15~30% |
| 인프라 | L2 마이그레이션 | 90%+ |

실무에서는 **Hardhat Gas Reporter** 나 **foundry의 `--gas-report`** 플래그로 함수별 가스 소비량을 측정하며 개발하는 습관을 들이는 것이 중요하다. 측정 없는 최적화는 추측일 뿐이다. 가스 최적화는 성능 튜닝과 마찬가지로 **프로파일링 → 병목 확인 → 개선 → 검증**의 사이클로 접근하라.
