# 리눅스 cgroup과 컨테이너 격리 원리

## 개요

Docker, Kubernetes를 매일 사용하면서도 "컨테이너가 어떻게 격리되는가?"라는 질문에 명확히 답하지 못하는 개발자가 생각보다 많다. 컨테이너는 VM과 달리 별도의 하이퍼바이저 없이 **호스트 커널을 공유**하면서도 독립된 환경처럼 동작한다. 이 마법의 핵심에는 리눅스 커널의 두 가지 기술, **cgroup(Control Groups)** 과 **namespace**가 있다.

이 글에서는 cgroup의 동작 원리를 깊이 있게 살펴보고, namespace와 함께 실제 컨테이너 격리가 어떻게 구현되는지 실전 예제와 함께 분석한다. 단순히 "알면 좋은 지식"이 아니라, 운영 환경에서 컨테이너 리소스를 튜닝하고 문제를 진단할 때 즉시 활용할 수 있는 수준을 목표로 한다.

## 핵심 개념

### cgroup이란?

cgroup(Control Groups)은 **프로세스 그룹에 대한 리소스 사용량을 제한, 측정, 격리**하는 리눅스 커널 기능이다. 2007년 Google 엔지니어들이 개발해 커널 2.6.24에 병합됐으며, 현재 대부분의 배포판은 **cgroup v2** (unified hierarchy)를 기본으로 사용한다.

cgroup이 제어할 수 있는 리소스는 다음과 같다.

| 서브시스템 | 제어 대상 |
|---|---|
| `cpu` | CPU 사용량, 스케줄링 가중치 |
| `memory` | 메모리 사용량, OOM 동작 |
| `blkio` / `io` | 블록 디바이스 I/O 대역폭 및 IOPS |
| `net_cls` / `net_prio` | 네트워크 패킷 분류 및 우선순위 |
| `pids` | 프로세스 수 제한 |
| `devices` | 장치 접근 제어 |
| `cpuset` | 특정 CPU 코어/NUMA 노드 할당 |

### namespace란?

namespace는 프로세스가 보는 **시스템 자원의 뷰를 격리**한다. cgroup이 "얼마나 쓸 수 있는가"를 제어한다면, namespace는 "무엇을 볼 수 있는가"를 제어한다.

| namespace | 격리 대상 |
|---|---|
| `pid` | 프로세스 ID 공간 |
| `net` | 네트워크 인터페이스, 라우팅 테이블 |
| `mnt` | 마운트 포인트 |
| `uts` | 호스트명, 도메인명 |
| `ipc` | System V IPC, POSIX 메시지 큐 |
| `user` | UID/GID 매핑 |
| `cgroup` | cgroup 루트 디렉터리 |
| `time` | 시스템 시계 (커널 5.6+) |

컨테이너는 이 두 가지를 조합해 격리된 실행 환경을 만든다.

### cgroup v1 vs cgroup v2

실무에서는 두 버전 모두 마주칠 수 있기 때문에 차이를 알아야 한다.

- **cgroup v1**: 서브시스템별로 독립적인 계층 구조. `/sys/fs/cgroup/cpu/`, `/sys/fs/cgroup/memory/` 등 분리된 마운트 포인트. 동일 프로세스가 각 서브시스템에서 다른 그룹에 속할 수 있어 일관성 문제가 발생했다.
- **cgroup v2**: 단일 계층 구조(unified hierarchy). `/sys/fs/cgroup/` 하나로 통합. 스레드 모드, PSI(Pressure Stall Information) 지원 등 추가.

Ubuntu 22.04, RHEL 9, 최신 Debian은 기본적으로 cgroup v2를 사용한다. `stat -fc %T /sys/fs/cgroup/` 명령으로 확인 가능하다.

## 실전 예제

### 1. cgroup을 직접 만들어 메모리 제한하기

Docker 없이 순수 리눅스 커널 기능만으로 cgroup을 생성하고 메모리를 제한해보자.

```bash
# cgroup v2 기준
# 새 cgroup 디렉터리 생성
sudo mkdir /sys/fs/cgroup/my-test-group

# 메모리 최대 사용량 50MB로 제한
echo "52428800" | sudo tee /sys/fs/cgroup/my-test-group/memory.max

# 메모리 swap 제한 (swap 포함 최대치)
echo "52428800" | sudo tee /sys/fs/cgroup/my-test-group/memory.swap.max

# 현재 셸 프로세스를 cgroup에 추가
echo $$ | sudo tee /sys/fs/cgroup/my-test-group/cgroup.procs

# 메모리 50MB 초과 할당 시도 → OOM 발생 확인
python3 -c "x = ' ' * 100 * 1024 * 1024"
```

```bash
# 현재 cgroup의 메모리 사용량 모니터링
watch -n 1 cat /sys/fs/cgroup/my-test-group/memory.current

# OOM 이벤트 확인
cat /sys/fs/cgroup/my-test-group/memory.events
# 출력 예시:
# low 0
# high 0
# max 3       ← max 한도 도달 횟수
# oom 1       ← OOM 발생 횟수
# oom_kill 1  ← OOM killer 발동 횟수
```

### 2. CPU 제한 설정

```bash
# CPU 쿼터 설정: 100ms 주기 중 50ms만 사용 = 50% CPU
sudo mkdir /sys/fs/cgroup/cpu-limited

# cpu.max 형식: "quota period" (단위: 마이크로초)
echo "50000 100000" | sudo tee /sys/fs/cgroup/cpu-limited/cpu.max

# 무한 루프 프로그램을 해당 cgroup에서 실행
echo $$ | sudo tee /sys/fs/cgroup/cpu-limited/cgroup.procs
stress-ng --cpu 1 --timeout 10s &

# 다른 터미널에서 CPU 사용량 확인
top -p $(cat /sys/fs/cgroup/cpu-limited/cgroup.procs)
```

### 3. namespace를 활용한 프로세스 격리

```bash
# unshare 명령으로 새 PID, UTS, mount namespace 생성
sudo unshare --pid --uts --mount --fork bash

# 격리된 환경 내에서 실행
hostname container-test  # UTS namespace 격리 덕분에 호스트 영향 없음
hostname                 # container-test 출력

# PID namespace 격리 확인
ps aux                   # 1번 PID가 현재 bash
echo $$                  # 1 출력 (격리된 PID 공간)

# 호스트에서는 실제 PID로 보임
# 다른 터미널에서:
# ps aux | grep bash → 실제 PID (예: 12345) 확인
```

### 4. Docker 컨테이너의 cgroup 매핑 확인

실제 Docker 컨테이너가 어떻게 cgroup을 사용하는지 직접 확인해보자.

```bash
# 메모리 256MB 제한 컨테이너 실행
docker run -d --name test-cgroup \
  --memory="256m" \
  --memory-swap="256m" \
  --cpus="1.5" \
  nginx:alpine

# 컨테이너 PID 확인
CONTAINER_PID=$(docker inspect test-cgroup --format '{{.State.Pid}}')

# cgroup 경로 확인
cat /proc/${CONTAINER_PID}/cgroup
# 출력 예시 (cgroup v2):
# 0::/system.slice/docker-<container-id>.scope

# 실제 cgroup 설정값 확인
CGROUP_PATH="/sys/fs/cgroup/system.slice/docker-$(docker inspect test-cgroup --format '{{.Id}}').scope"

cat ${CGROUP_PATH}/memory.max
# 268435456 (256MB = 256 * 1024 * 1024)

cat ${CGROUP_PATH}/cpu.max
# 150000 100000 (1.5 CPU = 150000/100000)

# 실시간 리소스 사용량
cat ${CGROUP_PATH}/memory.current
cat ${CGROUP_PATH}/cpu.stat
```

### 5. PSI(Pressure Stall Information)로 리소스 압박 감지

cgroup v2의 강력한 기능 중 하나인 PSI를 활용하면 리소스 부족 신호를 조기에 포착할 수 있다.

```bash
# 메모리 PSI 확인
cat /sys/fs/cgroup/my-test-group/memory.pressure
# some avg10=0.00 avg60=0.00 avg300=0.00 total=0
# full avg10=15.23 avg60=8.45 avg300=3.12 total=123456
# full: 모든 프로세스가 리소스 대기 → 실질적 중단 상태

# CPU PSI 확인
cat /sys/fs/cgroup/my-test-group/cpu.pressure

# PSI 임계값 기반 알림 설정 (메모리 압박 70% 초과 시 알림)
# 1초 윈도우 중 700ms 이상 stall 발생 시 트리거
echo "some 700000 1000000" | sudo tee /sys/fs/cgroup/my-test-group/memory.pressure
```

## 주의사항 및 트레이드오프

### 메모리 제한과 OOM Killer

컨테이너에 메모리 제한을 설정할 때 가장 흔한 실수는 **JVM 기반 애플리케이션**에서 발생한다. JVM은 기본적으로 호스트 전체 메모리를 기준으로 힙을 설정하기 때문에, 컨테이너 제한보다 훨씬 큰 힙을 할당하려 해 OOM이 발생한다.

```bash
# 잘못된 방식: 컨테이너 메모리 제한 고려 없음
java -Xmx4g -jar app.jar  # 컨테이너가 512MB 제한이면 즉시 OOM

# 올바른 방식: 컨테이너 인식 JVM 플래그 (JDK 8u191+, JDK 11+)
java -XX:+UseContainerSupport \
     -XX:MaxRAMPercentage=75.0 \
     -jar app.jar
```

### CPU 제한의 함정: Throttling

CPU 제한을 너무 낮게 설정하면 CPU Throttling이 발생해 레이턴시 스파이크를 유발한다. 특히 GC 작업이 많은 JVM이나 주기적 배치 작업이 있는 서비스에서 심각한 문제가 된다.

```bash
# Kubernetes에서 CPU throttling 확인
kubectl exec -it <pod-name> -- cat /sys/fs/cgroup/cpu.stat | grep throttled
# throttled_usec 값이 지속적으로 증가하면 CPU limit 상향 필요

# 또는 cAdvisor + Prometheus 쿼리
# container_cpu_cfs_throttled_seconds_total / container_cpu_cfs_periods_total
```

**권장 접근법**: CPU request는 평균 사용량 기준으로, limit은 버스트를 고려해 request의 2~4배로 설정하거나, 레이턴시 민감 서비스는 limit을 아예 설정하지 않는 경우도 있다.

### cgroup v1/v2 혼재 환경

일부 오래된 클러스터나 커스텀 OS 이미지를 사용하는 환경에서는 v1/v2가 혼재할 수 있다. 특히 `systemd`와의 연동, Docker 버전, Kubernetes 버전에 따라 동작이 달라질 수 있으므로 반드시 환경을 확인해야 한다.

```bash
# cgroup 버전 확인
mount | grep cgroup
stat -fc %T /sys/fs/cgroup/
# tmpfs → v1, cgroup2fs → v2

# systemd cgroup driver 확인 (Kubernetes 노드)
systemctl show --property=DefaultControllers kubelet
```

### 네임스페이스 탈출 취약점

user namespace와 관련된 권한 승격 취약점이 지속적으로 발견된다. 특히 `--privileged` 컨테이너나 잘못된 capabilities 설정은 namespace 격리를 무력화할 수 있다.

```bash
# 위험: 모든 capabilities 부여
docker run --privileged ...

# 권장: 필요한 capability만 명시적으로 추가
docker run --cap-drop=ALL --cap-add=NET_BIND_SERVICE ...
```

## 정리

컨테이너 격리는 단일 기술이 아니라 여러 리눅스 커널 기능의 조합이다.

- **cgroup**: CPU, 메모리, I/O 등 리소스 사용량 제한 및 측정
- **namespace**: 프로세스, 네트워크, 파일시스템 등 시스템 뷰 격리
- **seccomp, capabilities, AppArmor/SELinux**: 보안 레이어 추가

이 원리를 이해하면 다음과 같은 실무 역량이 향상된다.

1. **OOM, CPU throttling 원인 분석**: cgroup 파일시스템을 직접 읽어 정확한 원인 파악
2. **Kubernetes 리소스 설정 최적화**: request/limit 튜닝 근거 마련
3. **보안 강화**: 최소 권한 원칙을 컨테이너 수준에서 적용
4. **성능 이상 조기 감지**: PSI를 활용한 리소스 압박 모니터링

컨테이너 기술은 끊임없이 발전하고 있지만, 그 기반은 결국 리눅스 커널이다. 추상화 레이어 아래를 이해하는 것이 진정한 시니어 엔지니어의 역량이다.
