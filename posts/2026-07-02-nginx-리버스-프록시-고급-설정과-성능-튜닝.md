# Nginx 리버스 프록시 고급 설정과 성능 튜닝

## 개요

Nginx는 단순한 웹 서버를 넘어 고성능 리버스 프록시, 로드 밸런서, HTTP 캐시 서버로서 현대 웹 아키텍처의 핵심 컴포넌트로 자리 잡았다. 기본적인 `proxy_pass` 설정을 넘어, 실제 프로덕션 환경에서 수만 RPS(Requests Per Second)를 안정적으로 처리하려면 세밀한 튜닝이 필수다.

이 포스팅에서는 단순 설정을 넘어 **커넥션 풀 관리**, **업스트림 헬스 체크**, **캐싱 전략**, **Keep-Alive 최적화**, **버퍼 튜닝** 등 프로덕션에서 실제로 효과를 보는 고급 설정들을 다룬다. Spring Boot 기반의 백엔드 서버와 연동하는 시나리오를 기준으로 설명한다.

---

## 핵심 개념

### 리버스 프록시 동작 원리 재정립

Nginx가 리버스 프록시로 동작할 때 클라이언트와의 커넥션, 업스트림(백엔드)과의 커넥션 두 가지를 독립적으로 관리한다. 이 두 커넥션의 생명주기를 어떻게 다루느냐가 성능 튜닝의 핵심이다.

- **클라이언트 ↔ Nginx**: Keep-Alive, HTTP/2 설정이 영향
- **Nginx ↔ 업스트림**: 커넥션 풀(`keepalive`), 타임아웃이 영향

이 두 레이어를 분리해서 생각하면 각 지시어의 역할이 명확해진다.

### Worker 프로세스와 이벤트 모델

Nginx는 비동기 이벤트 기반 모델을 사용한다. Worker 프로세스 수와 커넥션 수 설정이 CPU 코어 수와 맞아야 최적의 성능을 낸다.

---

## 실전 예제

### 1. 기본 Worker 및 이벤트 튜닝

```nginx
# /etc/nginx/nginx.conf

# CPU 코어 수에 맞게 설정 (auto는 자동 감지)
worker_processes auto;

# 각 Worker당 최대 커넥션 수
# ulimit -n 값과 연동 필요
events {
    worker_connections 4096;
    use epoll;           # Linux에서 epoll 명시 (기본값이지만 명시 권장)
    multi_accept on;     # 한 번에 여러 커넥션 수락
}

http {
    # 파일 전송 최적화
    sendfile        on;
    tcp_nopush      on;   # sendfile과 함께 사용 시 패킷 효율 향상
    tcp_nodelay     on;   # Keep-Alive 커넥션에서 지연 최소화

    # Keep-Alive 설정 (클라이언트 ↔ Nginx)
    keepalive_timeout  65;
    keepalive_requests 1000;  # 하나의 Keep-Alive 커넥션으로 처리할 최대 요청 수
}
```

### 2. 업스트림 커넥션 풀 및 로드 밸런싱

업스트림 서버와의 Keep-Alive 커넥션 풀을 유지하면 매 요청마다 TCP 핸드셰이크를 반복하지 않아 레이턴시를 크게 줄일 수 있다.

```nginx
upstream spring_backend {
    # least_conn: 활성 커넥션이 가장 적은 서버로 라우팅 (기본 round-robin보다 부하 분산 효과적)
    least_conn;

    server 10.0.1.10:8080 weight=3 max_fails=3 fail_timeout=30s;
    server 10.0.1.11:8080 weight=3 max_fails=3 fail_timeout=30s;
    server 10.0.1.12:8080 weight=1 max_fails=3 fail_timeout=30s backup;

    # 핵심: Nginx ↔ 업스트림 간 Keep-Alive 커넥션 풀 크기
    # 이 값은 worker 프로세스당 유지할 idle 커넥션 수
    keepalive 32;

    # 하나의 keepalive 커넥션으로 처리할 최대 요청 수
    keepalive_requests 1000;

    # idle 커넥션 유지 시간
    keepalive_time 1h;
    keepalive_timeout 60s;
}

server {
    listen 80;
    server_name api.example.com;

    location /api/ {
        proxy_pass http://spring_backend;

        # Keep-Alive 사용을 위해 반드시 HTTP/1.1 명시
        proxy_http_version 1.1;
        proxy_set_header Connection "";  # Connection: close 헤더 제거

        # 실제 클라이언트 IP 전달
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Host $host;
    }
}
```

> **주의**: `keepalive 32`는 worker당 idle 커넥션 수다. `worker_processes auto`로 4개 worker가 뜨면 총 128개 커넥션이 유지된다. 업스트림 서버의 max 커넥션 설정(Spring Boot의 `server.tomcat.max-connections`)보다 작게 유지해야 한다.

### 3. 프록시 버퍼 튜닝

버퍼 크기는 응답 크기와 네트워크 특성에 따라 튜닝이 필요하다. 버퍼가 너무 작으면 디스크 I/O가 발생하고, 너무 크면 메모리를 낭비한다.

```nginx
location /api/ {
    proxy_pass http://spring_backend;
    proxy_http_version 1.1;
    proxy_set_header Connection "";

    # 업스트림 응답 헤더를 위한 버퍼
    proxy_buffer_size 8k;

    # 응답 본문 버퍼 (개수 × 크기)
    # API 응답이 대부분 작다면 줄여도 됨, 큰 JSON 응답이라면 늘림
    proxy_buffers 16 16k;

    # 클라이언트로 보내기 전 버퍼링할 최대 크기
    proxy_busy_buffers_size 32k;

    # 버퍼링이 꺼진 상태에서 한 번에 전달할 크기
    proxy_max_temp_file_size 0;  # 0으로 설정 시 임시 파일 사용 안 함

    # 타임아웃 설정 (업스트림 서버 특성에 맞게)
    proxy_connect_timeout 5s;    # 업스트림 커넥션 수립 타임아웃
    proxy_send_timeout    60s;   # 업스트림으로 요청 전송 타임아웃
    proxy_read_timeout    60s;   # 업스트림 응답 대기 타임아웃
}
```

### 4. 프록시 캐싱 설정

정적 자원이나 변경이 적은 API 응답은 Nginx 레벨에서 캐싱하면 업스트림 부하를 획기적으로 줄일 수 있다.

```nginx
http {
    # 캐시 저장소 정의
    # levels: 디렉토리 구조 (해시 충돌 방지)
    # keys_zone: 캐시 키 메모리 영역 이름:크기 (1MB ≈ 8000개 키)
    # max_size: 캐시 디스크 최대 크기
    # inactive: 이 시간 동안 접근 없으면 삭제
    proxy_cache_path /var/cache/nginx/api
        levels=1:2
        keys_zone=api_cache:10m
        max_size=1g
        inactive=60m
        use_temp_path=off;

    server {
        location /api/v1/products {
            proxy_pass http://spring_backend;
            proxy_http_version 1.1;
            proxy_set_header Connection "";

            proxy_cache api_cache;
            proxy_cache_key "$scheme$request_method$host$request_uri";

            # GET, HEAD만 캐싱
            proxy_cache_methods GET HEAD;

            # 업스트림 응답 코드별 캐시 유지 시간
            proxy_cache_valid 200 301 10m;
            proxy_cache_valid 404       1m;

            # 업스트림 서버 오류 시 stale 캐시 사용
            proxy_cache_use_stale error timeout updating
                                   http_500 http_502 http_503 http_504;

            # 동시 요청 시 한 번만 업스트림 호출 (Cache Stampede 방지)
            proxy_cache_lock on;
            proxy_cache_lock_timeout 5s;

            # 캐시 상태 헤더 추가 (디버깅용)
            add_header X-Cache-Status $upstream_cache_status;
        }
    }
}
```

### 5. 능동 헬스 체크 (Nginx Plus 없이 구현)

오픈소스 Nginx에서 수동 헬스 체크는 기본 제공되지만, `nginx_upstream_check_module`을 컴파일하거나 다음과 같이 별도 헬스 체크 서버를 두는 방법을 활용할 수 있다.

```nginx
# 수동 헬스 체크: max_fails, fail_timeout으로 서킷 브레이커 흉내
upstream spring_backend {
    server 10.0.1.10:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;

    keepalive 32;
}

# 헬스 체크 전용 엔드포인트 내부 호출용 location
server {
    listen 8081;  # 내부 모니터링 포트

    location /nginx-health {
        access_log off;
        return 200 "healthy\n";
        add_header Content-Type text/plain;
    }

    location /upstream-health {
        proxy_pass http://spring_backend/actuator/health;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        access_log off;
    }
}
```

### 6. 요청 제한 및 보호 설정

리버스 프록시는 백엔드를 보호하는 첫 번째 방어선이기도 하다.

```nginx
http {
    # IP별 초당 요청 수 제한
    limit_req_zone $binary_remote_addr zone=api_limit:10m rate=100r/s;

    # IP별 동시 커넥션 수 제한
    limit_conn_zone $binary_remote_addr zone=conn_limit:10m;

    server {
        location /api/ {
            # burst: 버스트 허용량, nodelay: 버스트 요청 즉시 처리
            limit_req zone=api_limit burst=200 nodelay;
            limit_conn conn_limit 20;

            # 클라이언트 요청 본문 크기 제한 (대용량 업로드 제한)
            client_max_body_size 10m;

            proxy_pass http://spring_backend;
            proxy_http_version 1.1;
            proxy_set_header Connection "";
        }
    }
}
```

## 주의사항 및 트레이드오프

### Keep-Alive 커넥션 풀 사이즈 설정

`keepalive` 값을 무작정 늘리면 안 된다. 업스트림 서버의 최대 스레드/커넥션 수를 넘기면 오히려 장애가 발생한다. Spring Boot Tomcat의 경우 `server.tomcat.max-threads`(기본 200)와 `server.tomcat.max-connections`(기본 8192)를 확인하고 역산해서 설정해야 한다.

```
적정 keepalive = (업스트림 max-connections) / (Nginx worker_processes) × 안전계수(0.7)
```

### 캐시와 데이터 일관성

`proxy_cache_use_stale`은 가용성을 높여주지만 오래된 데이터를 서빙할 수 있다. 금융, 재고 수량처럼 정합성이 중요한 API에는 절대 적용하면 안 된다. 캐시 무효화 전략(`proxy_cache_bypass`, `proxy_no_cache`)을 함께 설계해야 한다.

### 버퍼 설정과 스트리밍

`proxy_buffering on`(기본값)은 응답을 전부 받아 버퍼링한 뒤 클라이언트에 전달한다. SSE(Server-Sent Events)나 스트리밍 응답에는 `proxy_buffering off`로 설정해야 한다. 그렇지 않으면 클라이언트가 전체 응답이 끝날 때까지 아무것도 받지 못한다.

```nginx
location /api/stream {
    proxy_pass http://spring_backend;
    proxy_buffering off;
    proxy_cache off;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
}
```

### 타임아웃 설정의 균형

`proxy_read_timeout`이 너무 짧으면 정상 요청이 504를 반환하고, 너무 길면 슬로우 쿼리나 장애 상황에서 Nginx Worker가 커넥션을 오래 붙들어 리소스를 낭비한다. 업스트림 API의 P99 응답 시간을 측정하고 2~3배 여유를 두는 것이 일반적인 가이드라인이다.

## 정리

Nginx 리버스 프록시 튜닝은 설정 하나하나가 상호 연관되어 있다. 핵심 포인트를 다시 정리하면 다음과 같다.

| 설정 항목 | 핵심 포인트 |
|---|---|
| `worker_processes` / `worker_connections` | CPU 코어 수, `ulimit -n`과 맞춰라 |
| `upstream keepalive` | 업스트림 max-connections와 worker 수를 고려해 계산 |
| `proxy_buffers` | 응답 크기 분포를 측정하고 설정 |
| `proxy_cache` | Cache Stampede 방지(`proxy_cache_lock`)와 Stale 전략 필수 |
| `limit_req` / `limit_conn` | 백엔드 보호를 위한 1차 방어선 |
| 타임아웃 | P99 레이턴시 기준으로 여유 있게 설정 |

설정 변경 후에는 반드시 `nginx -t`로 문법을 검증하고, 단계적 배포와 함께 `access_log`, `upstream_response_time`, `upstream_cache_status` 등의 지표를 모니터링하며 효과를 검증하는 습관이 중요하다. Nginx 성능 튜닝은 한 번에 끝나는 작업이 아니라 트래픽 패턴이 바뀔 때마다 반복적으로 리뷰해야 하는 지속적인 작업이다.
