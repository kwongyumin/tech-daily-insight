# Redis 메모리 최적화와 만료 정책 설계

## 개요

Redis는 인메모리 데이터 구조 저장소로서 캐시, 세션 관리, 실시간 리더보드, 메시지 큐 등 다양한 용도로 활용된다. 그러나 메모리는 본질적으로 유한한 자원이다. Redis를 운영하다 보면 어느 순간 `OOM command not allowed when used memory > 'maxmemory'` 에러를 마주치거나, 예상치 못한 키 증가로 메모리 사용량이 급격히 치솟는 상황을 경험하게 된다.

이 글에서는 Redis 메모리를 효율적으로 관리하기 위한 핵심 전략과, 만료 정책(Expiration Policy) 및 축출 정책(Eviction Policy)을 어떻게 설계해야 하는지를 실무 관점에서 다룬다. 단순히 `TTL`을 붙이는 수준을 넘어, 데이터 특성에 맞는 정책 선택과 모니터링까지 포괄하는 내용을 정리했다.

## 핵심 개념

### 1. Redis 메모리 관리의 두 축: 만료(Expiration) vs 축출(Eviction)

이 두 개념은 혼용되기 쉽지만 명확히 구분해야 한다.

- **만료(Expiration)**: 키에 TTL(Time To Live)을 설정하면, 만료 시각이 지난 키는 삭제된다. 개발자가 명시적으로 제어한다.
- **축출(Eviction)**: `maxmemory` 한계에 도달했을 때 Redis가 자동으로 키를 삭제하는 메커니즘이다. `maxmemory-policy` 설정으로 전략을 선택한다.

### 2. Redis의 만료 처리 방식

Redis는 만료된 키를 두 가지 방식으로 처리한다.

**지연 삭제(Lazy Expiration)**
클라이언트가 키에 접근할 때 비로소 만료 여부를 확인하고 삭제한다. CPU 효율적이지만, 접근이 없는 키는 메모리에 계속 남는다.

**주기적 삭제(Active Expiration)**
Redis는 100ms마다 만료된 키를 샘플링하여 삭제한다. 기본적으로 `hz` 설정값(기본 10)에 따라 초당 실행 빈도가 결정된다.

```bash
# redis.conf
hz 10  # 초당 10회 백그라운드 작업 실행 (기본값)
# 만료 키가 많다면 hz를 높일 수 있지만, CPU 사용률 증가에 주의
hz 20
```

이 구조로 인해, TTL이 설정된 키라도 즉시 메모리에서 해제된다는 보장이 없다는 점을 이해해야 한다.

### 3. maxmemory-policy 옵션 비교

| 정책 | 설명 | 적합한 사용 사례 |
|---|---|---|
| `noeviction` | 메모리 초과 시 에러 반환 | 데이터 손실이 절대 안 되는 경우 |
| `allkeys-lru` | 전체 키 중 LRU 기준 삭제 | 일반적인 캐시 용도 |
| `volatile-lru` | TTL 있는 키 중 LRU 기준 삭제 | 캐시와 영구 데이터 혼용 |
| `allkeys-lfu` | 전체 키 중 LFU 기준 삭제 | 접근 빈도 편차가 큰 경우 |
| `volatile-lfu` | TTL 있는 키 중 LFU 기준 삭제 | 위와 같되 영구 데이터 보호 필요 시 |
| `volatile-ttl` | TTL이 짧은 키 우선 삭제 | TTL 기반으로 중요도를 명시한 경우 |
| `allkeys-random` | 무작위 삭제 | 접근 패턴이 균일한 경우 |

## 실전 예제

### Spring Boot에서 Redis TTL 전략 적용

```java
@Configuration
@EnableCaching
public class RedisCacheConfig {

    @Bean
    public RedisCacheManager cacheManager(RedisConnectionFactory connectionFactory) {
        // 기본 TTL 설정
        RedisCacheConfiguration defaultConfig = RedisCacheConfiguration.defaultCacheConfig()
                .entryTtl(Duration.ofMinutes(30))
                .serializeKeysWith(
                    RedisSerializationContext.SerializationPair.fromSerializer(new StringRedisSerializer()))
                .serializeValuesWith(
                    RedisSerializationContext.SerializationPair.fromSerializer(new GenericJackson2JsonRedisSerializer()))
                .disableCachingNullValues();

        // 캐시 용도별 TTL 개별 설정
        Map<String, RedisCacheConfiguration> cacheConfigurations = new HashMap<>();
        
        // 사용자 세션: 2시간
        cacheConfigurations.put("userSession",
                defaultConfig.entryTtl(Duration.ofHours(2)));
        
        // 상품 정보: 10분 (변경 빈도 높음)
        cacheConfigurations.put("productInfo",
                defaultConfig.entryTtl(Duration.ofMinutes(10)));
        
        // 공지사항: 1일 (변경 빈도 낮음)
        cacheConfigurations.put("notice",
                defaultConfig.entryTtl(Duration.ofDays(1)));

        return RedisCacheManager.builder(connectionFactory)
                .cacheDefaults(defaultConfig)
                .withInitialCacheConfigurations(cacheConfigurations)
                .build();
    }
}
```

### TTL Jitter 적용으로 Cache Stampede 방지

동일한 TTL을 가진 키가 대량으로 동시에 만료되면 캐시 스탬피드(Cache Stampede) 현상이 발생한다. 약간의 무작위 편차(Jitter)를 추가하는 것이 효과적이다.

```java
@Component
public class CacheService {

    private final RedisTemplate<String, Object> redisTemplate;
    private final Random random = new Random();

    public CacheService(RedisTemplate<String, Object> redisTemplate) {
        this.redisTemplate = redisTemplate;
    }

    /**
     * 기본 TTL에 ±10% 범위의 jitter를 추가하여 저장
     */
    public void setWithJitter(String key, Object value, Duration baseTtl) {
        long baseSeconds = baseTtl.getSeconds();
        // ±10% 범위의 jitter 적용
        long jitter = (long) (baseSeconds * 0.1 * (random.nextDouble() * 2 - 1));
        long finalTtl = baseSeconds + jitter;

        redisTemplate.opsForValue().set(key, value, Duration.ofSeconds(finalTtl));
    }

    /**
     * 논리적 만료 시간을 값에 포함시켜 Soft TTL 구현
     * 실제 Redis TTL보다 먼저 갱신 로직을 트리거
     */
    public void setWithSoftExpiry(String key, Object value,
                                   Duration softTtl, Duration hardTtl) {
        Map<String, Object> wrapper = new HashMap<>();
        wrapper.put("data", value);
        wrapper.put("expireAt", Instant.now().plus(softTtl).toEpochMilli());

        redisTemplate.opsForValue().set(key, wrapper, hardTtl);
    }
}
```

### 메모리 효율적인 자료구조 선택

Redis는 작은 크기의 컬렉션에 대해 내부적으로 압축된 인코딩(ziplist, listpack 등)을 사용한다. 이 임계값을 적절히 조정하면 상당한 메모리 절감이 가능하다.

```bash
# redis.conf - 소규모 Hash 압축 인코딩 임계값
hash-max-listpack-entries 128   # 기본값: 128
hash-max-listpack-value 64      # 기본값: 64 (bytes)

# 소규모 ZSet 압축
zset-max-listpack-entries 128
zset-max-listpack-value 64

# 소규모 List 압축
list-max-listpack-size -2       # 최대 8kb per listpack node
```

```java
// 개별 String 키 대신 Hash를 사용한 메모리 절감 예시
// 나쁜 예: 사용자 필드마다 별도 키 사용
// user:1001:name, user:1001:email, user:1001:age → 키 오버헤드 3배

// 좋은 예: Hash로 묶어서 저장
@Service
public class UserCacheService {

    private final RedisTemplate<String, String> redisTemplate;

    public void cacheUser(Long userId, UserDto user) {
        String key = "user:" + userId;
        Map<String, String> userMap = new HashMap<>();
        userMap.put("name", user.getName());
        userMap.put("email", user.getEmail());
        userMap.put("age", String.valueOf(user.getAge()));

        redisTemplate.opsForHash().putAll(key, userMap);
        redisTemplate.expire(key, Duration.ofHours(1));
    }

    public UserDto getUser(Long userId) {
        String key = "user:" + userId;
        Map<Object, Object> entries = redisTemplate.opsForHash().entries(key);
        if (entries.isEmpty()) return null;

        return UserDto.builder()
                .name((String) entries.get("name"))
                .email((String) entries.get("email"))
                .age(Integer.parseInt((String) entries.get("age")))
                .build();
    }
}
```

### 메모리 사용량 모니터링

```bash
# 전체 메모리 현황
127.0.0.1:6379> INFO memory

# 주요 지표
# used_memory: 실제 사용 중인 메모리
# used_memory_rss: OS가 Redis에 할당한 메모리 (단편화 포함)
# mem_fragmentation_ratio: 단편화 비율 (1.0~1.5가 정상, 1.5 초과 시 주의)
# maxmemory_human: 설정된 최대 메모리

# 키 패턴별 메모리 분석 (redis-cli --bigkeys)
redis-cli --bigkeys

# 특정 키의 메모리 사용량 확인
127.0.0.1:6379> MEMORY USAGE user:1001
(integer) 184  # bytes

# 만료 예정 키 통계
127.0.0.1:6379> INFO keyspace
# db0:keys=10234,expires=8192,avg_ttl=85400
```

```java
// Spring Actuator + Micrometer로 Redis 메모리 메트릭 수집
@Component
public class RedisMemoryMetrics {

    private final RedisTemplate<String, Object> redisTemplate;
    private final MeterRegistry meterRegistry;

    @Scheduled(fixedDelay = 60000)
    public void collectMemoryMetrics() {
        Properties info = redisTemplate.getConnectionFactory()
                .getConnection()
                .serverCommands()
                .info("memory");

        double usedMemory = Double.parseDouble(info.getProperty("used_memory"));
        double fragmentationRatio = Double.parseDouble(
                info.getProperty("mem_fragmentation_ratio"));

        Gauge.builder("redis.memory.used", () -> usedMemory)
                .description("Redis used memory in bytes")
                .register(meterRegistry);

        Gauge.builder("redis.memory.fragmentation.ratio", () -> fragmentationRatio)
                .description("Redis memory fragmentation ratio")
                .register(meterRegistry);
    }
}
```

## 주의사항 및 트레이드오프

### 1. TTL이 없는 키의 위험성

운영 초기에는 메모리가 충분해 보여도, TTL 없이 쌓이는 키는 시간이 지날수록 치명적인 문제가 된다. 가능하면 모든 캐시 키에 TTL을 의무화하고, 코드 리뷰 단계에서 이를 체크하는 것이 좋다. `noeviction` 정책을 사용한다면 TTL 없는 키는 더욱 위험하다.

### 2. `volatile-lru` vs `allkeys-lru` 선택

Redis에 캐시 데이터와 영구 데이터를 함께 저장하고 있다면 `volatile-lru`가 안전하다. 그러나 현실적으로는 **Redis 인스턴스를 용도별로 분리**하는 것이 더 나은 선택이다. 캐시용 Redis는 `allkeys-lru`로 운영하고, 세션이나 영구 데이터는 별도 인스턴스를 사용한다.

### 3. `hz` 값과 CPU 트레이드오프

만료 키가 많은 환경에서 `hz`를 높이면(예: 20~100) 삭제 지연은 줄어들지만 CPU 사용률이 증가한다. Redis 4.0 이후에는 `dynamic-hz yes`로 설정하면 클라이언트 연결 수에 따라 hz를 동적으로 조정한다.

### 4. 메모리 단편화(Fragmentation) 관리

`mem_fragmentation_ratio`가 1.5를 넘으면 단편화가 심각한 수준이다. Redis 4.0 이상에서는 `activedefrag yes` 옵션으로 온라인 조각 모음을 활성화할 수 있다.

```bash
# redis.conf
activedefrag yes
active-defrag-ignore-bytes 100mb   # 단편화 100mb 이상 시 활성화
active-defrag-enabled yes
active-defrag-threshold-lower 10   # 단편화율 10% 이상 시 시작
active-defrag-threshold-upper 100  # 단편화율 100% 도달 시 최대 노력
```

### 5. SCAN을 활용한 안전한 키 관리

`KEYS *` 명령은 프로덕션에서 절대 사용하면 안 된다. Redis는 싱글 스레드로 동작하므로 대규모 키 목록 조회 시 서비스가 블로킹된다. 대신 `SCAN`을 사용한다.

```java
// KEYS * 대신 SCAN 사용
public Set<String> scanKeys(String pattern) {
    Set<String> keys = new HashSet<>();
    ScanOptions options = ScanOptions.scanOptions()
            .match(pattern)
            .count(100)  // 한 번에 처리할 키 수 힌트
            .build();

    try (Cursor<byte[]> cursor = redisTemplate.getConnectionFactory()
            .getConnection()
            .keyCommands()
            .scan(options)) {
        while (cursor.hasNext()) {
            keys.add(new String(cursor.next()));
        }
    }
    return keys;
}
```

## 정리

Redis 메모리 최적화는 단일 설정 하나로 해결되는 문제가 아니다. 아래 체크리스트를 기반으로 체계적으로 접근해야 한다.

| 항목 | 권장 사항 |
|---|---|
| TTL 설정 | 모든 캐시 키에 TTL 의무화, Jitter 적용 |
| 축출 정책 | 용도별 인스턴스 분리 후 `allkeys-lru` 또는 `allkeys-lfu` 적용 |
| 자료구조 | 가능하면 Hash로 묶어 키 오버헤드 절감 |
| 단편화 | `activedefrag yes` 활성화, fragmentation ratio 모니터링 |
| 키 조회 | `KEYS *` 금지, `SCAN` 사용 |
| 모니터링 | `INFO memory`, `MEMORY USAGE`, Micrometer 메트릭 수집 |

메모리 최적화는 성능과 비용의 균형을 맞추는 과정이다. 데이터의 접근 패턴, 비즈니스 중요도, 갱신 빈도를 분석하여 TTL과 축출 정책을 설계하고, 운영 중에도 지속적으로 메트릭을 관찰하며 튜닝하는 습관을 갖는 것이 중요하다.
