# Rust 언어가 시스템 프로그래밍에서 주목받는 이유

## 개요

2023년 Stack Overflow 개발자 설문에서 Rust는 8년 연속 "가장 사랑받는 프로그래밍 언어" 1위를 차지했다. Microsoft, Google, Amazon, Meta뿐만 아니라 Linux 커널마저 Rust를 공식 개발 언어로 채택하기 시작했다. 단순한 유행이 아니다. C/C++가 수십 년간 독점해온 시스템 프로그래밍 영역에서 Rust는 명확한 기술적 우위를 증명하고 있다.

백엔드 개발자 입장에서도 Rust는 무관하지 않다. WebAssembly, CLI 도구, 고성능 네트워크 서버, 임베디드 시스템 등 그 영역이 빠르게 확장되고 있으며, JVM 기반 언어로는 해결하기 어려운 메모리 효율과 지연 시간(latency) 문제를 Rust로 해결하는 사례가 늘고 있다. 이 글에서는 Rust가 왜 시스템 프로그래밍에서 주목받는지, 핵심 개념과 실전 예제를 통해 중급 이상의 개발자 관점에서 깊이 있게 살펴본다.

---

## 핵심 개념

### 1. 소유권(Ownership)과 빌림(Borrowing) — 가비지 컬렉터 없는 메모리 안전성

Rust의 가장 혁신적인 특징은 **GC(Garbage Collector) 없이 메모리 안전성을 보장**한다는 점이다. 이를 가능하게 하는 것이 바로 소유권 시스템이다.

- **소유권(Ownership)**: 각 값은 단 하나의 소유자(owner)를 가진다. 소유자가 스코프를 벗어나면 값은 자동으로 해제된다.
- **빌림(Borrowing)**: 소유권을 이전하지 않고 참조(`&`)를 통해 값에 접근할 수 있다. 불변 참조는 여러 개 허용되지만, 가변 참조(`&mut`)는 동시에 하나만 존재할 수 있다.
- **생명주기(Lifetime)**: 참조가 유효한 범위를 컴파일러가 추적하여 댕글링 포인터(dangling pointer)를 원천 차단한다.

이 규칙들은 모두 **컴파일 타임에 강제**된다. 런타임 오버헤드가 없다.

### 2. 제로 코스트 추상화(Zero-Cost Abstraction)

C++가 표방하는 원칙이지만 Rust는 이를 더 엄격하게 구현한다. 고수준의 추상화(Iterator, trait 등)를 사용해도 직접 작성한 저수준 코드와 동일한 성능을 낸다. 컴파일러가 런타임 비용 없이 최적화한다.

### 3. 두려움 없는 동시성(Fearless Concurrency)

소유권 시스템은 동시성 문제도 컴파일 타임에 잡아낸다. 데이터 레이스(data race)는 Rust에서 컴파일 자체가 되지 않는다. `Send`와 `Sync` trait을 통해 스레드 간 데이터 공유의 안전성을 타입 시스템으로 보장한다.

### 4. 에러 처리 — `Result`와 `Option`

Null 포인터 예외나 암묵적 예외 전파 대신, Rust는 `Result<T, E>`와 `Option<T>`를 통해 에러를 타입 시스템에 녹인다. `?` 연산자로 간결하게 에러를 전파할 수 있어 Java의 checked exception보다 훨씬 실용적이다.

## 실전 예제

### 예제 1: 소유권과 빌림 기본

```rust
fn main() {
    let s1 = String::from("hello");
    
    // s1의 소유권이 s2로 이동(move). 이후 s1은 사용 불가.
    let s2 = s1;
    // println!("{}", s1); // 컴파일 에러: value moved here
    
    let s3 = String::from("world");
    
    // 소유권 이전 없이 불변 참조로 빌림
    let len = calculate_length(&s3);
    println!("'{}' 의 길이: {}", s3, len); // s3 여전히 유효
}

fn calculate_length(s: &String) -> usize {
    s.len()
} // s는 참조이므로 여기서 값이 해제되지 않음
```

### 예제 2: 고성능 멀티스레드 HTTP 서버 (tokio + hyper)

실무에서 Rust로 고성능 네트워크 서버를 구축하는 대표적인 패턴이다.

```rust
use std::convert::Infallible;
use std::net::SocketAddr;

use hyper::service::{make_service_fn, service_fn};
use hyper::{Body, Request, Response, Server};

async fn handle_request(req: Request<Body>) -> Result<Response<Body>, Infallible> {
    let path = req.uri().path().to_owned();
    
    let response = match path.as_str() {
        "/health" => Response::builder()
            .status(200)
            .header("Content-Type", "application/json")
            .body(Body::from(r#"{"status":"ok"}"#))
            .unwrap(),
        "/echo" => {
            let body_bytes = hyper::body::to_bytes(req.into_body()).await.unwrap();
            Response::new(Body::from(body_bytes))
        }
        _ => Response::builder()
            .status(404)
            .body(Body::from("Not Found"))
            .unwrap(),
    };
    
    Ok(response)
}

#[tokio::main]
async fn main() {
    let addr = SocketAddr::from(([0, 0, 0, 0], 8080));
    
    let make_svc = make_service_fn(|_conn| async {
        Ok::<_, Infallible>(service_fn(handle_request))
    });
    
    let server = Server::bind(&addr).serve(make_svc);
    
    println!("서버 시작: http://{}", addr);
    
    if let Err(e) = server.await {
        eprintln!("서버 에러: {}", e);
    }
}
```

```toml
# Cargo.toml
[dependencies]
hyper = { version = "0.14", features = ["full"] }
tokio = { version = "1", features = ["full"] }
```

이 서버는 Spring Boot의 Tomcat 내장 서버 대비 메모리 사용량이 수십 배 적고, 초기 기동 시간이 수십 밀리초 수준이다.

### 예제 3: 데이터 레이스 없는 멀티스레딩

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    // Arc: 여러 스레드에서 안전하게 참조 카운팅
    // Mutex: 내부 가변성을 안전하게 제공
    let counter = Arc::new(Mutex::new(0u64));
    let mut handles = vec![];

    for _ in 0..10 {
        let counter_clone = Arc::clone(&counter);
        let handle = thread::spawn(move || {
            let mut num = counter_clone.lock().unwrap();
            *num += 1;
        }); // lock은 스코프를 벗어나면 자동 해제
        handles.push(handle);
    }

    for handle in handles {
        handle.join().unwrap();
    }

    println!("최종 카운터 값: {}", *counter.lock().unwrap()); // 항상 10
}
```

Java에서 `synchronized` 키워드를 빠뜨리거나 `volatile` 처리를 실수하면 런타임에서야 발견되는 문제들이, Rust에서는 컴파일 타임에 차단된다.

### 예제 4: `Result`를 활용한 에러 처리

```rust
use std::fs;
use std::num::ParseIntError;

#[derive(Debug)]
enum AppError {
    IoError(std::io::Error),
    ParseError(ParseIntError),
}

impl From<std::io::Error> for AppError {
    fn from(e: std::io::Error) -> Self {
        AppError::IoError(e)
    }
}

impl From<ParseIntError> for AppError {
    fn from(e: ParseIntError) -> Self {
        AppError::ParseError(e)
    }
}

fn read_and_parse(path: &str) -> Result<i32, AppError> {
    // ?  연산자: 에러 발생 시 From 변환 후 즉시 반환
    let content = fs::read_to_string(path)?;
    let number: i32 = content.trim().parse()?;
    Ok(number * 2)
}

fn main() {
    match read_and_parse("number.txt") {
        Ok(value) => println!("계산 결과: {}", value),
        Err(AppError::IoError(e)) => eprintln!("파일 읽기 오류: {}", e),
        Err(AppError::ParseError(e)) => eprintln!("파싱 오류: {}", e),
    }
}
```

## 주의사항 및 트레이드오프

### 1. 가파른 학습 곡선

소유권, 빌림, 생명주기 개념은 기존 언어 사용자에게 낯설다. 특히 Java/Spring에 익숙한 백엔드 개발자라면 "왜 이게 컴파일이 안 되지?"라는 상황을 수없이 겪게 된다. **초기 생산성은 확실히 낮다.** 팀 전체가 Rust를 도입하려면 충분한 러닝 커브 기간을 감안해야 한다.

### 2. 빌드 시간

Rust의 컴파일러(`rustc`)는 매우 많은 분석을 컴파일 타임에 수행하기 때문에, 대형 프로젝트에서 빌드 시간이 상당히 길어질 수 있다. `cargo check`를 통한 빠른 문법 검사, `sccache` 등의 빌드 캐시 도구 활용이 필수적이다.

### 3. 생태계 성숙도

Rust의 생태계는 빠르게 성장하고 있지만, Java/Python 대비 아직 성숙하지 않은 영역이 존재한다. 특히 ORM, 엔터프라이즈 수준의 프레임워크는 Spring 생태계와 비교하기 어렵다. `sqlx`, `Diesel`, `Axum`, `Actix-web` 등 주요 라이브러리들이 있지만, 레퍼런스와 커뮤니티 지원은 여전히 성장 중이다.

### 4. Unsafe 코드의 위험

성능을 극한으로 끌어올리거나 외부 C 라이브러리와 FFI(Foreign Function Interface)를 통해 통신할 때 `unsafe` 블록을 사용한다. `unsafe`는 Rust의 메모리 안전 보장을 개발자가 직접 책임지겠다는 선언이므로, 최소한으로 사용하고 철저히 문서화해야 한다.

```rust
// unsafe 사용 예시 — 반드시 정당한 이유가 있을 때만
unsafe {
    let raw_ptr = 0x12345usize as *const i32;
    // 이 포인터가 유효한지 Rust는 보장하지 않는다
    // 개발자가 직접 책임져야 함
    // let value = *raw_ptr; // 잘못된 주소라면 세그멘테이션 폴트
}
```

### 5. 모든 문제의 해답이 아니다

Rust는 성능과 안전성이 동시에 중요한 시스템 레이어에 최적화되어 있다. 비즈니스 로직이 복잡하고 빠른 프로토타이핑이 필요한 애플리케이션 레이어에서는 여전히 Java, Kotlin, Python이 더 적합할 수 있다. **도구는 문제에 맞게 선택해야 한다.**

## 정리

Rust가 시스템 프로그래밍에서 주목받는 이유를 한 줄로 요약하면 다음과 같다.

> **"C/C++의 성능과 제어권, 그리고 현대 언어의 안전성과 생산성을 동시에 제공하는 유일한 언어"**

| 항목 | C/C++ | Java/JVM | Rust |
|---|---|---|---|
| 메모리 관리 | 수동 (위험) | GC (편하지만 지연 발생) | 소유권 (자동+안전) |
| 성능 | 최고 | GC 오버헤드 있음 | C/C++ 수준 |
| 메모리 안전 | 보장 안 됨 | 보장 | 컴파일 타임 보장 |
| 동시성 안전 | 보장 안 됨 | 런타임 감지 | 컴파일 타임 보장 |
| 학습 곡선 | 높음 | 낮음 | 매우 높음 |

백엔드 개발자 관점에서 Rust를 지금 당장 주 언어로 바꿀 필요는 없다. 그러나 **고성능 CLI 도구, 사이드카 프록시, WebAssembly 모듈, 레이턴시에 민감한 마이크로서비스** 등 특정 컴포넌트를 Rust로 구현하는 시도는 충분히 실용적이다.

Rust를 배우는 과정에서 소유권과 메모리 모델을 깊이 이해하게 되면, Java 애플리케이션의 GC 튜닝이나 JVM 메모리 구조를 바라보는 시각도 달라진다. 언어 하나를 배우는 것 이상의 가치가 있다. 지금이 Rust를 시작하기 좋은 시점이다.
