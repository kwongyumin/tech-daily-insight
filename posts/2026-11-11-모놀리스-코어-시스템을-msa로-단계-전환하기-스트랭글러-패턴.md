# 모놀리스 코어 시스템을 MSA로 단계 전환하기 (스트랭글러 패턴)

## 개요

레거시 모놀리스 시스템을 운영하면서 "지금 당장 MSA로 전환하고 싶지만, 서비스를 멈출 수 없다"는 딜레마를 겪어본 개발자라면 이 글이 반가울 것이다.

빅뱅(Big Bang) 방식의 전면 재작성은 대규모 프로젝트에서 대부분 실패한다. 개발 기간이 예측 불가능하게 늘어나고, 기존 비즈니스 로직의 미묘한 동작을 모두 복원하기가 사실상 불가능에 가깝다. 현실에서는 신규 기능 개발과 마이그레이션을 동시에 진행해야 하고, 서비스 다운타임은 허용되지 않는다.

이런 상황에서 **스트랭글러 무화과 패턴(Strangler Fig Pattern)**은 현실적인 해법이 된다. 오래된 나무를 무화과 덩굴이 천천히 감아 올라가 결국 대체하는 것처럼, 모놀리스를 조금씩 감싸며 대체하는 접근 방식이다. 이 글에서는 이 패턴의 핵심 개념부터 Spring Boot 기반의 실전 구현 예제, 그리고 실무에서 반드시 고려해야 할 트레이드오프까지 단계적으로 살펴본다.

## 핵심 개념

### 스트랭글러 패턴이란?

마틴 파울러(Martin Fowler)가 제안한 이 패턴의 핵심은 다음 세 단계로 요약된다.

1. **식별(Identify)**: 모놀리스에서 독립적으로 분리 가능한 도메인 경계(Bounded Context)를 찾는다.
2. **공존(Coexist)**: 새로운 마이크로서비스를 모놀리스와 병렬로 배포하고, 라우팅 레이어에서 트래픽을 점진적으로 전환한다.
3. **제거(Remove)**: 충분한 검증 후 모놀리스의 해당 코드를 제거한다.

핵심은 **라우팅 파사드(Routing Facade)** 또는 **API Gateway**가 중간에서 요청을 중재한다는 점이다. 클라이언트는 변경을 인식하지 못하고, 내부적으로 점진적인 이전이 이루어진다.

```
[Client]
    │
    ▼
[API Gateway / Facade]
    ├── /orders/** → 신규 Order Service (MSA)
    ├── /users/**  → 신규 User Service (MSA)
    └── /**        → 레거시 모놀리스 (점진적 축소)
```

### 도메인 경계 식별 전략

분리 순서를 결정할 때는 다음 기준을 활용한다.

- **변경 빈도**: 자주 변경되는 도메인을 먼저 분리하면 릴리즈 주기를 단축할 수 있다.
- **팀 소유권**: 명확한 담당 팀이 있는 도메인은 경계가 이미 존재한다.
- **결합도**: 다른 도메인과 의존 관계가 적은 도메인부터 시작한다 (Leaf Node 우선).
- **데이터 소유권**: 특정 테이블을 단일 도메인이 거의 독점적으로 사용하는 경우 분리 비용이 낮다.

## 실전 예제

### 시나리오

주문, 상품, 사용자, 결제가 하나의 모놀리스에 묶여 있는 커머스 시스템을 가정한다. 이중 **주문(Order)** 도메인부터 먼저 분리한다.

### 1단계: API Gateway 라우팅 설정 (Spring Cloud Gateway)

```yaml
# application.yml - API Gateway
spring:
  cloud:
    gateway:
      routes:
        # 신규 Order Service로 라우팅
        - id: order-service
          uri: lb://order-service
          predicates:
            - Path=/api/v1/orders/**
          filters:
            - name: CircuitBreaker
              args:
                name: orderServiceCB
                fallbackUri: forward:/fallback/orders

        # 나머지는 모놀리스로 라우팅
        - id: monolith
          uri: http://monolith-service:8080
          predicates:
            - Path=/**
```

이 설정만으로 `/api/v1/orders/**` 경로는 새 서비스로, 나머지는 모놀리스로 흘러간다. 클라이언트 코드는 전혀 변경되지 않는다.

### 2단계: 신규 Order Service 구현

```java
// OrderController.java
@RestController
@RequestMapping("/api/v1/orders")
@RequiredArgsConstructor
public class OrderController {

    private final OrderService orderService;

    @PostMapping
    public ResponseEntity<OrderResponse> createOrder(
            @RequestBody @Valid CreateOrderRequest request,
            @RequestHeader("X-User-Id") Long userId) {
        OrderResponse response = orderService.createOrder(userId, request);
        return ResponseEntity.status(HttpStatus.CREATED).body(response);
    }

    @GetMapping("/{orderId}")
    public ResponseEntity<OrderResponse> getOrder(@PathVariable Long orderId) {
        return ResponseEntity.ok(orderService.getOrder(orderId));
    }
}
```

```java
// OrderService.java
@Service
@RequiredArgsConstructor
@Transactional
public class OrderService {

    private final OrderRepository orderRepository;
    private final ProductClient productClient;   // 모놀리스 or 상품 서비스 호출
    private final EventPublisher eventPublisher;

    public OrderResponse createOrder(Long userId, CreateOrderRequest request) {
        // 상품 재고 확인 (아직 모놀리스에 존재하는 경우 Feign Client로 호출)
        ProductInfo product = productClient.getProduct(request.getProductId());

        if (product.getStock() < request.getQuantity()) {
            throw new InsufficientStockException("재고 부족");
        }

        Order order = Order.builder()
                .userId(userId)
                .productId(request.getProductId())
                .quantity(request.getQuantity())
                .totalPrice(product.getPrice() * request.getQuantity())
                .status(OrderStatus.PENDING)
                .build();

        Order saved = orderRepository.save(order);

        // 이벤트 발행으로 모놀리스와 느슨한 결합 유지
        eventPublisher.publish(new OrderCreatedEvent(saved.getId(), userId, request.getProductId()));

        return OrderResponse.from(saved);
    }
}
```

### 3단계: 모놀리스와의 데이터 동기화 처리

분리 초기에는 모놀리스와 신규 서비스가 같은 데이터를 참조해야 하는 상황이 반드시 발생한다. 이를 위한 전략은 두 가지다.

**전략 A: 공유 DB (단기 허용)**

마이그레이션 초기에는 같은 DB를 바라보되, 스키마 소유권을 명확히 한다. Order 서비스만 `orders` 테이블에 Write하고, 모놀리스는 Read-only로 접근한다.

```java
// 모놀리스의 OrderRepository를 Read-only 전용으로 변경
@Repository
public interface LegacyOrderRepository extends JpaRepository<Order, Long> {

    // 모놀리스에서는 조회만 허용, 쓰기는 신규 서비스가 담당
    @Query("SELECT o FROM Order o WHERE o.userId = :userId")
    List<Order> findByUserId(@Param("userId") Long userId);
}
```

**전략 B: 이벤트 기반 동기화 (중장기)**

```java
// Order Service - Kafka 이벤트 발행
@Component
@RequiredArgsConstructor
public class OrderEventPublisher {

    private final KafkaTemplate<String, Object> kafkaTemplate;

    public void publishOrderCreated(Order order) {
        OrderCreatedEvent event = new OrderCreatedEvent(
            order.getId(),
            order.getUserId(),
            order.getProductId(),
            order.getTotalPrice(),
            Instant.now()
        );
        kafkaTemplate.send("order.created", String.valueOf(order.getId()), event);
    }
}

// 모놀리스 - 이벤트 구독하여 자체 캐시 갱신
@KafkaListener(topics = "order.created", groupId = "monolith-group")
public void handleOrderCreated(OrderCreatedEvent event) {
    // 모놀리스 내부 주문 현황 동기화 (예: 통계, 알림 등)
    orderSummaryRepository.updateSummary(event.getUserId(), event.getTotalPrice());
}
```

### 4단계: 카나리 배포로 점진적 트래픽 전환

```yaml
# Spring Cloud Gateway - 가중치 기반 라우팅
spring:
  cloud:
    gateway:
      routes:
        - id: order-service-canary
          uri: lb://order-service
          predicates:
            - Path=/api/v1/orders/**
            - Weight=order-group, 20   # 20% 트래픽만 신규 서비스로

        - id: order-monolith
          uri: http://monolith-service:8080
          predicates:
            - Path=/api/v1/orders/**
            - Weight=order-group, 80   # 80%는 모놀리스 유지
```

20% → 50% → 100% 순으로 트래픽을 늘리면서 오류율, 응답 시간, 비즈니스 지표를 모니터링한다. 문제가 생기면 즉시 롤백이 가능하다.

## 주의사항 및 트레이드오프

### 분산 트랜잭션 문제

모놀리스에서는 하나의 트랜잭션으로 처리하던 작업이 MSA에서는 여러 서비스에 걸쳐진다. 예를 들어 주문 생성 → 재고 차감 → 결제 승인이 각각 다른 서비스에 존재한다면, 중간 단계 실패 시 데이터 정합성을 보장해야 한다.

이를 위해 **Saga 패턴**을 함께 적용해야 한다. Choreography(이벤트 기반) 또는 Orchestration(중앙 조율) 방식 중 도메인 복잡도에 따라 선택한다. 보상 트랜잭션(Compensating Transaction)을 처음부터 설계해두지 않으면 나중에 큰 부채가 된다.

### 공유 DB는 반드시 한시적으로만

공유 DB는 단기 편의를 위한 타협이다. 장기간 유지하면 서비스 간 결합도가 DB 레벨에서 고착화된다. 한쪽에서 스키마를 변경하면 다른 서비스가 깨지는 상황이 반복된다. **DB 분리 타임라인을 처음부터 명시적으로 계획**해야 한다.

### 운영 복잡도 증가

서비스가 늘어날수록 배포 파이프라인, 모니터링, 로그 추적, 서비스 디스커버리 등의 운영 부담이 급격히 증가한다. 최소한 아래 요소는 MSA 도입 초기부터 준비해야 한다.

| 항목 | 도구 예시 |
|------|-----------|
| 분산 추적 | Zipkin, Jaeger |
| 중앙 로깅 | ELK Stack, Loki |
| 메트릭 수집 | Prometheus + Grafana |
| 서비스 디스커버리 | Eureka, Consul |
| 설정 중앙화 | Spring Cloud Config, Vault |

### 팀 구조와 Conway의 법칙

마이크로서비스 경계는 결국 팀의 커뮤니케이션 구조를 반영한다. 도메인 경계가 팀 경계와 맞지 않으면 서비스 분리 후에도 과도한 협업 오버헤드가 발생한다. 기술 전환 이전에 팀 소유권(Team Ownership)을 먼저 정의하는 것이 중요하다.

### 언제 MSA가 오히려 독이 되는가?

- 팀 규모가 작아 서비스별 독립 운영 비용을 감당하기 어려운 경우
- 도메인 경계가 아직 불명확하고 비즈니스 모델이 자주 바뀌는 초기 스타트업
- 네트워크 레이턴시가 중요한 실시간 처리 시스템에서 불필요한 서비스 간 호출이 증가하는 경우

## 정리

스트랭글러 패턴은 **멈추지 않고 달리는 기차의 선로를 교체하는** 작업과 같다. 성공적인 전환을 위한 핵심 원칙을 정리하면 다음과 같다.

1. **작게 시작하라**: 가장 독립적인 도메인부터 분리하고, 성공 패턴을 학습한다.
2. **라우팅 파사드를 먼저 구축하라**: API Gateway가 없으면 점진적 전환 자체가 불가능하다.
3. **공유 DB는 임시 수단임을 명심하라**: 반드시 분리 계획을 세운다.
4. **이벤트로 결합도를 낮춰라**: 동기 호출 의존성이 많을수록 모놀리스와 다를 바 없다.
5. **관찰 가능성(Observability)을 처음부터 갖춰라**: 분산 시스템에서 디버깅은 가시성이 전부다.
6. **팀 구조를 함께 바꿔라**: 기술만 바꾸고 조직이 그대로라면 전환 효과가 반감된다.

MSA 전환은 기술 프로젝트이기 이전에 **조직과 문화의 변화**다. 스트랭글러 패턴은 이 긴 여정에서 리스크를 최소화하면서 현실적으로 나아갈 수 있는 가장 검증된 경로를 제공한다.
