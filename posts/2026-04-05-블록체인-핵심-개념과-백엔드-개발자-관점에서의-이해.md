# 블록체인 핵심 개념과 백엔드 개발자 관점에서의 이해

## 개요

백엔드 개발자로 일하다 보면 "블록체인을 도입해보자"는 이야기를 한 번쯤 들어봤을 것이다. 하지만 막상 깊이 파고들면 암호화폐 이야기만 나오거나, 반대로 지나치게 추상적인 개념 설명에 그치는 경우가 많다.

이 포스팅은 **이미 분산 시스템, 데이터베이스, 네트워크를 다뤄본 백엔드 개발자**를 대상으로 블록체인의 핵심 개념을 재해석한다. "이건 결국 어떤 자료구조고, 어떤 네트워크 모델이며, 어떤 트레이드오프를 감수하는 기술인가?"라는 시각으로 접근할 것이다.

---

## 핵심 개념

### 1. 블록체인은 특수한 형태의 분산 데이터베이스다

가장 먼저 머릿속에 박아둬야 할 것이 있다. 블록체인은 결국 **append-only, 분산, 합의 기반의 데이터 저장소**다. RDBMS나 NoSQL과 비교하면 아래와 같다.

| 속성 | RDBMS | NoSQL (예: Cassandra) | 블록체인 |
|---|---|---|---|
| 데이터 변경 | UPDATE/DELETE 가능 | UPDATE 가능 | append-only (불변) |
| 일관성 모델 | ACID | Eventually Consistent | 합의 알고리즘에 따라 다름 |
| 신뢰 모델 | 중앙 서버 신뢰 | 클러스터 내 신뢰 | Trustless (수학적 검증) |
| TPS | 수만~수십만 | 수만 | 수십~수천 (체인에 따라 다름) |

블록체인의 핵심 가치는 **중앙 관리자 없이도 데이터의 무결성과 신뢰를 보장**한다는 점이다. 이것이 필요 없다면 블록체인은 오히려 과도한 선택이다.

### 2. 블록의 구조: 링크드 리스트 + 해시 체인

블록은 본질적으로 **해시로 연결된 링크드 리스트**다. 각 블록은 이전 블록의 해시값을 포함하기 때문에, 중간 블록 하나만 수정해도 이후 모든 블록의 해시가 깨진다.

```java
// 블록 구조를 Java로 모델링
import java.security.MessageDigest;
import java.nio.charset.StandardCharsets;
import java.time.Instant;
import java.util.List;

public class Block {
    private final int index;
    private final long timestamp;
    private final List<String> transactions;
    private final String previousHash;
    private final int nonce;
    private final String hash;

    public Block(int index, List<String> transactions, String previousHash) {
        this.index = index;
        this.timestamp = Instant.now().toEpochMilli();
        this.transactions = transactions;
        this.previousHash = previousHash;
        this.nonce = 0;
        this.hash = calculateHash();
    }

    public String calculateHash() {
        String data = index + timestamp + transactions.toString() + previousHash + nonce;
        return sha256(data);
    }

    private String sha256(String input) {
        try {
            MessageDigest digest = MessageDigest.getInstance("SHA-256");
            byte[] hashBytes = digest.digest(input.getBytes(StandardCharsets.UTF_8));
            StringBuilder hexString = new StringBuilder();
            for (byte b : hashBytes) {
                hexString.append(String.format("%02x", b));
            }
            return hexString.toString();
        } catch (Exception e) {
            throw new RuntimeException("SHA-256 계산 실패", e);
        }
    }
}
```

### 3. 합의 알고리즘: 분산 시스템의 Byzantine Fault Tolerance

백엔드 개발자라면 CAP 정리를 알 것이다. 블록체인도 결국 분산 시스템이므로 CAP에서 자유롭지 않다. 주요 합의 알고리즘을 비교하면:

**Proof of Work (PoW)**
- 계산 경쟁으로 블록 생성 권한 획득
- 51% 공격에 대한 경제적 방어
- 에너지 소비가 극단적으로 높음
- Bitcoin, (과거의) Ethereum

**Proof of Stake (PoS)**
- 지분(stake) 기반으로 검증자 선출
- PoW 대비 에너지 효율적
- 부자가 더 많은 검증 권한 → 중앙화 우려
- Ethereum (Merge 이후), Cardano

**PBFT (Practical Byzantine Fault Tolerance)**
- 허가형(Permissioned) 네트워크에서 주로 사용
- 노드 수가 적을 때 빠른 합의 가능
- Hyperledger Fabric

엔터프라이즈 환경에서는 대부분 **허가형 블록체인(Permissioned Blockchain)** 을 사용하며, 이 경우 합의 알고리즘의 복잡도가 낮아지고 성능이 크게 향상된다.

### 4. 스마트 컨트랙트: 블록체인 위에서 실행되는 비즈니스 로직

스마트 컨트랙트는 "코드가 곧 계약"이다. 블록체인 위에 배포된 코드는 조건이 충족되면 자동으로 실행되며, 수정이 불가능하다.

```solidity
// Solidity로 작성한 간단한 에스크로 컨트랙트
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

contract Escrow {
    address public buyer;
    address public seller;
    address public arbiter;
    uint public amount;
    bool public isCompleted;

    constructor(address _seller, address _arbiter) payable {
        buyer = msg.sender;
        seller = _seller;
        arbiter = _arbiter;
        amount = msg.value;
        isCompleted = false;
    }

    // 구매자 또는 중재자가 거래 완료 승인
    function confirmDelivery() external {
        require(
            msg.sender == buyer || msg.sender == arbiter,
            "권한 없음"
        );
        require(!isCompleted, "이미 완료된 거래");
        
        isCompleted = true;
        payable(seller).transfer(amount);
    }

    // 중재자가 환불 처리
    function refund() external {
        require(msg.sender == arbiter, "중재자만 환불 가능");
        require(!isCompleted, "이미 완료된 거래");

        isCompleted = true;
        payable(buyer).transfer(amount);
    }
}
```

## 실전 예제: Spring Boot에서 이더리움 블록체인 연동

실무에서는 직접 블록체인 노드를 구현하기보다 **기존 네트워크에 연결하여 트랜잭션을 읽고 쓰는** 작업이 대부분이다. Java/Spring 환경에서는 `web3j` 라이브러리가 표준이다.

### 의존성 추가

```gradle
// build.gradle
dependencies {
    implementation 'org.web3j:core:4.9.8'
    implementation 'org.springframework.boot:spring-boot-starter-web'
}
```

### Web3j 설정 및 블록체인 서비스

```java
@Configuration
public class Web3jConfig {

    @Value("${blockchain.node.url}")
    private String nodeUrl;

    @Bean
    public Web3j web3j() {
        // Infura, Alchemy 등의 노드 프로바이더 또는 자체 노드 연결
        return Web3j.build(new HttpService(nodeUrl));
    }
}

@Service
@RequiredArgsConstructor
@Slf4j
public class BlockchainService {

    private final Web3j web3j;

    // 특정 주소의 ETH 잔액 조회
    public BigDecimal getBalance(String address) {
        try {
            EthGetBalance balance = web3j
                .ethGetBalance(address, DefaultBlockParameterName.LATEST)
                .send();
            
            return Convert.fromWei(
                balance.getBalance().toString(), 
                Convert.Unit.ETHER
            );
        } catch (IOException e) {
            log.error("잔액 조회 실패: address={}", address, e);
            throw new BlockchainException("잔액 조회 중 오류 발생", e);
        }
    }

    // 트랜잭션 해시로 트랜잭션 정보 조회
    public Optional<Transaction> getTransaction(String txHash) {
        try {
            EthTransaction ethTransaction = web3j
                .ethGetTransactionByHash(txHash)
                .send();
            return ethTransaction.getTransaction();
        } catch (IOException e) {
            log.error("트랜잭션 조회 실패: txHash={}", txHash, e);
            throw new BlockchainException("트랜잭션 조회 중 오류 발생", e);
        }
    }

    // 새 블록 이벤트 구독 (Reactive)
    public Disposable subscribeToNewBlocks(Consumer<EthBlock> blockHandler) {
        return web3j.blockFlowable(false)
            .subscribe(
                blockHandler::accept,
                error -> log.error("블록 구독 오류", error)
            );
    }
}
```

### 트랜잭션 상태를 추적하는 이벤트 리스너

```java
@Component
@RequiredArgsConstructor
@Slf4j
public class BlockchainEventListener implements ApplicationRunner {

    private final Web3j web3j;
    private final PaymentService paymentService;

    @Override
    public void run(ApplicationArguments args) {
        // 특정 컨트랙트 주소의 이벤트 구독
        String contractAddress = "0xYourContractAddress";

        web3j.ethLogFlowable(buildFilter(contractAddress))
            .subscribe(
                log -> processLog(log),
                error -> log.error("이벤트 구독 오류", error)
            );
    }

    private EthFilter buildFilter(String contractAddress) {
        EthFilter filter = new EthFilter(
            DefaultBlockParameterName.LATEST,
            DefaultBlockParameterName.LATEST,
            contractAddress
        );
        // Transfer 이벤트 토픽 필터
        filter.addSingleTopic(EventEncoder.encode(
            new Event("Transfer",
                Arrays.asList(
                    new TypeReference<Address>() {},
                    new TypeReference<Address>() {},
                    new TypeReference<Uint256>() {}
                ))
        ));
        return filter;
    }

    private void processLog(Log eventLog) {
        log.info("이벤트 감지: txHash={}, blockNumber={}",
            eventLog.getTransactionHash(),
            eventLog.getBlockNumber());
        // DB 업데이트, 알림 발송 등 비즈니스 로직 처리
        paymentService.confirmPayment(eventLog.getTransactionHash());
    }
}
```

## 주의사항 및 트레이드오프

### 1. 블록 최종성(Finality) 문제

RDBMS에서 커밋된 트랜잭션은 즉시 확정된다. 하지만 블록체인에서는 **블록이 충분히 쌓여야 최종 확정**으로 볼 수 있다. 이더리움의 경우 12~15 블록 확인을 기다리는 게 일반적이다.

```java
// 트랜잭션 확인 수 체크
public boolean isTransactionConfirmed(String txHash, int requiredConfirmations) 
        throws IOException {
    
    EthTransaction tx = web3j.ethGetTransactionByHash(txHash).send();
    if (tx.getTransaction().isEmpty()) return false;
    
    BigInteger txBlockNumber = tx.getTransaction().get().getBlockNumber();
    BigInteger currentBlock = web3j.ethBlockNumber().send().getBlockNumber();
    
    long confirmations = currentBlock.subtract(txBlockNumber).longValue();
    return confirmations >= requiredConfirmations;
}
```

### 2. 가스비와 트랜잭션 실패

이더리움 네트워크에서 트랜잭션은 실패해도 **가스비는 소진**된다. 비즈니스 로직상 트랜잭션 실패를 반드시 핸들링해야 한다.

```java
// 트랜잭션 영수증으로 성공/실패 판별
public boolean isTransactionSuccessful(String txHash) throws IOException {
    EthGetTransactionReceipt receipt = web3j
        .ethGetTransactionReceipt(txHash)
        .send();
    
    return receipt.getTransactionReceipt()
        .map(r -> "0x1".equals(r.getStatus()))  // status: 0x1 = 성공, 0x0 = 실패
        .orElse(false);
}
```

### 3. 언제 블록체인을 쓰지 말아야 하는가

블록체인 도입을 검토할 때 다음 조건을 먼저 확인하라:

- **중앙 관리자가 있어도 되는가?** → 있어도 된다면 블록체인 불필요
- **데이터 수정이 필요한가?** → append-only 제약이 비즈니스에 맞지 않을 수 있음
- **성능이 중요한가?** → TPS가 낮고 레이턴시가 높음
- **참여자들 간의 신뢰가 이미 있는가?** → 블록체인의 가치가 희석됨

단순히 "데이터를 안전하게 저장하고 싶다"는 요구라면 **HSM(Hardware Security Module)** 이나 **감사 로그(Audit Log)** 가 더 현실적인 선택이다.

## 정리

백엔드 개발자 관점에서 블록체인을 정리하면 다음과 같다.

| 개념 | 백엔드 관점에서의 해석 |
|---|---|
| 블록 | 해시로 연결된 링크드 리스트의 노드 |
| 합의 알고리즘 | 분산 시스템의 리더 선출 + Byzantine Fault Tolerance |
| 스마트 컨트랙트 | 블록체인 위에서 실행되는 서버리스 함수 |
| 트랜잭션 | DB 트랜잭션과 유사하나, 비동기·최종성 보장 방식이 다름 |
| 퍼블릭 블록체인 | 허가 없는 완전 분산 네트워크 |
| 프라이빗 블록체인 | 허가형 분산 원장, 엔터프라이즈 적합 |

블록체인은 **중앙 기관 없이 불특정 다수가 신뢰를 형성해야 하는 문제**를 해결하는 기술이다. 이 문제가 실제로 존재하는 도메인에서만 도입을 고려하라. 나머지 경우에는 검증된 분산 데이터베이스, 메시지 큐, 이벤트 소싱 아키텍처로 충분히 해결할 수 있다.

실무에서 블록체인과 연동할 일이 생긴다면 `web3j`(Java), `ethers.js`(Node.js), 또는 Hyperledger Fabric SDK를 사용하게 될 것이다. 핵심은 블록체인 노드를 완전히 이해하기보다, **내 서비스가 노드와 어떻게 안전하게 통신하고 이벤트를 처리할 것인가**를 설계하는 것이다.
