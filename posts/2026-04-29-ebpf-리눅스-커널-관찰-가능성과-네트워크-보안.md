# eBPF 리눅스 커널 관찰 가능성과 네트워크 보안

## 개요

커널 수준에서 시스템을 관찰하고 제어한다는 것은 한때 커널 모듈을 직접 작성하거나 커스텀 패치를 적용해야 하는 매우 위험하고 복잡한 작업이었습니다. 그러나 **eBPF(Extended Berkeley Packet Filter)** 의 등장으로 이 패러다임이 완전히 바뀌었습니다.

eBPF는 커널 소스를 수정하거나 커널 모듈을 로드하지 않고도, 커널 내부에서 안전하게 샌드박스된 프로그램을 실행할 수 있게 해주는 혁명적인 기술입니다. Cilium, Falco, Pixie, Tetragon 등의 도구가 eBPF를 기반으로 등장하면서, 쿠버네티스 네트워킹, 보안 관찰, 성능 프로파일링 분야에서 사실상 표준으로 자리잡고 있습니다.

이 글에서는 eBPF의 핵심 아키텍처를 살펴보고, 실제 네트워크 패킷 필터링과 시스템 콜 추적 예제를 통해 실무에서 어떻게 활용할 수 있는지 깊이 다뤄보겠습니다.

## 핵심 개념

### eBPF 아키텍처

eBPF 프로그램은 다음과 같은 라이프사이클을 거칩니다.

```
사용자 공간 코드 (C/Python/Go/Rust)
        ↓
   LLVM/Clang 컴파일
        ↓
    eBPF 바이트코드
        ↓
   커널 Verifier (안전성 검증)
        ↓
   JIT 컴파일 (네이티브 코드)
        ↓
  커널 훅 포인트에 Attach
```

커널 Verifier는 무한 루프, 메모리 경계 위반, 인증되지 않은 포인터 역참조 등을 사전에 차단하여 시스템 안정성을 보장합니다.

### 주요 훅 포인트

| 훅 타입 | 용도 |
|---|---|
| `kprobe/kretprobe` | 커널 함수 진입/반환 추적 |
| `tracepoint` | 정적으로 정의된 커널 이벤트 |
| `XDP (eXpress Data Path)` | 네트워크 드라이버 레벨 패킷 처리 |
| `TC (Traffic Control)` | 네트워크 스케줄러 레벨 훅 |
| `LSM (Linux Security Module)` | 보안 정책 강제 |
| `uprobe` | 사용자 공간 함수 추적 |

### eBPF Maps

eBPF 프로그램은 커널-사용자 공간 간 데이터 공유를 위해 **Maps**를 사용합니다. Hash, Array, Ring Buffer, LRU Hash 등 다양한 타입이 있으며, 이를 통해 실시간으로 수집된 데이터를 사용자 공간으로 전달합니다.

## 실전 예제

### 예제 1: BCC를 이용한 네트워크 연결 추적

`bcc(BPF Compiler Collection)`는 Python으로 eBPF 프로그램을 작성하기 가장 쉬운 도구입니다. 아래는 TCP 연결 이벤트를 실시간으로 추적하는 예제입니다.

```python
#!/usr/bin/env python3
# tcp_tracer.py - TCP 연결 이벤트 추적

from bcc import BPF
import socket
import struct

# eBPF C 코드 (커널 공간에서 실행)
bpf_program = """
#include <uapi/linux/ptrace.h>
#include <net/sock.h>
#include <bcc/proto.h>

// 이벤트 데이터 구조체
struct tcp_event_t {
    u32 pid;
    u32 saddr;
    u32 daddr;
    u16 dport;
    char comm[TASK_COMM_LEN];
};

// Ring Buffer Map - 사용자 공간으로 이벤트 전달
BPF_RINGBUF_OUTPUT(events, 1 << 4);

// tcp_v4_connect 커널 함수 반환 시점 훅
int trace_tcp_connect(struct pt_regs *ctx, struct sock *sk) {
    if (sk->__sk_common.skc_family != AF_INET)
        return 0;

    struct tcp_event_t event = {};
    event.pid = bpf_get_current_pid_tgid() >> 32;
    event.saddr = sk->__sk_common.skc_rcv_saddr;
    event.daddr = sk->__sk_common.skc_daddr;
    event.dport = sk->__sk_common.skc_dport;
    bpf_get_current_comm(&event.comm, sizeof(event.comm));

    events.ringbuf_output(&event, sizeof(event), 0);
    return 0;
}
"""

b = BPF(text=bpf_program)
b.attach_kretprobe(event="tcp_v4_connect", fn_name="trace_tcp_connect")

print(f"{'PID':<8} {'COMM':<16} {'SRC':<16} {'DST':<16} {'DPORT':<8}")

def print_event(cpu, data, size):
    event = b["events"].event(data)
    src_ip = socket.inet_ntoa(struct.pack("I", event.saddr))
    dst_ip = socket.inet_ntoa(struct.pack("I", event.daddr))
    dport = socket.ntohs(event.dport)
    comm = event.comm.decode('utf-8', 'replace')
    print(f"{event.pid:<8} {comm:<16} {src_ip:<16} {dst_ip:<16} {dport:<8}")

b["events"].open_ring_buffer(print_event)

try:
    while True:
        b.ring_buffer_poll()
except KeyboardInterrupt:
    print("\n추적 종료")
```

### 예제 2: XDP를 활용한 고성능 DDoS 방어

XDP는 네트워크 드라이버 레벨에서 동작하여 커널 네트워크 스택을 거치기 전에 패킷을 처리합니다. 초당 수천만 패킷을 처리할 수 있어 DDoS 방어에 매우 효과적입니다.

```c
// xdp_ddos_filter.c
#include <linux/bpf.h>
#include <linux/if_ether.h>
#include <linux/ip.h>
#include <linux/tcp.h>
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_endian.h>

// 차단할 IP 주소를 저장하는 HashMap
struct {
    __uint(type, BPF_MAP_TYPE_HASH);
    __uint(max_entries, 10000);
    __type(key, __u32);    // IP 주소
    __type(value, __u64);  // 차단 타임스탬프
} blocked_ips SEC(".maps");

// 패킷 카운터
struct {
    __uint(type, BPF_MAP_TYPE_PERCPU_ARRAY);
    __uint(max_entries, 2);
    __type(key, __u32);
    __type(value, __u64);
} pkt_counter SEC(".maps");

SEC("xdp")
int xdp_ddos_filter(struct xdp_md *ctx) {
    void *data     = (void *)(long)ctx->data;
    void *data_end = (void *)(long)ctx->data_end;

    // 이더넷 헤더 파싱
    struct ethhdr *eth = data;
    if ((void *)(eth + 1) > data_end)
        return XDP_PASS;

    if (eth->h_proto != bpf_htons(ETH_P_IP))
        return XDP_PASS;

    // IP 헤더 파싱
    struct iphdr *ip = (void *)(eth + 1);
    if ((void *)(ip + 1) > data_end)
        return XDP_PASS;

    __u32 src_ip = ip->saddr;

    // 차단 목록 확인
    __u64 *blocked = bpf_map_lookup_elem(&blocked_ips, &src_ip);
    if (blocked) {
        // 패킷 드롭 카운터 증가
        __u32 key = 1;
        __u64 *counter = bpf_map_lookup_elem(&pkt_counter, &key);
        if (counter)
            __sync_fetch_and_add(counter, 1);

        return XDP_DROP;  // 커널 스택 도달 전에 즉시 드롭
    }

    // 정상 패킷 카운터
    __u32 key = 0;
    __u64 *counter = bpf_map_lookup_elem(&pkt_counter, &key);
    if (counter)
        __sync_fetch_and_add(counter, 1);

    return XDP_PASS;
}

char LICENSE[] SEC("license") = "GPL";
```

XDP 프로그램 로드 및 차단 IP 관리:

```bash
# XDP 프로그램 컴파일
clang -O2 -g -target bpf \
  -I/usr/include/$(uname -m)-linux-gnu \
  -c xdp_ddos_filter.c \
  -o xdp_ddos_filter.o

# 네트워크 인터페이스에 XDP 프로그램 연결 (Native 모드)
ip link set dev eth0 xdp obj xdp_ddos_filter.o sec xdp

# 특정 IP 차단 (bpftool 활용)
bpftool map update pinned /sys/fs/bpf/blocked_ips \
  key hex $(python3 -c "import socket,struct; print(struct.pack('I', socket.inet_aton('192.168.1.100')[0]).hex())") \
  value hex 0000000000000001

# 패킷 카운터 확인
bpftool map dump pinned /sys/fs/bpf/pkt_counter

# XDP 프로그램 제거
ip link set dev eth0 xdp off
```

### 예제 3: Tetragon을 활용한 런타임 보안 정책

Cilium의 Tetragon은 eBPF 기반의 쿠버네티스 런타임 보안 도구입니다. 아래는 특정 바이너리 실행을 감지하고 차단하는 TracingPolicy 예제입니다.

```yaml
# tetragon-policy.yaml
apiVersion: cilium.io/v1alpha1
kind: TracingPolicy
metadata:
  name: "detect-crypto-miner"
spec:
  kprobes:
  - call: "sys_execve"
    syscall: true
    args:
    - index: 0
      type: "string"
    selectors:
    # 알려진 크립토 마이너 바이너리 실행 감지
    - matchArgs:
      - index: 0
        operator: "Postfix"
        values:
        - "/xmrig"
        - "/minerd"
        - "/cryptonight"
      matchActions:
      - action: Sigkill  # 즉시 프로세스 종료
  
  # 의심스러운 네트워크 연결 감지
  - call: "tcp_connect"
    syscall: false
    args:
    - index: 0
      type: "sock"
    selectors:
    - matchArgs:
      - index: 0
        operator: "DPort"
        values:
        - "3333"   # Monero 마이닝 풀
        - "14444"
        - "45700"
      matchActions:
      - action: Sigkill
```

## 주의사항 및 트레이드오프

### 1. 커널 버전 의존성

eBPF 기능은 커널 버전에 따라 크게 다릅니다. BTF(BPF Type Format)와 CO-RE(Compile Once - Run Everywhere)는 커널 5.2 이상에서 지원됩니다. 프로덕션 환경에서 구버전 커널을 사용하는 경우 기능 제약이 심각할 수 있습니다.

```bash
# 커널 버전 및 eBPF 기능 확인
uname -r
bpftool feature probe kernel

# BTF 지원 여부 확인
ls /sys/kernel/btf/vmlinux
```

### 2. Verifier 제약과 복잡도

eBPF Verifier는 프로그램 복잡도에 엄격한 제한을 둡니다. 기본적으로 명령어 수 100만 개, 스택 크기 512바이트로 제한됩니다. 복잡한 로직을 구현하려면 Tail Call이나 BPF-to-BPF 함수 호출로 분리해야 합니다.

### 3. 성능 오버헤드

XDP의 경우 거의 제로에 가까운 오버헤드를 보이지만, kprobe 기반 추적은 핫 패스(Hot Path)에 연결할 경우 의미 있는 성능 저하를 유발할 수 있습니다. 특히 고빈도 시스템 콜(read, write)에 kprobe를 걸면 10~30% 처리량 저하가 발생할 수 있습니다.

```
성능 특성 비교:
XDP Native    : ~25M pps (패킷/초) - 최고 성능
XDP Generic   : ~3M pps - 커널 스택 이후 처리
TC BPF        : ~2M pps - 소켓 레벨 처리
iptables      : ~1M pps - 비교 기준
```

### 4. 보안 고려사항

eBPF 프로그램 로드는 기본적으로 `CAP_BPF` 또는 `CAP_SYS_ADMIN` 권한이 필요합니다. 이 권한이 컨테이너에 부여되면 전체 호스트 시스템을 관찰할 수 있어 사이드카 컨테이너의 권한 관리에 각별한 주의가 필요합니다. 또한, `unprivileged_bpf_disabled` 커널 파라미터를 활성화하여 일반 사용자의 eBPF 사용을 제한하는 것을 권장합니다.

```bash
# 비권한 eBPF 비활성화 (보안 강화)
sysctl -w kernel.unprivileged_bpf_disabled=1
echo "kernel.unprivileged_bpf_disabled=1" >> /etc/sysctl.conf
```

### 5. 디버깅과 관찰 가능성 도구 선택

실무에서는 직접 eBPF를 작성하기보다 목적에 맞는 도구를 선택하는 것이 효율적입니다.

| 목적 | 권장 도구 |
|---|---|
| 쿠버네티스 CNI + 보안 | Cilium |
| 런타임 보안 감지 | Tetragon, Falco |
| 성능 프로파일링 | bpftrace, perf |
| 애플리케이션 관찰 | Pixie, Parca |
| 빠른 프로토타이핑 | BCC, bpftrace |
| 프로덕션 eBPF 개발 | libbpf + CO-RE |

## 정리

eBPF는 단순한 네트워크 필터 도구를 넘어, 현대 클라우드 네이티브 인프라에서 **관찰 가능성(Observability)**, **네트워크 성능**, **보안 강제(Security Enforcement)** 를 아우르는 핵심 기반 기술로 자리잡았습니다.

백엔드 개발자 관점에서 주목할 포인트는 다음과 같습니다:

- **서비스 메시 대체**: Cilium은 eBPF를 통해 Envoy 사이드카 없이도 L7 네트워크 정책을 구현하여 레이턴시와 리소스 사용을 크게 줄입니다.
- **제로 인스트루먼테이션 APM**: Pixie, Odigos 같은 도구는 코드 수정 없이 HTTP, gRPC, DB 쿼리를 자동으로 추적합니다.
- **공급망 보안**: Tetragon의 LSM 훅을 통해 컨테이너가 허가되지 않은 시스템 콜이나 파일 접근을 시도할 때 즉각 차단할 수 있습니다.

eBPF 생태계는 현재도 빠르게 성숙하고 있으며, 리눅스 커널에 대한 깊은 이해 없이도 `bpftrace`나 Tetragon의 선언적 정책만으로도 강력한 보안과 관찰 가능성을 구현할 수 있게 되었습니다. 인프라 레벨의 문제를 애플리케이션 코드로 해결하려 했던 많은 문제들이 eBPF로 더 우아하게 해결되는 시대가 열리고 있습니다.
