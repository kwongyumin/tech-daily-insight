# IDC와 퍼블릭 클라우드를 묶는 하이브리드 클라우드 설계

## 개요

온프레미스 IDC(Internet Data Center)에 이미 상당한 투자가 이뤄진 조직이라면, 퍼블릭 클라우드로의 완전 전환(All-in Cloud)보다는 두 환경을 함께 운영하는 **하이브리드 클라우드**를 선택하는 경우가 많다. 규제 준수, 데이터 주권, 레거시 시스템 의존성, TCO(총 소유 비용) 등 복합적인 이유가 얽혀 있다.

하지만 하이브리드 클라우드는 단순히 IDC와 클라우드를 VPN으로 연결하는 것이 아니다. 네트워크 토폴로지 설계, 서비스 디스커버리, 보안 경계, 데이터 동기화 전략 등 고려해야 할 요소가 훨씬 많다. 이 글에서는 실무에서 하이브리드 클라우드를 설계할 때 반드시 짚어야 할 핵심 개념과 실전 예제를 중심으로 살펴본다.

---

## 핵심 개념

### 1. 연결 방식 선택: VPN vs. 전용선(Direct Connect)

IDC와 퍼블릭 클라우드를 연결하는 첫 번째 결정은 **연결 매체**다.

| 구분 | IPSec VPN | 전용선 (AWS Direct Connect / Azure ExpressRoute) |
|------|-----------|--------------------------------------------------|
| 비용 | 낮음 | 높음 (월 수백만 원~) |
| 대역폭 | 제한적 (보통 1Gbps 이하) | 1~100Gbps |
| 지연 시간 | 가변적 (인터넷 경유) | 안정적, 낮음 |
| 가용성 | 단일 경로 위험 | SLA 기반 보장 |
| 적합 사례 | 소규모, DR용, 개발/테스트 | 대용량 데이터 이동, 프로덕션 하이브리드 |

**실무 팁**: 전용선 단독으로만 연결하면 전용선 장애 시 고립되므로, 전용선 + VPN을 Active/Standby 구성으로 함께 운영하는 것이 일반적이다.

### 2. 네트워크 주소 체계 설계

IDC와 클라우드의 VPC/VNet이 IP 대역이 겹치면 라우팅 문제가 발생한다. 처음부터 **전사 IP 주소 계획(IP Address Management, IPAM)**을 세워야 한다.

```
IDC        : 10.0.0.0/8  (예: 10.0.x.x ~ 10.127.x.x)
AWS VPC    : 172.16.0.0/12 (예: 172.16.x.x ~ 172.31.x.x)
Azure VNet : 192.168.0.0/16
```

> CIDR 충돌이 발생하면 NAT로 우회할 수 있지만, 운영 복잡도가 급증한다. 처음부터 겹치지 않게 설계하는 것이 최선이다.

### 3. 서비스 디스커버리와 DNS 전략

하이브리드 환경에서 서비스 간 통신은 IP가 아닌 **DNS 이름**을 기반으로 해야 한다. 환경에 따라 IP가 바뀌기 때문이다.

권장 패턴:
- **Split-horizon DNS**: 같은 도메인이지만 IDC 내부에서는 IDC 내부 IP를, 클라우드 내부에서는 클라우드 IP를 반환
- **중앙 DNS 포워더**: Route 53 Resolver Endpoint(AWS) 또는 Azure Private DNS Resolver를 사용해 양방향 쿼리 위임

## 실전 예제

### 예제 1: Terraform으로 AWS와 IDC를 잇는 Site-to-Site VPN 구성

```hcl
# IDC 쪽 외부 IP (예: 203.0.113.10)
variable "on_premise_public_ip" {
  default = "203.0.113.10"
}

# Customer Gateway: IDC VPN 장비 등록
resource "aws_customer_gateway" "idc_cgw" {
  bgp_asn    = 65000
  ip_address = var.on_premise_public_ip
  type       = "ipsec.1"

  tags = {
    Name = "idc-customer-gateway"
  }
}

# Virtual Private Gateway: AWS VPC 쪽 엔드포인트
resource "aws_vpn_gateway" "vgw" {
  vpc_id = aws_vpc.main.id

  tags = {
    Name = "hybrid-vgw"
  }
}

# Site-to-Site VPN 연결
resource "aws_vpn_connection" "idc_to_aws" {
  vpn_gateway_id      = aws_vpn_gateway.vgw.id
  customer_gateway_id = aws_customer_gateway.idc_cgw.id
  type                = "ipsec.1"
  static_routes_only  = false  # BGP 사용

  tags = {
    Name = "idc-to-aws-vpn"
  }
}

# IDC 대역 라우팅 전파 활성화
resource "aws_vpn_gateway_route_propagation" "main" {
  vpn_gateway_id = aws_vpn_gateway.vgw.id
  route_table_id = aws_route_table.private.id
}
```

### 예제 2: AWS Route 53 Resolver로 양방향 DNS 조회 구현

```hcl
# IDC → AWS: IDC에서 aws.internal 도메인 쿼리 시 Route 53으로 포워딩
resource "aws_route53_resolver_endpoint" "inbound" {
  name      = "hybrid-inbound-resolver"
  direction = "INBOUND"

  security_group_ids = [aws_security_group.resolver_sg.id]

  ip_address {
    subnet_id = aws_subnet.private_a.id
  }

  ip_address {
    subnet_id = aws_subnet.private_b.id
  }
}

# AWS → IDC: AWS에서 corp.internal 도메인 쿼리 시 IDC DNS로 포워딩
resource "aws_route53_resolver_endpoint" "outbound" {
  name      = "hybrid-outbound-resolver"
  direction = "OUTBOUND"

  security_group_ids = [aws_security_group.resolver_sg.id]

  ip_address {
    subnet_id = aws_subnet.private_a.id
  }

  ip_address {
    subnet_id = aws_subnet.private_b.id
  }
}

resource "aws_route53_resolver_rule" "idc_dns" {
  domain_name          = "corp.internal"
  name                 = "forward-to-idc-dns"
  rule_type            = "FORWARD"
  resolver_endpoint_id = aws_route53_resolver_endpoint.outbound.id

  target_ip {
    ip   = "10.0.1.53"  # IDC 내부 DNS 서버
    port = 53
  }
}
```

### 예제 3: Spring Boot 애플리케이션에서 하이브리드 환경 인식

하이브리드 환경에서는 애플리케이션이 **어느 환경에서 실행되는지**에 따라 다른 엔드포인트를 사용해야 하는 경우가 있다. Spring의 Profile과 환경 변수를 활용한다.

```yaml
# application-idc.yml (IDC 환경)
datasource:
  primary:
    url: jdbc:postgresql://db-primary.corp.internal:5432/appdb
    username: ${DB_USER}
    password: ${DB_PASS}

storage:
  type: on-premise
  nfs:
    path: /mnt/nfs/data

message-queue:
  broker-url: tcp://mq.corp.internal:61616

# application-cloud.yml (클라우드 환경)
datasource:
  primary:
    url: jdbc:postgresql://${RDS_ENDPOINT}:5432/appdb
    username: ${DB_USER}
    password: ${DB_PASS}

storage:
  type: s3
  bucket: my-app-bucket
  region: ap-northeast-2

message-queue:
  broker-url: ${SQS_ENDPOINT}
```

```java
@Configuration
public class StorageConfig {

    @Value("${storage.type}")
    private String storageType;

    @Bean
    public StorageService storageService(
            @Autowired(required = false) S3Client s3Client,
            @Autowired(required = false) NfsProperties nfsProperties) {

        return switch (storageType) {
            case "s3"         -> new S3StorageService(s3Client);
            case "on-premise" -> new NfsStorageService(nfsProperties);
            default -> throw new IllegalStateException(
                "Unknown storage type: " + storageType);
        };
    }
}
```

```java
// 클라우드 버스트 시 작업 큐 라우팅 예시
@Service
@RequiredArgsConstructor
public class WorkloadRouter {

    private final MetricsCollector metricsCollector;
    private final IdcJobQueue     idcQueue;
    private final CloudJobQueue   cloudQueue;

    // IDC 부하가 임계치를 넘으면 클라우드로 오버플로우
    private static final double BURST_THRESHOLD = 0.80;

    public void dispatch(Job job) {
        double idcUtilization = metricsCollector.getIdcCpuUtilization();

        if (idcUtilization < BURST_THRESHOLD) {
            idcQueue.enqueue(job);
            log.info("Job {} dispatched to IDC (utilization={})",
                     job.getId(), idcUtilization);
        } else {
            cloudQueue.enqueue(job);
            log.info("Job {} burst to Cloud (utilization={})",
                     job.getId(), idcUtilization);
        }
    }
}
```

## 주의사항 및 트레이드오프

### ⚠️ 레이턴시 비대칭 문제

IDC와 클라우드 간 왕복 지연(RTT)은 일반적으로 수 ms~수십 ms가 발생한다. 이 경우 **동기 호출 체인**이 IDC↔클라우드 경계를 넘으면 응답 시간이 급격히 나빠진다.

**해결 방향**:
- 경계를 넘는 호출은 가능한 **비동기(메시지 큐, 이벤트)**로 처리
- 자주 조회하는 IDC 데이터는 클라우드 쪽에 **캐싱 레이어(Redis, CDN)** 구성
- 서비스 경계를 IDC 또는 클라우드 중 한 곳에 완결되도록 설계(채터링 최소화)

### ⚠️ 보안 경계 명확화

하이브리드 환경에서는 보안 정책이 두 환경에 걸쳐 일관되게 적용되어야 한다.

- **제로 트러스트** 원칙 적용: 내부망이라도 mTLS 또는 서비스 메시(Istio, Linkerd)로 인증
- **보안 그룹 / 방화벽 규칙 최소 권한**: 필요한 포트/IP만 허용, 화이트리스트 방식
- **비밀 관리 통합**: AWS Secrets Manager ↔ HashiCorp Vault를 연동하거나 한쪽으로 통합
- 클라우드 IAM 역할과 IDC LDAP/AD 계정 체계를 **연합(Federation)** 해 단일 인증 기반 유지

### ⚠️ 데이터 중력(Data Gravity)과 Egress 비용

데이터가 많을수록 클라우드 외부로 꺼낼 때 발생하는 **Egress 요금**이 상당하다. 클라우드에서 IDC로 대용량 데이터를 지속적으로 보내는 아키텍처는 비용 폭탄의 원인이 된다.

- **원칙**: 데이터를 소비하는 컴퓨팅을 데이터가 있는 곳 근처에 배치
- 클라우드 → IDC 방향의 대량 데이터 전송은 Direct Connect로 Egress 절감
- 아키텍처 검토 시 **데이터 흐름 다이어그램(DFD)**과 함께 비용 시뮬레이션 선행

### ⚠️ 운영 복잡도 증가

단일 환경보다 모니터링, 배포 파이프라인, 장애 대응 모두 복잡해진다.

- **통합 관측성(Observability)**: Prometheus + Grafana를 IDC와 클라우드 모두에 배포하거나, 클라우드 중앙 수집소(예: Amazon Managed Grafana)로 메트릭 집계
- **단일 CI/CD 파이프라인**: GitOps(ArgoCD, Flux)로 멀티 클러스터 배포를 단일 소스에서 관리
- **런북(Runbook) 명확화**: IDC와 클라우드 각각의 장애 시나리오, 페일오버 절차를 문서화

## 정리

하이브리드 클라우드는 "IDC도 쓰고 클라우드도 쓰자"는 단순한 발상이지만, 실제 구현은 네트워크·보안·데이터·운영 각 레이어에서 세밀한 설계를 요구한다. 핵심 원칙을 다시 정리하면 다음과 같다.

1. **연결 매체부터 결정**: 용량과 가용성 요구사항에 따라 VPN/전용선을 선택하고, 반드시 이중화 구성
2. **IP 주소와 DNS를 먼저 설계**: 나중에 고치면 전체 트래픽 경로를 재설계해야 한다
3. **경계를 넘는 동기 호출을 최소화**: 비동기 메시징과 캐싱으로 레이턴시 영향 차단
4. **제로 트러스트 보안 적용**: 내부망 신뢰 가정을 버리고, 모든 서비스 간 인증·암호화 적용
5. **Egress 비용 선행 계산**: 아키텍처 결정 전 데이터 흐름과 비용을 시뮬레이션
6. **운영 통합 관측성**: 두 환경을 하나의 대시보드에서 볼 수 있어야 장애 시 빠른 대응이 가능

하이브리드 클라우드가 복잡하게 느껴지는 이유는 두 세계의 추상화 수준이 다르기 때문이다. IDC는 물리 장비와 네트워크를 직접 다루고, 클라우드는 API로 추상화된 리소스를 다룬다. 이 간극을 Terraform, Ansible 같은 **IaC(Infrastructure as Code)** 도구로 코드 레벨에서 통일하는 것이 운영 복잡도를 낮추는 가장 현실적인 접근이다.
