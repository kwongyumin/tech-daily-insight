# 해외 브로커 연동 서비스의 장애 격리와 안정화

## 개요

해외 브로커와 연동하는 서비스를 운영하다 보면 국내 시스템과는 다른 차원의 도전에 직면하게 된다. 네트워크 레이턴시, 외부 브로커의 예고 없는 점검, API 스펙 변경, 그리고 타임존 차이로 인한 운영 공백까지 — 통제하기 어려운 변수들이 훨씬 많다.

문제는 이런 외부 의존성이 하나라도 흔들리면 그 여파가 고스란히 사용자 경험으로 번진다는 점이다. 특히 금융·트레이딩 도메인처럼 실시간성이 중요한 서비스라면 외부 브로커의 장애가 주문 처리 실패, 잔고 불일치, 최악의 경우 자산 손실로 이어질 수 있다.

이 글에서는 해외 브로커 연동 서비스에서 반드시 고려해야 할 **장애 격리 패턴**과 **안정화 전략**을 실전 예제와 함께 정리한다. Circuit Breaker, Bulkhead, Fallback, 멱등성 처리, 비동기 큐 버퍼링까지 실무에서 바로 적용할 수 있는 수준으로 다룬다.

## 핵심 개념

### 1. 외부 브로커 연동의 장애 유형

해외 브로커 연동에서 발생하는 장애는 크게 세 가지로 분류할 수 있다.

| 유형 | 설명 | 영향 |
|------|------|------|
| **완전 단절** | 브로커 API 자체가 응답 불가 | 전체 기능 중단 |
| **지연 증가** | 응답은 오지만 수 초~수십 초 소요 | 스레드 고갈, 연쇄 장애 |
| **부분 오류** | 특정 엔드포인트만 오류 반환 | 조용한 데이터 불일치 |

가장 위험한 건 "지연 증가" 유형이다. 완전 단절은 빠르게 감지되지만, 응답이 느리게라도 오는 경우 타임아웃 설정이 없으면 스레드 풀이 조용히 소진되어 서비스 전체가 영향을 받는다.

### 2. 핵심 패턴 요약

- **Circuit Breaker**: 오류율이 임계치를 넘으면 즉시 차단하여 연쇄 장애 방지
- **Bulkhead**: 브로커별 스레드/커넥션 풀을 격리하여 한 브로커 장애가 다른 브로커에 전파되지 않도록 차단
- **Retry with Backoff**: 일시적 오류에 대한 지수 백오프 재시도
- **Fallback**: 브로커 응답 불가 시 캐시 데이터 또는 기본값 반환
- **Idempotency Key**: 재시도 시 중복 주문/처리 방지

### 의존성 설정

### Circuit Breaker + Bulkhead 설정

```yaml
# application.yml
resilience4j:
  circuitbreaker:
    instances:
      brokerA:
        sliding-window-size: 20
        failure-rate-threshold: 50
        wait-duration-in-open-state: 30s
        permitted-number-of-calls-in-half-open-state: 5
        slow-call-duration-threshold: 3s
        slow-call-rate-threshold: 80
      brokerB:
        sliding-window-size: 20
        failure-rate-threshold: 50
        wait-duration-in-open-state: 60s

  bulkhead:
    instances:
      brokerA:
        max-concurrent-calls: 20
        max-wait-duration: 500ms
      brokerB:
        max-concurrent-calls: 10
        max-wait-duration: 500ms

  retry:
    instances:
      brokerA:
        max-attempts: 3
        wait-duration: 1s
        exponential-backoff-multiplier: 2
        retry-exceptions:
          - java.net.SocketTimeoutException
          - java.io.IOException
        ignore-exceptions:
          - com.example.broker.exception.BrokerBusinessException
```

### 브로커 클라이언트 서비스

```java
@Service
@Slf4j
public class BrokerOrderService {

    private final BrokerAClient brokerAClient;
    private final BrokerOrderCacheRepository cacheRepository;

    public BrokerOrderService(BrokerAClient brokerAClient,
                               BrokerOrderCacheRepository cacheRepository) {
        this.brokerAClient = brokerAClient;
        this.cacheRepository = cacheRepository;
    }

    @CircuitBreaker(name = "brokerA", fallbackMethod = "submitOrderFallback")
    @Bulkhead(name = "brokerA", type = Bulkhead.Type.SEMAPHORE)
    @Retry(name = "brokerA")
    public OrderResult submitOrder(OrderRequest request) {
        // 멱등성 키를 요청에 포함
        String idempotencyKey = generateIdempotencyKey(request);
        return brokerAClient.submit(request.withIdempotencyKey(idempotencyKey));
    }

    // Circuit Breaker가 열렸을 때 호출되는 Fallback
    private OrderResult submitOrderFallback(OrderRequest request, Exception ex) {
        log.warn("[BrokerA] Circuit open or error. Routing to fallback. cause={}", 
                 ex.getMessage());

        // 큐에 적재하여 브로커 복구 후 재처리
        cacheRepository.enqueueForRetry(request);

        return OrderResult.pending(request.getClientOrderId(), 
                "브로커 일시 불가. 복구 후 자동 처리됩니다.");
    }

    private String generateIdempotencyKey(OrderRequest request) {
        // 클라이언트 주문 ID + 타임스탬프(분 단위) 조합으로 중복 방지
        return request.getClientOrderId() + ":" + 
               (System.currentTimeMillis() / 60_000);
    }
}
```

### Bulkhead 격리: 브로커별 스레드 풀 분리

단순 세마포어 방식보다 스레드 풀 Bulkhead를 사용하면 더 강한 격리가 가능하다.

```java
@Configuration
public class BrokerThreadPoolConfig {

    @Bean("brokerAExecutor")
    public Executor brokerAExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(10);
        executor.setMaxPoolSize(20);
        executor.setQueueCapacity(50);
        executor.setThreadNamePrefix("broker-a-");
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        executor.initialize();
        return executor;
    }

    @Bean("brokerBExecutor")
    public Executor brokerBExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(5);
        executor.setMaxPoolSize(10);
        executor.setQueueCapacity(30);
        executor.setThreadNamePrefix("broker-b-");
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.AbortPolicy());
        executor.initialize();
        return executor;
    }
}
```

```java
@Service
@Slf4j
public class BrokerBOrderService {

    private final BrokerBClient brokerBClient;
    private final Executor brokerBExecutor;

    @Async("brokerBExecutor")
    @CircuitBreaker(name = "brokerB", fallbackMethod = "asyncFallback")
    public CompletableFuture<OrderResult> submitOrderAsync(OrderRequest request) {
        OrderResult result = brokerBClient.submit(request);
        return CompletableFuture.completedFuture(result);
    }

    private CompletableFuture<OrderResult> asyncFallback(OrderRequest request, 
                                                          Exception ex) {
        log.error("[BrokerB] Fallback triggered: {}", ex.getMessage());
        return CompletableFuture.completedFuture(
                OrderResult.failed(request.getClientOrderId(), ex.getMessage()));
    }
}
```

### 장애 복구 큐: Outbox 패턴 적용

브로커가 장애 중일 때 발생한 주문을 유실 없이 처리하려면 Outbox 패턴이 효과적이다.

```java
@Entity
@Table(name = "broker_order_outbox")
public class BrokerOrderOutbox {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String clientOrderId;
    private String brokerCode;

    @Enumerated(EnumType.STRING)
    private OutboxStatus status; // PENDING, PROCESSING, DONE, FAILED

    @Column(columnDefinition = "TEXT")
    private String payload; // JSON 직렬화된 OrderRequest

    private int retryCount;
    private LocalDateTime nextRetryAt;
    private LocalDateTime createdAt;
}
```

```java
@Component
@Slf4j
public class BrokerOutboxProcessor {

    private final BrokerOrderOutboxRepository outboxRepository;
    private final BrokerOrderService brokerOrderService;
    private final ObjectMapper objectMapper;

    // 30초마다 미처리 항목 재시도
    @Scheduled(fixedDelay = 30_000)
    @Transactional
    public void processOutbox() {
        List<BrokerOrderOutbox> pendingItems = outboxRepository
                .findByStatusAndNextRetryAtBeforeAndRetryCountLessThan(
                        OutboxStatus.PENDING, LocalDateTime.now(), 5);

        for (BrokerOrderOutbox outbox : pendingItems) {
            try {
                outbox.setStatus(OutboxStatus.PROCESSING);
                outboxRepository.save(outbox);

                OrderRequest request = objectMapper.readValue(
                        outbox.getPayload(), OrderRequest.class);
                OrderResult result = brokerOrderService.submitOrder(request);

                if (result.isAccepted()) {
                    outbox.setStatus(OutboxStatus.DONE);
                } else {
                    scheduleRetry(outbox);
                }
            } catch (Exception e) {
                log.error("[Outbox] Retry failed for orderId={}", 
                          outbox.getClientOrderId(), e);
                scheduleRetry(outbox);
            }
        }
    }

    private void scheduleRetry(BrokerOrderOutbox outbox) {
        outbox.setRetryCount(outbox.getRetryCount() + 1);
        // 지수 백오프: 1분, 2분, 4분, 8분, 16분
        long delayMinutes = (long) Math.pow(2, outbox.getRetryCount());
        outbox.setNextRetryAt(LocalDateTime.now().plusMinutes(delayMinutes));
        outbox.setStatus(outbox.getRetryCount() >= 5 
                ? OutboxStatus.FAILED : OutboxStatus.PENDING);
        outboxRepository.save(outbox);
    }
}
```

### Circuit Breaker 상태 모니터링

장애 감지를 빠르게 하려면 Circuit Breaker 상태 변화를 실시간으로 모니터링해야 한다.

```java
@Component
@Slf4j
public class CircuitBreakerMonitor {

    @EventListener
    public void onStateChange(CircuitBreakerOnStateTransitionEvent event) {
        String name = event.getCircuitBreakerName();
        String from = event.getStateTransition().getFromState().name();
        String to = event.getStateTransition().getToState().name();

        log.warn("[CircuitBreaker] {} 상태 변경: {} → {}", name, from, to);

        // OPEN 상태 진입 시 알람 발송
        if (event.getStateTransition().getToState() == CircuitBreaker.State.OPEN) {
            alertService.sendAlert(String.format(
                    "[긴급] 브로커 %s Circuit Breaker OPEN. 즉시 확인 필요.", name));
        }
    }
}
```

## 주의사항 및 트레이드오프

### 1. 타임아웃 설정의 중요성

Circuit Breaker가 아무리 잘 설계되어 있어도 **HTTP 클라이언트의 타임아웃 설정이 없으면 무의미**하다. 연결 타임아웃과 읽기 타임아웃을 반드시 별도로 설정해야 한다.

```java
@Bean
public RestTemplate brokerRestTemplate() {
    HttpComponentsClientHttpRequestFactory factory = 
            new HttpComponentsClientHttpRequestFactory();
    factory.setConnectTimeout(2_000);    // 연결 타임아웃: 2초
    factory.setReadTimeout(5_000);       // 읽기 타임아웃: 5초
    return new RestTemplate(factory);
}
```

### 2. Fallback의 정직성

Fallback에서 무조건 성공 응답을 반환하면 사용자는 주문이 체결된 줄 알지만 실제로는 대기 중인 상황이 발생한다. **Fallback 응답에는 반드시 상태를 명확히 표현**해야 하며, 사용자에게도 현재 상황을 투명하게 안내해야 한다.

### 3. 멱등성 키의 범위 설계

멱등성 키를 너무 좁게 설계하면 정상적인 재주문도 중복으로 처리되고, 너무 넓게 설계하면 실제 중복 요청을 걸러내지 못한다. 도메인 특성에 맞게 **클라이언트 주문 ID + 유효 시간 범위** 조합을 권장한다.

### 4. Outbox 테이블 증가 관리

DONE 상태의 Outbox 레코드는 주기적으로 아카이빙하거나 삭제해야 한다. 방치하면 쿼리 성능에 영향을 준다.

```sql
-- 7일 이상 완료된 항목 정리 (배치 처리)
DELETE FROM broker_order_outbox
WHERE status = 'DONE'
  AND created_at < NOW() - INTERVAL 7 DAY
LIMIT 1000;
```

### 5. 트레이드오프 정리

| 패턴 | 장점 | 단점 |
|------|------|------|
| Circuit Breaker | 연쇄 장애 방지, 빠른 실패 | 임계값 튜닝 필요, Half-Open 관리 복잡 |
| Bulkhead | 장애 격리, 리소스 보호 | 스레드 풀 증가로 메모리 사용 증가 |
| Outbox 패턴 | 유실 없는 재처리 보장 | DB 부하 증가, 처리 지연 가능 |
| Fallback | 사용자 경험 보호 | 불일치 가능성, 복잡도 증가 |

## 정리

해외 브로커 연동은 "통제 불가능한 외부 시스템에 얼마나 의존하는가"의 문제다. 중요한 것은 브로커가 언제든 장애를 일으킬 수 있다는 전제로 시스템을 설계하는 것이다.

핵심 원칙을 다시 정리하면 다음과 같다.

1. **빠른 실패**: 타임아웃과 Circuit Breaker로 느린 장애가 전파되지 않게 차단한다.
2. **격리**: Bulkhead로 브로커별 리소스 풀을 분리하여 한 브로커의 장애가 다른 브로커에 번지지 않게 한다.
3. **유실 방지**: Outbox 패턴으로 장애 중 발생한 요청을 안전하게 보관하고 복구 후 재처리한다.
4. **멱등성 보장**: 재시도가 발생하더라도 중복 처리가 일어나지 않도록 멱등성 키를 설계한다.
5. **투명한 Fallback**: Fallback 시 사용자에게 명확한 상태를 전달하고, 내부적으로는 추적 가능한 상태로 관리한다.

장애는 막을 수 없다. 하지만 **장애가 얼마나 퍼지는지, 얼마나 빠르게 복구되는지**는 설계로 충분히 통제할 수 있다. 이것이 해외 브로커 연동 서비스 안정화의 핵심이다.
