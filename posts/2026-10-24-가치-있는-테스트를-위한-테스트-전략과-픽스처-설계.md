# 가치 있는 테스트를 위한 테스트 전략과 픽스처 설계

## 개요

테스트를 작성하는 것과 가치 있는 테스트를 작성하는 것은 다르다. 많은 팀이 커버리지 숫자를 높이는 데 집중하다 보면, 정작 시스템의 복잡한 경계 조건은 검증하지 못하면서 단순한 getter/setter를 수백 개의 테스트로 뒤덮는 역설에 빠진다. 반대로 테스트가 느리고 불안정해서 CI 파이프라인이 무너지면, 팀은 테스트를 신뢰하지 않게 되고 결국 "테스트는 있지만 없는 것과 같은" 상황이 된다.

이 글에서는 **무엇을 테스트해야 하는가**부터 시작해서, **픽스처를 어떻게 설계해야 테스트가 유지보수 가능해지는가**까지 실무 관점에서 다룬다. Spring 기반의 백엔드 서비스를 주요 예시로 사용하지만, 핵심 원칙은 어떤 스택에도 적용할 수 있다.

## 핵심 개념

### 테스트 피라미드를 다시 읽기

마틴 파울러의 테스트 피라미드는 여전히 유효하다. 하지만 많은 팀이 이를 단순히 "유닛 테스트를 많이 써라"로 받아들이는 경향이 있다. 실제로 중요한 것은 **각 레이어가 검증하는 관심사가 명확히 분리되어야 한다**는 점이다.

```
        [E2E]
       /      \
   [통합 테스트]
  /              \
[단위 테스트 (대다수)]
```

- **단위 테스트**: 비즈니스 로직, 도메인 규칙, 계산 알고리즘 — 외부 의존성 없이 빠르게 실행
- **통합 테스트**: 데이터베이스, 메시지 큐, 외부 API 연동 — 실제 인프라와의 계약 검증
- **E2E 테스트**: 사용자 시나리오 전체 흐름 — 핵심 비즈니스 경로만 커버

레이어를 잘못 선택하면 유지보수 비용이 폭발한다. 데이터베이스 스키마가 바뀔 때마다 수백 개의 단위 테스트가 깨진다면, 그건 단위 테스트가 DB 레이어에 결합된 것이다.

### 테스트의 가치를 결정하는 네 가지 기준

Vladimir Khorikov의 접근법을 실무에 맞게 재해석하면 다음과 같다:

1. **회귀 방지**: 버그가 배포되는 것을 얼마나 잘 막는가
2. **리팩터링 내성**: 구현을 바꿔도 테스트가 깨지지 않는가
3. **빠른 피드백**: 개발자가 즉각적인 피드백을 받을 수 있는가
4. **유지보수성**: 테스트 자체를 이해하고 수정하는 비용이 낮은가

이 네 가지는 서로 트레이드오프 관계에 있다. E2E 테스트는 회귀 방지력이 높지만 느리고 유지보수가 어렵다. 반대로 구현 세부사항을 검증하는 단위 테스트는 빠르지만 리팩터링에 취약하다.

## 실전 예제

### 1. 도메인 로직 단위 테스트 — 올바른 관심사 분리

주문 할인 계산 로직을 예시로 보자. 나쁜 예부터 시작한다.

```java
// BAD: 외부 의존성에 결합된 단위 테스트
@ExtendWith(MockitoExtension.class)
class OrderServiceTest {

    @Mock
    private OrderRepository orderRepository;

    @Mock
    private DiscountPolicyRepository discountPolicyRepository;

    @InjectMocks
    private OrderService orderService;

    @Test
    void 회원등급에_따라_할인이_적용된다() {
        // given
        Order order = new Order(userId: 1L, totalPrice: 10000);
        when(orderRepository.findById(1L)).thenReturn(Optional.of(order));
        when(discountPolicyRepository.findByGrade("VIP")).thenReturn(...);

        // 구현 세부사항에 너무 결합되어 있어 리팩터링 시 모두 깨짐
    }
}
```

이 테스트의 문제는 Mock이 구현의 내부 호출 순서에 결합되어 있다는 점이다. 할인 로직을 별도 서비스로 분리하거나 캐싱을 도입하는 순간 테스트가 깨진다.

더 나은 접근법은 **도메인 로직을 순수 함수나 도메인 객체 메서드로 격리**하는 것이다.

```java
// GOOD: 순수한 도메인 로직만 검증
class DiscountPolicyTest {

    @Test
    void VIP_회원은_10퍼센트_할인이_적용된다() {
        // given
        DiscountPolicy policy = new RateDiscountPolicy(MemberGrade.VIP, 0.10);
        int originalPrice = 10_000;

        // when
        int discountedPrice = policy.apply(originalPrice);

        // then
        assertThat(discountedPrice).isEqualTo(9_000);
    }

    @Test
    void 할인_금액은_음수가_될_수_없다() {
        DiscountPolicy policy = new RateDiscountPolicy(MemberGrade.VIP, 0.10);

        assertThatThrownBy(() -> policy.apply(-1000))
                .isInstanceOf(InvalidPriceException.class);
    }
}
```

이 테스트는 빠르고, 구현 세부사항에 결합되지 않으며, 도메인 규칙을 명확히 문서화한다.

### 2. 통합 테스트 — Testcontainers로 실제 인프라 검증

DB 쿼리, 트랜잭션 경계, JPA 연관관계 매핑 같은 것은 Mock으로 검증할 수 없다. 이런 경우에는 실제 DB와 통합 테스트를 작성하되, **Testcontainers**를 활용해 재현 가능한 환경을 구성한다.

```java
@SpringBootTest
@Testcontainers
@Transactional
class OrderRepositoryIntegrationTest {

    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:15")
            .withDatabaseName("testdb")
            .withUsername("test")
            .withPassword("test");

    @DynamicPropertySource
    static void configureProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }

    @Autowired
    private OrderRepository orderRepository;

    @Test
    void 특정_기간_내_사용자의_주문을_조회한다() {
        // given — 픽스처 직접 저장
        Order order1 = OrderFixture.aCompletedOrder().withUserId(1L)
                .withCreatedAt(LocalDateTime.now().minusDays(3))
                .build();
        Order order2 = OrderFixture.aCompletedOrder().withUserId(1L)
                .withCreatedAt(LocalDateTime.now().minusDays(10))
                .build();
        orderRepository.saveAll(List.of(order1, order2));

        // when
        List<Order> result = orderRepository.findByUserIdAndCreatedAtBetween(
                1L,
                LocalDateTime.now().minusDays(7),
                LocalDateTime.now()
        );

        // then
        assertThat(result).hasSize(1);
        assertThat(result.get(0).getId()).isEqualTo(order1.getId());
    }
}
```

### 3. 픽스처 설계 — 테스트 데이터의 복잡성을 통제하라

테스트 코드가 유지보수하기 어려워지는 가장 큰 원인 중 하나는 **픽스처 코드가 테스트 본문을 압도하는 것**이다. 5줄짜리 검증 로직을 위해 30줄의 객체 생성 코드를 반복하다 보면, 스키마 변경 한 번에 수십 개의 테스트를 손봐야 한다.

**빌더 패턴 기반의 픽스처 클래스**를 만들면 이 문제를 해결할 수 있다.

```java
// 픽스처 클래스 정의
public class OrderFixture {

    public static OrderBuilder aCompletedOrder() {
        return Order.builder()
                .userId(1L)
                .status(OrderStatus.COMPLETED)
                .totalPrice(10_000)
                .createdAt(LocalDateTime.now());
    }

    public static OrderBuilder aPendingOrder() {
        return Order.builder()
                .userId(1L)
                .status(OrderStatus.PENDING)
                .totalPrice(5_000)
                .createdAt(LocalDateTime.now());
    }
}

// 테스트에서 필요한 부분만 오버라이드
@Test
void 취소된_주문은_환불_대상이다() {
    Order order = OrderFixture.aCompletedOrder()
            .status(OrderStatus.CANCELLED)
            .totalPrice(20_000)
            .build();

    // 테스트 본문이 의도를 드러냄
    assertThat(refundPolicy.isEligible(order)).isTrue();
}
```

픽스처 클래스의 핵심 원칙은 다음과 같다:

- **의미 있는 기본값 제공**: 테스트에서 중요하지 않은 필드는 기본값으로 채운다
- **의도를 드러내는 네이밍**: `aCompletedOrder()`, `aPendingOrderWithExpiredPayment()` 같이 시나리오가 읽히도록 한다
- **불변성 유지**: 픽스처 메서드 자체는 상태를 변경하지 않는다
- **공유는 최소화**: 픽스처를 `@BeforeEach`로 모든 테스트에 주입하면 테스트 간 결합이 생긴다

### 4. 슬라이스 테스트로 레이어 격리

Spring에서는 `@WebMvcTest`, `@DataJpaTest` 같은 슬라이스 테스트를 적극 활용하면 `@SpringBootTest`보다 훨씬 빠른 컨텍스트 로딩이 가능하다.

```java
@WebMvcTest(OrderController.class)
class OrderControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @MockBean
    private OrderService orderService;

    @Test
    void 존재하지_않는_주문_조회시_404를_반환한다() throws Exception {
        given(orderService.findById(999L))
                .willThrow(new OrderNotFoundException(999L));

        mockMvc.perform(get("/api/orders/999"))
                .andExpect(status().isNotFound())
                .andExpect(jsonPath("$.errorCode").value("ORDER_NOT_FOUND"));
    }
}
```

## 주의사항 및 트레이드오프

### 과도한 Mock 사용의 위험

Mock은 강력하지만 남용하면 테스트가 구현 세부사항에 결합되어 **리팩터링 내성이 제로**에 가까워진다. 특히 `verify(mock, times(2)).someMethod(...)` 같은 행위 검증은 내부 호출 횟수까지 테스트에 박아버리는 것이라 구현이 조금만 바뀌어도 깨진다. 행위 검증은 정말 필요한 경우(예: 메일 발송 서비스가 외부 시스템에 요청을 보내는지 확인)에만 사용하라.

### 테스트 간 데이터 격리

통합 테스트에서 데이터 격리 전략은 크게 세 가지다:

| 전략 | 장점 | 단점 |
|------|------|------|
| `@Transactional` 롤백 | 빠르고 간단 | 실제 트랜잭션 커밋 동작 검증 불가 |
| 테스트별 DB 초기화 | 완전한 격리 | 느림 |
| 고유 데이터 사용 | 병렬 실행 가능 | 데이터 정리 필요 |

JPA의 `LAZY` 로딩이나 배치 INSERT처럼 트랜잭션 커밋 이후에 발생하는 동작을 검증해야 한다면, `@Transactional` 롤백 방식은 적합하지 않다.

### 픽스처 공유의 덫

공통 픽스처를 부모 클래스나 `@BeforeEach`에 몰아넣으면 테스트가 어떤 전제 데이터를 기반으로 실행되는지 파악하기 어려워진다. 테스트 하나를 이해하기 위해 여러 클래스를 탐색해야 하는 순간, 그 테스트는 이미 가치를 잃기 시작한 것이다. **테스트는 최대한 자기 완결적이어야 한다.**

### 느린 테스트 스위트의 경제학

테스트가 느려지면 개발자들은 로컬에서 테스트를 실행하지 않기 시작한다. 이것이 "테스트는 있지만 아무도 신뢰하지 않는" 상황의 출발점이다. Testcontainers를 사용한다면 컨테이너 재사용(`withReuse(true)`) 전략을 검토하고, Spring 컨텍스트 캐싱이 제대로 동작하는지 확인하라. `@MockBean`을 사용할 때마다 컨텍스트가 재생성된다는 점도 주의해야 한다.

## 정리

가치 있는 테스트를 만드는 것은 단순히 코드를 많이 커버하는 것이 아니다. 핵심은 다음 세 가지로 압축된다.

**첫째, 무엇을 테스트할지 명확히 결정하라.** 비즈니스 로직과 도메인 규칙은 단위 테스트로, 인프라와의 계약은 통합 테스트로, 핵심 사용자 흐름은 E2E로 분리하라. 레이어를 혼용하면 두 레이어 모두의 단점만 가져오게 된다.

**둘째, 픽스처를 1급 객체로 대우하라.** 테스트 코드도 프로덕션 코드와 동일한 설계 원칙이 적용된다. 빌더 패턴 기반의 픽스처 클래스를 만들고, 의미 있는 기본값과 시나리오를 명확히 드러내는 네이밍을 부여하라. 픽스처에 투자하는 시간은 이후 수백 번의 테스트 수정 비용을 절감해준다.

**셋째, 리팩터링 내성을 항상 고려하라.** 구현 세부사항이 아닌 **관찰 가능한 동작**을 검증하라. 테스트가 구현에 결합되어 있으면, 안전하게 리팩터링하기 위해 작성한 테스트가 오히려 리팩터링의 발목을 잡는 역설이 된다.

테스트는 코드베이스의 품질을 높이는 도구이기 이전에, 팀이 자신 있게 변경할 수 있도록 해주는 **안전망**이다. 그 안전망이 신뢰할 수 없다면, 있는 것이 없는 것보다 더 위험할 수 있다.
