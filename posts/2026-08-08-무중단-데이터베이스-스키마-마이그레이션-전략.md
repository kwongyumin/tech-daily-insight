# 무중단 데이터베이스 스키마 마이그레이션 전략

## 개요

서비스가 성장할수록 데이터베이스 스키마 변경은 피할 수 없는 작업이다. 그런데 트래픽이 몰리는 프로덕션 환경에서 단순히 `ALTER TABLE`을 실행하면 어떤 일이 벌어질까? 테이블 락(Lock)이 걸리고, 수백만 건의 레코드가 있는 테이블이라면 수십 분간 서비스가 멈출 수 있다.

실무에서는 **"배포 시간 = 다운타임"** 이라는 공식을 깨는 것이 핵심 과제다. 이 포스팅에서는 무중단 스키마 마이그레이션을 가능하게 하는 핵심 전략들을 이론부터 실전 예제까지 다룬다. 대상 독자는 Flyway, Liquibase 같은 마이그레이션 도구를 써본 경험이 있고, 제로 다운타임 배포에 관심 있는 중급 이상의 백엔드 개발자다.

---

## 핵심 개념

### Expand-Contract 패턴 (aka. Parallel Change)

무중단 마이그레이션의 가장 핵심적인 패턴이다. 한 번에 스키마를 바꾸는 대신 **Expand → Migrate → Contract** 세 단계로 나눠 진행한다.

| 단계 | 설명 |
|------|------|
| **Expand** | 기존 스키마를 유지하면서 새로운 컬럼/테이블을 추가 |
| **Migrate** | 기존 데이터를 새로운 구조로 이전 |
| **Contract** | 더 이상 사용하지 않는 구 컬럼/테이블 제거 |

이 패턴의 핵심은 **각 단계 사이에 애플리케이션 배포가 들어간다**는 것이다. 즉, 한 번의 배포가 아니라 여러 번의 배포에 걸쳐 스키마를 변경한다.

### 호환성(Compatibility) 원칙

마이그레이션 중에는 **구버전 앱과 신버전 앱이 동시에 동작**한다. 롤링 배포(Rolling Deployment)나 블루-그린 배포 환경에서는 두 버전의 애플리케이션이 같은 DB를 바라보는 구간이 반드시 존재한다.

따라서 각 마이그레이션 단계는 다음 호환성을 반드시 지켜야 한다:

- **Expand 단계**: 신버전 앱이 정상 동작 + 구버전 앱도 깨지지 않아야 함
- **Contract 단계**: 구버전 앱이 완전히 교체된 이후에만 실행

## 실전 예제

### 시나리오: `users` 테이블의 `name` 컬럼을 `first_name`, `last_name`으로 분리

가장 흔한 케이스 중 하나다. 단순히 컬럼을 바꾸면 되지만, 무중단으로 하려면 여러 단계가 필요하다.

#### Step 1 — Expand: 새 컬럼 추가 (마이그레이션 V1)

```sql
-- V1__add_first_last_name_columns.sql
ALTER TABLE users
    ADD COLUMN first_name VARCHAR(100),
    ADD COLUMN last_name  VARCHAR(100);
```

이 시점에서 `name` 컬럼은 그대로 존재한다. 구버전 앱은 `name`만 쓰고, 신버전 앱은 두 컬럼을 모두 핸들링하도록 작성한다.

#### Step 1 — 애플리케이션 코드 (신버전)

신버전 앱은 **쓰기 시점에 두 컬럼을 모두 채워야** 한다. 읽기는 새 컬럼 우선, 없으면 `name`에서 파싱하는 방어 로직을 넣는다.

```java
@Entity
@Table(name = "users")
public class User {

    @Column(name = "name")
    private String name; // 구 컬럼, 아직 유지

    @Column(name = "first_name")
    private String firstName;

    @Column(name = "last_name")
    private String lastName;

    // 읽기: 새 컬럼 우선, 없으면 name에서 파싱
    public String getFirstName() {
        if (firstName != null) return firstName;
        return name != null ? name.split(" ")[0] : null;
    }

    public String getLastName() {
        if (lastName != null) return lastName;
        if (name != null && name.contains(" ")) {
            return name.substring(name.indexOf(" ") + 1);
        }
        return null;
    }
}
```

```java
@Service
@RequiredArgsConstructor
public class UserService {

    private final UserRepository userRepository;

    public User createUser(String firstName, String lastName) {
        User user = new User();
        user.setFirstName(firstName);
        user.setLastName(lastName);
        // 구버전 앱과의 호환을 위해 name도 함께 설정
        user.setName(firstName + " " + lastName);
        return userRepository.save(user);
    }
}
```

#### Step 2 — Migrate: 기존 데이터 백필(Backfill)

신버전 앱 배포 완료 후, 기존 레코드의 데이터를 새 컬럼으로 채운다. **전체를 한 번에 업데이트하면 락이 발생**하므로 배치(Batch) 방식으로 처리한다.

```sql
-- V2__backfill_first_last_name.sql
-- Flyway repeatable migration 또는 별도 스크립트로 관리
-- 한 번에 1000건씩 처리 (애플리케이션 레벨에서 실행 권장)
UPDATE users
SET
    first_name = SUBSTRING_INDEX(name, ' ', 1),
    last_name  = SUBSTRING(name, LENGTH(SUBSTRING_INDEX(name, ' ', 1)) + 2)
WHERE first_name IS NULL
  AND name IS NOT NULL
LIMIT 1000;
```

대용량 테이블이라면 Flyway로 직접 실행하지 말고 Spring Batch나 별도 스크립트로 배치 처리하는 것을 강권한다.

```java
@Component
@RequiredArgsConstructor
public class UserNameBackfillJob {

    private final JdbcTemplate jdbcTemplate;

    @Scheduled(fixedDelay = 5000)
    public void backfill() {
        int updated;
        do {
            updated = jdbcTemplate.update("""
                UPDATE users
                SET
                    first_name = SUBSTRING_INDEX(name, ' ', 1),
                    last_name  = SUBSTRING(name,
                                   LENGTH(SUBSTRING_INDEX(name, ' ', 1)) + 2)
                WHERE first_name IS NULL
                  AND name IS NOT NULL
                LIMIT 500
                """);
            log.info("Backfilled {} rows", updated);
        } while (updated > 0);
    }
}
```

#### Step 3 — Contract: 구 컬럼 제거

모든 인스턴스가 신버전으로 교체되고, 백필이 완료된 것을 확인한 후에만 실행한다.

```sql
-- V3__drop_name_column.sql
-- 반드시 신버전 앱이 name 컬럼 참조를 완전히 제거한 이후 실행
ALTER TABLE users DROP COLUMN name;
```

애플리케이션에서도 `name` 필드를 완전히 제거한다.

```java
@Entity
@Table(name = "users")
public class User {
    // name 컬럼 완전 제거
    @Column(name = "first_name")
    private String firstName;

    @Column(name = "last_name")
    private String lastName;
}
```

### Flyway를 활용한 마이그레이션 버전 관리

```yaml
# application.yml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
    baseline-on-migrate: true
    out-of-order: false  # 순서 보장
    validate-on-migrate: true
```

```
src/main/resources/db/migration/
├── V1__add_first_last_name_columns.sql
├── V2__backfill_first_last_name.sql  # 주의: 대용량은 앱에서 처리
└── V3__drop_name_column.sql
```

### pt-online-schema-change 활용 (MySQL)

MySQL 환경에서 대용량 테이블 DDL은 Percona의 `pt-online-schema-change`나 `gh-ost`를 활용하면 락 없이 스키마를 변경할 수 있다.

```bash
# pt-online-schema-change 예시
pt-online-schema-change \
  --alter "ADD COLUMN email_verified TINYINT(1) DEFAULT 0 NOT NULL" \
  --host=localhost \
  --user=root \
  --password=secret \
  --execute \
  D=mydb,t=users

# gh-ost 예시 (GitHub 오픈소스)
gh-ost \
  --user="root" \
  --password="secret" \
  --host="localhost" \
  --database="mydb" \
  --table="users" \
  --alter="ADD COLUMN email_verified TINYINT(1) DEFAULT 0 NOT NULL" \
  --execute
```

이 도구들은 내부적으로 임시 테이블을 생성하고 트리거나 바이너리 로그를 통해 변경 사항을 동기화하면서 온라인으로 스키마를 변경한다.

## 주의사항 및 트레이드오프

### 1. NOT NULL 컬럼 추가 시 함정

`NOT NULL` 컬럼을 기본값 없이 추가하면 기존 레코드에서 즉시 오류가 발생한다. 순서를 지켜야 한다:

```sql
-- ❌ 잘못된 방법: 한 번에 NOT NULL 추가
ALTER TABLE orders ADD COLUMN status VARCHAR(20) NOT NULL;

-- ✅ 올바른 방법: 3단계로 분리
-- Step 1: nullable로 추가
ALTER TABLE orders ADD COLUMN status VARCHAR(20) NULL;

-- Step 2: 백필
UPDATE orders SET status = 'PENDING' WHERE status IS NULL;

-- Step 3: NOT NULL 제약 추가
ALTER TABLE orders MODIFY COLUMN status VARCHAR(20) NOT NULL DEFAULT 'PENDING';
```

### 2. 인덱스 생성의 락 문제

```sql
-- ❌ 일반 인덱스 생성은 테이블 락 유발 가능 (MySQL 5.5 이하)
CREATE INDEX idx_users_email ON users(email);

-- ✅ CONCURRENTLY 옵션 사용 (PostgreSQL)
CREATE INDEX CONCURRENTLY idx_users_email ON users(email);

-- ✅ MySQL 8.0+: 기본적으로 온라인 DDL 지원
ALTER TABLE users ADD INDEX idx_email(email), ALGORITHM=INPLACE, LOCK=NONE;
```

### 3. 외래 키(Foreign Key) 제약의 위험성

외래 키 추가는 전체 테이블 스캔이 발생할 수 있다. 대용량 테이블에서는 명시적으로 락 수준을 제어해야 한다.

### 4. 배포 파이프라인과의 결합

마이그레이션 스크립트 실행 시점에 주의가 필요하다. **마이그레이션은 새 앱 인스턴스가 뜨기 전에 실행**되어야 하는 경우(Expand)와 **이후에 실행**되어야 하는 경우(Contract)가 다르다.

```yaml
# GitHub Actions 예시 - 배포 순서 제어
jobs:
  migrate-expand:
    runs-on: ubuntu-latest
    steps:
      - name: Run Expand Migrations
        run: flyway migrate -locations=filesystem:migrations/expand

  deploy:
    needs: migrate-expand
    steps:
      - name: Deploy new version
        run: kubectl rollout restart deployment/app

  migrate-contract:
    needs: deploy
    steps:
      - name: Wait for rollout
        run: kubectl rollout status deployment/app
      - name: Run Contract Migrations
        run: flyway migrate -locations=filesystem:migrations/contract
```

### 5. 롤백 전략

무중단 마이그레이션이라도 롤백 시나리오를 반드시 준비해야 한다. Contract 단계의 DDL은 롤백이 매우 어렵기 때문에, 삭제 전에 **충분한 관찰 기간**을 두는 것이 실무 관례다.

| 단계 | 롤백 용이성 | 전략 |
|------|-------------|------|
| Expand (컬럼 추가) | 쉬움 | DROP COLUMN |
| Migrate (데이터 이전) | 중간 | 역방향 백필 |
| Contract (컬럼 삭제) | 매우 어려움 | 삭제 전 충분한 검증 필수 |

## 정리

무중단 데이터베이스 스키마 마이그레이션은 단순한 기술 문제가 아니라 **배포 전략, 팀 프로세스, 모니터링**이 모두 맞물린 운영 문제다.

핵심을 정리하면 다음과 같다:

1. **Expand-Contract 패턴**을 기본 원칙으로 삼는다. 스키마 변경은 항상 여러 단계로 분리한다.
2. **구버전과 신버전 앱의 동시 운영 구간**을 항상 고려해서 호환성을 설계한다.
3. **대용량 백필은 Flyway가 아닌 배치 잡**으로 처리해 DB 부하를 분산한다.
4. **pt-osc, gh-ost** 같은 전문 도구를 적극 활용해 DDL 락을 회피한다.
5. Contract 단계(삭제)는 **절대 서두르지 않는다**. 최소 1~2주의 관찰 기간을 두는 것이 실무 관례다.

스키마 마이그레이션은 무섭지 않다. 충분히 작은 단계로 나누고, 각 단계를 독립적으로 안전하게 만들면 된다. "작게, 자주, 안전하게"가 무중단 마이그레이션의 핵심 철학이다.
