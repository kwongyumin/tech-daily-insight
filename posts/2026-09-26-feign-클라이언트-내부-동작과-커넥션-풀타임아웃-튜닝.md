# Feign 클라이언트 내부 동작과 커넥션 풀·타임아웃 튜닝

## 개요

마이크로서비스 아키텍처가 일반화되면서, 서비스 간 HTTP 통신은 일상적인 작업이 되었다. Spring Cloud OpenFeign은 인터페이스 기반의 선언적 HTTP 클라이언트를 제공해 개발 생산성을 높이지만, 내부 동작을 제대로 이해하지 않으면 커넥션 고갈, 응답 지연, 타임아웃 설정 오류 등의 문제로 장애를 맞닥뜨리게 된다.

이 글에서는 Feign 클라이언트가 실제로 어떻게 동작하는지 내부 구조부터 살펴보고, 커넥션 풀과 타임아웃을 실무에서 어떻게 튜닝해야 하는지 실전 예제와 함께 설명한다.

---

## 핵심 개념

### Feign의 내부 동작 구조

Feign은 크게 다음 레이어로 구성된다.

```
[Interface Proxy]
      ↓
[MethodHandler (SynchronousMethodHandler)]
      ↓
[Encoder / Decoder]
      ↓
[RequestInterceptor]
      ↓
[Client (HTTP 실행층)]
      ↓
[Retryer]
```

1. **Proxy 생성**: `@FeignClient`가 붙은 인터페이스는 Spring Bean으로 등록될 때 `ReflectiveFeign`이 JDK Dynamic Proxy를 생성한다.
2. **MethodHandler**: 메서드 호출 시 `SynchronousMethodHandler`가 요청 템플릿을 빌드하고 실제 HTTP 요청을 실행한다.
3. **Client**: 기본적으로 `java.net.HttpURLConnection`을 사용하는 `Client.Default`가 사용된다. 이것이 핵심 문제다. **`Client.Default`는 커넥션 풀을 지원하지 않는다.**

### 기본 Client의 한계

`Client.Default`는 요청마다 새로운 커넥션을 생성하고 닫는다. 소규모 트래픽에서는 문제가 없지만, TPS가 높아질수록 TCP 커넥션 생성/해제 오버헤드와 TIME_WAIT 상태의 소켓이 누적되어 성능 저하를 유발한다.

이를 해결하기 위해 실무에서는 주로 아래 두 가지 HTTP 클라이언트를 Feign의 실행층으로 교체한다.

| 구분 | Apache HttpClient 5 | OkHttpClient |
|------|---------------------|--------------|
| 커넥션 풀 | `PoolingHttpClientConnectionManager` | `ConnectionPool` |
| HTTP/2 지원 | 5.x부터 지원 | 기본 지원 |
| 설정 복잡도 | 상대적으로 복잡 | 간결 |
| Spring Cloud 통합 | `feign-httpclient` | `feign-okhttp` |

### 타임아웃 종류 이해

Feign에서 타임아웃은 두 가지로 구분된다.

- **connectTimeout**: TCP 커넥션 수립에 걸리는 최대 시간
- **readTimeout**: 커넥션 수립 후 응답 데이터를 기다리는 최대 시간

이 두 값을 구분하지 않고 설정하면 실제 문제 원인을 오판할 수 있다.

## 실전 예제

### 1. 의존성 추가 (Apache HttpClient 5 기준)

```xml
<!-- pom.xml -->
<dependency>
    <groupId>io.github.openfeign</groupId>
    <artifactId>feign-hc5</artifactId>
</dependency>
<dependency>
    <groupId>org.apache.httpcomponents.client5</groupId>
    <artifactId>httpclient5</artifactId>
</dependency>
```

또는 Gradle:

```groovy
implementation 'io.github.openfeign:feign-hc5'
implementation 'org.apache.httpcomponents.client5:httpclient5'
```

### 2. 커넥션 풀 설정

```java
@Configuration
public class FeignHttpClientConfig {

    @Bean
    public CloseableHttpClient httpClient() {
        // 커넥션 풀 매니저 설정
        PoolingHttpClientConnectionManager connectionManager =
            new PoolingHttpClientConnectionManager();

        // 전체 최대 커넥션 수
        connectionManager.setMaxTotal(200);
        // 호스트(라우트)별 최대 커넥션 수
        connectionManager.setDefaultMaxPerRoute(50);
        // 유효성 검사 주기 (유휴 커넥션 검사)
        connectionManager.setValidateAfterInactivity(TimeValue.ofSeconds(10));

        return HttpClients.custom()
            .setConnectionManager(connectionManager)
            // 유휴 커넥션 정리 (30초 이상 유휴 상태)
            .evictIdleConnections(TimeValue.ofSeconds(30))
            // 만료된 커넥션 자동 제거
            .evictExpiredConnections()
            .build();
    }

    @Bean
    public Client feignClient(CloseableHttpClient httpClient) {
        return new ApacheHttp5Client(httpClient);
    }
}
```

### 3. 타임아웃 설정 (application.yml)

Spring Cloud OpenFeign 4.x (Spring Boot 3.x 기준)에서는 아래와 같이 설정한다.

```yaml
spring:
  cloud:
    openfeign:
      client:
        config:
          # 전역 기본값
          default:
            connect-timeout: 3000   # ms
            read-timeout: 10000     # ms
            logger-level: basic

          # 특정 Feign 클라이언트 개별 설정 (우선순위 높음)
          order-service:
            connect-timeout: 2000
            read-timeout: 5000
            logger-level: full

          payment-service:
            connect-timeout: 1000
            read-timeout: 15000  # 결제는 외부 PG 연동으로 더 길게
```

### 4. FeignClient 인터페이스 정의

```java
@FeignClient(
    name = "order-service",
    url = "${service.order.url}",
    configuration = OrderFeignConfig.class
)
public interface OrderServiceClient {

    @GetMapping("/api/orders/{orderId}")
    OrderResponse getOrder(@PathVariable("orderId") Long orderId);

    @PostMapping("/api/orders")
    OrderResponse createOrder(@RequestBody OrderRequest request);
}
```

### 5. OkHttpClient 사용 시 설정

```java
@Configuration
@ConditionalOnProperty(name = "feign.okhttp.enabled", havingValue = "true")
public class FeignOkHttpConfig {

    @Bean
    public okhttp3.OkHttpClient okHttpClient() {
        return new okhttp3.OkHttpClient.Builder()
            .connectionPool(new ConnectionPool(
                50,           // 최대 유휴 커넥션 수
                30,           // keep-alive 유지 시간
                TimeUnit.SECONDS
            ))
            .connectTimeout(3, TimeUnit.SECONDS)
            .readTimeout(10, TimeUnit.SECONDS)
            .writeTimeout(10, TimeUnit.SECONDS)
            // 커넥션 재사용을 위한 Keep-Alive 활성화
            .retryOnConnectionFailure(false) // Feign Retryer에 위임
            .build();
    }
}
```

```yaml
feign:
  okhttp:
    enabled: true
```

### 6. 커넥션 풀 모니터링

운영 환경에서 커넥션 풀 상태를 추적하는 것은 필수다.

```java
@Component
@RequiredArgsConstructor
public class HttpClientMetrics {

    private final PoolingHttpClientConnectionManager connectionManager;
    private final MeterRegistry meterRegistry;

    @PostConstruct
    public void bindMetrics() {
        Gauge.builder("httpclient.pool.total.max", connectionManager,
                cm -> cm.getTotalStats().getMax())
            .description("최대 커넥션 수")
            .register(meterRegistry);

        Gauge.builder("httpclient.pool.total.available", connectionManager,
                cm -> cm.getTotalStats().getAvailable())
            .description("사용 가능한 커넥션 수")
            .register(meterRegistry);

        Gauge.builder("httpclient.pool.total.leased", connectionManager,
                cm -> cm.getTotalStats().getLeased())
            .description("현재 사용 중인 커넥션 수")
            .register(meterRegistry);

        Gauge.builder("httpclient.pool.total.pending", connectionManager,
                cm -> cm.getTotalStats().getPending())
            .description("커넥션 대기 중인 요청 수")
            .register(meterRegistry);
    }
}
```

`pending` 값이 지속적으로 증가한다면 `maxTotal` 또는 `defaultMaxPerRoute` 조정을 검토해야 한다는 신호다.

## 주의사항 및 트레이드오프

### 1. readTimeout과 비즈니스 SLA의 관계

`readTimeout`을 너무 길게 설정하면 다운스트림 서비스 장애 시 스레드가 오래 점유되어 Thread Pool 고갈로 이어질 수 있다. 반대로 너무 짧게 설정하면 정상적인 요청이 타임아웃으로 실패한다.

**권장 접근법**: 해당 서비스의 P99 응답 시간을 측정한 후, 여유분을 더해 설정한다. 일반적으로 `readTimeout = P99 latency * 2~3` 수준이 출발점이 된다.

```
P99 latency: 800ms → readTimeout: 2000~3000ms
```

### 2. Feign Retryer와 타임아웃의 조합 위험성

Feign의 기본 `Retryer`는 `Retryer.NEVER_RETRY`다. 만약 재시도를 활성화할 경우, 멱등하지 않은 POST 요청에서 중복 처리가 발생할 수 있다.

```java
// 재시도가 필요하다면 GET 등 멱등 요청에만 적용
@Bean
public Retryer retryer() {
    // period: 초기 대기 ms, maxPeriod: 최대 대기 ms, maxAttempts: 최대 시도 횟수
    return new Retryer.Default(100, 500, 3);
}
```

재시도와 Circuit Breaker(Resilience4j)를 함께 사용한다면, 재시도가 먼저 동작하고 그 이후 Circuit Breaker가 판단하도록 순서를 명확히 해야 한다.

### 3. maxPerRoute 설정의 함정

`defaultMaxPerRoute`를 너무 낮게 설정하면 특정 서비스에 대한 동시 요청이 몰릴 때 큐잉이 발생하고 응답 지연이 대기 시간과 더해진다. 반대로 너무 높게 설정하면 다운스트림 서비스에 과부하를 줄 수 있다. 다운스트림 서비스의 처리 용량을 파악하고, 역방향으로 최대 커넥션 수를 도출하는 것이 올바른 방향이다.

### 4. Spring Cloud LoadBalancer와의 통합

`@FeignClient`에 `url`을 명시하지 않으면 Spring Cloud LoadBalancer가 개입한다. 이 경우 `FeignBlockingLoadBalancerClient`가 래핑되어 동작하므로, 커넥션 풀 설정이 예상대로 적용되는지 반드시 확인해야 한다.

```java
// LoadBalancer 사용 시 올바른 Bean 등록
@Bean
@ConditionalOnMissingBean
public Client feignClient(CloseableHttpClient httpClient, 
                          LoadBalancerClient loadBalancerClient,
                          LoadBalancerClientFactory loadBalancerClientFactory) {
    ApacheHttp5Client delegate = new ApacheHttp5Client(httpClient);
    return new FeignBlockingLoadBalancerClient(delegate, loadBalancerClient, loadBalancerClientFactory);
}
```

### 5. 커넥션 풀 크기와 스레드 풀 크기의 균형

Tomcat 스레드 풀(기본 200)보다 커넥션 풀의 `maxTotal`이 작으면, 모든 스레드가 동시에 외부 서비스를 호출할 경우 커넥션 경합이 발생한다. 반드시 스레드 수와 커넥션 풀 크기를 함께 고려해야 한다.

```
스레드 수 × 외부 서비스 호출 비율 ≤ maxPerRoute
```

## 정리

| 항목 | 권장 설정 |
|------|-----------|
| HTTP 클라이언트 | Apache HttpClient 5 또는 OkHttp (기본 Client.Default 지양) |
| maxTotal | 애플리케이션 전체 동시 요청 예상치 기반 설정 |
| maxPerRoute | 다운스트림 서비스 처리 용량 기반 설정 |
| connectTimeout | 일반적으로 1~3초 |
| readTimeout | P99 latency 기반, 서비스별 개별 설정 |
| 모니터링 | pending, leased, available 메트릭 수집 |

Feign은 편리한 추상화를 제공하지만, 내부 HTTP 클라이언트가 `Client.Default`로 동작한다는 점과 커넥션 풀이 기본 비활성화 상태라는 사실을 반드시 인지해야 한다. 타임아웃 설정은 단순히 숫자를 넣는 것이 아니라 서비스의 SLA, 다운스트림 특성, 스레드 모델을 종합적으로 고려한 설계 결정이다. 운영 중에는 커넥션 풀 메트릭을 지속적으로 모니터링하면서 점진적으로 값을 조정해 나가는 것이 안정적인 운영의 핵심이다.
