# R2DBC 반응형 데이터베이스 접근 전략

## 개요

Spring WebFlux와 Project Reactor를 기반으로 한 반응형(Reactive) 애플리케이션을 구축할 때, 가장 흔히 맞닥뜨리는 벽이 바로 **데이터베이스 계층**이다. Spring MVC 진영의 JPA/Hibernate는 내부적으로 블로킹 I/O를 전제로 설계되었기 때문에, WebFlux 파이프라인에서 JPA를 그대로 사용하면 Non-blocking 스레드 모델의 이점을 전혀 살릴 수 없다.

이 문제를 해결하기 위해 등장한 것이 **R2DBC(Reactive Relational Database Connectivity)**다. R2DBC는 관계형 데이터베이스에 대한 완전한 Non-blocking, 비동기 접근을 가능하게 해주는 SPI(Service Provider Interface) 명세이며, Spring Data R2DBC는 이를 Spring 생태계에 자연스럽게 통합한 추상화 레이어다.

이 글에서는 R2DBC의 핵심 개념부터 실전 프로젝트에서 적용할 수 있는 전략, 그리고 흔히 발생하는 트레이드오프까지 심층적으로 다룬다.

---

## 핵심 개념

### R2DBC vs JDBC

| 구분 | JDBC | R2DBC |
|---|---|---|
| I/O 모델 | 블로킹(Blocking) | Non-blocking |
| 반환 타입 | ResultSet | Publisher (Mono/Flux) |
| 트랜잭션 | ThreadLocal 기반 | Reactive Context 기반 |
| ORM 지원 | JPA/Hibernate | 미지원 (Spring Data R2DBC) |
| 커넥션 풀 | HikariCP 등 | r2dbc-pool |

JDBC는 커넥션을 스레드에 귀속시켜 동기적으로 응답을 대기하는 반면, R2DBC는 Reactive Streams 명세를 따라 **백프레셔(Backpressure)**와 비동기 흐름을 지원한다.

### Spring Data R2DBC의 위치

Spring Data R2DBC는 JPA처럼 완전한 ORM이 아니다. **객체-관계 매핑을 일부 지원**하지만, 지연 로딩(Lazy Loading), 1차 캐시, 더티 체킹(Dirty Checking) 같은 JPA의 복잡한 기능은 의도적으로 배제되어 있다. 이는 Reactive 환경과의 철학적 충돌을 피하기 위한 설계 결정이다.

### Reactive Streams와 백프레셔

R2DBC의 핵심은 Reactive Streams 명세 구현이다. `Publisher<T>`를 통해 데이터를 스트림으로 처리하며, `Subscription.request(n)` 메커니즘으로 소비자가 처리할 수 있는 만큼만 데이터를 요청(백프레셔)할 수 있다.

```
Database → R2DBC Driver → Reactor (Flux/Mono) → WebFlux Handler → Client
```

이 파이프라인 전체가 Non-blocking으로 동작할 때 진정한 반응형 시스템이 완성된다.

### 엔티티 및 레포지토리 정의

```java
// 엔티티
@Table("orders")
@Data
@AllArgsConstructor
@NoArgsConstructor
public class Order {

    @Id
    private Long id;

    @Column("user_id")
    private Long userId;

    @Column("product_name")
    private String productName;

    private Integer quantity;

    @Column("total_price")
    private BigDecimal totalPrice;

    @Column("status")
    private OrderStatus status;

    @Column("created_at")
    private LocalDateTime createdAt;
}

// 레포지토리
public interface OrderRepository extends ReactiveCrudRepository<Order, Long> {

    Flux<Order> findByUserId(Long userId);

    Flux<Order> findByStatus(OrderStatus status);

    @Query("SELECT * FROM orders WHERE user_id = :userId AND status = :status ORDER BY created_at DESC LIMIT :limit")
    Flux<Order> findRecentOrdersByUserAndStatus(
        @Param("userId") Long userId,
        @Param("status") String status,
        @Param("limit") int limit
    );
}
```

### 서비스 레이어 - 반응형 체이닝

```java
@Service
@RequiredArgsConstructor
@Slf4j
public class OrderService {

    private final OrderRepository orderRepository;
    private final DatabaseClient databaseClient;
    private final TransactionalOperator transactionalOperator;

    // 단순 조회
    public Mono<Order> findById(Long orderId) {
        return orderRepository.findById(orderId)
            .switchIfEmpty(Mono.error(new OrderNotFoundException(orderId)))
            .doOnNext(order -> log.debug("Order found: {}", order.getId()));
    }

    // 사용자의 주문 목록 조회 (페이지네이션)
    public Flux<Order> findUserOrders(Long userId, int page, int size) {
        return databaseClient.sql("""
                SELECT * FROM orders
                WHERE user_id = :userId
                ORDER BY created_at DESC
                LIMIT :size OFFSET :offset
                """)
            .bind("userId", userId)
            .bind("size", size)
            .bind("offset", (long) page * size)
            .mapProperties(Order.class)
            .all();
    }

    // 트랜잭션을 활용한 주문 생성
    public Mono<Order> createOrder(OrderCreateRequest request) {
        Order newOrder = Order.builder()
            .userId(request.getUserId())
            .productName(request.getProductName())
            .quantity(request.getQuantity())
            .totalPrice(request.getTotalPrice())
            .status(OrderStatus.PENDING)
            .createdAt(LocalDateTime.now())
            .build();

        return transactionalOperator.transactional(
            orderRepository.save(newOrder)
                .flatMap(this::processPayment)
                .flatMap(this::updateInventory)
                .doOnSuccess(order -> log.info("Order created successfully: {}", order.getId()))
                .doOnError(e -> log.error("Order creation failed", e))
        );
    }

    // @Transactional 어노테이션 방식 (권장)
    @Transactional
    public Mono<Void> cancelOrder(Long orderId) {
        return orderRepository.findById(orderId)
            .switchIfEmpty(Mono.error(new OrderNotFoundException(orderId)))
            .filter(order -> order.getStatus() == OrderStatus.PENDING)
            .switchIfEmpty(Mono.error(new InvalidOrderStateException("Cannot cancel non-pending order")))
            .flatMap(order -> {
                order.setStatus(OrderStatus.CANCELLED);
                return orderRepository.save(order);
            })
            .then();
    }

    // 집계 쿼리 - DatabaseClient 직접 사용
    public Mono<OrderSummary> getOrderSummary(Long userId) {
        return databaseClient.sql("""
                SELECT 
                    COUNT(*) as total_orders,
                    SUM(total_price) as total_amount,
                    AVG(total_price) as avg_amount
                FROM orders
                WHERE user_id = :userId AND status != 'CANCELLED'
                """)
            .bind("userId", userId)
            .map(row -> OrderSummary.builder()
                .totalOrders(row.get("total_orders", Long.class))
                .totalAmount(row.get("total_amount", BigDecimal.class))
                .avgAmount(row.get("avg_amount", BigDecimal.class))
                .build())
            .one();
    }

    private Mono<Order> processPayment(Order order) {
        // 결제 처리 로직
        return Mono.just(order);
    }

    private Mono<Order> updateInventory(Order order) {
        // 재고 업데이트 로직
        return Mono.just(order);
    }
}
```

### WebFlux 핸들러와의 통합

```java
@RestController
@RequestMapping("/api/orders")
@RequiredArgsConstructor
public class OrderController {

    private final OrderService orderService;

    @GetMapping("/{orderId}")
    public Mono<ResponseEntity<Order>> getOrder(@PathVariable Long orderId) {
        return orderService.findById(orderId)
            .map(ResponseEntity::ok)
            .onErrorReturn(OrderNotFoundException.class, ResponseEntity.notFound().build());
    }

    @GetMapping("/users/{userId}")
    public Flux<Order> getUserOrders(
        @PathVariable Long userId,
        @RequestParam(defaultValue = "0") int page,
        @RequestParam(defaultValue = "20") int size
    ) {
        return orderService.findUserOrders(userId, page, size);
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public Mono<Order> createOrder(@RequestBody @Validated OrderCreateRequest request) {
        return orderService.createOrder(request);
    }

    // SSE를 활용한 실시간 스트리밍
    @GetMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<Order> streamNewOrders() {
        return orderService.streamPendingOrders()
            .delayElements(Duration.ofSeconds(1));
    }
}
```

```java
@SpringBootTest
@AutoConfigureR2dbcDatabasePopulator  
class OrderServiceIntegrationTest {

    @Autowired
    private OrderService orderService;

    @Autowired
    private OrderRepository orderRepository;

    @Test
    void createOrder_shouldPersistAndReturnOrder() {
        OrderCreateRequest request = OrderCreateRequest.builder()
            .userId(1L)
            .productName("테스트 상품")
            .quantity(2)
            .totalPrice(new BigDecimal("29900"))
            .build();

        StepVerifier.create(orderService.createOrder(request))
            .assertNext(order -> {
                assertThat(order.getId()).isNotNull();
                assertThat(order.getStatus()).isEqualTo(OrderStatus.PENDING);
                assertThat(order.getProductName()).isEqualTo("테스트 상품");
            })
            .verifyComplete();
    }

    @Test
    void findUserOrders_shouldReturnPagedResults() {
        StepVerifier.create(orderService.findUserOrders(1L, 0, 5))
            .expectNextCount(5)
            .verifyComplete();
    }
}
```

## 주의사항 및 트레이드오프

### 1. JPA 기능 부재에 따른 설계 변화

R2DBC는 연관 관계(Relation) 매핑을 자동으로 처리하지 않는다. `@OneToMany`, `@ManyToOne` 같은 어노테이션이 없기 때문에, **조인 쿼리는 `DatabaseClient`로 직접 작성**하거나 별도의 조회 후 조립(Assemble) 패턴을 사용해야 한다.

```java
// 연관 엔티티 수동 조립 예시
public Mono<OrderWithUser> findOrderWithUser(Long orderId) {
    return orderRepository.findById(orderId)
        .zipWith(userRepository.findById(/* userId */))
        .map(tuple -> new OrderWithUser(tuple.getT1(), tuple.getT2()));
}
```

### 2. 트랜잭션 전파의 차이

JPA의 `@Transactional`은 ThreadLocal에 트랜잭션을 바인딩하지만, R2DBC의 트랜잭션은 **Reactor Context**에 저장된다. 따라서 반드시 **리액티브 파이프라인 안에서 연산이 완결**되어야 하며, 파이프라인 밖에서 블로킹 코드를 섞으면 트랜잭션이 의도대로 동작하지 않는다.

### 3. N+1 문제 주의

JPA의 경우 배치 조회 전략으로 N+1 문제를 일부 완화할 수 있지만, R2DBC에서는 수동으로 `flatMap` + 개별 조회를 구성할 경우 N+1이 쉽게 발생한다. 이 경우 `DatabaseClient`로 조인 쿼리를 직접 작성하거나, `IN` 절을 사용한 배치 조회를 고려해야 한다.

```java
// 나쁜 예: N+1 패턴
Flux<OrderWithUser> badPattern = orderRepository.findAll()
    .flatMap(order -> userRepository.findById(order.getUserId())
        .map(user -> new OrderWithUser(order, user)));

// 좋은 예: 배치 조회
Flux<OrderWithUser> goodPattern = orderRepository.findAll()
    .collectList()
    .flatMapMany(orders -> {
        List<Long> userIds = orders.stream().map(Order::getUserId).toList();
        return userRepository.findAllById(userIds)
            .collectMap(User::getId)
            .flatMapMany(userMap -> Flux.fromIterable(orders)
                .map(order -> new OrderWithUser(order, userMap.get(order.getUserId()))));
    });
```

### 4. 마이그레이션 도구의 블로킹 한계

Flyway와 Liquibase는 JDBC 기반이기 때문에 R2DBC와 직접 통합되지 않는다. 애플리케이션 구동 시 **별도의 JDBC DataSource를 구성**해 마이그레이션을 선행 실행하는 방식으로 우회해야 한다.

### 5. 커넥션 풀 튜닝

r2dbc-pool의 `max-size`를 무작정 크게 잡는 것은 금물이다. Non-blocking 모델에서는 적은 수의 커넥션으로도 높은 처리량을 달성할 수 있으므로, **CPU 코어 수 × 2 ~ 4** 정도를 기본값으로 두고 부하 테스트를 통해 조정하는 것이 바람직하다.

## 정리

R2DBC는 **진정한 Non-blocking 반응형 시스템**을 구축하려는 팀에게 강력한 선택지다. 다만 JPA에 익숙한 개발자에게는 상당한 패러다임 전환이 요구된다. 다음 기준으로 도입 여부를 판단하자.

| 상황 | 권장 선택 |
|---|---|
| 높은 동시성, 실시간 스트리밍 요구 | R2DBC + WebFlux |
| 복잡한 도메인 모델, 다양한 조인 | JPA + Spring MVC |
| 기존 블로킹 레거시와 혼용 | 별도 마이크로서비스로 분리 |
| 팀 내 Reactive 경험 부족 | 충분한 학습 후 점진적 도입 |

R2DBC는 은탄환이 아니다. 그러나 고성능 비동기 데이터 파이프라인이 필요한 곳에서, 올바르게 적용된 R2DBC는 시스템의 처리량과 자원 효율을 극적으로 향상시킬 수 있다. WebFlux와 함께 전체 스택을 반응형으로 구성할 때 R2DBC는 빠질 수 없는 핵심 퍼즐 조각이다.
