# TCP 혼잡 제어 알고리즘과 성능 영향

## 개요

네트워크 엔지니어링에서 TCP 혼잡 제어(Congestion Control)는 단순한 이론을 넘어 실제 서비스 성능에 직접적인 영향을 미치는 핵심 메커니즘이다. 대용량 파일 전송, 스트리밍 서비스, 마이크로서비스 간 통신 등 다양한 시나리오에서 어떤 혼잡 제어 알고리즘을 선택하느냐에 따라 처리량(throughput)과 지연 시간(latency)이 크게 달라질 수 있다.

이 포스팅에서는 대표적인 TCP 혼잡 제어 알고리즘의 동작 원리와 차이점을 살펴보고, Linux 커널 설정과 Java 애플리케이션 레벨에서 실제로 활용할 수 있는 방법을 다룬다. 특히 클라우드 환경과 고성능 서버 운영 관점에서 각 알고리즘의 트레이드오프를 중점적으로 분석한다.

## 핵심 개념

### TCP 혼잡 제어의 기본 원리

TCP 혼잡 제어는 네트워크 혼잡을 감지하고 전송 속도를 조절하여 패킷 손실을 최소화하는 메커니즘이다. 핵심 변수는 다음과 같다.

- **cwnd (Congestion Window)**: 송신자가 ACK 없이 보낼 수 있는 최대 데이터 양
- **ssthresh (Slow Start Threshold)**: Slow Start와 Congestion Avoidance 전환 기준값
- **RTT (Round Trip Time)**: 패킷의 왕복 시간

혼잡 감지 방식은 크게 두 가지로 나뉜다.

- **손실 기반(Loss-based)**: 패킷 손실을 혼잡 신호로 간주 (Reno, CUBIC)
- **지연 기반(Delay-based)**: RTT 증가를 혼잡 신호로 간주 (Vegas, BBR)

### 주요 알고리즘 비교

#### TCP Reno (전통적 알고리즘)

가장 오래된 알고리즘으로, Slow Start → Congestion Avoidance → Fast Retransmit → Fast Recovery 단계로 구성된다. 패킷 손실 발생 시 cwnd를 절반으로 줄이는 방식이라 고대역폭-고지연(High BDP) 환경에서 성능이 낮다.

#### TCP CUBIC (Linux 기본값)

현재 Linux 커널의 기본 알고리즘으로, cwnd 증가 패턴을 3차 함수(cubic function)로 모델링한다. 손실 발생 지점 근처에서는 완만하게 증가하고, 멀어질수록 빠르게 증가한다. 고대역폭 환경에서 Reno 대비 훨씬 공격적으로 대역폭을 활용한다.

#### BBR (Bottleneck Bandwidth and RTT)

Google이 2016년 개발한 알고리즘으로, 실제 병목 대역폭과 RTT를 지속적으로 측정하여 최적의 전송 속도를 찾는다. 손실이 아닌 실제 네트워크 상태를 모델링하는 방식이라 장거리 고지연 환경에서 탁월한 성능을 보인다.

## 실전 예제

### Linux 커널 혼잡 제어 알고리즘 확인 및 변경

```bash
# 현재 사용 중인 혼잡 제어 알고리즘 확인
sysctl net.ipv4.tcp_congestion_control

# 사용 가능한 알고리즘 목록 확인
sysctl net.ipv4.tcp_available_congestion_control

# BBR로 변경 (즉시 적용)
sudo sysctl -w net.ipv4.tcp_congestion_control=bbr

# 영구 적용 (/etc/sysctl.conf 또는 /etc/sysctl.d/)
echo "net.ipv4.tcp_congestion_control=bbr" | sudo tee /etc/sysctl.d/99-bbr.conf
sudo sysctl --system

# BBR 사용 시 권장 설정 (fq qdisc와 함께 사용)
sudo tc qdisc replace dev eth0 root fq
```

BBR은 반드시 `fq` (Fair Queuing) qdisc와 함께 사용해야 최대 성능을 낼 수 있다.

### TCP 소켓 성능 튜닝 (시스템 버퍼 설정)

```bash
# TCP 송수신 버퍼 크기 최적화
sudo sysctl -w net.core.rmem_max=134217728      # 128MB
sudo sysctl -w net.core.wmem_max=134217728
sudo sysctl -w net.ipv4.tcp_rmem="4096 87380 134217728"
sudo sysctl -w net.ipv4.tcp_wmem="4096 65536 134217728"

# BBR에서 권장되는 추가 설정
sudo sysctl -w net.ipv4.tcp_mtu_probing=1        # MTU 탐색 활성화
sudo sysctl -w net.core.default_qdisc=fq
```

### Java에서 TCP 소켓 옵션 제어

Java 애플리케이션에서는 커널 수준의 혼잡 제어 알고리즘을 직접 바꿀 수는 없지만, 소켓 버퍼 및 연결 옵션을 최적화하여 성능을 향상시킬 수 있다.

```java
import java.net.*;
import java.nio.channels.*;
import java.io.*;

public class OptimizedServerSocket {

    public static ServerSocket createOptimizedServer(int port) throws IOException {
        ServerSocket serverSocket = new ServerSocket();

        // SO_REUSEADDR: TIME_WAIT 상태 포트 재사용
        serverSocket.setReuseAddress(true);

        // SO_RCVBUF: 수신 버퍼 크기 (커널 설정과 일치 권장)
        serverSocket.setReceiveBufferSize(128 * 1024 * 1024); // 128MB

        serverSocket.bind(new InetSocketAddress(port));
        return serverSocket;
    }

    public static Socket createOptimizedClientSocket(String host, int port)
            throws IOException {
        Socket socket = new Socket();

        // TCP_NODELAY: Nagle 알고리즘 비활성화 (저지연 우선)
        socket.setTcpNoDelay(true);

        // SO_KEEPALIVE: 연결 유지 확인
        socket.setKeepAlive(true);

        // 송수신 버퍼 크기 설정
        socket.setSendBufferSize(128 * 1024 * 1024);
        socket.setReceiveBufferSize(128 * 1024 * 1024);

        // SO_LINGER: 연결 종료 시 데이터 전송 보장 (초 단위)
        socket.setSoLinger(true, 0);

        socket.connect(new InetSocketAddress(host, port), 5000);
        return socket;
    }
}
```

### NIO를 활용한 고성능 서버 구현

```java
import java.io.IOException;
import java.net.InetSocketAddress;
import java.net.StandardSocketOptions;
import java.nio.ByteBuffer;
import java.nio.channels.*;
import java.util.Iterator;

public class NioOptimizedServer {

    private static final int PORT = 8080;
    private static final int BUFFER_SIZE = 65536; // 64KB

    public static void main(String[] args) throws IOException {
        Selector selector = Selector.open();
        ServerSocketChannel serverChannel = ServerSocketChannel.open();

        // 소켓 옵션 설정
        serverChannel.setOption(StandardSocketOptions.SO_REUSEADDR, true);
        serverChannel.setOption(StandardSocketOptions.SO_RCVBUF, 4 * 1024 * 1024);
        serverChannel.configureBlocking(false);
        serverChannel.bind(new InetSocketAddress(PORT), 1024); // backlog 설정
        serverChannel.register(selector, SelectionKey.OP_ACCEPT);

        System.out.println("Server started on port " + PORT);

        while (true) {
            selector.select();
            Iterator<SelectionKey> keys = selector.selectedKeys().iterator();

            while (keys.hasNext()) {
                SelectionKey key = keys.next();
                keys.remove();

                if (key.isAcceptable()) {
                    handleAccept(serverChannel, selector);
                } else if (key.isReadable()) {
                    handleRead(key);
                }
            }
        }
    }

    private static void handleAccept(ServerSocketChannel serverChannel,
                                      Selector selector) throws IOException {
        SocketChannel clientChannel = serverChannel.accept();
        if (clientChannel != null) {
            clientChannel.configureBlocking(false);
            // TCP_NODELAY: 지연 최소화
            clientChannel.setOption(StandardSocketOptions.TCP_NODELAY, true);
            clientChannel.setOption(StandardSocketOptions.SO_KEEPALIVE, true);
            clientChannel.setOption(StandardSocketOptions.SO_SNDBUF, 4 * 1024 * 1024);

            clientChannel.register(selector, SelectionKey.OP_READ,
                    ByteBuffer.allocateDirect(BUFFER_SIZE));
        }
    }

    private static void handleRead(SelectionKey key) throws IOException {
        SocketChannel channel = (SocketChannel) key.channel();
        ByteBuffer buffer = (ByteBuffer) key.attachment();
        buffer.clear();

        int bytesRead = channel.read(buffer);
        if (bytesRead == -1) {
            channel.close();
            return;
        }

        buffer.flip();
        // 에코 처리 (실제 비즈니스 로직으로 대체)
        channel.write(buffer);
    }
}
```

### 혼잡 제어 성능 측정 스크립트

```bash
#!/bin/bash
# iperf3를 이용한 알고리즘별 성능 비교 테스트

ALGORITHMS=("cubic" "bbr" "reno")
SERVER_IP="192.168.1.100"
DURATION=30

for algo in "${ALGORITHMS[@]}"; do
    echo "=== Testing $algo ==="

    # 커널 알고리즘 변경
    sudo sysctl -w net.ipv4.tcp_congestion_control=$algo

    # iperf3 테스트 (병렬 스트림 4개)
    iperf3 -c $SERVER_IP \
           -t $DURATION \
           -P 4 \
           --json \
           -o "result_${algo}.json"

    # 결과 파싱
    python3 -c "
import json
with open('result_${algo}.json') as f:
    data = json.load(f)
    bps = data['end']['sum_received']['bits_per_second']
    retrans = data['end']['sum_sent']['retransmits']
    print(f'Algorithm: ${algo}')
    print(f'Throughput: {bps/1e9:.2f} Gbps')
    print(f'Retransmits: {retrans}')
    print()
"
done
```

## 주의사항 및 트레이드오프

### 1. BBR이 항상 최선은 아니다

BBR은 장거리(RTT > 40ms) 고대역폭 환경에서 탁월하지만, LAN 환경(RTT < 1ms)에서는 CUBIC과 큰 차이가 없거나 오히려 오버헤드가 생길 수 있다. 또한 BBR v1은 **공유 네트워크에서 CUBIC 기반 트래픽보다 불공정하게 대역폭을 점유**하는 문제가 보고된 바 있다. Google이 개발한 BBR v3는 이 문제를 일부 개선했지만, 프로덕션 적용 전 충분한 테스트가 필요하다.

### 2. TCP_NODELAY와 Nagle 알고리즘

`TCP_NODELAY`는 소규모 패킷을 즉시 전송하므로 저지연 시스템(게임 서버, 실시간 API)에 유리하지만, 대량의 소규모 패킷이 발생하여 네트워크 효율이 떨어질 수 있다. 대용량 배치 전송이 주인 시스템에서는 Nagle 알고리즘을 활성화(기본값)하는 것이 처리량 측면에서 유리하다.

### 3. 버퍼 크기 설정의 딜레마

버퍼를 크게 설정하면 처리량은 높아지지만 **버퍼 블로트(Bufferbloat)** 문제로 지연이 증가할 수 있다. 고처리량과 저지연을 동시에 달성하려면 BDP(Bandwidth-Delay Product) 기반으로 버퍼를 계산해야 한다.

```
최적 버퍼 크기 = 대역폭(bps) × RTT(초)
예) 1Gbps × 0.05s (50ms RTT) = 6.25MB
```

### 4. 클라우드 환경에서의 고려사항

AWS, GCP 등 클라우드 환경에서는 가상화 계층으로 인해 실제 RTT가 물리 환경과 다를 수 있으며, 인스턴스 타입에 따라 네트워크 성능 한계가 다르다. EC2 Enhanced Networking(ENA) 환경에서는 BBR을 활성화하면 Inter-AZ 통신에서 유의미한 성능 향상을 얻을 수 있다. 단, 같은 인스턴스 내 통신(loopback)에서는 혼잡 제어 알고리즘이 영향을 미치지 않는다.

### 5. 알고리즘 선택 가이드

| 환경 | 권장 알고리즘 | 이유 |
|---|---|---|
| 일반 데이터센터 LAN | CUBIC | 안정적, 공정한 대역폭 공유 |
| 장거리 WAN / CDN | BBR | 고지연 환경 처리량 극대화 |
| 실시간 게임/트레이딩 | CUBIC + TCP_NODELAY | 저지연 우선 |
| 대용량 파일 전송 | BBR 또는 CUBIC | 처리량 우선 |
| 혼합 트래픽 환경 | CUBIC | 공정성 보장 |

## 정리

TCP 혼잡 제어 알고리즘은 "한 가지가 모든 상황에 최적"이라는 Silver Bullet이 존재하지 않는다. CUBIC은 안정적이고 공정하며 대부분의 환경에서 검증된 선택이고, BBR은 장거리 고지연 환경에서 처리량을 극적으로 향상시킬 수 있는 강력한 도구다.

실무에서 중요한 것은 다음 세 가지다.

1. **측정이 먼저다**: `iperf3`, `ss`, `tcpdump` 등으로 현재 네트워크 상태를 먼저 파악하라.
2. **환경에 맞는 알고리즘을 선택하라**: RTT, 대역폭, 트래픽 패턴에 따라 최적 알고리즘이 다르다.
3. **Java/애플리케이션 레벨 최적화와 병행하라**: 커널 설정만으로는 한계가 있으며, 소켓 버퍼 크기, TCP_NODELAY, Keep-Alive 설정을 함께 고려해야 한다.

혼잡 제어는 네트워크 스택 전체의 문제이므로, 커널 파라미터 튜닝부터 애플리케이션 소켓 설정까지 전체적인 관점에서 접근하는 것이 핵심이다. 변경 후에는 반드시 프로덕션과 유사한 환경에서 충분한 부하 테스트를 거쳐 사이드 이펙트를 검증하길 권장한다.
