# ZFS 기반 스토리지 성능·비용 최적화

## 개요

데이터 집약적 서비스를 운영하다 보면 스토리지는 항상 성능과 비용 사이의 팽팽한 줄다리기 지점이 된다. NVMe SSD 전체를 데이터 볼륨으로 쓰기엔 비용이 부담스럽고, 그렇다고 HDD만 사용하기엔 I/O 레이턴시가 발목을 잡는다. 이 딜레마를 해소하는 현실적인 선택지 중 하나가 **ZFS(Zettabyte File System)** 다.

ZFS는 Sun Microsystems가 개발하고 OpenZFS 프로젝트로 계승된 파일 시스템이자 볼륨 매니저다. Copy-on-Write, 내장 압축, 중복 제거, 계층형 캐시(ARC/L2ARC/ZIL) 같은 기능을 운영체제 레벨에서 제공한다. 단순히 "파일 시스템 하나 더 쓴다"는 개념이 아니라, **스토리지 아키텍처 자체를 재설계하는 도구**로 접근해야 제값을 낸다.

이 글에서는 ZFS의 핵심 캐시 계층 구조를 이해하고, 실무에서 성능과 비용을 동시에 잡을 수 있는 구성 예제와 튜닝 포인트를 다룬다.

## 핵심 개념

### ZFS 캐시 계층 구조

ZFS의 I/O 성능 최적화를 이해하려면 세 가지 캐시 컴포넌트를 먼저 파악해야 한다.

```
┌─────────────────────────────────────┐
│           Application I/O           │
└─────────────┬───────────────────────┘
              │
       ┌──────▼──────┐
       │  ARC (RAM)  │  ← L1 읽기 캐시 (메모리)
       └──────┬──────┘
              │ Miss
       ┌──────▼──────┐
       │  L2ARC(SSD) │  ← L2 읽기 캐시 (저렴한 SSD)
       └──────┬──────┘
              │ Miss
       ┌──────▼──────┐
       │  ZIL (SSD)  │  ← 쓰기 인텐트 로그 (SLOG 장치)
       └──────┬──────┘
              │
       ┌──────▼──────┐
       │  vdev (HDD) │  ← 실제 데이터 풀 (대용량 HDD)
       └─────────────┘
```

- **ARC (Adaptive Replacement Cache)**: 메모리를 L1 캐시로 사용. 기본적으로 전체 RAM의 약 50~75%를 차지한다.
- **L2ARC**: ARC의 확장으로, SSD를 읽기 캐시로 활용. ARC 미스 시 L2ARC를 탐색하고, 여기서도 미스가 나면 실제 디스크를 읽는다.
- **ZIL/SLOG**: 동기 쓰기의 내구성을 보장하기 위한 Write-Ahead Log. 별도 SSD(SLOG 장치)로 분리하면 쓰기 레이턴시를 극적으로 줄일 수 있다.

### Pool 구성 전략 (vdev 토폴로지)

| 구성 | 내용 | 적합한 워크로드 |
|------|------|----------------|
| mirror | 2개 이상 디스크를 미러링 | 읽기 중심, 높은 IOPS 필요 |
| RAIDZ1 | 패리티 1개, 1디스크 장애 허용 | 순차 쓰기, 대용량 저장 |
| RAIDZ2 | 패리티 2개, 2디스크 장애 허용 | 중요 데이터, 균형 구성 |
| RAIDZ3 | 패리티 3개, 3디스크 허용 | 아카이브, 안정성 최우선 |
| dRAID | 분산 스페어 | 대형 클러스터, 빠른 리빌드 |

> **실무 팁**: 랜덤 읽기 성능이 중요하다면 RAIDZ보다 mirror vdev 여러 개를 조합하는 방식이 낫다. RAIDZ는 전체 stripe를 읽어야 하기 때문에 랜덤 읽기에 불리하다.

## 실전 예제

### 1. ZFS Pool 생성 및 기본 설정

```bash
# HDD 4개로 RAIDZ2 풀 구성 (2디스크 장애 허용)
zpool create \
  -o ashift=12 \
  datapool raidz2 \
  /dev/sdb /dev/sdc /dev/sdd /dev/sde

# ashift=12는 4KB 섹터 정렬. HDD/SSD 모두 현대 장치는 12가 권장값
# ashift=13은 8KB 섹터 장치 (일부 NVMe) 에 사용

# SLOG(ZIL) 장치 추가 - NVMe SSD 사용 권장
zpool add datapool log /dev/nvme0n1

# L2ARC 장치 추가 - SATA SSD로 비용 절감 가능
zpool add datapool cache /dev/sdf
```

### 2. 압축 및 레코드 크기 최적화

```bash
# ZFS 데이터셋 생성 및 압축 활성화
zfs create datapool/database
zfs set compression=lz4 datapool/database

# 레코드 크기는 워크로드에 맞게 조정
# 데이터베이스 (PostgreSQL, MySQL): 16K 또는 8K
zfs set recordsize=16K datapool/database

# 로그, 백업, 아카이브: 1M
zfs create datapool/archive
zfs set compression=zstd-3 datapool/archive
zfs set recordsize=1M datapool/archive

# 현재 설정 확인
zfs get compression,recordsize,compressratio datapool/database
```

```
NAME               PROPERTY       VALUE     SOURCE
datapool/database  compression    lz4       local
datapool/database  recordsize     16K       local
datapool/database  compressratio  2.14x     -
```

### 3. ARC 크기 튜닝

```bash
# 현재 ARC 사용량 확인
arc_summary | grep -E "ARC|Size"

# /etc/modprobe.d/zfs.conf 또는 /etc/sysctl.d/zfs.conf 에 설정
# RAM 64GB 서버에서 ARC 최대 48GB로 제한 (나머지는 애플리케이션용)
cat >> /etc/modprobe.d/zfs.conf <<EOF
options zfs zfs_arc_max=51539607552
EOF

# 런타임 즉시 적용 (재부팅 불필요)
echo 51539607552 > /sys/module/zfs/parameters/zfs_arc_max

# ARC 통계 실시간 모니터링
zpool iostat -v datapool 2
```

### 4. 스냅샷 기반 백업 자동화 스크립트

ZFS의 Copy-on-Write 특성을 활용한 스냅샷은 거의 비용 없이 시점 복구 지점을 만들 수 있다. 아래는 보존 정책을 포함한 자동화 스크립트다.

```bash
#!/usr/bin/env bash
# zfs_snapshot.sh - ZFS 스냅샷 자동 생성 및 정리

set -euo pipefail

DATASET="datapool/database"
SNAPSHOT_PREFIX="auto"
KEEP_HOURLY=24
KEEP_DAILY=7
KEEP_WEEKLY=4

create_snapshot() {
  local label="$1"
  local timestamp
  timestamp=$(date +%Y%m%dT%H%M%S)
  local snap_name="${DATASET}@${SNAPSHOT_PREFIX}-${label}-${timestamp}"

  zfs snapshot "$snap_name"
  echo "[$(date)] Snapshot created: $snap_name"
}

cleanup_snapshots() {
  local label="$1"
  local keep="$2"

  local snaps
  snaps=$(zfs list -H -t snapshot -o name -s creation \
    | grep "${DATASET}@${SNAPSHOT_PREFIX}-${label}-" \
    | head -n -"$keep")

  if [[ -n "$snaps" ]]; then
    echo "$snaps" | while read -r snap; do
      zfs destroy "$snap"
      echo "[$(date)] Destroyed: $snap"
    done
  fi
}

main() {
  local mode="${1:-hourly}"

  case "$mode" in
    hourly)
      create_snapshot "hourly"
      cleanup_snapshots "hourly" "$KEEP_HOURLY"
      ;;
    daily)
      create_snapshot "daily"
      cleanup_snapshots "daily" "$KEEP_DAILY"
      ;;
    weekly)
      create_snapshot "weekly"
      cleanup_snapshots "weekly" "$KEEP_WEEKLY"
      ;;
    *)
      echo "Usage: $0 {hourly|daily|weekly}"
      exit 1
      ;;
  esac
}

main "$@"
```

```bash
# crontab 등록
# 매시간 hourly 스냅샷
0 * * * * /usr/local/bin/zfs_snapshot.sh hourly

# 매일 자정 daily 스냅샷
0 0 * * * /usr/local/bin/zfs_snapshot.sh daily

# 매주 일요일 weekly 스냅샷
0 0 * * 0 /usr/local/bin/zfs_snapshot.sh weekly
```

### 5. zpool 상태 모니터링 및 알림

```bash
#!/usr/bin/env bash
# zfs_health_check.sh - 풀 상태 점검 및 Slack 알림

SLACK_WEBHOOK_URL="${SLACK_WEBHOOK_URL:-}"
POOLS=$(zpool list -H -o name)

check_pool_health() {
  local pool="$1"
  local health
  health=$(zpool list -H -o health "$pool")

  if [[ "$health" != "ONLINE" ]]; then
    local detail
    detail=$(zpool status "$pool")
    send_alert "⚠️ ZFS Pool Alert" \
      "Pool: *${pool}*\nStatus: *${health}*\n\`\`\`${detail}\`\`\`"
  fi
}

check_scrub_age() {
  local pool="$1"
  local last_scrub
  last_scrub=$(zpool status "$pool" \
    | grep "scan:" \
    | grep -oP '\w+ \d+ \d{4}')

  echo "[INFO] Pool $pool last scrub: $last_scrub"
}

send_alert() {
  local title="$1"
  local message="$2"

  if [[ -n "$SLACK_WEBHOOK_URL" ]]; then
    curl -s -X POST "$SLACK_WEBHOOK_URL" \
      -H 'Content-type: application/json' \
      -d "{\"text\": \"${title}\n${message}\"}"
  fi
}

for pool in $POOLS; do
  check_pool_health "$pool"
  check_scrub_age "$pool"
done
```

## 주의사항 및 트레이드오프

### L2ARC의 함정

L2ARC를 추가한다고 무조건 성능이 좋아지지 않는다. L2ARC 메타데이터는 **반드시 ARC(RAM)에 올라가야** 한다. L2ARC 용량 1TB당 약 1~5GB의 ARC 메모리가 메타데이터로 소비된다. RAM이 부족한 서버에서 대용량 L2ARC를 붙이면 오히려 ARC 공간이 줄어들어 전체 캐시 효율이 떨어질 수 있다.

**적용 기준**: L2ARC는 워크로드의 working set이 ARC보다 크고, 동일 블록의 재접근 빈도가 높은 읽기 중심 시스템에서만 효과적이다.

### RAIDZ vs Mirror 선택

- **RAIDZ**: 공간 효율은 좋지만 쓰기 시 full stripe를 구성해야 하므로 **랜덤 쓰기 성능이 낮다**. 또한 리빌드 시간이 매우 길다(대용량 HDD의 경우 수일 소요 가능).
- **Mirror**: 공간 효율은 50%지만, 랜덤 읽기/쓰기 모두 우수하고 리빌드가 빠르다.

데이터베이스, 메시지 큐처럼 랜덤 I/O가 많은 시스템은 mirror vdev를 선택해야 한다.

### 중복 제거(dedup)는 신중하게

ZFS의 dedup은 블록 단위 중복 제거로 저장 공간을 줄일 수 있지만, **dedup 테이블(DDT)이 모두 ARC에 올라가야** 실시간 성능이 유지된다. DDT는 1TB당 최소 5GB 이상의 RAM을 요구한다. 메모리 압박 환경에서 dedup을 활성화하면 시스템 전체가 심각하게 느려질 수 있다. 대부분의 경우 compression으로 대체하는 것이 더 실용적이다.

### 정기 scrub 스케줄링

ZFS는 Silent Data Corruption 감지를 위해 주기적인 scrub이 필요하다. 단, scrub은 I/O 부하를 유발하므로 트래픽이 낮은 시간대에 스케줄링해야 한다.

```bash
# 매월 1일 새벽 2시에 scrub 실행
echo "0 2 1 * * root zpool scrub datapool" >> /etc/cron.d/zfs-scrub

# scrub 우선순위 제한 (I/O 영향 최소화)
echo 10 > /sys/module/zfs/parameters/zfs_scrub_delay
```

## 정리

ZFS를 올바르게 활용하면 **비싼 올-플래시 스토리지 없이도 충분한 성능**을 확보할 수 있다. 핵심은 워크로드 특성을 먼저 분석하고, 그에 맞는 계층 구조를 설계하는 것이다.

| 최적화 항목 | 권장 설정 | 효과 |
|------------|----------|------|
| 압축 | lz4 (일반), zstd-3 (아카이브) | 공간 절감 + I/O 감소 |
| recordsize | DB 8~16K, 로그 1M | 워크로드별 I/O 효율화 |
| SLOG (ZIL) | 저지연 NVMe | 동기 쓰기 레이턴시 감소 |
| L2ARC | SATA SSD | 읽기 캐시 확장 (RAM 충분 시) |
| ARC 상한 | RAM의 50~75% | 애플리케이션과 메모리 공유 |
| scrub 주기 | 월 1회 이상 | 데이터 무결성 보장 |

ZFS는 도입 초기 설정이 까다롭지만, 한번 올바르게 구성하면 **스냅샷, 압축, 캐시 계층화를 통해 스토리지 TCO를 크게 낮출 수 있다**. 특히 대용량 데이터를 다루는 백엔드 시스템, 데이터 파이프라인, 온프레미스 데이터베이스 서버에서 그 가치가 두드러진다. 운영 중인 시스템의 I/O 패턴을 `zpool iostat`과 `arc_summary`로 먼저 측정하고, 병목 지점을 확인한 뒤 단계적으로 튜닝을 적용하는 접근을 권장한다.
