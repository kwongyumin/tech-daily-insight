# 네트워크 지연 측정과 RTT 최적화 기법

## 개요

분산 시스템과 마이크로서비스 아키텍처가 일반화된 오늘날, 네트워크 지연(Latency)은 시스템 성능을 결정짓는 핵심 변수다. 특히 **RTT(Round-Trip Time)** 는 클라이언트가 요청을 보내고 응답을 받기까지 걸리는 시간을 나타내며, 이 값 하나가 사용자 경험과 서비스 안정성에 직접적인 영향을 미친다.

실무에서는 "느리다"는 막연한 인식만으로는 문제를 해결할 수 없다. 지연이 발생하는 구간을 정확히 측정하고, 데이터 기반으로 최적화 전략을 수립해야 한다. 이 글에서는 RTT의 구성 요소부터 실전 측정 방법, 그리고 Java/Spring 환경에서 바로 적용할 수 있는 최적화 기법까지 체계적으로 다룬다.

## 핵심 개념

### RTT의 구성 요소

RTT는 단일 값처럼 보이지만 실제로는 여러 레이어의 지연이 누적된 결과다.

```
RTT = 전파 지연(Propagation Delay)
    + 전송 지연(Transmission Delay)
    + 처리 지연(Processing Delay)
    + 큐잉 지연(Queuing Delay)
```

- **전파 지연**: 물리적 거리에 의한 빛의 속도 제한. 서울 → 뉴욕 구간은 이론상 최소 ~70ms
- **전송 지연**: 패킷 크기 / 대역폭. 대용량 페이로드일수록 증가
- **처리 지연**: 라우터, 프록시, 서버의 실제 처리 시간
- **큐잉 지연**: 네트워크 혼잡 시 버퍼에서 대기하는 시간. 가장 변동폭이 크다

### TCP 핸드셰이크와 지연의 관계

TCP 기반 연결에서 실제 데이터 전송 전에 1.5 RTT가 소요된다. HTTPS의 경우 TLS 핸드셰이크까지 더해져 최대 3~4 RTT가 초기 연결에서 낭비된다. 이것이 **Keep-Alive**와 **Connection Pool**이 중요한 이유다.

```
TCP 3-Way Handshake: 1.5 RTT
TLS 1.2:             2 RTT  (추가)
TLS 1.3:             1 RTT  (추가, 개선됨)
HTTP/2:              멀티플렉싱으로 RTT 절감
HTTP/3 (QUIC):       0-RTT 재연결 지원
```

## 실전 예제

### 1. 정밀한 RTT 측정 — Java 기반 계측

단순히 `System.currentTimeMillis()`를 사용하면 JVM GC 등의 영향으로 정확한 측정이 어렵다. `System.nanoTime()`을 활용하고, 워밍업 구간을 제외해야 한다.

```java
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.net.URI;
import java.time.Duration;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

public class RttMeasurer {

    private static final int WARMUP_ROUNDS = 5;
    private static final int MEASURE_ROUNDS = 50;

    public static void main(String[] args) throws Exception {
        HttpClient client = HttpClient.newBuilder()
                .connectTimeout(Duration.ofSeconds(5))
                .build();

        String targetUrl = "https://api.example.com/health";
        List<Long> latencies = new ArrayList<>();

        // 워밍업: JIT 컴파일, 커넥션 풀 준비
        for (int i = 0; i < WARMUP_ROUNDS; i++) {
            sendRequest(client, targetUrl);
        }

        // 실제 측정
        for (int i = 0; i < MEASURE_ROUNDS; i++) {
            long latency = sendRequest(client, targetUrl);
            latencies.add(latency);
        }

        printStats(latencies);
    }

    private static long sendRequest(HttpClient client, String url) throws Exception {
        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(url))
                .GET()
                .build();

        long start = System.nanoTime();
        client.send(request, HttpResponse.BodyHandlers.discarding());
        long end = System.nanoTime();

        return (end - start) / 1_000_000; // ms 변환
    }

    private static void printStats(List<Long> latencies) {
        Collections.sort(latencies);
        int size = latencies.size();

        double avg = latencies.stream().mapToLong(Long::longValue).average().orElse(0);
        long p50 = latencies.get((int) (size * 0.50));
        long p95 = latencies.get((int) (size * 0.95));
        long p99 = latencies.get((int) (size * 0.99));
        long min = latencies.get(0);
        long max = latencies.get(size - 1);

        System.out.printf("=== RTT 측정 결과 ===%n");
        System.out.printf("AVG: %.2f ms%n", avg);
        System.out.printf("MIN: %d ms | MAX: %d ms%n", min, max);
        System.out.printf("P50: %d ms | P95: %d ms | P99: %d ms%n", p50, p95, p99);
    }
}
```

> **핵심**: 평균(AVG)보다 **P95, P99** 지표를 주시해야 한다. 평균은 이상값에 둔감하며, 실제 사용자의 최악 경험은 테일 레이턴시(tail latency)에 있다.

### 2. Spring Boot에서 HTTP 클라이언트 RTT 최적화

**Connection Pool 튜닝** — Apache HttpClient 5 기반

```java
@Configuration
public class HttpClientConfig {

    @Bean
    public HttpComponentsClientHttpRequestFactory requestFactory() {
        // 커넥션 풀 설정
        PoolingHttpClientConnectionManager connectionManager =
                PoolingHttpClientConnectionManagerBuilder.create()
                        .setMaxConnTotal(200)          // 전체 최대 커넥션
                        .setMaxConnPerRoute(50)         // 라우트당 최대 커넥션
                        .setConnectionTimeToLive(TimeValue.ofMinutes(5))
                        .build();

        // 소켓 및 연결 타임아웃
        RequestConfig requestConfig = RequestConfig.custom()
                .setConnectionRequestTimeout(Timeout.ofMilliseconds(500))
                .setResponseTimeout(Timeout.ofSeconds(3))
                .build();

        CloseableHttpClient httpClient = HttpClients.custom()
                .setConnectionManager(connectionManager)
                .setDefaultRequestConfig(requestConfig)
                // TCP Keep-Alive 설정
                .setKeepAliveStrategy((response, context) -> TimeValue.ofSeconds(30))
                .evictExpiredConnections()
                .evictIdleConnections(TimeValue.ofSeconds(60))
                .build();

        HttpComponentsClientHttpRequestFactory factory =
                new HttpComponentsClientHttpRequestFactory(httpClient);

        return factory;
    }

    @Bean
    public RestTemplate restTemplate(HttpComponentsClientHttpRequestFactory factory) {
        return new RestTemplate(factory);
    }
}
```

### 3. TCP 소켓 레벨 튜닝 — Nagle 알고리즘 비활성화

소규모 패킷을 자주 전송하는 API 서버라면 **Nagle 알고리즘**이 오히려 지연을 유발한다. `TCP_NODELAY` 옵션으로 이를 비활성화할 수 있다.

```java
// Netty 기반 Spring WebFlux 설정 예시
@Configuration
public class NettyServerConfig {

    @Bean
    public NettyReactiveWebServerFactory nettyReactiveWebServerFactory() {
        NettyReactiveWebServerFactory factory = new NettyReactiveWebServerFactory();
        factory.addServerCustomizers(httpServer ->
                httpServer.option(ChannelOption.TCP_NODELAY, true)       // Nagle 비활성화
                          .option(ChannelOption.SO_KEEPALIVE, true)      // Keep-Alive
                          .option(ChannelOption.SO_BACKLOG, 1024)        // 연결 대기 큐
                          .childOption(ChannelOption.SO_RCVBUF, 65536)   // 수신 버퍼
                          .childOption(ChannelOption.SO_SNDBUF, 65536)   // 송신 버퍼
        );
        return factory;
    }
}
```

### 4. Micrometer + Prometheus로 RTT 지속 모니터링

일회성 측정보다 **지속적인 관측(Observability)** 이 더 중요하다. 운영 환경에서 RTT 분포를 추적하는 방법이다.

```java
@Component
public class ExternalApiClient {

    private final RestTemplate restTemplate;
    private final MeterRegistry meterRegistry;

    public ExternalApiClient(RestTemplate restTemplate, MeterRegistry meterRegistry) {
        this.restTemplate = restTemplate;
        this.meterRegistry = meterRegistry;
    }

    public String callExternalApi(String endpoint) {
        Timer.Sample sample = Timer.start(meterRegistry);
        try {
            ResponseEntity<String> response =
                    restTemplate.getForEntity(endpoint, String.class);
            return response.getBody();
        } finally {
            // 히스토그램 버킷 지정으로 P95/P99 정확도 향상
            sample.stop(Timer.builder("external.api.rtt")
                    .tag("endpoint", sanitize(endpoint))
                    .publishPercentiles(0.5, 0.95, 0.99)
                    .publishPercentileHistogram(true)
                    .serviceLevelObjectives(
                            Duration.ofMillis(50),
                            Duration.ofMillis(100),
                            Duration.ofMillis(500)
                    )
                    .register(meterRegistry));
        }
    }

    private String sanitize(String endpoint) {
        // URL에서 동적 파라미터 제거 (카디널리티 폭발 방지)
        return endpoint.replaceAll("/[0-9]+", "/{id}");
    }
}
```

### 5. 시스템 레벨 커널 파라미터 최적화

애플리케이션 코드만으로는 한계가 있다. Linux 커널 파라미터 튜닝으로 추가 개선이 가능하다.

```bash
# /etc/sysctl.conf 또는 런타임 적용

# TCP 백로그 큐 크기 증가
net.core.somaxconn = 65535
net.ipv4.tcp_max_syn_backlog = 65535

# TIME_WAIT 소켓 재사용 (포트 고갈 방지)
net.ipv4.tcp_tw_reuse = 1

# TCP Fast Open 활성화 (3-way handshake 최적화)
net.ipv4.tcp_fastopen = 3

# 수신/송신 소켓 버퍼 자동 조정
net.core.rmem_max = 16777216
net.core.wmem_max = 16777216
net.ipv4.tcp_rmem = 4096 87380 16777216
net.ipv4.tcp_wmem = 4096 65536 16777216

# 적용
sysctl -p
```

## 주의사항 및 트레이드오프

### 측정 자체의 함정

- **측정 오버헤드**: 계측 코드 자체가 지연을 유발할 수 있다. 고빈도 측정 시에는 샘플링 비율(예: 10%)을 조정하라.
- **단일 측정의 함정**: 콜드 스타트, GC Pause, 네트워크 버스트 등으로 단발 측정값은 신뢰도가 낮다. 반드시 통계적 분포로 분석하라.
- **헤이젠버그 효과**: 관찰 행위가 대상에 영향을 미친다. 프로덕션 과부하를 유발하지 않는 선에서 모니터링을 설계해야 한다.

### 최적화 시 트레이드오프

| 기법 | 장점 | 트레이드오프 |
|------|------|-------------|
| TCP_NODELAY | 소패킷 지연 감소 | 대역폭 효율 저하 (패킷 수 증가) |
| 커넥션 풀 확대 | 연결 재사용으로 RTT 절감 | 서버 리소스(FD, 메모리) 증가 |
| HTTP/2 멀티플렉싱 | HOL 블로킹 해소 | 단일 TCP 연결 장애 시 전체 영향 |
| Keep-Alive 연장 | 재연결 비용 제거 | 유휴 커넥션이 서버 리소스 점유 |
| 버퍼 크기 증가 | 처리량 향상 | 메모리 사용량 증가, 지연 증폭 가능 |

### 거짓 최적화 주의

**Bufferbloat** 문제를 간과하지 말 것. 버퍼를 무한정 늘리면 처리량은 높아지지만, 큐잉 지연이 폭발적으로 증가한다. 이는 사용자 체감 속도를 오히려 악화시킨다. AQM(Active Queue Management) 알고리즘인 **CoDel** 또는 **FQ-CoDel**을 적용하는 것이 근본적인 해법이다.

## 정리

네트워크 지연 최적화는 단일 기법으로 해결되지 않는다. 레이어별 접근이 필요하다.

1. **측정 먼저**: P95/P99 기반의 지속적 모니터링 체계를 먼저 구축하라. 수치 없는 최적화는 감이다.
2. **병목 구간 특정**: 전파 지연인지, 처리 지연인지, 큐잉 지연인지에 따라 해결책이 완전히 다르다.
3. **애플리케이션 레벨**: Connection Pool 튜닝, Keep-Alive, HTTP/2 전환으로 재연결 비용을 제거하라.
4. **OS/커널 레벨**: `tcp_fastopen`, 버퍼 튜닝, `tcp_tw_reuse`로 시스템 수준의 병목을 해소하라.
5. **인프라 레벨**: CDN, 엣지 서버 배치, GeoDNS로 물리적 거리 자체를 줄여라.

결국 RTT 최적화의 핵심은 **불필요한 왕복을 줄이고(연결 재사용), 불가피한 왕복을 빠르게 만드는(전파 지연 최소화)** 두 가지 원칙으로 귀결된다. 코드 최적화에 앞서 아키텍처 수준에서 왕복 횟수를 먼저 줄이는 것이 가장 효율적인 접근이다.
