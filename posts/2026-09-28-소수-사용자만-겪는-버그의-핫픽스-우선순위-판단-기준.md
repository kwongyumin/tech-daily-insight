# 소수 사용자만 겪는 버그의 핫픽스 우선순위 판단 기준

## 개요

"이 버그는 전체 유저의 0.3%만 겪고 있어요."

이 말이 나왔을 때, 당신은 어떻게 반응하는가? 무시해도 될 것 같은 수치지만, 실제로는 이 판단이 꽤 복잡하다. 100만 명이 사용하는 서비스라면 0.3%는 3,000명이다. 결제 플로우에서 발생하는 버그라면? 혹은 의료 정보와 관련된 기능이라면? 단순한 퍼센트로 우선순위를 결정하는 건 위험하다.

반면 핫픽스는 공짜가 아니다. 충분한 테스트 없이 빠르게 배포된 패치는 더 많은 사용자에게 새로운 문제를 일으킬 수 있다. 특히 배포 파이프라인이 복잡할수록, 핫픽스 하나가 전체 릴리즈 사이클에 미치는 영향은 크다.

이 글에서는 소수 사용자만 겪는 버그의 핫픽스 우선순위를 결정하는 실무적인 기준을 정리한다. 감으로 판단하지 않고, 구조적으로 접근할 수 있는 프레임워크와 예제 코드를 함께 제시한다.

---

## 핵심 개념: 우선순위 판단의 4가지 축

버그의 영향도는 단순히 "몇 명이 겪느냐"만으로 결정되지 않는다. 실무에서 검증된 판단 기준은 다음 네 가지 축으로 구성된다.

### 1. 영향 범위 (Blast Radius)

- **사용자 수**: 절대값과 비율 모두 중요하다
- **사용자 세그먼트**: 일반 유저 vs. 프리미엄/결제 유저 vs. 운영자
- **기능의 크리티컬리티**: 핵심 플로우(로그인, 결제, 데이터 저장)인가, 부가 기능인가

### 2. 비즈니스 임팩트 (Business Impact)

- **매출 영향**: 결제 실패, 구독 해지 유도 여부
- **SLA 위반 여부**: 계약상 보장된 가용성 수준을 침해하는가
- **법적/규정 준수 리스크**: GDPR, 개인정보보호법 등 규정 관련 기능인가

### 3. 재현 가능성과 확산 가능성 (Reproducibility & Spread Risk)

- **재현 조건**: 특정 브라우저, OS, 데이터 조합에서만 발생하는가
- **확산 가능성**: 특정 조건이 점점 더 많은 사용자에게 적용될 수 있는가 (예: 신규 가입자에게만 발생하는 버그)
- **데이터 손상 가능성**: 조용히 잘못된 데이터를 기록하고 있는가

### 4. 수정 비용과 리스크 (Fix Cost & Risk)

- **코드 변경 범위**: 수정이 단일 함수인가, 여러 모듈에 걸쳐있는가
- **테스트 커버리지**: 회귀 테스트가 충분한가
- **배포 복잡도**: 핫픽스가 다른 진행 중인 릴리즈와 충돌하는가

## 실전 예제: 우선순위 스코어링 시스템

판단을 일관성 있게 하려면 스코어링 시스템을 두는 것이 효과적이다. 아래는 Spring Boot 기반 서비스에서 버그 리포트를 수신했을 때 자동으로 우선순위 점수를 계산하는 예시다.

```java
public enum UserSegment {
    GENERAL(1),
    PREMIUM(3),
    ENTERPRISE(5);

    private final int weight;
    UserSegment(int weight) { this.weight = weight; }
    public int getWeight() { return weight; }
}

public enum FeatureCriticality {
    AUXILIARY(1),       // 부가 기능
    STANDARD(2),        // 일반 기능
    CORE(4),            // 핵심 기능 (로그인, 프로필)
    TRANSACTIONAL(8);   // 결제, 데이터 저장 등

    private final int weight;
    FeatureCriticality(int weight) { this.weight = weight; }
    public int getWeight() { return weight; }
}

@Getter
@Builder
public class BugReport {
    private long affectedUsers;
    private long totalUsers;
    private UserSegment userSegment;
    private FeatureCriticality featureCriticality;
    private boolean dataCorruptionRisk;
    private boolean spreadRisk;         // 확산 가능성
    private boolean complianceRisk;     // 법적/규정 리스크
    private int fixComplexity;          // 1(낮음) ~ 5(높음)
}

@Service
public class BugPriorityService {

    private static final int HOTFIX_THRESHOLD = 50;

    public PriorityResult evaluate(BugReport report) {
        int score = calculateImpactScore(report);
        int riskPenalty = calculateRiskPenalty(report);
        int fixCost = report.getFixComplexity() * 5;

        int finalScore = score + riskPenalty - fixCost;

        Priority priority = determinePriority(finalScore);

        return PriorityResult.builder()
                .score(finalScore)
                .priority(priority)
                .recommendation(buildRecommendation(priority, report))
                .build();
    }

    private int calculateImpactScore(BugReport report) {
        double affectedRatio = (double) report.getAffectedUsers() / report.getTotalUsers();

        // 비율 점수 (0~30점)
        int ratioScore = (int) Math.min(affectedRatio * 3000, 30);

        // 절대 사용자 수 점수 (0~20점)
        int absoluteScore = (int) Math.min(report.getAffectedUsers() / 100.0, 20);

        // 세그먼트 가중치
        int segmentScore = report.getUserSegment().getWeight() * 5;

        // 기능 크리티컬리티
        int criticalityScore = report.getFeatureCriticality().getWeight() * 3;

        return ratioScore + absoluteScore + segmentScore + criticalityScore;
    }

    private int calculateRiskPenalty(BugReport report) {
        int penalty = 0;
        if (report.isDataCorruptionRisk()) penalty += 30;
        if (report.isSpreadRisk()) penalty += 20;
        if (report.isComplianceRisk()) penalty += 25;
        return penalty;
    }

    private Priority determinePriority(int score) {
        if (score >= HOTFIX_THRESHOLD) return Priority.HOTFIX_IMMEDIATE;
        if (score >= 30) return Priority.HOTFIX_SCHEDULED;
        if (score >= 15) return Priority.NEXT_SPRINT;
        return Priority.BACKLOG;
    }

    private String buildRecommendation(Priority priority, BugReport report) {
        return switch (priority) {
            case HOTFIX_IMMEDIATE -> "즉시 핫픽스 배포. 영향받은 사용자 직접 공지 필요.";
            case HOTFIX_SCHEDULED -> "48시간 이내 핫픽스. 릴리즈 브랜치 분기 검토.";
            case NEXT_SPRINT -> "다음 스프린트에 포함. 임시 워크어라운드 제공 검토.";
            case BACKLOG -> "백로그 등록. 재현 조건 문서화 후 모니터링.";
        };
    }
}
```

이 스코어링 모델은 "0.3%라서 괜찮다"는 식의 단편적 판단을 방지한다. 예를 들어, 엔터프라이즈 사용자 50명이 결제 기능에서 데이터 손상 위험이 있는 버그를 겪고 있다면, 비율이 낮더라도 높은 점수를 받아 즉각적인 핫픽스 대상이 된다.

## 핫픽스 배포 전략: 위험을 최소화하는 방법

우선순위가 결정된 후에도, 핫픽스를 어떻게 배포하느냐에 따라 위험이 달라진다.

### Feature Flag를 활용한 안전한 핫픽스

소수 사용자에게만 발생하는 버그라면, 수정 코드도 소수에게 먼저 적용하는 것이 안전하다.

```java
@Service
public class PaymentService {

    private final FeatureFlagService featureFlag;

    public PaymentResult processPayment(PaymentRequest request) {
        // 핫픽스된 로직을 Feature Flag로 점진적 적용
        if (featureFlag.isEnabled("hotfix-payment-rounding", request.getUserId())) {
            return processPaymentV2(request); // 수정된 버전
        }
        return processPaymentV1(request); // 기존 버전
    }

    // 수정 전: 부동소수점 반올림 버그 존재
    private PaymentResult processPaymentV1(PaymentRequest request) {
        double amount = request.getAmount() * 1.1; // VAT 계산 버그
        return charge(amount);
    }

    // 수정 후: BigDecimal로 정확한 계산
    private PaymentResult processPaymentV2(PaymentRequest request) {
        BigDecimal amount = BigDecimal.valueOf(request.getAmount())
                .multiply(new BigDecimal("1.1"))
                .setScale(2, RoundingMode.HALF_UP);
        return charge(amount.doubleValue());
    }
}
```

```yaml
# Feature Flag 설정 예시 (LaunchDarkly, Unleash 등 활용)
feature-flags:
  hotfix-payment-rounding:
    enabled: true
    rollout:
      strategy: user-list        # 영향받은 사용자 ID 목록
      target-users:
        - "user-12345"
        - "user-67890"
      percentage: 0              # 전체 롤아웃 전 0%
```

### 핫픽스 배포 체크리스트

```markdown
## Hotfix Deployment Checklist

### Before Deploy
- [ ] 재현 시나리오 문서화 완료
- [ ] 수정 코드 리뷰 최소 2인 완료
- [ ] 단위 테스트 추가 완료 (버그 재현 케이스 포함)
- [ ] 스테이징 환경에서 수정 확인
- [ ] 롤백 계획 수립 완료
- [ ] 모니터링 알림 임계값 조정

### During Deploy
- [ ] 배포 담당자 및 온콜 엔지니어 대기
- [ ] Feature Flag로 단계적 적용 (10% → 50% → 100%)
- [ ] 에러율, 응답시간 실시간 모니터링

### After Deploy
- [ ] 영향받은 사용자 그룹 에러 해소 확인
- [ ] 전체 에러율 정상 수준 유지 확인
- [ ] 포스트모템 작성 일정 잡기
```

## 주의사항 및 트레이드오프

### 1. 스코어링 모델을 맹신하지 말 것

수치 기반 판단은 일관성을 높이지만, 컨텍스트를 놓칠 수 있다. 예를 들어, SNS 상에서 버그에 대한 불만이 바이럴되고 있다면 영향받는 사용자 수와 무관하게 대응 속도를 높여야 한다. 스코어는 **의사결정 보조 도구**이지, **의사결정 주체**가 아니다.

### 2. 핫픽스가 만드는 기술 부채

긴급 배포로 인해 테스트가 부족하거나 코드 품질이 낮아지면, 이후에 더 큰 버그의 원인이 된다. 핫픽스를 배포한 뒤 반드시 **리팩터링 티켓**을 즉시 생성하고 다음 스프린트에 포함시키는 프로세스를 강제해야 한다.

### 3. "소수의 사용자"가 실제로는 미래의 다수일 수 있다

신규 가입자, 특정 디바이스 사용자, 특정 국가/언어 사용자에게만 발생하는 버그는 확산 가능성이 높다. 재현 조건이 시간이 지날수록 더 많은 사용자에게 해당될 수 있는지를 반드시 검토해야 한다.

```java
// 예: 신규 가입자에게만 발생하는 버그 패턴 감지
public boolean isSpreadRisk(BugReport report) {
    // 재현 조건이 "성장하는" 사용자 그룹에 해당하는지 확인
    return report.getAffectedCondition().contains("new_user")
        || report.getAffectedCondition().contains("latest_os_version")
        || report.getAffectedCondition().contains("new_feature_flag_enabled");
}
```

### 4. 워크어라운드의 비용도 고려하라

핫픽스를 하지 않더라도 사용자에게 임시 방편을 제공하거나, CS팀이 수동으로 처리하는 비용이 발생한다. 이 비용이 핫픽스 배포 비용보다 크다면, 빠른 수정이 오히려 합리적이다. 특히 CS 처리 비용은 개발팀에서 잘 보이지 않으므로 명시적으로 추적해야 한다.

## 정리

소수 사용자만 겪는 버그는 "무시할 수 있는 버그"가 아니다. 동시에 "즉시 핫픽스해야 하는 버그"도 아닐 수 있다. 핵심은 **구조적인 판단 기준**을 갖는 것이다.

| 판단 기준 | 고려 요소 |
|---|---|
| 영향 범위 | 절대 사용자 수, 세그먼트, 기능 크리티컬리티 |
| 비즈니스 임팩트 | 매출, SLA, 법적 리스크 |
| 확산 가능성 | 재현 조건의 성장성, 데이터 손상 위험 |
| 수정 비용 | 코드 복잡도, 테스트 커버리지, 배포 리스크 |

실무에서는 이 기준을 팀 내에서 공유된 형태로 문서화해두고, 버그가 들어왔을 때 동일한 프레임으로 빠르게 판단할 수 있어야 한다. 판단의 일관성이 없으면 긴급함에 끌려다니거나, 반대로 중요한 버그를 방치하는 양극단으로 빠지기 쉽다.

핫픽스는 "빠른 수정"이 아니라 "통제된 위험 감수"다. 그 판단을 구조화하는 것이 시니어 개발자와 팀의 역할이다.
