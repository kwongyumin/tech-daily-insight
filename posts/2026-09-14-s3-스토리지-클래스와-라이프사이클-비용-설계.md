# S3 스토리지 클래스와 라이프사이클 비용 설계

## 개요

AWS S3는 단순한 오브젝트 스토리지처럼 보이지만, 스토리지 클래스와 라이프사이클 정책을 얼마나 정교하게 설계하느냐에 따라 월 수백만 원의 비용 차이가 발생할 수 있다. 특히 데이터가 수 테라바이트 이상으로 쌓이는 서비스라면 "그냥 Standard에 올려두면 되겠지"라는 생각은 인프라 비용 낭비의 주범이 된다.

이 글에서는 S3의 스토리지 클래스별 특성과 비용 구조를 정확히 이해하고, 실제 서비스 시나리오에 맞는 라이프사이클 정책을 설계하는 방법을 다룬다. Terraform을 활용한 IaC 예제와 AWS CLI, Java SDK 예제를 함께 제공하여 실무에서 바로 적용할 수 있도록 구성했다.

## 핵심 개념

### S3 스토리지 클래스 비교

S3는 총 7가지 스토리지 클래스를 제공한다. 각 클래스는 **접근 빈도**, **내구성**, **가용성**, **최소 보관 기간**, **검색 비용** 측면에서 다르게 설계되어 있다.

| 클래스 | GB당 월 비용(서울) | 최소 보관 | 검색 비용 | 가용성 | 사용 시나리오 |
|---|---|---|---|---|---|
| Standard | $0.025 | 없음 | 없음 | 99.99% | 자주 접근하는 데이터 |
| Intelligent-Tiering | $0.025 + 모니터링 | 없음 | 없음 | 99.9% | 접근 패턴 불규칙 |
| Standard-IA | $0.019 | 30일 | GB당 $0.01 | 99.9% | 월 1회 미만 접근 |
| One Zone-IA | $0.0152 | 30일 | GB당 $0.01 | 99.5% | 재생성 가능 데이터 |
| Glacier Instant | $0.005 | 90일 | GB당 $0.03 | 99.9% | 분기별 접근 |
| Glacier Flexible | $0.0045 | 90일 | GB당 $0.03 | 99.99% | 연 1~2회 접근 |
| Glacier Deep Archive | $0.002 | 180일 | GB당 $0.022 | 99.99% | 장기 보관/컴플라이언스 |

> **핵심 포인트**: 저렴한 클래스일수록 최소 보관 기간과 검색 비용이 존재한다. 짧게 보관하고 자주 접근하는 데이터를 Glacier로 이동하면 오히려 비용이 증가한다.

### 비용 설계 시 고려해야 할 요소

**1. 접근 패턴 분석**
- 데이터 생성 후 첫 30일: 대부분의 서비스에서 가장 접근이 많음
- 30~90일: 접근 빈도 급감
- 90일 이후: 법적 보존 또는 분석 목적 외 접근 거의 없음

**2. PUT/GET 요청 비용**
Standard IA는 GB당 스토리지 비용은 싸지만, GET 요청당 비용이 Standard보다 비싸다. 소용량 파일이 많다면 요청 비용이 스토리지 절감분을 상쇄할 수 있다.

**3. 최소 객체 크기**
Standard-IA와 One Zone-IA는 128KB 미만 객체에 128KB 요금이 부과된다. 썸네일, 작은 JSON 파일 등은 Standard를 유지하는 것이 유리할 수 있다.

## 실전 예제

### 시나리오: 미디어 스트리밍 서비스의 S3 비용 최적화

사용자가 업로드한 영상 파일이 매월 10TB씩 누적되는 서비스를 가정한다.
- 업로드 후 7일: 인코딩 및 CDN 서빙 (빈번한 접근)
- 8~30일: 간헐적 재생
- 31~90일: 거의 접근 없음
- 91일 이후: 사용자 요청 또는 법적 보존 목적

### Terraform으로 라이프사이클 정책 구성

```hcl
# main.tf
resource "aws_s3_bucket" "media_storage" {
  bucket = "my-media-storage-prod"
}

resource "aws_s3_bucket_lifecycle_configuration" "media_lifecycle" {
  bucket = aws_s3_bucket.media_storage.id

  # 원본 영상 파일 라이프사이클
  rule {
    id     = "original-video-lifecycle"
    status = "Enabled"

    filter {
      prefix = "videos/original/"
    }

    # 30일 후 Standard-IA로 전환
    transition {
      days          = 30
      storage_class = "STANDARD_IA"
    }

    # 90일 후 Glacier Instant Retrieval로 전환
    transition {
      days          = 90
      storage_class = "GLACIER_IR"
    }

    # 365일 후 Glacier Deep Archive로 전환
    transition {
      days          = 365
      storage_class = "DEEP_ARCHIVE"
    }

    # 7년 후 삭제 (법적 보존 기간)
    expiration {
      days = 2555
    }
  }

  # 인코딩된 영상 (자주 접근)
  rule {
    id     = "encoded-video-lifecycle"
    status = "Enabled"

    filter {
      prefix = "videos/encoded/"
    }

    transition {
      days          = 60
      storage_class = "STANDARD_IA"
    }

    transition {
      days          = 180
      storage_class = "GLACIER_IR"
    }

    expiration {
      days = 730
    }
  }

  # 썸네일 (소용량, Standard 유지 권장)
  rule {
    id     = "thumbnail-lifecycle"
    status = "Enabled"

    filter {
      prefix = "thumbnails/"
      # 128KB 이상 객체에만 적용
      object_size_greater_than = 131072
    }

    transition {
      days          = 90
      storage_class = "STANDARD_IA"
    }

    expiration {
      days = 365
    }
  }

  # 불완전한 멀티파트 업로드 정리 (비용 절감 필수)
  rule {
    id     = "abort-incomplete-multipart"
    status = "Enabled"

    filter {}

    abort_incomplete_multipart_upload {
      days_after_initiation = 7
    }
  }
}

# Intelligent-Tiering 설정 (접근 패턴이 불규칙한 버킷)
resource "aws_s3_bucket_intelligent_tiering_configuration" "media_tiering" {
  bucket = aws_s3_bucket.media_storage.id
  name   = "media-intelligent-tiering"

  tiering {
    access_tier = "DEEP_ARCHIVE_ACCESS"
    days        = 180
  }

  tiering {
    access_tier = "ARCHIVE_ACCESS"
    days        = 90
  }
}
```

### Java SDK로 라이프사이클 정책 프로그래밍 방식 적용

```java
import software.amazon.awssdk.services.s3.S3Client;
import software.amazon.awssdk.services.s3.model.*;

import java.util.List;

@Component
public class S3LifecycleManager {

    private final S3Client s3Client;

    public S3LifecycleManager(S3Client s3Client) {
        this.s3Client = s3Client;
    }

    public void applyMediaLifecyclePolicy(String bucketName) {
        // 원본 영상 라이프사이클 규칙
        LifecycleRule originalVideoRule = LifecycleRule.builder()
            .id("original-video-lifecycle")
            .status(ExpirationStatus.ENABLED)
            .filter(LifecycleRuleFilter.builder()
                .prefix("videos/original/")
                .build())
            .transitions(List.of(
                Transition.builder()
                    .days(30)
                    .storageClass(TransitionStorageClass.STANDARD_IA)
                    .build(),
                Transition.builder()
                    .days(90)
                    .storageClass(TransitionStorageClass.GLACIER_IR)
                    .build(),
                Transition.builder()
                    .days(365)
                    .storageClass(TransitionStorageClass.DEEP_ARCHIVE)
                    .build()
            ))
            .expiration(LifecycleExpiration.builder()
                .days(2555)
                .build())
            .build();

        // 불완전한 멀티파트 업로드 정리 규칙
        LifecycleRule cleanupRule = LifecycleRule.builder()
            .id("abort-incomplete-multipart")
            .status(ExpirationStatus.ENABLED)
            .filter(LifecycleRuleFilter.builder()
                .prefix("")
                .build())
            .abortIncompleteMultipartUpload(
                AbortIncompleteMultipartUpload.builder()
                    .daysAfterInitiation(7)
                    .build()
            )
            .build();

        BucketLifecycleConfiguration lifecycleConfiguration =
            BucketLifecycleConfiguration.builder()
                .rules(List.of(originalVideoRule, cleanupRule))
                .build();

        PutBucketLifecycleConfigurationRequest request =
            PutBucketLifecycleConfigurationRequest.builder()
                .bucket(bucketName)
                .lifecycleConfiguration(lifecycleConfiguration)
                .build();

        s3Client.putBucketLifecycleConfiguration(request);
    }

    /**
     * 특정 접두사의 객체 스토리지 클래스 분포 조회 (비용 분석용)
     */
    public void analyzeStorageClassDistribution(String bucketName, String prefix) {
        ListObjectsV2Request listRequest = ListObjectsV2Request.builder()
            .bucket(bucketName)
            .prefix(prefix)
            .build();

        Map<String, Long> classCount = new HashMap<>();
        Map<String, Long> classSize = new HashMap<>();

        s3Client.listObjectsV2Paginator(listRequest).forEach(response -> {
            response.contents().forEach(obj -> {
                String storageClass = obj.storageClassAsString();
                classCount.merge(storageClass, 1L, Long::sum);
                classSize.merge(storageClass, obj.size(), Long::sum);
            });
        });

        classSize.forEach((cls, size) -> {
            System.out.printf("Class: %-20s | Count: %6d | Size: %8.2f GB%n",
                cls, classCount.get(cls), size / (1024.0 * 1024 * 1024));
        });
    }
}
```

### AWS CLI로 현재 라이프사이클 정책 확인 및 비용 분석

```bash
# 현재 라이프사이클 정책 조회
aws s3api get-bucket-lifecycle-configuration \
  --bucket my-media-storage-prod \
  --output json | jq '.Rules[] | {id: .ID, transitions: .Transitions}'

# 스토리지 클래스별 객체 수 및 용량 집계 (Storage Lens 없이)
aws s3api list-objects-v2 \
  --bucket my-media-storage-prod \
  --prefix "videos/" \
  --query 'Contents[*].{Key: Key, Size: Size, Class: StorageClass}' \
  --output json | jq 'group_by(.Class) | map({
    class: .[0].Class,
    count: length,
    total_gb: (map(.Size) | add) / 1073741824
  })'

# S3 Storage Lens로 비용 분석 활성화
aws s3control put-storage-lens-configuration \
  --account-id 123456789012 \
  --config-id my-storage-lens \
  --storage-lens-configuration '{
    "Id": "my-storage-lens",
    "IsEnabled": true,
    "DataExport": {
      "S3BucketDestination": {
        "AccountId": "123456789012",
        "Arn": "arn:aws:s3:::my-lens-reports",
        "Format": "CSV",
        "OutputSchemaVersion": "V_1"
      }
    },
    "Include": {
      "Buckets": ["arn:aws:s3:::my-media-storage-prod"]
    },
    "AccountLevel": {
      "BucketLevel": {
        "ActivityMetrics": {"IsEnabled": true},
        "PrefixLevel": {
          "StorageMetrics": {
            "IsEnabled": true,
            "SelectionCriteria": {
              "MaxDepth": 3,
              "MinStorageBytesPercentage": 1.0
            }
          }
        }
      }
    }
  }'
```

## 주의사항 및 트레이드오프

### 1. 최소 보관 기간 함정

Standard-IA는 30일, Glacier 계열은 90~180일의 최소 보관 기간이 있다. **30일 이전에 삭제해도 30일치 요금이 청구된다.** 사용자가 업로드 직후 삭제하는 패턴이 많은 서비스라면 Standard를 유지하는 것이 더 저렴하다.

```
예시: 1GB 파일을 업로드 후 10일 만에 삭제
- Standard-IA: 30일치 요금 = $0.019 (10일만 사용했어도)
- Standard: 10일치 요금 = $0.008
```

### 2. 라이프사이클 전환 요청 비용

객체를 다른 스토리지 클래스로 전환할 때마다 PUT 요청 비용이 발생한다. 객체가 수억 개라면 전환 비용만으로도 수백 달러가 청구될 수 있다. 전환 주기와 객체 수를 함께 계산해야 한다.

### 3. Glacier 복구 지연 시간 계획

- **Glacier Flexible**: 표준 복구 3~5시간, 긴급 복구 1~5분 (긴급은 GB당 $0.033 추가)
- **Glacier Deep Archive**: 표준 복구 12시간

장애 복구 시나리오에서 Glacier에 있는 데이터가 필요하다면, RTO 목표와 맞지 않을 수 있다. 복구 계획에 반드시 반영해야 한다.

### 4. Intelligent-Tiering 모니터링 비용

Intelligent-Tiering은 객체당 월 $0.0025의 모니터링 비용이 발생한다. **128KB 미만 소용량 파일이 많다면 모니터링 비용이 절감 효과를 상쇄한다.** 일반적으로 객체당 평균 크기가 128KB 이상이고 접근 패턴이 불규칙할 때 유리하다.

### 5. 버전 관리 활성화 시 주의점

버킷에 버전 관리를 활성화한 경우, 이전 버전 객체에 대한 별도 라이프사이클 규칙이 없으면 모든 버전이 Standard로 유지된다. `NoncurrentVersionTransition`을 반드시 설정해야 한다.

```hcl
# Terraform 예시: 이전 버전 객체 라이프사이클
noncurrent_version_transition {
  noncurrent_days = 30
  storage_class   = "STANDARD_IA"
}

noncurrent_version_transition {
  noncurrent_days = 90
  storage_class   = "DEEP_ARCHIVE"
}

noncurrent_version_expiration {
  noncurrent_days = 365
}
```

## 정리

S3 비용 최적화는 단순히 "오래된 파일을 Glacier로 보내자"가 아니라, 데이터의 접근 패턴, 파일 크기, 삭제 주기, 복구 요구사항을 종합적으로 분석하는 설계 작업이다.

**실무 적용 체크리스트:**

- [ ] 접근 로그 또는 Storage Lens로 접근 패턴 데이터 수집 (최소 30일)
- [ ] 파일 크기 분포 분석 (128KB 미만 비율 확인)
- [ ] 서비스별 RTO/RPO 기준으로 Glacier 사용 가능 여부 판단
- [ ] 불완전한 멀티파트 업로드 정리 규칙 반드시 추가
- [ ] 버전 관리 사용 시 NoncurrentVersionTransition 설정
- [ ] 라이프사이클 전환 전 AWS 비용 계산기로 사전 시뮬레이션
- [ ] 정책 적용 후 Cost Explorer에서 월별 효과 모니터링

비용 설계는 한 번 하고 끝나는 게 아니다. 서비스 성장에 따라 데이터 패턴이 바뀌므로 **분기마다 Storage Lens 리포트를 검토하고 정책을 재조정**하는 습관을 만드는 것이 장기적으로 인프라 비용을 관리하는 핵심이다.
