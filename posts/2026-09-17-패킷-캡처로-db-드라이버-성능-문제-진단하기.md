# 패킷 캡처로 DB 드라이버 성능 문제 진단하기

## 개요

애플리케이션이 느리다. DB 쿼리 로그를 봐도 느린 쿼리는 없다. APM에서 DB 레이턴시도 정상 범위다. 그런데 실제 응답은 분명히 느리다. 이런 상황에서 많은 개발자들이 막막함을 느낀다.

이 시나리오에서 종종 범인은 **DB 드라이버 레벨의 동작**이다. 드라이버가 내부적으로 어떤 패킷을 주고받는지, 얼마나 많은 라운드트립이 발생하는지, 커넥션 핸드셰이크에 얼마나 시간이 걸리는지 — 이것들은 애플리케이션 로그만으로는 절대 보이지 않는다.

패킷 캡처는 이런 블랙박스를 열어젖히는 도구다. Wireshark나 `tcpdump`로 네트워크 레벨에서 실제 DB 프로토콜 패킷을 분석하면, "드라이버가 실제로 무엇을 하고 있는가"를 정확히 파악할 수 있다. 이 글에서는 실무에서 바로 적용할 수 있는 패킷 캡처 기반 DB 드라이버 성능 진단 방법을 정리한다.

## 핵심 개념

### DB 드라이버와 네트워크 레이어의 관계

Java 기준으로, 애플리케이션이 `preparedStatement.executeQuery()`를 호출하면 내부적으로 다음과 같은 일이 벌어진다.

1. JDBC 드라이버가 DB 프로토콜(MySQL의 경우 MySQL Protocol, PostgreSQL의 경우 Frontend/Backend Protocol)에 맞는 패킷을 생성
2. TCP 소켓을 통해 패킷 전송
3. DB 서버가 응답 패킷 반환
4. 드라이버가 응답을 파싱하여 ResultSet 구성

이 과정에서 **라운드트립(RTT)**이 몇 번 발생하느냐가 성능에 직결된다. Prepared Statement를 사용하더라도 드라이버 설정에 따라 실제 `PREPARE → EXECUTE → CLOSE` 패킷이 매번 발생할 수 있다.

### 주목해야 할 패턴들

| 문제 패턴 | 증상 | 원인 |
|---|---|---|
| Statement Prepare 반복 | 동일 쿼리마다 PREPARE 패킷 발생 | `cachePrepStmts=false` |
| Auto-commit 남용 | 단건 쿼리마다 BEGIN/COMMIT | 트랜잭션 미사용 |
| Cursor fetch 비효율 | 대량 데이터 조회 시 패킷 폭증 | fetchSize 미설정 |
| SSL 핸드셰이크 | 쿼리마다 TLS 협상 발생 | 커넥션 풀 미사용 |
| TCP Nagle 알고리즘 | 작은 패킷 지연 전송 | `tcpNoDelay=false` |

## 실전 예제

### 1단계: tcpdump로 트래픽 캡처

DB 서버 혹은 애플리케이션 서버에서 아래 명령으로 패킷을 캡처한다. MySQL 기본 포트 3306 기준이다.

```bash
# DB 서버에서 실행 (MySQL 3306 포트 기준)
sudo tcpdump -i any -w /tmp/db_capture.pcap \
  -s 0 \
  port 3306 \
  -n

# 실시간 텍스트 출력으로 확인할 경우
sudo tcpdump -i any -A -s 0 port 3306 -n | head -200
```

PostgreSQL이라면 포트를 5432로 변경한다. `-s 0`은 패킷을 잘림 없이 전체 캡처하는 옵션이다.

캡처 중 문제가 의심되는 시나리오(예: 특정 API 호출, 배치 실행)를 재현한 뒤 캡처를 중단한다.

### 2단계: Wireshark로 분석

`.pcap` 파일을 로컬로 내려받아 Wireshark로 연다.

**MySQL 프로토콜 디코딩 활성화:**
- `Analyze > Decode As`에서 TCP 포트 3306을 MySQL로 지정하면 패킷 내용이 SQL 레벨로 파싱된다.

**유용한 Wireshark 필터:**

```
# MySQL 쿼리 패킷만 필터
mysql.command == 3

# 특정 클라이언트 IP에서 오는 트래픽
ip.src == 10.0.1.100 && mysql

# 응답 시간이 100ms 이상인 요청 (Statistics > Service Response Time)
```

### 3단계: 문제 패턴 식별

**Prepared Statement 캐시 미사용 패턴 예시**

Wireshark에서 다음과 같은 패킷 시퀀스가 반복되면 의심해야 한다.

```
Client → Server: COM_STMT_PREPARE  (SELECT * FROM users WHERE id = ?)
Server → Client: COM_STMT_PREPARE response (stmt_id=1)
Client → Server: COM_STMT_EXECUTE  (stmt_id=1, param=42)
Server → Client: Result Set
Client → Server: COM_STMT_CLOSE    (stmt_id=1)

-- 다음 요청에서 동일 패턴 반복 --
Client → Server: COM_STMT_PREPARE  (SELECT * FROM users WHERE id = ?)
Server → Client: COM_STMT_PREPARE response (stmt_id=2)
...
```

쿼리마다 PREPARE와 CLOSE가 반복된다면, 드라이버 캐시가 비활성화된 것이다.

**Java MySQL Connector/J 수정 예시:**

```java
// 문제가 있는 설정 (기본값)
String url = "jdbc:mysql://localhost:3306/mydb";

// 개선된 설정
String url = "jdbc:mysql://localhost:3306/mydb"
    + "?cachePrepStmts=true"           // PS 캐시 활성화
    + "&prepStmtCacheSize=250"         // 캐시 사이즈
    + "&prepStmtCacheSqlLimit=2048"    // 캐시할 SQL 최대 길이
    + "&useServerPrepStmts=true"       // 서버 사이드 PS 사용
    + "&rewriteBatchedStatements=true" // 배치 최적화
    + "&tcpNoDelay=true";              // Nagle 알고리즘 비활성화
```

**Auto-commit 남용 패턴:**

```
Client → Server: SET autocommit=1
Client → Server: COM_QUERY (INSERT INTO orders ...)
Server → Client: OK
Client → Server: COM_QUERY (INSERT INTO orders ...)  -- 다시 BEGIN 없이
Server → Client: OK
```

각 INSERT마다 암묵적 커밋이 발생하는 패턴이다. 배치 처리라면 명시적 트랜잭션으로 묶어야 한다.

```java
// 문제 코드: 개별 커밋
for (Order order : orders) {
    orderRepository.save(order); // 매번 INSERT + 암묵적 COMMIT
}

// 개선 코드: 트랜잭션 묶기
@Transactional
public void saveOrders(List<Order> orders) {
    for (Order order : orders) {
        orderRepository.save(order);
    }
    // 한 번의 COMMIT
}
```

### 4단계: fetchSize 문제 진단

대량 데이터 조회 시 패킷 수가 예상보다 훨씬 많다면 fetchSize 문제일 수 있다.

**Wireshark에서 패킷 수 카운팅:**

```
Statistics > Conversations > TCP
```

특정 커넥션의 패킷 수와 바이트를 확인한다. 10만 건 조회인데 패킷이 수십만 개라면 행 단위로 패킷이 오가는 것이다.

```java
// 문제 코드: fetchSize 미설정 (MySQL 기본값: 모든 행을 한 번에 메모리로)
Statement stmt = connection.createStatement();
ResultSet rs = stmt.executeQuery("SELECT * FROM large_table");

// 개선 코드: 스트리밍 방식
Statement stmt = connection.createStatement(
    ResultSet.TYPE_FORWARD_ONLY,
    ResultSet.CONCUR_READ_ONLY
);
stmt.setFetchSize(Integer.MIN_VALUE); // MySQL 스트리밍 모드

// PostgreSQL의 경우
stmt.setFetchSize(1000); // 1000행씩 fetch
```

### 5단계: 커스텀 스크립트로 자동화

반복 진단을 위해 `tshark`(Wireshark CLI)로 자동 분석 스크립트를 구성할 수 있다.

```bash
#!/bin/bash
# analyze_db_traffic.sh

PCAP_FILE=$1
PORT=${2:-3306}

echo "=== MySQL Query Summary ==="
tshark -r "$PCAP_FILE" \
  -Y "mysql.command == 3" \
  -T fields \
  -e frame.time_relative \
  -e ip.src \
  -e mysql.query \
  2>/dev/null | head -50

echo ""
echo "=== Prepared Statement PREPARE count ==="
tshark -r "$PCAP_FILE" \
  -Y "mysql.command == 22" \
  -T fields \
  -e mysql.query \
  2>/dev/null | sort | uniq -c | sort -rn | head -20

echo ""
echo "=== COM_STMT_CLOSE count ==="
tshark -r "$PCAP_FILE" \
  -Y "mysql.command == 25" \
  2>/dev/null | wc -l
```

```bash
chmod +x analyze_db_traffic.sh
./analyze_db_traffic.sh /tmp/db_capture.pcap 3306
```

## 주의사항 및 트레이드오프

### 보안 및 법적 고려사항

패킷 캡처는 **네트워크 상의 모든 데이터를 평문으로 확인**할 수 있다. 운영 환경에서 실행 시 반드시 고려해야 할 점들이 있다.

- **개인정보 보호**: 캡처 파일에는 쿼리 결과의 실제 데이터가 포함된다. PII(개인식별정보)가 담길 수 있으므로 캡처 파일 보관과 공유에 주의한다.
- **접근 권한**: `tcpdump`는 root 또는 `CAP_NET_RAW` 권한이 필요하다. 최소 권한 원칙에 따라 별도 사용자 계정을 활용한다.
- **TLS 암호화 환경**: SSL/TLS가 활성화된 경우 패킷 내용은 암호화되어 분석이 어렵다. 이 경우 DB 서버 로컬에서 캡처하거나, 테스트 환경에서 TLS를 일시 비활성화하고 분석하는 방법을 고려한다.

### 성능 영향

- `tcpdump` 자체도 CPU와 디스크 I/O를 사용한다. 고트래픽 환경에서는 캡처 필터를 정밀하게 설정하거나 짧은 시간만 캡처한다.
- `-s 0` (full packet capture) 대신 `-s 256`처럼 슬랩 사이즈를 제한하면 오버헤드를 줄일 수 있다. 단, SQL 전체를 보려면 충분한 크기가 필요하다.

### 드라이버 버전에 따른 차이

MySQL Connector/J 8.x와 5.x는 기본 동작이 다르다. `useServerPrepStmts` 기본값, SSL 기본 활성화 여부 등이 버전마다 달라지므로, 드라이버 업그레이드 전후로 패킷 캡처 비교를 하면 예상치 못한 동작 변화를 조기에 발견할 수 있다.

### 커넥션 풀과 캡처의 관계

HikariCP 같은 커넥션 풀을 사용하면 TCP 커넥션이 재사용된다. 따라서 "커넥션 수립 → 쿼리 → 커넥션 종료"가 매 요청마다 보이지 않는다. 반대로, 캡처에서 매 요청마다 TCP 3-way handshake가 보인다면 커넥션 풀이 제대로 동작하지 않는 신호다.

```bash
# TCP SYN 패킷만 필터링하여 커넥션 수립 빈도 확인
tshark -r db_capture.pcap \
  -Y "tcp.flags.syn == 1 && tcp.flags.ack == 0 && tcp.dstport == 3306" \
  -T fields -e frame.time_relative | wc -l
```

## 정리

패킷 캡처는 DB 드라이버 성능 문제를 진단하는 데 있어 로그나 APM이 보여주지 못하는 영역을 정확히 드러낸다. 핵심은 "드라이버가 실제로 무엇을 하고 있는가"를 네트워크 레벨에서 직접 확인하는 것이다.

진단 절차를 요약하면 다음과 같다.

1. `tcpdump`로 DB 포트 트래픽을 캡처한다
2. Wireshark에서 DB 프로토콜로 디코딩하여 패킷 시퀀스를 분석한다
3. PREPARE/EXECUTE/CLOSE 반복, 불필요한 AUTO COMMIT, fetchSize 문제, TCP 핸드셰이크 반복 등을 식별한다
4. 드라이버 설정(URL 파라미터)과 애플리케이션 코드를 개선한다
5. 개선 후 재캡처하여 패킷 패턴이 예상대로 변경되었는지 검증한다

가장 중요한 교훈은, **드라이버 설정 하나가 수십 배의 라운드트립 차이를 만든다**는 점이다. `cachePrepStmts` 한 줄이 쿼리당 3번의 네트워크 왕복을 1번으로 줄일 수 있다. 패킷 캡처는 이 사실을 추측이 아닌 실증으로 보여준다.
