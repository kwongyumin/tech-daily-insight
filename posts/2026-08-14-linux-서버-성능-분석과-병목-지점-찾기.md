# Linux 서버 성능 분석과 병목 지점 찾기

## 성능 튜닝과 벤치마킹 관점에서의 심화 접근

---

## 개요

이전 글에서 `top`, `vmstat`, `iostat` 같은 기본 도구로 서버 상태를 모니터링하는 방법을 다뤘다. 이번 글은 그 다음 단계다. **"어디가 느린지 알았다. 그럼 어떻게 수치로 증명하고, 어떻게 개선하며, 개선 효과를 어떻게 검증하는가?"**

성능 튜닝에서 가장 흔한 실수는 측정 없이 직관으로 튜닝하는 것이다. 수치 없는 튜닝은 도박이다. 이 글은 **벤치마킹 → 병목 식별 → 튜닝 → 재측정**이라는 사이클을 실전 수치와 함께 다룬다.

대상 독자는 서버 운영 경험이 있고 기본 Linux 명령어에 익숙한 중급 이상 개발자다.

---

## 핵심 개념: 성능 튜닝의 방법론

### USE 메서드: 체계적 병목 탐색

Netflix의 Brendan Gregg가 정립한 **USE(Utilization, Saturation, Errors)** 메서드는 각 리소스에 대해 세 가지를 측정한다.

| 리소스 | Utilization | Saturation | Errors |
|--------|-------------|------------|--------|
| CPU | `mpstat` 사용률 | `vmstat r` 런큐 | `perf stat` |
| Memory | 사용 중인 메모리 % | swap-in/out rate | ECC 에러 |
| Disk I/O | `iostat %util` | `iostat await` | `/proc/diskstats` |
| Network | `sar -n DEV` | 드롭 패킷 수 | `netstat -s` |

단순히 CPU가 80%라는 수치보다, **런큐(r)가 CPU 코어 수를 지속적으로 초과하는지**가 실제 포화 상태를 나타낸다.

### 벤치마킹의 황금 원칙

1. **기준선(Baseline)을 먼저 측정하라** — 튜닝 전 수치 없이는 개선 여부를 판단할 수 없다
2. **단일 변수 변경 원칙** — 한 번에 하나의 파라미터만 변경한다
3. **동일한 조건 재현** — 워밍업 시간, 테스트 부하, 측정 시간을 통일한다
4. **통계적으로 의미 있는 반복** — 최소 5회 이상 측정 후 평균/표준편차를 본다

## 실전 예제

### 1. CPU 병목: 무엇이 CPU를 잡아먹는가

`perf`는 커널 레벨에서 CPU 사이클을 소비하는 함수를 찾아준다.

```bash
# 30초간 시스템 전체 CPU 프로파일링
sudo perf record -g -a -- sleep 30
sudo perf report --stdio | head -50

# 특정 프로세스의 CPU 핫스팟 분석
sudo perf record -g -p $(pgrep java) -- sleep 30
sudo perf report
```

실전 사례: JVM 기반 서비스에서 CPU가 지속적으로 95% 이상인 상황. `perf top`으로 확인했더니 `java.util.zip.Inflater`가 상위에 올라왔다. Gzip 압축을 모든 내부 API 통신에 적용한 것이 원인이었다. 내부 통신에서 압축 제거 후 CPU 사용률이 **95% → 55%**로 감소했고, Throughput은 **2.3배** 증가했다.

```bash
# CPU 캐시 미스 측정 (cache miss가 높으면 메모리 접근 패턴 문제)
perf stat -e cache-misses,cache-references,instructions,cycles \
  -p $(pgrep myapp) -- sleep 10

# 출력 예시 해석
# cache-miss rate = cache-misses / cache-references
# 10% 이상이면 데이터 지역성(locality) 문제를 의심
```

### 2. 메모리 병목: OOM이 아닌 성능 저하 수준의 메모리 압박

```bash
# 페이지 폴트와 스왑 활동 5초 간격 모니터링
vmstat -w 5 | awk 'NR==1{print} NR>2{print}' | \
  awk '{printf "r=%s b=%s swpd=%s free=%s si=%s so=%s\n",$1,$2,$3,$4,$7,$8}'

# NUMA 아키텍처에서 노드 간 메모리 접근 분석
numastat -p $(pgrep java)
numactl --hardware
```

**NUMA 최적화 실전 사례**: 32코어 듀얼 소켓 서버에서 Java 서비스 latency가 불규칙하게 튀는 현상. `numastat` 결과 numa_miss가 전체 접근의 35%를 차지했다. 

```bash
# NUMA 노드 0에 프로세스를 고정
numactl --cpunodebind=0 --membind=0 java -jar service.jar

# 또는 JVM 힙을 특정 NUMA 노드에 바인딩
java -XX:+UseNUMA -XX:+UseParallelGC -jar service.jar
```

`-XX:+UseNUMA` 옵션 적용 후 p99 latency가 **340ms → 180ms**로 개선됐다.

### 3. 디스크 I/O 병목: await와 %util의 함정

```bash
# I/O 스케줄러 확인 및 변경
cat /sys/block/nvme0n1/queue/scheduler
# 출력: [mq-deadline] kyber bfq none

# NVMe SSD에는 none(noop)이 일반적으로 더 빠름
echo none | sudo tee /sys/block/nvme0n1/queue/scheduler

# 변경 전후 벤치마크
fio --name=randread --ioengine=libaio --iodepth=32 \
    --rw=randread --bs=4k --direct=1 \
    --size=4G --numjobs=4 --runtime=60 \
    --group_reporting --filename=/dev/nvme0n1
```

**중요한 트레이드오프**: `%util`이 100%라도 NVMe는 포화 상태가 아닐 수 있다. NVMe는 큐 깊이가 65535까지 지원하는 병렬 장치다. 실제 포화 지표는 **await 시간**이다.

```bash
# await 분포를 히스토그램으로 확인 (bpftrace 사용)
sudo bpftrace -e '
kprobe:blk_account_io_start { @start[arg0] = nsecs; }
kprobe:blk_account_io_done
/@start[arg0]/
{
  @usecs = hist((nsecs - @start[arg0]) / 1000);
  delete(@start[arg0]);
}'
```

### 4. 네트워크 병목: 패킷 레벨 분석

```bash
# 네트워크 드롭/에러 상세 분석
netstat -s | grep -E "segments retransmitted|failed connection|resets received"
ss -s  # 소켓 상태 요약

# TCP 재전송 실시간 모니터링
watch -n 1 "netstat -s | grep retransmit"

# 네트워크 인터페이스별 처리량과 에러
sar -n DEV 1 10
```

**실전 사례: TCP 소켓 고갈**

백엔드 서비스에서 간헐적 연결 실패 발생. `ss -s` 결과 TIME_WAIT 소켓이 60,000개 이상 쌓인 것이 원인이었다.

```bash
# 현재 소켓 상태 분포 확인
ss -tan | awk '{print $1}' | sort | uniq -c | sort -rn

# 커널 파라미터 튜닝
sudo sysctl -w net.ipv4.tcp_tw_reuse=1
sudo sysctl -w net.ipv4.ip_local_port_range="1024 65535"
sudo sysctl -w net.core.somaxconn=65535
sudo sysctl -w net.ipv4.tcp_fin_timeout=15

# 영구 적용
cat >> /etc/sysctl.conf << 'EOF'
net.ipv4.tcp_tw_reuse = 1
net.ipv4.ip_local_port_range = 1024 65535
net.core.somaxconn = 65535
net.ipv4.tcp_fin_timeout = 15
EOF
```

### 5. 종합 벤치마킹: 부하 시나리오 재현

단순한 `ab`(ApacheBench)보다 **wrk2**는 고정 throughput으로 latency 분포를 측정할 수 있어 실제 운영 환경과 유사한 벤치마킹이 가능하다.

```bash
# wrk2로 일정 RPS 유지하며 latency 분포 측정
# --rate: 초당 요청 수 고정 (중요: -R 옵션이 wrk2의 핵심)
wrk2 -t4 -c100 -d60s -R1000 --latency \
  http://localhost:8080/api/endpoint

# 출력 예시
# Latency Distribution
#    50%    4.51ms
#    75%    6.12ms
#    90%    8.34ms
#    99%   45.23ms  ← p99이 p50의 10배 이상이면 tail latency 문제
#    99.9% 234.56ms
```

**왜 wrk보다 wrk2인가**: wrk는 "coordinated omission" 문제가 있다. 서버가 느려지면 요청 자체를 덜 보내 latency가 실제보다 좋게 나온다. wrk2는 고정 RPS를 유지하므로 실제 latency를 정확하게 측정한다.

## 주의사항 및 트레이드오프

### 튜닝 파라미터별 트레이드오프

| 튜닝 항목 | 이득 | 리스크 |
|-----------|------|--------|
| `vm.swappiness=0` | 스왑 방지, 메모리 성능 향상 | OOM Killer 발동 가능성 증가 |
| `tcp_tw_reuse=1` | 포트 고갈 방지 | NAT 환경에서 연결 충돌 가능 |
| I/O 스케줄러 `none` | NVMe 처리량 증가 | HDD에는 역효과 |
| `huge pages` 활성화 | TLB 미스 감소 | 메모리 단편화, 소규모 서비스에는 낭비 |
| `net.core.rmem_max` 증가 | 고대역폭 연결 성능 향상 | 메모리 사용량 증가 |

### 프로덕션 튜닝 시 필수 체크리스트

```bash
# 튜닝 전 반드시 기준선 측정 및 저장
date +%Y%m%d_%H%M%S > baseline_timestamp.txt
vmstat 1 60 > baseline_vmstat.txt &
iostat -x 1 60 > baseline_iostat.txt &
sar -n DEV 1 60 > baseline_network.txt &

# 튜닝 파라미터는 반드시 sysctl로 런타임 먼저 적용 (재부팅 없이 롤백 가능)
sudo sysctl -w kernel.parameter=value

# 효과 확인 후 /etc/sysctl.conf에 영구 적용
# 롤백이 필요할 경우
sudo sysctl -w kernel.parameter=original_value
```

### 측정 자체가 성능에 미치는 영향

`strace`, `tcpdump`는 실행 중인 서비스 성능에 **10~50% 오버헤드**를 줄 수 있다. 프로덕션 환경에서는 반드시 eBPF 기반 도구(`bpftrace`, `bcc-tools`)를 사용하라. eBPF는 커널 레벨에서 JIT 컴파일되어 오버헤드가 **1~5%** 수준이다.

```bash
# strace 대신 bpftrace로 시스템콜 추적
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_* 
  /pid == strtoull(str($1), 10, 10)/
  { @[probe] = count(); }' -- $(pgrep myapp)
```

## 정리

성능 튜닝은 **데이터 주도의 반복 프로세스**다. 핵심을 세 줄로 요약하면:

1. **측정 먼저**: 기준선 없는 튜닝은 의미없다. wrk2, fio, perf로 수치를 먼저 확보하라
2. **USE 메서드로 체계화**: 감으로 찾지 말고 Utilization → Saturation → Errors 순서로 좁혀가라
3. **트레이드오프를 이해하라**: 모든 튜닝에는 비용이 있다. 특히 운영 환경의 워크로드 특성(읽기 많은지, 쓰기 많은지, latency 중심인지, throughput 중심인지)을 반드시 고려해야 한다

다음 단계로는 **Flame Graph를 활용한 CPU 프로파일 시각화**나 **eBPF 기반의 커스텀 트레이싱**을 익히면 이 글에서 다룬 도구들만으로 찾기 어려운 미묘한 병목까지 잡을 수 있다.
