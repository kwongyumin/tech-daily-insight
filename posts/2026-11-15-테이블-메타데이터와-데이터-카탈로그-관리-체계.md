# 테이블 메타데이터와 데이터 카탈로그 관리 체계

## 개요

데이터 규모가 커지고 팀이 성장할수록 "이 테이블이 뭘 저장하는 거지?", "이 컬럼의 의미가 뭐지?", "이 데이터의 오너가 누구지?" 같은 질문이 반복된다. 처음에는 슬랙 채널에 물어보거나 오래된 팀원에게 구두로 전달받는 방식으로 버텨지지만, 어느 순간 이 비공식적인 지식 전달 체계가 병목이 된다.

**데이터 카탈로그(Data Catalog)** 는 이 문제를 조직 차원에서 해결하는 체계다. 단순히 테이블 목록을 나열하는 것이 아니라, 각 데이터 자산의 의미, 혈통(lineage), 품질, 접근 권한을 통합적으로 관리하는 플랫폼이다.

이 글에서는 테이블 메타데이터가 왜 중요한지부터 시작해서, 직접 구축하거나 오픈소스를 도입할 때 고려해야 할 핵심 개념과 실전 설계 패턴을 살펴본다.

---

## 핵심 개념

### 메타데이터의 종류

테이블 메타데이터는 크게 세 가지 계층으로 나눌 수 있다.

| 계층 | 종류 | 예시 |
|---|---|---|
| 기술적 메타데이터 | 스키마, 타입, 파티션 정보 | `user_id BIGINT NOT NULL` |
| 비즈니스 메타데이터 | 설명, 태그, 오너, 용어집 | "MAU 집계에 사용하는 사용자 테이블" |
| 운영 메타데이터 | 최근 갱신 시각, 쿼리 빈도, 데이터 품질 지표 | 최근 7일 평균 쿼리 횟수: 2,400회 |

세 계층 모두 관리하지 않으면 카탈로그가 "있어도 쓰지 않는 시스템"이 된다. 기술적 메타데이터만 자동으로 수집해두고 비즈니스 컨텍스트가 빠진 카탈로그는 결국 `SHOW TABLES`와 다를 게 없다.

### 데이터 혈통(Data Lineage)

데이터 혈통은 "이 데이터가 어디서 왔고, 어디로 흘러가는가"를 추적하는 것이다. 배치 파이프라인에서 버그가 발생했을 때 영향 범위를 즉시 파악하거나, 특정 소스 테이블을 deprecated할 때 downstream 의존성을 분석하는 데 필수적이다.

```
raw_events (Kafka)
    └── stg_events (Spark ETL)
            ├── dim_users (dbt)
            │       └── mart_mau (dbt)
            └── fct_orders (dbt)
                    └── mart_revenue (dbt)
```

### 용어집(Business Glossary)

동일한 개념을 팀마다 다른 이름으로 부르는 경우가 많다. "활성 사용자"가 마케팅 팀에서는 30일 내 로그인 유저를 의미하고, 프로덕트 팀에서는 7일 내 핵심 기능 사용자를 의미할 수 있다. 용어집은 이런 개념을 조직 차원에서 단일 정의로 관리한다.

## 실전 예제

### 1. 메타데이터 스키마 설계

메타데이터를 직접 저장하고 관리할 때 사용할 수 있는 기본 스키마 구조다.

```sql
-- 데이터 자산 기본 정보
CREATE TABLE data_assets (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    asset_type  ENUM('TABLE', 'VIEW', 'TOPIC', 'PIPELINE') NOT NULL,
    platform    VARCHAR(50)  NOT NULL,  -- 'mysql', 'bigquery', 'kafka'
    database_name VARCHAR(100),
    schema_name   VARCHAR(100),
    asset_name    VARCHAR(200) NOT NULL,
    description   TEXT,
    owner_team    VARCHAR(100),
    owner_email   VARCHAR(200),
    tags          JSON,                  -- ["pii", "core", "deprecated"]
    status        ENUM('ACTIVE', 'DEPRECATED', 'DRAFT') DEFAULT 'ACTIVE',
    created_at    DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at    DATETIME ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uq_asset (platform, database_name, schema_name, asset_name)
);

-- 컬럼 수준 메타데이터
CREATE TABLE asset_columns (
    id           BIGINT PRIMARY KEY AUTO_INCREMENT,
    asset_id     BIGINT NOT NULL REFERENCES data_assets(id),
    column_name  VARCHAR(200) NOT NULL,
    data_type    VARCHAR(100),
    description  TEXT,
    is_pii       BOOLEAN DEFAULT FALSE,
    glossary_term_id BIGINT,            -- 용어집 연결
    nullable     BOOLEAN DEFAULT TRUE,
    ordinal_position INT,
    UNIQUE KEY uq_column (asset_id, column_name)
);

-- 데이터 혈통 (방향 그래프)
CREATE TABLE data_lineage (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    source_asset_id BIGINT NOT NULL REFERENCES data_assets(id),
    target_asset_id BIGINT NOT NULL REFERENCES data_assets(id),
    lineage_type    ENUM('ETL', 'QUERY', 'STREAM', 'COPY') NOT NULL,
    transformation  TEXT,               -- SQL 또는 파이프라인 참조
    pipeline_name   VARCHAR(200),
    created_at      DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

### 2. 메타데이터 자동 수집 (Java/Spring 예제)

JDBC를 통해 데이터베이스 스키마를 자동으로 수집하는 컴포넌트 예시다.

```java
@Component
@RequiredArgsConstructor
public class MetadataCrawler {

    private final DataSource dataSource;
    private final DataAssetRepository dataAssetRepository;
    private final AssetColumnRepository columnRepository;

    @Scheduled(cron = "0 0 2 * * *") // 매일 새벽 2시
    public void crawlMysqlMetadata() {
        try (Connection conn = dataSource.getConnection()) {
            DatabaseMetaData dbMeta = conn.getMetaData();
            crawlTables(dbMeta, conn.getCatalog());
        } catch (SQLException e) {
            log.error("메타데이터 수집 중 오류 발생", e);
        }
    }

    private void crawlTables(DatabaseMetaData dbMeta, String catalog) throws SQLException {
        try (ResultSet tables = dbMeta.getTables(catalog, null, "%", new String[]{"TABLE", "VIEW"})) {
            while (tables.next()) {
                String tableName = tables.getString("TABLE_NAME");
                String tableType = tables.getString("TABLE_TYPE");
                String remarks   = tables.getString("REMARKS");

                DataAsset asset = dataAssetRepository
                    .findByPlatformAndAssetName("mysql", tableName)
                    .orElse(new DataAsset());

                // 기술적 메타데이터만 덮어씀 — 비즈니스 메타데이터는 보존
                asset.setPlatform("mysql");
                asset.setAssetName(tableName);
                asset.setAssetType(tableType.equals("VIEW") ? AssetType.VIEW : AssetType.TABLE);
                if (StringUtils.hasText(remarks) && !StringUtils.hasText(asset.getDescription())) {
                    asset.setDescription(remarks); // DB 코멘트를 초기값으로만 사용
                }
                dataAssetRepository.save(asset);

                crawlColumns(dbMeta, catalog, tableName, asset.getId());
            }
        }
    }

    private void crawlColumns(DatabaseMetaData dbMeta, String catalog,
                               String tableName, Long assetId) throws SQLException {
        try (ResultSet cols = dbMeta.getColumns(catalog, null, tableName, "%")) {
            while (cols.next()) {
                String colName  = cols.getString("COLUMN_NAME");
                String dataType = cols.getString("TYPE_NAME");
                String remarks  = cols.getString("REMARKS");
                int    position = cols.getInt("ORDINAL_POSITION");
                boolean nullable = cols.getInt("NULLABLE") == DatabaseMetaData.columnNullable;

                AssetColumn column = columnRepository
                    .findByAssetIdAndColumnName(assetId, colName)
                    .orElse(new AssetColumn());

                column.setAssetId(assetId);
                column.setColumnName(colName);
                column.setDataType(dataType);
                column.setOrdinalPosition(position);
                column.setNullable(nullable);
                if (StringUtils.hasText(remarks) && !StringUtils.hasText(column.getDescription())) {
                    column.setDescription(remarks);
                }
                columnRepository.save(column);
            }
        }
    }
}
```

### 3. 혈통 그래프 조회 API

downstream 의존성을 재귀적으로 조회하는 쿼리와 API 예시다.

```sql
-- MySQL 8.0+ CTE를 이용한 혈통 탐색
WITH RECURSIVE lineage_tree AS (
    -- 시작점
    SELECT
        source_asset_id,
        target_asset_id,
        pipeline_name,
        1 AS depth
    FROM data_lineage
    WHERE source_asset_id = :startAssetId

    UNION ALL

    -- 재귀 탐색
    SELECT
        dl.source_asset_id,
        dl.target_asset_id,
        dl.pipeline_name,
        lt.depth + 1
    FROM data_lineage dl
    INNER JOIN lineage_tree lt ON dl.source_asset_id = lt.target_asset_id
    WHERE lt.depth < 10  -- 순환 방지
)
SELECT
    da_src.asset_name AS source,
    da_tgt.asset_name AS target,
    lt.pipeline_name,
    lt.depth
FROM lineage_tree lt
JOIN data_assets da_src ON lt.source_asset_id = da_src.id
JOIN data_assets da_tgt ON lt.target_asset_id = da_tgt.id
ORDER BY lt.depth;
```

```java
@RestController
@RequestMapping("/api/catalog")
@RequiredArgsConstructor
public class DataCatalogController {

    private final DataCatalogService catalogService;

    @GetMapping("/assets/{assetId}/lineage/downstream")
    public ResponseEntity<LineageGraphResponse> getDownstreamLineage(
            @PathVariable Long assetId,
            @RequestParam(defaultValue = "5") int maxDepth) {

        LineageGraphResponse graph = catalogService.buildDownstreamGraph(assetId, maxDepth);
        return ResponseEntity.ok(graph);
    }

    @GetMapping("/assets")
    public ResponseEntity<Page<DataAssetSummary>> searchAssets(
            @RequestParam(required = false) String keyword,
            @RequestParam(required = false) List<String> tags,
            @RequestParam(required = false) String ownerTeam,
            Pageable pageable) {

        return ResponseEntity.ok(catalogService.search(keyword, tags, ownerTeam, pageable));
    }
}
```

### 4. 오픈소스 도입 시 연동 예시 (Apache Atlas REST API 호출)

직접 구축 대신 Apache Atlas나 DataHub 같은 오픈소스를 도입하는 경우, 사내 파이프라인에서 엔티티를 등록하는 패턴이다.

```java
@Service
public class AtlasLineagePublisher {

    private final RestTemplate restTemplate;
    private final String atlasBaseUrl;

    public void publishLineage(String sourceTable, String targetTable, String jobName) {
        Map<String, Object> payload = Map.of(
            "entities", List.of(
                buildTableEntity(sourceTable),
                buildTableEntity(targetTable),
                buildProcessEntity(jobName, sourceTable, targetTable)
            )
        );

        restTemplate.postForEntity(
            atlasBaseUrl + "/api/atlas/v2/entity/bulk",
            payload,
            String.class
        );
    }

    private Map<String, Object> buildProcessEntity(String jobName, String src, String tgt) {
        return Map.of(
            "typeName", "spark_process",
            "attributes", Map.of(
                "name", jobName,
                "qualifiedName", jobName + "@cluster",
                "inputs",  List.of(Map.of("typeName", "hive_table",
                                          "uniqueAttributes", Map.of("qualifiedName", src))),
                "outputs", List.of(Map.of("typeName", "hive_table",
                                          "uniqueAttributes", Map.of("qualifiedName", tgt)))
            )
        );
    }
}
```

## 주의사항 및 트레이드오프

### 자동 수집 vs 수동 관리

자동 크롤링으로 기술적 메타데이터를 수집하는 건 비교적 쉽다. 그러나 비즈니스 메타데이터(설명, 태그, 오너)는 사람이 채워야 한다. 이 두 계층의 갱신 주기와 소유권이 다르기 때문에, **자동으로 수집된 필드와 사람이 입력한 필드를 명확히 분리**해야 한다. 자동 크롤러가 사람이 쓴 설명을 덮어쓰는 사고가 의외로 자주 발생한다.

### 카탈로그 갱신 타이밍 문제

배포와 메타데이터 등록 사이에 시차가 생기면 카탈로그가 현실과 어긋난다. DDL 변경이 발생하는 시점에 메타데이터 등록을 강제하는 방법을 고려해야 한다. 예를 들어 Flyway/Liquibase 마이그레이션 완료 후 훅으로 카탈로그 API를 호출하거나, CI 파이프라인에 메타데이터 검증 스텝을 추가하는 방식이 있다.

### 직접 구축 vs 오픈소스 도입

| 기준 | 직접 구축 | 오픈소스 (DataHub, Atlas 등) |
|---|---|---|
| 초기 비용 | 낮음 | 높음 (운영 복잡도 포함) |
| 커스터마이징 | 자유로움 | 제한적 |
| 혈통 추적 깊이 | 구현 범위 내 | 풍부한 커넥터 기본 제공 |
| 유지보수 부담 | 높음 | 커뮤니티 의존 |

규모가 작고 플랫폼 종류가 단순하다면 직접 구축이 현실적이다. 반면 Kafka, Spark, BigQuery, dbt 등 여러 플랫폼을 혼용하고 있다면 DataHub처럼 풍부한 커넥터를 제공하는 오픈소스의 ROI가 훨씬 높다.

### PII 관리와 접근 제어

메타데이터 카탈로그에 PII 컬럼 표시를 했다면, 그것이 단순한 레이블에 그치지 않고 실제 접근 제어와 연동되어야 의미가 있다. 카탈로그에 "PII: true"라고 표시해놓고 실제 테이블 권한은 별도로 관리하면, 두 시스템 간 불일치가 보안 사고로 이어질 수 있다.

### 카탈로그의 "신선도" 문제

사용하지 않는 카탈로그는 오히려 혼란을 야기한다. 오래된 설명, 퇴사한 직원이 오너로 등록된 테이블, deprecated된 테이블이 ACTIVE로 표시된 경우 등이 쌓이면 개발자들이 카탈로그를 신뢰하지 않게 된다. 주기적인 오너 확인 알림, 일정 기간 쿼리가 없는 테이블 자동 플래깅 같은 **능동적인 데이터 품질 유지 프로세스**가 필수다.

## 정리

데이터 카탈로그는 도구보다 **문화와 프로세스**의 문제에 가깝다. 아무리 정교한 시스템을 구축해도 팀이 메타데이터를 갱신하지 않으면 쓸모없는 레거시가 된다.

실용적인 접근법은 다음 순서로 단계적으로 도입하는 것이다.

1. **기술적 메타데이터 자동 수집부터 시작** — 스키마 정보는 자동으로 얻을 수 있다.
2. **코어 테이블부터 비즈니스 메타데이터 채우기** — 전체를 한 번에 채우려 하지 말고 임팩트가 큰 테이블 20~30개부터 시작한다.
3. **개발 프로세스에 메타데이터 등록을 의무화** — 새 테이블 생성 시 PR 체크리스트에 카탈로그 등록을 포함한다.
4. **신선도 유지 메커니즘 추가** — 주기적 오너 확인, 품질 지표 대시보드, 알림 연동.

데이터가 조직의 핵심 자산이 된 시대에, 그 자산에 대한 메타데이터를 체계적으로 관리하는 것은 선택이 아니라 필수 인프라다. 처음에는 overhead처럼 느껴지지만, 온보딩 시간 단축, 사고 대응 속도 향상, 데이터 거버넌스 강화 측면에서 복리로 돌아오는 투자다.
