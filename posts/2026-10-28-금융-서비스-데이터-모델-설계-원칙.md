# 금융 서비스 데이터 모델 설계 원칙

## 개요

금융 서비스 도메인에서 데이터 모델 설계는 일반적인 CRUD 애플리케이션과 근본적으로 다른 접근이 필요하다. 잔액이 음수가 되거나, 거래 내역이 유실되거나, 동시 처리 중에 데이터 정합성이 깨지는 순간 서비스 신뢰도는 회복하기 어려운 타격을 입는다.

금융 데이터 모델의 핵심은 **불변성(Immutability)**, **추적 가능성(Auditability)**, **정합성(Consistency)** 이 세 가지다. 이 글에서는 실무에서 마주치는 대표적인 설계 문제들을 짚어보고, 각 상황에서 어떤 선택 기준으로 모델을 구성하는지 예제와 함께 설명한다.

---

## 핵심 개념

### 1. 잔액을 컬럼으로 관리하지 마라

가장 흔하고 치명적인 안티패턴은 계좌 테이블에 `balance` 컬럼을 두고 이를 직접 UPDATE하는 방식이다.

```sql
-- 안티패턴
UPDATE account SET balance = balance - 10000 WHERE account_id = 1;
```

이 방식의 문제는 단순하다. **현재 잔액은 맞을 수 있지만, 어떤 과정을 거쳐 그 값이 됐는지 알 수 없다.** 동시 요청 처리 시 Race Condition이 발생하고, 롤백 시점의 상태 복원도 까다롭다.

금융 도메인에서 검증된 방식은 **원장(Ledger) 기반 설계**다. 잔액은 거래 원장 테이블의 합산으로 계산하고, 원장 레코드는 한번 기록되면 수정되지 않는다.

### 2. 원장(Ledger) 패턴

원장 패턴의 핵심은 **모든 금액 변동을 이벤트로 기록**하는 것이다. 잔액은 파생값(Derived Value)이며, 항상 원장의 합산으로 계산된다.

```
거래 원장 레코드: account_id, amount(+/-), entry_type, created_at, transaction_id
잔액: SUM(amount) WHERE account_id = ?
```

이 패턴은 자연스럽게 감사 로그를 제공하고, 특정 시점의 잔액 재현도 가능하게 한다.

### 3. 복식 부기(Double-Entry Bookkeeping)

회계 원칙에서 차용한 복식 부기는 **모든 거래가 반드시 두 개 이상의 원장 항목으로 구성**되어야 한다는 원칙이다. 출금 계좌의 차변과 입금 계좌의 대변이 항상 합산 0이 되어야 한다. 이 제약 조건 자체가 데이터 정합성을 보장하는 강력한 도구다.

## 실전 예제

### 테이블 설계

```sql
-- 계좌 테이블 (잔액 컬럼 없음)
CREATE TABLE accounts (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id     BIGINT NOT NULL,
    account_no  VARCHAR(20) NOT NULL UNIQUE,
    currency    CHAR(3) NOT NULL DEFAULT 'KRW',
    status      ENUM('ACTIVE', 'SUSPENDED', 'CLOSED') NOT NULL DEFAULT 'ACTIVE',
    created_at  DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    updated_at  DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6) ON UPDATE CURRENT_TIMESTAMP(6),
    INDEX idx_user_id (user_id)
);

-- 거래 원장 테이블 (INSERT ONLY)
CREATE TABLE ledger_entries (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    transaction_id  VARCHAR(36) NOT NULL,   -- UUID
    account_id      BIGINT NOT NULL,
    amount          DECIMAL(19, 4) NOT NULL, -- 양수: 입금(대변), 음수: 출금(차변)
    entry_type      ENUM('DEBIT', 'CREDIT') NOT NULL,
    balance_after   DECIMAL(19, 4) NOT NULL, -- 기록 시점 잔액 스냅샷
    description     VARCHAR(255),
    created_at      DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    INDEX idx_account_id_created (account_id, created_at),
    INDEX idx_transaction_id (transaction_id)
);

-- 거래 트랜잭션 테이블
CREATE TABLE financial_transactions (
    id              VARCHAR(36) PRIMARY KEY,  -- UUID
    transaction_type ENUM('TRANSFER', 'DEPOSIT', 'WITHDRAWAL', 'FEE') NOT NULL,
    status          ENUM('PENDING', 'COMPLETED', 'FAILED', 'CANCELLED') NOT NULL DEFAULT 'PENDING',
    total_amount    DECIMAL(19, 4) NOT NULL,
    currency        CHAR(3) NOT NULL,
    idempotency_key VARCHAR(64) UNIQUE,       -- 중복 요청 방지
    created_at      DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    completed_at    DATETIME(6)
);
```

### Java/Spring 서비스 레이어 구현

```java
@Service
@RequiredArgsConstructor
@Transactional
public class TransferService {

    private final AccountRepository accountRepository;
    private final LedgerEntryRepository ledgerEntryRepository;
    private final FinancialTransactionRepository transactionRepository;
    private final ApplicationEventPublisher eventPublisher;

    public TransferResult transfer(TransferCommand command) {
        // 1. 멱등성 키 중복 체크
        if (transactionRepository.existsByIdempotencyKey(command.getIdempotencyKey())) {
            return transactionRepository
                .findByIdempotencyKey(command.getIdempotencyKey())
                .map(TransferResult::fromExisting)
                .orElseThrow();
        }

        // 2. 계좌 조회 (비관적 잠금 - 데드락 방지를 위해 ID 오름차순 정렬)
        long fromId = command.getFromAccountId();
        long toId = command.getToAccountId();
        
        Account fromAccount = accountRepository
            .findByIdWithLock(Math.min(fromId, toId) == fromId ? fromId : toId);
        Account toAccount = accountRepository
            .findByIdWithLock(Math.min(fromId, toId) == fromId ? toId : fromId);

        // 3. 잔액 검증 (원장 합산으로 계산)
        BigDecimal currentBalance = ledgerEntryRepository
            .sumAmountByAccountId(command.getFromAccountId());
        
        if (currentBalance.compareTo(command.getAmount()) < 0) {
            throw new InsufficientBalanceException(command.getFromAccountId(), currentBalance);
        }

        // 4. 거래 트랜잭션 생성
        FinancialTransaction txn = FinancialTransaction.builder()
            .id(UUID.randomUUID().toString())
            .transactionType(TransactionType.TRANSFER)
            .status(TransactionStatus.PENDING)
            .totalAmount(command.getAmount())
            .currency(command.getCurrency())
            .idempotencyKey(command.getIdempotencyKey())
            .build();
        transactionRepository.save(txn);

        // 5. 복식 부기 원장 항목 생성
        BigDecimal fromBalanceAfter = currentBalance.subtract(command.getAmount());
        BigDecimal toCurrentBalance = ledgerEntryRepository
            .sumAmountByAccountId(command.getToAccountId());
        BigDecimal toBalanceAfter = toCurrentBalance.add(command.getAmount());

        LedgerEntry debitEntry = LedgerEntry.builder()
            .transactionId(txn.getId())
            .accountId(command.getFromAccountId())
            .amount(command.getAmount().negate())  // 차변: 음수
            .entryType(EntryType.DEBIT)
            .balanceAfter(fromBalanceAfter)
            .description("이체 출금: " + command.getDescription())
            .build();

        LedgerEntry creditEntry = LedgerEntry.builder()
            .transactionId(txn.getId())
            .accountId(command.getToAccountId())
            .amount(command.getAmount())            // 대변: 양수
            .entryType(EntryType.CREDIT)
            .balanceAfter(toBalanceAfter)
            .description("이체 입금: " + command.getDescription())
            .build();

        ledgerEntryRepository.saveAll(List.of(debitEntry, creditEntry));

        // 6. 거래 완료 처리
        txn.complete();
        transactionRepository.save(txn);

        // 7. 도메인 이벤트 발행 (비동기 후처리: 알림, 통계 등)
        eventPublisher.publishEvent(new TransferCompletedEvent(txn.getId(), command));

        return TransferResult.success(txn.getId(), fromBalanceAfter);
    }
}
```

### 잔액 조회 최적화

원장 합산 방식은 정합성이 높지만 레코드가 누적되면 성능이 저하된다. 이를 위한 **스냅샷(Checkpoint) 패턴**을 함께 사용한다.

```java
@Repository
public interface LedgerEntryRepository extends JpaRepository<LedgerEntry, Long> {

    // 최신 스냅샷 이후의 원장 항목만 합산 (성능 최적화)
    @Query("""
        SELECT COALESCE(SUM(le.amount), 0)
        FROM LedgerEntry le
        WHERE le.accountId = :accountId
          AND le.createdAt > (
              SELECT COALESCE(MAX(bs.snapshotAt), '1970-01-01')
              FROM BalanceSnapshot bs
              WHERE bs.accountId = :accountId
          )
        """)
    BigDecimal sumAmountAfterLastSnapshot(@Param("accountId") Long accountId);

    @Query("SELECT COALESCE(SUM(le.amount), 0) FROM LedgerEntry le WHERE le.accountId = :accountId")
    BigDecimal sumAmountByAccountId(@Param("accountId") Long accountId);
}
```

## 주의사항 및 트레이드오프

### 금액 타입: DECIMAL vs Long(원화 단위)

`DECIMAL(19, 4)` vs `BIGINT`(최소 단위 정수) 선택은 서비스 특성에 따라 달라진다.

| 기준 | DECIMAL | Long(최소 단위) |
|---|---|---|
| 다통화 지원 | 유리 | 통화별 변환 필요 |
| 연산 정확도 | DB 레벨 보장 | 애플리케이션 레벨 관리 |
| 성능 | 상대적으로 느림 | 빠름 |
| 코드 복잡도 | 낮음 | 높음 (단위 변환 실수 위험) |

Java에서는 `BigDecimal`을 사용하고, **절대 `double`이나 `float`으로 금액을 다루지 않는다.**

### 비관적 잠금 vs 낙관적 잠금

- **비관적 잠금(Pessimistic Lock)**: 잔액 차감처럼 충돌 가능성이 높은 연산에 적합. 처리량이 낮아지는 대신 재시도 로직이 불필요.
- **낙관적 잠금(Optimistic Lock)**: 충돌이 드문 경우에 적합하나, 금융 서비스의 핵심 자금 이동 경로에는 권장하지 않는다. 재시도 폭풍(Retry Storm)이 오히려 부하를 키울 수 있다.

데드락 방지를 위해 **여러 계좌를 잠글 때는 반드시 일관된 순서(예: account_id 오름차순)로 잠금을 획득**해야 한다.

### 멱등성(Idempotency) 설계

네트워크 장애로 인한 재요청은 필연적이다. `idempotency_key`를 클라이언트가 생성한 UUID로 받아, 동일한 키가 들어오면 이전 결과를 그대로 반환해야 한다. 이 키는 **DB UNIQUE 제약 조건**으로 강제해야 하며, 애플리케이션 레벨 체크만으로는 부족하다.

### 소프트 삭제와 상태 전이

금융 데이터는 물리 삭제하지 않는다. 계좌 폐쇄도 `status = 'CLOSED'` 상태 전이일 뿐이다. 상태 전이 규칙은 도메인 객체 내부에서 강제하고, 허용되지 않는 전이는 예외로 처리한다.

```java
public void close() {
    if (this.status == AccountStatus.SUSPENDED) {
        this.status = AccountStatus.CLOSED;
    } else {
        throw new InvalidStateTransitionException(
            "계좌는 정지 상태에서만 폐쇄할 수 있습니다. 현재 상태: " + this.status
        );
    }
}
```

### 원장 테이블 파티셔닝

거래 원장은 데이터가 빠르게 쌓이는 테이블이다. `created_at` 기준 **범위 파티셔닝(Range Partitioning)** 을 월 단위로 적용하면 조회 성능과 데이터 아카이빙 모두 챙길 수 있다. 단, 파티션 키가 쿼리의 WHERE 절에 반드시 포함되도록 인덱스 전략을 함께 설계해야 한다.

## 정리

금융 서비스 데이터 모델 설계의 핵심을 다시 정리하면 다음과 같다.

1. **잔액은 파생값이다.** 원장 합산으로 계산하고, 별도 컬럼으로 관리하지 않는다.
2. **원장 레코드는 불변이다.** 수정이나 삭제 없이, 오류도 역방향 원장 항목으로 정정한다.
3. **복식 부기로 정합성을 강제한다.** 모든 거래의 차변/대변 합이 0이 되어야 한다.
4. **멱등성 키는 DB 제약으로 보장한다.** 애플리케이션 레벨 중복 체크는 보조 수단일 뿐이다.
5. **금액은 `BigDecimal`만 사용한다.** 부동소수점 타입은 금융 연산에서 사용을 금지한다.
6. **잠금 전략은 충돌 가능성 기반으로 결정한다.** 핵심 자금 이동에는 비관적 잠금이 안전하다.

이 원칙들은 특정 기술 스택에 종속되지 않는다. MySQL이든 PostgreSQL이든, 모놀리스든 MSA든, 금융 도메인의 불변 설계 원칙은 동일하게 적용된다. 처음 설계할 때 이 원칙을 지키는 비용보다, 나중에 잘못된 설계를 수정하는 비용이 훨씬 크다는 점을 항상 기억하자.
