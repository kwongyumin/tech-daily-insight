# 분산 트랜잭션 Saga 패턴과 이벤트 소싱 적용

## 개요

마이크로서비스 아키텍처가 보편화되면서 가장 골치 아픈 문제 중 하나로 **분산 트랜잭션** 처리가 떠올랐다. 단일 데이터베이스 환경에서는 ACID 트랜잭션으로 데이터 일관성을 손쉽게 보장할 수 있었지만, 서비스가 분리되고 각자 독립된 데이터 저장소를 가지는 순간 이야기가 달라진다.

고전적인 해법인 **2PC(Two-Phase Commit)** 는 분산 환경에서 성능 병목과 단일 장애점(SPOF) 문제를 야기하며, 클라우드 네이티브 환경에서는 사실상 적용이 어렵다. 이에 대한 현실적인 대안으로 **Saga 패턴**과 **이벤트 소싱(Event Sourcing)** 이 주목받고 있다.

이 글에서는 Saga 패턴의 두 가지 구현 방식을 비교하고, 이벤트 소싱과 결합했을 때 얻을 수 있는 시너지를 Spring Boot + Kafka 기반의 실전 예제와 함께 살펴본다.

---

## 핵심 개념

### Saga 패턴이란?

Saga는 **로컬 트랜잭션들의 시퀀스**로 글로벌 트랜잭션을 대체하는 패턴이다. 각 서비스는 자신의 로컬 트랜잭션을 완료한 후 이벤트를 발행하고, 실패 시에는 **보상 트랜잭션(Compensating Transaction)** 을 실행하여 이전 상태로 롤백한다.

구현 방식은 두 가지로 나뉜다.

| 방식 | 특징 | 적합한 상황 |
|------|------|-------------|
| **Choreography** | 각 서비스가 이벤트를 구독하고 자율적으로 반응 | 서비스 수가 적고 단순한 플로우 |
| **Orchestration** | 중앙 오케스트레이터가 각 서비스를 직접 호출 | 복잡한 비즈니스 플로우, 가시성 중요 |

### 이벤트 소싱이란?

이벤트 소싱은 **현재 상태 대신 상태 변화 이벤트를 저장**하는 패턴이다. 주문 상태가 `PENDING → PAID → SHIPPED`로 변할 때, 각 변화를 이벤트로 저장하고 이를 재생(replay)하여 현재 상태를 도출한다.

Saga와 이벤트 소싱의 결합이 강력한 이유는 다음과 같다.

- Saga의 각 단계가 이벤트로 기록되어 **감사(Audit) 추적**이 자연스럽게 된다.
- 이벤트 저장소가 **신뢰할 수 있는 단일 진실 공급원(Single Source of Truth)** 이 된다.
- **멱등성(Idempotency)** 보장이 용이해진다.

## 실전 예제: 주문-결제-재고 Saga

주문 생성 시 결제 서비스와 재고 서비스를 차례로 호출하는 **Orchestration 기반 Saga**를 Kafka와 Spring Boot로 구현해보자.

public sealed interface OrderEvent permits

    Instant occurredAt

### 이벤트 저장소 (Event Store)

```java
@Entity
@Table(name = "event_store")
@Getter
@NoArgsConstructor
public class EventStoreEntry {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String aggregateId;

    @Column(nullable = false)
    private String aggregateType;

    @Column(nullable = false)
    private String eventType;

    @Column(columnDefinition = "TEXT", nullable = false)
    private String payload;

    @Column(nullable = false)
    private Long version;

    @Column(nullable = false)
    private Instant occurredAt;

    public static EventStoreEntry of(String aggregateId, String aggregateType,
                                      OrderEvent event, Long version, String payload) {
        EventStoreEntry entry = new EventStoreEntry();
        entry.aggregateId = aggregateId;
        entry.aggregateType = aggregateType;
        entry.eventType = event.getClass().getSimpleName();
        entry.payload = payload;
        entry.version = version;
        entry.occurredAt = event.occurredAt();
        return entry;
    }
}

@Repository
public interface EventStoreRepository extends JpaRepository<EventStoreEntry, Long> {
    List<EventStoreEntry> findByAggregateIdOrderByVersionAsc(String aggregateId);
    Optional<EventStoreEntry> findTopByAggregateIdOrderByVersionDesc(String aggregateId);
}
```

### Saga Orchestrator 구현

```java
@Service
@RequiredArgsConstructor
@Slf4j
public class OrderSagaOrchestrator {

    private final KafkaTemplate<String, Object> kafkaTemplate;
    private final EventStoreRepository eventStoreRepository;
    private final ObjectMapper objectMapper;

    // 1단계: 주문 생성 → 결제 요청
    @Transactional
    public void startOrderSaga(OrderCreatedEvent event) {
        log.info("[Saga Start] orderId={}", event.orderId());

        // 이벤트 저장
        saveEvent(event.orderId(), "Order", event);

        // 결제 서비스에 커맨드 발행
        PaymentRequestCommand command = PaymentRequestCommand.builder()
            .orderId(event.orderId())
            .userId(event.userId())
            .amount(event.totalAmount())
            .build();

        kafkaTemplate.send("payment.request", event.orderId(), command);
        log.info("[Saga] Payment request sent for orderId={}", event.orderId());
    }

    // 2단계: 결제 완료 → 재고 예약 요청
    @KafkaListener(topics = "payment.completed", groupId = "order-saga")
    @Transactional
    public void onPaymentCompleted(PaymentCompletedEvent event) {
        log.info("[Saga] Payment completed for orderId={}", event.orderId());
        saveEvent(event.orderId(), "Order", event);

        // 재고 서비스에 커맨드 발행
        StockReserveCommand command = StockReserveCommand.builder()
            .orderId(event.orderId())
            .build();

        kafkaTemplate.send("stock.reserve", event.orderId(), command);
    }

    // 결제 실패 → 보상 트랜잭션 (주문 취소)
    @KafkaListener(topics = "payment.failed", groupId = "order-saga")
    @Transactional
    public void onPaymentFailed(PaymentFailedEvent event) {
        log.warn("[Saga Compensate] Payment failed for orderId={}, reason={}", 
            event.orderId(), event.reason());
        saveEvent(event.orderId(), "Order", event);

        // 주문 취소 보상 트랜잭션 발행
        OrderCancelCommand cancelCommand = OrderCancelCommand.builder()
            .orderId(event.orderId())
            .reason("PAYMENT_FAILED: " + event.reason())
            .build();

        kafkaTemplate.send("order.cancel", event.orderId(), cancelCommand);
    }

    // 이벤트 저장 (낙관적 잠금으로 중복 방지)
    private void saveEvent(String aggregateId, String aggregateType, OrderEvent event) {
        long nextVersion = eventStoreRepository
            .findTopByAggregateIdOrderByVersionDesc(aggregateId)
            .map(e -> e.getVersion() + 1)
            .orElse(1L);

        try {
            String payload = objectMapper.writeValueAsString(event);
            EventStoreEntry entry = EventStoreEntry.of(
                aggregateId, aggregateType, event, nextVersion, payload
            );
            eventStoreRepository.save(entry);
        } catch (JsonProcessingException e) {
            throw new IllegalStateException("Event serialization failed", e);
        }
    }
}
```

### 이벤트 재생을 통한 상태 복원

```java
@Service
@RequiredArgsConstructor
public class OrderAggregateService {

    private final EventStoreRepository eventStoreRepository;
    private final ObjectMapper objectMapper;

    public OrderAggregate reconstitute(String orderId) {
        List<EventStoreEntry> events = eventStoreRepository
            .findByAggregateIdOrderByVersionAsc(orderId);

        if (events.isEmpty()) {
            throw new OrderNotFoundException(orderId);
        }

        OrderAggregate aggregate = new OrderAggregate();

        for (EventStoreEntry entry : events) {
            OrderEvent event = deserialize(entry);
            aggregate.apply(event); // 이벤트를 순서대로 재생
        }

        return aggregate;
    }

    private OrderEvent deserialize(EventStoreEntry entry) {
        try {
            return switch (entry.getEventType()) {
                case "OrderCreatedEvent" -> 
                    objectMapper.readValue(entry.getPayload(), OrderCreatedEvent.class);
                case "PaymentCompletedEvent" -> 
                    objectMapper.readValue(entry.getPayload(), PaymentCompletedEvent.class);
                case "PaymentFailedEvent" -> 
                    objectMapper.readValue(entry.getPayload(), PaymentFailedEvent.class);
                default -> throw new UnknownEventTypeException(entry.getEventType());
            };
        } catch (JsonProcessingException e) {
            throw new EventDeserializationException(e);
        }
    }
}

// 집합체(Aggregate) - 이벤트를 적용하여 상태 유지
@Getter
public class OrderAggregate {
    private String orderId;
    private OrderStatus status;
    private BigDecimal totalAmount;

    public void apply(OrderEvent event) {
        switch (event) {
            case OrderCreatedEvent e -> {
                this.orderId = e.orderId();
                this.totalAmount = e.totalAmount();
                this.status = OrderStatus.PENDING;
            }
            case PaymentCompletedEvent e -> this.status = OrderStatus.PAID;
            case PaymentFailedEvent e -> this.status = OrderStatus.PAYMENT_FAILED;
            default -> { /* no-op */ }
        }
    }
}
```

## 주의사항 및 트레이드오프

### 1. 멱등성 보장은 필수다

Kafka 메시지는 **최소 1회(at-least-once)** 전달을 보장하기 때문에 동일 이벤트가 중복 처리될 수 있다. 이벤트 ID 기반의 중복 체크 테이블을 두거나, 이벤트 저장소의 버전 충돌 감지를 활용해야 한다.

```java
// 멱등성 체크 예시
@Column(unique = true)
private String eventId; // UUID 기반 고유 이벤트 식별자
```

### 2. 최종 일관성(Eventual Consistency)을 받아들여야 한다

Saga는 즉각적인 일관성을 포기하고 **최종 일관성**을 선택한다. 결제가 완료됐지만 재고 예약이 아직 처리 중인 순간이 존재한다. UI/UX 레벨에서도 이를 반영해야 하며, 비즈니스 팀과 사전 합의가 반드시 필요하다.

### 3. 보상 트랜잭션 설계는 신중하게

보상 트랜잭션은 **의미론적 롤백(Semantic Rollback)** 이지, DB 수준의 롤백이 아니다. 이미 전송된 이메일, 외부 API 호출 등은 되돌릴 수 없다. 이런 **피벗 트랜잭션(Pivot Transaction)** 을 식별하고, 전 단계까지만 보상이 가능하도록 설계해야 한다.

### 4. 이벤트 스키마 버전 관리

이벤트 소싱에서 저장된 이벤트는 **영구적**이다. 시간이 지나 이벤트 스키마가 변경되면 하위 호환성 문제가 발생한다. Apache Avro + Schema Registry를 사용하거나, 이벤트 업캐스팅(Upcasting) 전략을 미리 수립해두자.

### 5. 관찰 가능성(Observability) 확보

분산 Saga 플로우는 추적하기 어렵다. **분산 트레이싱(Distributed Tracing)** 을 위해 Saga 시작 시점에 `correlationId`를 생성하고, 모든 이벤트에 이를 전파하여 Jaeger나 Zipkin으로 시각화하는 것을 강력히 권장한다.

## 정리

Saga 패턴과 이벤트 소싱은 마이크로서비스의 분산 트랜잭션 문제에 대한 **현실적이고 검증된 해법**이다. 두 패턴의 핵심을 다시 정리하면 다음과 같다.

| 항목 | Saga 패턴 | 이벤트 소싱 |
|------|-----------|-------------|
| **목적** | 분산 트랜잭션 일관성 보장 | 상태 변화의 완전한 이력 관리 |
| **복잡도** | 보상 트랜잭션 설계 필요 | 이벤트 스키마 관리 필요 |
| **장점** | 서비스 간 결합도 낮춤 | 완벽한 감사 로그, 상태 재현 가능 |
| **단점** | 최종 일관성, 디버깅 어려움 | 이벤트 재생 성능(스냅샷 필요) |

두 패턴 모두 **도입 전 팀의 기술적 성숙도**와 **비즈니스 요구사항의 복잡도**를 먼저 평가해야 한다. 단순한 서비스에 과도한 패턴을 적용하면 오히려 복잡성만 증가한다.

하지만 주문, 결제, 정산처럼 **데이터 무결성이 핵심인 도메인**에서는 이 두 패턴의 조합이 분산 환경에서 가장 강력한 무기가 될 것이다. Axon Framework나 Eventuate Tram 같은 검증된 라이브러리도 함께 검토해보길 추천한다.
