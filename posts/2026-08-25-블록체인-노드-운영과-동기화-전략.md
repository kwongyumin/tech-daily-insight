# 블록체인 노드 운영과 동기화 전략

## 개요

블록체인 인프라를 직접 운영하다 보면 "노드를 어떻게 띄우고, 네트워크와 어떻게 동기화할 것인가"라는 질문이 생각보다 복잡하다는 것을 금방 깨닫게 됩니다. 단순히 바이너리를 실행하는 것 이상으로, 노드 타입 선택, 동기화 전략, 리소스 관리, 장애 대응까지 고려해야 할 요소가 산적해 있습니다.

이 글에서는 이더리움(Geth/Lighthouse 기준)을 중심으로 블록체인 노드 운영의 핵심 개념과 실전에서 바로 활용할 수 있는 전략을 다룹니다. AWS나 온프레미스 환경에서 노드를 운영해본 경험이 있거나, RPC 엔드포인트를 직접 관리해야 하는 백엔드 개발자라면 이 글이 실질적인 도움이 될 것입니다.

---

## 핵심 개념

### 노드 타입 분류

블록체인 노드는 저장하는 상태의 범위에 따라 세 가지로 나뉩니다.

| 노드 타입 | 저장 데이터 | 디스크 용량(이더리움) | 용도 |
|---|---|---|---|
| **Full Node** | 모든 블록 + 현재 상태 | ~1TB+ | 일반 RPC, 트랜잭션 검증 |
| **Archive Node** | 모든 블록 + 모든 역사적 상태 | ~14TB+ | eth_call 과거 블록 조회 |
| **Light Node** | 블록 헤더만 | ~수 GB | 경량 클라이언트 |

> **실무 포인트**: DeFi 프로토콜이나 인덱서를 개발할 때 과거 블록 시점의 상태(`eth_call` with `blockNumber`)가 필요하다면 반드시 Archive Node가 필요합니다. Full Node에서 오래된 상태를 조회하면 `missing trie node` 에러가 발생합니다.

### 동기화 모드

이더리움 실행 클라이언트(Geth)는 여러 동기화 모드를 제공합니다.

- **Full Sync**: 제네시스 블록부터 모든 트랜잭션을 직접 실행. 가장 신뢰도 높지만 수 주가 소요.
- **Snap Sync (기본값)**: 최신 상태 스냅샷을 다운로드 후 나머지를 채움. 수 시간~수 일 내 완료.
- **Light Sync**: 헤더만 동기화. 빠르지만 Full Node의 신뢰를 전제.

## 실전 예제

### 1. Docker Compose로 이더리움 노드 구성

이더리움 Merge 이후 실행 레이어(EL)와 합의 레이어(CL)를 함께 운영해야 합니다. 아래는 Geth(EL) + Lighthouse(CL) 조합의 Docker Compose 예시입니다.

```yaml
# docker-compose.yml
version: '3.8'

services:
  geth:
    image: ethereum/client-go:latest
    container_name: geth
    restart: unless-stopped
    ports:
      - "8545:8545"   # HTTP RPC
      - "8546:8546"   # WebSocket
      - "8551:8551"   # Engine API (CL 통신)
      - "30303:30303" # P2P
    volumes:
      - ./data/geth:/root/.ethereum
      - ./jwt.hex:/jwt.hex:ro
    command: >
      --mainnet
      --syncmode snap
      --http
      --http.addr 0.0.0.0
      --http.api eth,net,web3,txpool
      --http.vhosts "*"
      --ws
      --ws.addr 0.0.0.0
      --ws.api eth,net,web3
      --authrpc.addr 0.0.0.0
      --authrpc.port 8551
      --authrpc.jwtsecret /jwt.hex
      --authrpc.vhosts "*"
      --maxpeers 50
      --cache 4096
    networks:
      - eth-network

  lighthouse:
    image: sigp/lighthouse:latest
    container_name: lighthouse
    restart: unless-stopped
    ports:
      - "9000:9000/tcp"
      - "9000:9000/udp"
      - "5052:5052"   # Beacon API
    volumes:
      - ./data/lighthouse:/root/.lighthouse
      - ./jwt.hex:/jwt.hex:ro
    command: >
      lighthouse bn
      --network mainnet
      --execution-endpoint http://geth:8551
      --execution-jwt /jwt.hex
      --http
      --http-address 0.0.0.0
      --checkpoint-sync-url https://mainnet.checkpoint.sigp.io
      --disable-deposit-contract-sync
    networks:
      - eth-network

networks:
  eth-network:
    driver: bridge
```

JWT 시크릿 생성:

```bash
# JWT 공유 시크릿 생성 (EL-CL 인증용)
openssl rand -hex 32 > ./jwt.hex
```

### 2. Spring Boot에서 Web3j를 활용한 노드 상태 모니터링

노드가 정상적으로 동기화 중인지, 피어 수는 충분한지를 주기적으로 체크하는 헬스 모니터를 구현합니다.

```java
@Component
@Slf4j
public class NodeHealthMonitor {

    private final Web3j web3j;
    private final MeterRegistry meterRegistry;

    public NodeHealthMonitor(
            @Value("${node.rpc.url}") String rpcUrl,
            MeterRegistry meterRegistry) {
        this.web3j = Web3j.build(new HttpService(rpcUrl));
        this.meterRegistry = meterRegistry;
    }

    @Scheduled(fixedDelay = 30_000)
    public void checkNodeHealth() {
        try {
            // 동기화 상태 확인
            EthSyncing syncing = web3j.ethSyncing().send();
            boolean isSyncing = syncing.isSyncing();

            // 최신 블록 번호
            EthBlockNumber blockNumber = web3j.ethBlockNumber().send();
            long currentBlock = blockNumber.getBlockNumber().longValue();

            // 피어 수 확인
            NetPeerCount peerCount = web3j.netPeerCount().send();
            long peers = peerCount.getQuantity().longValue();

            // Micrometer 메트릭 기록
            Gauge.builder("node.block.number", () -> currentBlock)
                    .register(meterRegistry);
            Gauge.builder("node.peer.count", () -> peers)
                    .register(meterRegistry);

            if (isSyncing) {
                EthSyncing.Syncing syncData = (EthSyncing.Syncing) syncing.getResult();
                long highestBlock = Long.parseLong(
                    syncData.getHighestBlock().replace("0x", ""), 16);
                long lag = highestBlock - currentBlock;

                log.warn("[Node] 동기화 중 - 현재: {}, 최신: {}, 차이: {} 블록",
                        currentBlock, highestBlock, lag);

                Gauge.builder("node.sync.lag", () -> lag)
                        .register(meterRegistry);
            } else {
                log.info("[Node] 동기화 완료 - 블록: {}, 피어: {}", currentBlock, peers);
            }

            // 피어 수 임계값 경고
            if (peers < 5) {
                log.error("[Node] 피어 수 부족: {}개. 네트워크 연결 확인 필요.", peers);
                // 알림 발송 로직 (Slack, PagerDuty 등)
                sendAlert("피어 수 부족: " + peers);
            }

        } catch (IOException e) {
            log.error("[Node] RPC 연결 실패: {}", e.getMessage());
            sendAlert("노드 RPC 응답 없음");
        }
    }

    private void sendAlert(String message) {
        // Slack Webhook, PagerDuty API 등 연동
        log.error("[ALERT] {}", message);
    }
}
```

### 3. 노드 Failover를 위한 RPC 라우터 구현

단일 노드 장애에 대비한 멀티 노드 라운드로빈 + 헬스체크 기반 라우터입니다.

```java
@Component
public class RpcRouter {

    private final List<Web3j> nodePool;
    private final AtomicInteger index = new AtomicInteger(0);

    public RpcRouter(@Value("${node.rpc.urls}") List<String> rpcUrls) {
        this.nodePool = rpcUrls.stream()
                .map(url -> Web3j.build(new HttpService(url,
                        buildHttpClient(), false)))
                .collect(Collectors.toList());
    }

    /**
     * 살아있는 노드를 순환하며 반환. 모두 죽었으면 예외 발생.
     */
    public Web3j getHealthyNode() {
        int attempts = nodePool.size();
        for (int i = 0; i < attempts; i++) {
            int currentIndex = index.getAndIncrement() % nodePool.size();
            Web3j node = nodePool.get(currentIndex);
            if (isNodeAlive(node)) {
                return node;
            }
            log.warn("노드 {}번 응답 없음, 다음 노드 시도", currentIndex);
        }
        throw new IllegalStateException("사용 가능한 노드가 없습니다.");
    }

    private boolean isNodeAlive(Web3j node) {
        try {
            node.ethBlockNumber().send();
            return true;
        } catch (Exception e) {
            return false;
        }
    }

    private OkHttpClient buildHttpClient() {
        return new OkHttpClient.Builder()
                .connectTimeout(5, TimeUnit.SECONDS)
                .readTimeout(10, TimeUnit.SECONDS)
                .retryOnConnectionFailure(false)
                .build();
    }
}
```

## 주의사항 및 트레이드오프

### ⚠️ 디스크 I/O가 병목

블록체인 노드는 **SSD(NVMe 권장)** 가 필수입니다. HDD 환경에서는 동기화 속도가 수십 배 느려지며, 특히 Snap Sync의 상태 트리 쓰기 과정에서 I/O 포화가 발생합니다.

```bash
# 디스크 I/O 실시간 모니터링
iostat -x 2 | grep -E "Device|nvme|sda"

# Geth 데이터 디렉토리 크기 확인
du -sh ~/.ethereum/geth/chaindata/
```

### ⚠️ 메모리 캐시 튜닝

`--cache` 옵션은 Geth가 사용할 메모리(MB)를 지정합니다. 서버 RAM의 50~70%를 할당하는 것이 일반적입니다. 너무 작으면 디스크 읽기가 증가하고, 너무 크면 OOM이 발생합니다.

```bash
# 32GB RAM 서버 기준 권장 설정
--cache 16384
```

### ⚠️ Archive Node 운영 비용

Archive Node는 현재 기준 14TB 이상의 스토리지가 필요하며, 계속 증가합니다. 직접 운영하는 대신 **Alchemy, QuickNode, Infura** 같은 서드파티 노드 서비스를 Archive 조회 전용으로 활용하는 하이브리드 전략이 비용 효율적입니다.

### ⚠️ 동기화 재시작 시 스냅샷 활용

처음부터 다시 동기화하는 것은 시간 낭비입니다. [ethpandaops](https://ethpandaops.io/) 또는 각 클라이언트가 제공하는 공식 스냅샷을 활용하면 수 시간 내 따라잡을 수 있습니다.

```bash
# Lighthouse 체크포인트 동기화 (수 분 내 합의 레이어 동기화)
--checkpoint-sync-url https://mainnet.checkpoint.sigp.io

# Geth 상태 스냅샷 다운로드 후 임포트
geth snapshot dump <blockHash>
```

### 트레이드오프 요약

| 항목 | 자체 노드 | 서드파티 RPC |
|---|---|---|
| **신뢰성** | 직접 검증 가능, 높음 | 제공자 의존 |
| **비용** | 초기 인프라 비용 높음 | 사용량 기반, 저렴할 수 있음 |
| **레이턴시** | 내부망 사용 시 낮음 | 외부 네트워크 의존 |
| **운영 부담** | 모니터링/업그레이드 필요 | 없음 |
| **Rate Limit** | 없음 | 플랜별 제한 |

## 정리

블록체인 노드 운영은 단순한 서버 관리가 아닙니다. 네트워크 프로토콜, 상태 데이터베이스, 합의 메커니즘을 이해하고 그에 맞는 인프라 전략을 수립해야 합니다. 핵심을 정리하면 다음과 같습니다.

1. **노드 타입은 용도에 맞게 선택**: 일반 트랜잭션 처리는 Full Node, 과거 상태 조회는 Archive Node.
2. **Snap Sync를 기본으로 활용**: 합리적인 시간 내 동기화 완료 가능.
3. **EL + CL 이중 구성 필수(이더리움)**: Merge 이후 단독 실행 불가.
4. **모니터링은 필수**: 블록 지연, 피어 수, 디스크 I/O를 실시간으로 추적.
5. **멀티 노드 Failover**: 단일 노드에 의존하지 않는 RPC 라우터 구성.
6. **비용 최적화**: 자체 Full Node + 서드파티 Archive Node 하이브리드 전략 고려.

노드를 직접 운영해야 하는 시스템이라면 초기 설계 단계부터 동기화 전략과 장애 시나리오를 함께 고려하는 것이 장기적으로 안정적인 서비스를 만드는 지름길입니다.
