# DNS 동작 원리와 서비스 배포 시 고려사항 — 비용 최적화 관점

## 비용 최적화 관점에서 다시 보는 DNS 전략

---

## 개요

DNS는 단순한 "이름 → IP 변환" 인프라로 여겨지기 쉽습니다. 대부분의 팀이 초기 설정 후 거의 손대지 않는 영역이기도 합니다. 하지만 트래픽이 늘어나고 멀티 리전, 멀티 클라우드 아키텍처가 복잡해질수록 **DNS 쿼리 비용, 레코드 관리 비용, 잘못된 TTL 설정으로 인한 캐시 미스 비용**이 조용히 누적됩니다.

이 글은 DNS 동작 원리 자체보다는, 실무에서 DNS 설계를 **비용 관점**으로 다시 검토할 때 놓치기 쉬운 포인트들을 다룹니다. Route 53 기준 수치와 실전 트레이드오프를 중심으로 서술합니다.

---

## 핵심 개념: 비용이 발생하는 DNS 레이어

### 1. DNS 쿼리 비용 구조

AWS Route 53을 기준으로 DNS 비용은 크게 세 가지로 나뉩니다.

| 항목 | 비용 |
|---|---|
| 호스팅 존 (Hosted Zone) | $0.50 / 월 (존당) |
| 표준 쿼리 (Standard Query) | $0.40 / 100만 쿼리 |
| 레이턴시 기반 / 지역 라우팅 | $0.60 / 100만 쿼리 |
| Health Check | $0.50~$0.75 / 월 (체크당) |

월 10억 쿼리를 처리하는 서비스라면 라우팅 정책 하나 차이로 **월 $200 이상 차이**가 발생합니다. 소규모처럼 보여도, 마이크로서비스 환경에서 내부 서비스 디스커버리까지 Route 53을 쓴다면 쿼리 수가 폭발적으로 늘어납니다.

### 2. TTL이 곧 캐시 효율이고, 캐시 효율이 곧 비용

TTL(Time To Live)은 단순한 "캐시 유지 시간"이 아닙니다. TTL이 낮으면 클라이언트가 자주 Resolver에 질의하고, Resolver는 Authoritative NS에 자주 질의합니다. 이는 곧 **쿼리 횟수 증가 → 비용 증가**로 직결됩니다.

```
TTL = 60초일 때: 클라이언트 1만 명 → 1만 회/분 쿼리
TTL = 300초일 때: 동일 조건 → 2천 회/분 쿼리 (80% 절감)
```

배포 편의를 위해 낮게 설정한 TTL이 트래픽 증가 후에도 그대로 남아 있는 경우가 많습니다. **배포 완료 후 TTL을 다시 올리는 프로세스**를 파이프라인에 자동화하는 것이 중요합니다.

## 실전 예제

### 예제 1: 배포 전후 TTL 자동 조정 스크립트 (AWS CLI + Shell)

배포 시 Blue/Green 전환을 위해 TTL을 낮추고, 전환 완료 후 자동으로 복원하는 패턴입니다.

```bash
#!/bin/bash

HOSTED_ZONE_ID="Z1234567890ABC"
RECORD_NAME="api.example.com"
RECORD_TYPE="A"
NEW_IP="203.0.113.10"
LOW_TTL=60
HIGH_TTL=300

get_current_value() {
  aws route53 list-resource-record-sets \
    --hosted-zone-id "$HOSTED_ZONE_ID" \
    --query "ResourceRecordSets[?Name=='${RECORD_NAME}.']|[0].ResourceRecords[0].Value" \
    --output text
}

upsert_record() {
  local ip=$1
  local ttl=$2
  aws route53 change-resource-record-sets \
    --hosted-zone-id "$HOSTED_ZONE_ID" \
    --change-batch "{
      \"Changes\": [{
        \"Action\": \"UPSERT\",
        \"ResourceRecordSet\": {
          \"Name\": \"${RECORD_NAME}\",
          \"Type\": \"${RECORD_TYPE}\",
          \"TTL\": ${ttl},
          \"ResourceRecords\": [{\"Value\": \"${ip}\"}]
        }
      }]
    }"
}

CURRENT_IP=$(get_current_value)
echo "[1] TTL을 ${LOW_TTL}초로 낮춤 (현재 IP 유지)"
upsert_record "$CURRENT_IP" "$LOW_TTL"

echo "[2] 기존 TTL 만료 대기 (${HIGH_TTL}초)"
sleep "$HIGH_TTL"

echo "[3] 새 IP로 전환"
upsert_record "$NEW_IP" "$LOW_TTL"

echo "[4] 전환 검증 대기"
sleep 120

echo "[5] TTL을 ${HIGH_TTL}초로 복원 (비용 최적화)"
upsert_record "$NEW_IP" "$HIGH_TTL"

echo "배포 완료. TTL 복원됨."
```

> **포인트**: 많은 팀이 배포 전 TTL을 낮추지만, 복원을 잊습니다. 이 스크립트는 배포 파이프라인의 마지막 단계에 넣어 TTL 복원을 강제합니다.

### 예제 2: 내부 서비스 디스커버리 비용 절감 — Route 53 대신 CoreDNS 캐시 활용

Kubernetes 환경에서 Pod 간 통신이 매 요청마다 DNS 쿼리를 유발할 수 있습니다. 기본 CoreDNS 설정은 TTL을 그대로 따르기 때문에, 외부 Route 53까지 쿼리가 올라가는 구조가 생깁니다.

```yaml
# coredns-configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: coredns
  namespace: kube-system
data:
  Corefile: |
    .:53 {
        errors
        health
        ready
        
        # 외부 DNS 쿼리 캐시 TTL 강제 설정 (최소 30초, 최대 300초)
        cache 300 {
            success 9984 300   # 성공 응답 최대 300초 캐시
            denial  9984 30    # NXDOMAIN 최대 30초 캐시
        }
        
        kubernetes cluster.local in-addr.arpa ip6.arpa {
            pods insecure
            fallthrough in-addr.arpa ip6.arpa
            ttl 30
        }
        
        # 내부 서비스는 로컬에서만 resolve
        forward . /etc/resolv.conf {
            max_concurrent 1000
            prefer_udp
        }
        
        loop
        reload
        loadbalance
    }
```

이 설정으로 외부 DNS 쿼리 횟수를 **최대 70~80% 감소**시킬 수 있으며, Route 53 쿼리 비용을 직접적으로 절감합니다.

### 예제 3: Hosted Zone 통합으로 고정 비용 절감

마이크로서비스 팀별로 Hosted Zone을 분리하면 관리는 편하지만 비용이 누적됩니다.

```
# 비효율적인 구조 (월 $5.00)
api.team-a.example.com  → Hosted Zone A ($0.50)
api.team-b.example.com  → Hosted Zone B ($0.50)
api.team-c.example.com  → Hosted Zone C ($0.50)
...
# 존 10개 = 월 $5.00 고정비

# 최적화 구조 (월 $0.50)
# 단일 example.com Hosted Zone에 서브도메인으로 통합
api.team-a.example.com  ─┐
api.team-b.example.com  ─┤→ example.com Hosted Zone ($0.50)
api.team-c.example.com  ─┘
```

단, 이 경우 팀별 권한 분리(IAM Policy)를 세밀하게 설계해야 합니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "route53:ChangeResourceRecordSets",
        "route53:ListResourceRecordSets"
      ],
      "Resource": "arn:aws:route53:::hostedzone/Z1234567890ABC",
      "Condition": {
        "StringLike": {
          "route53:ChangeResourceRecordSetsNormalizedRecordNames": [
            "*.team-a.example.com"
          ]
        }
      }
    }
  ]
}
```

## 주의사항 및 트레이드오프

### 1. TTL 높이기 vs. 장애 복구 시간

| TTL | 쿼리 비용 | 장애 시 복구 시간 |
|---|---|---|
| 60초 | 높음 | 최대 1분 |
| 300초 | 중간 | 최대 5분 |
| 3600초 | 낮음 | 최대 1시간 |

**실전 권장값**: 일반 서비스는 300초, Health Check 연동 Failover 레코드는 60초, 변경이 거의 없는 레코드(MX, NS)는 3600초 이상.

> **함정**: Health Check와 연동된 Failover 레코드에 TTL을 높게 설정하면, Health Check가 실패를 감지해도 클라이언트 캐시 때문에 실제 Failover가 지연됩니다. Failover 레코드의 TTL은 반드시 낮게 유지해야 합니다.

### 2. Health Check 남발 금지

Route 53 Health Check는 각 엔드포인트당 월 $0.50~$0.75입니다. 50개 서비스에 각각 설정하면 **월 $25~$37.50이 고정 비용**으로 발생합니다.

**비용 최적화 전략**:
- ALB/NLB의 자체 Health Check + Route 53 Alias 레코드 조합으로 Route 53 Health Check를 생략
- 중요도가 낮은 서비스는 애플리케이션 레벨 모니터링(CloudWatch Alarm)으로 대체
- Health Check가 꼭 필요한 Critical 서비스에만 적용 후 CloudWatch Alarm과 연동하여 알림 통합

### 3. Private Hosted Zone의 숨겨진 비용

VPC 내부 Private Hosted Zone은 쿼리 비용이 없다고 오해하는 경우가 있습니다. **Private Hosted Zone도 쿼리당 $0.40**이 부과됩니다. 대규모 내부 서비스 디스커버리를 Route 53 Private Hosted Zone으로 처리하면 비용이 생각보다 클 수 있습니다.

대안으로 고려할 수 있는 옵션:

- **AWS Cloud Map**: 서비스 디스커버리 특화, API 호출 기반 과금으로 DNS 쿼리보다 비용 구조 예측이 쉬움
- **Consul**: 자체 호스팅 비용 vs. 관리형 DNS 비용 비교 필요
- **Kubernetes CoreDNS**: 클러스터 내부에서 완결되는 경우 외부 쿼리 0

### 4. CNAME vs. Alias 레코드

```
# CNAME: 쿼리 2회 (CNAME 조회 → 최종 A 레코드 조회)
api.example.com CNAME alb-1234.us-east-1.elb.amazonaws.com.

# Alias: 쿼리 1회 (Route 53이 내부적으로 해결)
api.example.com ALIAS alb-1234.us-east-1.elb.amazonaws.com.
```

AWS 리소스(ALB, CloudFront, S3 등)를 가리킬 때는 반드시 **Alias 레코드**를 사용하세요. Alias는 쿼리 비용이 무료이며, 쿼리 횟수도 절반으로 줄어듭니다. CNAME 대비 실질적으로 비용이 0원인 선택지입니다.

## 정리

DNS 비용 최적화는 인프라 비용의 큰 비중을 차지하지 않을 수 있지만, 잘못된 설계는 **쿼리 비용, 고정 비용, 불필요한 Health Check 비용**이 복합적으로 누적됩니다. 특히 마이크로서비스 환경에서는 내부 서비스 간 DNS 쿼리가 폭발적으로 증가하는 만큼, 설계 초기부터 비용 관점을 포함해야 합니다.

핵심 체크리스트:

- [ ] 배포 파이프라인에 **TTL 낮춤 → 전환 → TTL 복원** 자동화 포함
- [ ] AWS 리소스 연결 시 CNAME 대신 **Alias 레코드** 사용
- [ ] Hosted Zone 수 최소화, IAM으로 팀별 권한 분리
- [ ] Kubernetes 환경에서 **CoreDNS 캐시 설정** 적극 활용
- [ ] Health Check는 Critical 서비스에만 적용, ALB Health Check와 역할 분리
- [ ] Private Hosted Zone 쿼리 비용 모니터링 (CloudWatch DNS Query Logging 활성화)

DNS는 "한번 설정하면 끝"이 아니라, **트래픽 증가와 아키텍처 변화에 따라 주기적으로 재검토해야 하는 비용 최적화 대상**입니다.
