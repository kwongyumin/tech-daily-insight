# 배너·프로모션 기능을 유연하게 확장하는 도메인 설계

## 개요

거의 모든 서비스에는 배너와 프로모션이 존재한다. 이벤트 팝업, 메인 슬라이더, 카테고리별 띠 배너, 쿠폰 발급 프로모션, 타임딜... 처음에는 단순해 보이지만 서비스가 성장할수록 이 도메인은 걷잡을 수 없이 복잡해진다.

초기에 `banner` 테이블 하나로 시작한 설계가 반년 뒤 어떻게 변해있는지 본 적이 있는가? `is_popup`, `is_full_width`, `promotion_type`, `discount_rate`, `coupon_id`, `target_user_grade` 같은 컬럼이 하나씩 추가되고, 결국 null이 가득한 거대한 테이블 하나와 수십 개의 조건 분기로 가득 찬 서비스 레이어가 탄생한다.

이 글에서는 배너·프로모션 도메인을 처음부터 유연하게 설계하는 방법, 그리고 이미 복잡해진 설계를 개선하는 방향을 실전 예제 중심으로 살펴본다.

---

## 핵심 개념

### 왜 배너·프로모션 도메인은 복잡해지는가

배너와 프로모션이 복잡해지는 근본적인 이유는 **두 가지 다른 관심사가 하나의 테이블에 혼재**하기 때문이다.

- **노출 관심사**: 어디에(위치), 언제(기간), 누구에게(타겟), 어떻게(UI/UX) 보여줄 것인가
- **행동 관심사**: 클릭했을 때 무슨 일이 벌어지는가 (페이지 이동, 쿠폰 발급, 할인 적용 등)

이 둘을 분리하는 것이 설계의 핵심이다.

### 핵심 설계 원칙

**1. 노출(Display)과 액션(Action)의 분리**

배너가 "어떻게 보이는가"와 "무엇을 하는가"는 독립적으로 변경될 수 있어야 한다. 같은 디자인의 배너가 쿠폰을 발급하기도 하고, 외부 링크로 이동하기도 한다.

**2. 타입 계층 대신 전략 패턴 활용**

`banner_type = 'COUPON' | 'LINK' | 'POPUP'` 같은 단순 열거형으로 처리하면 타입마다 다른 비즈니스 로직을 조건문으로 분기해야 한다. 전략 패턴(Strategy Pattern)으로 액션을 추상화하면 새 타입 추가 시 기존 코드를 수정하지 않아도 된다.

**3. 타겟팅 조건을 별도 엔티티로 추출**

"로그인한 사용자 중 VIP 등급이고 최근 30일 내 구매 이력이 있는"과 같은 복잡한 타겟팅 조건은 배너 자체가 아닌 별도 도메인으로 관리해야 한다.

## 실전 예제

### 도메인 모델 설계

먼저 핵심 엔티티를 정의한다.

```java
// 배너의 노출 정보를 담당하는 핵심 엔티티
@Entity
@Table(name = "banners")
public class Banner {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String title;
    private String imageUrl;
    private String altText;

    @Enumerated(EnumType.STRING)
    private BannerSlot slot; // MAIN_TOP, CATEGORY_SIDE, POPUP 등

    private LocalDateTime startAt;
    private LocalDateTime endAt;
    private int displayOrder;

    @Enumerated(EnumType.STRING)
    private BannerStatus status; // DRAFT, ACTIVE, PAUSED, EXPIRED

    // 액션은 별도 엔티티로 위임
    @OneToOne(mappedBy = "banner", cascade = CascadeType.ALL, fetch = FetchType.LAZY)
    private BannerAction action;

    // 타겟팅 조건
    @OneToOne(mappedBy = "banner", cascade = CascadeType.ALL, fetch = FetchType.LAZY)
    private BannerTargeting targeting;

    public boolean isActiveDuring(LocalDateTime now) {
        return status == BannerStatus.ACTIVE
            && !now.isBefore(startAt)
            && !now.isAfter(endAt);
    }
}
```

```java
// 액션 타입을 추상화한 엔티티
@Entity
@Table(name = "banner_actions")
@Inheritance(strategy = InheritanceType.JOINED)
public abstract class BannerAction {

    @Id
    private Long id;

    @OneToOne(fetch = FetchType.LAZY)
    @MapsId
    @JoinColumn(name = "banner_id")
    private Banner banner;

    @Enumerated(EnumType.STRING)
    private ActionType actionType;

    public abstract ActionResult execute(ActionContext context);
}

@Entity
@Table(name = "banner_link_actions")
public class LinkAction extends BannerAction {

    private String targetUrl;
    private boolean openInNewTab;

    @Override
    public ActionResult execute(ActionContext context) {
        return ActionResult.redirect(targetUrl, openInNewTab);
    }
}

@Entity
@Table(name = "banner_coupon_actions")
public class CouponAction extends BannerAction {

    private String couponCode;
    private int maxIssuanceCount;

    @Override
    public ActionResult execute(ActionContext context) {
        // 쿠폰 발급 로직은 CouponService에 위임
        return ActionResult.issueCoupon(couponCode, context.getUserId());
    }
}
```

### 타겟팅 조건 설계

타겟팅 조건은 JSON 또는 별도 테이블로 관리할 수 있다. 조건이 단순하다면 JSON 컬럼이 편리하고, 조건이 복잡하고 쿼리가 필요하다면 정규화된 테이블이 낫다.

```java
@Entity
@Table(name = "banner_targetings")
public class BannerTargeting {

    @Id
    private Long id;

    @OneToOne(fetch = FetchType.LAZY)
    @MapsId
    @JoinColumn(name = "banner_id")
    private Banner banner;

    // 회원 등급 타겟팅 (null이면 전체)
    @ElementCollection
    @CollectionTable(name = "banner_targeting_grades")
    @Enumerated(EnumType.STRING)
    private Set<UserGrade> targetGrades;

    // 플랫폼 타겟팅
    @ElementCollection
    @CollectionTable(name = "banner_targeting_platforms")
    @Enumerated(EnumType.STRING)
    private Set<Platform> targetPlatforms; // WEB, AOS, IOS

    // 로그인 여부
    private Boolean requireLogin; // null이면 무관

    public boolean matches(TargetingContext context) {
        if (requireLogin != null && requireLogin != context.isLoggedIn()) {
            return false;
        }
        if (!targetGrades.isEmpty() && !targetGrades.contains(context.getUserGrade())) {
            return false;
        }
        if (!targetPlatforms.isEmpty() && !targetPlatforms.contains(context.getPlatform())) {
            return false;
        }
        return true;
    }
}
```

### 배너 조회 서비스

```java
@Service
@RequiredArgsConstructor
public class BannerQueryService {

    private final BannerRepository bannerRepository;

    public List<BannerResponse> getActiveBanners(BannerSlot slot, TargetingContext context) {
        LocalDateTime now = LocalDateTime.now();

        return bannerRepository.findActiveBySlot(slot, now)
            .stream()
            .filter(banner -> banner.getTargeting().matches(context))
            .sorted(Comparator.comparingInt(Banner::getDisplayOrder))
            .map(BannerResponse::from)
            .collect(Collectors.toList());
    }
}
```

```java
// Repository - 기본 필터링은 DB에서 처리
public interface BannerRepository extends JpaRepository<Banner, Long> {

    @Query("""
        SELECT b FROM Banner b
        JOIN FETCH b.action
        JOIN FETCH b.targeting
        WHERE b.slot = :slot
          AND b.status = 'ACTIVE'
          AND b.startAt <= :now
          AND b.endAt >= :now
        ORDER BY b.displayOrder ASC
    """)
    List<Banner> findActiveBySlot(
        @Param("slot") BannerSlot slot,
        @Param("now") LocalDateTime now
    );
}
```

### 프로모션 도메인 연계

프로모션은 배너와 별개의 도메인으로 존재하고, 배너는 프로모션을 "참조"하는 형태가 바람직하다.

```java
@Entity
@Table(name = "promotions")
public class Promotion {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private String description;

    @Enumerated(EnumType.STRING)
    private DiscountType discountType; // RATE, FIXED_AMOUNT

    private BigDecimal discountValue;
    private BigDecimal minimumOrderAmount;

    private LocalDateTime startAt;
    private LocalDateTime endAt;

    private int usageLimitPerUser;

    // 배너와의 연관은 배너 쪽에서 관리
    // Promotion은 Banner를 모른다 (단방향 참조)
}

// 프로모션 연결 액션
@Entity
@Table(name = "banner_promotion_actions")
public class PromotionAction extends BannerAction {

    private Long promotionId; // FK 대신 ID만 보관해 느슨한 결합 유지

    @Override
    public ActionResult execute(ActionContext context) {
        return ActionResult.applyPromotion(promotionId, context.getUserId());
    }
}
```

## 주의사항 및 트레이드오프

### 1. JPA Inheritance 전략 선택

`BannerAction`을 상속 구조로 설계할 때 JPA 상속 전략마다 트레이드오프가 있다.

| 전략 | 장점 | 단점 |
|---|---|---|
| `SINGLE_TABLE` | 조회 쿼리 단순, 성능 우수 | null 컬럼 증가, DB 무결성 약화 |
| `JOINED` | 정규화, 무결성 강 | JOIN 비용, 쿼리 복잡도 증가 |
| `TABLE_PER_CLASS` | 각 타입 독립적 | 다형성 쿼리 시 UNION 발생 |

액션 타입이 5개 미만이고 필드가 단순하다면 `SINGLE_TABLE`이, 타입별로 필드 수가 크게 다르고 타입이 많다면 `JOINED`가 적합하다. 실용적으로는 **JSON 컬럼으로 액션 메타데이터를 직렬화**하는 방식도 고려해볼 수 있다.

```java
// 대안: 단일 테이블 + JSON payload
@Entity
@Table(name = "banner_actions")
public class BannerAction {

    @Id
    private Long id;

    @Enumerated(EnumType.STRING)
    private ActionType actionType;

    @Convert(converter = JsonConverter.class)
    @Column(columnDefinition = "json")
    private Map<String, Object> payload; // 타입별 가변 데이터

    public ActionResult execute(ActionContext context) {
        ActionHandler handler = ActionHandlerRegistry.getHandler(actionType);
        return handler.handle(payload, context);
    }
}
```

이 방식은 단순하지만 타입 안전성을 잃고 스키마 변경이 어려워진다는 점을 감안해야 한다.

### 2. 타겟팅 조건의 복잡도 관리

타겟팅 조건이 단순 등급/플랫폼 필터를 넘어 "최근 N일 내 구매 이력"이나 "특정 상품 조회 이력" 같은 동적 조건으로 확장될 경우, **애플리케이션 레이어에서 모든 필터링을 처리하면 성능 문제**가 발생한다.

이런 경우 두 가지 접근을 고려한다.

- **Segment 기반 타겟팅**: 사용자를 사전에 세그먼트로 분류해두고 배너에 세그먼트 ID를 연결. 타겟팅 평가 비용을 조회 시점이 아닌 배치 처리 시점으로 이동
- **Feature Flag 서비스 연계**: 토글 기반 노출 제어는 LaunchDarkly 등 전용 도구에 위임

### 3. 캐싱 전략

배너는 조회가 빈번하고 변경이 드물다. 하지만 타겟팅 조건이 있으면 사용자별로 다른 결과가 나오므로 단순 전체 캐싱은 불가능하다.

현실적인 전략은 다음과 같다.

- **슬롯별 전체 배너 목록**을 캐싱 (타겟팅 필터링 전 데이터)
- 타겟팅 필터링은 애플리케이션에서 처리 (캐시 히트 후 경량 연산)
- TTL은 배너 수정 주기에 맞춰 설정 (보통 1~5분)

```java
@Cacheable(value = "banners", key = "#slot.name()")
public List<Banner> getCachedBannersBySlot(BannerSlot slot) {
    return bannerRepository.findActiveBySlot(slot, LocalDateTime.now());
}
```

### 4. 배너와 프로모션의 결합도 주의

배너가 프로모션 ID를 직접 FK로 갖는 순간 두 도메인은 강하게 결합된다. 프로모션이 삭제되거나 스키마가 변경될 때 배너도 함께 영향을 받는다. 가능하다면 **ID만 보관하고 조회 시점에 느슨하게 연결**하거나, 도메인 이벤트로 동기화하는 방식을 택하라.

## 정리

배너·프로모션 도메인의 복잡성은 비즈니스 요구사항이 늘어날수록 필연적으로 증가한다. 중요한 것은 그 복잡성을 **코드 한 곳에 쌓지 않고 적절한 경계로 분산**시키는 것이다.

핵심 원칙을 다시 정리하면:

1. **노출 정보와 액션을 분리**해 각각 독립적으로 변경 가능하게 설계한다
2. **액션을 전략 패턴으로 추상화**해 새 액션 타입 추가 시 OCP를 준수한다
3. **타겟팅 조건을 별도 엔티티로 추출**해 조건의 복잡도를 관리한다
4. **배너와 프로모션은 별개의 도메인**으로 느슨하게 연결한다
5. **조회 성능을 위해 슬롯 단위 캐싱**을 도입하고, 타겟팅 필터링은 애플리케이션 레이어에서 처리한다

처음부터 완벽한 설계를 하려 하기보다, 현재 요구사항에 맞는 단순한 구조로 시작하되 **확장 포인트를 명확히 열어두는 것**이 현실적인 접근이다. 이 글에서 소개한 구조는 하나의 출발점이며, 각 서비스의 도메인 맥락에 따라 적절히 조정해 적용하길 권장한다.
