# Flyway로 데이터베이스 마이그레이션 자동화

## 개요

데이터베이스 스키마 변경은 애플리케이션 개발에서 피할 수 없는 작업이다. 초기에는 개발자가 직접 SQL 스크립트를 실행하거나, 팀 내 공유 문서에 변경 사항을 기록하는 방식으로 관리했다. 하지만 팀 규모가 커지고 배포 환경이 다양해질수록 이런 수동 방식은 금세 한계를 드러낸다. "내 로컬에서는 되는데 스테이징에서 안 돼요"라는 말이 DB 스키마 불일치에서 비롯되는 경우도 적지 않다.

**Flyway**는 이러한 문제를 해결하기 위한 오픈소스 데이터베이스 마이그레이션 도구다. SQL 또는 Java 기반의 마이그레이션 스크립트를 버전 관리하고, 애플리케이션 시작 시 자동으로 현재 DB 상태에 맞는 스크립트를 순서대로 실행해준다. Spring Boot와의 통합이 매우 자연스러워 실무에서 가장 널리 쓰이는 마이그레이션 도구 중 하나다.

이 글에서는 Flyway의 핵심 개념부터 Spring Boot 프로젝트에서의 실전 적용, 그리고 실무에서 주의해야 할 트레이드오프까지 다룬다.

---

## 핵심 개념

### 버전 기반 마이그레이션 (Versioned Migration)

Flyway는 마이그레이션 스크립트의 파일명 컨벤션으로 버전을 관리한다.

```
V{version}__{description}.sql
```

예를 들어 `V1__init_schema.sql`, `V2__add_user_table.sql` 형태다. Flyway는 내부적으로 `flyway_schema_history`라는 메타데이터 테이블을 생성하고, 어떤 스크립트가 언제 실행되었는지를 기록한다. 애플리케이션이 시작될 때마다 이 히스토리와 파일 목록을 비교해 아직 실행되지 않은 마이그레이션만 순서대로 적용한다.

### Repeatable Migration

버전 없이 `R__` 접두사로 시작하는 스크립트는 내용이 변경될 때마다 재실행된다. 뷰(View), 저장 프로시저, 함수 등 내용 기반으로 갱신이 필요한 오브젝트 관리에 유용하다.

```
R__create_user_view.sql
```

### Checksum 검증

Flyway는 이미 실행된 마이그레이션 파일의 체크섬을 저장해두고, 파일이 변경되면 시작 시 오류를 발생시킨다. 이미 배포된 마이그레이션 파일을 수정하는 것은 금지된 행위다. 변경이 필요하다면 반드시 새로운 버전의 파일을 생성해야 한다.

## 실전 예제

### 1. 의존성 추가 (Spring Boot)

```xml
<!-- Maven -->
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>

<!-- MySQL 사용 시 추가 필요 (Flyway 9.x 이상) -->
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-mysql</artifactId>
</dependency>
```

```groovy
// Gradle
implementation 'org.flywaydb:flyway-core'
implementation 'org.flywaydb:flyway-mysql' // MySQL 사용 시
```

Spring Boot의 Auto Configuration 덕분에 의존성 추가만으로 기본 동작이 활성화된다.

### 2. 설정 (application.yml)

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/mydb
    username: root
    password: secret
    driver-class-name: com.mysql.cj.jdbc.Driver

  flyway:
    enabled: true
    locations: classpath:db/migration
    baseline-on-migrate: true     # 기존 DB에 처음 Flyway 적용 시
    validate-on-migrate: true     # 체크섬 검증 활성화
    out-of-order: false           # 버전 순서 강제
    table: flyway_schema_history  # 메타 테이블명 (기본값)
```

### 3. 마이그레이션 파일 구조

```
src/main/resources/
└── db/
    └── migration/
        ├── V1__init_schema.sql
        ├── V2__add_member_table.sql
        ├── V3__add_index_on_email.sql
        ├── V4__alter_member_add_phone.sql
        └── R__create_active_members_view.sql
```

### 4. 실제 마이그레이션 스크립트 예제

**V1__init_schema.sql** — 초기 스키마 생성

```sql
CREATE TABLE IF NOT EXISTS member (
    id          BIGINT          NOT NULL AUTO_INCREMENT,
    username    VARCHAR(50)     NOT NULL,
    email       VARCHAR(100)    NOT NULL,
    password    VARCHAR(255)    NOT NULL,
    status      VARCHAR(20)     NOT NULL DEFAULT 'ACTIVE',
    created_at  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_member_email (email)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**V2__add_member_table.sql** — 게시글 테이블 추가

```sql
CREATE TABLE IF NOT EXISTS post (
    id          BIGINT          NOT NULL AUTO_INCREMENT,
    member_id   BIGINT          NOT NULL,
    title       VARCHAR(200)    NOT NULL,
    content     TEXT,
    created_at  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    CONSTRAINT fk_post_member FOREIGN KEY (member_id)
        REFERENCES member (id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**V3__add_index_on_email.sql** — 성능 개선을 위한 인덱스 추가

```sql
-- 기존 UK가 있으므로 별도 인덱스는 생략하고, 복합 인덱스 추가 예시
CREATE INDEX idx_member_status_created
    ON member (status, created_at);
```

**V4__alter_member_add_phone.sql** — 컬럼 추가

```sql
ALTER TABLE member
    ADD COLUMN phone VARCHAR(20) NULL AFTER email,
    ADD COLUMN last_login_at DATETIME NULL;
```

**R__create_active_members_view.sql** — Repeatable 마이그레이션 (뷰)

```sql
CREATE OR REPLACE VIEW v_active_members AS
SELECT
    id,
    username,
    email,
    phone,
    created_at
FROM member
WHERE status = 'ACTIVE';
```

### 5. Java 기반 마이그레이션

복잡한 데이터 마이그레이션은 SQL만으로 표현하기 어려울 때 Java 클래스를 활용할 수 있다.

```java
package db.migration;

import org.flywaydb.core.api.migration.BaseJavaMigration;
import org.flywaydb.core.api.migration.Context;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.datasource.SingleConnectionDataSource;

import java.util.List;
import java.util.Map;

public class V5__migrate_legacy_data extends BaseJavaMigration {

    @Override
    public void migrate(Context context) throws Exception {
        JdbcTemplate jdbcTemplate = new JdbcTemplate(
            new SingleConnectionDataSource(context.getConnection(), true)
        );

        // 레거시 테이블에서 데이터를 읽어 변환 후 신규 테이블에 삽입
        List<Map<String, Object>> legacyUsers =
            jdbcTemplate.queryForList("SELECT * FROM legacy_user WHERE migrated = false");

        for (Map<String, Object> user : legacyUsers) {
            String normalizedEmail = ((String) user.get("email")).toLowerCase().trim();

            jdbcTemplate.update(
                "INSERT INTO member (username, email, password, status) VALUES (?, ?, ?, ?)",
                user.get("name"),
                normalizedEmail,
                user.get("pwd"),
                "ACTIVE"
            );

            jdbcTemplate.update(
                "UPDATE legacy_user SET migrated = true WHERE id = ?",
                user.get("id")
            );
        }
    }
}
```

> **주의:** Java 마이그레이션 클래스는 `db.migration` 패키지에 위치해야 하며, 클래스명이 버전 컨벤션을 따라야 한다. (`V5__migrate_legacy_data`)

### 6. 테스트 환경 분리

테스트에서는 별도의 마이그레이션 경로나 H2 인메모리 DB를 사용하는 경우가 많다.

```yaml
# src/test/resources/application-test.yml
spring:
  datasource:
    url: jdbc:h2:mem:testdb;MODE=MySQL;DB_CLOSE_DELAY=-1
    driver-class-name: org.h2.Driver

  flyway:
    locations: classpath:db/migration,classpath:db/testdata
```

```sql
-- src/test/resources/db/testdata/V100__insert_test_data.sql
INSERT INTO member (username, email, password, status)
VALUES
    ('tester1', 'test1@example.com', 'hashed_pw', 'ACTIVE'),
    ('tester2', 'test2@example.com', 'hashed_pw', 'INACTIVE');
```

## 주의사항 및 트레이드오프

### ⚠️ 실행된 마이그레이션 파일은 절대 수정하지 말 것

Flyway가 체크섬 불일치를 감지하면 애플리케이션 시작 자체가 실패한다. 이미 배포된 스크립트의 오탈자나 논리적 오류를 수정하고 싶다면, 반드시 새 버전 파일을 만들어 보정 마이그레이션을 수행해야 한다.

```sql
-- 잘못된 접근: V2 파일을 직접 수정 ❌
-- 올바른 접근: V2_1 또는 V3으로 보정 스크립트 추가 ✅
ALTER TABLE post MODIFY COLUMN title VARCHAR(300) NOT NULL;
```

### ⚠️ 대용량 테이블의 DDL은 별도 계획 필요

MySQL에서 대용량 테이블에 `ALTER TABLE`을 수행하면 긴 Lock이 발생할 수 있다. `pt-online-schema-change`나 `gh-ost`와 같은 도구를 활용하거나, Flyway 마이그레이션과 별도로 무중단 DDL 전략을 수립해야 한다. Flyway는 마이그레이션 실행의 순서와 기록을 관리할 뿐, DDL의 안전한 실행 전략까지 책임지지는 않는다.

### ⚠️ 멀티 인스턴스 환경에서의 동시성

여러 애플리케이션 인스턴스가 동시에 시작될 때 마이그레이션이 중복 실행될 위험이 있다. Flyway는 기본적으로 DB 레벨의 분산 락을 사용하여 이를 방지하므로, 지원 DB(MySQL, PostgreSQL 등)에서는 안전하다. 단, 락 타임아웃 설정(`flyway.lock-retry-count`)을 적절히 조정해야 한다.

```yaml
spring:
  flyway:
    lock-retry-count: 10  # 기본값: 50
```

### ⚠️ baseline-on-migrate 옵션 주의

이미 운영 중인 DB에 Flyway를 처음 도입할 때 `baseline-on-migrate: true`를 사용한다. 이 옵션은 처음 한 번만 필요하며, 이후에도 계속 켜두면 의도치 않은 동작을 유발할 수 있다. 도입 완료 후에는 `false`로 되돌리거나 제거하는 것이 바람직하다.

### 트레이드오프: Flyway vs Liquibase

| 항목 | Flyway | Liquibase |
|------|--------|-----------|
| 설정 복잡도 | 낮음 | 높음 |
| 스크립트 형식 | SQL / Java | XML, YAML, JSON, SQL |
| 롤백 지원 | 유료 기능 (Flyway Teams) | 무료 지원 |
| 조건부 마이그레이션 | 제한적 | 풍부한 Preconditions |
| 학습 곡선 | 완만 | 가파름 |

단순하고 빠른 도입이 목적이라면 Flyway가 낫고, 복잡한 롤백 시나리오나 다중 DB 벤더 지원이 필요하다면 Liquibase를 고려해볼 수 있다.

## 정리

Flyway는 데이터베이스 스키마 변경 이력을 코드와 함께 버전 관리함으로써, "DB 수동 관리"라는 고질적인 문제를 근본적으로 해결해준다. Spring Boot와의 Auto Configuration 덕분에 진입 장벽이 낮고, 실무에서도 빠르게 도입할 수 있다.

핵심 원칙은 간단하다.

1. **마이그레이션 파일은 불변이다.** 한번 배포된 스크립트는 수정하지 않는다.
2. **모든 환경은 동일한 마이그레이션 경로를 따른다.** 로컬, 스테이징, 프로덕션 모두 같은 스크립트로 관리한다.
3. **Git과 함께 관리한다.** 스키마 변경은 코드 변경과 동일한 PR 사이클로 리뷰하고 병합한다.

이 세 가지 원칙만 지켜도, 팀 내 "DB 스키마 불일치"로 인한 장애와 혼란을 크게 줄일 수 있다. 아직 수동으로 DB를 관리하고 있다면, Flyway 도입을 지금 바로 시작해보길 권한다.
