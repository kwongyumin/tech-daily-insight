# 마이크로서비스 vs 모놀리스 선택 기준과 트레이드오프

## 개요

"우리 시스템을 마이크로서비스로 전환해야 할까요?" 많은 팀에서 반복적으로 던지는 질문이다. 마이크로서비스 아키텍처는 넷플릭스, 아마존, 우버 같은 대형 테크 기업의 성공 사례를 통해 업계 표준처럼 여겨지는 분위기가 있다. 하지만 모든 상황에 마이크로서비스가 정답은 아니다.

이 글에서는 실무 경험을 바탕으로 **언제 모놀리스를 유지해야 하고, 언제 마이크로서비스로 전환해야 하는지**에 대한 구체적인 기준을 제시한다. 단순한 이론이 아닌, 실제 의사결정에 활용할 수 있는 판단 기준과 코드 레벨의 예제를 함께 살펴본다.

---

## 핵심 개념

### 모놀리식 아키텍처

모놀리스(Monolith)는 단일 배포 단위로 모든 비즈니스 로직이 하나의 애플리케이션에 포함된 구조다. 잘못 설계된 모놀리스는 "Big Ball of Mud"가 되지만, 잘 설계된 모놀리스는 오히려 강력한 무기가 된다.

```
[Monolith Application]
├── User Module
├── Order Module
├── Payment Module
├── Inventory Module
└── Notification Module
       ↓
  [Single DB]
```

**장점:**
- 개발/배포/디버깅이 단순
- 트랜잭션 일관성 확보 용이
- 초기 개발 속도 빠름
- 운영 오버헤드 낮음

**단점:**
- 팀 규모가 커질수록 병목 발생
- 특정 모듈의 스케일 아웃 불가
- 기술 스택 변경 어려움
- 배포 시 전체 서비스 영향

### 마이크로서비스 아키텍처

마이크로서비스는 독립적으로 배포 가능한 작은 서비스들의 집합이다. 각 서비스는 단일 비즈니스 도메인을 담당하며, API를 통해 통신한다.

```
[API Gateway]
     ↓
┌────┬────┬────┬────┐
│User│Order│Pay │Inv │
│ SVC│ SVC │SVC │ SVC│
└────┴────┴────┴────┘
  ↓     ↓    ↓    ↓
 DB1   DB2  DB3  DB4
```

**장점:**
- 독립적 배포 및 스케일링
- 팀별 기술 스택 자율성
- 장애 격리(Fault Isolation)
- 대규모 조직에 적합

**단점:**
- 분산 트랜잭션 복잡도 증가
- 네트워크 레이턴시 및 장애 포인트 증가
- 운영 인프라 비용 증가
- 서비스 간 계약 관리 필요

## 실전 예제

### 예제 1: 모놀리스에서의 트랜잭션 처리

모놀리스에서는 로컬 트랜잭션으로 데이터 일관성을 간단하게 보장할 수 있다.

```java
@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository orderRepository;
    private final InventoryRepository inventoryRepository;
    private final PaymentRepository paymentRepository;

    @Transactional
    public OrderResult placeOrder(OrderRequest request) {
        // 모두 같은 DB 트랜잭션 내에서 처리
        Order order = orderRepository.save(Order.from(request));
        
        inventoryRepository.decreaseStock(
            request.getProductId(), 
            request.getQuantity()
        );
        
        Payment payment = paymentRepository.save(
            Payment.of(order.getId(), request.getPaymentInfo())
        );
        
        // 하나라도 실패하면 전체 롤백 - 간단하고 명확!
        return OrderResult.of(order, payment);
    }
}
```

단 몇 줄의 `@Transactional` 어노테이션으로 ACID를 보장할 수 있다. 이것이 모놀리스의 가장 큰 강점이다.

### 예제 2: 마이크로서비스에서의 분산 트랜잭션 (SAGA 패턴)

마이크로서비스에서 동일한 시나리오를 구현하려면 훨씬 복잡한 패턴이 필요하다.

```java
// Choreography-based SAGA 예시 (Spring + Kafka)

@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository orderRepository;
    private final KafkaTemplate<String, Object> kafkaTemplate;

    public Order placeOrder(OrderRequest request) {
        // 1. 주문 생성 (PENDING 상태)
        Order order = orderRepository.save(
            Order.builder()
                .status(OrderStatus.PENDING)
                .productId(request.getProductId())
                .quantity(request.getQuantity())
                .build()
        );

        // 2. 재고 감소 이벤트 발행
        kafkaTemplate.send("inventory.decrease", 
            InventoryDecreaseEvent.of(order.getId(), request.getProductId(), request.getQuantity())
        );

        return order;
    }

    // 재고 감소 성공 이벤트 수신
    @KafkaListener(topics = "inventory.decreased")
    public void onInventoryDecreased(InventoryDecreasedEvent event) {
        kafkaTemplate.send("payment.process",
            PaymentProcessEvent.of(event.getOrderId(), getPaymentInfo(event.getOrderId()))
        );
    }

    // 보상 트랜잭션: 결제 실패 시 재고 복구
    @KafkaListener(topics = "payment.failed")
    public void onPaymentFailed(PaymentFailedEvent event) {
        orderRepository.updateStatus(event.getOrderId(), OrderStatus.FAILED);
        
        // 재고 복구 이벤트 발행 (Compensating Transaction)
        kafkaTemplate.send("inventory.compensate",
            InventoryCompensateEvent.of(event.getOrderId())
        );
    }

    // 결제 성공 시 주문 확정
    @KafkaListener(topics = "payment.completed")
    public void onPaymentCompleted(PaymentCompletedEvent event) {
        orderRepository.updateStatus(event.getOrderId(), OrderStatus.CONFIRMED);
    }
}
```

이 코드만 봐도 마이크로서비스에서의 복잡도가 얼마나 올라가는지 체감된다. 단순한 주문 처리 하나를 위해 이벤트 기반의 SAGA 패턴, 보상 트랜잭션, 멱등성 처리까지 고려해야 한다.

### 예제 3: 선택 기준 체크리스트 구현

실제로 아키텍처 의사결정 시 활용할 수 있는 판단 기준을 코드로 표현해보면 다음과 같다.

```java
public class ArchitectureDecisionHelper {

    public ArchitectureRecommendation evaluate(ProjectProfile profile) {
        int microserviceScore = 0;

        // 팀 규모: Conway's Law 적용
        if (profile.getTeamSize() >= 10) microserviceScore += 2;
        if (profile.getTeamCount() >= 3) microserviceScore += 2;

        // 트래픽 및 스케일링 요구사항
        if (profile.hasHeterogeneousScalingNeeds()) microserviceScore += 3;
        if (profile.getDailyActiveUsers() > 1_000_000) microserviceScore += 2;

        // 배포 독립성 필요 여부
        if (profile.requiresIndependentDeployment()) microserviceScore += 3;

        // 도메인 복잡도
        if (profile.hasClearDomainBoundaries()) microserviceScore += 2;
        if (profile.getDomainCount() >= 5) microserviceScore += 1;

        // 조직 성숙도
        if (!profile.hasDevOpsCapability()) microserviceScore -= 3;
        if (!profile.hasContainerOrchestration()) microserviceScore -= 2;
        if (profile.isEarlyStage()) microserviceScore -= 4;

        if (microserviceScore >= 8) {
            return ArchitectureRecommendation.MICROSERVICES;
        } else if (microserviceScore >= 4) {
            return ArchitectureRecommendation.MODULAR_MONOLITH; // 중간 단계
        } else {
            return ArchitectureRecommendation.MONOLITH;
        }
    }
}
```

## 주의사항 및 트레이드오프

### 1. "Premature Microservices" 안티패턴

가장 흔한 실수는 서비스 초기에 마이크로서비스로 시작하는 것이다. **도메인 경계가 명확하지 않은 상태에서 분리하면 오히려 잘못된 경계가 굳어진다.** 나중에 서비스를 합치는 것이 분리보다 훨씬 어렵다.

> "Don't start with microservices. Start with a monolith, identify the seams, then extract." — Sam Newman

### 2. 조직 구조와의 정렬 (Conway's Law)

기술적 선택은 조직 구조와 맞아야 한다. 5명짜리 팀이 10개의 마이크로서비스를 운영한다면, 인프라 관리 오버헤드가 개발 생산성을 잠식한다.

| 조직 규모 | 권장 아키텍처 |
|-----------|--------------|
| 1~10명 | 모놀리스 또는 모듈러 모놀리스 |
| 10~50명 | 모듈러 모놀리스 → 점진적 분리 |
| 50명 이상 | 마이크로서비스 (팀당 2~3개 서비스) |

### 3. 네트워크 신뢰성 문제

로컬 메서드 호출이 네트워크 호출로 바뀌는 순간, 다음을 반드시 고려해야 한다:

```yaml
# 마이크로서비스 운영 시 필수 고려사항
resilience:
  - Circuit Breaker (Resilience4j)
  - Retry with Exponential Backoff
  - Timeout 설정
  - Bulkhead Pattern
  
observability:
  - Distributed Tracing (Jaeger, Zipkin)
  - Centralized Logging (ELK Stack)
  - Metrics 수집 (Prometheus + Grafana)
  
deployment:
  - Container Orchestration (Kubernetes)
  - Service Mesh (Istio) 검토
  - Blue-Green / Canary 배포 전략
```

### 4. 모듈러 모놀리스: 현실적인 중간 지점

순수 마이크로서비스와 전통적 모놀리스 사이의 현실적 대안이다. 코드베이스는 하나지만, 도메인 경계를 명확히 패키지로 분리하여 향후 마이크로서비스 전환을 준비한다.

```
com.example.app
├── order/
│   ├── domain/
│   ├── application/
│   ├── infrastructure/
│   └── api/            ← 외부에 노출할 인터페이스만 공개
├── payment/
│   ├── domain/
│   ├── application/
│   ├── infrastructure/
│   └── api/
└── shared/
    └── kernel/         ← 공통 도메인 개념만 공유
```

이 구조는 단일 배포의 단순성을 유지하면서, 향후 서비스 분리 시 경계를 명확히 할 수 있다.

### 5. 데이터 일관성 vs 가용성 트레이드오프

마이크로서비스에서는 **Eventual Consistency를 수용하는 문화와 설계**가 필수다. 모든 쿼리에 강한 일관성이 필요하다면, 마이크로서비스 도입을 재고해야 한다.

```
강한 일관성 필요 → 모놀리스 유리
  예) 금융 계좌 이체, 재고 차감

결과적 일관성 수용 가능 → 마이크로서비스 유리
  예) SNS 팔로워 수, 조회수, 추천 피드
```

## 정리

마이크로서비스와 모놀리스 중 무엇이 우월하다는 답은 없다. 실무에서 판단 기준을 요약하면 다음과 같다.

**모놀리스를 선택해야 할 때:**
- 팀이 작고 도메인이 아직 명확하지 않을 때
- 빠른 초기 제품 출시(MVP)가 목표일 때
- DevOps/SRE 역량이 부족할 때
- 강한 트랜잭션 일관성이 핵심 요구사항일 때

**마이크로서비스를 선택해야 할 때:**
- 도메인 경계가 명확하고 팀이 독립적으로 움직여야 할 때
- 특정 컴포넌트의 독립적인 스케일링이 필요할 때
- 배포 주기가 팀마다 달라야 할 때
- 충분한 운영 인프라와 역량이 갖춰져 있을 때

결국 핵심은 **기술적 결정이 아닌 조직적 결정**이다. 어떤 아키텍처를 선택하든, 잘 설계된 모듈 경계와 명확한 팀 오너십이 뒷받침되어야 한다. "어떻게 배포하느냐"보다 "어떻게 경계를 나누느냐"가 더 중요한 질문임을 기억하자.

> 마이크로서비스는 목적이 아닌 수단이다. 목적은 팀의 자율성과 시스템의 확장성이다.
