# NFT 기술 원리와 ERC-721 스마트 컨트랙트 구현 — 장애 대응과 트러블슈팅

## 장애 대응과 트러블슈팅: 프로덕션에서 살아남기

---

## 개요

ERC-721 기반 NFT 컨트랙트를 배포하고 나면 진짜 싸움이 시작된다. 이론과 실습 환경에서는 문제없이 동작하던 코드가 메인넷에서는 전혀 다른 얼굴을 보인다. 가스 스파이크로 민팅이 실패하거나, 메타데이터가 사라지거나, 재진입 공격으로 이더가 빠져나가는 사태를 직접 겪어본 개발자라면 이 글이 더 와닿을 것이다.

이 글에서는 **프로덕션 NFT 서비스에서 실제로 발생하는 장애 유형과 트러블슈팅 방법론**을 구체적인 코드와 수치를 기반으로 다룬다. 기본 ERC-721 구현법은 이전 포스팅을 참고하고, 여기서는 "왜 죽었고, 어떻게 살렸는가"에 집중한다.

---

## 핵심 개념: NFT 장애의 세 가지 레이어

NFT 시스템의 장애는 크게 세 레이어에서 발생한다.

| 레이어 | 대표 장애 유형 | 복구 가능 여부 |
|--------|---------------|----------------|
| 컨트랙트 레이어 | 재진입 공격, overflow, 잘못된 접근제어 | 대부분 불가 (immutable) |
| 인프라 레이어 | 가스 추정 실패, nonce 충돌, RPC 노드 장애 | 가능 |
| 데이터 레이어 | IPFS 핀 유실, 중앙화 메타데이터 서버 다운 | 부분적으로 가능 |

블록체인의 불변성 때문에 **컨트랙트 레이어 장애는 사전 예방이 유일한 해결책**이다. 나머지 두 레이어는 적절한 모니터링과 복구 절차로 대응할 수 있다.

## 실전 예제

### 1. 재진입 공격 취약점과 방어 패턴

가장 고전적이지만 여전히 반복되는 실수다. 다음은 **취약한 코드**와 **수정된 코드**를 나란히 비교한다.

```solidity
// ❌ 취약한 코드: Check-Effects-Interactions 패턴 위반
contract VulnerableNFT is ERC721 {
    mapping(address => uint256) public pendingWithdrawals;

    function withdraw() external {
        uint256 amount = pendingWithdrawals[msg.sender];
        // 외부 호출이 상태 변경보다 먼저 발생
        (bool success, ) = msg.sender.call{value: amount}("");
        require(success, "Transfer failed");
        pendingWithdrawals[msg.sender] = 0; // 너무 늦음
    }
}

// ✅ 수정된 코드: CEI 패턴 + ReentrancyGuard 이중 적용
import "@openzeppelin/contracts/security/ReentrancyGuard.sol";

contract SecureNFT is ERC721, ReentrancyGuard {
    mapping(address => uint256) public pendingWithdrawals;

    function withdraw() external nonReentrant {
        uint256 amount = pendingWithdrawals[msg.sender];
        require(amount > 0, "Nothing to withdraw");
        
        // 1. Check
        // 2. Effects (상태 먼저 변경)
        pendingWithdrawals[msg.sender] = 0;
        
        // 3. Interactions (외부 호출은 마지막)
        (bool success, ) = msg.sender.call{value: amount}("");
        require(success, "Transfer failed");
        
        emit Withdrawn(msg.sender, amount);
    }
}
```

`nonReentrant` modifier 하나로 gas overhead는 약 **20,000 gas** 추가되지만, 이 비용이 아까워서 생략했다가 프로토콜 전체 TVL을 잃은 사례가 실제로 존재한다.

### 2. 가스 추정 실패와 민팅 트랜잭션 드롭

민팅 대기열이 쌓일 때 가장 흔한 장애다. 서버 사이드에서 트랜잭션을 제출하는 백엔드 코드 기준으로 살펴보자.

```java
// Spring Boot + Web3j 기반 민팅 서비스
@Service
@Slf4j
public class NFTMintingService {
    
    private final Web3j web3j;
    private final BigInteger BASE_GAS_LIMIT = BigInteger.valueOf(200_000L);
    private final BigDecimal GAS_BUFFER_MULTIPLIER = new BigDecimal("1.3"); // 30% 버퍼
    
    public TransactionReceipt mintWithRetry(String toAddress, String tokenURI, int maxRetries) {
        int attempt = 0;
        
        while (attempt < maxRetries) {
            try {
                // 동적 가스 추정 + 버퍼
                BigInteger estimatedGas = estimateGasWithBuffer(toAddress, tokenURI);
                BigInteger currentGasPrice = getEIP1559GasPrice();
                
                String txHash = submitMintTransaction(toAddress, tokenURI, estimatedGas, currentGasPrice);
                
                // 트랜잭션 컨펌 대기 (타임아웃 120초)
                TransactionReceipt receipt = waitForReceipt(txHash, 120);
                
                if (receipt.isStatusOK()) {
                    log.info("Mint successful. txHash={}, gasUsed={}", txHash, receipt.getGasUsed());
                    return receipt;
                }
                
            } catch (TransactionException e) {
                log.warn("Mint attempt {} failed: {}", attempt + 1, e.getMessage());
                
                // nonce 충돌 감지
                if (e.getMessage().contains("nonce too low")) {
                    syncNonce(); // nonce 재동기화
                }
                
                // 지수 백오프
                long backoffMs = (long) Math.pow(2, attempt) * 1000;
                Thread.sleep(Math.min(backoffMs, 30_000)); // 최대 30초
            }
            attempt++;
        }
        
        throw new MintingFailedException("Max retries exceeded for address: " + toAddress);
    }
    
    private BigInteger estimateGasWithBuffer(String toAddress, String tokenURI) throws Exception {
        // 실제 가스 추정
        BigInteger estimated = web3j.ethEstimateGas(
            Transaction.createFunctionCallTransaction(
                adminWallet.getAddress(), null, null, null,
                contractAddress, encodeMinFunction(toAddress, tokenURI)
            )
        ).send().getAmountUsed();
        
        // 추정값이 BASE_GAS_LIMIT보다 낮으면 BASE 사용 (추정 실패 방어)
        BigInteger safeEstimate = estimated.max(BASE_GAS_LIMIT);
        
        return new BigDecimal(safeEstimate)
            .multiply(GAS_BUFFER_MULTIPLIER)
            .toBigInteger();
    }
    
    private BigInteger getEIP1559GasPrice() throws Exception {
        EthFeeHistory feeHistory = web3j.ethFeeHistory(
            10, DefaultBlockParameterName.LATEST, Arrays.asList(25.0, 75.0)
        ).send();
        
        // 75th percentile 우선순위 fee 기반으로 maxPriorityFeePerGas 계산
        // 네트워크 혼잡도에 따른 동적 조정
        BigInteger baseFee = feeHistory.getFeeHistory().getBaseFeePerGas()
            .get(feeHistory.getFeeHistory().getBaseFeePerGas().size() - 1);
        
        return baseFee.multiply(BigInteger.TWO); // baseFee * 2 as maxFeePerGas
    }
}
```

실제 운영에서 `ethEstimateGas`는 **현재 블록 상태 기준**으로 추정하기 때문에, 혼잡한 네트워크에서는 추정값이 부정확할 수 있다. **30% 버퍼**는 최소한의 안전망이다.

### 3. IPFS 메타데이터 유실 대응

NFT 메타데이터가 IPFS에서 사라지는 현상은 생각보다 자주 발생한다. Pinata나 Infura의 핀 서비스가 중단되거나, 자체 IPFS 노드가 재시작되면서 핀이 해제되는 경우다.

```solidity
// 컨트랙트 레벨에서 메타데이터 다중화 전략
contract ResilientNFT is ERC721, Ownable {
    
    // 기본 IPFS URI (ipfs://Qm...)
    mapping(uint256 => string) private _primaryTokenURIs;
    // 백업 URI (Arweave 또는 자체 서버)
    mapping(uint256 => string) private _fallbackTokenURIs;
    
    bool public useArweaveFallback = false;
    
    function tokenURI(uint256 tokenId) public view override returns (string memory) {
        require(_exists(tokenId), "Token does not exist");
        
        if (useArweaveFallback) {
            string memory fallback = _fallbackTokenURIs[tokenId];
            if (bytes(fallback).length > 0) {
                return fallback;
            }
        }
        
        return _primaryTokenURIs[tokenId];
    }
    
    // 긴급 상황 시 fallback URI 일괄 설정 (onlyOwner)
    function setFallbackURIBatch(
        uint256[] calldata tokenIds,
        string[] calldata uris
    ) external onlyOwner {
        require(tokenIds.length == uris.length, "Length mismatch");
        for (uint256 i = 0; i < tokenIds.length; i++) {
            _fallbackTokenURIs[tokenIds[i]] = uris[i];
        }
        emit FallbackURIsUpdated(tokenIds.length);
    }
    
    // 긴급 스위치 (governance 또는 multisig 권장)
    function activateFallback(bool activate) external onlyOwner {
        useArweaveFallback = activate;
        emit FallbackActivated(activate);
    }
}
```

이 패턴의 핵심은 **컨트랙트 배포 시점에 미리 탈출구를 설계해두는 것**이다. 장애가 발생한 후에는 컨트랙트를 수정할 수 없다.

### 4. 이벤트 기반 장애 모니터링

온체인 이벤트를 실시간으로 감지하는 모니터링 시스템은 장애 대응의 첫 번째 방어선이다.

```java
@Component
@Slf4j
public class NFTEventMonitor {
    
    @PostConstruct
    public void startMonitoring() {
        // Transfer 이벤트 구독 (비정상 대량 전송 감지)
        nftContract.transferEventFlowable(DefaultBlockParameterName.LATEST, DefaultBlockParameterName.LATEST)
            .buffer(10, TimeUnit.SECONDS) // 10초 단위로 배치 처리
            .subscribe(events -> {
                if (events.size() > 50) { // 10초 내 50건 초과 = 이상 징후
                    alertService.sendCritical(
                        String.format("비정상 Transfer 급증 감지: %d건/10s", events.size())
                    );
                    // 자동 일시 중지 로직 (컨트랙트에 pause 기능이 있는 경우)
                    emergencyPause();
                }
                
                // 각 이벤트 DB 기록
                events.forEach(this::persistTransferEvent);
            }, error -> {
                log.error("이벤트 스트림 오류: {}", error.getMessage());
                // 자동 재연결
                reconnectWithBackoff();
            });
    }
    
    // 블록 reorg 감지
    public void detectReorg(long currentBlock) {
        long storedBlock = blockRepository.getLatestProcessedBlock();
        
        if (currentBlock < storedBlock - 6) { // 6블록 이상 차이 = reorg 의심
            log.warn("Chain reorg 감지! stored={}, current={}", storedBlock, currentBlock);
            // 영향받은 트랜잭션 재검증
            revalidateTransactionsFrom(currentBlock);
        }
    }
}
```

## 주의사항 및 트레이드오프

### Pausable 패턴의 양날의 검

`Pausable` 컨트랙트는 긴급 정지 기능을 제공하지만, 탈중앙화 철학과 충돌한다. 운영자가 언제든 NFT 전송을 막을 수 있다는 것은 **진정한 소유권을 해친다**는 비판을 받는다.

- **도입 시**: 명확한 거버넌스 정책과 multisig(최소 3/5) 구조 필수
- **대안**: 시간 제한 pause (예: 최대 72시간), DAO 투표 기반 pause

### 업그레이더블 컨트랙트의 위험

Proxy 패턴으로 업그레이더블 컨트랙트를 구현하면 장애 복구가 쉬워지지만, **스토리지 충돌(Storage Collision)** 이라는 새로운 장애를 유발할 수 있다.

```
Implementation V1 storage:
  slot 0: _owner
  slot 1: _tokenCounter

Implementation V2 storage (잘못된 업그레이드):
  slot 0: _paused     ← 충돌! _owner 값이 덮어써짐
  slot 1: _owner
  slot 2: _tokenCounter
```

**OpenZeppelin의 `@custom:storage-location` 패턴**과 스토리지 레이아웃 검증 도구(`hardhat-upgrades`)를 반드시 CI 파이프라인에 포함시켜야 한다.

### 가스비 vs 보안의 트레이드오프

| 전략 | 추가 가스 비용 | 보안 효과 |
|------|---------------|-----------|
| ReentrancyGuard | ~20,000 gas | 재진입 공격 방어 |
| Pausable | ~5,000 gas | 긴급 정지 |
| AccessControl | ~8,000 gas | 세밀한 권한 관리 |
| 이벤트 로깅 강화 | ~375 gas/topic | 감사 추적성 향상 |

## 정리

NFT 컨트랙트의 장애 대응은 **"예방 → 감지 → 대응 → 복구"** 사이클로 구조화해야 한다.

1. **예방**: CEI 패턴, ReentrancyGuard, 스토리지 충돌 검증을 CI에 통합
2. **감지**: 온체인 이벤트 실시간 구독 + 비정상 패턴 임계값 알림
3. **대응**: 미리 설계된 fallback URI, multisig 기반 긴급 pause
4. **복구**: 체인 reorg 감지 및 트랜잭션 재검증 자동화

가장 중요한 교훈은 **컨트랙트는 배포 후 수정 불가**라는 사실이다. 장애 대응 시나리오를 배포 전 설계에 반드시 녹여야 하며, 테스트넷에서 공격 시뮬레이션까지 수행한 후 메인넷에 올려야 한다. "나중에 고치면 되지"라는 생각은 블록체인 세계에서 통하지 않는다.
