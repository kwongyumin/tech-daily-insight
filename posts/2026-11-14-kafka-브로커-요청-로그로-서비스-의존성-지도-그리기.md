# Kafka 브로커 요청 로그로 서비스 의존성 지도 그리기

## 개요

마이크로서비스 환경이 성숙해질수록 서비스 간 의존성은 복잡해지고, 그 복잡성은 종종 문서화되지 않은 채로 운영 조직에 암묵적 지식으로만 남겨진다. "이 토픽을 누가 소비하고 있나요?"라는 질문에 즉시 답할 수 없다면, 여러분의 팀도 이 문제를 겪고 있는 것이다.

Kafka는 비동기 메시지 브로커로서 서비스 간 결합도를 낮추는 데 탁월하지만, 역설적으로 그 비동기성 때문에 의존성이 불투명해진다. HTTP API는 Swagger나 호출 스택으로 의존성을 추적할 수 있지만, Kafka 토픽을 통한 의존성은 코드 리뷰나 운영 중 장애 상황이 아니면 드러나지 않는 경우가 많다.

이 글에서는 **Kafka 브로커의 요청 로그(Request Log)**를 분석하여 서비스 의존성 지도를 시각화하는 실용적인 방법을 소개한다. 별도의 분산 추적 인프라 없이도, 이미 브로커가 기록하고 있는 로그에서 의미 있는 의존성 정보를 추출할 수 있다.

## 핵심 개념

### Kafka Request Log란?

Kafka 브로커는 `log4j` 기반의 요청 로그를 `kafka.request.logger` 라는 로거를 통해 출력한다. 이 로그는 브로커가 처리하는 모든 API 요청을 기록하며, 기본적으로 `TRACE` 레벨로 활성화된다.

```properties
# log4j.properties (Kafka 브로커 설정)
log4j.logger.kafka.request.logger=TRACE, requestAppender
log4j.additivity.kafka.request.logger=false
log4j.appender.requestAppender=org.apache.log4j.DailyRollingFileAppender
log4j.appender.requestAppender.DatePattern='.'yyyy-MM-dd-HH
log4j.appender.requestAppender.File=${kafka.logs.dir}/kafka-request.log
log4j.appender.requestAppender.layout=org.apache.log4j.PatternLayout
log4j.appender.requestAppender.layout.ConversionPattern=[%d] %p %m (%c)%n
```

요청 로그에는 다음 정보가 포함된다.

- **clientId**: 요청을 보낸 클라이언트의 식별자
- **API Key**: Produce(0), Fetch(1), ListOffsets(2), Metadata(3) 등
- **principal**: 인증된 사용자 정보 (SASL 사용 시)
- **correlationId**: 요청-응답 매핑용 ID
- **remoteAddress**: 클라이언트 IP

### 의존성 지도 구성 요소

서비스 의존성 지도를 구성하려면 세 가지 관계를 추출해야 한다.

| 관계 | Kafka API | 의미 |
|------|-----------|------|
| 서비스 → 토픽 | Produce (API Key 0) | 서비스가 토픽에 메시지를 발행 |
| 토픽 → 서비스 | Fetch (API Key 1) | 서비스가 토픽을 구독 |
| 서비스 → 토픽 | Metadata (API Key 3) | 서비스가 토픽 메타데이터를 조회 (존재 확인) |

## 실전 예제

### 1단계: 요청 로그 파싱

실제 요청 로그 한 줄의 예시는 다음과 같다.

```
[2024-01-15 10:23:45,123] TRACE Completed request:RequestHeader(apiKey=PRODUCE, apiVersion=9, correlationId=12345, clientId=order-service) -- {acks=-1,timeout=30000,partitionSizes=[order-events-0=1234]} from connection /10.0.1.5:52341; totalTime:5,requestQueueTime:1,localTime:3,remoteTime:0,throttleTime:0,responseQueueTime:1,sendTime:0,securityProtocol:PLAINTEXT,principal:User:ANONYMOUS,listener:PLAINTEXT,request:PRODUCE (kafka.request.logger)
```

이 로그에서 다음 정보를 추출할 수 있다.

- `clientId=order-service` → 발행자 서비스 식별
- `apiKey=PRODUCE` → 발행 행위
- `order-events-0` → 토픽명 (`order-events`)과 파티션(0)

Python으로 로그 파서를 작성해보자.

```python
import re
import json
from collections import defaultdict
from dataclasses import dataclass, field
from typing import Optional

@dataclass
class KafkaRequest:
    timestamp: str
    api_key: str
    client_id: str
    topics: list[str] = field(default_factory=list)
    principal: Optional[str] = None

class KafkaRequestLogParser:
    # 요청 헤더 파싱용 패턴
    HEADER_PATTERN = re.compile(
        r'RequestHeader\(apiKey=(\w+),.*?clientId=([^)]+)\)'
    )
    # Produce 요청에서 토픽-파티션 추출
    PRODUCE_TOPIC_PATTERN = re.compile(
        r'partitionSizes=\[([^\]]+)\]'
    )
    # Fetch 요청에서 토픽-파티션 추출
    FETCH_TOPIC_PATTERN = re.compile(
        r'fetchData=\{([^}]+)\}'
    )
    # principal 추출
    PRINCIPAL_PATTERN = re.compile(r'principal:([^,]+)')

    def parse_line(self, line: str) -> Optional[KafkaRequest]:
        if 'Completed request' not in line:
            return None

        header_match = self.HEADER_PATTERN.search(line)
        if not header_match:
            return None

        api_key = header_match.group(1)
        client_id = header_match.group(2).strip()

        # 타임스탬프 추출
        ts_match = re.match(r'\[(.+?)\]', line)
        timestamp = ts_match.group(1) if ts_match else ''

        # principal 추출
        principal_match = self.PRINCIPAL_PATTERN.search(line)
        principal = principal_match.group(1) if principal_match else None

        topics = []
        if api_key == 'PRODUCE':
            topic_match = self.PRODUCE_TOPIC_PATTERN.search(line)
            if topic_match:
                topics = self._extract_topics_from_partitions(topic_match.group(1))
        elif api_key == 'FETCH':
            fetch_match = self.FETCH_TOPIC_PATTERN.search(line)
            if fetch_match:
                topics = self._extract_topics_from_partitions(fetch_match.group(1))

        return KafkaRequest(
            timestamp=timestamp,
            api_key=api_key,
            client_id=client_id,
            topics=topics,
            principal=principal
        )

    def _extract_topics_from_partitions(self, partition_str: str) -> list[str]:
        """
        'order-events-0=1234, order-events-1=5678' 형태에서
        토픽명만 추출 (파티션 번호 제거)
        """
        topics = set()
        for entry in partition_str.split(','):
            entry = entry.strip()
            # 마지막 '-숫자' 패턴을 파티션으로 간주
            topic_match = re.match(r'^(.+)-\d+=', entry)
            if topic_match:
                topics.add(topic_match.group(1))
        return list(topics)
```

### 2단계: 의존성 그래프 구축

파싱된 요청들을 집계하여 의존성 그래프를 구축한다.

```python
class DependencyGraphBuilder:
    def __init__(self):
        # (producer_service, topic) → count
        self.produces: defaultdict[tuple, int] = defaultdict(int)
        # (topic, consumer_service) → count
        self.consumes: defaultdict[tuple, int] = defaultdict(int)
        # 서비스별 연결된 토픽 목록
        self.service_topics: defaultdict[str, set] = defaultdict(set)

    def process_request(self, req: KafkaRequest):
        if not req.topics:
            return

        for topic in req.topics:
            if req.api_key == 'PRODUCE':
                self.produces[(req.client_id, topic)] += 1
                self.service_topics[req.client_id].add(topic)
            elif req.api_key == 'FETCH':
                self.consumes[(topic, req.client_id)] += 1
                self.service_topics[req.client_id].add(topic)

    def build_graph(self) -> dict:
        nodes = set()
        edges = []

        for (service, topic), count in self.produces.items():
            nodes.add(('service', service))
            nodes.add(('topic', topic))
            edges.append({
                'from': service,
                'to': topic,
                'type': 'PRODUCE',
                'count': count
            })

        for (topic, service), count in self.consumes.items():
            nodes.add(('topic', topic))
            nodes.add(('service', service))
            edges.append({
                'from': topic,
                'to': service,
                'type': 'CONSUME',
                'count': count
            })

        return {
            'nodes': [{'id': n[1], 'type': n[0]} for n in nodes],
            'edges': edges
        }

    def export_mermaid(self) -> str:
        """Mermaid 다이어그램 형식으로 출력"""
        lines = ['graph LR']

        # 서비스 노드 스타일
        processed_services = set()
        for (service, _) in self.produces:
            if service not in processed_services:
                lines.append(f'    {self._safe_id(service)}["{service}"]:::service')
                processed_services.add(service)
        for (_, service) in self.consumes:
            if service not in processed_services:
                lines.append(f'    {self._safe_id(service)}["{service}"]:::service')
                processed_services.add(service)

        # Produce 엣지
        for (service, topic), count in self.produces.items():
            lines.append(
                f'    {self._safe_id(service)} -->|"produce\\n({count:,})"| {self._safe_id(topic)}[("{topic}")]'
            )

        # Consume 엣지
        for (topic, service), count in self.consumes.items():
            lines.append(
                f'    {self._safe_id(topic)}[("{topic}")] -->|"consume\\n({count:,})"| {self._safe_id(service)}'
            )

        lines.append('    classDef service fill:#4A90D9,color:#fff')
        return '\n'.join(lines)

    def _safe_id(self, name: str) -> str:
        return re.sub(r'[^a-zA-Z0-9]', '_', name)
```

### 3단계: 로그 파일 처리 및 출력

```python
def analyze_kafka_logs(log_file_path: str):
    parser = KafkaRequestLogParser()
    builder = DependencyGraphBuilder()

    with open(log_file_path, 'r') as f:
        for line in f:
            req = parser.parse_line(line)
            if req:
                builder.process_request(req)

    # JSON 그래프 출력
    graph = builder.build_graph()
    with open('dependency_graph.json', 'w') as f:
        json.dump(graph, f, indent=2, ensure_ascii=False)

    # Mermaid 다이어그램 출력
    mermaid_diagram = builder.export_mermaid()
    with open('dependency_graph.md', 'w') as f:
        f.write('```mermaid\n')
        f.write(mermaid_diagram)
        f.write('\n```\n')

    print(f"서비스 수: {len(set([e['from'] for e in graph['edges'] if '.' not in e['from']]))}")
    print(f"토픽 수: {len(set([n['id'] for n in graph['nodes'] if n['type'] == 'topic']))}")
    print(f"의존성 엣지 수: {len(graph['edges'])}")

if __name__ == '__main__':
    analyze_kafka_logs('/var/log/kafka/kafka-request.log')
```

### 4단계: 이상 의존성 탐지

단순 시각화를 넘어, 운영상 위험한 패턴도 탐지할 수 있다.

```python
def detect_anomalies(builder: DependencyGraphBuilder) -> list[dict]:
    anomalies = []

    # 1. 단일 토픽에 과도하게 많은 소비자가 붙은 경우
    topic_consumer_count = defaultdict(int)
    for (topic, service) in builder.consumes:
        topic_consumer_count[topic] += 1

    for topic, count in topic_consumer_count.items():
        if count > 10:  # 임계값은 조직마다 다름
            anomalies.append({
                'type': 'HIGH_FAN_OUT',
                'topic': topic,
                'consumer_count': count,
                'message': f'{topic} 토픽에 {count}개 서비스가 연결되어 있습니다. 토픽 분리를 고려하세요.'
            })

    # 2. 발행자 없이 소비만 하는 토픽 (데이터 소스 미확인)
    produced_topics = {topic for (_, topic) in builder.produces}
    consumed_topics = {topic for (topic, _) in builder.consumes}
    orphan_consumers = consumed_topics - produced_topics

    for topic in orphan_consumers:
        anomalies.append({
            'type': 'NO_PRODUCER',
            'topic': topic,
            'message': f'{topic} 토픽에 발행자가 감지되지 않았습니다. 외부 시스템이나 로그 누락을 확인하세요.'
        })

    # 3. 순환 의존성 탐지 (A→토픽→B→토픽→A)
    # 간단한 DFS 기반 사이클 탐지
    adjacency = defaultdict(set)
    for (service, topic) in builder.produces:
        adjacency[service].add(topic)
    for (topic, service) in builder.consumes:
        adjacency[topic].add(service)

    # 여기서는 개념만 표시, 실제 구현은 networkx 등 활용 권장
    anomalies.append({
        'type': 'INFO',
        'message': '순환 의존성 탐지를 위해 networkx 라이브러리 사용을 권장합니다.'
    })

    return anomalies
```

## 주의사항 및 트레이드오프

### clientId 명명 규칙 의존성 문제

이 접근법의 가장 큰 한계는 **clientId가 의미 있는 값으로 설정되어야 한다**는 점이다. Kafka 클라이언트는 `client.id` 설정을 통해 임의의 문자열을 사용할 수 있으며, 설정하지 않으면 `producer-1`, `consumer-2` 같은 의미 없는 값이 된다.

```yaml
# Spring Boot application.yml 설정 예시
spring:
  kafka:
    producer:
      client-id: ${spring.application.name}-producer
    consumer:
      client-id: ${spring.application.name}-consumer
```

조직 차원에서 `{서비스명}-{역할}-{인스턴스ID}` 같은 명명 컨벤션을 표준화하는 것이 선행되어야 한다.

### 로그 볼륨과 성능 영향

TRACE 레벨의 요청 로그는 트래픽이 많은 환경에서 **브로커 디스크 I/O에 상당한 부하**를 줄 수 있다. 운영 환경에서는 샘플링 전략이 필요하다.

- 특정 시간대(트래픽이 적은 새벽 시간)에만 로그를 활성화
- 로그 로테이션 주기를 짧게 설정 (예: 1시간 단위)
- Kafka 자체의 `--describe` 명령어와 Admin API를 함께 활용하여 로그 의존도 낮추기

### Admin API를 보완적으로 활용

요청 로그 분석과 함께 Kafka Admin API로 컨슈머 그룹 정보를 수집하면 더 정확한 지도를 그릴 수 있다.

```java
// Java AdminClient로 컨슈머 그룹 정보 수집
try (AdminClient adminClient = AdminClient.create(props)) {
    ListConsumerGroupsResult groups = adminClient.listConsumerGroups();
    Collection<ConsumerGroupListing> listings = groups.all().get();

    for (ConsumerGroupListing listing : listings) {
        DescribeConsumerGroupsResult desc = adminClient.describeConsumerGroups(
            Collections.singletonList(listing.groupId())
        );
        // 그룹 ID, 멤버, 구독 토픽 정보 추출
    }
}
```

### 스냅샷이지 실시간이 아님

로그 파일 기반 분석은 **특정 시점의 스냅샷**이다. 카나리 배포 중이거나 A/B 테스트 중인 서비스는 간헐적으로 나타났다 사라질 수 있다. 이를 해결하려면 로그 수집을 주기적으로 자동화(예: 매일 새벽 cron)하고 시계열 형태로 의존성 변화를 추적해야 한다.

## 정리

Kafka 브로커 요청 로그는 별도의 분산 추적 인프라를 도입하지 않고도 서비스 의존성 지도를 그릴 수 있는 현실적인 출발점이다. 특히 의존성 문서화가 미흡한 레거시 환경이나 급격히 성장한 마이크로서비스 환경에서 "현재 무엇이 무엇에 의존하는가"를 빠르게 파악하는 데 효과적이다.

핵심은 세 가지다.

1. **clientId 명명 컨벤션 표준화**: 분석의 정확도는 여기서 결정된다
2. **요청 로그 + Admin API 조합**: 로그만으로는 놓치는 정보를 Admin API로 보완한다
3. **정기적인 자동화**: 한 번의 스냅샷보다 시계열 추적이 훨씬 가치 있다

의존성 지도는 그 자체가 목적이 아니라, **장애 영향 범위 분석**, **토픽 오너십 정의**, **서비스 분리/통합 의사결정**의 도구다. 이 그래프를 팀의 위키나 CI 파이프라인에 연동하여 아키텍처 변화를 지속적으로 추적하는 것을 권장한다.
