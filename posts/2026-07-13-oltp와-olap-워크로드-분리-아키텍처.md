# OLTP와 OLAP 워크로드 분리 아키텍처

## 개요

서비스 규모가 커지면서 많은 팀이 공통적으로 마주치는 문제가 있다. 운영 데이터베이스에서 분석 쿼리를 실행하면 서비스 응답 속도가 급격히 떨어지는 현상이다. 마케팅팀이 요청한 "지난 3개월간 유저 코호트별 구매 패턴 분석" 쿼리 하나가 결제 API 레이턴시를 5배로 뛰게 만드는 상황, 낯설지 않을 것이다.

이 문제의 근본 원인은 **OLTP(Online Transaction Processing)**와 **OLAP(Online Analytical Processing)** 워크로드의 특성 차이를 무시하고 단일 데이터베이스에 모든 부하를 몰아넣는 아키텍처에 있다. 이 글에서는 두 워크로드의 차이를 명확히 이해하고, 실무에서 적용 가능한 분리 아키텍처 패턴을 살펴본다.

---

## 핵심 개념

### OLTP vs OLAP 특성 비교

| 구분 | OLTP | OLAP |
|------|------|------|
| 목적 | 트랜잭션 처리 | 데이터 분석 |
| 쿼리 패턴 | 단순 CRUD, 인덱스 활용 | 복잡한 집계, 풀스캔 |
| 데이터 범위 | 소량의 최신 데이터 | 대량의 히스토리 데이터 |
| 응답 시간 | 밀리초 단위 | 초~분 단위 허용 |
| 동시 사용자 | 수천~수만 명 | 수십~수백 명 |
| 스키마 | 정규화 (3NF) | 비정규화 (Star/Snowflake Schema) |
| 대표 DB | MySQL, PostgreSQL, Oracle | Redshift, BigQuery, ClickHouse |

OLTP는 짧고 빈번한 트랜잭션에 최적화되어 있다. 행 단위로 데이터를 처리하며, 인덱스를 최대한 활용한다. 반면 OLAP는 수백만~수억 건의 레코드를 집계하는 데 최적화되어 있으며, 컬럼 기반 스토리지(Columnar Storage)를 사용해 특정 컬럼만 읽는 작업에서 압도적인 성능을 낸다.

### 왜 분리해야 하는가?

**리소스 경합(Resource Contention)** 이 핵심이다. OLAP 쿼리는 일반적으로 CPU와 I/O를 오랫동안 점유한다. OLTP 트랜잭션과 같은 I/O 버퍼를 공유하면 버퍼 캐시 히트율이 떨어지고, 락 경합이 발생하며, 전체 서비스 품질이 저하된다.

## 실전 예제

### 아키텍처 패턴 1: CDC 기반 실시간 데이터 파이프라인

가장 널리 사용되는 패턴은 **CDC(Change Data Capture)**를 활용해 OLTP DB의 변경 사항을 실시간으로 OLAP 저장소에 복제하는 방식이다.

```
[Application] → [MySQL (OLTP)] → [Debezium] → [Kafka] → [ClickHouse/Redshift (OLAP)]
```

**Debezium + Kafka Connect 설정 예시**

```json
{
  "name": "mysql-source-connector",
  "config": {
    "connector.class": "io.debezium.connector.mysql.MySqlConnector",
    "database.hostname": "mysql-oltp.internal",
    "database.port": "3306",
    "database.user": "debezium",
    "database.password": "${DB_PASSWORD}",
    "database.server.id": "1",
    "database.server.name": "oltp-db",
    "database.include.list": "ecommerce",
    "table.include.list": "ecommerce.orders,ecommerce.order_items",
    "database.history.kafka.bootstrap.servers": "kafka:9092",
    "database.history.kafka.topic": "schema-changes.ecommerce",
    "transforms": "unwrap",
    "transforms.unwrap.type": "io.debezium.transforms.ExtractNewRecordState",
    "transforms.unwrap.drop.tombstones": "false",
    "transforms.unwrap.delete.handling.mode": "rewrite"
  }
}
```

**Spring Kafka Consumer로 OLAP에 적재하는 예시**

```java
@Service
@RequiredArgsConstructor
@Slf4j
public class OrderEventConsumer {

    private final ClickHouseOrderRepository clickHouseRepository;
    private final ObjectMapper objectMapper;

    @KafkaListener(
        topics = "oltp-db.ecommerce.orders",
        groupId = "olap-sync-group",
        containerFactory = "kafkaListenerContainerFactory"
    )
    public void consume(
        @Payload String message,
        @Header(KafkaHeaders.RECEIVED_TOPIC) String topic,
        Acknowledgment acknowledgment
    ) {
        try {
            OrderEvent event = objectMapper.readValue(message, OrderEvent.class);

            // DELETE 이벤트 처리 (soft delete로 마킹)
            if ("d".equals(event.getOp())) {
                clickHouseRepository.markAsDeleted(event.getBefore().getId());
            } else {
                // INSERT/UPDATE 모두 upsert로 처리
                clickHouseRepository.upsert(toAnalyticsOrder(event.getAfter()));
            }

            acknowledgment.acknowledge();
        } catch (Exception e) {
            log.error("Failed to process order event: {}", message, e);
            // DLQ로 전송하거나 재시도 로직 적용
            throw new RuntimeException(e);
        }
    }

    private AnalyticsOrder toAnalyticsOrder(OrderPayload payload) {
        return AnalyticsOrder.builder()
            .orderId(payload.getId())
            .userId(payload.getUserId())
            .totalAmount(payload.getTotalAmount())
            .status(payload.getStatus())
            .createdAt(Instant.ofEpochMilli(payload.getCreatedAt()))
            .build();
    }
}
```

### 아키텍처 패턴 2: Read Replica + 쿼리 라우팅

분석 요구사항이 복잡하지 않다면, MySQL/PostgreSQL의 **Read Replica**를 분석 전용으로 운영하는 방법이 빠른 대안이 될 수 있다.

```java
@Configuration
public class DataSourceConfig {

    @Bean
    @ConfigurationProperties("spring.datasource.oltp")
    public DataSource oltpDataSource() {
        return DataSourceBuilder.create().build();
    }

    @Bean
    @ConfigurationProperties("spring.datasource.olap")
    public DataSource olapDataSource() {
        return DataSourceBuilder.create().build();
    }

    @Bean
    @Primary
    public DataSource routingDataSource(
        @Qualifier("oltpDataSource") DataSource oltp,
        @Qualifier("olapDataSource") DataSource olap
    ) {
        Map<Object, Object> dataSources = new HashMap<>();
        dataSources.put(DataSourceType.OLTP, oltp);
        dataSources.put(DataSourceType.OLAP, olap);

        RoutingDataSource routingDataSource = new RoutingDataSource();
        routingDataSource.setTargetDataSources(dataSources);
        routingDataSource.setDefaultTargetDataSource(oltp);
        return routingDataSource;
    }
}

public class RoutingDataSource extends AbstractRoutingDataSource {

    @Override
    protected Object determineCurrentLookupKey() {
        return DataSourceContextHolder.getDataSourceType();
    }
}

// 분석 쿼리용 애너테이션
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface OlapQuery {}

// AOP로 자동 라우팅
@Aspect
@Component
public class DataSourceRoutingAspect {

    @Around("@annotation(OlapQuery)")
    public Object routeToOlap(ProceedingJoinPoint joinPoint) throws Throwable {
        try {
            DataSourceContextHolder.setDataSourceType(DataSourceType.OLAP);
            return joinPoint.proceed();
        } finally {
            DataSourceContextHolder.clearDataSourceType();
        }
    }
}

// 사용 예시
@Service
public class SalesAnalyticsService {

    @OlapQuery
    @Transactional(readOnly = true)
    public List<MonthlySalesDto> getMonthlySalesByCategory(YearMonth from, YearMonth to) {
        return salesRepository.aggregateSalesByCategory(from, to);
    }
}
```

### ClickHouse 분석 쿼리 예시

OLAP 저장소로 ClickHouse를 사용할 경우, 컬럼 기반 스토리지의 특성을 활용한 쿼리가 MySQL 대비 10~100배 이상 빠르게 동작한다.

```sql
-- ClickHouse: 월별 카테고리별 매출 분석
SELECT
    toYYYYMM(created_at)          AS year_month,
    category_name,
    count()                        AS order_count,
    sum(total_amount)              AS total_revenue,
    avg(total_amount)              AS avg_order_value,
    uniqExact(user_id)             AS unique_buyers
FROM orders_analytics
WHERE
    created_at BETWEEN '2024-01-01' AND '2024-12-31'
    AND status = 'COMPLETED'
GROUP BY year_month, category_name
ORDER BY year_month, total_revenue DESC
SETTINGS max_threads = 8;
```

## 주의사항 및 트레이드오프

### 1. 데이터 일관성과 지연(Lag) 허용 범위 설정

CDC 기반 파이프라인은 근본적으로 **최종 일관성(Eventual Consistency)** 모델이다. 복제 지연이 발생할 수 있으므로, OLAP 데이터를 기반으로 실시간 의사결정을 내리는 로직이 있다면 반드시 지연 허용 범위를 명시적으로 정의해야 한다.

```yaml
# 모니터링 지표 예시
olap:
  lag:
    warning-threshold-seconds: 30   # 30초 이상 지연 시 경고
    critical-threshold-seconds: 300 # 5분 이상 지연 시 알람
```

### 2. 스키마 변경(Schema Evolution) 관리

OLTP 스키마가 변경되면 CDC 파이프라인과 OLAP 스키마도 함께 관리해야 한다. Avro + Schema Registry를 도입해 스키마 버전을 체계적으로 관리하거나, ClickHouse의 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 같은 안전한 DDL을 활용한다.

```sql
-- ClickHouse 무중단 컬럼 추가
ALTER TABLE orders_analytics
    ADD COLUMN IF NOT EXISTS coupon_code Nullable(String) AFTER total_amount,
    ADD COLUMN IF NOT EXISTS discount_amount Decimal(18, 2) DEFAULT 0;
```

### 3. 비용과 운영 복잡도

| 패턴 | 초기 구축 비용 | 운영 복잡도 | 실시간성 | 권장 상황 |
|------|--------------|------------|---------|---------|
| Read Replica | 낮음 | 낮음 | 높음 (초 단위) | 분석 쿼리가 단순, 소규모 팀 |
| CDC + Kafka | 높음 | 높음 | 중간 (초~분) | 분석 요구사항 복잡, 전담 DE팀 존재 |
| 배치 ETL | 낮음 | 중간 | 낮음 (일 단위) | 실시간성 불필요, 비용 최우선 |

### 4. OLTP 성능에 미치는 영향

Debezium 같은 CDC 도구는 MySQL의 binlog를 읽는 방식으로 동작하므로 OLTP DB에 직접적인 부하를 거의 주지 않는다. 그러나 binlog 보존 기간 설정을 놓치면 디스크 공간 문제로 이어질 수 있다.

```sql
-- MySQL binlog 보존 기간 설정 (최소 CDC lag + 버퍼)
SET GLOBAL binlog_expire_logs_seconds = 604800; -- 7일
```

### 5. 멱등성(Idempotency) 보장

네트워크 장애나 Consumer 재시작 시 동일 이벤트가 중복 처리될 수 있다. OLAP 저장소에 데이터를 적재할 때는 반드시 upsert(INSERT OR REPLACE) 방식을 사용해야 한다.

```sql
-- ClickHouse ReplacingMergeTree 엔진 사용으로 중복 처리
CREATE TABLE orders_analytics (
    order_id     UInt64,
    user_id      UInt64,
    total_amount Decimal(18, 2),
    status       String,
    created_at   DateTime,
    updated_at   DateTime,
    is_deleted   UInt8 DEFAULT 0
) ENGINE = ReplacingMergeTree(updated_at)
PARTITION BY toYYYYMM(created_at)
ORDER BY (order_id);
```

## 정리

OLTP와 OLAP 워크로드 분리는 선택이 아닌 서비스 성장 단계에서 반드시 마주치게 되는 과제다. 핵심을 정리하면 다음과 같다.

1. **Read Replica부터 시작하라.** 복잡한 파이프라인을 처음부터 구축하기보다, Read Replica에 `@OlapQuery` 라우팅 패턴을 먼저 적용하고 한계를 확인한다.

2. **CDC는 강력하지만 운영 비용이 따른다.** Debezium + Kafka 조합은 실시간성과 확장성이 뛰어나지만, 스키마 변경 관리와 모니터링 체계가 선행되어야 한다.

3. **지연 허용 범위를 비즈니스와 합의하라.** OLAP 데이터는 항상 약간 과거의 데이터임을 비즈니스 이해관계자와 명확히 공유하고, SLA를 수치로 정의해 두어야 한다.

4. **멱등성과 스키마 진화 전략을 처음부터 설계하라.** 나중에 추가하면 이미 쌓인 데이터의 정합성을 보장하기 어렵다.

데이터 팀과 백엔드 팀이 함께 파이프라인을 설계하는 문화를 만드는 것이 기술적 선택만큼 중요하다. 아키텍처는 결국 사람과 프로세스 위에 동작한다.
