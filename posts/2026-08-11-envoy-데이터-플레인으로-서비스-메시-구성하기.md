# Envoy 데이터 플레인으로 서비스 메시 구성하기

## 개요

마이크로서비스 아키텍처가 확산되면서 서비스 간 통신 관리의 복잡성은 기하급수적으로 증가했다. 수십, 수백 개의 서비스가 서로 통신하는 환경에서 재시도 로직, 서킷 브레이커, TLS 인증, 분산 트레이싱 같은 기능을 각 애플리케이션 코드에 직접 구현하는 것은 명백한 한계가 있다.

**서비스 메시(Service Mesh)** 는 이러한 문제를 인프라 레이어에서 해결하는 패턴이다. 그 중심에는 **Envoy Proxy** 가 있다. Envoy는 Lyft가 개발하고 CNCF(Cloud Native Computing Foundation)에 기증한 고성능 L7 프록시로, Istio, Linkerd v2(일부), AWS App Mesh 등 대부분의 서비스 메시 구현체의 데이터 플레인으로 활용된다.

이 포스팅에서는 Envoy를 데이터 플레인으로 활용해 서비스 메시를 직접 구성하는 방법을 실전 예제와 함께 다룬다. Istio처럼 완성된 솔루션을 사용하는 것도 좋지만, Envoy의 동작 원리를 직접 이해하면 트러블슈팅 능력과 아키텍처 설계 역량이 비약적으로 향상된다.

## 핵심 개념

### 데이터 플레인 vs 컨트롤 플레인

서비스 메시는 두 계층으로 나뉜다.

- **데이터 플레인**: 실제 네트워크 트래픽을 처리하는 프록시 집합. Envoy가 여기에 해당한다. 사이드카 패턴으로 각 서비스 Pod에 주입되어 인바운드/아웃바운드 트래픽을 모두 가로챈다.
- **컨트롤 플레인**: 데이터 플레인의 프록시들을 동적으로 관리하는 중앙 제어 컴포넌트. Istio의 istiod, Consul Connect 등이 이 역할을 한다.

Envoy는 컨트롤 플레인으로부터 **xDS(Discovery Service) API** 를 통해 설정을 동적으로 수신한다. xDS는 LDS(Listener), RDS(Route), CDS(Cluster), EDS(Endpoint) 등의 Discovery Service를 통칭하는 개념이다.

### Envoy의 핵심 구성 요소

```
[Downstream Client] → Listener → Filter Chain → Router → Cluster → [Upstream Service]
```

| 구성 요소 | 역할 |
|---|---|
| **Listener** | 특정 포트를 바인딩하고 연결을 수락 |
| **Filter Chain** | HTTP 코덱, 인증, 트레이싱 등 다양한 필터 적용 |
| **Router** | 요청을 특정 클러스터로 라우팅 |
| **Cluster** | 업스트림 서비스의 논리적 그룹 |
| **Endpoint** | 클러스터 내 실제 호스트:포트 |

## 실전 예제

### 환경 구성

Docker Compose로 간단한 서비스 메시 환경을 구성한다. `service-a`가 `service-b`를 호출할 때 Envoy 사이드카를 통해 트래픽이 흐르도록 설정한다.

```yaml
# docker-compose.yml
version: "3.8"

services:
  service-a:
    image: curlimages/curl:latest
    command: ["sleep", "infinity"]
    network_mode: "service:envoy-a"
    depends_on:
      - envoy-a

  envoy-a:
    image: envoyproxy/envoy:v1.29-latest
    volumes:
      - ./envoy-a.yaml:/etc/envoy/envoy.yaml
    ports:
      - "9901:9901"  # Admin 포트
    networks:
      - mesh-network

  service-b:
    image: kennethreitz/httpbin
    network_mode: "service:envoy-b"
    depends_on:
      - envoy-b

  envoy-b:
    image: envoyproxy/envoy:v1.29-latest
    volumes:
      - ./envoy-b.yaml:/etc/envoy/envoy.yaml
    ports:
      - "9902:9901"  # Admin 포트
    networks:
      - mesh-network

networks:
  mesh-network:
    driver: bridge
```

### 아웃바운드 프록시 설정 (envoy-a.yaml)

`service-a`의 사이드카로 동작하는 Envoy 설정이다. 아웃바운드 요청을 `service-b`의 Envoy 사이드카로 전달하며, 재시도 정책과 서킷 브레이커를 함께 설정한다.

```yaml
# envoy-a.yaml
static_resources:
  listeners:
    - name: outbound_listener
      address:
        socket_address:
          address: 0.0.0.0
          port_value: 8080
      filter_chains:
        - filters:
            - name: envoy.filters.network.http_connection_manager
              typed_config:
                "@type": type.googleapis.com/envoy.extensions.filters.network.http_connection_manager.v3.HttpConnectionManager
                stat_prefix: ingress_http
                access_log:
                  - name: envoy.access_loggers.stdout
                    typed_config:
                      "@type": type.googleapis.com/envoy.extensions.access_loggers.stream.v3.StdoutAccessLog
                http_filters:
                  - name: envoy.filters.http.router
                    typed_config:
                      "@type": type.googleapis.com/envoy.extensions.filters.http.router.v3.Router
                route_config:
                  name: local_route
                  virtual_hosts:
                    - name: service_b
                      domains: ["service-b", "service-b:8080"]
                      routes:
                        - match:
                            prefix: "/"
                          route:
                            cluster: service_b_cluster
                            timeout: 10s
                            retry_policy:
                              retry_on: "5xx,gateway-error,connect-failure"
                              num_retries: 3
                              per_try_timeout: 3s

  clusters:
    - name: service_b_cluster
      connect_timeout: 5s
      type: STRICT_DNS
      lb_policy: ROUND_ROBIN
      circuit_breakers:
        thresholds:
          - priority: DEFAULT
            max_connections: 100
            max_pending_requests: 100
            max_requests: 1000
            max_retries: 3
      load_assignment:
        cluster_name: service_b_cluster
        endpoints:
          - lb_endpoints:
              - endpoint:
                  address:
                    socket_address:
                      address: envoy-b  # service-b의 사이드카 Envoy
                      port_value: 8080

admin:
  address:
    socket_address:
      address: 0.0.0.0
      port_value: 9901
```

### 인바운드 프록시 설정 (envoy-b.yaml)

`service-b`의 사이드카로 동작하며, 인바운드 트래픽을 실제 서비스로 전달한다. 여기에 Rate Limiting 필터와 요청 헤더 조작을 추가한다.

```yaml
# envoy-b.yaml
static_resources:
  listeners:
    - name: inbound_listener
      address:
        socket_address:
          address: 0.0.0.0
          port_value: 8080
      filter_chains:
        - filters:
            - name: envoy.filters.network.http_connection_manager
              typed_config:
                "@type": type.googleapis.com/envoy.extensions.filters.network.http_connection_manager.v3.HttpConnectionManager
                stat_prefix: ingress_http
                generate_request_id: true
                tracing:
                  provider:
                    name: envoy.tracers.zipkin
                    typed_config:
                      "@type": type.googleapis.com/envoy.config.trace.v3.ZipkinConfig
                      collector_cluster: zipkin
                      collector_endpoint: "/api/v2/spans"
                      collector_endpoint_version: HTTP_JSON
                access_log:
                  - name: envoy.access_loggers.stdout
                    typed_config:
                      "@type": type.googleapis.com/envoy.extensions.access_loggers.stream.v3.StdoutAccessLog
                      log_format:
                        json_format:
                          timestamp: "%START_TIME%"
                          method: "%REQ(:METHOD)%"
                          path: "%REQ(X-ENVOY-ORIGINAL-PATH?:PATH)%"
                          response_code: "%RESPONSE_CODE%"
                          duration: "%DURATION%"
                          upstream_host: "%UPSTREAM_HOST%"
                http_filters:
                  - name: envoy.filters.http.router
                    typed_config:
                      "@type": type.googleapis.com/envoy.extensions.filters.http.router.v3.Router
                route_config:
                  name: local_route
                  virtual_hosts:
                    - name: local_service
                      domains: ["*"]
                      request_headers_to_add:
                        - header:
                            key: "x-forwarded-by"
                            value: "envoy-sidecar"
                          append: false
                      routes:
                        - match:
                            prefix: "/"
                          route:
                            cluster: local_service

  clusters:
    - name: local_service
      connect_timeout: 1s
      type: STATIC
      load_assignment:
        cluster_name: local_service
        endpoints:
          - lb_endpoints:
              - endpoint:
                  address:
                    socket_address:
                      address: 127.0.0.1  # 동일 Pod의 실제 서비스
                      port_value: 80

    - name: zipkin
      connect_timeout: 1s
      type: STRICT_DNS
      load_assignment:
        cluster_name: zipkin
        endpoints:
          - lb_endpoints:
              - endpoint:
                  address:
                    socket_address:
                      address: zipkin
                      port_value: 9411

admin:
  address:
    socket_address:
      address: 0.0.0.0
      port_value: 9901
```

### Admin API로 실시간 상태 확인

Envoy의 Admin API는 운영 시 매우 강력한 도구다.

```bash
# 클러스터 상태 및 통계 확인
curl http://localhost:9901/clusters

# 현재 적용된 설정 전체 덤프
curl http://localhost:9901/config_dump | jq '.configs[] | select(.["@type"] | contains("Clusters"))'

# 라이브 트래픽 통계 (5xx 에러율, 재시도 횟수 등)
curl http://localhost:9901/stats | grep "upstream_rq_5xx\|retry\|circuit_breakers"

# 서킷 브레이커 상태 확인
curl http://localhost:9901/stats | grep "overflow"

# 핫 리로드 없이 설정 적용 (xDS 연동 시)
curl -X POST http://localhost:9901/quitquitquit
```

### 헬스체크 및 Outlier Detection 설정

```yaml
# cluster 설정에 추가
clusters:
  - name: service_b_cluster
    # ... 기존 설정 ...
    health_checks:
      - timeout: 2s
        interval: 10s
        unhealthy_threshold: 3
        healthy_threshold: 2
        http_health_check:
          path: "/health"
    outlier_detection:
      # 5xx 에러 발생 시 자동으로 엔드포인트를 풀에서 제거
      consecutive_5xx: 5
      interval: 10s
      base_ejection_time: 30s
      max_ejection_percent: 50
      success_rate_minimum_hosts: 5
      success_rate_request_volume: 100
      success_rate_stdev_factor: 1900
```

## 주의사항 및 트레이드오프

### 1. 성능 오버헤드

Envoy 사이드카는 모든 요청에 추가적인 홉(hop)을 추가한다. 일반적으로 레이턴시 오버헤드는 **1~5ms** 수준이지만, 초고성능이 요구되는 금융 트랜잭션이나 실시간 게임 서버에서는 무시할 수 없는 수치다.

**완화 방법**: HTTP/2와 멀티플렉싱 활용, Keep-Alive 커넥션 풀 최적화, `http2_protocol_options` 설정을 통해 업스트림 연결을 HTTP/2로 업그레이드하는 것을 고려한다.

### 2. 설정 복잡성

정적 설정(static_resources)은 서비스 수가 늘어날수록 관리가 극히 어려워진다. **실무에서는 반드시 xDS 컨트롤 플레인을 도입**해야 한다. 자체 구현보다는 Istio, Consul, 또는 go-control-plane을 활용한 경량 컨트롤 플레인을 검토하라.

### 3. 디버깅 난이도

트래픽이 애플리케이션을 거치지 않고 프록시 레이어에서 처리되므로, 문제 발생 시 디버깅 포인트가 늘어난다. 반드시 **구조화된 액세스 로그**와 **분산 트레이싱**을 함께 구성하고, Envoy의 로그 레벨을 동적으로 조절할 수 있도록 Admin API를 활용하라.

```bash
# 특정 컴포넌트의 로그 레벨 동적 변경
curl -X POST "http://localhost:9901/logging?http=debug"
curl -X POST "http://localhost:9901/logging?router=trace"
```

### 4. mTLS 도입 시 인증서 관리

mTLS를 활성화하면 보안이 대폭 강화되지만, 인증서 갱신과 배포 자동화가 필수다. 수동으로 관리하면 인증서 만료로 인한 장애가 발생한다. **SPIFFE/SPIRE** 를 활용한 워크로드 아이덴티티 관리를 적극 검토하라.

### 5. 리소스 소비

각 Pod마다 Envoy 사이드카가 주입되므로 CPU와 메모리 오버헤드가 발생한다. 기본적으로 Pod당 약 **50~200MB 메모리**를 추가로 소비한다. 수백 개 서비스가 운영되는 환경에서는 무시할 수 없는 비용이다. Kubernetes의 Resource Request/Limit을 명확히 설정하고 모니터링하라.

## 정리

Envoy를 데이터 플레인으로 서비스 메시를 구성하면 다음과 같은 이점을 얻을 수 있다.

| 기능 | 애플리케이션 코드 | Envoy 사이드카 |
|---|---|---|
| 재시도/타임아웃 | 각 서비스마다 구현 | 설정으로 일괄 적용 |
| 서킷 브레이커 | 라이브러리 의존 | 네이티브 지원 |
| mTLS | 복잡한 인증서 처리 | 투명하게 처리 |
| 분산 트레이싱 | 코드 수정 필요 | 자동 헤더 전파 |
| 트래픽 관리 | 배포 없이 불가 | 동적 설정 변경 |

Envoy는 단순한 프록시가 아닌, 서비스 메시의 핵심 인프라 컴포넌트다. 정적 설정으로 시작해 Envoy의 동작 원리를 체득한 뒤, xDS 기반의 동적 컨트롤 플레인으로 발전시키는 단계적 접근을 권장한다.

실무에서는 Istio나 Consul 같은 완성된 솔루션을 사용하더라도, 오늘 다룬 Envoy의 내부 구조와 설정 방식을 이해하고 있다면 장애 대응 속도와 아키텍처 의사결정의 질이 분명히 달라질 것이다.
