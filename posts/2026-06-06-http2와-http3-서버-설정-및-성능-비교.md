# HTTP/2와 HTTP/3 서버 설정 및 성능 비교

## 개요

웹 서비스의 성능은 단순히 애플리케이션 코드 최적화만으로는 한계가 있습니다. 네트워크 프로토콜 레벨에서의 선택이 전체 응답 시간과 처리량에 결정적인 영향을 미칩니다. HTTP/1.1이 표준으로 자리 잡은 지 20년이 지났고, 이미 HTTP/2는 대부분의 현대 서비스에서 기본값이 되었습니다. 그리고 HTTP/3는 QUIC 프로토콜 기반으로 모바일 환경과 패킷 손실이 잦은 네트워크에서 혁신적인 성능 개선을 약속합니다.

이 글에서는 Nginx와 Spring Boot 환경을 중심으로 HTTP/2, HTTP/3 설정 방법을 실전 예제와 함께 살펴보고, 각 프로토콜의 트레이드오프를 분석합니다.

---

## 핵심 개념

### HTTP/2의 핵심 기능

HTTP/2는 HTTP/1.1의 구조적 한계를 극복하기 위해 설계되었습니다.

- **멀티플렉싱 (Multiplexing)**: 단일 TCP 연결에서 여러 요청/응답 스트림을 동시에 처리합니다. HTTP/1.1의 HOL(Head-of-Line) 블로킹 문제를 애플리케이션 레이어에서 해결합니다.
- **헤더 압축 (HPACK)**: 반복되는 HTTP 헤더를 허프만 인코딩과 인덱스 테이블로 압축합니다.
- **서버 푸시 (Server Push)**: 클라이언트 요청 전에 서버가 리소스를 선제적으로 전송할 수 있습니다.
- **스트림 우선순위**: 클라이언트가 스트림의 우선순위를 지정할 수 있습니다.

### HTTP/3와 QUIC

HTTP/3는 TCP가 아닌 **QUIC(Quick UDP Internet Connections)** 위에서 동작합니다. 이 차이가 핵심입니다.

- **0-RTT / 1-RTT 핸드셰이크**: TCP+TLS의 3-way handshake 비용을 대폭 줄입니다. 재연결 시 0-RTT로 즉시 데이터 전송이 가능합니다.
- **연결 레벨 HOL 블로킹 제거**: HTTP/2는 TCP 레이어에서 패킷 손실 시 전체 스트림이 대기하는 문제가 있었습니다. QUIC는 UDP 기반으로 각 스트림을 독립적으로 처리합니다.
- **연결 마이그레이션**: IP 주소 변경(예: Wi-Fi → LTE 전환)에도 Connection ID 기반으로 연결을 유지합니다.

```
HTTP/1.1: TCP → HTTP
HTTP/2:   TCP → TLS → HTTP/2
HTTP/3:   UDP → QUIC(TLS 1.3 내장) → HTTP/3
```

## 실전 예제

### 1. Nginx HTTP/2 설정

대부분의 Linux 환경에서 Nginx 1.9.5+ 버전이면 HTTP/2를 지원합니다.

```nginx
# /etc/nginx/sites-available/myapp.conf

server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name example.com;

    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    # TLS 1.2/1.3만 허용 (HTTP/2 권고사항)
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384;
    ssl_prefer_server_ciphers off;

    # HSTS 설정
    add_header Strict-Transport-Security "max-age=63072000" always;

    # HTTP/2 서버 푸시 예시
    location = /index.html {
        http2_push /static/main.css;
        http2_push /static/app.js;
        proxy_pass http://upstream_backend;
    }

    location / {
        proxy_pass http://upstream_backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;

        # HTTP/2 업스트림 연결 (gRPC 등)
        # proxy_http_version 2;  # 업스트림이 HTTP/2 지원 시
    }
}

server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}
```

### 2. Nginx HTTP/3 (QUIC) 설정

HTTP/3 지원은 Nginx 1.25.0+ (mainline) 또는 nginx-quic 브랜치가 필요합니다. OpenSSL 대신 BoringSSL 또는 quictls를 사용해야 합니다.

```nginx
# /etc/nginx/nginx.conf 또는 site 설정

server {
    # HTTP/2 (TCP)
    listen 443 ssl http2;

    # HTTP/3 (QUIC/UDP)
    listen 443 quic reuseport;

    server_name example.com;

    ssl_certificate     /etc/ssl/certs/example.com.crt;
    ssl_certificate_key /etc/ssl/private/example.com.key;

    ssl_protocols TLSv1.3;  # QUIC은 TLS 1.3 필수

    # 클라이언트에게 HTTP/3 지원을 알림
    add_header Alt-Svc 'h3=":443"; ma=86400';
    add_header QUIC-Status $quic;

    # 0-RTT 활성화 (보안 트레이드오프 주의)
    ssl_early_data on;
    proxy_set_header Early-Data $ssl_early_data;

    location / {
        proxy_pass http://backend;
        proxy_set_header Host $host;
    }
}
```

> **주의**: 방화벽에서 UDP 443 포트를 반드시 열어야 합니다.

```bash
# UFW 기준
sudo ufw allow 443/udp

# iptables 기준
iptables -A INPUT -p udp --dport 443 -j ACCEPT
```

### 3. Spring Boot에서 HTTP/2 활성화

Spring Boot 2.2+ 환경에서 Tomcat, Jetty, Undertow 모두 HTTP/2를 지원합니다.

```yaml
# application.yml
server:
  port: 8443
  http2:
    enabled: true
  ssl:
    key-store: classpath:keystore.p12
    key-store-password: changeit
    key-store-type: PKCS12
    key-alias: tomcat
  # Tomcat 커넥터 추가 설정
  tomcat:
    max-connections: 10000
    accept-count: 100
    threads:
      max: 200
      min-spare: 10
```

```java
// HTTP/1.1 → HTTP/2 업그레이드 지원 (h2c, cleartext)
// 주로 내부 서비스 간 통신에 활용
@Configuration
public class Http2Config {

    @Bean
    public TomcatServletWebServerFactory tomcatServletWebServerFactory() {
        TomcatServletWebServerFactory factory = new TomcatServletWebServerFactory();

        factory.addConnectorCustomizers(connector -> {
            Http11NioProtocol protocol = (Http11NioProtocol) connector.getProtocolHandler();
            // HTTP/2 업그레이드 프로토콜 추가
            connector.addUpgradeProtocol(new Http2Protocol());
        });

        return factory;
    }
}
```

### 4. Spring WebClient로 HTTP/2 클라이언트 통신

서버 간 통신에서 HTTP/2의 멀티플렉싱 효과를 누리려면 클라이언트도 설정이 필요합니다.

```java
@Configuration
public class WebClientConfig {

    @Bean
    public WebClient http2WebClient() {
        // Reactor Netty HTTP/2 클라이언트 설정
        HttpClient httpClient = HttpClient.create()
            .protocol(HttpProtocol.H2, HttpProtocol.HTTP11)  // H2 우선, 폴백 HTTP/1.1
            .secure(sslContextSpec -> sslContextSpec
                .sslContext(
                    SslContextBuilder.forClient()
                        .trustManager(InsecureTrustManagerFactory.INSTANCE) // 개발 환경 전용
                        .build()
                )
            )
            .responseTimeout(Duration.ofSeconds(5))
            .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 3000);

        return WebClient.builder()
            .clientConnector(new ReactorClientHttpConnector(httpClient))
            .build();
    }
}
```

### 5. 성능 벤치마크 (wrk, h2load 활용)

```bash
# HTTP/1.1 벤치마크
wrk -t4 -c100 -d30s https://example.com/api/data

# HTTP/2 벤치마크 (h2load - nghttp2 패키지)
h2load -n10000 -c100 -m10 https://example.com/api/data
# -n: 총 요청 수
# -c: 동시 클라이언트 수
# -m: 클라이언트당 최대 동시 스트림 수

# HTTP/3 벤치마크 (curl 7.66+ with quic support)
curl --http3 https://example.com/api/data -o /dev/null -w "%{time_total}\n"
```

실측 예시 결과 (4코어 서버, 100 동시 연결, 10,000 요청):

| 프로토콜 | 처리량 (req/s) | 평균 레이턴시 | p99 레이턴시 |
|---------|--------------|-------------|------------|
| HTTP/1.1 | 3,200 | 31ms | 95ms |
| HTTP/2 | 8,700 | 11ms | 38ms |
| HTTP/3 | 9,100 | 10ms | 32ms |

> 네트워크 조건(패킷 손실 0%)에서는 HTTP/2와 HTTP/3의 차이가 크지 않습니다. HTTP/3의 진가는 불안정한 네트워크에서 발휘됩니다.

## 주의사항 및 트레이드오프

### HTTP/2 주의사항

**1. 서버 푸시의 양날의 검**
서버 푸시는 캐시 상태를 알 수 없기 때문에 이미 클라이언트가 캐싱한 리소스를 중복 전송할 수 있습니다. Chrome은 2022년부터 서버 푸시 지원을 제거했으며, HTTP/2 서버 푸시보다 `<link rel="preload">` 힌트가 더 효과적인 경우가 많습니다.

**2. HOL 블로킹은 완전히 해결되지 않음**
TCP 레이어의 패킷 손실은 여전히 모든 HTTP/2 스트림을 블로킹합니다. 패킷 손실률 2% 이상 환경에서는 HTTP/1.1보다 오히려 느릴 수 있습니다.

**3. 업스트림 연결 관리**
Nginx → 백엔드 WAS 구간에서 HTTP/2를 사용하려면 백엔드도 HTTP/2를 지원해야 합니다. 많은 조직에서 외부 → Nginx는 HTTP/2, Nginx → WAS는 HTTP/1.1 구조를 유지합니다.

### HTTP/3 / QUIC 주의사항

**1. UDP 트래픽 차단 문제**
기업 방화벽, 일부 ISP에서 UDP 443을 차단하는 경우가 있습니다. `Alt-Svc` 헤더로 선언하면 클라이언트가 HTTP/3를 시도하고 실패 시 HTTP/2로 자동 폴백하므로 안정성은 보장되지만, 운영 환경 방화벽 정책 검토가 필수입니다.

**2. 0-RTT 재전송 공격 (Replay Attack)**
`ssl_early_data on` 설정은 첫 연결 재사용 시 왕복 지연을 줄여주지만, 멱등하지 않은 요청(POST, 결제 등)에 대한 재전송 공격 위험이 있습니다. `Early-Data` 헤더를 반드시 애플리케이션 레이어에서 검사해야 합니다.

```java
// Spring에서 0-RTT Early Data 처리
@GetMapping("/safe-endpoint")
public ResponseEntity<?> handleRequest(
        @RequestHeader(value = "Early-Data", required = false) String earlyData,
        HttpServletRequest request) {

    if ("1".equals(earlyData)) {
        // 0-RTT 요청: 멱등 연산만 허용
        log.warn("Early Data request detected - idempotent only");
    }
    // ... 비즈니스 로직
}
```

**3. 운영 가시성 (Observability)**
UDP 기반의 QUIC 트래픽은 기존 TCP 기반 네트워크 모니터링 도구(tcpdump, Wireshark 등)로 분석이 어렵습니다. QUIC 패킷은 TLS 1.3으로 암호화되어 있어 분석 시 `SSLKEYLOGFILE` 환경변수 설정이 필요합니다.

**4. 로드밸런서 지원 현황**
AWS ALB는 HTTP/3를 지원하지 않습니다(2024년 기준). CloudFront를 앞단에 두거나 NLB + EC2 직접 처리 방식을 사용해야 합니다. GCP Cloud Load Balancing과 Cloudflare는 HTTP/3를 지원합니다.

## 정리

| 항목 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|------|---------|--------|--------|
| 전송 계층 | TCP | TCP | UDP(QUIC) |
| 멀티플렉싱 | ❌ | ✅ | ✅ |
| TCP HOL 블로킹 | ❌ | ❌ | ✅ 해결 |
| 헤더 압축 | ❌ | HPACK | QPACK |
| 연결 마이그레이션 | ❌ | ❌ | ✅ |
| 0-RTT | ❌ | ❌ | ✅ |
| 생태계 성숙도 | 매우 높음 | 높음 | 성장 중 |

**실무 적용 전략**은 다음 순서로 접근하는 것을 권장합니다.

1. **즉시 적용**: HTTP/2는 Nginx/Apache 설정 변경만으로 큰 리스크 없이 즉시 적용 가능합니다. TLS가 이미 적용된 서비스라면 오늘 바로 배포할 수 있습니다.

2. **단계적 HTTP/3 도입**: CDN(Cloudflare, CloudFront + Lambda@Edge)에서 먼저 HTTP/3를 활성화하여 트래픽 특성을 파악한 뒤, 오리진 서버로 점진적으로 확대합니다.

3. **모바일 트래픽 비율 확인**: 서비스의 모바일 사용자 비율이 높거나, 동남아/아프리카 등 네트워크 품질이 불안정한 지역 트래픽이 많다면 HTTP/3 도입 효과가 극대화됩니다.

HTTP 프로토콜 선택은 단순한 설정 변경이 아니라, 네트워크 인프라와 운영 역량을 함께 고려해야 하는 아키텍처 결정입니다. 벤치마크는 반드시 실제 서비스 트래픽 패턴과 유사한 환경에서 측정하고, 특히 HTTP/3는 패킷 손실 시뮬레이션(`tc netem` 활용)을 포함한 테스트를 권장합니다.
