# Nginx 리버스 프록시 고급 설정과 성능 튜닝

## 개요

Nginx는 단순한 웹 서버를 넘어 현대 인프라에서 API 게이트웨이, 로드 밸런서, SSL 터미네이터 등 다양한 역할을 수행한다. 특히 리버스 프록시 구성은 백엔드 서비스를 보호하고 트래픽을 효율적으로 분산시키는 핵심 레이어다.

하지만 많은 팀이 기본 `proxy_pass` 설정 이후 더 이상 최적화를 진행하지 않는다. 실제로 Nginx의 성능을 제대로 끌어내려면 **워커 프로세스 튜닝, 업스트림 keepalive, 버퍼링 전략, 캐시 설정, 헬스 체크** 등 여러 레이어를 함께 다뤄야 한다.

이 글에서는 실무에서 자주 마주치는 시나리오를 중심으로 Nginx 리버스 프록시의 고급 설정과 성능 튜닝 기법을 정리한다.

## 핵심 개념

### 워커 프로세스와 이벤트 모델

Nginx는 비동기 이벤트 기반 아키텍처를 사용한다. 전통적인 Apache의 스레드/프로세스 모델과 달리, 하나의 워커 프로세스가 수천 개의 동시 연결을 처리할 수 있다.

```nginx
# nginx.conf - 메인 컨텍스트
worker_processes auto;          # CPU 코어 수에 맞게 자동 설정
worker_rlimit_nofile 65535;     # 워커당 최대 파일 디스크립터 수

events {
    worker_connections 4096;    # 워커당 최대 동시 연결 수
    use epoll;                  # Linux에서 가장 효율적인 이벤트 모델
    multi_accept on;            # 한 번에 여러 연결 수락
}
```

`worker_processes auto`는 실제 CPU 코어 수를 읽어 설정하므로 대부분의 환경에서 적합하다. 단, CPU-intensive한 SSL 처리가 많다면 코어 수보다 약간 낮게 설정해 컨텍스트 스위칭 오버헤드를 줄이는 것도 고려할 수 있다.

### 업스트림 Keepalive

리버스 프록시의 성능에서 가장 큰 영향을 미치는 요소 중 하나가 **백엔드와의 TCP 연결 재사용**이다. 기본 설정에서는 요청마다 새로운 TCP 연결을 맺는데, 이는 상당한 레이턴시와 리소스 낭비를 유발한다.

```nginx
upstream backend_api {
    server 10.0.1.10:8080;
    server 10.0.1.11:8080;
    server 10.0.1.12:8080;

    keepalive 64;           # 각 워커가 유지할 유휴 keepalive 연결 수
    keepalive_requests 1000; # 하나의 keepalive 연결로 처리할 최대 요청 수
    keepalive_timeout 60s;   # 유휴 keepalive 연결 유지 시간
}
```

업스트림 keepalive를 활성화할 때는 반드시 프록시 헤더도 함께 설정해야 한다.

```nginx
location /api/ {
    proxy_pass http://backend_api;
    proxy_http_version 1.1;              # keepalive는 HTTP/1.1 필요
    proxy_set_header Connection "";      # Connection: close 헤더 제거
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

## 실전 예제

### 1. 완성형 리버스 프록시 설정

실무에서 사용할 수 있는 완전한 형태의 설정 예제다.

```nginx
# /etc/nginx/conf.d/api-gateway.conf

upstream spring_backend {
    least_conn;                  # 최소 연결 수 기반 로드 밸런싱
    server 10.0.1.10:8080 weight=3 max_fails=3 fail_timeout=30s;
    server 10.0.1.11:8080 weight=3 max_fails=3 fail_timeout=30s;
    server 10.0.1.12:8080 weight=1 max_fails=3 fail_timeout=30s backup;

    keepalive 32;
    keepalive_requests 500;
    keepalive_timeout 30s;
}

server {
    listen 443 ssl http2;
    server_name api.example.com;

    # SSL 설정
    ssl_certificate     /etc/ssl/certs/api.example.com.crt;
    ssl_certificate_key /etc/ssl/private/api.example.com.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_ciphers         ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256;
    ssl_session_cache   shared:SSL:10m;
    ssl_session_timeout 1d;
    ssl_session_tickets off;

    # 보안 헤더
    add_header Strict-Transport-Security "max-age=63072000" always;
    add_header X-Content-Type-Options nosniff;
    add_header X-Frame-Options DENY;

    # 버퍼 튜닝
    proxy_buffering on;
    proxy_buffer_size 16k;
    proxy_buffers 8 16k;
    proxy_busy_buffers_size 32k;

    # 타임아웃 설정
    proxy_connect_timeout 5s;
    proxy_send_timeout 60s;
    proxy_read_timeout 60s;

    location /api/ {
        proxy_pass http://spring_backend/;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 에러 처리
        proxy_next_upstream error timeout http_502 http_503 http_504;
        proxy_next_upstream_tries 2;
        proxy_next_upstream_timeout 10s;
    }

    # 정적 파일 직접 서빙
    location /static/ {
        root /var/www/html;
        expires 30d;
        add_header Cache-Control "public, immutable";
        access_log off;
    }
}
```

### 2. 프록시 캐시 설정

읽기가 많은 API 엔드포인트에는 Nginx 레벨의 캐시를 적용해 백엔드 부하를 크게 줄일 수 있다.

```nginx
# http 컨텍스트에 캐시 존 정의
proxy_cache_path /var/cache/nginx/api
    levels=1:2
    keys_zone=api_cache:10m     # 캐시 키 메타데이터 저장 공간
    max_size=1g                 # 최대 디스크 사용량
    inactive=60m                # 미사용 캐시 유효 시간
    use_temp_path=off;          # 임시 파일 경로 최적화

server {
    # ...

    location /api/v1/products {
        proxy_pass http://spring_backend;
        proxy_cache api_cache;
        proxy_cache_key "$scheme$host$request_uri";
        proxy_cache_valid 200 5m;       # 200 응답은 5분 캐시
        proxy_cache_valid 404 1m;       # 404 응답은 1분 캐시
        proxy_cache_use_stale error timeout updating; # 백엔드 장애 시 stale 캐시 사용
        proxy_cache_lock on;            # 동일 캐시 미스 요청 직렬화 (thundering herd 방지)

        add_header X-Cache-Status $upstream_cache_status; # HIT/MISS 디버깅용
    }
}
```

### 3. Rate Limiting과 연결 제어

```nginx
# http 컨텍스트
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=100r/m;
limit_req_zone $http_x_api_key zone=key_limit:10m rate=1000r/m;
limit_conn_zone $binary_remote_addr zone=conn_limit:10m;

server {
    location /api/ {
        # 일반 사용자: 분당 100요청, 버스트 20 허용
        limit_req zone=api_limit burst=20 nodelay;
        limit_conn conn_limit 20;       # IP당 최대 동시 연결 수

        limit_req_status 429;
        limit_conn_status 429;

        proxy_pass http://spring_backend;
        # ...
    }

    location /api/internal/ {
        # 내부 API는 API 키 기반으로 더 높은 제한 적용
        limit_req zone=key_limit burst=200 nodelay;
        proxy_pass http://spring_backend;
    }
}
```

## 주의사항 및 트레이드오프

### 버퍼 크기 설정의 함정

`proxy_buffer_size`와 `proxy_buffers`를 너무 크게 설정하면 메모리 사용량이 급증한다. 워커 연결당 버퍼가 할당되므로, `worker_connections × proxy_buffer_size × proxy_buffers` 만큼의 메모리가 최대로 필요하다.

```
예시 계산:
4 workers × 4096 connections × 8 buffers × 16KB = 약 2GB
```

응답 크기가 큰 API(파일 다운로드, 대용량 JSON)가 있다면 해당 location에만 별도로 큰 버퍼를 설정하는 것이 바람직하다.

### Keepalive 수 과다 설정

`keepalive` 값을 너무 높게 설정하면 백엔드 서버의 TCP 연결 한도를 초과할 수 있다. Spring Boot 기본 설정(Tomcat)은 최대 200개의 스레드를 사용하므로, Nginx 워커 수와 keepalive 값의 곱이 백엔드 최대 연결 수를 초과하지 않도록 주의해야 한다.

```
Nginx 워커 수 × keepalive 수 ≤ 백엔드 max_connections
예: 4 × 32 = 128 (Tomcat 기본 200 이하 ✓)
```

### proxy_next_upstream의 멱등성 문제

`proxy_next_upstream`은 실패한 요청을 다른 백엔드로 자동 재시도한다. **POST, PUT, PATCH와 같은 비멱등성 메서드에 이를 적용하면 중복 처리가 발생할 수 있다.**

```nginx
# 안전한 재시도 설정: GET/HEAD만 재시도
proxy_next_upstream error timeout;
proxy_next_upstream_tries 2;

# 비멱등성 메서드 보호
location /api/ {
    if ($request_method !~ ^(GET|HEAD)$) {
        proxy_next_upstream off;
    }
    proxy_pass http://spring_backend;
}
```

### 캐시 무효화 전략

Nginx 프록시 캐시는 기본적으로 자동 무효화 메커니즘이 없다. 배포나 데이터 변경 시 캐시를 수동으로 비워야 한다.

```bash
# 특정 캐시 키 패턴 삭제 (find + rm)
find /var/cache/nginx/api -type f -delete

# 또는 cache purge 모듈 사용 (Nginx Plus)
# curl -X PURGE https://api.example.com/api/v1/products
```

## 정리

Nginx 리버스 프록시 튜닝은 단일 설정 변경으로 극적인 효과를 기대하기보다는 **여러 레이어의 균형 잡힌 최적화**가 핵심이다.

| 최적화 항목 | 기대 효과 | 주요 주의사항 |
|---|---|---|
| 업스트림 keepalive | TCP 핸드셰이크 제거, 레이턴시 감소 | 백엔드 연결 한도 초과 주의 |
| 프록시 버퍼 튜닝 | 백엔드 연결 점유 시간 단축 | 메모리 사용량 증가 |
| 프록시 캐시 | 백엔드 부하 감소 | 데이터 정합성, 무효화 전략 필요 |
| Rate Limiting | 백엔드 보호, 공정한 자원 분배 | 429 에러 핸들링 클라이언트 협의 필요 |
| SSL 세션 캐시 | TLS 핸드셰이크 비용 감소 | 세션 티켓 보안 고려 |

실제 운영 환경에서는 변경 전후 반드시 `ab`, `wrk`, `k6` 같은 도구로 부하 테스트를 수행하고, Prometheus + Grafana나 Datadog으로 `upstream_response_time`, `upstream_connect_time` 메트릭을 모니터링하며 점진적으로 적용해 나가는 것을 권장한다.
