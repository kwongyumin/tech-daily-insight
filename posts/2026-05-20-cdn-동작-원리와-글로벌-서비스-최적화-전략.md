# CDN 동작 원리와 글로벌 서비스 최적화 전략

## 개요

글로벌 서비스를 운영하다 보면 반드시 마주치는 문제가 있다. 서울에서 완벽하게 동작하는 서비스가 미국이나 유럽 사용자에게는 느리게 느껴지는 현상이다. 근본 원인은 단순하다. 물리적 거리와 네트워크 홉(hop) 수가 응답 속도에 직접적인 영향을 미치기 때문이다.

CDN(Content Delivery Network)은 이 문제를 해결하기 위한 핵심 인프라다. 단순히 "정적 파일을 캐시해주는 서비스"로만 이해하면 CDN의 절반도 활용하지 못하는 것이다. 이 글에서는 CDN의 내부 동작 원리를 깊이 파헤치고, 실무에서 바로 적용할 수 있는 글로벌 서비스 최적화 전략을 다룬다.

---

## 핵심 개념

### CDN의 구조와 트래픽 흐름

CDN은 전 세계에 분산된 **PoP(Point of Presence)** 서버 집합으로 구성된다. 사용자가 콘텐츠를 요청하면 원본 서버(Origin)가 아닌 가장 가까운 PoP에서 응답한다.

```
[사용자 브라우저]
       ↓ DNS 쿼리
[Authoritative DNS / CDN DNS]
       ↓ 가장 가까운 Edge 노드 IP 반환
[Edge PoP 서버 (Cache Hit)]
       ↓ Cache Miss 시에만
[Origin 서버]
```

DNS 기반 라우팅이 가장 일반적이며, CDN 벤더는 사용자의 IP를 기반으로 지리적으로 가장 가까운 PoP의 IP를 응답한다. 이 외에도 **Anycast 라우팅**을 사용하는 방식도 있는데, Cloudflare가 이 방식을 적극 활용한다.

### Cache Hit Ratio와 TTL 설계

CDN의 효율성은 **Cache Hit Ratio**로 결정된다. Hit Ratio가 낮으면 Origin으로 요청이 집중되어 CDN을 도입한 의미가 없어진다.

캐시 동작을 결정하는 핵심 헤더들:

| 헤더 | 역할 |
|------|------|
| `Cache-Control` | 캐시 정책의 근간 |
| `ETag` | 콘텐츠 변경 여부 검증 |
| `Last-Modified` | 시간 기반 변경 여부 |
| `Vary` | 캐시 키 분리 조건 |
| `Surrogate-Control` | CDN 전용 캐시 지시어 |

### Edge Computing과 CDN의 진화

현대 CDN은 단순 캐시를 넘어 **Edge에서 코드를 실행**할 수 있는 플랫폼으로 진화했다. Cloudflare Workers, AWS Lambda@Edge, Fastly Compute@Edge가 대표적이다. 인증, A/B 테스트, 개인화 응답 등을 Origin 없이 Edge에서 처리할 수 있다.

## 실전 예제

### 1. Spring Boot에서 Cache-Control 헤더 최적화

정적 리소스와 동적 API를 명확하게 구분하여 캐시 전략을 다르게 가져가야 한다.

```java
@Configuration
@EnableWebMvc
public class WebMvcConfig implements WebMvcConfigurer {

    @Override
    public void addResourceHandlers(ResourceHandlerRegistry registry) {
        // 버전 해시가 포함된 정적 자산: 1년 캐시
        registry.addResourceHandler("/static/**")
                .addResourceLocations("classpath:/static/")
                .setCacheControl(CacheControl.maxAge(365, TimeUnit.DAYS)
                        .cachePublic()
                        .immutable());

        // 이미지 리소스: 7일 캐시
        registry.addResourceHandler("/images/**")
                .addResourceLocations("classpath:/images/")
                .setCacheControl(CacheControl.maxAge(7, TimeUnit.DAYS)
                        .cachePublic());
    }
}
```

```java
@RestController
@RequestMapping("/api")
public class ProductController {

    // 동적 API: CDN 캐시 허용, 1분 유지 + Stale-While-Revalidate 활용
    @GetMapping("/products/{id}")
    public ResponseEntity<ProductDto> getProduct(@PathVariable Long id) {
        ProductDto product = productService.findById(id);
        
        return ResponseEntity.ok()
                .cacheControl(CacheControl.maxAge(60, TimeUnit.SECONDS)
                        .cachePublic()
                        .staleWhileRevalidate(30, TimeUnit.SECONDS))
                .eTag(String.valueOf(product.getVersion()))
                .body(product);
    }

    // 사용자별 개인화 데이터: CDN 캐시 금지
    @GetMapping("/users/me/profile")
    public ResponseEntity<UserDto> getMyProfile() {
        UserDto user = userService.getCurrentUser();
        
        return ResponseEntity.ok()
                .cacheControl(CacheControl.noStore())
                .body(user);
    }
}
```

### 2. Nginx를 Origin Shield로 활용하기

**Origin Shield**는 CDN Edge와 Origin 사이에 위치하는 중간 캐시 레이어다. 전 세계 PoP에서 Origin으로 직접 오는 요청을 Shield 레이어 하나에서 흡수한다.

```nginx
# nginx.conf - Origin Shield 역할 설정
proxy_cache_path /var/cache/nginx levels=1:2 
                 keys_zone=cdn_cache:100m 
                 max_size=10g 
                 inactive=60m 
                 use_temp_path=off;

server {
    listen 80;
    server_name origin-shield.example.com;

    location / {
        proxy_pass http://origin-backend;
        proxy_cache cdn_cache;
        proxy_cache_valid 200 10m;
        proxy_cache_valid 404 1m;

        # Stale 콘텐츠 서빙으로 Origin 장애 시 내성 확보
        proxy_cache_use_stale error timeout updating 
                              http_500 http_502 http_503 http_504;
        proxy_cache_background_update on;
        proxy_cache_lock on;

        # 캐시 키에서 불필요한 쿼리 파라미터 제거
        proxy_cache_key "$scheme$host$uri$is_args$args";

        add_header X-Cache-Status $upstream_cache_status;
        add_header X-Cache-Age $upstream_http_age;
    }
}
```

### 3. Cloudflare Workers로 Edge에서 A/B 테스트 구현

```javascript
// cloudflare-worker.js
addEventListener('fetch', event => {
    event.respondWith(handleRequest(event.request));
});

async function handleRequest(request) {
    const url = new URL(request.url);
    
    // 특정 경로에만 A/B 테스트 적용
    if (!url.pathname.startsWith('/landing')) {
        return fetch(request);
    }

    // 사용자 식별: 쿠키 또는 신규 UUID 발급
    const cookies = parseCookies(request.headers.get('Cookie') || '');
    let userId = cookies['ab_user_id'];
    
    if (!userId) {
        userId = crypto.randomUUID();
    }

    // 해시 기반으로 버킷 결정 (50/50 분배)
    const bucket = await getBucket(userId);
    const targetOrigin = bucket === 'A' 
        ? 'https://origin-a.example.com' 
        : 'https://origin-b.example.com';

    const newRequest = new Request(
        `${targetOrigin}${url.pathname}${url.search}`,
        request
    );

    const response = await fetch(newRequest);
    const newResponse = new Response(response.body, response);

    // 사용자 버킷 쿠키 설정
    newResponse.headers.append(
        'Set-Cookie', 
        `ab_user_id=${userId}; Max-Age=86400; Path=/; SameSite=Lax`
    );
    newResponse.headers.set('X-AB-Bucket', bucket);

    return newResponse;
}

async function getBucket(userId) {
    const encoder = new TextEncoder();
    const data = encoder.encode(userId);
    const hashBuffer = await crypto.subtle.digest('SHA-256', data);
    const hashArray = new Uint8Array(hashBuffer);
    return hashArray[0] < 128 ? 'A' : 'B';
}

function parseCookies(cookieString) {
    return Object.fromEntries(
        cookieString.split(';')
            .map(cookie => cookie.trim().split('='))
            .filter(parts => parts.length === 2)
    );
}
```

### 4. Cache Purge 자동화 (Terraform + AWS CloudFront)

배포 시점에 CDN 캐시를 자동으로 무효화하는 파이프라인 구성:

```hcl
# cloudfront_invalidation.tf
resource "aws_cloudfront_distribution" "main" {
    # ... distribution 설정

    default_cache_behavior {
        allowed_methods  = ["GET", "HEAD"]
        cached_methods   = ["GET", "HEAD"]
        target_origin_id = "main-origin"

        forwarded_values {
            query_string = false
            cookies { forward = "none" }
        }

        min_ttl     = 0
        default_ttl = 86400
        max_ttl     = 31536000
        compress    = true
    }
}
```

```bash
#!/bin/bash
# deploy.sh - 배포 후 캐시 무효화 스크립트

DISTRIBUTION_ID="E1234567890ABC"
DEPLOY_PATHS=("/index.html" "/static/js/*" "/static/css/*")

echo "Creating CloudFront invalidation..."

INVALIDATION_ID=$(aws cloudfront create-invalidation \
    --distribution-id "$DISTRIBUTION_ID" \
    --paths "${DEPLOY_PATHS[@]}" \
    --query 'Invalidation.Id' \
    --output text)

echo "Waiting for invalidation $INVALIDATION_ID to complete..."

aws cloudfront wait invalidation-completed \
    --distribution-id "$DISTRIBUTION_ID" \
    --id "$INVALIDATION_ID"

echo "Cache invalidation completed successfully."
```

## 주의사항 및 트레이드오프

### Cache Stampede (Thundering Herd) 문제

캐시 TTL이 만료된 순간 수천 개의 요청이 동시에 Origin으로 몰리는 현상이다. 이를 방지하기 위해:

- **Stale-While-Revalidate**: 만료된 캐시를 서빙하면서 백그라운드에서 갱신
- **Cache Lock**: 첫 번째 요청만 Origin으로 보내고 나머지는 대기
- **Probabilistic Early Expiration**: TTL 만료 전에 확률적으로 조기 갱신

### Vary 헤더 오용 주의

```
# 잘못된 예: User-Agent를 Vary에 포함하면 캐시 키가 폭발적으로 증가
Vary: User-Agent, Accept-Encoding, Accept-Language
```

`Vary: User-Agent`는 수천 가지 User-Agent마다 별도 캐시를 생성하여 Hit Ratio를 사실상 0으로 만든다. 디바이스 유형 분기가 필요하다면 Edge에서 정규화 후 커스텀 헤더를 사용하라.

### 개인정보와 지역 규제 (GDPR, PIPA)

CDN은 사용자 데이터를 전 세계 PoP에 분산 저장할 수 있다. EU 사용자의 데이터가 EU 외부 서버에 캐시되면 GDPR 위반이 될 수 있다. 이를 위해:

- **Geo-Restriction**: 특정 국가에서의 접근 제한
- **Token Authentication**: 민감한 콘텐츠에 서명된 URL 적용
- **Regional Edge Cache 격리**: 특정 지역 데이터가 해당 지역 PoP에만 머물도록 설정

### TTL vs. 신선도 트레이드오프

| TTL 길이 | 장점 | 단점 |
|----------|------|------|
| 짧음 (< 5분) | 콘텐츠 신선도 높음 | Origin 부하 증가, Hit Ratio 하락 |
| 길음 (> 1시간) | Hit Ratio 높음, Origin 부하 감소 | 콘텐츠 갱신 지연, Purge 비용 발생 |

결론적으로 **버전 해시 기반 파일명** (`app.3f7a2b.js`)을 사용하면 파일이 변경되면 URL 자체가 바뀌므로 TTL을 무한대로 설정해도 안전하다. 이 전략이 정적 자산에서의 황금 법칙이다.

## 정리

CDN을 단순한 정적 파일 서버로만 활용하는 것은 그 잠재력의 극히 일부만 사용하는 것이다. 핵심 포인트를 정리하면 다음과 같다.

1. **Cache-Control 헤더 설계**가 CDN 효율의 70%를 결정한다. 리소스 유형별로 명확한 전략을 수립하라.
2. **Origin Shield**를 도입해 전 세계 PoP과 Origin 사이의 트래픽을 흡수하라.
3. **Edge Computing**을 활용하면 인증, A/B 테스트, 리다이렉트 등을 Origin 없이 처리할 수 있다.
4. **Cache Stampede**와 **Vary 헤더 오용**은 대표적인 안티패턴이다. 반드시 숙지하라.
5. GDPR 등 **개인정보 규제**를 고려한 CDN 설정은 선택이 아닌 필수다.

글로벌 서비스에서 CDN은 성능 최적화의 마지막 단계가 아니라 **아키텍처 설계의 시작점**이 되어야 한다. Origin 서버가 지구 반대편 사용자에게 직접 응답하는 구조는 처음부터 잘못된 설계임을 명심하자.
