# JWT 토큰 보안 설계와 갱신 전략 완전 가이드

## 개요

JWT(JSON Web Token)는 마이크로서비스 아키텍처와 REST API 환경에서 사실상 표준 인증 수단으로 자리 잡았다. 그러나 "JWT를 쓴다"는 것과 "JWT를 안전하게 쓴다"는 것은 전혀 다른 이야기다. 실무 현장에서는 Access Token 만료 시간을 너무 길게 설정하거나, Refresh Token을 단순히 로컬스토리지에 저장하거나, 토큰 탈취 시나리오를 고려하지 않은 설계가 빈번하게 발견된다.

이 글에서는 JWT의 구조적 특성에서 오는 보안 리스크를 짚고, Access/Refresh Token 이중 구조 설계, RTR(Refresh Token Rotation) 전략, 블랙리스트 관리까지 실무에서 바로 적용 가능한 수준으로 다룬다.

## 핵심 개념

### JWT의 구조적 특성과 보안 함의

JWT는 `Header.Payload.Signature` 세 부분으로 구성된다. 서버가 상태를 유지하지 않는 **Stateless** 특성이 핵심 장점이지만, 이로 인해 **서버 측에서 즉각적인 토큰 무효화가 불가능**하다는 치명적인 단점이 생긴다.

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9   ← Header (Base64)
.eyJzdWIiOiJ1c2VyMTIzIiwicm9sZSI6IlVTRVIiLCJleHAiOjE3MDAwMDAwMDB9  ← Payload (Base64)
.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c  ← Signature
```

Payload는 단순 Base64 인코딩이므로 **암호화가 아니다**. 민감 정보(비밀번호, 카드번호 등)는 절대 포함해선 안 된다.

### Access Token vs Refresh Token 이중 구조

| 구분 | Access Token | Refresh Token |
|------|-------------|---------------|
| 목적 | API 인증 | Access Token 재발급 |
| 만료 시간 | 15분 ~ 1시간 | 7일 ~ 30일 |
| 저장 위치 | 메모리 또는 쿠키 | HttpOnly 쿠키 |
| 서버 저장 | 불필요 | DB/Redis 필수 |

Access Token은 수명이 짧아 탈취되더라도 피해 범위가 제한된다. Refresh Token은 수명이 길기 때문에 반드시 서버에 저장하고 유효성을 검증해야 한다.

### RTR(Refresh Token Rotation) 전략

RTR은 Refresh Token을 사용할 때마다 새로운 Refresh Token을 발급하고 이전 토큰을 폐기하는 전략이다. 토큰이 탈취되어 재사용될 경우 탐지가 가능해진다.

```
[정상 흐름]
Client → /refresh (RT_v1) → Server: RT_v1 폐기, RT_v2 + AT_new 발급
Client → /refresh (RT_v2) → Server: RT_v2 폐기, RT_v3 + AT_new 발급

[탈취 탐지 흐름]
공격자 → /refresh (RT_v1) → 성공 (RT_v2 발급)
정상 유저 → /refresh (RT_v1) → 실패! → 서버: 해당 계정 모든 RT 폐기 + 알림
```

## 실전 예제 (Spring Boot + Redis)

### 의존성 및 설정

```gradle
// build.gradle
implementation 'io.jsonwebtoken:jjwt-api:0.12.3'
runtimeOnly 'io.jsonwebtoken:jjwt-impl:0.12.3'
runtimeOnly 'io.jsonwebtoken:jjwt-jackson:0.12.3'
implementation 'org.springframework.boot:spring-boot-starter-data-redis'
```

```yaml
# application.yml
jwt:
  secret: ${JWT_SECRET}  # 256비트 이상 랜덤 키 (환경변수로 관리)
  access-token-expiry: 900        # 15분 (초)
  refresh-token-expiry: 604800    # 7일 (초)
```

### JwtTokenProvider 구현

```java
@Component
@RequiredArgsConstructor
public class JwtTokenProvider {

    @Value("${jwt.secret}")
    private String secretKey;

    @Value("${jwt.access-token-expiry}")
    private long accessTokenExpiry;

    @Value("${jwt.refresh-token-expiry}")
    private long refreshTokenExpiry;

    private SecretKey getSigningKey() {
        byte[] keyBytes = Decoders.BASE64.decode(secretKey);
        return Keys.hmacShaKeyFor(keyBytes);
    }

    public String generateAccessToken(String userId, String role) {
        return Jwts.builder()
                .subject(userId)
                .claim("role", role)
                .claim("type", "access")
                .issuedAt(new Date())
                .expiration(new Date(System.currentTimeMillis() + accessTokenExpiry * 1000))
                .signWith(getSigningKey())
                .compact();
    }

    public String generateRefreshToken(String userId) {
        return Jwts.builder()
                .subject(userId)
                .claim("type", "refresh")
                .id(UUID.randomUUID().toString())  // jti: 고유 식별자
                .issuedAt(new Date())
                .expiration(new Date(System.currentTimeMillis() + refreshTokenExpiry * 1000))
                .signWith(getSigningKey())
                .compact();
    }

    public Claims parseClaims(String token) {
        return Jwts.parser()
                .verifyWith(getSigningKey())
                .build()
                .parseSignedClaims(token)
                .getPayload();
    }

    public boolean validateToken(String token) {
        try {
            parseClaims(token);
            return true;
        } catch (ExpiredJwtException e) {
            throw new CustomException(ErrorCode.TOKEN_EXPIRED);
        } catch (JwtException e) {
            throw new CustomException(ErrorCode.TOKEN_INVALID);
        }
    }
}
```

### Redis 기반 Refresh Token 저장소

```java
@Service
@RequiredArgsConstructor
public class RefreshTokenService {

    private final RedisTemplate<String, String> redisTemplate;
    private final JwtTokenProvider jwtTokenProvider;

    private static final String PREFIX = "RT:";

    // RTR: 기존 토큰 폐기 후 새 토큰 저장
    public TokenPair rotate(String oldRefreshToken) {
        Claims claims = jwtTokenProvider.parseClaims(oldRefreshToken);
        String userId = claims.getSubject();
        String jti = claims.getId();

        String storedToken = redisTemplate.opsForValue().get(PREFIX + userId);

        // 저장된 토큰과 불일치 → 재사용 공격 탐지
        if (storedToken == null || !storedToken.equals(oldRefreshToken)) {
            // 모든 세션 강제 만료
            deleteAllTokens(userId);
            throw new CustomException(ErrorCode.REFRESH_TOKEN_REUSE_DETECTED);
        }

        // 기존 토큰 폐기
        redisTemplate.delete(PREFIX + userId);

        // 새 토큰 쌍 발급
        String role = claims.get("role", String.class);
        String newAccessToken = jwtTokenProvider.generateAccessToken(userId, role);
        String newRefreshToken = jwtTokenProvider.generateRefreshToken(userId);

        long expiry = jwtTokenProvider.getRefreshTokenExpiry();
        redisTemplate.opsForValue()
                .set(PREFIX + userId, newRefreshToken, expiry, TimeUnit.SECONDS);

        return new TokenPair(newAccessToken, newRefreshToken);
    }

    public void save(String userId, String refreshToken, long expiry) {
        redisTemplate.opsForValue()
                .set(PREFIX + userId, refreshToken, expiry, TimeUnit.SECONDS);
    }

    public void deleteAllTokens(String userId) {
        redisTemplate.delete(PREFIX + userId);
        // 알림 이벤트 발행 (슬랙, 이메일 등)
    }
}
```

### Access Token 블랙리스트 처리 (로그아웃)

JWT는 만료 전에는 유효하므로 로그아웃 시 블랙리스트 처리가 필요하다.

```java
@Service
@RequiredArgsConstructor
public class TokenBlacklistService {

    private final RedisTemplate<String, String> redisTemplate;
    private static final String BLACKLIST_PREFIX = "BL:";

    public void blacklist(String accessToken) {
        Claims claims = jwtTokenProvider.parseClaims(accessToken);
        long remaining = claims.getExpiration().getTime() - System.currentTimeMillis();

        if (remaining > 0) {
            // 남은 만료 시간만큼만 Redis에 보관 (자동 TTL 만료)
            redisTemplate.opsForValue()
                    .set(BLACKLIST_PREFIX + accessToken, "logout",
                         remaining, TimeUnit.MILLISECONDS);
        }
    }

    public boolean isBlacklisted(String accessToken) {
        return Boolean.TRUE.equals(
            redisTemplate.hasKey(BLACKLIST_PREFIX + accessToken)
        );
    }
}
```

### Security Filter 통합

```java
@Component
@RequiredArgsConstructor
public class JwtAuthenticationFilter extends OncePerRequestFilter {

    private final JwtTokenProvider jwtTokenProvider;
    private final TokenBlacklistService blacklistService;

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        String token = resolveToken(request);

        if (token != null && jwtTokenProvider.validateToken(token)) {
            if (blacklistService.isBlacklisted(token)) {
                response.sendError(HttpServletResponse.SC_UNAUTHORIZED, "Logged out token");
                return;
            }

            Claims claims = jwtTokenProvider.parseClaims(token);
            Authentication auth = createAuthentication(claims);
            SecurityContextHolder.getContext().setAuthentication(auth);
        }

        chain.doFilter(request, response);
    }

    private String resolveToken(HttpServletRequest request) {
        String bearer = request.getHeader("Authorization");
        if (StringUtils.hasText(bearer) && bearer.startsWith("Bearer ")) {
            return bearer.substring(7);
        }
        return null;
    }
}
```

## 주의사항 및 트레이드오프

### 1. 알고리즘 선택: HS256 vs RS256

| 알고리즘 | 방식 | 적합한 환경 |
|---------|------|------------|
| HS256 | 대칭키 (공유 시크릿) | 단일 서비스, 내부 API |
| RS256 | 비대칭키 (공개/개인키) | 마이크로서비스, 서드파티 연동 |

마이크로서비스 환경에서는 **RS256**을 강력히 권장한다. 공개키만 배포하면 되므로 시크릿 공유 없이 각 서비스에서 검증이 가능하다.

### 2. 토큰 저장 위치별 위협 모델

- **LocalStorage**: XSS 공격에 완전히 노출. 절대 Refresh Token 저장 금지
- **SessionStorage**: 탭 닫으면 소멸. XSS 위험은 동일
- **HttpOnly Cookie**: XSS 방어. 단, CSRF 공격 위험 → `SameSite=Strict` + CSRF 토큰 병행
- **메모리(JS 변수)**: 가장 안전하나 새로고침 시 소멸 → UX 저하

### 3. RTR의 동시 요청 문제

여러 탭에서 동시에 토큰 갱신 요청이 발생하면 RTR에서 false positive 탐지가 생길 수 있다. 이를 해결하려면 Redis의 분산 락이나 요청 큐잉이 필요하며, 실용적으로는 **짧은 Grace Period(수 초)**를 두어 동일 토큰에 대한 중복 갱신을 허용하는 방식을 채택하기도 한다.

### 4. Payload 크기와 성능

JWT는 모든 요청 헤더에 포함된다. Claim이 많아질수록 네트워크 오버헤드가 늘어난다. `userId`, `role`, `exp` 정도로 최소화하고, 추가 사용자 정보는 API 호출로 조회하는 것이 원칙이다.

### 5. 비밀키 관리

환경변수 직접 주입보다 **HashiCorp Vault**, **AWS Secrets Manager**, **GCP Secret Manager** 같은 비밀 관리 시스템을 활용하자. 키 로테이션 정책도 반드시 수립해야 한다.

## 정리

JWT 보안은 단순히 라이브러리를 가져다 쓰는 것으로 끝나지 않는다. 핵심 설계 포인트를 정리하면 다음과 같다.

| 항목 | 권장 사항 |
|------|----------|
| Access Token 만료 | 15분 이하 |
| Refresh Token 저장 | Redis (서버 측 검증 필수) |
| 갱신 전략 | RTR 적용 |
| 로그아웃 처리 | 블랙리스트 (Redis TTL 활용) |
| 알고리즘 | 단일 서비스 HS256, MSA는 RS256 |
| 클라이언트 저장 | HttpOnly + Secure Cookie |
| Payload | 최소 정보만 포함 |
| 비밀키 | Secrets Manager 관리 |

JWT의 Stateless 특성은 분명한 장점이지만, 그 장점을 취하면서도 보안을 유지하려면 **Redis를 활용한 서버 상태 관리와의 하이브리드 접근**이 불가피하다. "완전한 Stateless"에 집착하기보다 서비스 요구사항에 맞는 트레이드오프를 선택하는 것이 시니어 개발자의 올바른 접근법이다.

> **보안은 제품 기능이 아니라 아키텍처 속성이다.** 초기 설계 단계에서부터 토큰 탈취 시나리오를 고려한 방어 계층을 쌓아두는 것이 핵심이다.
