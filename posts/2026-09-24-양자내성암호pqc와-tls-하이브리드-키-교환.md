# 양자내성암호(PQC)와 TLS 하이브리드 키 교환

## 개요

양자 컴퓨터의 발전은 현재 우리가 사용하는 공개키 암호 시스템(RSA, ECDSA, ECDH 등)을 무력화할 수 있다는 우려를 낳고 있다. Shor 알고리즘을 충분한 큐비트의 양자 컴퓨터에서 실행하면 RSA-2048이나 ECC P-256 수준의 키를 다항 시간 내에 깰 수 있다. 물론 현재의 양자 컴퓨터는 아직 이 수준에 도달하지 못했지만, "지금 수집해서 나중에 해독한다(Harvest Now, Decrypt Later, HNDL)" 전략은 이미 현실적인 위협으로 간주된다.

이에 대응해 NIST는 2024년 8월 최종 표준으로 ML-KEM(CRYSTALS-Kyber), ML-DSA(CRYSTALS-Dilithium), SLH-DSA(SPHINCS+)를 발표했다. 그러나 새로운 알고리즘은 충분한 현장 검증이 부족하다. 이 간극을 메우기 위한 실용적 접근이 바로 **하이브리드 키 교환(Hybrid Key Exchange)**이다.

이 포스팅에서는 PQC의 핵심 개념을 정리하고, TLS 1.3 환경에서 하이브리드 키 교환을 실제로 구성하는 방법을 다룬다.

---

## 핵심 개념

### 왜 하이브리드인가?

하이브리드 방식은 전통적인 키 교환(예: X25519)과 PQC 키 교환(예: ML-KEM-768)을 **병렬로 수행**하고, 두 공유 비밀(shared secret)을 KDF(Key Derivation Function)로 결합해 최종 세션 키를 도출하는 방식이다.

```
최종 세션 키 = KDF(classical_shared_secret || pqc_shared_secret)
```

이 설계의 핵심 보안 속성은 다음과 같다:

- **클래식 알고리즘이 안전하다면**, 양자 컴퓨터가 없는 공격자로부터 보호된다.
- **PQC 알고리즘이 안전하다면**, 양자 컴퓨터가 있는 공격자로부터 보호된다.
- **둘 중 하나가 뚫리더라도** 나머지 하나의 보안 속성이 전체 세션 키를 보호한다.

즉, 하이브리드는 마이그레이션 기간 동안 "최선의 보안"을 제공하는 현실적인 선택이다.

### ML-KEM(CRYSTALS-Kyber) 개요

ML-KEM은 Module Learning With Errors(MLWE) 문제의 어려움에 기반한 키 캡슐화 메커니즘(KEM)이다. TLS의 키 교환에서는 다음과 같이 동작한다.

1. **서버**: `pk, sk = ML-KEM.KeyGen()`으로 공개키/비밀키 쌍 생성 후 `pk`를 클라이언트에 전송
2. **클라이언트**: `ciphertext, shared_secret = ML-KEM.Encaps(pk)`로 공유 비밀을 캡슐화
3. **서버**: `shared_secret = ML-KEM.Decaps(sk, ciphertext)`로 공유 비밀 복원

TLS 1.3에서는 이 KEM이 `KeyShare` 확장을 통해 동작한다.

### TLS 1.3과 NamedGroup 확장

TLS 1.3은 키 교환을 `supported_groups` 확장의 `NamedGroup`으로 협상한다. IETF RFC 8446에 정의된 클래식 그룹(x25519, secp256r1 등) 외에, 하이브리드를 위한 새로운 코드포인트가 IETF 드래프트(`draft-ietf-tls-hybrid-design`)에서 정의되고 있다.

주요 하이브리드 그룹 예시:

| 식별자 | 구성 |
|--------|------|
| `X25519MLKEM768` | X25519 + ML-KEM-768 |
| `SecP256r1MLKEM768` | P-256 + ML-KEM-768 |
| `X25519MLKEM1024` | X25519 + ML-KEM-1024 |

현재 Chrome 124+, Firefox 128+, OpenSSL 3.5, BoringSSL 등에서 이미 지원이 추가되었거나 추가 중이다.

## 실전 예제

### 1. OpenSSL 3.5를 활용한 하이브리드 TLS 서버 설정

OpenSSL 3.5는 ML-KEM을 기본 지원한다. 다음은 `X25519MLKEM768`을 우선 협상하도록 서버를 구성하는 예다.

```bash
# OpenSSL 버전 확인
openssl version
# OpenSSL 3.5.x 이상이어야 함

# 지원되는 그룹 목록 확인
openssl list -providers
openssl list -kem-algorithms
```

```ini
# openssl.cnf 설정 예시
[ssl_sect]
Groups = X25519MLKEM768:x25519:secp256r1
```

```bash
# s_server로 테스트 서버 실행
openssl s_server \
  -cert server.crt \
  -key server.key \
  -groups "X25519MLKEM768:x25519:secp256r1" \
  -tls1_3 \
  -port 8443

# 클라이언트 접속 테스트
openssl s_client \
  -connect localhost:8443 \
  -groups "X25519MLKEM768:x25519" \
  -tls1_3 \
  -keylogfile /tmp/tls_keylog.txt
```

접속 후 협상된 그룹을 확인하면 `Server Temp Key: X25519MLKEM768` 형태로 출력된다.

### 2. Java/Spring Boot 환경에서 Bouncy Castle + OQS 활용

Java 생태계에서는 현재 JDK 기본 JSSE가 PQC를 지원하지 않으므로, Open Quantum Safe(OQS) 기반의 liboqs-java 또는 Bouncy Castle을 활용해야 한다.

```xml
<!-- pom.xml -->
<dependency>
    <groupId>org.bouncycastle</groupId>
    <artifactId>bcprov-jdk18on</artifactId>
    <version>1.78.1</version>
</dependency>
<dependency>
    <groupId>org.bouncycastle</groupId>
    <artifactId>bctls-jdk18on</artifactId>
    <version>1.78.1</version>
</dependency>
```

```java
import org.bouncycastle.crypto.AsymmetricCipherKeyPair;
import org.bouncycastle.crypto.SecretWithEncapsulation;
import org.bouncycastle.pqc.crypto.mlkem.MLKEMExtractedParameters;
import org.bouncycastle.pqc.crypto.mlkem.MLKEMKeyGenerationParameters;
import org.bouncycastle.pqc.crypto.mlkem.MLKEMKeyPairGenerator;
import org.bouncycastle.pqc.crypto.mlkem.MLKEMParameters;
import org.bouncycastle.pqc.crypto.mlkem.MLKEMPublicKeyParameters;
import org.bouncycastle.pqc.crypto.mlkem.MLKEMKEMExtractor;
import org.bouncycastle.pqc.crypto.mlkem.MLKEMKEMGenerator;

import java.security.SecureRandom;

public class HybridKeyExchangeExample {

    private static final SecureRandom SECURE_RANDOM = new SecureRandom();

    /**
     * ML-KEM-768 키 쌍 생성 (서버 측)
     */
    public static AsymmetricCipherKeyPair generateMLKEMKeyPair() {
        MLKEMKeyPairGenerator keyGen = new MLKEMKeyPairGenerator();
        keyGen.init(new MLKEMKeyGenerationParameters(SECURE_RANDOM, MLKEMParameters.ml_kem_768));
        return keyGen.generateKeyPair();
    }

    /**
     * 클라이언트: 서버 공개키로 캡슐화, 공유 비밀 + 암호문 반환
     */
    public static SecretWithEncapsulation encapsulate(MLKEMPublicKeyParameters serverPublicKey) {
        MLKEMKEMGenerator kemGenerator = new MLKEMKEMGenerator(SECURE_RANDOM);
        return kemGenerator.generateEncapsulated(serverPublicKey);
    }

    /**
     * 서버: 비밀키로 암호문에서 공유 비밀 복원
     */
    public static byte[] decapsulate(AsymmetricCipherKeyPair serverKeyPair, byte[] ciphertext) {
        MLKEMKEMExtractor extractor = new MLKEMKEMExtractor(
            (MLKEMExtractedParameters) serverKeyPair.getPrivate()
        );
        return extractor.extractSecret(ciphertext);
    }
}
```

```java
import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;

public class HybridSessionKeyDeriver {

    /**
     * X25519 공유 비밀 + ML-KEM 공유 비밀을 결합해 최종 세션 키 도출
     * RFC 9180(HPKE) 스타일의 KDF 적용
     */
    public static byte[] deriveHybridSessionKey(
            byte[] classicalSharedSecret,   // X25519 결과
            byte[] pqcSharedSecret,         // ML-KEM 결과
            byte[] label                    // 컨텍스트 바인딩용 레이블
    ) throws Exception {

        // 두 공유 비밀 연결
        byte[] combined = new byte[classicalSharedSecret.length + pqcSharedSecret.length];
        System.arraycopy(classicalSharedSecret, 0, combined, 0, classicalSharedSecret.length);
        System.arraycopy(pqcSharedSecret, 0, combined, classicalSharedSecret.length, pqcSharedSecret.length);

        // HKDF-Extract: 의사난수 키 생성
        Mac hmac = Mac.getInstance("HmacSHA256");
        hmac.init(new SecretKeySpec(label, "HmacSHA256")); // label을 salt로 사용
        byte[] prk = hmac.doFinal(combined);

        // HKDF-Expand: 최종 32바이트 세션 키 도출
        hmac.init(new SecretKeySpec(prk, "HmacSHA256"));
        hmac.update("hybrid-tls-session-key".getBytes());
        hmac.update((byte) 0x01);
        return hmac.doFinal();
    }
}
```

### 3. Nginx + OpenSSL 3.5 기반 리버스 프록시 설정

Spring Boot 애플리케이션 앞에 Nginx를 두고 TLS 터미네이션을 처리하는 경우:

```nginx
server {
    listen 443 ssl;
    server_name example.com;

    ssl_certificate     /etc/ssl/certs/server.crt;
    ssl_certificate_key /etc/ssl/private/server.key;

    # TLS 1.3만 허용
    ssl_protocols TLSv1.3;

    # 하이브리드 그룹 우선 협상
    # X25519MLKEM768를 최우선으로, 폴백으로 x25519 설정
    ssl_ecdh_curve X25519MLKEM768:x25519:secp256r1;

    # 세션 설정 (PFS 보장)
    ssl_session_tickets off;
    ssl_session_cache off;

    location / {
        proxy_pass http://localhost:8080;
        proxy_set_header X-Forwarded-Proto https;
    }
}
```

```bash
# Nginx가 사용 중인 OpenSSL 버전 및 지원 그룹 확인
nginx -V 2>&1 | grep OpenSSL
openssl list -kem-algorithms | grep -i kyber
```

## 주의사항 및 트레이드오프

### 성능 오버헤드

ML-KEM은 기존 ECC 대비 핸드셰이크에서 추가 비용이 발생한다.

| 항목 | X25519 | ML-KEM-768 | X25519MLKEM768 (하이브리드) |
|------|--------|------------|--------------------------|
| 공개키 크기 | 32 B | 1,184 B | ~1,216 B |
| 암호문 크기 | 32 B | 1,088 B | ~1,120 B |
| KeyGen 속도 | 매우 빠름 | 빠름 | 빠름 |
| TLS 핸드셰이크 추가 RTT | 없음 | 없음 | 없음 |

키 자체의 크기가 크기 때문에 TLS `ClientHello`와 `ServerHello` 메시지 크기가 증가하고, 이는 **TCP 초기 윈도우를 초과할 가능성**이 있다. 특히 기존 TLS 레코드 분할 설정이 최소화된 환경에서는 추가 RTT가 발생할 수 있다.

**대응 방안:**
- HTTP/3(QUIC) 환경에서는 UDP 기반이므로 영향이 다름을 고려할 것
- `ssl_buffer_size`나 TCP 초기 윈도우(`initcwnd`) 조정을 검토
- 서버 측 세션 재사용(Session Resumption)으로 반복 핸드셰이크 비용 절감

### 알고리즘 민첩성(Crypto Agility) 설계

PQC 표준은 아직 진화 중이다. Kyber가 ML-KEM으로 표준화되었지만, NIST Round 4 후보들(BIKE, HQC, McEliece 등)의 결과에 따라 추가 알고리즘이 등장할 수 있다. 따라서 알고리즘을 코드에 하드코딩하지 않고 **설정으로 분리**하는 것이 중요하다.

```java
// 나쁜 예: 알고리즘 하드코딩
MLKEMKeyPairGenerator keyGen = new MLKEMKeyPairGenerator();
keyGen.init(new MLKEMKeyGenerationParameters(rng, MLKEMParameters.ml_kem_768));

// 좋은 예: 설정 기반 팩토리 패턴
@Component
public class KemAlgorithmFactory {
    
    @Value("${crypto.kem.algorithm:ML-KEM-768}")
    private String kemAlgorithm;

    public KemParameters getParameters() {
        return switch (kemAlgorithm) {
            case "ML-KEM-512"  -> MLKEMParameters.ml_kem_512;
            case "ML-KEM-768"  -> MLKEMParameters.ml_kem_768;
            case "ML-KEM-1024" -> MLKEMParameters.ml_kem_1024;
            default -> throw new IllegalArgumentException("지원하지 않는 KEM: " + kemAlgorithm);
        };
    }
}
```

### 클라이언트 호환성

모든 클라이언트가 하이브리드 그룹을 지원하지는 않는다. 그룹 협상 실패 시 TLS 핸드셰이크 자체가 실패할 수 있으므로, 반드시 **폴백 그룹**을 함께 설정해야 한다.

```
# 권장 그룹 우선순위 설정
X25519MLKEM768 → x25519 → secp256r1 → secp384r1
```

레거시 클라이언트(JDK 11 미만, 구형 모바일 앱 등)를 지원해야 한다면 TLS 1.2 + 클래식 스위트를 병행 유지하되, 별도 포트나 SNI 라우팅으로 분리하는 것을 고려하라.

### 인증서와 서명 알고리즘

키 교환을 하이브리드화하더라도 **서버 인증서 서명 알고리즘이 여전히 RSA/ECDSA**라면, 공격자는 서버 인증서 자체를 위조할 수 있다. 완전한 PQC 마이그레이션을 위해서는 ML-DSA 기반 인증서도 함께 고려해야 하지만, 현재 공개 CA 인프라는 아직 PQC 인증서를 발급하지 않는다. 따라서 단계적 접근이 현실적이다:

1. **1단계**: 하이브리드 키 교환 도입 (HNDL 위협 대응)
2. **2단계**: 내부 PKI에서 ML-DSA 인증서 테스트
3. **3단계**: CA 생태계 성숙 후 프로덕션 PQC 인증서 배포

## 정리

양자내성암호로의 전환은 단순히 알고리즘 교체가 아니라 전체 암호 생태계의 마이그레이션이다. 지금 당장 완전한 PQC 전환이 어렵다면, **TLS 하이브리드 키 교환**이 가장 현실적이고 안전한 첫 번째 단계다.

핵심 체크리스트를 정리하면 다음과 같다:

- [ ] OpenSSL 3.5+ 또는 BoringSSL 최신 버전으로 인프라 업그레이드
- [ ] Nginx/HAProxy의 `ssl_ecdh_curve`에 `X25519MLKEM768` 추가 (폴백 포함)
- [ ] Java 환경이라면 Bouncy Castle 최신 버전으로 PQC KEM 실험
- [ ] TLS 핸드셰이크 크기 증가에 따른 네트워크 레이어 검토 (TCP 초기 윈도우, MTU)
- [ ] 알고리즘을 설정으로 분리해 Crypto Agility 확보
- [ ] 클라이언트 호환성 매트릭스 점검 및 폴백 그룹 설정
- [ ] 장기적으로 PQC 서명 알고리즘(ML-DSA) 마이그레이션 로드맵 수립

HNDL 공격은 지금 이 순간에도 이루어지고 있을 수 있다. 민감한 데이터를 다루는 서비스라면 하이브리드 키 교환 도입을 더 이상 미루지 않는 것이 좋다.
