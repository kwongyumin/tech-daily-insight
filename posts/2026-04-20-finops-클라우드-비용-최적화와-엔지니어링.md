# FinOps 클라우드 비용 최적화와 엔지니어링

## 개요

클라우드를 도입한 기업이라면 누구나 한 번쯤 "이번 달 AWS 비용이 왜 이렇게 많이 나왔지?"라는 질문에 직면한 경험이 있을 것이다. 클라우드의 유연성과 확장성은 분명한 장점이지만, 그 이면에는 **예측하기 어려운 비용 구조**라는 함정이 숨어 있다.

**FinOps(Financial Operations)**는 이 문제를 해결하기 위해 등장한 문화적, 운영적 프레임워크다. 단순히 비용을 줄이는 것이 목표가 아니라, 엔지니어링 팀과 재무 팀, 비즈니스 팀이 협력하여 클라우드 지출을 **비즈니스 가치에 최대한 정렬**시키는 것을 목표로 한다.

이 글에서는 FinOps의 핵심 개념과 함께, 실무에서 바로 적용할 수 있는 엔지니어링 전략과 코드 예제를 소개한다.

## 핵심 개념

### FinOps의 세 가지 단계

FinOps Foundation에서 정의한 FinOps 성숙도 모델은 세 단계로 구성된다.

| 단계 | 설명 |
|------|------|
| **Crawl (탐색)** | 비용 가시성 확보, 기본 태깅 전략 수립 |
| **Walk (적용)** | 비용 할당, 예산 알림, 최적화 시작 |
| **Run (최적화)** | 자동화된 비용 최적화, 실시간 의사결정 |

대부분의 조직이 Crawl 단계에서 머무르는 이유는 **비용의 주체가 명확하지 않기 때문**이다. 누가 어떤 리소스를 사용하는지 파악하지 못하면 최적화 자체가 불가능하다.

### 비용 가시성: 태깅 전략

비용 최적화의 첫 번째 단계는 **태깅(Tagging)**이다. 모든 클라우드 리소스에 일관된 태그를 부착해야 팀별, 서비스별, 환경별 비용을 추적할 수 있다.

```
# 권장 태그 스키마 예시
Environment: production | staging | development
Team:        platform | backend | frontend | data
Service:     user-service | payment-service | recommendation
CostCenter:  engineering | marketing | operations
Project:     project-alpha | project-beta
```

이 태그 스키마를 Terraform으로 강제하는 방법은 아래와 같다.

```hcl
# terraform/modules/common/variables.tf
variable "required_tags" {
  type = object({
    Environment = string
    Team        = string
    Service     = string
    CostCenter  = string
    Project     = string
  })

  validation {
    condition     = contains(["production", "staging", "development"], var.required_tags.Environment)
    error_message = "Environment must be one of: production, staging, development."
  }
}

# terraform/modules/common/main.tf
locals {
  common_tags = merge(var.required_tags, {
    ManagedBy   = "terraform"
    CreatedAt   = timestamp()
  })
}

resource "aws_instance" "app_server" {
  ami           = var.ami_id
  instance_type = var.instance_type

  tags = local.common_tags
}
```

## 실전 예제

### 1. AWS Cost Explorer API로 비용 모니터링 자동화

Java/Spring 환경에서 AWS SDK를 활용해 팀별 비용을 조회하고 슬랙으로 알림을 보내는 예제다.

```java
// build.gradle
dependencies {
    implementation 'software.amazon.awssdk:costexplorer:2.21.0'
    implementation 'com.slack.api:slack-api-client:1.36.1'
}
```

```java
@Service
@Slf4j
public class CostMonitoringService {

    private final CostExplorerClient costExplorerClient;
    private final SlackNotificationService slackService;

    public CostMonitoringService(CostExplorerClient costExplorerClient,
                                  SlackNotificationService slackService) {
        this.costExplorerClient = costExplorerClient;
        this.slackService = slackService;
    }

    @Scheduled(cron = "0 0 9 * * MON") // 매주 월요일 오전 9시
    public void sendWeeklyCostReport() {
        LocalDate endDate = LocalDate.now();
        LocalDate startDate = endDate.minusDays(7);

        GetCostAndUsageRequest request = GetCostAndUsageRequest.builder()
            .timePeriod(DateInterval.builder()
                .start(startDate.toString())
                .end(endDate.toString())
                .build())
            .granularity(Granularity.DAILY)
            .groupBy(GroupDefinition.builder()
                .type(GroupDefinitionType.TAG)
                .key("Team")
                .build())
            .metrics("UnblendedCost")
            .build();

        GetCostAndUsageResponse response = costExplorerClient.getCostAndUsage(request);

        Map<String, BigDecimal> teamCosts = aggregateByTeam(response);
        String report = buildSlackReport(teamCosts, startDate, endDate);

        slackService.sendMessage("#finops-alerts", report);
    }

    private Map<String, BigDecimal> aggregateByTeam(GetCostAndUsageResponse response) {
        Map<String, BigDecimal> teamCosts = new TreeMap<>();

        response.resultsByTime().forEach(result ->
            result.groups().forEach(group -> {
                String teamName = group.keys().isEmpty() ? "Untagged" : group.keys().get(0);
                BigDecimal cost = new BigDecimal(
                    group.metrics().get("UnblendedCost").amount()
                );
                teamCosts.merge(teamName, cost, BigDecimal::add);
            })
        );

        return teamCosts;
    }

    private String buildSlackReport(Map<String, BigDecimal> teamCosts,
                                     LocalDate start, LocalDate end) {
        StringBuilder sb = new StringBuilder();
        sb.append(String.format("*📊 주간 클라우드 비용 리포트 (%s ~ %s)*\n\n", start, end));

        BigDecimal total = BigDecimal.ZERO;
        for (Map.Entry<String, BigDecimal> entry : teamCosts.entrySet()) {
            sb.append(String.format("• *%s*: $%.2f\n", entry.getKey(), entry.getValue()));
            total = total.add(entry.getValue());
        }

        sb.append(String.format("\n*총 비용: $%.2f*", total));
        return sb.toString();
    }
}
```

### 2. 유휴 리소스 자동 감지 및 정리

운영 중에 생성되고 잊혀지는 리소스들이 비용 누수의 주범이다. 아래는 EC2 인스턴스의 CPU 사용률을 모니터링하여 유휴 인스턴스를 감지하는 예제다.

```java
@Component
@Slf4j
public class IdleResourceDetector {

    private static final double CPU_THRESHOLD = 5.0; // 5% 미만이면 유휴 상태
    private static final int EVALUATION_DAYS = 7;

    private final CloudWatchClient cloudWatchClient;
    private final Ec2Client ec2Client;

    public List<IdleInstance> detectIdleInstances() {
        List<IdleInstance> idleInstances = new ArrayList<>();

        DescribeInstancesResponse instancesResponse = ec2Client.describeInstances(
            DescribeInstancesRequest.builder()
                .filters(Filter.builder()
                    .name("instance-state-name")
                    .values("running")
                    .build())
                .build()
        );

        instancesResponse.reservations().stream()
            .flatMap(r -> r.instances().stream())
            .forEach(instance -> {
                double avgCpu = getAverageCpuUtilization(instance.instanceId());
                if (avgCpu < CPU_THRESHOLD) {
                    String teamTag = instance.tags().stream()
                        .filter(t -> "Team".equals(t.key()))
                        .map(Tag::value)
                        .findFirst()
                        .orElse("Untagged");

                    idleInstances.add(IdleInstance.builder()
                        .instanceId(instance.instanceId())
                        .instanceType(instance.instanceTypeAsString())
                        .avgCpuUtilization(avgCpu)
                        .team(teamTag)
                        .estimatedMonthlySaving(estimateSaving(instance.instanceTypeAsString()))
                        .build());
                }
            });

        log.info("유휴 인스턴스 {}개 감지됨", idleInstances.size());
        return idleInstances;
    }

    private double getAverageCpuUtilization(String instanceId) {
        Instant endTime = Instant.now();
        Instant startTime = endTime.minus(EVALUATION_DAYS, ChronoUnit.DAYS);

        GetMetricStatisticsResponse response = cloudWatchClient.getMetricStatistics(
            GetMetricStatisticsRequest.builder()
                .namespace("AWS/EC2")
                .metricName("CPUUtilization")
                .dimensions(Dimension.builder()
                    .name("InstanceId")
                    .value(instanceId)
                    .build())
                .startTime(startTime)
                .endTime(endTime)
                .period(3600) // 1시간 단위
                .statistics(Statistic.AVERAGE)
                .build()
        );

        return response.datapoints().stream()
            .mapToDouble(Datapoint::average)
            .average()
            .orElse(0.0);
    }
}
```

### 3. Spot Instance 활용으로 비용 최대 90% 절감

배치 작업이나 내결함성이 있는 워크로드에는 Spot Instance를 활용하면 비용을 극적으로 절감할 수 있다.

```yaml
# kubernetes/spot-batch-job.yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: data-processing-job
  labels:
    team: data
    service: batch-processor
spec:
  template:
    spec:
      # Spot Node 우선 스케줄링
      affinity:
        nodeAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 80
            preference:
              matchExpressions:
              - key: eks.amazonaws.com/capacityType
                operator: In
                values:
                - SPOT
      tolerations:
      - key: "spot"
        operator: "Equal"
        value: "true"
        effect: "NoSchedule"
      # Spot 중단 시 체크포인트 저장을 위한 terminationGracePeriodSeconds
      terminationGracePeriodSeconds: 120
      containers:
      - name: batch-processor
        image: myapp/batch-processor:latest
        resources:
          requests:
            memory: "2Gi"
            cpu: "1000m"
          limits:
            memory: "4Gi"
            cpu: "2000m"
        env:
        - name: CHECKPOINT_ENABLED
          value: "true"
        - name: CHECKPOINT_S3_BUCKET
          value: "my-batch-checkpoints"
      restartPolicy: OnFailure
```

## 주의사항 및 트레이드오프

### ⚠️ 과도한 최적화의 위험

비용 절감이 목표가 되면 오히려 역효과가 날 수 있다. 몇 가지 안티패턴을 소개한다.

**1. 성능을 희생한 비용 절감**
- 데이터베이스 인스턴스를 과도하게 다운그레이드하면 쿼리 레이턴시가 증가하고, 결국 사용자 이탈로 이어질 수 있다.
- 비용 절감이 비즈니스 KPI에 미치는 영향을 항상 함께 측정해야 한다.

**2. Spot Instance 오남용**
- 스테이트풀(Stateful) 서비스나 데이터베이스에 Spot Instance를 사용하면 데이터 유실 위험이 있다.
- Spot Instance는 **무상태(Stateless) 워크로드**에만 적용할 것.

**3. Reserved Instance 과잉 구매**
- 1년 또는 3년 약정의 Reserved Instance는 사용하지 않으면 그냥 비용 낭비다.
- 실제 베이스라인 사용량을 6개월 이상 측정한 후에 구매를 결정해야 한다.

### 💡 트레이드오프 정리

| 전략 | 비용 절감 | 리스크 | 권장 대상 |
|------|-----------|--------|-----------|
| Spot Instance | 최대 90% | 인스턴스 중단 | 배치, CI/CD |
| Reserved Instance | 40~60% | 유연성 감소 | 프로덕션 베이스라인 |
| Auto Scaling 최적화 | 20~40% | 스케일링 지연 | 웹 서비스 |
| 스토리지 티어링 | 30~70% | 접근 속도 저하 | 콜드 데이터 |
| 멀티 리전 최적화 | 10~20% | 아키텍처 복잡도 | 글로벌 서비스 |

### 엔지니어링 팀의 역할 변화

FinOps가 정착되면 엔지니어는 단순히 기능을 개발하는 것을 넘어, **비용 효율성을 코드 품질의 일부**로 인식해야 한다. PR 리뷰 시 성능과 함께 예상 비용 영향도를 논의하는 문화가 필요하다.

```yaml
# PR 체크리스트 예시
- [ ] 기능 요구사항 충족
- [ ] 단위/통합 테스트 작성
- [ ] 코드 리뷰 완료
- [ ] 성능 영향도 분석
- [ ] 예상 클라우드 비용 영향도 기재 (Infracost 활용)
- [ ] 리소스 태깅 적용 확인
```

## 정리

FinOps는 단순한 비용 절감 캠페인이 아니다. 클라우드 시대의 새로운 엔지니어링 문화다. 핵심을 다시 정리하면 다음과 같다.

1. **가시성이 먼저다**: 태깅 전략을 수립하고 팀별 비용을 투명하게 공개하라.
2. **자동화로 지속성을 확보하라**: 비용 모니터링, 유휴 리소스 감지, 알림을 자동화하지 않으면 일회성 이벤트로 끝난다.
3. **엔지니어가 비용 오너십을 가져야 한다**: "비용은 재무팀 문제"가 아니라 코드를 배포하는 엔지니어가 직접 책임져야 한다.
4. **비즈니스 가치와 함께 측정하라**: 비용 절감이 매출이나 사용자 경험에 미치는 영향을 항상 함께 트래킹해야 한다.

클라우드 비용은 방치하면 기하급수적으로 늘어나지만, 올바른 FinOps 문화와 자동화 엔지니어링이 결합되면 **비용 효율과 기술적 민첩성을 동시에 달성**할 수 있다. 지금 당장 팀의 리소스 태깅 현황부터 점검해보자.
