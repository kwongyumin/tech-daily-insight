# 수천 개 서버 설정을 일관되게 관리하는 설정 체계 설계

## 개요

서버가 10대일 때는 SSH로 접속해서 설정 파일을 직접 수정해도 큰 문제가 없다. 하지만 수백, 수천 대의 서버를 운영하는 환경에서는 그 순간 모든 것이 달라진다. 한 서버의 nginx.conf가 다른 서버와 다르고, 환경 변수가 누락된 인스턴스가 조용히 오작동하고, 새벽 3시에 "왜 이 서버만 다르게 동작하죠?"라는 알람을 받게 된다.

이 글은 수천 개의 서버 설정을 **일관되고 추적 가능하며 자동화된 방식으로 관리**하기 위한 설정 체계(Configuration Management System)를 설계하는 방법을 다룬다. 특정 도구의 튜토리얼이 아니라, 어떤 도구를 선택하든 반드시 고려해야 할 설계 원칙과 실전 패턴에 초점을 맞춘다.

---

## 핵심 개념

### 1. 설정의 세 가지 계층

대규모 환경에서 설정은 하나의 평탄한 구조가 아니라 **계층적으로 구성**되어야 한다.

```
Global (전사 공통)
  └── Environment (dev / staging / prod)
        └── Region (ap-northeast-2 / us-east-1)
              └── Service (order-service / payment-service)
                    └── Instance (서버 개별 오버라이드)
```

상위 계층의 값이 기본값이 되고, 하위 계층에서 필요한 경우에만 오버라이드한다. 이 계층 구조를 명확히 정의하지 않으면 "어느 설정이 최종적으로 적용되는 값인가?"를 추적하기가 매우 어려워진다.

### 2. 단일 진실 공급원 (Single Source of Truth)

설정의 출처가 여러 곳에 분산되면 반드시 불일치가 발생한다. 모든 서버의 설정은 **하나의 중앙 저장소에서 파생**되어야 한다.

- 설정 파일은 Git 저장소에서 버전 관리
- 서버는 "설정을 가지는" 것이 아니라 "설정을 pull하거나 받아오는" 존재
- 사람이 서버에 직접 접속해서 설정을 바꾸는 행위(Snowflake 서버 생성)를 원천 차단

### 3. Idempotency (멱등성)

설정 적용 작업은 몇 번을 실행해도 동일한 결과를 보장해야 한다. Ansible의 `state: present`, Terraform의 선언적 모델이 이 원칙을 구현한 대표 사례다. 멱등성이 보장되지 않으면 자동화 스크립트를 안심하고 반복 실행할 수 없다.

### 4. 드리프트 감지 (Configuration Drift Detection)

시간이 지날수록 실제 서버 상태와 선언된 설정 간의 차이(드리프트)가 발생한다. 이를 주기적으로 감지하고 교정하는 메커니즘이 없으면 설정 체계는 점점 신뢰를 잃는다.

## 실전 예제

### 계층적 설정 구조 — Ansible 기반

Ansible을 사용한다면 group_vars와 host_vars를 활용해 계층 구조를 구현할 수 있다.

```
inventory/
├── group_vars/
│   ├── all.yml               # 전사 공통
│   ├── prod.yml              # prod 환경
│   ├── prod_ap.yml           # prod + ap 리전
│   └── order_service.yml     # 특정 서비스
├── host_vars/
│   └── server-01.yml         # 개별 서버 오버라이드 (최소화)
└── hosts.ini
```

```yaml
# group_vars/all.yml
ntp_servers:
  - 169.254.169.123
log_level: "INFO"
max_open_files: 65536

# group_vars/prod.yml
log_level: "WARN"          # prod에서는 WARN으로 오버라이드
max_open_files: 131072

# group_vars/order_service.yml
app_port: 8080
jvm_heap_size: "4g"
db_pool_size: 20
```

```yaml
# roles/common/tasks/main.yml
- name: Set system limits
  pam_limits:
    domain: "*"
    limit_type: "{{ item.type }}"
    limit_item: nofile
    value: "{{ max_open_files }}"
  loop:
    - { type: soft }
    - { type: hard }

- name: Configure NTP
  template:
    src: chrony.conf.j2
    dest: /etc/chrony.conf
    owner: root
    mode: '0644'
  notify: restart chronyd
```

### 설정 드리프트 감지 — Python 스크립트 예제

서버의 실제 상태를 주기적으로 체크하고 기준값과 비교하는 간단한 스크립트다.

```python
import subprocess
import yaml
import json
from dataclasses import dataclass
from typing import Dict, Any

@dataclass
class DriftReport:
    host: str
    key: str
    expected: Any
    actual: Any

def get_actual_config(host: str) -> Dict[str, Any]:
    """실제 서버에서 현재 설정값을 수집"""
    commands = {
        "max_open_files": "ulimit -n",
        "ntp_server": "chronyc sources | grep '^\\*' | awk '{print $2}'",
        "java_version": "java -version 2>&1 | head -1",
    }
    result = {}
    for key, cmd in commands.items():
        output = subprocess.run(
            ["ssh", host, cmd],
            capture_output=True, text=True, timeout=10
        )
        result[key] = output.stdout.strip()
    return result

def detect_drift(expected: Dict[str, Any], actual: Dict[str, Any], host: str):
    """기대값과 실제값을 비교하여 드리프트 목록 반환"""
    drifts = []
    for key, expected_val in expected.items():
        actual_val = actual.get(key)
        if str(expected_val) != str(actual_val):
            drifts.append(DriftReport(
                host=host,
                key=key,
                expected=expected_val,
                actual=actual_val
            ))
    return drifts

def run_drift_check(inventory_file: str, baseline_file: str):
    with open(baseline_file) as f:
        baseline = yaml.safe_load(f)

    with open(inventory_file) as f:
        hosts = [line.strip() for line in f if line.strip()]

    all_drifts = []
    for host in hosts:
        actual = get_actual_config(host)
        drifts = detect_drift(baseline, actual, host)
        all_drifts.extend(drifts)

    if all_drifts:
        print(f"[DRIFT DETECTED] {len(all_drifts)} 건의 불일치 발견")
        for d in all_drifts:
            print(f"  Host: {d.host} | Key: {d.key} | Expected: {d.expected} | Actual: {d.actual}")
    else:
        print("[OK] 모든 서버 설정이 기준값과 일치합니다.")

if __name__ == "__main__":
    run_drift_check("inventory/hosts.txt", "baseline/prod.yml")
```

### GitOps 파이프라인 — GitHub Actions 예제

설정 변경이 Git 푸시로 시작되어 자동으로 서버에 적용되는 파이프라인이다.

```yaml
# .github/workflows/deploy-config.yml
name: Deploy Configuration

on:
  push:
    branches: [main]
    paths:
      - 'inventory/**'
      - 'roles/**'
      - 'group_vars/**'

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Ansible Lint
        run: |
          pip install ansible ansible-lint
          ansible-lint playbooks/site.yml

  diff:
    needs: lint
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Show config diff (check mode)
        run: |
          ansible-playbook playbooks/site.yml \
            --check --diff \
            -i inventory/prod/hosts.ini \
            --private-key ${{ secrets.SSH_PRIVATE_KEY }}

  deploy:
    needs: diff
    runs-on: ubuntu-latest
    environment: production  # 수동 승인 게이트
    steps:
      - uses: actions/checkout@v3
      - name: Apply configuration
        run: |
          ansible-playbook playbooks/site.yml \
            -i inventory/prod/hosts.ini \
            --private-key ${{ secrets.SSH_PRIVATE_KEY }} \
            --forks 50 \
            -e "deploy_version=${{ github.sha }}"
      - name: Notify Slack
        uses: slackapi/slack-github-action@v1
        with:
          payload: '{"text": "✅ Config deployed: ${{ github.sha }}"}'
        env:
          SLACK_WEBHOOK_URL: ${{ secrets.SLACK_WEBHOOK_URL }}
```

## 주의사항 및 트레이드오프

### 1. 시크릿과 일반 설정의 분리

설정 저장소에 DB 패스워드, API 키 같은 민감 정보를 평문으로 커밋하는 실수를 흔히 저지른다. 반드시 **Vault(HashiCorp), AWS Secrets Manager, 혹은 git-crypt** 같은 별도 시크릿 관리 체계를 사용하고, 설정 파일에는 "어디서 가져올 것인가"만 기록해야 한다.

```yaml
# BAD - 절대 하지 말 것
db_password: "P@ssw0rd1234"

# GOOD - 참조만 보관
db_password: "{{ lookup('aws_ssm', '/prod/order-service/db-password') }}"
```

### 2. 적용 속도 vs. 안전성 트레이드오프

`--forks` 값을 높이면 수천 대 서버에 빠르게 설정을 배포할 수 있지만, 설정 오류가 있을 경우 그 오류도 빠르게 전파된다. 프로덕션 배포에는 **카나리 배포 패턴**을 적용해 소수 서버에 먼저 적용하고, 메트릭 이상이 없을 때 전체로 확산하는 전략이 권장된다.

```
1단계: canary 그룹 (전체의 1~5%) 적용 → 모니터링 10분
2단계: 이상 없으면 staging 그룹 (25%) 확장 → 모니터링 5분
3단계: 나머지 전체 적용
```

### 3. 풀(Pull) vs. 푸시(Push) 모델

| 방식 | 장점 | 단점 |
|------|------|------|
| Push (Ansible 방식) | 중앙에서 즉시 제어 가능 | 대상 서버가 많을수록 시간 증가 |
| Pull (Puppet, Chef 방식) | 에이전트가 주기적으로 자가 교정 | 에이전트 관리 오버헤드 발생 |

수천 대 환경에서는 보통 **Pull 모델이 드리프트 교정에 유리**하지만, 에이전트 설치와 버전 관리라는 추가 복잡성을 감수해야 한다. 조직의 운영 성숙도와 팀 규모를 고려해 선택해야 한다.

### 4. 테스트 환경 없는 자동화는 위험하다

설정 파이프라인에도 반드시 테스트 단계가 존재해야 한다. `ansible-lint`, `yamllint` 같은 정적 검사는 기본이고, Molecule이나 Test Kitchen을 사용해 가상 환경에서 Role을 실제 실행해보는 통합 테스트까지 갖추는 것이 이상적이다.

### 5. 긴급 패치와 프로세스 충돌

장애 상황에서 개발자가 서버에 직접 접속해 설정을 바꾸고 싶은 충동은 자연스럽다. 이를 무조건 막으면 현실적이지 않다. 대신 **긴급 변경 절차(Break-glass procedure)**를 명문화하고, 긴급 변경 후에는 반드시 Git에 반영하도록 프로세스를 수립해야 한다. 그렇지 않으면 다음 자동화 배포 시 긴급 패치가 롤백된다.

## 정리

수천 개 서버의 설정을 일관되게 관리하는 것은 단순히 "좋은 도구를 고르는 문제"가 아니다. 계층적 설정 구조, 단일 진실 공급원, 멱등성, 드리프트 감지라는 **네 가지 원칙이 체계의 근간**이 되어야 한다.

도구 선택(Ansible, Puppet, Chef, Terraform 등)은 그 다음 문제다. 어떤 도구를 선택하든 아래 체크리스트를 갖추었는지 확인하라.

- [ ] 모든 설정 변경은 Git 커밋에서 시작된다
- [ ] 환경별 계층 구조가 명확하게 정의되어 있다
- [ ] 시크릿은 별도 저장소(Vault 등)에서 관리된다
- [ ] 적용 전 --check/--diff 단계가 자동화 파이프라인에 포함되어 있다
- [ ] 드리프트를 주기적으로 감지하고 알림을 받는다
- [ ] 카나리 배포 혹은 단계적 롤아웃이 가능하다
- [ ] 긴급 변경 절차가 문서화되어 있다

설정 체계가 성숙해질수록 "서버를 관리한다"는 개념은 점점 사라지고, "선언된 상태를 유지한다"는 개념으로 전환된다. 그 전환점에 도달했을 때 운영 팀은 비로소 화재 진압이 아닌 시스템 개선에 집중할 수 있게 된다.
