# 외부 연동 테스트를 위한 Mock 서버 설계

## 개요

실무에서 외부 API와의 연동은 피할 수 없는 과제다. 결제 PG사, 메시지 발송 서비스, 소셜 로그인 제공자, 물류 추적 API 등 대부분의 서비스는 하나 이상의 외부 시스템에 의존한다. 문제는 이 외부 시스템들이 항상 테스트하기 좋은 환경을 제공하지는 않는다는 점이다.

- 외부 API의 Sandbox 환경이 불안정하거나 아예 존재하지 않는 경우
- 특정 에러 시나리오(타임아웃, 5xx, 비정상 응답)를 의도적으로 재현하기 어려운 경우
- 연동 비용이 테스트마다 발생하는 경우
- CI/CD 파이프라인에서 외부 의존성으로 인해 빌드가 불안정해지는 경우

이러한 상황에서 Mock 서버는 단순히 "테스트를 위한 가짜 서버"가 아니라, **개발 생산성과 서비스 안정성을 동시에 높이는 핵심 인프라**로 기능한다. 이 글에서는 Mock 서버의 설계 전략과 실전 구현 방법을 다룬다.

---

## 핵심 개념

### Mock 서버의 역할과 범위

Mock 서버는 실제 외부 시스템의 HTTP 엔드포인트를 흉내 내어, 클라이언트(우리 서비스)가 실제 외부 시스템 없이도 연동 로직을 검증할 수 있게 해준다.

크게 두 가지 방식으로 구분할 수 있다.

| 방식 | 설명 | 적합한 상황 |
|---|---|---|
| **In-process Mock** | 테스트 코드 내부에서 HTTP 클라이언트를 가로채는 방식 (WireMock embedded 등) | 단위/통합 테스트 |
| **Out-of-process Mock** | 별도의 프로세스로 실행되는 독립 Mock 서버 | 로컬 개발, E2E 테스트, CI 환경 |

두 방식은 상호 배타적이 아니다. 일반적으로 단위 테스트에서는 In-process Mock을, 개발 환경 전체에 걸친 통합 테스트나 로컬 개발 편의성을 위해서는 Out-of-process Mock을 함께 운용한다.

### Contract 기반 Mock의 중요성

Mock 서버를 단순히 "예상되는 응답을 하드코딩한 서버"로만 운용하면, 실제 외부 API의 스펙이 변경되었을 때 Mock과 실제 사이의 괴리(drift)가 발생한다. 이를 방지하기 위해 **Consumer-Driven Contract Testing** 개념을 도입하면 좋다.

Pact와 같은 도구를 사용하면, 소비자(Consumer)가 기대하는 계약(Contract)을 명세하고, 실제 외부 API(Provider)가 그 계약을 만족하는지 자동으로 검증할 수 있다. 단, 외부 서드파티 API는 Provider 측의 협조가 필요하므로 내부 MSA 간 연동에 더 적합하다.

## 실전 예제

### 1. WireMock을 활용한 In-process Mock

Spring Boot 프로젝트에서 가장 많이 쓰이는 방식이다.

**의존성 추가 (Gradle)**

```groovy
testImplementation 'org.springframework.cloud:spring-cloud-contract-wiremock:4.1.0'
// 또는 직접 WireMock 사용
testImplementation 'com.github.tomakehurst:wiremock-jre8:2.35.0'
```

**테스트 코드 예시 - 결제 API 연동**

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@AutoConfigureWireMock(port = 0) // 랜덤 포트 사용
class PaymentServiceIntegrationTest {

    @Autowired
    private PaymentService paymentService;

    @Value("${wiremock.server.port}")
    private int wireMockPort;

    @Test
    void 결제_승인_성공_시나리오() {
        // given
        stubFor(post(urlEqualTo("/v1/payments/approve"))
            .withHeader("Authorization", matching("Bearer .+"))
            .withRequestBody(matchingJsonPath("$.orderId"))
            .willReturn(aResponse()
                .withStatus(200)
                .withHeader("Content-Type", "application/json")
                .withBodyFile("payment/approve-success.json")));

        PaymentRequest request = PaymentRequest.builder()
            .orderId("ORDER-001")
            .amount(50000)
            .build();

        // when
        PaymentResult result = paymentService.approve(request);

        // then
        assertThat(result.isSuccess()).isTrue();
        assertThat(result.getTransactionId()).isNotBlank();
    }

    @Test
    void 결제_API_타임아웃_발생_시_폴백_처리() {
        // given - 타임아웃 시나리오 재현
        stubFor(post(urlEqualTo("/v1/payments/approve"))
            .willReturn(aResponse()
                .withStatus(200)
                .withFixedDelay(5000))); // 5초 지연

        PaymentRequest request = PaymentRequest.builder()
            .orderId("ORDER-002")
            .amount(10000)
            .build();

        // when & then - 타임아웃 후 폴백 동작 확인
        assertThatThrownBy(() -> paymentService.approve(request))
            .isInstanceOf(PaymentTimeoutException.class);
    }
}
```

**응답 파일 (src/test/resources/__files/payment/approve-success.json)**

```json
{
  "transactionId": "TXN-20240101-001",
  "status": "APPROVED",
  "approvedAt": "2024-01-01T10:00:00Z",
  "amount": 50000
}
```

### 2. 독립 실행형 Mock 서버 구성

로컬 개발 환경 전체에서 활용하려면 Docker 기반으로 Out-of-process Mock 서버를 구성하는 것이 효과적이다.

**docker-compose.yml**

```yaml
version: '3.8'

services:
  mock-payment-api:
    image: wiremock/wiremock:3.3.1
    ports:
      - "8081:8080"
    volumes:
      - ./mocks/payment:/home/wiremock/mappings
      - ./mocks/payment/__files:/home/wiremock/__files
    command:
      - "--global-response-templating"
      - "--verbose"

  mock-notification-api:
    image: wiremock/wiremock:3.3.1
    ports:
      - "8082:8080"
    volumes:
      - ./mocks/notification:/home/wiremock/mappings
```

**mapping 파일 (mocks/payment/approve.json)**

```json
{
  "request": {
    "method": "POST",
    "url": "/v1/payments/approve",
    "headers": {
      "Authorization": {
        "matches": "Bearer .+"
      }
    }
  },
  "response": {
    "status": 200,
    "headers": {
      "Content-Type": "application/json"
    },
    "jsonBody": {
      "transactionId": "{{randomValue type='UUID'}}",
      "status": "APPROVED",
      "approvedAt": "{{now format='yyyy-MM-dd\\'T\\'HH:mm:ss\\'Z\\''}}"
    }
  }
}
```

응답 템플릿을 사용하면 UUID나 타임스탬프처럼 매번 달라져야 하는 값도 동적으로 생성할 수 있다.

### 3. 시나리오 기반 상태 관리

실제 외부 API는 상태를 가지는 경우가 많다. 예를 들어 첫 번째 호출에서는 "처리 중" 응답을, 두 번째 호출에서는 "완료" 응답을 반환해야 하는 폴링 시나리오가 대표적이다.

```java
@Test
void 비동기_결제_폴링_시나리오() {
    // 첫 번째 조회: 처리 중
    stubFor(get(urlEqualTo("/v1/payments/TXN-001/status"))
        .inScenario("Payment Processing")
        .whenScenarioStateIs(STARTED)
        .willReturn(aResponse()
            .withStatus(200)
            .withBody("{\"status\": \"PROCESSING\"}"))
        .willSetStateTo("COMPLETED"));

    // 두 번째 조회: 완료
    stubFor(get(urlEqualTo("/v1/payments/TXN-001/status"))
        .inScenario("Payment Processing")
        .whenScenarioStateIs("COMPLETED")
        .willReturn(aResponse()
            .withStatus(200)
            .withBody("{\"status\": \"APPROVED\", \"transactionId\": \"TXN-001\"}")));

    // when
    PaymentStatus finalStatus = paymentService.pollUntilComplete("TXN-001");

    // then
    assertThat(finalStatus).isEqualTo(PaymentStatus.APPROVED);
    verify(2, getRequestedFor(urlEqualTo("/v1/payments/TXN-001/status")));
}
```

### 4. 애플리케이션 설정 분리

Mock 서버와 실제 외부 API의 URL을 환경에 따라 쉽게 전환할 수 있도록 설정을 분리한다.

```yaml
# application-local.yml
external:
  payment:
    base-url: http://localhost:8081
    timeout: 30s
  notification:
    base-url: http://localhost:8082

# application-prod.yml
external:
  payment:
    base-url: https://api.realpayment.com
    timeout: 10s
  notification:
    base-url: https://api.realnotification.com
```

## 주의사항 및 트레이드오프

### Mock과 실제 API 사이의 Drift

가장 큰 위험은 Mock이 실제 API와 달라지는 것이다. 이를 방지하기 위한 전략은 다음과 같다.

**1. 정기적인 Contract 검증**: Mock의 응답 스펙을 실제 API 문서(OpenAPI 스펙 등)와 주기적으로 대조하는 프로세스를 팀 내에 정착시킨다.

**2. Recording 모드 활용**: WireMock의 Record 기능을 사용하면 실제 외부 API를 한 번 호출하여 그 요청/응답을 그대로 mapping 파일로 저장할 수 있다. 이를 초기 세팅이나 스펙 업데이트 시 활용한다.

```bash
# WireMock을 proxy + record 모드로 실행
java -jar wiremock-standalone.jar \
  --proxy-all="https://api.realpayment.com" \
  --record-mappings \
  --port 8081
```

**3. API 버전 변경 알림 체계**: 외부 API 제공자의 changelog 구독, Webhook 알림 등을 통해 스펙 변경을 조기에 감지한다.

### 테스트의 현실성 vs 복잡성

Mock이 너무 단순하면 실제 환경과의 괴리가 커지고, 너무 정교하면 Mock 자체가 유지보수 부담이 된다. 아래 기준으로 적정선을 잡는 것이 좋다.

- **해피 패스(정상 흐름)**: 가장 현실적인 응답을 Mock에 반영
- **에러 시나리오**: 실제로 발생 가능한 에러 코드와 메시지를 정확히 재현 (4xx, 5xx, 타임아웃, 네트워크 오류)
- **엣지 케이스**: 비즈니스 로직상 중요한 경계값(빈 배열, null 필드 등)에 한정하여 추가

### Mock 서버를 프로덕션에 혼용하는 위험

환경 변수나 feature flag로 Mock/실제를 전환하는 구조에서, 운영 환경에 Mock URL이 잘못 설정되는 사고가 발생할 수 있다. 이를 방지하기 위해:

- Mock URL은 `localhost` 또는 내부 도메인으로만 고정
- 운영 프로파일에서는 Mock 관련 빈이 활성화되지 않도록 `@Profile` 등으로 격리
- 배포 전 설정값 검증 로직을 CI 파이프라인에 포함

### CI/CD 환경에서의 고려사항

GitHub Actions, Jenkins 등의 CI 환경에서 Docker Compose를 활용한 Mock 서버를 띄울 때는 서비스 기동 순서와 헬스체크를 반드시 처리해야 한다.

```yaml
# .github/workflows/test.yml 일부
services:
  mock-payment-api:
    image: wiremock/wiremock:3.3.1
    ports:
      - 8081:8080
    options: >-
      --health-cmd "curl -f http://localhost:8080/__admin/health || exit 1"
      --health-interval 5s
      --health-timeout 3s
      --health-retries 5
```

## 정리

외부 연동 테스트를 위한 Mock 서버 설계는 단순히 "가짜 응답 반환"을 넘어, 개발팀의 테스트 전략 전반과 맞닿아 있다.

| 목적 | 권장 방식 |
|---|---|
| 단위/통합 테스트 자동화 | WireMock Embedded (In-process) |
| 로컬 개발 환경 | Docker Compose 기반 Out-of-process Mock |
| 에러/타임아웃 시나리오 | WireMock의 Fault, Delay 기능 |
| 상태 기반 시나리오 | WireMock Stateful Scenarios |
| Contract 검증 | Pact (내부 MSA), 주기적 스펙 대조 (외부 API) |

핵심은 **Mock의 신뢰성을 유지하는 프로세스**를 만드는 것이다. 아무리 정교한 Mock 서버도 실제 API와의 동기화가 깨지면 오히려 거짓된 안정감을 주는 함정이 된다. 테스트가 통과하더라도 실제 연동에서 실패하는 상황은 Mock의 가장 큰 역설이다.

이를 위해 Mock 파일을 코드와 함께 버전 관리하고, 실제 외부 API 호출 결과로 주기적으로 갱신하며, 팀 내에 "Mock 업데이트"를 하나의 개발 프로세스로 정착시키는 것이 장기적으로 가장 중요한 과제다.
