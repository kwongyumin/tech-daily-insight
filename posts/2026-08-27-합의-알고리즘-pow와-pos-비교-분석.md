# 합의 알고리즘 PoW와 PoS 비교 분석

## 개요

블록체인 네트워크에서 **합의 알고리즘(Consensus Algorithm)**은 분산된 노드들이 단일한 진실(single source of truth)에 동의하는 메커니즘이다. 중앙 관리자 없이 수천 개의 노드가 동일한 장부를 유지할 수 있는 것도 바로 이 합의 알고리즘 덕분이다.

현재 가장 널리 사용되는 두 가지 합의 방식은 **작업 증명(Proof of Work, PoW)**과 **지분 증명(Proof of Stake, PoS)**이다. 비트코인이 PoW를 채택하고, 이더리움이 2022년 The Merge를 통해 PoS로 전환한 이후, 두 방식의 차이점과 트레이드오프에 대한 논의는 더욱 활발해졌다.

이 글에서는 중급 이상의 개발자를 대상으로 두 합의 알고리즘의 핵심 원리와 구현 관점에서의 차이를 분석하고, 실제 코드를 통해 각 메커니즘을 이해하는 시간을 갖는다.

---

## 핵심 개념

### Proof of Work (PoW)

PoW는 블록을 생성하기 위해 **컴퓨팅 파워**를 소모하는 방식이다. 채굴자(Miner)는 특정 조건(예: 해시값이 목표 난이도 이하)을 만족하는 **논스(nonce)** 값을 찾아야 한다.

핵심 특성:
- **난이도(Difficulty)**: 해시값이 특정 0 비트 수를 앞에 포함해야 함
- **51% 공격**: 네트워크 해시레이트의 51% 이상을 장악해야 공격 가능
- **에너지 집약적**: 대규모 전력 소비가 불가피
- **대표 체인**: Bitcoin, Litecoin, Monero

### Proof of Stake (PoS)

PoS는 블록 생성 권한을 **보유한 자산(스테이킹된 코인)**에 비례해 부여하는 방식이다. 검증자(Validator)는 담보로 코인을 잠그고(스테이킹), 무작위 또는 확률적으로 블록 생성 기회를 얻는다.

핵심 특성:
- **슬래싱(Slashing)**: 악의적 행동 시 스테이킹 자산 일부 몰수
- **검증자 선택**: 지분 크기, 랜덤성, 오래된 코인 나이 등 다양한 기준 적용
- **에너지 효율**: PoW 대비 약 99.95% 에너지 절감 (이더리움 재단 발표 기준)
- **대표 체인**: Ethereum 2.0, Cardano, Solana, Polkadot

## 실전 예제

### 1. PoW 핵심 로직 구현 (Java)

아래는 PoW의 해시 채굴 과정을 Java로 단순화하여 구현한 예제다.

```java
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.nio.charset.StandardCharsets;

public class ProofOfWork {

    private final int difficulty;

    public ProofOfWork(int difficulty) {
        this.difficulty = difficulty;
    }

    public String sha256(String input) {
        try {
            MessageDigest digest = MessageDigest.getInstance("SHA-256");
            byte[] hash = digest.digest(input.getBytes(StandardCharsets.UTF_8));
            StringBuilder hexString = new StringBuilder();
            for (byte b : hash) {
                String hex = Integer.toHexString(0xff & b);
                if (hex.length() == 1) hexString.append('0');
                hexString.append(hex);
            }
            return hexString.toString();
        } catch (NoSuchAlgorithmException e) {
            throw new RuntimeException(e);
        }
    }

    /**
     * 목표 난이도: 해시 앞 N자리가 모두 '0'이어야 함
     */
    public MiningResult mine(String blockData) {
        String target = "0".repeat(difficulty);
        long nonce = 0;
        long startTime = System.currentTimeMillis();

        while (true) {
            String input = blockData + nonce;
            String hash = sha256(input);

            if (hash.startsWith(target)) {
                long elapsed = System.currentTimeMillis() - startTime;
                return new MiningResult(nonce, hash, elapsed);
            }
            nonce++;
        }
    }

    public record MiningResult(long nonce, String hash, long elapsedMs) {}

    public static void main(String[] args) {
        // difficulty=4: 해시 앞 4자리가 "0000"
        ProofOfWork pow = new ProofOfWork(4);
        String blockData = "Block#1|PrevHash:0000abc|Tx:[Alice->Bob:10BTC]|Timestamp:1700000000";

        System.out.println("Mining started...");
        MiningResult result = pow.mine(blockData);

        System.out.printf("✅ Block Mined!%n");
        System.out.printf("   Nonce   : %d%n", result.nonce());
        System.out.printf("   Hash    : %s%n", result.hash());
        System.out.printf("   Time    : %d ms%n", result.elapsedMs());
    }
}
```

> **실행 포인트**: `difficulty` 값을 4→5→6으로 올려보면 채굴 시간이 지수적으로 증가하는 것을 확인할 수 있다. 이것이 바로 PoW의 계산 비용 구조다.

### 2. PoS 검증자 선택 로직 구현 (Java)

PoS에서는 스테이킹 지분에 비례한 가중 랜덤 선택으로 검증자를 선출한다.

```java
import java.util.*;

public class ProofOfStake {

    private final List<Validator> validators = new ArrayList<>();
    private final Random random = new Random();

    public void addValidator(String address, long stakedAmount) {
        validators.add(new Validator(address, stakedAmount));
    }

    /**
     * 가중 랜덤 선택 (Weighted Random Selection)
     * 스테이킹 비율에 따라 검증자 선출 확률 결정
     */
    public Validator selectValidator() {
        long totalStake = validators.stream()
                .mapToLong(Validator::stakedAmount)
                .sum();

        long randomPoint = (long) (random.nextDouble() * totalStake);
        long cumulative = 0;

        for (Validator v : validators) {
            cumulative += v.stakedAmount();
            if (randomPoint < cumulative) {
                return v;
            }
        }
        throw new IllegalStateException("Validator selection failed");
    }

    /**
     * 슬래싱: 악의적 행동 감지 시 스테이킹 자산 일부 몰수
     */
    public void slash(String address, double slashRatio) {
        validators.stream()
                .filter(v -> v.address().equals(address))
                .findFirst()
                .ifPresent(v -> {
                    long penalty = (long) (v.stakedAmount() * slashRatio);
                    v.setStakedAmount(v.stakedAmount() - penalty);
                    System.out.printf("⚠️  Slashed %s: -%d tokens (%.0f%%)%n",
                            address, penalty, slashRatio * 100);
                });
    }

    public record ValidatorInfo(String address, long stake, double probability) {}

    public List<ValidatorInfo> getDistribution() {
        long total = validators.stream().mapToLong(Validator::stakedAmount).sum();
        return validators.stream()
                .map(v -> new ValidatorInfo(
                        v.address(),
                        v.stakedAmount(),
                        (double) v.stakedAmount() / total * 100))
                .toList();
    }

    // Mutable Validator (슬래싱을 위해 가변 필드 허용)
    static class Validator {
        private final String address;
        private long stakedAmount;

        Validator(String address, long stakedAmount) {
            this.address = address;
            this.stakedAmount = stakedAmount;
        }

        String address() { return address; }
        long stakedAmount() { return stakedAmount; }
        void setStakedAmount(long amount) { this.stakedAmount = amount; }
    }

    public static void main(String[] args) {
        ProofOfStake pos = new ProofOfStake();
        pos.addValidator("Alice", 3200);   // 32 ETH 기준
        pos.addValidator("Bob",   6400);
        pos.addValidator("Carol", 9600);
        pos.addValidator("Dave",  800);

        System.out.println("=== Validator Distribution ===");
        pos.getDistribution().forEach(info ->
                System.out.printf("  %s: %d tokens (%.1f%%)%n",
                        info.address(), info.stake(), info.probability()));

        System.out.println("\n=== 10 Block Proposals ===");
        Map<String, Integer> counter = new HashMap<>();
        for (int i = 0; i < 10; i++) {
            ProofOfStake.Validator selected = pos.selectValidator();
            counter.merge(selected.address(), 1, Integer::sum);
            System.out.printf("  Block #%d → %s%n", i + 1, selected.address());
        }

        System.out.println("\n=== Selection Count ===");
        counter.forEach((addr, cnt) ->
                System.out.printf("  %s: %d times%n", addr, cnt));

        // 슬래싱 시뮬레이션
        System.out.println("\n=== Slashing Simulation ===");
        pos.slash("Bob", 0.10); // 10% 슬래싱
    }
}
```

## 주의사항 및 트레이드오프

### 보안 모델 차이

| 구분 | PoW | PoS |
|------|-----|-----|
| 공격 비용 | 물리적 하드웨어 + 전기료 | 스테이킹 자산 가치 |
| 51% 공격 | 해시레이트 51% 확보 | 지분 51% 확보 |
| 롱 레인지 공격 | 이론적으로 불가 | 체크포인트로 방어 필요 |
| 복구 가능성 | 포크로 복구 어려움 | 슬래싱으로 공격자 처벌 가능 |

### Nothing at Stake 문제

PoS 초기 설계에서는 **Nothing at Stake** 문제가 존재한다. 포크 상황에서 검증자가 잃을 것이 없기 때문에 여러 체인에 동시에 투표할 수 있다. 이를 해결하기 위해 현대 PoS는 **슬래싱 조건(Slashing Condition)**을 도입했다.

```
// Casper FFG (Ethereum)의 슬래싱 조건
1. Double Voting   : 동일 epoch의 두 다른 체크포인트에 투표
2. Surround Voting : 기존 투표를 감싸는 형태의 새 투표
→ 두 조건 위반 시 스테이킹 전액 몰수 + 네트워크 추방
```

### 탈중앙화 수준 비교

- **PoW**: 채굴 풀(Mining Pool) 집중화 문제. 현재 비트코인 해시레이트의 상위 3개 풀이 약 50% 이상 점유
- **PoS**: 대형 자본 보유자(Whale)와 스테이킹 서비스(Lido, Coinbase 등)로의 집중 우려. 이더리움 스테이킹에서 Lido의 비중이 30% 이상

### 검증자 진입 장벽

```
// Ethereum PoS 진입 조건
- 최소 스테이킹: 32 ETH (현재 약 1억원 이상)
- 검증자 노드 운영: 24/7 업타임 요구
- 슬래싱 리스크: 잘못된 설정 시 자산 손실
- 대안: 리퀴드 스테이킹(Lido stETH, rETH 등)으로 소액 참여 가능
```

### 파이널리티(Finality)

- **PoW**: 확률적 파이널리티. 6블록 확인 후 사실상 불가역으로 간주 (비트코인 기준 약 60분)
- **PoS**: 명시적 파이널리티. 이더리움은 2 epoch(약 12.8분) 후 finalized 상태 보장

## 정리

```
┌────────────────────┬──────────────────────┬──────────────────────┐
│ 항목               │ PoW                  │ PoS                  │
├────────────────────┼──────────────────────┼──────────────────────┤
│ 보안 근거          │ 컴퓨팅 파워          │ 경제적 지분          │
│ 에너지 소비        │ 매우 높음            │ 낮음 (99.95% 절감)   │
│ 파이널리티         │ 확률적 (~60분)       │ 명시적 (~13분)       │
│ 탈중앙화           │ 채굴 풀 집중 우려    │ 대형 스테이커 집중   │
│ 진입 장벽          │ ASIC 장비 비용       │ 최소 스테이킹 금액   │
│ 공격 복구          │ 어려움               │ 슬래싱으로 처벌 가능 │
│ 주요 체인          │ Bitcoin, Monero      │ Ethereum, Cardano    │
└────────────────────┴──────────────────────┴──────────────────────┘
```

PoW와 PoS는 각기 다른 철학과 보안 모델을 기반으로 한다. PoW는 **물리적 세계와의 연결**을 통해 공격 비용을 현실화하고, 수십 년에 걸쳐 검증된 보안성을 제공한다. 반면 PoS는 **에너지 효율과 빠른 파이널리티**를 무기로 이더리움 생태계를 중심으로 빠르게 확산되고 있다.

실무에서 블록체인 기반 서비스를 설계할 때는 단순히 어떤 알고리즘이 더 좋은지를 따지기보다, **서비스의 보안 요구사항, 트랜잭션 속도, 탈중앙화 수준**을 고려해 적합한 체인과 합의 메커니즘을 선택하는 것이 핵심이다.

앞으로는 PoW와 PoS를 넘어 **DPoS(Delegated PoS), PoH(Proof of History), PBFT 계열**의 BFT 합의 알고리즘도 점차 주목받고 있으므로, 이 방향으로도 학습을 이어가길 권장한다.
