# 서비스 메시 사이드카 패턴과 mTLS 자동화

## 개요

마이크로서비스 아키텍처가 보편화되면서 서비스 간 통신 보안은 더 이상 선택이 아닌 필수가 되었습니다. 수십, 수백 개의 서비스가 서로 통신하는 환경에서 각 애플리케이션 코드에 TLS 인증서 관리 로직을 심는 방식은 유지보수 지옥을 초래합니다. 이 문제를 우아하게 해결하는 것이 바로 **서비스 메시(Service Mesh)** 와 그 핵심 구성 요소인 **사이드카 패턴(Sidecar Pattern)** 입니다.

이번 포스팅에서는 사이드카 패턴의 동작 원리부터 Istio 기반 mTLS(mutual TLS) 자동화까지, 실무에서 바로 적용 가능한 예제와 함께 깊이 있게 다루겠습니다.

---

## 핵심 개념

### 사이드카 패턴이란?

사이드카 패턴은 메인 애플리케이션 컨테이너와 함께 동일한 Pod 내에 보조 컨테이너(사이드카)를 배치하는 디자인 패턴입니다. 사이드카는 애플리케이션과 네트워크 레이어 사이에 위치하여 모든 인바운드/아웃바운드 트래픽을 가로채고 처리합니다.

```
[서비스 A Pod]                     [서비스 B Pod]
┌─────────────────────┐            ┌─────────────────────┐
│  App Container      │            │  App Container      │
│  (localhost:8080)   │            │  (localhost:8080)   │
│         ↕           │            │         ↕           │
│  Envoy Sidecar      │ ──mTLS──▶  │  Envoy Sidecar      │
│  (iptables 리다이렉트)│            │  (iptables 리다이렉트)│
└─────────────────────┘            └─────────────────────┘
```

핵심은 **애플리케이션 코드 변경 없이** 네트워크 정책, 보안, 관찰 가능성을 인프라 레이어에서 처리한다는 점입니다.

### mTLS(Mutual TLS)란?

일반 TLS는 서버만 인증서를 제공하지만, mTLS는 클라이언트와 서버 **양방향**으로 인증서를 교환합니다. 이를 통해:

- **인증(Authentication)**: "이 요청이 정말 서비스 A에서 온 것인가?"
- **암호화(Encryption)**: 전송 중 데이터 도청 방지
- **무결성(Integrity)**: 데이터 위변조 탐지

를 동시에 보장합니다. 서비스 메시 환경에서는 인증서 발급, 갱신, 배포를 Control Plane이 자동으로 처리하므로 개발자는 비즈니스 로직에만 집중할 수 있습니다.

### Istio와 Envoy의 역할

- **Istio Control Plane (istiod)**: 인증서 발급(SPIFFE/X.509), Envoy 설정 동적 배포(xDS API)
- **Envoy Proxy**: 실제 트래픽 처리, mTLS 핸드셰이크 수행, 트래픽 정책 집행

## 실전 예제

### 1. 환경 설정: Istio 설치

```bash
# Istio 다운로드 및 설치 (v1.20 기준)
curl -L https://istio.io/downloadIstio | ISTIO_VERSION=1.20.0 sh -
cd istio-1.20.0
export PATH=$PWD/bin:$PATH

# demo 프로파일로 설치 (개발/테스트 환경)
istioctl install --set profile=demo -y

# 설치 검증
istioctl verify-install
```

### 2. 네임스페이스에 사이드카 자동 주입 활성화

```bash
# 사이드카 자동 주입 레이블 추가
kubectl label namespace default istio-injection=enabled

# 확인
kubectl get namespace default --show-labels
```

### 3. 샘플 서비스 배포

Spring Boot 기반 두 서비스를 배포합니다.

```yaml
# order-service.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
  namespace: default
spec:
  replicas: 2
  selector:
    matchLabels:
      app: order-service
      version: v1
  template:
    metadata:
      labels:
        app: order-service
        version: v1
    spec:
      containers:
      - name: order-service
        image: myregistry/order-service:latest
        ports:
        - containerPort: 8080
        env:
        - name: PAYMENT_SERVICE_URL
          value: "http://payment-service:8080"
---
apiVersion: v1
kind: Service
metadata:
  name: order-service
spec:
  selector:
    app: order-service
  ports:
  - port: 8080
    targetPort: 8080
```

배포 후 Pod를 확인하면 컨테이너가 2개(앱 + Envoy 사이드카)임을 볼 수 있습니다.

```bash
kubectl get pods
# NAME                             READY   STATUS    RESTARTS
# order-service-7d9f8b6c4-xk2mn   2/2     Running   0
#                                  ↑
#                             앱 + 사이드카
```

### 4. mTLS PeerAuthentication 정책 적용

```yaml
# mtls-policy.yaml
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: default
spec:
  mtls:
    mode: STRICT  # STRICT: mTLS 강제, PERMISSIVE: 선택적 허용
```

```bash
kubectl apply -f mtls-policy.yaml

# mTLS 동작 확인
istioctl x describe pod order-service-7d9f8b6c4-xk2mn
```

`STRICT` 모드에서는 사이드카 없이 직접 통신을 시도하면 연결이 거부됩니다. 마이그레이션 중에는 `PERMISSIVE` 모드를 사용해 점진적으로 전환하세요.

### 5. AuthorizationPolicy로 세밀한 접근 제어

mTLS로 신원은 확인했지만, 어떤 서비스가 어떤 엔드포인트에 접근할 수 있는지도 제어해야 합니다.

```yaml
# authz-policy.yaml
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: payment-service-authz
  namespace: default
spec:
  selector:
    matchLabels:
      app: payment-service
  action: ALLOW
  rules:
  - from:
    - source:
        principals:
          # SPIFFE URI 형식: 오직 order-service만 접근 허용
          - "cluster.local/ns/default/sa/order-service-account"
    to:
    - operation:
        methods: ["POST"]
        paths: ["/api/v1/payments/*"]
```

```yaml
# ServiceAccount 바인딩
apiVersion: v1
kind: ServiceAccount
metadata:
  name: order-service-account
  namespace: default
---
# Deployment에 serviceAccountName 지정
spec:
  template:
    spec:
      serviceAccountName: order-service-account
```

### 6. 인증서 상태 확인

```bash
# Envoy가 보유한 인증서 정보 확인
istioctl proxy-config secret order-service-7d9f8b6c4-xk2mn

# 출력 예시
# RESOURCE NAME     TYPE           STATUS     VALID CERT  SERIAL NUMBER
# default           Cert Chain     ACTIVE     true        ...
# ROOTCA            CA             ACTIVE     true        ...

# 상세 인증서 내용 (SPIFFE URI 확인)
istioctl proxy-config secret order-service-7d9f8b6c4-xk2mn -o json | \
  jq -r '.dynamicActiveSecrets[0].secret.tlsCertificate.certificateChain.inlineBytes' | \
  base64 -d | openssl x509 -text -noout | grep -A2 "Subject Alternative Name"

# 출력: URI:spiffe://cluster.local/ns/default/sa/order-service-account
```

### 7. Java 애플리케이션 코드 (변경 불필요)

사이드카 패턴의 진정한 가치는 **애플리케이션 코드가 일반 HTTP 통신만 하면 된다**는 점입니다.

```java
@Service
@RequiredArgsConstructor
public class OrderService {

    private final WebClient.Builder webClientBuilder;

    public Mono<PaymentResponse> processPayment(PaymentRequest request) {
        // 그냥 HTTP로 호출 - mTLS는 Envoy 사이드카가 자동 처리
        return webClientBuilder.build()
                .post()
                .uri("http://payment-service:8080/api/v1/payments/process")
                .bodyValue(request)
                .retrieve()
                .bodyToMono(PaymentResponse.class)
                .timeout(Duration.ofSeconds(5))
                .retryWhen(Retry.backoff(3, Duration.ofMillis(100)));
    }
}
```

```java
@Configuration
public class WebClientConfig {

    @Bean
    public WebClient.Builder webClientBuilder() {
        // TLS 설정 없음 - 사이드카가 처리
        return WebClient.builder()
                .defaultHeader(HttpHeaders.CONTENT_TYPE, MediaType.APPLICATION_JSON_VALUE);
    }
}
```

## 주의사항 및 트레이드오프

### ⚠️ 성능 오버헤드

사이드카는 추가적인 네트워크 홉을 발생시킵니다. 실측 기준으로 레이턴시가 **0.5ms~2ms** 가량 증가할 수 있습니다. 고빈도 내부 통신이 많은 서비스에서는 반드시 벤치마킹이 필요합니다.

```bash
# fortio로 레이턴시 측정
kubectl apply -f https://raw.githubusercontent.com/istio/istio/release-1.20/samples/httpbin/httpbin.yaml

kubectl exec -it fortio-pod -- fortio load \
  -c 50 -qps 1000 -t 60s \
  http://order-service:8080/api/orders
```

### ⚠️ 인증서 로테이션 주기

Istio 기본 인증서 유효기간은 **24시간**이며 자동 갱신됩니다. 하지만 갱신 실패 시나리오에 대한 알림 설정은 필수입니다.

```bash
# 인증서 만료 임박 모니터링 (Prometheus 쿼리)
# citadel_server_csr_count 메트릭으로 CSR 발급 추적
istioctl dashboard prometheus
```

### ⚠️ PERMISSIVE → STRICT 전환 전략

기존 레거시 서비스가 있다면 무작정 STRICT 모드를 적용하면 장애가 발생합니다.

```
1단계: 전체 네임스페이스 PERMISSIVE 설정
2단계: 서비스별 사이드카 주입 확인
3단계: 개별 서비스 수준에서 STRICT 테스트
4단계: 전체 네임스페이스 STRICT 전환
```

### ⚠️ 리소스 사용량

Envoy 사이드카는 Pod당 기본 **50~100Mi 메모리, 10m~100m CPU**를 추가로 소비합니다. 수백 개의 Pod가 있다면 클러스터 용량 계획에 반드시 반영해야 합니다.

```yaml
# 사이드카 리소스 제한 설정
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
spec:
  values:
    global:
      proxy:
        resources:
          requests:
            cpu: 10m
            memory: 40Mi
          limits:
            cpu: 200m
            memory: 128Mi
```

### ⚠️ 디버깅 복잡도 증가

트래픽이 Envoy를 거치기 때문에 장애 시 원인 파악이 복잡해집니다. `istioctl analyze`와 Kiali 대시보드를 적극 활용하세요.

```bash
# 설정 이상 분석
istioctl analyze --namespace default

# Kiali 대시보드로 트래픽 시각화
istioctl dashboard kiali
```

## 정리

서비스 메시와 사이드카 패턴은 마이크로서비스 환경에서 보안, 관찰 가능성, 트래픽 관리를 **애플리케이션 코드에서 분리**하는 강력한 방법입니다. 특히 mTLS 자동화를 통해:

| 항목 | 사이드카 패턴 도입 전 | 도입 후 |
|------|----------------------|---------|
| 인증서 관리 | 각 서비스 코드에 직접 구현 | Control Plane 자동화 |
| 서비스 신원 | 별도 인증 로직 필요 | SPIFFE URI 자동 발급 |
| 정책 변경 | 코드 배포 필요 | kubectl apply 즉시 반영 |
| 트래픽 암호화 | 선택적, 일관성 없음 | 전 구간 강제 암호화 |

실무 도입 시에는 **PERMISSIVE 모드로 시작해 점진적으로 STRICT 전환**, 리소스 오버헤드 모니터링, 그리고 팀 전체의 서비스 메시 개념 이해가 성공의 열쇠입니다.

사이드카 패턴은 단순한 보안 솔루션을 넘어, 인프라와 애플리케이션 관심사를 명확히 분리하는 아키텍처 철학의 실천입니다. 제로 트러스트 네트워크를 향한 여정의 첫걸음으로 서비스 메시 도입을 적극 검토해 보시길 권장합니다.
