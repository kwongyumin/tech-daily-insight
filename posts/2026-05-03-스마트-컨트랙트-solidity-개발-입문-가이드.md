# 스마트 컨트랙트 Solidity 개발 입문 가이드

## 개요

백엔드 개발자라면 한 번쯤 블록체인 기술에 관심을 가져봤을 것이다. 특히 이더리움(Ethereum) 생태계에서 스마트 컨트랙트는 "신뢰가 필요 없는 자동화 계약"을 코드로 구현하는 핵심 개념이다. Solidity는 이더리움 스마트 컨트랙트를 작성하기 위한 정적 타입(statically typed) 언어로, 문법은 JavaScript/C++에서 영향을 받았지만 실행 환경과 패러다임이 기존 서버 개발과는 근본적으로 다르다.

이 글에서는 실무 경험이 있는 개발자가 Solidity를 빠르게 이해하고 실전에 적용할 수 있도록, 핵심 개념부터 실용적인 예제 코드, 그리고 실무에서 반드시 알아야 할 트레이드오프까지 다룬다.

> **개발 환경**: Solidity ^0.8.20, Hardhat, OpenZeppelin Contracts

## 핵심 개념

### 1. EVM과 Gas

스마트 컨트랙트는 **EVM(Ethereum Virtual Machine)** 위에서 실행된다. EVM은 결정론적(deterministic) 환경으로, 동일한 입력에 항상 동일한 결과를 보장한다. 중요한 것은 모든 연산에 **Gas**라는 비용이 발생한다는 점이다.

- **SSTORE** (스토리지 쓰기): 약 20,000 gas (가장 비싼 연산 중 하나)
- **SLOAD** (스토리지 읽기): 약 2,100 gas
- **ADD** (덧셈): 3 gas

이 비용 모델 때문에 Solidity 코드는 단순히 "동작하는 코드"가 아닌 "Gas를 최소화하는 코드"를 지향해야 한다.

### 2. 상태 변수와 스토리지 레이아웃

컨트랙트의 상태 변수는 블록체인의 영구 스토리지(persistent storage)에 저장된다. 변수의 선언 순서와 타입에 따라 스토리지 슬롯(32바이트)이 결정되며, 이는 Gas 비용에 직접적인 영향을 미친다.

```solidity
// 비효율적인 레이아웃 - 3개의 슬롯 사용
contract BadLayout {
    uint128 a; // slot 0
    uint256 b; // slot 1 (uint128이 남아있지만 uint256은 새 슬롯 필요)
    uint128 c; // slot 2
}

// 효율적인 레이아웃 - 2개의 슬롯 사용
contract GoodLayout {
    uint128 a; // slot 0 (상위 16바이트)
    uint128 c; // slot 0 (하위 16바이트) - 패킹됨
    uint256 b; // slot 1
}
```

### 3. 함수 가시성과 상태 변경성

| 키워드 | 설명 |
|--------|------|
| `public` | 외부/내부 모두 호출 가능, 자동으로 getter 생성 |
| `external` | 외부에서만 호출 가능 (calldata 사용으로 Gas 절약) |
| `internal` | 컨트랙트 내부 및 상속 컨트랙트에서만 호출 가능 |
| `private` | 해당 컨트랙트에서만 호출 가능 |
| `view` | 상태를 읽기만 하고 변경하지 않음 |
| `pure` | 상태를 읽지도 변경하지도 않음 |

### 4. 이벤트(Event)와 로그

이벤트는 블록체인의 트랜잭션 로그에 데이터를 기록하는 메커니즘이다. 스토리지 저장보다 훨씬 저렴하며, 프론트엔드나 오프체인 서비스가 컨트랙트 상태 변화를 추적하는 데 사용된다.

```solidity
event Transfer(address indexed from, address indexed to, uint256 value);
```

`indexed` 키워드가 붙은 파라미터는 토픽(topic)으로 처리되어 효율적인 필터링이 가능하다. 단, 토픽은 최대 3개까지만 허용된다.

## 실전 예제

### ERC-20 토큰 컨트랙트 구현

실무에서 가장 자주 접하는 패턴인 ERC-20 토큰을 OpenZeppelin을 활용해 구현한다. 단순한 예제를 넘어, 실무에서 필요한 **민팅 권한 제어**, **일시 정지 기능**, **소각 기능**까지 포함한다.

```bash
# 프로젝트 초기화
npm init -y
npm install --save-dev hardhat
npx hardhat init

# OpenZeppelin 설치
npm install @openzeppelin/contracts
```

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import "@openzeppelin/contracts/token/ERC20/extensions/ERC20Burnable.sol";
import "@openzeppelin/contracts/token/ERC20/extensions/ERC20Pausable.sol";
import "@openzeppelin/contracts/access/AccessControl.sol";

/**
 * @title MyToken
 * @notice 실무용 ERC-20 토큰 컨트랙트
 * @dev AccessControl을 사용한 역할 기반 권한 관리
 */
contract MyToken is ERC20, ERC20Burnable, ERC20Pausable, AccessControl {
    bytes32 public constant MINTER_ROLE = keccak256("MINTER_ROLE");
    bytes32 public constant PAUSER_ROLE = keccak256("PAUSER_ROLE");

    uint256 public constant MAX_SUPPLY = 100_000_000 * 10 ** 18; // 1억 토큰

    event MaxSupplyReached(uint256 totalSupply);

    error ExceedsMaxSupply(uint256 requested, uint256 available);
    error InvalidAddress();

    constructor(
        string memory name,
        string memory symbol,
        address admin
    ) ERC20(name, symbol) {
        if (admin == address(0)) revert InvalidAddress();

        _grantRole(DEFAULT_ADMIN_ROLE, admin);
        _grantRole(MINTER_ROLE, admin);
        _grantRole(PAUSER_ROLE, admin);
    }

    /**
     * @notice 토큰 민팅 (MINTER_ROLE 필요)
     * @param to 수신 주소
     * @param amount 민팅 수량 (wei 단위)
     */
    function mint(address to, uint256 amount) external onlyRole(MINTER_ROLE) {
        if (to == address(0)) revert InvalidAddress();

        uint256 available = MAX_SUPPLY - totalSupply();
        if (amount > available) {
            revert ExceedsMaxSupply(amount, available);
        }

        _mint(to, amount);

        if (totalSupply() == MAX_SUPPLY) {
            emit MaxSupplyReached(totalSupply());
        }
    }

    /**
     * @notice 컨트랙트 일시 정지 (PAUSER_ROLE 필요)
     */
    function pause() external onlyRole(PAUSER_ROLE) {
        _pause();
    }

    function unpause() external onlyRole(PAUSER_ROLE) {
        _unpause();
    }

    // 다중 상속 시 _update 함수 충돌 해결
    function _update(
        address from,
        address to,
        uint256 value
    ) internal override(ERC20, ERC20Pausable) {
        super._update(from, to, value);
    }
}
```

### Hardhat 테스트 작성

컨트랙트 배포 전 반드시 테스트를 작성해야 한다. 블록체인에 배포된 컨트랙트는 수정이 불가능하기 때문이다.

```javascript
// test/MyToken.test.js
const { expect } = require("chai");
const { ethers } = require("hardhat");
const { loadFixture } = require("@nomicfoundation/hardhat-network-helpers");

describe("MyToken", function () {
  async function deployTokenFixture() {
    const [owner, minter, user1, user2] = await ethers.getSigners();

    const MyToken = await ethers.getContractFactory("MyToken");
    const token = await MyToken.deploy("MyToken", "MTK", owner.address);
    await token.waitForDeployment();

    const MINTER_ROLE = await token.MINTER_ROLE();
    await token.grantRole(MINTER_ROLE, minter.address);

    return { token, owner, minter, user1, user2, MINTER_ROLE };
  }

  describe("Minting", function () {
    it("MINTER_ROLE을 가진 계정만 민팅 가능", async function () {
      const { token, minter, user1 } = await loadFixture(deployTokenFixture);
      const amount = ethers.parseEther("1000");

      await expect(token.connect(minter).mint(user1.address, amount))
        .to.emit(token, "Transfer")
        .withArgs(ethers.ZeroAddress, user1.address, amount);

      expect(await token.balanceOf(user1.address)).to.equal(amount);
    });

    it("권한 없는 계정의 민팅 시도는 revert", async function () {
      const { token, user1, user2, MINTER_ROLE } = await loadFixture(deployTokenFixture);

      await expect(
        token.connect(user1).mint(user2.address, ethers.parseEther("100"))
      ).to.be.revertedWithCustomError(token, "AccessControlUnauthorizedAccount")
        .withArgs(user1.address, MINTER_ROLE);
    });

    it("MAX_SUPPLY 초과 민팅 시도는 revert", async function () {
      const { token, minter, user1 } = await loadFixture(deployTokenFixture);
      const maxSupply = await token.MAX_SUPPLY();
      const overAmount = maxSupply + 1n;

      await expect(
        token.connect(minter).mint(user1.address, overAmount)
      ).to.be.revertedWithCustomError(token, "ExceedsMaxSupply");
    });
  });

  describe("Pausable", function () {
    it("일시 정지 중 토큰 전송 불가", async function () {
      const { token, owner, minter, user1, user2 } = await loadFixture(deployTokenFixture);
      await token.connect(minter).mint(user1.address, ethers.parseEther("100"));
      await token.connect(owner).pause();

      await expect(
        token.connect(user1).transfer(user2.address, ethers.parseEther("10"))
      ).to.be.revertedWithCustomError(token, "EnforcedPause");
    });
  });
});
```

```bash

npx hardhat test

# Gas 리포트와 함께 실행
REPORT_GAS=true npx hardhat test
```

## 주의사항 및 트레이드오프

### 1. 재진입 공격(Reentrancy Attack)

이더리움 역사상 가장 큰 해킹 사례인 DAO 해킹의 원인이다. 외부 컨트랙트 호출 시 상태를 변경하기 전에 이더를 전송하면 취약점이 발생한다.

```solidity
// ❌ 취약한 패턴 (Checks-Effects-Interactions 위반)
function withdraw() external {
    uint256 amount = balances[msg.sender];
    (bool success, ) = msg.sender.call{value: amount}(""); // 외부 호출 먼저
    require(success);
    balances[msg.sender] = 0; // 상태 변경 나중에 → 재진입 가능!
}

// ✅ 안전한 패턴 (CEI 패턴 준수)
function withdraw() external nonReentrant { // OpenZeppelin ReentrancyGuard 사용
    uint256 amount = balances[msg.sender];
    balances[msg.sender] = 0;               // 상태 먼저 변경
    (bool success, ) = msg.sender.call{value: amount}(""); // 외부 호출 나중에
    require(success, "Transfer failed");
}
```

### 2. 정수 오버플로우/언더플로우

Solidity 0.8.0 이상에서는 기본적으로 오버플로우 체크가 내장되어 있다. 하지만 `unchecked` 블록을 사용하면 이를 우회할 수 있으며, Gas 절약을 위해 신중하게 사용해야 한다.

```solidity
// for 루프에서의 unchecked 최적화 (안전한 경우에만)
for (uint256 i = 0; i < length; ) {
    // 처리 로직
    unchecked { ++i; } // 오버플로우 불가능한 상황에서 Gas 절약
}
```

### 3. 블록체인의 공개성

스마트 컨트랙트의 `private` 변수는 외부에서 직접 호출할 수 없지만, 블록체인 스토리지는 누구나 읽을 수 있다. 민감한 데이터를 온체인에 저장하는 것은 피해야 한다.

```solidity
// ❌ 잘못된 이해
string private secretKey = "my-secret"; // 누구나 eth_getStorageAt으로 읽을 수 있음

// ✅ 민감 데이터는 해시만 저장
bytes32 private secretKeyHash = keccak256(abi.encodePacked("my-secret"));
```

### 4. 업그레이드 가능성 vs 불변성 트레이드오프

| 접근 방식 | 장점 | 단점 |
|----------|------|------|
| 불변 컨트랙트 | 신뢰성 최대, 검증 용이 | 버그 수정 불가 |
| 프록시 패턴 (UUPS/Transparent) | 업그레이드 가능 | 복잡성 증가, 중앙화 위험 |
| 다이아몬드 패턴 | 모듈화, 유연성 | 매우 복잡한 구현 |

실무에서는 **OpenZeppelin의 UUPS 프록시** 패턴을 가장 많이 사용하며, 거버넌스 메커니즘과 함께 구성하는 것이 권장된다.

### 5. 오라클 의존성

스마트 컨트랙트는 외부 데이터(가격, 날씨 등)에 직접 접근할 수 없다. Chainlink 같은 오라클을 사용하지만, 오라클 자체가 단일 실패 지점(SPOF)이 될 수 있다는 점을 인식해야 한다.

## 정리

Solidity와 스마트 컨트랙트 개발은 기존 백엔드 개발과 패러다임이 다르다. 핵심 차이를 정리하면 다음과 같다.

| 구분 | 일반 백엔드 | 스마트 컨트랙트 |
|------|------------|----------------|
| 배포 후 수정 | 가능 | 불가 (프록시 패턴 제외) |
| 연산 비용 | 서버 스펙에 따름 | 모든 연산에 Gas 비용 |
| 데이터 공개성 | 접근 제어 가능 | 블록체인은 기본 공개 |
| 실행 보장 | 서버 가용성 의존 | 네트워크 유지 시 보장 |
| 보안 위협 | OWASP Top 10 | 재진입, 오라클 조작 등 특수 취약점 |

**시작하기 좋은 학습 경로**를 추천하면:
1. [Solidity 공식 문서](https://docs.soliditylang.org/) 정독
2. [OpenZeppelin 컨트랙트](https://github.com/OpenZeppelin/openzeppelin-contracts) 소스 분석
3. [Ethernaut](https://ethernaut.openzeppelin.com/) - 보안 취약점 학습 게임
4. Hardhat + Foundry 테스트 환경 구축

스마트 컨트랙트는 한 번 배포하면 수억 달러 규모의 자산을 관리할 수 있는 코드가 된다. 단 한 줄의 실수가 돌이킬 수 없는 결과를 만들 수 있기 때문에, 철저한 테스트와 감사(Audit)는 선택이 아닌 필수다. 백엔드 개발자로서 쌓아온 코드 설계와 시스템 사고 능력은 스마트 컨트랙트 개발에서도 핵심 경쟁력이 된다.
