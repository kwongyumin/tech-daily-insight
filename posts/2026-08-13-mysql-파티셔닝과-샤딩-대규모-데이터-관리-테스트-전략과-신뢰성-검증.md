# MySQL 파티셔닝과 샤딩 대규모 데이터 관리 — 테스트 전략과 신뢰성 검증

## 테스트 전략과 신뢰성 검증: 운영 환경에서 살아남는 법

---

## 개요

파티셔닝과 샤딩을 도입했다고 해서 끝이 아니다. 진짜 문제는 **"이 구조가 실제로 올바르게 동작하는가"** 를 어떻게 검증하느냐다. 잘못 설계된 파티션 프루닝(Partition Pruning)은 성능 개선은커녕 풀스캔을 유발하고, 샤딩 키 해시 분포가 불균일하면 특정 샤드에만 핫스팟이 몰려 장애가 발생한다. 

이 글은 MySQL 파티셔닝과 샤딩의 **테스트 전략과 신뢰성 검증**에 집중한다. 파티션 프루닝이 실제로 동작하는지 확인하는 쿼리 검증 방법, 샤드 분포의 편향도 측정, 장애 시뮬레이션, 그리고 데이터 정합성 검증까지 실무에서 마주치는 핵심 문제를 다룬다.

---

## 핵심 개념: 무엇을 검증해야 하는가

신뢰성 검증의 범위를 명확히 정의하는 것부터 시작해야 한다.

| 검증 영역 | 핵심 질문 | 도구 |
|---|---|---|
| **파티션 프루닝** | 쿼리가 불필요한 파티션을 읽고 있지 않은가? | `EXPLAIN PARTITIONS`, `EXPLAIN FORMAT=JSON` |
| **샤드 분포 균일성** | 특정 샤드에 데이터가 몰리지 않는가? | 커스텀 스크립트, Prometheus |
| **쿼리 라우팅 정확성** | 올바른 샤드로 쿼리가 전달되는가? | 통합 테스트, 감사 로그 |
| **장애 복구 신뢰성** | 샤드 장애 시 데이터 유실 없이 복구되는가? | Chaos Engineering |
| **데이터 정합성** | 파티션/샤드 간 중복 또는 누락 데이터가 없는가? | 체크섬 비교, COUNT 검증 |

## 실전 예제

### 1. 파티션 프루닝 검증: `EXPLAIN`을 믿지 마라

많은 개발자가 `EXPLAIN`에 `partitions` 컬럼에 단 하나의 파티션이 보이면 안심한다. 하지만 실제 실행 계획이 달라지는 경우가 있다. **함수 호출이나 타입 불일치**가 섞이면 프루닝이 무력화된다.

```sql
-- 파티션 정의 예시
CREATE TABLE orders (
    id BIGINT NOT NULL,
    created_at DATETIME NOT NULL,
    user_id BIGINT NOT NULL,
    amount DECIMAL(10,2)
)
PARTITION BY RANGE (YEAR(created_at)) (
    PARTITION p2022 VALUES LESS THAN (2023),
    PARTITION p2023 VALUES LESS THAN (2024),
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION p_future VALUES LESS THAN MAXVALUE
);

-- 프루닝이 되는 경우
EXPLAIN PARTITIONS
SELECT * FROM orders WHERE created_at >= '2023-01-01' AND created_at < '2024-01-01';
-- 결과: partitions = p2023 ✅

-- 프루닝이 깨지는 경우 (함수 사용)
EXPLAIN PARTITIONS
SELECT * FROM orders WHERE YEAR(created_at) = 2023;
-- 결과: partitions = p2022,p2023,p2024,p_future ❌ (풀스캔!)
```

**프루닝 검증을 자동화하는 Python 스크립트:**

```python
import mysql.connector
import json

def verify_partition_pruning(connection, query, expected_partitions: list[str]):
    cursor = connection.cursor(dictionary=True)
    explain_query = f"EXPLAIN FORMAT=JSON {query}"
    cursor.execute(explain_query)
    result = cursor.fetchone()
    
    explain_json = json.loads(result['EXPLAIN'])
    accessed_partitions = explain_json['query_block']['table']['partitions_accessed']
    
    accessed_set = set(accessed_partitions.split(','))
    expected_set = set(expected_partitions)
    
    if accessed_set != expected_set:
        raise AssertionError(
            f"Partition pruning FAILED!\n"
            f"Expected: {expected_set}\n"
            f"Actual:   {accessed_set}\n"
            f"Query: {query}"
        )
    
    print(f"✅ Partition pruning OK: {accessed_set}")
    cursor.close()

# 사용 예시
conn = mysql.connector.connect(host='localhost', user='root', database='shop')
verify_partition_pruning(
    conn,
    "SELECT * FROM orders WHERE created_at >= '2023-01-01' AND created_at < '2024-01-01'",
    expected_partitions=['p2023']
)
```

이 스크립트를 **CI/CD 파이프라인에 통합**해 스키마 변경이나 쿼리 수정 시 자동으로 프루닝 검증을 실행하게 한다. 실무에서 스키마 변경 후 프루닝이 깨지는 케이스의 **약 70%는 타입 변경이나 인덱스 컬럼에 함수 추가**에서 발생한다.

### 2. 샤드 분포 편향도 측정

샤딩 키를 잘못 선택하면 특정 샤드에만 부하가 몰리는 **핫샤드(Hot Shard)** 문제가 생긴다. 이를 정량적으로 측정해야 한다.

```java
// Spring Boot + JPA 환경에서 샤드별 데이터 분포 측정
@Component
public class ShardDistributionVerifier {

    private final List<DataSource> shardDataSources; // 샤드별 DataSource 리스트

    public ShardDistributionReport verify() {
        List<Long> rowCounts = new ArrayList<>();
        
        for (int i = 0; i < shardDataSources.size(); i++) {
            try (Connection conn = shardDataSources.get(i).getConnection();
                 Statement stmt = conn.createStatement()) {
                
                ResultSet rs = stmt.executeQuery("SELECT COUNT(*) FROM orders");
                rs.next();
                rowCounts.add(rs.getLong(1));
                
            } catch (SQLException e) {
                log.error("Shard {} connection failed", i, e);
                rowCounts.add(-1L);
            }
        }
        
        return analyzeDistribution(rowCounts);
    }
    
    private ShardDistributionReport analyzeDistribution(List<Long> counts) {
        long total = counts.stream().filter(c -> c >= 0).mapToLong(Long::longValue).sum();
        double mean = (double) total / counts.size();
        
        // 표준편차 계산
        double variance = counts.stream()
            .filter(c -> c >= 0)
            .mapToDouble(c -> Math.pow(c - mean, 2))
            .average()
            .orElse(0);
        double stdDev = Math.sqrt(variance);
        
        // 변동계수(CV): 분포 편향 지표
        double cv = (stdDev / mean) * 100;
        
        long maxCount = counts.stream().mapToLong(Long::longValue).max().orElse(0);
        long minCount = counts.stream().mapToLong(Long::longValue).min().orElse(0);
        double skewRatio = (double) maxCount / Math.max(minCount, 1);
        
        return ShardDistributionReport.builder()
            .totalRows(total)
            .meanRowsPerShard(mean)
            .standardDeviation(stdDev)
            .coefficientOfVariation(cv)
            .skewRatio(skewRatio)
            .isHealthy(cv < 20.0 && skewRatio < 1.5) // 임계값 기준
            .build();
    }
}
```

**편향도 판단 기준 (실무 경험 기반):**

| 변동계수(CV) | 왜곡 비율(Max/Min) | 상태 | 조치 |
|---|---|---|---|
| < 10% | < 1.2 | 🟢 정상 | 유지 |
| 10~20% | 1.2~1.5 | 🟡 주의 | 샤딩 키 재검토 |
| 20~40% | 1.5~3.0 | 🟠 경고 | 리샤딩 계획 수립 |
| > 40% | > 3.0 | 🔴 위험 | 즉시 리샤딩 |

### 3. 장애 시뮬레이션: Chaos Engineering 적용

샤드 하나가 다운됐을 때 나머지 샤드가 정상적으로 서비스되는지, 그리고 복구 후 데이터 정합성이 유지되는지를 **운영 전에 반드시 테스트**해야 한다.

```java
@SpringBootTest
class ShardFailoverTest {

    @Autowired
    private OrderRepository orderRepository;
    
    @Autowired
    private ShardRouter shardRouter;

    @Test
    @DisplayName("샤드 2번 장애 시 샤드 0,1,3은 정상 동작해야 한다")
    void whenShard2IsDown_otherShardsRemainAvailable() {
        // Given: 샤드 2를 강제로 연결 불가 상태로 만들기
        shardRouter.disableShard(2); // 테스트용 메서드
        
        List<Long> userIdsOnOtherShards = generateUserIdsForShards(List.of(0, 1, 3));
        
        // When & Then: 다른 샤드의 쿼리는 성공해야 함
        assertDoesNotThrow(() -> {
            userIdsOnOtherShards.forEach(userId ->
                orderRepository.findByUserId(userId)
            );
        });
        
        // 샤드 2에 해당하는 쿼리는 명확한 예외를 던져야 함
        List<Long> userIdsOnShard2 = generateUserIdsForShard(2);
        userIdsOnShard2.forEach(userId ->
            assertThrows(ShardUnavailableException.class, () ->
                orderRepository.findByUserId(userId)
            )
        );
        
        // Cleanup
        shardRouter.enableShard(2);
    }
    
    @Test
    @DisplayName("샤드 복구 후 데이터 정합성이 유지되어야 한다")
    void afterShardRecovery_dataConsistencyMaintained() throws InterruptedException {
        // 장애 전 체크섬
        Map<Integer, String> checksumsBefore = calculateAllShardChecksums();
        
        // 장애 시뮬레이션 (30초)
        shardRouter.disableShard(1);
        Thread.sleep(5000);
        shardRouter.enableShard(1);
        
        // 복구 후 체크섬
        Map<Integer, String> checksumsAfter = calculateAllShardChecksums();
        
        // 정합성 비교
        assertEquals(checksumsBefore.get(1), checksumsAfter.get(1),
            "Shard 1 data consistency violated after recovery");
    }
    
    private Map<Integer, String> calculateAllShardChecksums() {
        // 각 샤드에 CHECKSUM TABLE 실행
        return shardRouter.getAllShards().stream()
            .collect(Collectors.toMap(
                shardId -> shardId,
                shardId -> shardRouter.executeOnShard(shardId,
                    "CHECKSUM TABLE orders EXTENDED")
            ));
    }
}
```

### 4. 파티션 간 데이터 정합성 검증

파티션 교환(EXCHANGE PARTITION)이나 마이그레이션 후에는 반드시 정합성을 검증해야 한다.

```sql
-- 파티션별 행 수 및 체크섬 비교 쿼리
SELECT
    PARTITION_NAME,
    TABLE_ROWS,
    AVG_ROW_LENGTH,
    DATA_LENGTH,
    CHECKSUM
FROM information_schema.PARTITIONS
WHERE TABLE_SCHEMA = 'shop' AND TABLE_NAME = 'orders'
ORDER BY PARTITION_NAME;

-- 파티션 간 날짜 범위 침범 여부 확인 (데이터 오염 감지)
SELECT 'p2023' AS partition_name, COUNT(*) AS violating_rows
FROM orders PARTITION (p2023)
WHERE created_at < '2023-01-01' OR created_at >= '2024-01-01'

UNION ALL

SELECT 'p2024', COUNT(*)
FROM orders PARTITION (p2024)
WHERE created_at < '2024-01-01' OR created_at >= '2025-01-01';
```

## 주의사항 및 트레이드오프

### 테스트 환경과 운영 환경의 간극

가장 흔한 함정은 **테스트 데이터 규모의 차이**다. 100만 건 테스트에서는 파티션 프루닝이 완벽히 동작했지만, 10억 건 운영 환경에서는 통계 정보(Statistics) 오차로 인해 옵티마이저가 다른 실행 계획을 선택하는 경우가 있다. 

- **해결책**: 운영 데이터의 5~10%를 샘플링한 스테이징 환경을 유지하고, `ANALYZE TABLE`로 통계를 최신 상태로 유지한다.

### 파티션 프루닝 vs 인덱스 성능 트레이드오프

| 상황 | 파티션 프루닝 | 인덱스 |
|---|---|---|
| 날짜 범위 조회 (대량) | ✅ 유리 | 🔶 비효율 |
| 단건 PK 조회 | 🔶 비효율 | ✅ 유리 |
| 멀티 컬럼 조건 | ❌ 프루닝 불가 | ✅ 복합 인덱스 |

파티셔닝과 인덱스를 동시에 쓸 때는 **로컬 인덱스(Local Index)**만 사용 가능하다는 점을 명심해야 한다. 글로벌 인덱스는 MySQL에서 지원하지 않으므로, 파티션 키를 포함하지 않는 유니크 제약은 파티셔닝과 함께 사용할 수 없다.

### 샤딩 키 선택의 비가역성

샤딩 키를 한 번 잘못 선택하면 리샤딩 비용이 매우 크다. `user_id`로 샤딩했을 때 특정 헤비 유저가 한 샤드에 몰리는 **셀러브리티 문제**는 테스트 단계에서 프로덕션 데이터 분포를 시뮬레이션하지 않으면 발견하기 어렵다. **히스토그램 기반의 카디널리티 분석**을 샤딩 키 선정 전에 반드시 수행해야 한다.

```sql
-- 샤딩 키 후보의 분포 분석
SELECT
    FLOOR(user_id / 100000) AS bucket,
    COUNT(*) AS row_count,
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 2) AS percentage
FROM orders
GROUP BY bucket
ORDER BY row_count DESC
LIMIT 20;
```

## 정리

MySQL 파티셔닝과 샤딩의 신뢰성은 **설계 단계가 아니라 검증 단계**에서 완성된다. 핵심 체크리스트를 요약하면:

1. **파티션 프루닝 자동화 검증**: 모든 주요 쿼리의 프루닝 여부를 CI에서 검증한다.
2. **샤드 분포 모니터링**: 변동계수(CV) 20% 미만, 왜곡 비율 1.5 미만을 기준으로 상시 모니터링한다.
3. **장애 시뮬레이션 정례화**: 최소 분기 1회 샤드 장애 복구 시나리오를 실제로 테스트한다.
4. **데이터 정합성 체크섬**: 파티션 교환이나 마이그레이션 후에는 항상 `CHECKSUM TABLE`로 검증한다.
5. **프로덕션 데이터 분포 시뮬레이션**: 샤딩 키 선정 전 실제 데이터 히스토그램을 분석한다.

대규모 데이터를 다루는 시스템에서 "동작한다"는 것과 "신뢰할 수 있다"는 것은 다르다. 위의 검증 전략을 운영에 내재화할 때, 파티셔닝과 샤딩은 비로소 안전한 무기가 된다.
