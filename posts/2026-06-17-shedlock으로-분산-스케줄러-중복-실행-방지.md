# ShedLock으로 분산 스케줄러 중복 실행 방지

## 개요

MSA(Microservices Architecture)나 멀티 인스턴스 배포 환경에서 Spring의 `@Scheduled`를 그대로 사용하면 치명적인 문제가 발생한다. 서버 인스턴스가 3대라면 스케줄러도 3번 실행된다. 매일 자정에 정산 배치를 돌리는데 3번 중복 실행된다면? 고객에게 포인트가 3배로 적립되거나, 외부 API가 3번 호출되어 과금이 발생할 수 있다.

이 문제를 해결하는 방법은 여러 가지가 있다. 별도의 스케줄러 전용 서버를 띄우거나, Quartz Cluster를 구성하거나, Kubernetes CronJob을 쓰거나. 하지만 이런 방법들은 인프라 비용이 늘거나 설정 복잡도가 급격히 올라간다.

**ShedLock**은 이 문제에 대한 가장 실용적인 해답 중 하나다. 데이터베이스(또는 Redis, ZooKeeper 등)를 잠금 저장소로 활용해 특정 시점에 하나의 노드만 스케줄러를 실행하도록 보장한다. 기존 코드 변경을 최소화하면서 애너테이션 몇 줄로 분산 락을 적용할 수 있다는 점이 강력한 장점이다.

## 핵심 개념

### ShedLock의 동작 원리

ShedLock은 스케줄러 실행 전에 잠금 레코드를 공유 저장소에 삽입(또는 업데이트)하고, 실행이 끝나면 잠금을 해제하는 방식으로 동작한다.

```
[인스턴스 A] -- lock 획득 시도 --> [DB: shedlock 테이블]
[인스턴스 B] -- lock 획득 시도 --> [DB: shedlock 테이블] → 실패, 스킵
[인스턴스 C] -- lock 획득 시도 --> [DB: shedlock 테이블] → 실패, 스킵

인스턴스 A 실행 완료 → lock 해제
```

핵심은 `lockAtMostFor`와 `lockAtLeastFor` 두 가지 파라미터다.

- **`lockAtMostFor`**: 최대 잠금 유지 시간. 실행 중인 노드가 죽어도 이 시간이 지나면 자동으로 잠금이 해제된다. **데드락 방지용** 안전장치다.
- **`lockAtLeastFor`**: 최소 잠금 유지 시간. 작업이 빨리 끝나도 이 시간 동안은 다른 노드가 실행하지 못하게 막는다. **클러스터 시간 불일치(Clock Skew)** 대응용이다.

> ⚠️ `lockAtMostFor`는 실제 배치 실행 시간보다 넉넉하게 설정해야 한다. 작업이 끝나기 전에 잠금이 풀리면 중복 실행이 발생할 수 있다.

### 지원하는 잠금 저장소

ShedLock은 다양한 백엔드를 지원한다.

| 저장소 | 의존성 |
|---|---|
| JDBC (MySQL, PostgreSQL 등) | `shedlock-provider-jdbc-template` |
| Redis | `shedlock-provider-redis-spring` |
| MongoDB | `shedlock-provider-mongo` |
| ZooKeeper | `shedlock-provider-zookeeper-curator` |
| Elasticsearch | `shedlock-provider-elasticsearch` |

대부분의 백엔드 서비스는 이미 RDB나 Redis를 사용하고 있으므로, **추가 인프라 없이** 바로 적용 가능하다는 점이 매력적이다.

### DB 테이블 생성

JDBC를 사용하는 경우 아래 DDL로 잠금 테이블을 생성해야 한다.

```sql
-- MySQL / MariaDB
CREATE TABLE shedlock (
    name        VARCHAR(64)  NOT NULL,
    lock_until  TIMESTAMP(3) NOT NULL,
    locked_at   TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    locked_by   VARCHAR(255) NOT NULL,
    PRIMARY KEY (name)
);
```

```sql
-- PostgreSQL
CREATE TABLE shedlock (
    name        VARCHAR(64)  NOT NULL,
    lock_until  TIMESTAMP    NOT NULL,
    locked_at   TIMESTAMP    NOT NULL,
    locked_by   VARCHAR(255) NOT NULL,
    CONSTRAINT pk_shedlock PRIMARY KEY (name)
);
```

### Spring 설정

```java
@Configuration
@EnableScheduling
@EnableSchedulerLock(defaultLockAtMostFor = "10m") // 기본 최대 잠금 시간
public class SchedulerConfig {

    @Bean
    public LockProvider lockProvider(DataSource dataSource) {
        return new JdbcTemplateLockProvider(
            JdbcTemplateLockProvider.Configuration.builder()
                .withJdbcTemplate(new JdbcTemplate(dataSource))
                .usingDbTime() // DB 서버 시간 기준으로 잠금 처리 (권장)
                .build()
        );
    }
}
```

> `usingDbTime()`을 사용하면 각 애플리케이션 서버의 시스템 클럭 차이로 인한 문제를 방지할 수 있다. 강력히 권장한다.

### 스케줄러 적용

```java
@Slf4j
@Component
@RequiredArgsConstructor
public class SettlementScheduler {

    private final SettlementService settlementService;

    /**
     * 매일 새벽 1시에 전날 정산 처리
     * lockAtMostFor: 최대 30분간 잠금 유지 (작업 실패 시 안전장치)
     * lockAtLeastFor: 최소 5분간 잠금 유지 (클러스터 시간 불일치 대응)
     */
    @Scheduled(cron = "0 0 1 * * *")
    @SchedulerLock(
        name = "settlementScheduler_dailySettlement",
        lockAtMostFor = "30m",
        lockAtLeastFor = "5m"
    )
    public void dailySettlement() {
        log.info("[Settlement] 일별 정산 시작 - {}", LocalDate.now().minusDays(1));
        try {
            settlementService.processYesterdaySettlement();
            log.info("[Settlement] 일별 정산 완료");
        } catch (Exception e) {
            log.error("[Settlement] 일별 정산 실패", e);
            throw e; // 예외를 다시 던져야 잠금이 정상 해제됨
        }
    }

    /**
     * 5분마다 미처리 알림 재발송
     */
    @Scheduled(fixedDelay = 300_000)
    @SchedulerLock(
        name = "settlementScheduler_retryNotification",
        lockAtMostFor = "4m",
        lockAtLeastFor = "1m"
    )
    public void retryFailedNotifications() {
        log.info("[Notification] 미처리 알림 재발송 시작");
        settlementService.retryPendingNotifications();
    }
}
```

### Redis를 잠금 저장소로 사용하는 경우

RDB 없이 Redis만 사용하는 환경이라면 아래와 같이 설정한다.

```java
@Configuration
@EnableScheduling
@EnableSchedulerLock(defaultLockAtMostFor = "PT10M")
public class SchedulerConfig {

    @Bean
    public LockProvider lockProvider(RedisConnectionFactory connectionFactory) {
        return new RedisLockProvider(connectionFactory, "my-app"); // prefix 지정 가능
    }
}
```

### 잠금 상태 모니터링

운영 환경에서는 shedlock 테이블을 직접 조회하는 것만으로도 현재 실행 중인 배치와 마지막 실행 시간을 파악할 수 있다.

```sql
SELECT 
    name,
    locked_at,
    lock_until,
    locked_by,
    CASE 
        WHEN lock_until > NOW() THEN 'LOCKED'
        ELSE 'RELEASED'
    END AS status
FROM shedlock
ORDER BY locked_at DESC;
```

## 주의사항 및 트레이드오프

### 1. ShedLock은 분산 락이지, 트랜잭션 보장이 아니다

ShedLock은 **"동시에 하나만 실행"** 을 보장하지만, 멱등성(Idempotency)까지 보장하지는 않는다. 예를 들어 `lockAtMostFor` 시간이 지나 잠금이 강제 해제된 후 다른 노드가 같은 배치를 실행하면 중복 처리가 발생할 수 있다. 비즈니스 로직 자체도 멱등하게 설계하는 것이 좋다.

```java
// 나쁜 예: 매번 새로 INSERT
public void processSettlement() {
    insertSettlementRecord(yesterday);
}

// 좋은 예: UPSERT 또는 처리 여부 체크
public void processSettlement() {
    if (settlementRepository.existsByDate(yesterday)) {
        log.info("이미 처리된 정산입니다: {}", yesterday);
        return;
    }
    insertSettlementRecord(yesterday);
}
```

### 2. `lockAtMostFor`는 반드시 실제 실행 시간보다 길게 설정

가장 많이 하는 실수다. 배치가 20분 걸리는데 `lockAtMostFor = "10m"`으로 설정하면 10분 후 다른 노드가 락을 획득해 중복 실행된다. 실제 실행 시간의 2~3배를 권장한다.

### 3. DB 장애 시 스케줄러 자체가 실행 안 될 수 있다

잠금 저장소에 접근하지 못하면 스케줄러는 기본적으로 실행되지 않는다. DB 장애가 곧 배치 장애로 이어질 수 있다는 점을 운영팀과 공유해야 한다. 이를 허용하거나 알람을 설정해 두자.

### 4. 스케줄러 이름 충돌 주의

`@SchedulerLock`의 `name`은 전역적으로 유일해야 한다. 마이크로서비스 환경에서 여러 서비스가 동일한 DB를 잠금 저장소로 쓴다면 이름 충돌이 생길 수 있다. 서비스명을 prefix로 붙이는 컨벤션을 정해두자.

```java
// 권장 네이밍 컨벤션
name = "서비스명_스케줄러클래스명_메서드명"
name = "payment-service_settlementScheduler_dailySettlement"
```

### 5. `@Transactional`과의 조합

ShedLock과 `@Transactional`을 함께 쓸 때, 잠금 해제는 트랜잭션 커밋 이후에 일어나야 안전하다. Spring AOP 프록시 순서 때문에 의도치 않은 동작이 생길 수 있으므로, 가급적 스케줄러 메서드에서는 `@Transactional`을 분리하고, 내부 서비스 메서드에서 트랜잭션을 관리하는 것이 낫다.

### ShedLock vs. 대안 비교

| 방법 | 복잡도 | 인프라 비용 | 정확도 | 적합 환경 |
|---|---|---|---|---|
| **ShedLock** | 낮음 | 없음 | 높음 | 기존 RDB/Redis 활용 |
| Quartz Cluster | 높음 | 중간 | 높음 | 복잡한 스케줄링 필요 시 |
| K8s CronJob | 중간 | 높음 | 높음 | 쿠버네티스 환경 |
| 전용 스케줄러 서버 | 중간 | 높음 | 높음 | 대규모 배치 시스템 |

## 정리

ShedLock은 복잡한 인프라 변경 없이 분산 환경에서의 스케줄러 중복 실행 문제를 해결하는 가장 실용적인 선택지 중 하나다. 핵심을 정리하면 다음과 같다.

1. **`usingDbTime()`을 반드시 설정**해 서버 간 시간 불일치 문제를 제거한다.
2. **`lockAtMostFor`는 실제 실행 시간의 2~3배** 여유 있게 설정한다.
3. **비즈니스 로직도 멱등하게** 설계해 만약의 중복 실행에도 안전하게 만든다.
4. **잠금 이름 컨벤션**을 팀 내에서 통일해 충돌을 예방한다.
5. 운영 중 `shedlock` 테이블 모니터링으로 배치 실행 상태를 추적한다.

ShedLock 하나로 모든 분산 스케줄링 문제가 해결되지는 않는다. 그러나 중복 실행 방지라는 목표에 한해서는, 이만큼 적은 비용으로 빠르게 적용할 수 있는 도구는 드물다. 지금 당장 `@Scheduled`와 멀티 인스턴스 환경을 함께 운용하고 있다면, ShedLock 도입을 진지하게 검토해볼 것을 권장한다.
