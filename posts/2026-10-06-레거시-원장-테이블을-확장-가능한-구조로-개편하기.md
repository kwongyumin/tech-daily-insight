# 레거시 원장 테이블을 확장 가능한 구조로 개편하기

## 개요

금융 시스템, 포인트 시스템, 정산 시스템을 운영하다 보면 어김없이 마주치는 녀석이 있다. 바로 수년 전에 설계된 **원장 테이블(Ledger Table)**이다. 처음에는 단순하게 출발했겠지만, 지금쯤이면 수십 개의 컬럼이 추가되고, `CHAR(1)` 타입의 구분자 컬럼이 난무하며, `NULL`을 허용하는 컬럼들이 가득한 상태일 것이다.

이런 테이블은 운영팀도 두려워하고, 개발팀도 손대기 꺼린다. 그럼에도 매일 수백만 건의 트랜잭션이 오가며 시스템의 심장 역할을 한다. 본 포스팅에서는 이런 레거시 원장 테이블을 **점진적이고 안전하게** 확장 가능한 구조로 개편하는 전략을 다룬다.

## 핵심 개념

### 레거시 원장 테이블의 전형적인 문제

현장에서 흔히 발견되는 레거시 원장 테이블의 패턴은 다음과 같다.

```sql
-- 전형적인 레거시 원장 테이블
CREATE TABLE TB_LEDGER (
    LEDGER_ID     BIGINT       NOT NULL,
    ACNT_NO       VARCHAR(20)  NOT NULL,
    TR_DT         VARCHAR(8)   NOT NULL,  -- YYYYMMDD 문자열
    TR_TM         VARCHAR(6),             -- HHMMSS 문자열
    TR_AMT        DECIMAL(18,2),
    BAL_AMT       DECIMAL(18,2),
    TR_GBN        CHAR(1),     -- 1:입금, 2:출금, 3:이체... 문서 없으면 해독 불가
    STAT_CD       CHAR(2),
    MEMO1         VARCHAR(200),
    MEMO2         VARCHAR(200),
    MEMO3         VARCHAR(200),           -- 용도 불명의 MEMO 컬럼들
    REF_NO        VARCHAR(50),
    REG_ID        VARCHAR(20),
    REG_DT        DATETIME,
    UPD_ID        VARCHAR(20),
    UPD_DT        DATETIME,
    EXT1          VARCHAR(100),           -- 확장용이라고 만들었으나 지금은 뭔가 들어있음
    EXT2          VARCHAR(100),
    PRIMARY KEY (LEDGER_ID)
);
```

이 구조의 핵심 문제는 세 가지다.

1. **의미 불명확성**: `TR_GBN`, `EXT1` 같은 컬럼은 코드를 추적하지 않으면 의미를 알 수 없다.
2. **변경 불가능성**: 잔액(`BAL_AMT`)이 행에 박혀 있어, 중간 데이터를 수정하면 이후 모든 잔액이 깨진다.
3. **확장 불가능성**: 새로운 거래 유형이 생길 때마다 컬럼을 추가하거나 `MEMO` 컬럼을 오용한다.

### 확장 가능한 원장의 설계 원칙

현대적인 원장 설계는 회계의 **복식부기(Double-Entry Bookkeeping)** 원리를 차용한다.

- **불변성(Immutability)**: 원장 항목은 수정하지 않는다. 오류는 반대 방향의 새 항목으로 정정한다.
- **잔액은 계산한다**: 잔액을 컬럼에 저장하지 않고, 필요 시 집계 쿼리나 캐시로 계산한다.
- **메타데이터 분리**: 거래 유형별 부가 정보는 별도 테이블에 저장한다.
- **이벤트 소싱 친화적**: 모든 변경을 이벤트로 기록하면 감사(Audit)와 재현이 쉬워진다.

## 실전 예제

### 1단계: 목표 스키마 설계

먼저 도달하고자 하는 목표 스키마를 명확히 정의한다.

```sql
-- 계좌 테이블
CREATE TABLE account (
    account_id    BIGINT          NOT NULL AUTO_INCREMENT,
    account_no    VARCHAR(20)     NOT NULL,
    account_type  VARCHAR(30)     NOT NULL,  -- SAVINGS, CHECKING, POINT, ...
    currency      CHAR(3)         NOT NULL DEFAULT 'KRW',
    status        VARCHAR(20)     NOT NULL DEFAULT 'ACTIVE',
    created_at    TIMESTAMP       NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (account_id),
    UNIQUE KEY uk_account_no (account_no)
);

-- 핵심 원장 항목 테이블 (불변)
CREATE TABLE ledger_entry (
    entry_id          BIGINT          NOT NULL AUTO_INCREMENT,
    account_id        BIGINT          NOT NULL,
    transaction_id    VARCHAR(36)     NOT NULL,  -- UUID
    entry_type        VARCHAR(30)     NOT NULL,  -- DEBIT / CREDIT
    amount            DECIMAL(18,4)   NOT NULL,
    currency          CHAR(3)         NOT NULL DEFAULT 'KRW',
    effective_at      TIMESTAMP       NOT NULL,  -- 실제 발생 시각
    recorded_at       TIMESTAMP       NOT NULL DEFAULT CURRENT_TIMESTAMP,
    idempotency_key   VARCHAR(100)    NOT NULL,  -- 멱등성 보장
    PRIMARY KEY (entry_id),
    UNIQUE KEY uk_idempotency (idempotency_key),
    KEY idx_account_effective (account_id, effective_at),
    KEY idx_transaction (transaction_id)
);

-- 거래 메타데이터 테이블
CREATE TABLE transaction_metadata (
    transaction_id    VARCHAR(36)     NOT NULL,
    meta_key          VARCHAR(100)    NOT NULL,
    meta_value        TEXT,
    PRIMARY KEY (transaction_id, meta_key)
);
```

`ledger_entry`에는 핵심 숫자 정보만 남기고, 거래별 부가 정보는 `transaction_metadata`의 EAV(Entity-Attribute-Value) 구조로 분리했다.

### 2단계: 잔액 조회 전략

잔액을 컬럼으로 관리하지 않으면 조회 성능 문제가 생긴다. 이를 위해 **잔액 스냅샷 테이블**을 별도로 운용한다.

```sql
-- 잔액 스냅샷 (주기적으로 갱신되는 체크포인트)
CREATE TABLE account_balance_snapshot (
    account_id        BIGINT          NOT NULL,
    snapshot_at       TIMESTAMP       NOT NULL,
    balance           DECIMAL(18,4)   NOT NULL,
    last_entry_id     BIGINT          NOT NULL,  -- 이 스냅샷이 반영한 마지막 entry_id
    PRIMARY KEY (account_id, snapshot_at)
);
```

잔액 조회는 다음과 같은 방식으로 최근 스냅샷 + 이후 항목 합산으로 처리한다.

```java
// Spring + JPA 기반 잔액 계산 서비스
@Service
@Transactional(readOnly = true)
public class BalanceQueryService {

    private final AccountBalanceSnapshotRepository snapshotRepository;
    private final LedgerEntryRepository ledgerEntryRepository;

    public BigDecimal getCurrentBalance(Long accountId) {
        // 1. 가장 최근 스냅샷 조회
        Optional<AccountBalanceSnapshot> latestSnapshot =
            snapshotRepository.findTopByAccountIdOrderBySnapshotAtDesc(accountId);

        BigDecimal baseBalance = BigDecimal.ZERO;
        Long fromEntryId = 0L;

        if (latestSnapshot.isPresent()) {
            baseBalance = latestSnapshot.get().getBalance();
            fromEntryId = latestSnapshot.get().getLastEntryId();
        }

        // 2. 스냅샷 이후의 항목만 집계
        BigDecimal delta = ledgerEntryRepository
            .sumDeltaAfterEntry(accountId, fromEntryId);

        return baseBalance.add(delta);
    }
}
```

```java
// Repository - 네이티브 쿼리
public interface LedgerEntryRepository extends JpaRepository<LedgerEntry, Long> {

    @Query(value = """
        SELECT COALESCE(
            SUM(CASE WHEN entry_type = 'CREDIT' THEN amount ELSE -amount END),
            0
        )
        FROM ledger_entry
        WHERE account_id = :accountId
          AND entry_id > :fromEntryId
        """, nativeQuery = true)
    BigDecimal sumDeltaAfterEntry(
        @Param("accountId") Long accountId,
        @Param("fromEntryId") Long fromEntryId
    );
}
```

### 3단계: 점진적 마이그레이션 전략 (Strangler Fig Pattern)

레거시 테이블을 한 번에 교체하는 것은 위험하다. **Strangler Fig 패턴**으로 점진적으로 전환한다.

```java
// 듀얼 라이트(Dual Write): 마이그레이션 기간 중 양쪽 테이블에 동시에 기록
@Service
@Slf4j
public class LedgerMigrationService {

    private final LegacyLedgerRepository legacyRepo;
    private final LedgerEntryRepository newRepo;
    private final MigrationFeatureFlag featureFlag;

    @Transactional
    public void recordTransaction(TransactionCommand command) {
        // 기존 레거시 테이블에 항상 기록 (롤백 기준점)
        TbLedger legacy = toLegacyEntity(command);
        legacyRepo.save(legacy);

        // 피처 플래그로 신규 테이블 쓰기 활성화 여부 제어
        if (featureFlag.isNewLedgerWriteEnabled()) {
            try {
                LedgerEntry newEntry = toNewEntry(command);
                newRepo.save(newEntry);
            } catch (Exception e) {
                // 신규 테이블 실패 시 알림만 보내고 레거시로 서빙 유지
                log.error("New ledger write failed. Continuing with legacy.", e);
                alertService.sendAlert("NEW_LEDGER_WRITE_FAILURE", e);
            }
        }
    }
}
```

마이그레이션 검증을 위한 Shadow Read 비교도 추가한다.

```java
@Component
public class LedgerConsistencyChecker {

    @Scheduled(fixedDelay = 60_000) // 1분마다 샘플 검증
    public void verifySample() {
        List<Long> sampleAccountIds = accountRepository.findRandomSample(100);

        sampleAccountIds.forEach(accountId -> {
            BigDecimal legacyBalance = legacyService.getBalance(accountId);
            BigDecimal newBalance = balanceQueryService.getCurrentBalance(accountId);

            if (legacyBalance.compareTo(newBalance) != 0) {
                log.warn("Balance mismatch for accountId={}, legacy={}, new={}",
                    accountId, legacyBalance, newBalance);
                metricsRegistry.counter("ledger.balance.mismatch").increment();
            }
        });
    }
}
```

## 주의사항 및 트레이드오프

### 잔액 정합성 vs 성능

| 전략 | 장점 | 단점 |
|---|---|---|
| 잔액 컬럼 저장 | 조회 O(1) | 동시성 이슈, 데이터 정합성 위험 |
| 전체 집계 | 항상 정확 | 대용량 시 쿼리 느림 |
| 스냅샷 + 증분 | 균형잡힌 성능 | 스냅샷 갱신 로직 복잡 |
| Redis 캐시 | 빠른 조회 | 캐시 정합성 관리 필요 |

실시간 잔액이 중요한 금융 시스템이라면 **낙관적 락(Optimistic Lock)** 혹은 **계좌 단위 직렬화(Serializable per Account)**를 고려해야 한다.

### EAV 구조의 함정

`transaction_metadata`와 같은 EAV 구조는 유연하지만 몇 가지 위험이 있다.

- **타입 안정성 없음**: `meta_value`가 `TEXT`이므로 숫자를 저장해도 문자열로 조회된다.
- **인덱스 활용 어려움**: 특정 메타데이터 값으로 필터링하는 쿼리는 풀 스캔으로 이어진다.
- **조인 폭발**: 여러 메타데이터를 한 번에 가져오려면 다중 조인 혹은 `GROUP_CONCAT`이 필요하다.

거래 유형별 부가 정보가 구조화되어 있다면, EAV 대신 **거래 유형별 상세 테이블** (예: `payment_detail`, `transfer_detail`)을 두는 것이 더 나을 수 있다. 이 경우 정규화를 유지하면서도 타입 안정성을 얻을 수 있다.

### 멱등성 키 관리

분산 환경에서 네트워크 재시도로 인한 중복 기록은 원장 데이터를 망가뜨린다. `idempotency_key`의 UNIQUE 제약은 필수이며, 키의 생명주기(TTL)도 정책으로 정해야 한다.

```java
// 멱등성 키 충돌 시 기존 결과를 반환하는 패턴
@Transactional
public LedgerEntry recordEntry(CreateEntryRequest request) {
    return ledgerEntryRepository
        .findByIdempotencyKey(request.getIdempotencyKey())
        .orElseGet(() -> ledgerEntryRepository.save(
            LedgerEntry.from(request)
        ));
}
```

### 파티셔닝 전략

원장 테이블은 시간이 지날수록 누적 데이터가 기하급수적으로 늘어난다. 초기 설계 시 **Range Partitioning**을 염두에 두자.

```sql
-- MySQL 파티셔닝 예시 (연도별)
ALTER TABLE ledger_entry
PARTITION BY RANGE (YEAR(effective_at)) (
    PARTITION p2022 VALUES LESS THAN (2023),
    PARTITION p2023 VALUES LESS THAN (2024),
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION p_future VALUES LESS THAN MAXVALUE
);
```

단, 파티션 키가 아닌 컬럼으로 조회할 경우 파티션 프루닝이 되지 않으니, 주요 조회 패턴을 반드시 파티션 키 기준으로 설계해야 한다.

## 정리

레거시 원장 테이블 개편은 단순한 스키마 변경이 아니다. 데이터의 **의미를 재정의**하고, **불변성과 감사 가능성**을 확보하며, 비즈니스가 성장해도 **구조가 버텨낼 수 있도록** 기반을 다시 쌓는 작업이다.

핵심 원칙을 요약하면 다음과 같다.

- **원장 항목은 불변으로** 설계하고 정정은 반대 항목으로 처리한다.
- **잔액은 저장이 아닌 계산**으로 얻되, 스냅샷으로 성능을 보완한다.
- **Strangler Fig + Dual Write**로 점진적으로 마이그레이션하고, 검증 단계를 충분히 거친다.
- **멱등성 키**로 중복 기록을 원천 차단한다.
- **파티셔닝**을 초기에 설계해 미래의 데이터 증가에 대비한다.

완벽한 마이그레이션보다 **되돌릴 수 있는 마이그레이션**이 더 안전하다. 피처 플래그와 일관성 검증 로직을 충분히 구비한 뒤, 작은 단위로 전환해 나가는 것이 실전에서 검증된 방식이다.
