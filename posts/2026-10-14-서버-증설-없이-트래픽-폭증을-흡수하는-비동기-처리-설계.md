# 서버 증설 없이 트래픽 폭증을 흡수하는 비동기 처리 설계

## 개요

트래픽 폭증은 언제나 예고 없이 찾아온다. 마케팅 이벤트, 바이럴 콘텐츠, 혹은 단순한 크론 잡의 동시 실행만으로도 순간 QPS는 평상시의 수십 배를 넘어설 수 있다. 이 상황에서 가장 직관적인 해결책은 "서버를 더 올리는 것"이지만, Auto Scaling이 반응하는 데는 최소 수 분이 걸리고, 그 공백 사이에 사용자는 이미 5xx 에러를 마주한다.

진짜 문제는 **처리 용량(Throughput)**이 아니라 **동시성 압력(Concurrency Pressure)**이다. 모든 요청이 즉각적인 응답을 기다리며 스레드와 DB 커넥션을 점유하는 동기적 구조에서는, 아무리 서버를 늘려도 병목은 다른 곳에서 다시 생긴다.

이 글에서는 서버 증설 없이 트래픽 폭증을 흡수하는 **비동기 처리 설계 전략**을 다룬다. 메시지 큐, 이벤트 드리븐 아키텍처, 백프레셔(Backpressure) 제어까지 실전 코드와 함께 살펴보자.

## 핵심 개념

### 동기 처리의 구조적 한계

일반적인 동기식 REST API는 다음 흐름으로 동작한다.

```
클라이언트 요청 → 스레드 점유 → DB 쿼리 → 외부 API 호출 → 응답 반환 → 스레드 해제
```

각 단계는 직렬로 실행되며, 외부 I/O가 블로킹되는 동안 스레드는 아무것도 하지 못한 채 대기한다. 톰캣 기본 스레드 풀이 200개라면, 동시에 처리 가능한 요청은 이론상 200개가 상한이다.

트래픽이 폭증하면 스레드 풀이 고갈되고, 이후 들어오는 요청은 큐에 쌓이다가 결국 타임아웃으로 실패한다.

### 비동기 설계의 핵심 원칙

비동기 처리가 트래픽 폭증에 강한 이유는 **요청의 수신과 처리를 분리**하기 때문이다.

- **수신(Accept)**: 즉시 응답 (202 Accepted), 스레드 반환
- **처리(Process)**: 별도 워커 혹은 컨슈머가 비동기적으로 처리

이 분리가 가능하려면 중간에 **버퍼 역할을 하는 레이어**가 필요하다. 메시지 큐(Kafka, RabbitMQ, SQS 등)가 그 역할을 담당한다.

```
클라이언트 → API 서버 (즉시 202) → 메시지 큐 → 워커 서버 (비동기 처리)
```

## 실전 예제

### 1. Spring + Kafka를 이용한 비동기 주문 처리

주문 생성 API는 트래픽이 집중되는 대표적인 엔드포인트다. 주문 저장, 재고 차감, 알림 발송을 동기로 묶으면 하나의 요청이 수백 ms를 소비한다.

**의존성 설정 (build.gradle)**

```groovy
implementation 'org.springframework.kafka:spring-kafka'
implementation 'org.springframework.boot:spring-boot-starter-web'
```

**주문 요청 수신 (Producer)**

```java
@RestController
@RequestMapping("/api/orders")
@RequiredArgsConstructor
public class OrderController {

    private final KafkaTemplate<String, OrderEvent> kafkaTemplate;
    private final OrderRepository orderRepository;

    @PostMapping
    public ResponseEntity<OrderResponse> createOrder(@RequestBody @Valid OrderRequest request) {
        // 1. 주문 ID 생성 및 PENDING 상태로 저장 (빠른 DB write 1회만)
        Order order = Order.create(request.getUserId(), request.getItems());
        orderRepository.save(order);

        // 2. 카프카에 이벤트 발행 (논블로킹)
        OrderEvent event = OrderEvent.from(order);
        kafkaTemplate.send("order.created", order.getId().toString(), event);

        // 3. 즉시 202 반환
        return ResponseEntity.accepted()
                .body(OrderResponse.of(order.getId(), "PENDING"));
    }
}
```

**주문 처리 (Consumer)**

```java
@Component
@RequiredArgsConstructor
@Slf4j
public class OrderProcessingConsumer {

    private final InventoryService inventoryService;
    private final NotificationService notificationService;
    private final OrderRepository orderRepository;

    @KafkaListener(
        topics = "order.created",
        groupId = "order-processing-group",
        concurrency = "5"  // 컨슈머 스레드 수 조절
    )
    public void handleOrderCreated(
            @Payload OrderEvent event,
            @Header(KafkaHeaders.RECEIVED_PARTITION) int partition,
            Acknowledgment ack) {
        try {
            // 재고 차감
            inventoryService.deduct(event.getItems());
            
            // 주문 상태 업데이트
            orderRepository.updateStatus(event.getOrderId(), OrderStatus.CONFIRMED);
            
            // 알림 발송 (별도 토픽으로 또 분리 가능)
            notificationService.sendConfirmation(event.getUserId(), event.getOrderId());

            ack.acknowledge(); // 수동 커밋
        } catch (InsufficientStockException e) {
            log.warn("재고 부족: orderId={}", event.getOrderId());
            orderRepository.updateStatus(event.getOrderId(), OrderStatus.FAILED);
            ack.acknowledge();
        } catch (Exception e) {
            log.error("주문 처리 실패: orderId={}", event.getOrderId(), e);
            // ack 하지 않으면 재처리 (DLQ 전략과 함께 고려)
        }
    }
}
```

**Kafka 설정**

```yaml
spring:
  kafka:
    bootstrap-servers: localhost:9092
    consumer:
      group-id: order-processing-group
      auto-offset-reset: earliest
      enable-auto-commit: false  # 수동 커밋으로 메시지 유실 방지
      max-poll-records: 50       # 한 번에 가져올 레코드 수 (백프레셔 조절)
    producer:
      acks: all                  # 모든 레플리카 확인 후 완료
      retries: 3
```

### 2. 백프레셔(Backpressure) 제어

비동기 처리에서 간과하기 쉬운 부분이 **컨슈머가 처리할 수 있는 속도보다 프로듀서가 빠를 때** 발생하는 문제다. 큐가 무한히 쌓이면 결국 OOM이나 처리 지연으로 이어진다.

Kafka에서는 `max-poll-records`와 `max.poll.interval.ms`로 컨슈머 처리 속도를 제어한다.

```java
@Configuration
public class KafkaConsumerConfig {

    @Bean
    public ConcurrentKafkaListenerContainerFactory<String, OrderEvent> 
            orderKafkaListenerContainerFactory(ConsumerFactory<String, OrderEvent> cf) {
        
        ConcurrentKafkaListenerContainerFactory<String, OrderEvent> factory =
                new ConcurrentKafkaListenerContainerFactory<>();
        factory.setConsumerFactory(cf);
        
        // 배치 처리로 DB 라운드트립 최소화
        factory.setBatchListener(true);
        
        // 컨슈머 스레드 수 (파티션 수 이하로 설정)
        factory.setConcurrency(5);
        
        // 수동 ACK 모드
        factory.getContainerProperties()
               .setAckMode(ContainerProperties.AckMode.MANUAL_IMMEDIATE);
        
        return factory;
    }
}
```

### 3. Dead Letter Queue(DLQ) 전략

처리에 실패한 메시지를 그냥 버리거나 무한 재시도하면 시스템 전체가 막힌다. DLQ를 활용해 실패 메시지를 격리하고, 별도로 분석/재처리하는 구조가 필요하다.

```java
@Configuration
public class KafkaDeadLetterConfig {

    @Bean
    public DefaultErrorHandler errorHandler(KafkaTemplate<String, Object> template) {
        // 최대 3회 재시도, 1초 간격
        FixedBackOff backOff = new FixedBackOff(1000L, 3L);

        DeadLetterPublishingRecoverer recoverer = 
            new DeadLetterPublishingRecoverer(template,
                (record, ex) -> {
                    // 실패 원인에 따라 다른 DLQ 토픽으로 라우팅
                    if (ex.getCause() instanceof InsufficientStockException) {
                        return new TopicPartition("order.dlq.stock", -1);
                    }
                    return new TopicPartition("order.dlq.general", -1);
                });

        return new DefaultErrorHandler(recoverer, backOff);
    }
}
```

## 주의사항 및 트레이드오프

### 1. 최종 일관성(Eventual Consistency)을 수용해야 한다

비동기 처리를 도입하는 순간 **즉각적인 일관성을 포기**한다. 주문을 생성했지만 재고 차감이 아직 이뤄지지 않은 상태가 존재한다. 이를 사용자에게 어떻게 전달할지, 어디까지 허용할지 **비즈니스 결정**이 선행되어야 한다.

- "주문이 접수되었습니다" → 처리 중 상태를 명시적으로 안내
- 주문 상세 페이지에서 상태 폴링 혹은 SSE/WebSocket으로 결과 전달

### 2. 멱등성(Idempotency) 보장

네트워크 오류나 재처리로 인해 **같은 메시지가 두 번 처리**될 수 있다. 컨슈머는 반드시 멱등하게 설계해야 한다.

```java
@Transactional
public void processOrder(OrderEvent event) {
    // 이미 처리된 이벤트인지 확인
    if (processedEventRepository.existsByEventId(event.getEventId())) {
        log.info("이미 처리된 이벤트 스킵: {}", event.getEventId());
        return;
    }
    
    // 비즈니스 로직 처리
    doProcess(event);
    
    // 처리 완료 기록
    processedEventRepository.save(new ProcessedEvent(event.getEventId()));
}
```

### 3. 메시지 순서 보장 문제

Kafka는 파티션 단위로 순서를 보장한다. 동일 사용자의 주문은 같은 파티션으로 라우팅해야 순서가 지켜진다.

```java
// userId를 파티션 키로 사용
kafkaTemplate.send("order.created", event.getUserId().toString(), event);
```

단, 이 경우 특정 파티션에 **핫스팟**이 생길 수 있으므로 키 설계에 주의가 필요하다.

### 4. 모니터링 없는 비동기는 블랙박스다

동기 처리는 에러가 즉시 드러나지만, 비동기는 장애가 조용히 쌓인다. 다음 지표는 반드시 모니터링해야 한다.

| 지표 | 의미 | 경보 기준 |
|------|------|-----------|
| Consumer Lag | 미처리 메시지 누적량 | 임계치 이상 지속 증가 |
| DLQ 메시지 수 | 처리 실패 건수 | 0 이상 발생 시 |
| 처리 지연(P95) | 수신~완료 소요 시간 | SLA 기준 초과 |
| 컨슈머 재시작 횟수 | 컨슈머 불안정성 | 빈번한 재시작 |

### 5. 언제 비동기를 쓰지 말아야 하는가

모든 API를 비동기로 만들면 안 된다. 다음 경우는 동기 처리가 맞다.

- 응답 결과가 즉시 다음 요청에 필요한 경우 (예: 인증 토큰 발급)
- 처리 실패 시 사용자가 즉각 대응해야 하는 경우 (예: 결제 실패 재시도)
- 트랜잭션 경계가 단일 서비스 내에 한정되는 단순 CRUD

## 정리

서버 증설은 트래픽 폭증의 근본적인 해결책이 아니다. 동기적 처리 구조를 유지한 채 서버만 늘리면, 병목은 DB 커넥션 풀이나 외부 서비스로 이동할 뿐이다.

비동기 처리 설계의 핵심은 다음 세 가지다.

1. **수신과 처리를 분리한다**: API 서버는 빠르게 받고, 워커가 천천히 처리한다.
2. **큐가 버퍼 역할을 한다**: 트래픽 스파이크를 메시지 큐가 흡수하고, 컨슈머는 일정한 속도로 처리한다.
3. **실패를 설계한다**: DLQ, 재시도, 멱등성은 선택이 아니라 필수다.

비동기 아키텍처는 공짜가 아니다. 최종 일관성, 복잡한 에러 핸들링, 모니터링 부담이 뒤따른다. 하지만 그 비용을 감수할 때 얻는 **탄력성(Resilience)**과 **확장성(Scalability)**은 서버를 10대 더 올리는 것보다 훨씬 강력한 무기가 된다.
