# 데이터 메시(Data Mesh) 아키텍처와 분산 데이터 관리

## 개요

전통적인 중앙집중식 데이터 아키텍처는 조직이 성장할수록 병목현상이 심화된다. 데이터 엔지니어링 팀이 모든 도메인의 데이터 파이프라인을 관리하다 보면, 비즈니스 요구에 민첩하게 대응하기 어렵고 데이터 품질 책임 소재도 불분명해진다.

**데이터 메시(Data Mesh)**는 2019년 Zhamak Dehghani가 제안한 아키텍처 패러다임으로, 마이크로서비스가 애플리케이션 개발의 패러다임을 바꿨듯이 데이터 아키텍처를 탈중앙화하는 접근 방식이다. 핵심은 데이터를 도메인 팀이 직접 소유하고, 이를 "데이터 프로덕트"로 제공하는 것이다.

이 글에서는 데이터 메시의 4가지 핵심 원칙부터 실제 Spring 기반 백엔드 서비스에서 어떻게 구현할 수 있는지, 그리고 도입 시 고려해야 할 트레이드오프까지 실무 관점으로 살펴본다.

---

## 핵심 개념

### 데이터 메시의 4가지 원칙

#### 1. 도메인 중심 소유권 (Domain Ownership)
데이터는 해당 도메인 팀이 소유하고 관리한다. 예를 들어 주문 도메인 팀은 `order_events`, `order_history` 같은 데이터셋을 직접 생산, 관리, 제공한다. 중앙 데이터 팀에 의존하는 구조를 탈피한다.

#### 2. 데이터를 프로덕트로 (Data as a Product)
도메인이 제공하는 데이터는 단순한 파이프라인 결과물이 아니라 **프로덕트**다. 명확한 SLA, 스키마 버전 관리, 품질 지표, 문서화가 포함된다.

#### 3. 셀프 서브 플랫폼 (Self-serve Data Platform)
인프라팀은 도메인 팀이 데이터를 쉽게 생산하고 소비할 수 있는 플랫폼을 제공한다. 데이터 카탈로그, 스키마 레지스트리, 데이터 계보(lineage) 도구가 이에 해당한다.

#### 4. 연합 거버넌스 (Federated Computational Governance)
각 도메인은 자율적으로 운영되지만, 조직 전체 차원에서 데이터 표준(명명 규칙, 보안 정책, 품질 기준)을 준수한다. 중앙 통제 없이 글로벌 정책을 구현하는 것이 핵심이다.

### 중앙집중식 데이터 레이크 vs 데이터 메시

| 항목 | 중앙집중식 데이터 레이크 | 데이터 메시 |
|------|----------------------|------------|
| 데이터 소유 | 중앙 데이터팀 | 도메인 팀 |
| 확장성 | 수직 확장 한계 | 도메인 단위 수평 확장 |
| 민첩성 | 낮음 (병목 발생) | 높음 |
| 데이터 품질 책임 | 불명확 | 도메인 팀 책임 |
| 거버넌스 | 중앙 집중 | 연합(federated) |

### 2. 데이터 프로덕트 게시자 (Order Domain)

```java
@Service
@Slf4j
public class OrderDataProductPublisher {

    private final KafkaTemplate<String, OrderCreatedEvent> kafkaTemplate;
    private final DataProductMetricsCollector metricsCollector;

    private static final String TOPIC = "order.data-product.v1";

    public OrderDataProductPublisher(
            KafkaTemplate<String, OrderCreatedEvent> kafkaTemplate,
            DataProductMetricsCollector metricsCollector) {
        this.kafkaTemplate = kafkaTemplate;
        this.metricsCollector = metricsCollector;
    }

    public void publish(Order order) {
        OrderCreatedEvent event = buildEvent(order);

        kafkaTemplate.send(TOPIC, order.getId().toString(), event)
            .addCallback(
                result -> {
                    log.info("Data product published: orderId={}, offset={}",
                        order.getId(), result.getRecordMetadata().offset());
                    metricsCollector.incrementPublishCount(TOPIC);
                },
                ex -> {
                    log.error("Failed to publish data product: orderId={}", order.getId(), ex);
                    metricsCollector.incrementErrorCount(TOPIC);
                }
            );
    }

    private OrderCreatedEvent buildEvent(Order order) {
        DataProductMetadata metadata = DataProductMetadata.newBuilder()
            .setProducer("order-service")
            .setVersion("1.2.0")
            .setQuality("GOLD") // BRONZE, SILVER, GOLD 등 품질 등급
            .build();

        return OrderCreatedEvent.newBuilder()
            .setOrderId(order.getId().toString())
            .setCustomerId(order.getCustomerId().toString())
            .setOrderAmount(order.getTotalAmount().doubleValue())
            .setStatus(OrderStatus.valueOf(order.getStatus().name()))
            .setCreatedAt(order.getCreatedAt().toEpochMilli())
            .setMetadata(metadata)
            .build();
    }
}
```

### 3. 데이터 프로덕트 품질 검증

```java
@Component
public class DataProductQualityGate {

    private final DataQualityRuleRepository ruleRepository;

    // 데이터 품질 SLA 검증 - 퍼블리시 전에 반드시 통과해야 함
    public DataQualityResult validate(OrderCreatedEvent event) {
        List<String> violations = new ArrayList<>();

        // 필수 필드 검증
        if (StringUtils.isBlank(event.getOrderId())) {
            violations.add("orderId must not be blank");
        }
        if (event.getOrderAmount() <= 0) {
            violations.add("orderAmount must be positive");
        }

        // 비즈니스 규칙 검증
        if (event.getCreatedAt() > System.currentTimeMillis()) {
            violations.add("createdAt cannot be in the future");
        }

        // 품질 등급 결정 로직
        DataQualityGrade grade = violations.isEmpty()
            ? DataQualityGrade.GOLD
            : DataQualityGrade.BRONZE;

        return DataQualityResult.builder()
            .grade(grade)
            .violations(violations)
            .checkedAt(Instant.now())
            .build();
    }
}
```

### 4. 데이터 프로덕트 카탈로그 API

```java
@RestController
@RequestMapping("/api/v1/data-products")
public class DataProductCatalogController {

    private final DataProductRegistry registry;

    // 데이터 프로덕트 메타데이터 노출 - 셀프서브 플랫폼의 핵심
    @GetMapping
    public List<DataProductInfo> listDataProducts() {
        return registry.findAll();
    }

    @GetMapping("/{domain}/{name}")
    public DataProductInfo getDataProduct(
            @PathVariable String domain,
            @PathVariable String name) {
        return registry.findByDomainAndName(domain, name)
            .orElseThrow(() -> new DataProductNotFoundException(domain, name));
    }

    @GetMapping("/{domain}/{name}/schema")
    public ResponseEntity<String> getSchema(
            @PathVariable String domain,
            @PathVariable String name,
            @RequestParam(defaultValue = "latest") String version) {
        String schema = registry.getSchema(domain, name, version);
        return ResponseEntity.ok()
            .contentType(MediaType.APPLICATION_JSON)
            .body(schema);
    }

    @GetMapping("/{domain}/{name}/lineage")
    public DataLineageGraph getLineage(
            @PathVariable String domain,
            @PathVariable String name) {
        // 데이터 계보(lineage) 반환 - 어떤 소스에서 어떻게 변환되었는지
        return registry.getLineage(domain, name);
    }
}
```

### 5. 연합 거버넌스 정책 적용

```java
@Aspect
@Component
public class DataGovernancePolicyAspect {

    private final GlobalPolicyValidator globalPolicyValidator;
    private final DataClassificationService classificationService;

    // 모든 데이터 프로덕트 퍼블리시에 글로벌 정책 적용
    @Around("@annotation(DataProduct)")
    public Object enforceGlobalPolicy(ProceedingJoinPoint pjp) throws Throwable {
        Object[] args = pjp.getArgs();

        for (Object arg : args) {
            if (arg instanceof DataProductEvent event) {
                // PII 데이터 마스킹 정책
                DataClassification classification =
                    classificationService.classify(event);

                if (classification == DataClassification.PII) {
                    applyPiiMasking(event);
                }

                // 글로벌 데이터 보존 정책 메타데이터 추가
                globalPolicyValidator.attachRetentionPolicy(event);
            }
        }

        return pjp.proceed();
    }

    private void applyPiiMasking(DataProductEvent event) {
        // SHA-256 해싱으로 PII 필드 마스킹
        event.maskPiiFields();
    }
}
```

## 주의사항 및 트레이드오프

### ⚠️ 데이터 중복과 일관성 문제

데이터 메시에서 각 도메인이 독립적으로 데이터를 소유하므로 **데이터 중복**은 필연적이다. 예를 들어 주문 도메인과 정산 도메인이 각각 고객 정보를 보유할 수 있다. 이때 "고객의 주소가 변경되면 어떻게 되는가?"라는 질문이 핵심 문제가 된다.

```java
// 이벤트 기반 동기화로 중복 데이터 최신화
@KafkaListener(topics = "member.data-product.v1")
public void onMemberUpdated(MemberUpdatedEvent event) {
    // 로컬 캐시/DB의 고객 정보 갱신
    // Eventually Consistent 방식 - 즉각적인 일관성은 포기
    localCustomerStore.updateSnapshot(event.getCustomerId(), event);
}
```

**Eventually Consistent** 모델을 수용해야 하며, 강한 일관성이 필요한 도메인에서는 데이터 메시가 적합하지 않을 수 있다.

### ⚠️ 운영 복잡도 증가

| 구분 | 중앙집중식 | 데이터 메시 |
|------|-----------|------------|
| 스키마 관리 | 단일 스키마 | 도메인별 스키마 + Schema Registry |
| 모니터링 | 단일 파이프라인 | 도메인별 SLA 모니터링 |
| 장애 대응 | 중앙팀 책임 | 도메인팀 책임 (교육 비용) |
| 초기 도입 비용 | 낮음 | 높음 |

### ⚠️ 도메인 경계 설정의 어려움

마이크로서비스와 동일하게, 데이터 메시도 도메인 경계를 잘못 설정하면 오히려 복잡도만 늘어난다. **DDD(Domain-Driven Design)**의 바운디드 컨텍스트 개념을 데이터 소유권에 먼저 적용하는 것이 중요하다.

### ⚠️ 조직 문화의 성숙도가 필수

기술보다 **조직의 준비도**가 더 중요하다. 도메인 팀이 데이터 품질에 책임감을 가지지 않으면, 데이터 메시는 "아무도 책임 안 지는 분산 데이터 카오스"가 된다. 도입 전 Data Ownership 문화를 먼저 정착시켜야 한다.

## 정리

데이터 메시는 **기술 솔루션이 아닌 조직 패러다임**이다. 성공적인 도입을 위해서는 다음 순서를 권장한다.

1. **도메인 경계부터 명확히** - DDD 기반으로 데이터 소유권을 먼저 정의
2. **파일럿 도메인 선정** - 데이터 성숙도가 높고 오너십 의지가 있는 팀 선택
3. **셀프서브 플랫폼 우선 구축** - Schema Registry, 데이터 카탈로그, 품질 모니터링 도구
4. **점진적 확대** - 성공 사례를 기반으로 다른 도메인으로 전파

마이크로서비스 전환과 마찬가지로, 무조건 전면 도입보다는 **현재 조직의 데이터 성숙도와 규모**를 냉정히 평가한 후 접근하는 것이 핵심이다. 팀이 5개 이하이거나 데이터 파이프라인 복잡도가 낮다면, 오히려 단순한 중앙집중식 아키텍처가 더 효율적일 수 있다.

데이터 메시는 "데이터가 조직의 핵심 자산이 되고, 도메인 팀이 그 가치를 직접 책임지는 구조"로 전환할 준비가 된 조직에게 강력한 경쟁력을 제공한다.
